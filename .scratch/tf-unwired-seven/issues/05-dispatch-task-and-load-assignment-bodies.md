# 派送任务与装载分配的本体——今天只有引用，没有被引用的那个东西

Category: enhancement
Status: resolved——两个本体各四层齐（表 + 重建门 + 端口 + 编排 + 真库适配器），棘轮两行都剪了；
变化与撤回的**入口**未接，不在本票判据内，理由见文末
Blocked by: 无

## 症状

生产代码里流转着指向从未被创建过的东西的引用：

| 引用（**有**生产调用点） | 本体（**零**生产调用点） |
|---|---|
| `NewDispatchTaskReference`（`perform_offsite_pickup.go`） | `OpenDispatchTask` |
| `NewLoadAssignmentReference`（`prepare_transport_opportunity.go`） | `FormLoadAssignment` |

一个尝试声称自己属于某个派送任务，而那个任务在系统里不存在；一次容量准备引用一份装载分配，
而分配从未形成。

## CONTEXT 要求什么

装载分配：

> 把明确载运对象安排到具体班次、运输资源或载运位置的执行意图。装载分配不证明节点已经完成
> 物理装载，也不证明运输控制已经转移。

> 运输委托、订舱、容量预占、承运接受和装载分配分别拥有业务身份、对象范围、数量、条件和
> 生命周期。任一对象的成功、失败或取消不能被压缩成其他对象的状态。

> 同一业务范围从申请、确认、预占、分配到实际使用时，沿明确关系转换数量；承运接受、装载分配
> 和实际装载不得把同一容量重复累计。

> 装载分配失败不自动使逻辑路由失效。同一线路仍有满足时间窗口和客户承诺的后续机会时，可以
> 重新分配。

派送任务（领域 `DispatchTaskSpec` 已实现的不变量）：工作范围不等于到场、改约不改身份、
关闭带依据且一次为限。

## 现状（锚 `9d6063c`）

领域 `domain/dispatch_task.go` 与 `domain/load_assignment_movement.go` 都有完整实现与测试。
**两者均无表、无端口、无编排。**

## 要做的

两张表两组端口，**分票做也可以**（本票内两件无相互阻塞，只是同族）。

**装载分配的关键约束**：分配版本链（`corrects` / `revisedAt`）与撤回（`withdrawn`）在领域里
已经建模，库面要跟上，**不得用 UPDATE 表达更正**。数量守恒那条尤其要小心：CONTEXT 要求申请量、
接受量、预占量、分配量、释放量、实际装载量**分别保存**，不要为了少几列把它们同步成一个
最终数字——「消除超配、短装或差异」是 CONTEXT 明禁的。

**派送任务的关键约束**：改约不改身份（改约形成新窗口而非新任务）、关闭带依据一次为限
（关闭列与依据列同在或同缺，且已关闭不可再关）。

## 陷阱

- 别把装载分配的状态压进班次或容量池的状态。CONTEXT 明说「任一对象的成功、失败或取消不能被
  压缩成其他对象的状态」。
- 别让分配失败去改路由。CONTEXT 明说它「不自动使逻辑路由失效」，重评是另一条路且有前置条件。

## 完工判据

`OpenDispatchTask` 与 `FormLoadAssignment` 各自有生产调用路径，棘轮基线两行可剪。

  **票面点名的两组关键约束，逐条交代：**

  **派送任务——改约不改身份、关闭带依据一次为限。** 表上**没有版本维**，主键就是（租户 + 任务）：
  改约只换窗口，领域原话是「改约或重派形成的是新**尝试**，不是新任务」。关闭三件与状态成组，
  库内 CHECK 与重建门各守一遍——半截会装回一个「关了但说不出依据」的任务，而**没有依据的关闭与
  「一次失败尝试自动结束任务」在库里分不开**，后者正是 CONTEXT 明禁的那条。

  **装载分配——版本链不得用 UPDATE 表达。** 主键**带版本**，写入只插不改；变化与撤回各自形成新
  版本、原版本原样保留。一条真库测试专门钉它：变化之后回读前一版，成员集仍是原来那两个。成员表
  主键也带版本，每版各存一份自己的成员集——共享前身那一份就等于改前身，两版之间差了哪些对象也就
  读不出来了。

  **数量守恒那条落到这两张表上的实际含义，与票面字面不同，写清楚**：`LoadAssignment` 与
  `DispatchTask` 身上**都没有数量字段**——申请量、接受量、预占量、分配量、释放量、实际装载量六个量
  在容量池那一侧（`0004` 已建）。所以这里要守的不是「别把六个量压成一个」，而是**别在这两张表上存
  成员计数列**：存了它会与成员行漂移，而漂移时没有任何东西会报。两张表都没有那一列。

  **陷阱两条都守住了**：分配状态没有压进班次或容量池（两张表各自独立，无任何回写）；分配失败不改
  路由（本票根本没有通往路由的边）。

  **动笔时发现领域少一个访问器**：`LoadAssignment.revisedAt` 一直存着却从不交出来，于是在此之前
  **没有任何东西能持久化或断言它**。不补的话变化版本往返之后会退化成首版，而重建门会因「有前身却
  没有变化时刻」把它拒掉。已补 `RevisedAt()`，与 `Withdrawn()` 同形。

  **未做且不在本票判据内**：变化（`ReviseMembers`）与撤回（`Withdraw`）的**入口**没有接。领域与库面

  分配」。本票判据只到两个导出工厂上生产调用路径 + 棘轮两行剪掉，那三样都齐了。
