# 实际履约段登记册——CONTEXT 的定义性边界今天在生产路径上跨不过去

Category: enhancement
Status: draft
Blocked by: 无

## CONTEXT 要求什么

> 载运对象通过有效收寄或权威交接进入运输方控制时，其履约参与关系和适用实际履约段才成立。
> 扫描、订舱确认、承运接受、列入总单或舱单、车辆到场、装载分配和物理装载中的任一单项均不能
> 替代该边界。

其它约束：

> 实际履约段是共同执行与控制责任范围；一个实际履约段可以承载多个载运对象，每个对象必须通过
> 履约参与关系分别关联自己的计划履约段、控制起止和结果。

> 实际履约段持续到载运对象形成有效交付、下一次权威交接或其他明确结束当前运输控制的有效事实。
> 达成计划、中断、折返、提前终止和异常转交必须保留不同结果，不能全部写成「已完成」。

> 已经成立的实际履约段及履约参与关系不能被取消、删除或回写为未发生。来源证据被更正时，
> 保留原事实和原判断，形成失效、替代及重新派生结果。

## 现状（锚 `9d6063c`）

领域 `ActualFulfillmentSegment` 与 `FulfillmentParticipation` 在
`domain/actual_fulfillment_segment.go`，有测试。**无表、无端口、无适配器、无编排。**

## 要做的

**表**：新开 `migrations/transport_fulfillment/0006_...`（当前最大 `0005`，不改旧迁移）。
段与参与关系分两张表——CONTEXT 明说一段承载多对象且每个对象**分别**成立、结束、更正，
压成一张表就表达不出成员差异。

**约束要跟上**，否则建了表等于没建：
- 段的成立来源只能是有效收寄或权威交接二者之一，且必须留下是哪一条（封闭词表 + 引用列）。
- 结束结果是封闭多值，**不得只有「已完成」**：达成计划 / 中断 / 折返 / 提前终止 / 异常转交
  各占一格。
- 不可回写：更正走新版本或失效—替代关系，**不 UPDATE 原行**。是否沿用本仓已有的修订式登记
  （`party_commercial` 0015 四表那套）须一并裁。
- 实际承运商**可以待确认**（CONTEXT：「实际承运商可以在实际履约段成立时仍处于待确认」），
  所以该列可空，且「待确认」与「无」要分得开。

**端口**：段登记册的存与取，形状照本上下文既有的 `*Store` / `*Registry`（`FindByKey` + `Save`
+ 明确的 `SaveOutcome`）。

**适配器**：postgres 实现，重建时逐字段走构造门。

## 边界

本票**只建册，不接入口**——两条立段入口进现有编排是[票 02](./02-establish-segment-from-pickup-and-handover.md)。
分开是因为建册可以独立验绿，而接入口会碰两例现有编排，风险不同。

**本票原写「不动领域模型」，那一句作废**（2026-09-02 更正，理由见下方 Comment 第二条）：
建册必须同时开一个重建入口，那是领域侧的新增。改动仍限于**新增**符号，不动任何既有签名。

## 完工判据

段与参与关系可以从生产路径登记并取回；棘轮基线上两条立段入口**仍在名单上**（它们由票 02 剪）。

## Comments

- 2026-09-02 · MCP-3：**读过领域模型了，建表形状基本由它决定，记下来免得下一个人重读一遍。**
  锚 `9661108`。领域层比本票正文预想的更完整——CONTEXT 那条「分别成立、结束、更正」已经
  被实现成了类型本身，不需要在表上再发明。

  **两张表，字段直接照领域取**：

  - 段（`ActualFulfillmentSegment`）：租户、段引用、`closed`、`closedAt`。段本身很薄，
    重量全在参与关系上。
  - 参与关系（`FulfillmentParticipation`）：租户、段引用、对象引用、计划段引用、
    入场种类、入场依据、入场时刻、离场种类、离场依据、离场时刻。

  **四条约束，每条都有领域侧的原话可引**：

  1. **入场种类是封闭二值**（`EnteredByOffsitePickup` / `EnteredByTransportHandover`）。
     领域注释写着「刻意没有第三格——扫描、装载、订舱确认都立不起参与」。库面镜像这个封闭集。
  2. **离场种类是封闭三值**（有效交付 / 下一次权威交接 / 明确控制终止）。领域注释：
     「中断、折返、异常案件不在其中——它们不结束控制」。**别为了省事加一个「其它」**。
  3. **离场三件同在或同缺**（种类、依据、时刻）——`Active()` 就是按 `endedAt.IsZero()` 判的，
     库面半截会让装载重建出一个既非在场又非离场的参与。形状照本仓既有的耦合 CHECK。
  4. **计划段引用可空，且「可缺席」是有依据的缺席不是数据缺失**。领域注释：「明确允许待路由
     的产品在没有可行候选时照样实际揽收，计划段此刻不存在」。所以是 NULL 而不是空串，
     且注释要写明这一格的含义，否则下一个人会当它是脏数据去补。

  **一条 SQL 表达不了、要留给领域的**：`ErrSegmentStillActive`——仍有有效参与关系时段结束
  不了。跨行的条件用 CHECK 写不动，硬写成触发器会把这条不变量分裂成两个口径。**留在领域，
  并在迁移注释里写明为什么这一条不下沉**，与本仓「不为同一形状立第二个口径」的既有做法一致。

  **端口形状**照本上下文既有的 `*Registry`：`FindByKey` + `Save` + 明确的 `SaveOutcome`
  三值。段的幂等键是（租户 + 段引用），参与关系挂在段下按对象唯一。

  **下一步**是写红测试再落迁移。本票仍 `draft`，未占号到具体人。

- 2026-09-02 · MCP-3：**本票还缺一件，而且它推翻了本票自己写的一条边界：实际履约段没有
  重建入口，建册必须先补上它。**

  `internal/transportfulfillment/domain/` 下已有五个重建入口——`RehydrateTransportHandover`、
  `RehydrateCapacityPool`、`RehydrateTransportCommission`、`RehydrateCarrierAcceptance`、
  `RehydrateEffectiveDelivery`——**唯独 `ActualFulfillmentSegment` 没有**。而按 ADR-0028
  构造与重建是两扇门：`EstablishSegmentWith*` 是构造门（从零创生、每条不变量当场算），
  从库里读回一个已经成立的段走不了它，因为那会重放「首个对象立段」的语义。

  所以本票正文那句「不动领域模型」是我在不知道这件事时写的，**已就地作废**。新增仍限于
  新增符号（`RehydrateActualFulfillmentSegmentSpec` + 入口函数），不动任何既有签名。

  **重建门要验什么，照 TF 既有五扇的做法**：验形状与成对关系，**不重走转换门**。具体到段：
  逐条参与关系的入场三件必须齐、离场三件同在或同缺、封闭集取值在集内、`closed` 与
  `closedAt` 成对；**但不重放 `JoinWith*` 也不重算 `ErrSegmentStillActive`**——
  `RehydrateCapacityPool` 的注释把这条理由写得最清楚：「读回已有预占不能重放
  Reserve/Release/Consume：那三条是转换门，有效期与装载分配是调用期依据，不是行上的事实」。

  **一处要当心的**：段是值类型且参与关系是未导出切片，重建入口必须能设它——这意味着入口
  只能待在 `domain` 包内（与 `parcel-shipment` 那扇门当年排除掉「入口放新包」的理由一字
  相同：包外设不了未导出字段）。`internal/architecture/rehydration_gate_test.go` 那道门禁
  **只作用于 `parcel-shipment`**（`rehydrationSurfaceFile` 与 `aggregateTypeName` 都写死在
  那个上下文），所以 TF 这一侧靠的是惯例不是门禁——**这本身是一处值得单独裁的缺口**，
  但不在本票范围内，别顺手扩。
