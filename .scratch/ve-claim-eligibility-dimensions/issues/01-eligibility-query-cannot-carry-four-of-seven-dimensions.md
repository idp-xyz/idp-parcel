# 资格审核七维里有四维进不了 EligibilityQuery，而 Screen 是一次性二值

Category: bug
Status: needs-triage

发现于 `EligibilityRuleView` 换真时。适配器已按当下端口把**能答的那一维**做实并提交，
本票记的是剩下四维为什么答不了，以及为什么"先凑一个答案"在这个端口上是不可逆的。

## CONTEXT 要求的七维与查询实际交出的维

CONTEXT 硬句：「按申请人授权、客户账户、合同版本、索赔时限、目标范围、重复关系和
最低材料要求判断资格」。`ports.EligibilityQuery` 交出的是
`{Batch, Item, Customer, Contract, Target, Kind}`。

| 维 | 查询里有吗 | 答得了吗 |
|---|---|---|
| 客户账户 | 有 | 作为键 |
| 合同版本 | 有（ContractScopeReference） | 作为键 |
| 目标范围 | 有 | 作为键 |
| 索赔类型 | 有 | **能答**——已实现 |
| 索赔时限 | **没有** | 查询不带任何时间戳；`ClaimItem.SubmittedAt()` 在聚合上有但没进查询，且还需起算事件与业务日历 |
| 申请人授权 | **没有** | 查询只有客户账户，申请人与账户不是一回事 |
| 最低材料要求 | **没有** | 证据是另一个聚合（`evidence.go`） |
| 重复关系 | **没有** | 要查同租户下已有索赔项，那是 `ClaimStore` 的数据 |

后两样尤其不该由视图补：目录答「规则是什么」，仓储答「事实是什么」；让视图去读仓储
就造出一个既是目录又能读业务数据的东西。

## 为什么不能"先凑一个答案"

`domain.EligibilityScreen` 是封闭二值（`ClaimEligible` / `ClaimIneligible`），而
`ClaimItem.ScreenEligibility` 是一次性的——`ErrClaimAlreadyScreened` 挡住重审。

于是：

- 因为"证不了"而答 `ClaimIneligible` → 该索赔**被永久拒掉且再也审不了**。这正是
  CONTEXT「默认受理与默认拒赔都是虚构」所禁的，且不可逆。
- 因为"这一维过了"而答 `ClaimEligible` → 把四维未核的索赔永久标成已过审。

对照 `parcel-shipment` 的 `IntakeEligibilityView`：它能如实答「未成立」并点名头一项
缺口，是因为它有**第三格且可续办**（`AT-PS-047` 那条路）。这里没有那一格。

## 还有一处二值与 CONTEXT 对不上

CONTEXT 生命周期写明「资格审核 → **等待补充**、不予受理或进入责任审核」，并要求
「资料不足时，索赔项进入限期补充，并固定缺少材料、补充范围、通知依据和当前截止时间」。
当前二值里没有「等待补充」这一格，而它恰恰是资料维不足时该走的那一格。

## 当下实现停在哪

- 合同的索赔声明不在场 → `found=false`
- 声明在场且该类型**不在**覆盖集合内 → `ClaimIneligible` 带依据。这一判定完整且
  永久成立：承担与否不随材料补充而变，变了就是换了合同范围，而换范围按 CONTEXT
  是另一个索赔项。
- 声明在场且类型在保 → 仍 `found=false`。端口把 `found=false` 定义为「资格目录未
  配置」并点名它含索赔时限、材料要求与授权目录——那三样确属 `PAR-VIS-08` 待提供，
  所以这一格是如实的。

也就是说：**即使 `PAR-VIS-08` 全部到位，这个端口按当前形状仍然答不全。**

## 要动哪一侧，未定

本票不拍方案，只列两侧各自要动什么：

- **查询加维**：至少补 `SubmittedAt` 与申请人身份。但重复关系与材料仍在别处，加维
  解决不了那两样。
- **拆职责**：目录只给规则（时限规则版本、最低材料清单、授权目录），由编排根据
  `ClaimStore` 与证据聚合逐维核对。这一路能把「规则是什么」与「事实是什么」分开，
  但会把资格审核从一次端口调用变成一段编排。
- **答复加格**：`EligibilityScreen` 是否要有「等待补充」，牵动 `ScreenEligibility`
  的一次性语义与 `ClaimItem` 的状态形状——那是领域改动。

三者可能要一起定，因为第三条决定了前两条的结果往哪儿放。
