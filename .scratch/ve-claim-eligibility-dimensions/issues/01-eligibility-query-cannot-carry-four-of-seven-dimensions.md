# 即使 PAR-VIS-08 全部到位，EligibilityRuleView 仍然答不全——缺的是维，不是参数

Category: bug
Status: in-progress

**结论先写在这里**：这个端口答不全，不是因为租户还没登记实例参数。就算 `PAR-VIS-08`
把索赔时限、最低材料与授权目录全部登记齐备，`ports.EligibilityRuleView.ScreenClaim`
按当前形状仍然作不出一次完整的资格审核。缺的是查询维、职责边界与答复代数三样，都要
改形状才补得上。

发现于 `EligibilityRuleView` 换真时（`5a1eded`）。适配器已按当下端口把**能答的那一维**
做实并提交——合同责任范围承不承担这个索赔类型；本票记的是剩下的为什么答不了。

## 一、查询缺两维

CONTEXT 硬句：「按申请人授权、客户账户、合同版本、索赔时限、目标范围、重复关系和
最低材料要求判断资格」。`ports.EligibilityQuery` 交出的是
`{Batch, Item, Customer, Contract, Target, Kind}`。

| 维 | 查询里有吗 | 答得了吗 |
|---|---|---|
| 客户账户 | 有 | 作为键 |
| 合同版本 | 有（ContractScopeReference） | 作为键 |
| 目标范围 | 有 | 作为键 |
| 索赔类型 | 有 | **能答**——已实现 |
| 索赔时限 | **没有** | 查询不带任何时间戳；`ClaimItem.SubmittedAt()` 在聚合上有但没进查询，且还需起算事件与业务日历 |
| 申请人授权 | **没有** | 查询只有客户账户，申请人与账户不是一回事 |
| 最低材料要求 | **没有** | 见第二节 |
| 重复关系 | **没有** | 见第二节 |

## 二、有两维根本不在目录里，可能整个形状就选错了

重复关系要查同租户下已有的索赔项，那是 `ClaimStore` 的数据；最低材料要看该索赔已提交
的证据，那是证据聚合（`evidence.go`）的数据。**两样都不是目录行，给目录加维也加不出来。**

让视图去读仓储可以让它"答得全"，但那会造出一个既是目录又能读业务数据的东西——目录
本该只答「规则是什么」，仓储答「事实是什么」。因此真正的出路可能不是给这个端口补维，
而是**把资格审核拆成「目录给规则 + 编排逐维核对」**：目录交出时限规则版本、最低材料
清单与授权目录，编排拿着它们去 `ClaimStore` 与证据聚合逐维核对。那样两类知识各归各位，
代价是资格审核从一次端口调用变成一段编排。

## 三、二值一次性的 Screen 与 CONTEXT 直接矛盾

这一条分量最重，且与前两节无关——**就算查询维补齐、职责也拆对了，它依然存在。**

CONTEXT 生命周期明写：「资格审核 → **等待补充**、不予受理或进入责任审核」，并要求
「资料不足时，索赔项进入限期补充，并固定缺少材料、补充范围、通知依据和当前截止时间」，
还专门规定了补充期限届满的复核后果与「不能默认拒赔」。

而 `domain.EligibilityScreen` 是封闭二值——`ClaimEligible` / `ClaimIneligible`，
**没有「等待补充」那一格**。偏偏它正是资料维不足时 CONTEXT 指定要走的那一格。

叠加 `ClaimItem.ScreenEligibility` 的一次性（`ErrClaimAlreadyScreened` 挡住重审），
后果是不可逆的：

- 因为"资料还不足"而答 `ClaimIneligible` → 该索赔**被永久拒掉且再也审不了**，而
  CONTEXT 恰恰要求这种情形进入限期补充、届满才复核后果、且不得默认拒赔。
- 因为"这一维过了"而答 `ClaimEligible` → 把其余维未核的索赔永久标成已过审。

对照 `parcel-shipment` 的 `IntakeEligibilityView`：它在证据取不到时能如实答「未成立」
并点名首项缺口，是因为它有**第三格且可续办**（`AT-PS-047` 那条路）。两边看着同形，
分界在答复代数上——**把那份写法搬到这里会变成不可逆的默认拒赔**，而编译与测试都不会拦。
适配器注释里已就地记下这一点。

## 四、当下实现停在哪

- 合同的索赔声明不在场 → `found=false`
- 声明在场且该类型**不在**覆盖集合内 → `ClaimIneligible` 带依据。这一判定完整且
  永久成立：承担与否不随材料补充而变，变了就是换了合同范围，而换范围按 CONTEXT
  是另一个索赔项。
- 声明在场且类型在保 → 仍 `found=false`。端口把 `found=false` 定义为「资格目录未
  配置」并点名它含索赔时限、材料要求与授权目录——那三样确属 `PAR-VIS-08` 待提供，
  所以这一格是如实的，不是搪塞。

## 五、要动哪几侧，未定

三条候选出路，本票不拍：

- **查询加维**：至少补 `SubmittedAt` 与申请人身份。解决第一节，解决不了第二、三节。
- **拆职责**：目录给规则，编排根据 `ClaimStore` 与证据聚合逐维核对。解决第二节。
- **答复加格**：`EligibilityScreen` 增「等待补充」，牵动 `ScreenEligibility` 的一次性
  语义与 `ClaimItem` 的状态形状（补充期限、缺少材料、通知依据都要有落点）。解决第三节。

三者大概要一起定：**第三条决定前两条核出来的结果往哪儿放**——没有「等待补充」那一格，
逐维核对得到的「这一维还差材料」依然无处安放。
