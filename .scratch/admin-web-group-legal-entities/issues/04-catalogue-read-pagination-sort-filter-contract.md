# 04 目录读口分页 / 排序 / 筛选下推的契约决策

Category: enhancement
Status: ready-for-agent——2026-09-24 用户授权通道 3 自决（见「裁决」节）；下一步起草 ADR 并拆逐册实施票。此前 needs-info（归 owner：这是全部目录读口的契约形状，一决策一处定义，要先出 ADR 或设计交接）
Blocked by: 无
Type: grilling

## 问题

十个上下文的目录读口（`GET /commercial-*`、`/network-*`、`/pricing-*`……）今天都是一次拉全量，`isolatedReadLimit = 200`
是唯一上限，无 `page` / `sort` / 过滤参数；管理台 README「列表页上列通则」明写「过滤只在已取回的数据上做，不下推成新查询参数
——那要改端点契约」。演示种子量级下够用，主数据规模上去（一个租户几百个货主客户账户、上千条网络版本行）就不够。

## 要裁的

1. **分页形状**：偏移分页（`page`/`pageSize`）还是游标分页（`after=<登记时间,标识>`）。登记册按修订版本化、只增不改，
   游标分页在这类只增表上稳定（不会因为新插入而漏行或重行）；偏移分页操作者更熟。
2. **排序维**：封闭集（每册点名可排的列）还是任意字段。封闭集与 `MALFORMED_REQUEST`「查询参数不在服务端接受的封闭集合内」
   那条既有纪律同形。
3. **筛选下推**：只放状态一维，还是开放到每列。
4. **答复形状**：`{ outcome, entities, page: { total, next } }`——`total` 在大表上要不要给（COUNT 的代价）。
5. **一次改全部读口还是逐册**：`ListPageTemplate` 已留 `pagination` 槽，前端一次接上；后端十个上下文各自的读适配器逐个改。

## 不裁的

- 不改任何登记写面。
- 不改 `isolatedReadLimit` 的含义：它是隔离形态的上限，不是分页。

## 产出

一份 ADR（或若 owner 判为实施细节则设计交接）+ 拆成逐上下文实施票。本票在 owner 裁前不动代码。

## 裁决（2026-09-24，用户授权通道 3 自决）

用户 2026-09-24 经 IDP 队列授权（「你能帮我自决吗，你是业务和系统专家」）。「要裁的」五问逐条定；产出照「产出」节不变。

1. **分页：游标（keyset）。** 游标由「排序键 + 标识」编成、对客户端不透明，答复只给 `next`。登记册按修订版本化、只增不改，默认序又是登记时间
   倒序——偏移分页在翻页期间一有新登记，就会把行挤到下一页重出一次、或让行漏掉，而操作者逐条复核时恰恰不能漏；游标在只增表上天然稳定，走索引
   也不随页码变慢。同一份契约将来还要服务包裹 / 委托这类量级大得多的列表，一决策一处定义，不给目录读口单开一套。代价：不能跳到第 N 页——操作者
   找行靠筛选与关键词，不靠页码。
2. **排序：每册点名的封闭集。** 可排的维由各册自己列出，越界照既有 `MALFORMED_REQUEST`「查询参数不在服务端接受的封闭集合内」拒；每个排序维都
   以标识作决胜键，游标才稳定。默认序为登记时间倒序。
3. **筛选下推：每册点名的封闭集维度 + 一个统一关键词 `q`。** 维度至少含状态，其余由各册按自己的关键标识 / 种类点名，不开放任意字段。`q` 在该册
   点名的文本列上做包含匹配，与管理台地址上的检索词同名（`admin-web-workspace-form/06` 定检索词进地址的 `?q=`）：读口支持之后前端把地址上的
   `q` 原样下推，客户端筛选随之退场。
4. **答复：`page: { next, total }`。** 目录读口给精确 `total`——登记册按租户读，租户级规模上 `COUNT` 便宜，而「共 N 条」是操作者判断筛得对不对的
   依据。契约允许将来的大表读口显式给 `null`，客户端见 `null` 就不显总数，不去猜。
5. **推进：契约一次定，读口逐册迁。** 一篇 ADR 定契约形状与错误口径，服务端出一份共用的游标编解码与参数校验件；逐册迁移按规模先到的先改，客户
   账户与网络版本打头。`ListPageTemplate` 的 `pagination` 槽加游标模式（上一页 / 下一页 + 总数），前端一次接。`isolatedReadLimit` 含义不变，只作
   每页条数的天花板。

下一步：起草上述 ADR，再按上下文拆实施票。本裁决不改任何登记写面。
