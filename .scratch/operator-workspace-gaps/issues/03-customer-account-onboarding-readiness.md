# 03 开户就绪清单：一个货主客户账户离「能下委托」还差哪几册

Category: enhancement
Status: draft
Blocked by: 无
出处：[spec](../spec.md) 缺口三。

## 为什么

给一个货主开户，要在参与方、货主客户账户、客户合同、结算政策、信用政策、接单规则包、价格政策与定价方案绑定等若干册上各登一笔。漏了哪一册，
今天要等第一单委托被拒才知道，而拒绝原因落在接受判断里，离「去补哪一册」隔着好几步。原型的做法是新账户先暂停、配置完整才启用，
并在列表上挂「待配置」；本仓不照搬那套状态，但「开户之前就看得见缺什么」这件事值得做。

## 已有的（取证钉 main `71e41e6d`）

- `UC-PC-002` 的商业依据解析对零匹配、重叠多匹配、证据不足分别答无适用依据、适用冲突、解析未决，不以客户级默认值补齐——答案本身就是清单的原料。
- 缺的：解析只在进程内被接受判断调用，`internal/partycommercial/adapters/http` 与 `cmd/parcel-api` 没有对外的解析读口
  （唯一带 resolution 的是法人资料按时点解析 `/commercial-group-legal-entities/{legalEntityId}/profile-resolution`，不相干）。

## 动手前要定的

1. **问的是什么**：给定客户账户、服务产品与一个商业选择锚点，逐项解析会用到的商业版本，列出每一项是已解析、无适用依据、适用冲突还是解析未决。
   锚点由谁给、给不给默认——不给默认（红线），页面让操作者显式选。
2. **范围边界**：只列 party-commercial 自己拥有的那几项；接受前财务控制的实际结果归 `settlement-accounting`、可达性归 `network-routing`，
   清单上如要出现，只能读它们各自的判断口，不在这里重算。
3. **不落账**：这次解析不形成任何接受判断、不写解析登记，与接受链上的解析分开，免得清单一刷就长出业务事实。可能要一篇 ADR 定「只读解析」的形状。

## 形态

碰 Go 与端点表，走并行会话那条路；管理台可挂在「客户与合同」页的客户账户行详情里，端点落地后另拆前端切片。
