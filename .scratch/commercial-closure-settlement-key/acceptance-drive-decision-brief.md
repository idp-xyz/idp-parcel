# 接受判断由什么驱动——票 03 的前置裁决简报

- 供裁对象：[票 03](./issues/03-acceptance-chain-has-no-assembly-point.md)「要先裁的一件事」。票面原话：这一裁决够一份 ADR——它决定接受判断在产品上是「被请求的」还是「被触发的」。
- 本文性质：**简报不是裁决**。证据与建议在此，裁决等用户点头（或授权后另开 ADR 落档）。
- 取证锚：`1f0d18f`（工作树已核干净）。执行方 MCP-2，2026-08-27。

## 要裁的一问

提交落库之后，接受判断链（推进可达性与财务控制判断、形成接受/拒绝决定，即
`AdvanceAcceptanceJudgmentHandler` / `AdvanceFinancialControlJudgmentHandler` /
`FormAcceptanceDecisionHandler` 三个编排）由什么推进：

- **路 A · HTTP 命令端点**——调用方显式请求推进一次，与提交/撤回/取消三条命令面同形；
- **路 B · 信封驱动**——提交落库即交出「委托已提交」意图，`cmd/parcel-dispatch` 消费门推进，与既有十二类消费者同形。

## 证据面

### 一、用例已经把驱动语义说死了

- UC-PS-001 步骤 8：「适用硬规则和所需判断全部通过时**自动接受**；规则显式要求时进入人工复核；授权角色可以依据结构化原因主动拒绝」。
- `AT-PS-033`：「系统自动形成接受决定；**不等待无依据的人工审批**，也不允许操作员重复接受」。
- `AT-PS-008`（商业或路由依赖超时）：「已建立委托保持已提交，并通过独立接受判断任务**安全续办**」；`BD-PS-001` 要求客户补缺与系统重试**分开续办路径**。

接受判断在用例里是提交之后的**自动推进**，未决靠**系统重试续办**。路 A 必须虚构一个用例里不存在的外部调用者；路 B 的 inbox 重投正是「系统重试续办」的既有形态。

### 二、机制半边的半成品都躺在信封侧

| 件 | 现状 |
|---|---|
| 出站意图 | `ports.ShipmentRequestSubmittedHandoff` 与 `OutboxShipmentRequestSubmittedHandoff`（事件类型 `parcel-shipment.shipment-request.submitted`）**已实现、有真库用例、零生产调用方**——生产提交编排今天五参无 Downstream（`assemble_submission.go`），信封根本没发过 |
| 下游先例 | 接受**决定**的出站已接线并被消费（`acceptance_decision_handoff` → NR 初始路由，调度器路由表首条）；FanOut、未决哨兵按路翻译、毒丸拒收等消费门机制全部有先例 |
| 三编排 | 已实现、有测试，`cmd/` 下唯一构造点是 `synthetic_v0_test.go`（测试内直连调用模拟装配） |
| 相邻勘察 | `.scratch/outbox-handoff-consumption-map/next-consumer-survey.md` 第 6 条早已点名：`reachability-judgment.formed` → PS 续办属「建模先行」，**事件半边与同步半边的分工无 UC 明文**——本裁决正是把这一格一并答掉的机会 |

路 A 则要在 `ADR-0055` 的未配置端点面上**再开一条端点**，而那个面语义上是「租户接入渠道的客户动作」——接受判断不是客户动作，混进去会让「渠道未配置」这句话对它失真。

### 三、两条路逐维对比

| 维 | 路 A · HTTP 端点 | 路 B · 信封驱动 |
|---|---|---|
| 与 UC 语义 | 冲突：自动接受不等外部命令 | 贴合：提交即触发、未决续办 |
| 失败/重试 | 调用方重发；「谁来调」成新的实例半边问题 | inbox/outbox 续办，哨兵按路翻译有先例 |
| 装配代价 | 新端点 + 未配置面枚举加行 + 一个不存在的调用方 | 提交编排加 Downstream + 路由表一行 + 消费门一份；`wireDispatcher` 依赖面再宽一格（ADR-0049 已认这类代价） |
| 与三堵墙 | 端点照样被墙一拦，链仍死 | 提交被墙一拦 → 无信封 → 链不动；但合成路径（`cmd/parcel-dispatch` 合成纵向测试、种子租户）可全链验证 |
| 演示/取证 | 无人可调，演不出 | 与票 02/03 的完成标准同路：种子租户下走到 `CONTROL_SCOPE_NOT_CONFIGURED` 那一格 |

## 建议（倾向路 B · 信封驱动），理由按份量排

1. **用例词已定性**：「自动形成接受决定、不等待无依据的人工审批」——路 A 的第一件事就是发明一个 UC 没有的请求者，那是在裁决之前先改了用例。
2. **半成品与先例全在 B 侧**：submitted 交接适配器闲置待接，消费门四条保证（恰一次、幂等、可重投、毒丸拒收）与未决哨兵机制是现成的；A 侧没有任何存量。
3. **失败面语义**：接受链的未决（依赖超时、`asOf` 未配置等）按 `AT-PS-008`/`BD-PS-001` 本就该系统续办；HTTP 重发把续办责任推给不存在的调用方，重试语义接不上。

## 若采纳路 B，裁决要一并说清的四格

1. **同步半边与事件半边的分工**（survey 第 6 条欠的那句 UC 明文）：建议裁为——提交编排内**不做**接受判断（维持今天的形状），接受链整段挂「委托已提交」信封的消费者；`reachability-judgment.formed` 不另立第二条推进路径，避免同一任务两处驱动。
2. **一个消费者还是三类信封接力**：建议一个消费者内按编排顺序推进（可达性 → 财务控制 → 形成决定），未决即登记续办退出，不拆中间事件类型——中间态本就落在接受判断任务里，拆出去是第二份状态。
3. **路由表新行的未决哨兵翻译**：按 ADR-0049「登记一个接不住的类型比不登记更糟」的既有纪律给出本行的翻译。
4. **落档**：驱动方式属难逆转产品行为（被请求 vs 被触发、失败面与重试语义不同），按 AGENTS.md 走**新 ADR**；本简报只作 Context 素材。

## 本简报不动什么

- 不动票 03 的实现范围与「Blocked by: 02」——无论哪条路，02 不落地闭包就形不成，链走不到可验证的那一格。
- 不裁人工复核与主动拒绝的命令面：那是「规则显式要求人工」时**由人请求**的另一条入口（将来 `acceptance-review` 页面的接线依据），与本裁决的自动链驱动是两件事，混裁会把「人工兜底」升格成「默认路径」。
- 不因本裁决移动墙一（`PAR-INT-01`）与墙二（治理坐标实例半边）。
