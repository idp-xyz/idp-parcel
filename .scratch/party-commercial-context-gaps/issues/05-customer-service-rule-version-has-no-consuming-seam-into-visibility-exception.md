# 客户服务规则版本进了封闭集，但 `visibility-exception` 那条消费缝仍然是断的

Category: chore
Status: draft
Blocked by: 04（封闭集拓宽已随 `85c1c7f` 落地，本票的前置已解除）

## 为什么单独一票

票 04 的裁决是「补，但拆两笔」。第一笔（拓宽 `CommercialObjectKind`、建迁移 `0019`）属
「会让旧调用点对不上」那一类，必须占号并预告变红窗口；把本票的内容并进去会把那个窗口拉长到
没必要的长度。第一笔已完成，本票是第二笔。

**拆出来还有一个好处：这两件的失败形态不同。** 第一笔漏了会当场变红（枚举穷尽门禁、库上
CHECK）；本票漏了**什么都不会红**——下游读不到规则依据时会落到某个既有的未决或默认分支，而
那个分支本来就存在、本来就绿。这正是本仓反复记的那一族，所以它需要自己的完成判据，不能靠
「跟着上一笔一起验」。

## CONTEXT 要求什么

`docs/domain/party-commercial/CONTEXT.md` Boundaries 一节：

> `visibility-exception` 拥有追踪投影、异常信号和案件、响应目标、客户披露及通知决定、客户索赔
> 项和追偿事项；`party-commercial` 只拥有服务产品、客户合同及客户服务规则版本，不能直接形成
> 或修改这些实际业务结果。

Rules 一节两条：

> 客户服务规则必须按服务产品和客户合同明确适用范围、有效期间及责任方。追踪披露、异常响应、
> 通知义务、索赔期限和最低材料可以具有客户差异，但不得把内部异常检测阈值、事实有效性或最终
> 赔付金额写成客户可以直接覆盖的商业配置。

> 客户服务规则版本变化只影响其声明生效范围内的新判断。`visibility-exception` 保存具体案件、
> 通知和索赔实际采用的规则依据；后续商业变化不得覆盖已经形成的响应目标、披露决定、通知内容
> 或索赔资格历史。

后一条给本票定了两头：**提供方**要能按（服务产品版本 / 客户合同版本 + 业务时点）解析出适用的
规则版本；**消费方**要在形成每一个响应目标、披露决定、通知与索赔资格判断时把当时采用的规则
依据快照下来，而不是每次现问。

## 代码里实际有什么

票 02 那份清点里已经点过一次，本票再确认一遍取证口径：`visibility-exception` 的跨上下文消费缝
连到了 CC / NR / NO / PS / TF，**没有一条连 partycommercial**。也就是说 CONTEXT 把响应目标、
披露决定、索赔期限交给客户服务规则版本作依据，而那条依据在代码里没有取回的路。

封闭集这一格现在有了（`CustomerServiceRuleObject`，`85c1c7f`），但**只是有了类别标识**：没有
领域类型、没有正文表、没有解析口、没有消费缝。**不要把「进了封闭集」读成「能用了」**——那一笔
的提交信息明写「只拓宽不接线」。

## 本票要摆清的几问（按序，前一问不答后一问没意义）

1. **正文放哪。** 客户服务规则版本的正文（追踪披露、异常响应、客户更新、通知义务、索赔期限、
   最低材料）落一张正文表，还是像票 03 那两类一样先只登记版本身份？形状可照
   `commercial_price_policy`（`object_kind` CHECK 钉死单一类别、外键指回 `commercial_version`）。
2. **解析口的形状。** 走 `resolve_commercial_basis` 那条既有的解析路，还是另开一个读口？
   前者的代价是它今天的闭包不含这一类；后者的代价是多一条口径。
3. **消费方怎么快照。** CONTEXT 说 VE「保存具体案件、通知和索赔实际采用的规则依据」——存引用
   还是存正文？**这一问与票 02 那个「冻正文还是冻引用」同形，答案很可能相同**（冻引用而正文
   可改等于没冻），但两票的重放要求强度不同，须各自确认而不是照抄。
4. **首发范围。** 六项规则内容是否全部进首发。索赔期限与最低材料牵涉客户合同差异，可能与票 03
   的客户合同正文表有先后依赖。

## 边界

本票**不建表、不写迁移、不动领域模型、不接缝**，只把差异摆到可裁的形状——与本批其余三票同一
体例。特别地，**不动 `visibility-exception`**：那一侧要不要改取决于上面第 3 问的答案，本票不
替它预设。

**不属本票**：封闭集拓宽（票 04 第一笔，已完成）。
