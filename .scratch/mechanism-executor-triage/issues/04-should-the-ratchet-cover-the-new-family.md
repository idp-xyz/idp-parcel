# 棘轮刻意排除的 `New*` 一族里也躺着真缺口——要不要把网加宽

Category: chore
Status: resolved——裁第三条路（2026-09-03，MCP-3，owner 授权自决）：**不动棘轮、另立类型侧名单**；探针不留在 `.scratch` 当没人跑的工具，做成第二道棘轮后退役。实现见票 [05](./05-type-reachability-ratchet-as-a-second-baseline.md)。理由：按返回类型改判据会重建基线、历轮不可比，而棘轮的价值有一半在可比；两份名单各守一族的维护代价，比丢掉可比性便宜
Blocked by: 无

## 棘轮排除 `New*` 是有理由的

`production_wiring_ratchet_test.go` 头注写明：

> 排除 `New*`：值对象与标识构造器是另一族，本票「边界」一节已将其列为后续。排除用前缀是
> 有意的，方向与「用前缀圈定范围」相反——**漏一个 `New*` 只多一行噪声让人看见，而漏一个
> 工厂就永远没看见**。判一道护栏好不好不看它用什么写，看它漏的时候倒向哪一边。

这段推理是对的：`New*` 里绝大多数是值对象构造器，全收进来会淹掉名单。**但「绝大多数」不是
「全部」**——聚合根若按 `NewXxx` 命名，它就跟着一起漏了，而漏的方向恰好是这段注释自己说的
那个更贵的方向。

## 探针捞出来的证据

写了一支[探针](../../domain-executor-audit/probe/main.go)按**类型可达性**量，判据与棘轮
互补：从生产代码指名的种子出发，沿字段类型与方法签名闭包，闭包外的导出领域类型即零生产
消费者。锚 `9d6063c`，全仓 1127 个导出领域类型报出 **122** 个。

**122 是上界不是答案**，它至少混三类。第一版按「有没有被指名」判报出 403 个全是噪声——
`CurrencyCode` 这类值对象由聚合的取值方法返回出去，外部从不指名却完全用得上；改成可达性
闭包才降到 122。剩下的噪声里还有一类是 `Resolution` 那种：只由未导出函数产出、导出了却只
在包内用，那是该改小写的设计瑕疵，不是缺执行器。

阳性对照通过：已知三处缺口（`ChannelAccountUseAuthorization`、`CreditPolicy`、
`SupplierAgreement`）全部捕中。而**后两个由 `New*` 构造，棘轮网外**。

抽验还捞出一个此前没人点过的：

**`ProductChannelMapping`**（`internal/partycommercial/domain/service_product.go`）。仓里有
两个近名类型——适配器、端口、应用编排接的全是 `ProductChannelMappingRegistration`（修订
版本化映射册），而带 `CandidatesAt` 与 `CandidatesAllowedBy` 的 `ProductChannelMapping`
零生产消费者。后者才是「这个时点给出哪些渠道候选、客户的渠道约束把它收窄成什么」那段逻辑。

它由 `NewProductChannelMapping` 构造，所以棘轮看不见它。而它恰好压在
[first-tenant-runway 票 03](../../first-tenant-runway/issues/03-network-resolution-layer.md)
（网络解析层——把目录折成逐候选事实）的路上。

## 论证不再靠推理了：漏网的实例找到了（2026-09-02 补）

上一节说 `New*` 排除「漏的方向恰好是这段注释自己说的那个更贵的方向」，当时那是推理。
补核 `parcel-pricing` 四条时撞见了实例，而且**它复发在基线自己记过事故的那个文件里**。

基线的原话（`parcel-pricing` 组末尾那段）：

> 初版这里还有两条与其余不同类的：`DecimalFromInt64` 与 `Evaluate` 全仓无人调用、测试里
> 也是零，不是「只被测试接线」而是死代码，各自都是一行转发给同文件里的正主……**已删**。
>
> 留这段是因为：本门禁按判据本就不管这一类，删掉之后**不会再有任何机制提醒下一个人这里
> 曾有过一对影子函数**。而它俩当初能长出来，正是因为同文件里已有正主却没有东西拦住第二个
> 写法。

同一个文件 `internal/parcelpricing/domain/decimal.go` 里，今天有：

    func NewDecimal(raw string) (Decimal, error) {
        return ParseDecimal(raw)
    }

全仓 `\bNewDecimal\b` 只命中一处——它自己的声明。零调用点，连测试都没有，函数体一行转发。

**关键在命名方向**：被删掉的那对叫 `DecimalFromInt64`（非 `New` 开头，落在棘轮网内，因此
被看见），这一个叫 `NewDecimal`（被 `New*` 规则挡在网外）。**同一种缺陷，命名方向相反，
门禁只守得住一个方向**——而基线那段话预言的正是「不会再有任何机制提醒下一个人」。

这条实例把待裁的三条路里第一条的天平压了一下：按返回类型判会收住它（`NewDecimal` 返回
本包具名类型 `Decimal`），按名字前缀判永远收不住。但代价那一栏没变，见下。

## 待裁

**一、要不要加宽棘轮的网。** 三种做法各有代价：

- **按返回类型判**而不按名字前缀：返回本包具名结构体（非基础类型别名）的导出函数入网。
  能收住 `NewProductChannelMapping` 这种聚合构造器，同时挡掉返回 `TenantID` 之类的值对象
  构造器。代价是判据变复杂，且棘轮头注明确说过「不看返回类型」，理由是「把它写进判据等于
  假设下一个工厂也长这样」——那条理由对**排除**规则同样适用，要一并回答。
- **改用类型可达性**（探针那套）替代或并行于函数名单：口径更本质，但基线名单要重建，
  与历轮不可比。棘轮的价值有一半来自可比性。
- **不动棘轮，另立一份类型侧名单**：两份名单各守一族，代价是维护两处。

**二、探针本身的去留。** 它是扔弃件，`.scratch` 下留着当取证过程。若裁定加宽用可达性口径，
它是现成的起点；若裁定不动，它随本目录一起归档，**不要留一份没人跑的工具在仓里**——那正是
它自己要找的那种东西。

## 边界

本票**不改棘轮、不改基线名单、不把探针搬进 `tools/`**。产出是三条路各自的代价，交人裁。
