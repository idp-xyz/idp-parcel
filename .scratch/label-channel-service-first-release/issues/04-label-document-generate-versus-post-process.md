# 04 面单文件是「生成」还是「取回渠道成品后加工」，口径未分

Category: enhancement
Status: resolved——三问由现行领域文档已答，见文末「裁决」；剩余的一个工程小问归 `09`
Blocked by: 无

## 为什么先立它

[ADR-0088](../../../docs/adr/0088-label-channel-service-enters-the-first-release-service-forms.md)
Consequences 把「面单文件生成与修改的文档适配器」列进机制半边要补的形状。而
[能力形状盘点](../capability-shape-inventory.md)第二段的公开资料显示：**末端渠道大多直接
返回成品面单**（FedEx/UPS/USPS 在 ship 应答里回图件，UniUni 第三次调用取 base64 PDF）。

于是「生成」与「取回成品后再修改/重排」是两件事，而今天**没有任何票面或文档区分它们**。
客户条目里的「面单 PDF 修改」指的是哪一件，盘点的取证不足以判定。

同盘点第五段实测：全仓 `internal/` 下 `PDF`/`ZPL` 零命中，按 `render`/`template`/`单证`/
`文档生成` 扫到的命中全部落在迁移框架模板与 outbox 信封测试，**无一处与单证渲染有关**。
也就是说这一段不是「实现得不好」，是一张白纸——正因为是白纸，先分清要画什么才不浪费。

## 要的裁决

1. 首发要的是哪一件：取回渠道成品并原样交付、取回后加工（加自有标识/重排版/合并批次）、
   还是自行生成面单。**三者的适配器形状与法律责任都不同**。
2. 若含「加工」：加工后的面单与渠道返回的原件是什么关系——两份都留、还是加工件替代原件。
   这决定 `09`（载荷落点）要留几份。
3. 若含「生成」：生成所依据的规则版本归谁（面单服务终局规则属 `PAR-COM-05`/`PAR-COM-07`，
   实例半边），机制上要不要现在就留位置。

## 红线

- 不填纸张尺寸、DPI、模板样式（实例半边）。
- 不在本票里写实现——盘点第五段明说「先一票只结口径，不写实现」。
- 不重开 ADR-0088 的范围决定。

## 完成判据

三问各有明确答复并落在可引用处；`09`（渠道返回载荷落点）据此知道要留几份载荷、留不留
加工件。

## 参照

## 裁决

**这三问不需要新裁决——现行领域文档已经答过了。** 立票时没查到，是因为两份盘点都只盘代码
不盘 `docs/domain/`：盘点在 `internal/` 下搜 `PDF`/`ZPL`/`render`/`template` 得到零命中，
据此判为「一张白纸」；而这一段的口径本来就不写在代码里，它写在 CONTEXT 与场景里。

### 依据（现行文档，非归档）

[SCENARIOS](../../../docs/domain/SCENARIOS.md)「面单渠道」一节：

> 查询、重打、渠道作废、替换和渠道退款分别判断，**不能以重新生成文件代替渠道业务操作**。

[PS CONTEXT](../../../docs/domain/parcel-shipment/CONTEXT.md)：

> 查询、重打、渠道作废、替换和渠道退款是不同业务动作。重打同一有效结果不改变包裹身份；
> 换单形成新的面单交易并显式关联被替代交易。

### 三问的答案

1. **首发取「取回渠道成品」。** 「自行生成面单」由上引 SCENARIOS 那半句直接排除——它禁的
   正是拿本地生成的文件去顶渠道业务操作。「取回后加工」首发也不做：客户条目里的「面单 PDF
   修改」**不是一个文档操作**，它落在 PS CONTEXT 已经定义的四个业务动作上，其中`重打`与`替换`
   覆盖了「改」的两种真实含义——前者不改包裹身份、不产生新标识与新费用，后者另开一笔交易
   并显式关联被替代交易。
2. **因此只留一份载荷**：渠道成品原件，不留加工件。`09` 据此不必为「两份」留形状。
3. **不含「生成」，因此本轮不为 `PAR-COM-05`/`PAR-COM-07` 的规则版本留位置。** 留一个没有
   生产者的位置，与盘点判为「无缺口不立票」的那三段同理。

### 已经实现的那一半

`替换`不是待建：`internal/parcelshipment/domain/label_transaction.go` 的
`EstablishPriorLabelTransactionLink`（在**新**交易出生时建立且要求原交易已定案）与
`FollowUpActionKind` 的 `ChannelReplacementAction` 就是它。本票不重做。

### 移交给 `09` 的一问

现行文档写`重打`是「重新取得**或渲染**同一面单」，两者未分。这一问不值得单独占一张裁决票，
归 `09` 与载荷落点一起答，**建议取「从本地留存的原件再交付」**：回渠道再取正是归档 QA
第二十二问（用户当时裁 `A`）点名要防的重复购买风险，而 USPS 的 `LABEL_BROKER`/`NONE` 形态
说明「取了面单」与「回了图件」不是同一件事，回取未必拿得到同一份图件。

### 能力边界

本裁决依据的是现行 `docs/domain/` 与聚合代码，**未打开 `docs/wooolink/` 或
`docs/reference/xls/` 下的客户文件**（两份盘点同样未打开）。因此这里裁的是**结构**——
首发做哪一类适配器、载荷留几份；若某个具体客户另有成文的面单加工要求，那属实例半边，
按 `PAR-COM-*` 登记，不推翻本裁决的结构结论。
