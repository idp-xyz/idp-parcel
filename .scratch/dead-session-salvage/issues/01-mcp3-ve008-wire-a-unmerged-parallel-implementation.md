## 只读对比所得（2026-08-20，MCP-4 办 03 号票时顺带，仅 `git show`，未 checkout / cherry-pick）

1. **零行格两版逐字同义**：都是 `!found` 交回 `nil`，不派生、不发明账户。
   所以外部评审 03 号票指出的空档**不是赢家那版的疏漏，是这道缝本身的形状**——
   两位作者独立落到同一格。

2. **`dca024a` 把 03 号票的假设写死在注释里**。原话：「若委托日后才落到已接受，下一版投影的
   信封会再触发本链，不靠重投这一封等」。**作者当时就想到了迟到接受，并明确托付给「下一版信封」。**
   于是 03 号票问的「没有下一封时怎么办」不是事后诸葛亮，而是一条**被自觉搁置的短路**，
   两版实现搁在同一处。这给 03 号票的真实性添了一道独立旁证。

3. **一处相反的设计分歧，两边都引了权威——这是本对比唯一真正未决的东西。**
   客户视图该基于哪一版投影：

   | | 做法 | 自陈理由 |
   |---|---|---|
   | `dca024a` | `FindByVersion` 读信封指名那版 | 各版各长自己的视图代（ADR-0065 / AT-VE-161）；读 `FindCurrent` 会让先到的信封吃掉后到那版的更正 |
   | main（`49a2ab0`） | `FindCurrent` + 版本相等判断跳过旧版 | 客户视图只基于**当前**投影形成（UC-VE-008） |

   两者未必真冲突——ADR-0065 的「版本只增不改写」管的是**投影**，UC-VE-008 管的是**客户视图**，
   是两个对象。但没有任何一处文档明写「客户视图是否需要按投影版本各留一代」。
   **要不要重开这一问，本票不裁。** 若重开，应是独立的领域裁断票，不塞进接线票。

### 这一条对 VE-008 迟到重派生（路线 a）是顺风

a 路线的补派生由**账户绑定**触发，手里没有「信封宣告的版本」，只能基于当前投影派生。
这在 main 的 `FindCurrent` 形状里是自然延伸，在 `FindByVersion` 形状里无处安放。
**赢家那版恰好让 a 更好落**，与选路结论一致。
