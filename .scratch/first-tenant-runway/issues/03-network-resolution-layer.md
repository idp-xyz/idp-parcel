# 网络解析层——把目录折成逐候选事实

Category: enhancement
Status: blocked（2026-09-02 MCP-5 答完三问；结论是被 `PAR-NET-14` 硬阻断，**本票暂不拆实现票**。阻断解除前唯一可动的是一张前置票，见 `## Answer` 第四节）

演示动线三堵墙的**墙三**，也是本批唯一一件真正在长的工程。取证基线 `c9835bf`。

## 墙

初始路由停在 `RouteEvidenceNotConfigured`（`create_initial_route.go`），可达性停在 `NetworkEvidenceNotConfigured`（`assess_parcel_reachability.go`），复核停在 `ReassessEvidenceNotConfigured`（`reassess_route.go`）。

成因是两张表之间没有桥：三个证据视图只读 `network_routing.network_definition`（迁移 `0007`），而那张表**零生产写入方**；演示种子灌的是迁移 `0008` 的七族目录版本表，`bumpRevision` 推的是目录修订锚，长不出 `0007` 的行。

目录那半边已经通了——`.scratch/syn-wall-door-audit/issues/04-network-definition-register-no-writer-no-resolver.md` 交付了登记用例 `register_network_catalog.go` 与进程口 `cmd/parcel-network-register`，并在票面预告「本票不降墙」。墙面状态因此是「无门（解析层缺）」。

## 做什么

把目录折成逐候选事实：候选生成、资格过滤、事实装配，交给三个证据视图能用的形状。

**这是全批最需要先设计再动手的一件，开工前必须先答三个问题：**

1. **`0007` 与 `0008` 的合流口径。**`network_definition` 那一行应随目录登记自动形成，还是另有登记路径？票 04 明确把这一问留给了解析层设计，没有替它定。
2. **`PAR-NET-14` 到底挡住了什么。**票 04 与 [ADR-0068](../../../docs/adr/0068-versioned-network-catalog-structure-precedes-rule-content.md) 都把解析层记为被 `PAR-NET-14` 阻断。但首发的准则集合其实已由 `PAR-NET-16` 定死为**成本单维**，而 `RankingCriterion` 本就是开放引用、准则由策略版本声明。**要分清被挡的是「候选怎么生成」还是「候选怎么排序」**——如果只是后者，解析层的前半段今天就能做。这一问答错会让整票要么白等、要么撞穿护栏。
3. **要不要改 ADR-0068。** 它的 Decision 六明写「三个证据视图仍不读本目录」，护栏钉在 `0008` 头注与 `network_catalog.go` 的类型注释两处。解析层落地那一刻这条护栏按定义要动。**同笔改 ADR（新 ADR 或 supersede），不留「代码已读、ADR 仍说不读」的中间态**——它的 Context 会在决定落地那一刻失效，这正是 AGENTS.md 点名 ADR 尤其要守的那一类。

三问答完再拆实现票。答案落在本票 `## Answer` 段。

## Answer

2026-09-02 MCP-5，取证锚 `c60ec2c`（工作树含本轮 ADR-0091 改动，与本节结论无交集）。

**先说总结论：第二问的答案与票面假设相反，因此「解析层前半段今天就能做」那条路不通，本票暂不拆实现票。** 三问逐条如下。

### 一、`0007` 与 `0008` 不合流：定义登记保留独立路径，但视图修订必须改由目录修订派生

**不自动形成。** 两张表的维度不同，这是决定性的一格：`network_definition`（0007）的主键是（租户 + **服务目的**），而 `0008` 七表与 `network_catalog_revision` 一律只按租户存放，没有服务目的维。要让 0007 那一行随目录登记自动形成，就得先回答「哪些目录行服务于哪个服务目的」——而那正是 `PAR-NET-14` 最低证据首项里的**候选生成规则**。自动派生不是省一次登记，是把一条待提供的规则写死在派生逻辑里。

**但有一处必须改，而且它是解析层的前置不是收尾：`view_revision` 不能再由 0007 独立登记。** 解析层一旦从 0008 产出事实，事实的内容就随目录变，而修订仍标在 0007 那一列上；`create_initial_route` 的提交前重校靠修订等值比对判断「证据有没有换代」（ADR-0068 决定五写明这条依赖），于是目录改过而修订不变时，它会把「证据已经换代」读成「没换」。这不是风格问题，是一次静默的错判。

**取值来源只能是目录修订锚**，不能是两个锚拼出来的复合值——ADR-0068 已经以同一条理由否决过「修订锚按（租户+族）分七行」：拼出来的修订没有单一权威。合流之后 0007 的职责收窄为两件：声明这个（租户+服务目的）范围**已登记**（`未配置`格的承载物，ADR-0052 的「空册与空集合可分辨」在这一层的落点），以及承载服务目的这一维。内容权威整体归 0008。

`0007` 已按校验和固定，改列走新迁移。

### 二、`PAR-NET-14` 挡的是候选生成、过滤与排序**三样全部**，`PAR-NET-16` 解不开其中任何一样

票面这一问的假设是「首发准则集合已由 `PAR-NET-16` 定死为成本单维，所以被挡的可能只是排序」。**该假设不成立，两条独立理由。**

**其一，参数登记册直接写着三样。** `PAR-NET-14` 的最低证据首项原文是「候选生成/过滤/排序规则」——三者并列在同一行、同一个「待提供」状态里。`0008` 的迁移头注是同一句话的另一面：「折叠语义一列不埋：候选生成、过滤、排序……全属 PAR-NET-14」。

**其二，`PAR-NET-16` 管的不是这件事。** 它是**供应商比价候选集合与择优规则**——决定哪个供应商/渠道承运，主要影响场景是 `OPS-01`、`OPS-09`、`SET-01`、`SET-04`。它确认的机制半边是「比价必须在各候选按自己的体积系数与进位策略算出计价重量之后进行」与「首发只按成本单维择优」，那是**采购择优的维度**，不是 `RouteStrategyVersion` 声明给 `SelectRouteCandidate` 的准则序。把它读成路由排序准则，等于让采购决策替网络策略声明准则序——两者恰好都能叫「按成本排」，所以这个混淆很自然，也正因为自然才要写下来。退一步说，即便认为它能覆盖排序那一维，它自己的登记状态是「待提供：候选集合与各维度实例值未确认」。

**有一样确实没被挡，但它不是解析层。** 领域侧的排序机制已经完整实现且是开放引用：`RankingCriterion` 刻意不是封闭枚举（「准则集合由路由策略版本声明（PAR-NET-14），在这里列一份就成了第二处定义」），`SelectRouteCandidate` 按声明序逐准则比较、全平时按候选标识收尾。解析层要做的不是「实现排序」，是「从目录里读出策略版本声明的准则序与各候选在各准则上的分值」——而准则序、分值量纲与折算方式全在 `PAR-NET-14` 那一行里。

**所以「前半段今天就能做」也不成立，理由比排序那一层更硬：解析层的输入不存在。** `0008` 按 ADR-0068 决定三**一列内容都没建**——服务区域没有地理覆盖列，服务日历没有营业日/服务窗口/截单列，路由策略没有规则正文列。今天从目录里读不出任何一个候选。真实顺序是：`PAR-NET-14` 到位 → 内容列按新迁移扩列 → 解析层。中间没有可以提前做的一段。

### 三、ADR-0068 要改，但不是现在；形式是新 ADR，同笔连护栏一起动

**要改。** 决定六「三个证据视图仍不读本目录」的 Context 会在解析层落地那一刻失效，这正是 AGENTS.md 点名「ADR 尤其要守」的那一类——它引的就是它自己要改的那份代码。

**但今天不改。** 按第二问的结论，解析层被硬阻断，现在改等于提前拆掉一条仍然成立的护栏，留下反向的中间态：ADR 已说可读，而代码读不了、也没有可读的内容。票面「不留『代码已读、ADR 仍说不读』的中间态」这条要求对称适用于两个方向。

**改的时机与形式**：与解析层实现票**同一笔**。新 ADR 按 [adr/README](../../../docs/adr/README.md) 的部分停用机制停用决定六那一句（`Status` 行与 Links 各加前向指针，索引行写明被停条款与「其余各条不变」），同笔改两处护栏——`migrations/network_routing/0008_network_catalog.sql` 的头注与 `internal/networkrouting/adapters/postgres/network_catalog.go` 的 `NetworkCatalog` 类型注释。决定六还有半句「目录修订与视图修订的合流属解析层设计，届时再裁」，由本节第一问的答案兑现，属同一笔。

### 四、本票据此的处置

**不拆实现票。** 三问答完的结果不是「可以开工了」，是「确认了开不了工，且确认了此前以为能提前做的那半段也不能」。`PAR-NET-14` 是实例半边，工程侧无法自解——它要的是真实网络规划参数（候选生成/过滤/排序规则、服务区域、业务时区、服务日历、截单与网络可用性采用方式等一整行），归网络规划与运营出证。

**唯一可动的一张前置票**：第一问认出的那处修订来源缺陷。它是机制半边、不依赖任何 `PAR-NET-*` 取值。**但不建议现在单独做**：`view_revision` 改由目录修订派生，只在解析层真的从目录产事实之后才有可观察行为，现在做出来没有任何用例能证明它对，等于往仓库里放一段无人走的代码。**记为解析层实现票的第一步**，开工时先做它，再做折叠。写在这里是因为它容易在开工时被漏掉——漏掉的症状是静默错判，不是报错。

**跨批依赖不变**：`label-channel-service-first-release` 的票 `13`（`BUY` 评价到成本准则分值的桥）与票 `01`（平局裁决）。注意那两票搭的桥属**供应商比价**那一侧（`PAR-NET-16`），与本票的路由候选排序（`PAR-NET-14`）是两条线——第二问那个混淆在这里会再出现一次，对齐时先分清。

## 必须守住的一格

**服务区域的地理覆盖、服务日历的营业日/服务窗口/截单、路由策略的规则正文在 `0008` 里刻意一列未建**（头注：属 `PAR-NET-14`，形态定了再以新迁移扩列）。解析层不得为了凑出候选而给这些列填形状——缺哪一格就让候选在那一格上如实不可用，按 ADR-0029 的取数失败代数分格答；`ErrNetworkDefinitionUnresolvable` 不得退成`未配置`或空事实（ADR-0053 第四条第三格）。

## 完成判据

三个证据视图之一能从合成目录产出逐候选事实并让初始路由形成计划；`ErrNetworkDefinitionUnresolvable` 那条响亮上抛的分支保持原语义；ADR 同笔更新；`gofmt -l` 空、`go build`/`go vet` 退 0、`go test -count=1 ./...` 绿并注明含不含真库。

测试值全 `SYN-` 合成，`S` 只记 `S`。
