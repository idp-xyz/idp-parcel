# 01 定下货物明细、销售订单引用与 FBA 头程的承接方式

Category: docs
Status: in-progress
Blocked by: 无

依据：用户 2026-11-10 在同一会话里的几句原话——

1. 「要支持多行货物明细需要改哪些地方」
2. 「请你参照国际成熟的国际跨界小包业务系统，帮我来决定把， 你自己来grill，参照自己来答复，符合国际跨境小包业务的实际业务需求的场景」
3. 「头部软件的做法是将商品放在运单(订单)下面的吗，订单，运单，小包到底是什么逻辑关系呢，目前我们只有运单，这个设计有缺陷吗」
4. 「这三点我们都要参照头部系统的做法确定掉， 我们这个系统也需要支持FBA的」
5. 「国际小包和FBA你觉得需要分成两个独立的入口，还是一致处理呢，头部系统的做法是什么呢」「你觉得是科学，专业的做法吗」「FBA是不是传统的货代业务啊」
6. 「可以，按这个范围写吧」

下面的裁决全部是会话代决（`/grill-with-docs`，问题由会话提出、按头部系统的通行做法代答），待小包托运、关务与贸易合规、仓配履约 owner 与产品 owner 复核。

取证时的现状（`main` 于 `8d6f5ffba`）：

- 客户下单时每个包裹只有一组扁平的货物字段，首方提交口拼成 `parcel[引用].goods.*` 条目；PS CONTEXT「客户原始资料版本」词条写明版本只另外保留声明测量与地址要素，其余条目只进摘要、不留原文——客户报的货物在系统里没有可读的值。

## 裁决（2026-11-10 会话代决）

### 第一轮：货物明细归谁、留不留原文

1. **归属。** 货物明细是客户原始资料的一部分，归小包托运：它是客户（或以货主名义代办的仓配履约）的声明，不是销售订单、仓配的商品、关务的正式申报资料或申报货物项。（ADR-0373 决定一）
2. **留原文。** 货物明细进客户原始资料版本保留的封闭要素内容，与声明测量、地址要素并列，提交版本与接受基线同样保留；不再只进摘要。（决定五）

### 第二轮：挂在哪一层——首稿与改稿

3. **首稿挂包裹，改稿挂委托。** 首稿照邮政 CN22/CN23 一件一单的做法挂在每个包裹上。用两种场景检验时不成立：FBA 同款五十箱要把同样的品名、税号与单价抄五十遍，改一个税号要改五十处；快递式一票多件只有整票商业发票、不知道每箱装了什么，挂包裹就报不出来。改为头部 FBA 与货代系统的「商业发票 + 装箱单」两层：货物明细行挂委托，一种货的值只写一处；各包裹另报装箱分配（包裹，行号，数量）。单件委托不报分配，与邮政做法等价。（决定二、三）
4. **装箱分配要么不报、要么报全。** 多件委托不报即整票清单（快递式）；报了就逐行数量之和对齐，只报一部分、指不存在的包裹或行、和对不上，答形状不对——这是同一份声明内部的结构，不是跨来源核对。是否必须报全由接单规则包说（FBA 与逐件报关的线路会要求）。（决定三）
5. **行号与修订。** 行号是版本内序号，不跨版本延续；资料组「货物明细」作用于整份委托，内件性质、行与装箱分配整组替换。国际上的报关单与物流商的修订接口都是整份重报，行级身份要另造行键、处理并发合并，得不偿失。（决定四）
6. **上限 999 行。** 产品机制；渠道或申报口更严的上限是它们的取值。（决定二）

### 第三轮：行里有哪些格、怎么保真

7. **行的格**（每格可缺、原样保串）：品名按语言多条；数量与计量单位（不默认为件）；单价、行总价与一行一个币种（两格可只报一格——国内 ERP 多报单价，欧美平台多报行总价）；净重；申报商品编码至多两条，分出口侧与进口侧（参照 DHL）；原产国；货主商品编码。（决定六）
8. **不核对。** 单价乘数量与行总价、行净重与毛重、行价值与保价声明价值、编码位数、国家码，一概不判；平台折扣后行总价本就常常不等于单价乘数量。必填由接单规则包说。（决定六）
9. **内件性质**照 UPU CN23 六格，委托一格。（决定二）
10. **来源标记**照 ADR-0370 决定五三格，标在申报格上；装箱分配不带标记，出处随委托的来源。（决定七）

### 第四轮：销售订单、运单与小包的关系（用户问的三点）

11. **订单、运单、小包是三层，归属不同。** 销售订单是卖家与平台的交易，归货主；运单（本仓的委托）是卖家与物流方的服务合同；小包（包裹）是物理件。物流方不拥有订单，只引用。头部系统里商品挂哪一层取决于系统站在哪一层：ERP 挂订单行，快递挂运单，邮政与小包挂包裹，FBA 与货代是发票加装箱单。本仓不建订单对象，不是缺陷。
12. **第一点：销售订单引用挂在行上。** 货物明细行可带（销售平台，订单号，订单行号），三格可缺、原样保存、一行至多一个。挂在行上而不是包裹或委托上，是因为合单时一个包裹里的几行出自不同订单；拆单时几份委托的行指同一张订单。委托级的客户参考号照旧，是客户这一票的号（云途一类的「客户订单号」）。按订单号查委托的读口另做。仓配的出库请求眼下不带销售订单号，那一格照实空着。（ADR-0373 决定六、十）
13. **第二点：一票多件只有整票清单。** 由第 3、4 条的委托级货物明细加可缺的装箱分配直接承接，不再是限制。（ADR-0373 决定三）
14. **第三点：号码的界面叫法。** 运单号指委托的单据号；客户单号指客户参考号；包裹号指包裹的本系统号；客户件号指客户包裹件号；跟踪号指渠道包裹件号（含尾程件号）；平台三种号照名。多件委托列表显示运单号与件数，详情逐件列；运单号不当跟踪号显示。这与快递的「主单号 + 子件号」同构，与国内小包行业「客户单号、运单号、跟踪号」三号的叫法一致。（ADR-0374 决定六）

### 第五轮：FBA

15. **入口分不分。** 模型统一、入口按场景分：FBA 与国际小包同一个委托、同一条受理链；界面上可分小包下单与 FBA 货件下单两页、两套导入模板，首方 API 同一个端点带可选的平台段。承运方（DHL、FedEx、UPS、EasyPost）统一模型，面向卖家的物流商与 ERP 分入口，本裁决取两者之长。（ADR-0374 决定三）
16. **是不是科学、专业。** 检验标准：生命周期、核心规则或权威方不同才拆，字段与必填不同不拆。专线型 FBA 头程（快递、空派、海派）的生命周期与小包相同，统一；货代型（整柜、拼箱、海卡：订舱、提单、托盘、预约送仓）生命周期不同，不进委托。会话同时如实交代了弱点：头部系统做法多出自已有知识、没有真实租户数据只能记 `S`、首稿改过一次、整票受理依赖 `BD-PS-007`。（ADR-0374 决定一）
17. **FBA 是不是传统货代业务。** 一半是：整柜与海卡仍是标准的货代业务；空派、海派已被小包专线公司做成按公斤卖、按箱操作、尾程打末端渠道面单的网络产品。开发主线把「小包专线与货代」列为目标客户群，专线型通过能力范围判据；货代型要另立能力范围决定。登记产品需求假设 `PA-FBA-01`。（ADR-0374 决定一）
18. **一个平台货件一份委托，一箱一个包裹。** 收件资料是平台仓；一个入库计划分到几个仓就是几个货件、几份委托。整票受理照 `BD-PS-007`，一箱有问题整票补正或拆票。（决定二）
19. **不设 FBA 标志。** 「这是 FBA」由服务产品说；平台号、箱标号、装箱分配报全、收件人是平台仓等要求是接单规则包的必填；整票计费由价卡声明（ADR-0364）。（决定三）
20. **外部标识加三种类型。** 平台货件号、平台参考号标识委托，平台箱标号标识包裹；分配方是销售平台，号由客户交来不核对，歧义照既有规则。（决定四）
21. **仓配平台备货整份提交一份委托。** 整份打包完成后提交，带全部包裹；不预取面单（预取按一个包裹先提交，装不下一个货件）；来源请求键（出库请求，提交轮次），被拒绝或撤回后重提加一，同一键不复用。部分停用 ADR-0368 决定四、ADR-0370 决定一、决定二、决定五、ADR-0371 决定一各一句，适用场景都是平台备货。（决定五）
22. **不在这两份记录里的。** 货物特性与危险品（带电等）、收件人税号与 IOSS、运费与凭证、材质品牌等细项（ADR-0373 决定十一）；送仓预约、托盘与零担整车、进口商与一般贸易清关、平台收货差异与短少索赔、与平台对接、按平台货件号查委托的读口（ADR-0374 决定七）。
