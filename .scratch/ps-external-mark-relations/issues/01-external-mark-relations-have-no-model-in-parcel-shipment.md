# 外部标识关系在 parcel-shipment 无任何模型，NO 的 ParcelIdentityView 因此无实现

Category: enhancement
Status: needs-triage

发现于接 `node-operations` 的 `ports.ParcelIdentityView` 时。该端口按外部标识核对正式包裹
身份，注释写明是「PS 侧只读引用」，`node-operations` 不得自建。核对结果：**PS 确实拥有这个
概念，但一行代码都没有**，而且它不是换了名字藏在别处。

本票只记事实与约束，**不定方案**——现在建它等于让一个消费侧端口反过来驱动 PS 开一片新
子域，顺序是反的。

## 代码侧现状

`internal/parcelshipment` 全搜「面单 / Waybill / Label / ExternalMark / 外部标识 /
TrackingNumber / 运单」，生产代码只一处命中，而且是条否定：`domain.IntakeSourceKind` 的
注释「普通扫描、卸载、车辆到场、任务创建与面单结果不是来源」（`AT-PS-043`）。领域层只有
`domain.DeclaredParcelID`，没有任何外部标识类型。

## CONTEXT 侧的定义与两条不变量

`parcel-shipment` 的 `CONTEXT.md` 开篇第一句就把「外部标识关系」列为本上下文所管，并单独
下了定义：

> **外部标识** 由外部参与方分配、用于标识明确业务对象的号码或代码。外部标识必须记录标识
> 类型、分配方、被标识对象、适用范围和替代关系，**不能全部解释为包裹的“当前运单号”**。

两条配套不变量：

> 外部标识必须关联其真实标识对象：客户参考号关联委托，渠道订单号或主号按其语义关联面单
> 交易，包裹件号或尾程件号关联包裹；总单号、舱单号和监管编号继续归相应源上下文。

> 外部标识作废、失效或被替代只改变适用关系，不删除历史标识，也不改变本系统拥有的委托或
> 包裹身份。

## 一张 mark→parcel 映射表为何从 schema 层面就错

三点，任何一点单独成立即足以否掉那种形状：

1. **被标识对象不止包裹。** 至少三类（委托、面单交易、包裹），且分类依据是标识的语义而
   不是它长什么样。一张只能指向包裹的表，等于把定义里明禁的那句「全部解释为包裹的当前
   运单号」直接写进了列定义。
2. **替代关系要留历史。** 作废与失效只改变适用关系、不删除标识，所以同一个标识值在不同
   时点可以有不同的适用结论。一张 `mark → parcel` 的唯一键表表达不了「曾经指向、现已被
   替代」，而那恰恰是核对身份时最需要分清的一格。
3. **适用范围是必填维。** 定义要求记录标识类型、分配方、适用范围三样，缺其一就无法回答
   「这个号在这个范围内还算数吗」。

## `ParcelIdentityView` 的三分支是对的，不是防御性写法

该端口按候选数分派：恰一个→关联、零个→待识别、多个→身份冲突。有替代关系与适用范围在，
**同一个 mark 出多个候选是真实情形**：一个被替代的旧件号与其后继可以同时匹配，跨适用范围
也可以各有一份。所以「多个」那一格不是保守兜底，是模型必然产生的结果。该端口的
`ExternalMarkObservation` 注释「外部条码只是线索，不自动等于正式包裹」与 PS 这边完全对齐。

## 依赖点名：它连着面单交易那一片

「渠道订单号或主号按其语义关联面单交易」这一支直接依赖面单交易模型，而 CONTEXT 里那是一
整片相互引用的概念——面单交易、面单交易包裹结果、面单交易定案、面单服务终局边界、面单继续
尝试决定、权威业务截断边界、受控关闭与重开。**这一片在 `internal/parcelshipment` 下同样一行
代码没有。**

因此外部标识不是一个可以顺手补的小端口：它的三类被标识对象里，有一类的宿主尚不存在。

## 当下状态

`ParcelIdentityView` 保持无生产实现。这是诚实状态而不是遗漏——它缺的是 PS 侧一片尚未建模的
子域，不是缺租户数据，也不是缺一个适配器。
