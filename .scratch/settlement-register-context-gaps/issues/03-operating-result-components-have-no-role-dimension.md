# 「审核应付与贷项按各自借贷方向分别计入一次」在册上验证不了——组成项没有角色维

Category: chore
Status: resolved——机制半边已落地（2026-09-01，见文末 Comment）：角色维按口径分组入类型，
写侧重建复验守「各至多一项、贷项在场应付必须在场」
Blocked by: 无

## CONTEXT 要求什么

`docs/domain/settlement-accounting/CONTEXT.md`「经营指标、人工调整与系统边界」一节，硬句原文：

> 经营毛利的客户与外部供应商基础必须按阶段成对采用：预估口径使用当前有效客户预估费用和当前有效
> 供应商预期成本；已确认口径使用当前有效客户运营应收，以及当前有效审核应付和与其关联的当前有效
> 供应商费用贷项，**审核应付与贷项按各自借贷方向分别计入一次**；已结算口径只使用 `UC-SA-005` 对
> 上述客户运营应收、审核应付和供应商费用贷项分别形成的运营核销分配范围。供应商账单未到、审核应付
> 未形成、贷项未明确关联或真实收付映射存在，均不能把缺失成本记为零、**把审核应付视为已净含贷项**
> 或跨阶段替代。

「经营毛利」词条同句复述一遍。两处都把「分别计入一次」与「不得视为已净含贷项」当成**可核对的
要求**在写。

## 登记册实际记了什么（取证 `35564ad`）

`settlement_accounting.operating_result`（`0005_cost_allocation_operating_result.sql`）把组成放在
一列 jsonb：`components`。表上唯一的形状约束是 `operating_result_components_shaped`——
**只要求它是非空数组**，对元素形状一字不管。

元素形状由写侧定，见 `adapters/postgres/operating_result.go` 的 `componentRow`：

    source       -- 来源金额身份
    effect       -- 对指标的影响，封闭二向 INCREASES / DECREASES
    amountMinor  -- 金额

**三个键，没有角色维。** 元素上没有任何东西说得出这一项是「客户运营应收」还是「审核应付」还是
「供应商费用贷项」。

## 差在哪儿：那条硬句成了验证不了的话

「审核应付与贷项按各自借贷方向分别计入一次」要能核对，至少得答得出两问：

1. 这份快照里，**哪一项是审核应付、哪一项是与它关联的贷项**？
2. 两者**是不是各计了一次**（而不是一项已经净含了另一项）？

拿着 `(source, effect, amountMinor)` 三元组，两问都答不出。`source` 是一个标识引用，
读的人得先去别的册子把它认出来才知道它是什么角色——而那正是「临时推断」。于是：

- **「不得把审核应付视为已净含贷项」在册上无法证伪。** 一份已经净含贷项的快照，与一份规矩地
  分列两项的快照，在 `components` 上可以长得一模一样（同样是若干个 `source/effect/amount`）。
  写侧就算真的净含了，也没有任何约束或读面会红。
- 这与本模块别处的做法不一致：`supplier_expected_cost` 把「原币／结算币／换算依据」整组显式成列，
  正是为了让「整组出自同一个评价」这件事看得见；`external_funds_fact` 的 `kind` 用封闭集，
  `operating_result.basis` 用封闭三格。**唯独组成项的角色靠读的人自己认。**

## 这处出入在管理台上的样子

「经营核算」页骨架有四栏是照 CONTEXT 这句写的：**客户侧采用、供应商侧采用、其中：审核应付、
其中：供应商费用贷项**。页面注释还专门写着「两栏并置呈现组成，不预先净额」。

票 [admin-skeleton-closure-batch/04](../../admin-skeleton-closure-batch/issues/04-settlement-accounting-http-read-faces.md)
的对栏裁定把这四栏**全撤了**，改为按组成逐项呈现（来源、增减向、金额）。理由记在那张票上：要填
这四栏，读面得先判断某个 `source` 属于哪一类，而那恰恰是这句硬句想让人**看见**的东西——由读面代贴
标签，等于把它重新藏起来，且藏得比现在更深（页面上会出现四个看起来有依据的数）。

所以页面那一侧已经收口了：**不假装能分辨**。但那四栏原本要呈现的东西，是 CONTEXT 明确要求可见的。

## 补与不补，各自的连带

### 若给组成项加角色维

- 元素加一个封闭集的角色键（客户运营应收／客户预估费用／供应商预期成本／审核应付／供应商费用贷项
  ／内部成本／赔付／追偿／分摊／汇兑……）。**封闭集怎么切要先裁**：CONTEXT 按三种口径各自点名了不同
  的采用物，角色集若不按口径分组，会出现「这个角色在这个口径下不该出现」而册上拦不住。
- 落约束的位置有两处可选，代价不同：写在 `CHECK` 里（要 `jsonb` 逐元素校验，本模块尚无先例）；
  或写在写侧重建时的复验里（已有先例——组成与毛利是否相符就是在写口复验的）。
- 加了角色维之后，「审核应付与贷项各计一次」才**可能**成为一条能落的约束（同一口径下两个角色各至多
  一项，且贷项在场时应付必须在场）。是否落这条约束是另一个裁量。
- 表当前 0 行，jsonb 列改元素形状无需迁移改表，但**已有的写侧与读侧要同步**，否则读回的旧形状会
  译不出角色。
- 读面连带：票 04 撤掉的四栏可以按角色分组重新算出来并加回；读面仍不做判断，只按册上的角色分组。

### 若不补

- 需要有人明说：**「分别计入一次」是写侧纪律，不要求在登记册上可核对**。这是个站得住的立场——
  本仓别处也有「不变量由写口守、读口不重算」的先例（毛利本身就是这么处置的：读面照册转写不重算）。
- 但代价要认下来：毛利那条的守卫在写口是**真的存在**（重建时复验组成与毛利相符），而
  「审核应付未净含贷项」在写口**有没有对应的复验**，需要一并核实。若两处都没有，那这句硬句就是
  完全空转的，那就该改文档而不是留着。
- 管理台那四栏永久撤销，页面注释里「两栏并置呈现组成，不预先净额」那句应跟着改——它现在承诺的
  东西册上给不出。

## 边界

本票**不改表、不建列、不写迁移、不动领域模型、不改元素形状**。不构成票 04 的阻断：读面按册上实有的
三个键照实转写，补不补角色维都成立。
