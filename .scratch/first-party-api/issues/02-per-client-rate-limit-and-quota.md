# 按 client 的限流与配额：`429` + `Retry-After`，缺省朝拦

Category: enhancement
Status: draft
Blocked by: ADR-0139 接受；首方 Intake 实施票

取证基线 `a608536d`。

## 问题

首方 API 一旦对外，没有按调用方的速率与配额保护，一个写错重试循环的客户系统就能把 `parcel-api` 与它背后那只库拖慢，而受害的是同一租户下的其他客户。ADR-0139 只裁了「谁能进」，没裁「能进多快」。`docs/api` 方案稿把 `429` + `Retry-After` 列进了对外契约示例与「幂等、分页、限流」约定，本仓没有落点。

## 做什么

1. **限流键是渠道行（client），不是 IP。** IP 在 NAT 与云出口后面没有身份意义；渠道行是首方族里唯一可信的调用方身份（两步校验之后才知道是谁）。因此限流**在校验之后、编排之前**——放在首方渠道 Intake 里或紧贴它的一层，不在路由层（ADR-0055 Decision 一：路由层不知道渠道）。校验不过的请求（`401`）走不到限流，它们的保护靠上游（网关 / WAF），那是部署形态，不在本票。
2. **两个量：速率与配额。** 速率按滑动窗口或令牌桶（实现票选，写明理由）；配额按自然日 / 自然月计数。两者的**取值**是运营参数：可配置、**不设默认**——按 AGENTS 红线，没登记的租户就没有限流值，而没有限流值的形状是「拒」还是「不限」要裁：倾向**未配置即不限流但出声**（启动日志与指标写明该 client 无限流配置），因为把「没配」答成 `429` 会让集成方去改一个不存在的频率问题——恢复动作指错，正是 ADR-0029 那条分格判据要防的。这一条在票面裁决段落定。
3. **答复形状**：`429`，`Retry-After`（秒），问题详情（ADR-0140 Decision 三）带稳定码 `RATE_LIMITED` / `QUOTA_EXCEEDED` 两格——恢复动作不同（等一会 vs 等下个周期或找租户运营提额），不合并。`429` 是 4xx，按 ADR-0022 离线客户端出队交人——**这一格要在契约文档里单独说明**：`429` 是唯一「重发会改变结果」的 4xx，客户端按 `Retry-After` 重发是正当的；文档必须写明这是 ADR-0022 三类表的显式例外，而不是让集成方自己猜。
4. **限流值挂在渠道行上**（与 scope、账户集同列），由租户运营在管理台写面登记（ADR-0085）；参数登记册增行「客户 API 速率与配额」（实例半边）。
5. **可观测**：被限的调用计数按 client 维进指标（票 03），管理台客户渠道页显示当前用量与上限。
6. **不做**：全局限流（那是部署形态，网关做）；按租户总量限流（先看有没有证据需要）；对操作者 API 限流（客户端与后端同版本发布，滥用不是它的威胁模型）。

## 验收点

- 同一 client 超速率答 `429` + `Retry-After` + `RATE_LIMITED`；超配额答 `429` + `QUOTA_EXCEEDED`；两格测试各一。
- 未登记限流值的 client 按票面裁决的形状（不限 + 出声 / 拒）行事，测试钉住。
- 限流状态在多实例部署下的一致性（进程内计数还是共享存储）——实现票写明取舍，若共享存储则不引入新依赖（用既有 PostgreSQL），理由同 ADR-0049「无负载证据不分布」。

## 归 owner 复核

- 「未配置即不限流但出声」还是「未配置即拒」——产品与运营决定。
- 配额周期（日 / 月 / 计费周期）是否与商业合同挂钩——PC owner。
- `429` 作为 ADR-0022 三类表的显式例外，要不要给 ADR-0022 加一条部分补记——倾向不动 ADR-0022，只在契约文档说明；若 owner 认为要进 ADR，另立小记录。
