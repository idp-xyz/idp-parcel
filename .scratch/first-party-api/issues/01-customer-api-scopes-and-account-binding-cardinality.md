# 客户 API 的 scope 模型与 1:N 账户绑定

Category: enhancement
Status: draft
Blocked by: ADR-0139 接受；首方 Intake 实施票（ADR-0139 Consequences 首条）

取证基线 `a608536d`。

## 问题

ADR-0139 立的客户渠道册一行绑定唯一（租户，客户账户），一枚令牌过了三格就拿到该账户下**全部**客户面能力：提交、撤回、取消、补充、资料修订、索赔提交、追踪查阅。两件事今天没有形状：

1. **能力粒度。** B2B 集成里「这个 client 只能查轨迹、不能提交」是常见要求（财务系统、BI 抓数、只读监控）。操作者族已有「授予按能力面显式登记」（ADR-0100 Decision 二），客户族没有对应物。
2. **绑定基数。** 平台型客户（电商平台、货代 SaaS）一个系统代多个货主账户。ADR-0139 风险点 5 已把它从「既有渠道适配」纠回「首方族自己的绑定模型问题」，并指出 1:N 要求「请求里认领账户并按行上的授予集核对」，与 ADR-0100 的授予集同形。

两件是同一张表的两列：能力集与账户集都挂在渠道行上。

## 做什么

1. **scope 词表由产品定义，按客户面能力分。** 候选粒度：`shipments:submit`、`shipments:withdraw`、`shipments:cancel`、`shipments:supplement`、`shipments:amend`、`claims:submit`、`tracking:read`、`webhooks:manage`。词表进 ADR-0140 的契约（OAuth2 Security Scheme 的 `scopes`），是对外承诺的一部分。**是否在令牌里带 `scope` 声明**还是只登在册上：倾向后者——ADR-0139 的判据是「授权数据归产品、不塞进令牌」，令牌只证明「你是谁」，能做什么由册答；发行方侧的 scope 只作请求提示，不作准入依据。这一条要在票面裁决段落定，若与发行方形态冲突回 owner。
2. **每条渠道行带授予集**（scope 集合 × 生效区间 × 可撤销），登记走管理台写面与受控 CLI（ADR-0085），与操作者册的授予同形。缺授予的调用答 ADR-0139 Decision 四的**第三格**（`403`，恢复动作在租户运营），不新造第四格——授予缺失与行不在册的恢复动作同侧。
3. **1:N 绑定**：渠道行从「绑唯一客户账户」改为「绑账户集」，请求里由客户系统**认领**本次操作的客户账户（载荷里的一格，进契约），`Minter` 在 `seal` 前核对认领的账户在行的账户集内；不在即第三格。`SourceEnvelope` 四要素不变——铸出来的信封仍带唯一客户账户，只是这个账户是「认领并核对过的」而不是「行上唯一的」。1:1 是 1:N 的特例（账户集只有一个元素、可省认领）。
4. **不做**：跨租户的账户集（ADR-0003）；令牌里自报租户；scope 的「通配」取值。

## 验收点

- 契约里每个客户面 operation 声明所需 scope；缺 scope 的调用在传输层测试里答第三格。
- 报文里认领一个不在行账户集内的账户，铸出的信封不变（`ErrCredentialRejected` 或同格），测试钉住——ADR-0003 边界在 1:N 下的落法。
- 1:1 行不带认领字段照旧可用，回归测试不动。

## 归 owner 复核

- scope 词表的粒度（按端点还是按用例）——PS / VE owner。
- 令牌里带不带 `scope`——与 ADR-0141 风险点 1（发行方形态）一并。
- 1:N 下 webhook 订阅按账户还是按 client——ADR-0142 风险点 6。
