## 缺口（评审 ← 通道 2 钉 `aa48912e`，逐符号名；推送方未复量，作者开工先复）

## 裁决（2026-09-15 15:2x 通道 1 按用户「自决」代裁，SA owner 口径；依据是下方 Comments「取证 ← 通道 2 · 钉 `93840328`」(1)–(6) 与 29 裁决 0–4；本票代码取证锚 main `d02fd926`）

0. **事实照收（取证条已量实，不再重量）**：ID = `租户 + "/funds-fact/" + 事实 + "/" + 版本`，三引用只经 `newRequiredValue` 非空门、无长度上限；`Store.Enqueue` **先 `Validate` 再任何 SQL**，`ErrInvalidEnvelope` 是导出哨兵；`handOffFact` 不分错误种类一律折续办、不返 error；`AdoptFact` / `CorrectFact` 与 `existingFact` 三条路都到它。由此在单事务入口（CLI，31 落地后端点同形）下，「行已落、信封未出、续办引用非空」这一格**只由 Go 侧确定性错误到达**——依赖故障（Outbox SQL 错）会把事务打进中止态、`WithinTransaction` 返 error、CLI 未决 3 且版本行不落。所以 27 那句「重跑同一命令补发同一封」在它今天唯一能到的因下恒假。
1. **要裁的 1——指纹化，helper 提炼到 `internal/platform/outboxintent` 导出，CC 三只改引。** ID = 口名前缀（`"funds-fact"`，与分区键口名段同词）+ `"/"` + `sha256(租户 / 事实 / 版本)` 十六进制——定长、必在 128 内、同输入同 ID；载荷三维（`tenantId` / `fact` / `version` / `corrects,omitempty`）照旧；`Subject`（事实 / 版本）与 `PartitionKey`（租户 / funds-fact / 事实）**保留可读形不哈希**（照 29 判断项 ③ 的同一取舍：能超 512，超了按裁决 2 响亮失败，不静默）。**helper 放哪**：CC `fingerprintEventID` 未导出、SA `adapters/postgres` 导 CC 包被 `boundaries_test` 挡；`internal/platform/outboxintent` 头注自述「三个上下文的适配器落出同形后按 rule-of-three 提炼至此」且已被 SA / CC 两侧 handoff 同时导入——本票是第四个调用方，提炼条件成立：新导出 `outboxintent.FingerprintEventID(portName string, dimensions ...string) eventing.EventID`（形与 CC 私有那只一字不差：`portName + "/" + hex(sha256(strings.Join(dimensions, "\x00")))`），CC 三只 `dutyPaymentVerificationEventID` / `gateVerificationEventID` / `verificationEventID` 改引它、私有 helper 删——**零行为**：三只 ID 字面不变，29 的定长 / 可重算用例零改（若它们经私有 helper 算期望值，改引导出的那只）。[34](34-cc-five-remaining-event-ids-still-concatenate-references.md) 落地时五只同引。**为什么不在 SA 再写一份**：两份同形 helper 是「同一张脸再长一回」，29 裁决 1 拒的正是这个。
2. **要裁的 2——`handOffFact` 只对确定性拒分出一格：返错、整笔回滚；其余错误照旧折续办。** (a) `errors.Is(err, eventing.ErrInvalidEnvelope)` → handoff 适配器包成 SA 哨兵 `ports.ErrFundsFactHandoffRejected`（形照 CC `ports.ErrHandoffEnvelopeRejected`），`handOffFact` 把它**原样返回**，`AdoptFact` / `CorrectFact` 随之返 error（不是 outcome）——版本行、信封、结果三者同生同灭，`existingFact` 路同样返错（重放同一超长引用永远同一结果，不该答`已存在`）。CLI `execute` 对它归 **用法格 `exitUsage`（1）**并打出原因：按 ADR-0029 恢复动作判据，什么都没登记、要改的是输入（引用长度）或形，不是「重跑」——归未决 3 会让人重跑到预算耗尽，那正是 29 缺口节点名的反例。裁决 1 落地后 (a) 在 ID 上不再发生，留它是为 `Subject` / `PartitionKey` 与将来任何确定性校验错（29 裁决 2 (b) 的同一句理由）。(b) 其余错误（依赖不可用、marshal、键缺席）**照旧折续办**、outcome 不翻、`FundsHandoffReference()` 非空、CLI 未决 3 并打「重跑补发」——这句对依赖故障是真的（`existingFact` 路重放会再交一次，取证 (2)）；今天在事务入口下它到不了（SQL 错先把事务打进中止态），**判断项写实这一点**，不删这一格：删它要动 `FundsResult` 的形与 27 / 31 两口的答案格，是另一张票的量，而它今天不说假话。**为什么不学 29 (b) 进硬失败哨兵名单**：SA 采用口没有派发器、没有重投预算——两个入口都是人发起的单次调用，「人动手」在这里就是非零退出码加原因，不需要第二种结构。
