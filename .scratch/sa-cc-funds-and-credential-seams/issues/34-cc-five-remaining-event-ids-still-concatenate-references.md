## 裁决（2026-09-15 15:3x 通道 1 按用户「自决」代裁，CC owner 口径；依据是下方 Comments「取证 ← 通道 6 · 钉 `93840328`」与 29 裁决 0–2、32 裁决 1–2；本票代码取证锚 main `760332c7`）

0. **事实照收**：五只都经 `outboxintent.EnqueueOnce`，都只 `%w` 包、没一只对 `eventing.ErrInvalidEnvelope` 分格；引用维全经 `newRequiredValue` 无长度门（`ExternalResultKey.SourceID` 是裸 `string` 连构造函数都没有）；失败全折续办挂结果、无一在重派路上；**五只里只有 `externalResultEventID` 有生产装配**（`cmd/parcel-api/assemble_external_results.go` → `/customs/external-results`，Intake `UnconfiguredIntake{}` 起步，续办引用经 HTTP `handoffReference` 有读者），且它的事件类型零消费者；`customsCaseEventID` / `externalResultEventID` **把 ID 直接当 `PartitionKey`**；有消费者的两只（customs-case / declaration-submission → VE）消费侧有自己的幂等键 `ports.FactKey{Tenant, Source, Fact, Version}` + 内容摘要；`func \w+EventID\(` 那条 grep 漏两只：`follow_up_handoff.go`（`followUpPartitionKey` 四维串接直接作 ID，串接形第六只）与 `restriction_handoff.go`（单一 `RestrictionID`，无上界非串接）。
1. **范围——七只一次同改，不分「今天到得了 / 到不了」。** 五只 + follow-up + restriction 全走指纹形。**为什么连 restriction 也改**：它不是串接，但同一句理由成立——单一引用的长度也是实例半边，本仓给不出上界；留一只等于留一张脸。**为什么连四只零生产装配的也改**：29 裁决 1「留两只带同一个潜伏缺口等于让同一张脸再长两回」——入口接上那一天没人会回头改 ID 形，改形那一刻消费方已经按旧 ID 去重过。做法候选 2（只改到得了的）由此否决。
2. **helper 归属——本票把 `fingerprintEventID` 提炼到 `internal/platform/outboxintent` 导出为 `FingerprintEventID(portName string, dimensions ...string) eventing.EventID`**（实现一字不差：`portName + "/" + hex(sha256(strings.Join(dimensions, "\x00")))`），29 的三只改引、私有 helper 删——零行为、三只 ID 字面不变、29 用例零改。理由与 32 裁决 1 同：`outboxintent` 头注自述 rule-of-three 提炼位、已被 SA / CC 两侧同时导入，跨上下文私有符号导不到（`boundaries_test`）；32 Blocked by 31 晚于本票，所以提炼归本票、32 只引（32 票面已注）。
3. **ID 形——口名前缀 + 全维哈希；分区键与 ID 解耦，可读形一字不变。** 每只一个口名常量（`customs-case` / `carrier-manifest` / `declaration-submission` / `case-closure` / `external-result` / `follow-up` / `restriction`，与既有 `*PartitionKey` 或事件类型的口名段同词），维度 = 今天串接进 ID 的全部维（含 `caseClosureCycle` 的整数字面、follow-up 三个后缀各自作一维——`base` / `replacement-proposed` / `replacement-effective` 三封 ID 互异这一点必须保住）。**`customsCaseEventID` 与 `externalResultEventID` 今天 `PartitionKey: eventID`——改成分区键取今天那一串可读形（五维 / 两维串接原样），只有 `ID` 换指纹**：分区键是顺序语义（同案件同分区），改它会让换形前后同一案件落两个分区，而 `internal/architecture/partition_subject_registry_test.go` 登的正是分区主体形；其余五只分区键本来另算、不动。`Subject` 七只都不动。**为什么不把分区键也哈希**：与 29 判断项 ③ / 32 裁决 1 同一取舍——可读形留给运维、超 512 按裁决 4 响亮失败。
4. **失败响法——只在唯一有生产装配的 `externalResultEventID` 那一路分格，形照 32 裁决 2。** `external_result_handoff.go` 对 `errors.Is(err, eventing.ErrInvalidEnvelope)` 包 `ports.ErrHandoffEnvelopeRejected`（29 已有的哨兵，同包同名不新造）；`ReceiveExternalResultHandler.handOff` 对它**返错**、`Handle` 随之返 error、`transactionalResults` 回滚——结果行与信封同生同灭；`customshttp.NewReceiveExternalResultEndpoint` 把它映成 4xx problem（作者照该端点既有 `writeProblem` 形定码写判断项），不再折成 `handoffReference` 让人重试到死。其余错误照旧折续办（对依赖故障那句是真的）。**其余六只的 `handOff*` 不动**——它们今天从生产到不了，分格的正确位置是把它们接上入口的那张票（那张票的地盘含各自 handler），本票在 spec 行记一句残差、不写进六只头注（头注里指将来的票会烂）。**为什么不进硬失败哨兵名单**：外部结果口是 HTTP 单次调用，没有派发器与重投预算，「人动手」就是 4xx。
5. **消费门幂等——VE 靠 `FactKey` + 摘要，不靠信封 ID，真库钉住有消费者的两只。** customs-case / declaration-submission 换形前后同一事实各发一封 → Inbox 门放行第二封 → VE `DeriveProjectionHandler` 同键同摘要答 `FactExistingResult`、不重派生。判据 (4) 用真库钉；manifest / case-closure / external-result / follow-up / restriction 零消费者，无幂等题（接上消费者的票自带）。已入 Inbox 的旧 ID 不重算、不迁移。
6. **做法写实**：(1) `internal/platform/outboxintent`：新文件导出 `FingerprintEventID` + 用例（定长、同输入同值、前缀互异则 ID 互异、`\x00` 拼接让「a/b」+「c」与「a」+「b/c」不同）；(2) CC `adapters/postgres` 29 的三只改引、删私有 helper；(3) 七只各加口名常量、ID 改 `FingerprintEventID(口名, 维…)`；`customs_case_handoff.go` / `external_result_handoff.go` 的 `PartitionKey` 改取原串接形（抽成各自 `*PartitionKey` 函数，形照其余五只）；载荷、`Subject`、事件类型全部不动；(4) `external_result_handoff.go` 拒收分格 + `receive_external_result.go` `handOff` 返错 + 端点 4xx；(5) 用例：manifest 的字面 ID 断言改 helper 重算、字面分区键断言**保留**（它证的正是分区键不变）；其余各只的 `*EventID` 重算 helper 改成调导出的 `FingerprintEventID` 或断定长 / 可重算；customs-case / external-result 各加一格「分区键仍是可读串接、ID 已非该串」；(6) 判据 (4) 真库格放 `cmd/parcel-dispatch/assemble_test.go`（29 判据 (4) 的同位，走生产路）或 VE `adapters/customscompliance` 测试。**不动**：迁移；七只载荷；事件类型；VE 消费方；05 / 29 / 32 语义；`endpoints.go` / `main.go`（端点映射改在 `customshttp` 包内，不碰共享接线文件；若必须碰，占号）。
7. **完成判据写实**（替换上方「待裁后写实」三条）：(1) 七只 ID 定长且 ≤ `eventing.MaxEventIDLength`，用超长合成引用（串接形下 > 128 字节）构造信封仍入队成功；同输入同 ID；follow-up 三封 ID 互异。(2) `customsCaseEventID` / `externalResultEventID` 所在信封的 `PartitionKey` 与 `760332c7` 上的字面**一字不变**（用例以字面断言）；其余五只分区键零改；`partition_subject_registry_test.go` 零改仍绿。(3) `git grep -n fingerprintEventID -- internal/` 零命中；`FingerprintEventID` 定义在 `outboxintent`、CC 十处引用（29 三只 + 本票七只）；29 的用例零改。(4) 真库：同一 customs-case 事实以两个不同信封 ID 各投一封到 VE 消费者 → 投影一份、第二封 `FactExistingResult`；declaration-submission 同形一格。(5) `/customs/external-results`：以超长 `SourceID` 把 `PartitionKey` 顶过 `MaxPartitionKeyLength` → handler 返 `ErrHandoffEnvelopeRejected`、结果行零、信封零、端点 4xx；依赖故障格照旧折续办（既有用例保留）。(6) `gofmt -l` 空、`go vet` 0；带 DSN CC `adapters/postgres` + `adapters/http` + `cmd/parcel-api` + `cmd/parcel-dispatch` + VE `adapters/customscompliance` + `internal/architecture` PASS 非 SKIP；迁移零 diff。(7) 清点在 tip 干净检出重生成：`internal/platform` 生产 +1 / 测试 +1，CC 零变（不增删文件），作者预报。
8. **能力边界**：裁的是范围、helper 归属、ID 与分区键解耦、失败分格的位置、幂等靠谁；具体不变式（七个口名字面、follow-up 三维怎么进哈希、`*PartitionKey` 函数名、4xx 取哪个码）归作者按代码定并写进判断项。读过：取证条全文、29 裁决 0–2 与完成记录「裁决 1——helper 与三只口」、32 裁决 1–2、`outboxintent` 头注（经取证引文）。**没读**：七只 `*_handoff.go` 正文、`receive_external_result.go` 正文、`customshttp` 外部结果端点、VE `DeriveProjectionHandler` 正文。作者量到与代码不符，以代码为准并写进判断项，不回头等我。
