## 第 2 项：ADR-0371（PS owner；授权等级一格兼 PC owner）

- **决定一**：方向认可。请求方记货主客户账户、实际提交方记仓配履约，授权另走授予，这与 PS CONTEXT「来源请求身份」「它只用于来源重放与冲突分类，不授予查询或操作权限」不冲突。但清单漏了补充，见阻断 2。
- **决定二**：PS 与 PC 都是有条件认可，条件见阻断 1。症结是：PC 的授予是「动作 × 等级」，而提交、补充、撤回、取消在 PC 册上没有动作可落。
- **决定三**：认可。
  - ADR-0132 决定二原文是「续办触发是**处置命令自身**，不新增信封类型」，「不新增信封类型」的主语是续办触发。它的 Alternatives 否决「处置已完成」信封，理由是「多一封信封就多一个驱动点」。
  - 「委托待受控补充」本上下文不消费，也不驱动接受链。PS CONTEXT 写了「它同样是发布意图，续办照旧由新提交版本已形成的信封驱动」，ADR-0371 的「对已接受记录的作用」也写明 ADR-0132 决定二不停用。所以不需要部分停用。
  - 进入等待受控补充有两条路：链里遇到客户可补充缺口，或授权处置选交客户补充。两条都在各自事务里交这封信封，没有漏的。
- **决定四**：认可。载荷取证属实。PS「当前资料采用判断」说待补充的续办方是客户，这一来源由代办方补，读得通。
- **决定五**：认可。与上轮条件一致，另加了「信封标识取决定标识，接受链再跑一轮时补交的是同一封」，与上轮取证的 `acceptance_decision_handoff.go` 以决定标识作信封标识相符（本提交未动 `internal/**`）。
- **决定六**（产品 owner 一格，代看）：认可。
  - 会话把用户的「集货到海外，然后走的本地小包」读作起运侧集货、干线出境、尾程交本地小包。这正是开发主线「小包专线与货代」一行「头程自营或半自营、尾程交末端渠道」的形态，委托仍是国际小包，客户群不变。
  - 那一行的「把这段单独对客销售是常见产品线」留给另立的 ADR，没有借这次把它读进来，做法对。
  - 措辞与读法的提醒见非阻断 4、5。
- **读法限定的形式**：认可。
  - README 把「改为、接上、扩成、按口解、收窄」都算部分停用，前提是改掉了前一份记录的条款。
  - ADR-0370 决定一、三没有一句提海外仓或目的国。海外仓发往当地的件，按 PS「委托」词条「客户要求运营企业为一个或多个包裹提供同一项约定国际小包服务的业务请求。」本来就不是委托。所以决定六没有改掉 ADR-0370 的哪一句，只是把既有定义的后果写在旁边。
  - 先例是 ADR-0015 的注记「**读法限定**（不是停用）」。ADR-0370 的注记逐字引了两句原文，并写「本记录正文不改写，其余内容不变」。

**PS owner 结论：有条件认可。** 阻断 1、2 照下文改法落地后，即算「PS owner 认可」，PC owner 那一格同样算认可。届时作者可以去掉 ADR-0371 的「待 PS owner 复核」，在越权风险点后补 owner 复核记录；非作者评审只需核对落地文字与改法一致。**现在还不说「PS owner 认可」。**

## 第 3 项：SA owner

读了结算与经营核算 CONTEXT（Status: Confirmed）：「结算账户」与「结算归属日」两个词条，确认费用、确认依据与 SELL 发起几条规则，费用来源一句，以及仓配履约的所有权一句。另读了 CONTEXT-MAP `warehouse-fulfillment → parcel-pricing / settlement-accounting`、UC-SA-002 仓储那一行，和仓配履约 CONTEXT 的「收费发生项」。

**一致的部分：**

- SA「费用引用……仓储作业收费发生项……但不得修改这些来源。」与仓配履约「本上下文不带金额，也不据它们改写发生项」一致。
- 仓配履约「同一作业事实至多形成一份发生项，重放答已有的那一份。发生项形成之后不改写；来源事实被更正时追加更正版本，指名被更正的那一份。」正合 SA「来源不可改」。
- 计费日不冲突。仓配履约写「凡按日计的（库龄、仓租计费日、日终在库）都按仓的业务时区；仓的业务时区没登记时这些都答未配置。」SA「结算归属日」是「由费用类型和合同规则决定、用于判断费用归入哪个结算周期的业务日期」。计费日是发生项的业务日期，归属日仍由 SA 定。

**缺的部分**（UC-SA-002 那一行只记了第三条，见阻断 3）：

1. **商业依据没有来处。**
   - SA 规定：「每条确认费用必须固定责任法人、结算相对方、收付方向、结算账户、合同或责任依据、结算币种、主要计费范围和来源事实。任何一项不能通过当前组织、当前客户属性或报表筛选临时推断。」
   - 包裹那一路靠接受时固定的商业解析回指（ADR-0190）。仓储发生项只有「作业种类、货主、仓、业务时间、来源事实引用，以及一组计量与作业属性」，没有可回指的东西。
2. **没有确认依据可用。** SA 规定「确认条件按费用项目点名要哪一种确认依据……产品内置一种：`有效交付已终局`」。那是包裹的终局，仓租、入库作业这些费用项目照现行规则会永远停在未确认。
3. **没有发起路。** SA 写「SELL 评价按包裹计费时点发起」，发生项原因触发册又「只回答发不发起、不铸造评价请求」。仓储发生项因此没有发起 SELL 请求的路。
4. **更正怎么成调整没定。** SA 的调整分「计价纠错类」与「商业让利类」，发生项的更正版本归哪一类、怎样成为费用调整，没有说。

**SA 结论：有条件认可。** 条件见阻断 3。这只是补差距记录与 CONTEXT-MAP 的待定格，不需要新 ADR：要立的那份 ADR，ADR-0368 决定七已经要求了，这里只是扩它的范围。

## 阻断

**1. ADR-0371 决定二在 PC 授权册上落不了（阻断 PS 与 PC 认可，也阻断合入）**

- **文件**：ADR-0371 决定二；参与方与商业 CONTEXT Rules。
- **原文**：
  - 「形照 ADR-0311 的 `CUSTOMER_SELF_SERVICE`：等级只在一处定义，含义是「仓配履约以货主名义代办来源为仓配出库的委托」；登在 PC 授权册上，租户的控制点是有没有给这个货主客户账户授予这一等级。」
  - 「没有授予时，四种请求都答`未配置`」
  - 「撤回时，仓配履约在这份授予下就是货主的当前有效授权代表。」
- **为什么**：
  - PC 的授予是「动作 × 等级」。ADR-0311 决定一原文：「租户是否放行，就是授权册里有没有一条 `SOURCE_DATA_AMENDMENT` × `CUSTOMER_SELF_SERVICE` 的授予」。
  - `AuthorizedAction` 里没有提交、补充、撤回、取消。
  - PC CONTEXT 规定：「接受后客户原始资料的修订是与人工复核、主动拒绝并列的授权动作，同样按责任法人、角色、适用范围和有效期间版本化，三者互不蕴含、不得互相顶替。」所以资料修订那条授予不能拿来放行提交与撤回。
  - 照现在的文字，提交与撤回去问 PC 时没有动作可问，实现只能自造。
  - 取消还另有一处缺口：ADR-0310 决定三的参考配置是「客户系统可在收寄前取消」，管的是客户系统；同一条规则管不管仓配代办，没有定。
  - 「等级只在一处定义」也没说定义在哪一处。ADR-0311 决定一点了名：`adapters/partycommercial` 的 `CustomerSelfServiceAuthorityLevel`。
- **改法**（ADR-0371 还没进 main，在本分支改正文，不另立 ADR）：
  - **决定二改为**：
    - PC 授权册新增一个授权动作「仓配代办」。租户按货主授予「仓配代办 × `WAREHOUSE_FULFILLMENT_AGENT`」，法人与范围照 ADR-0311 决定二，读该客户账户的解析键登记行。
    - 提交、补充、撤回问这一条授予。包裹取消也问这一条，另外还要租户的取消授权规则里有一条管仓配代办，没有就答`未配置`。资料修订问 `SOURCE_DATA_AMENDMENT × WAREHOUSE_FULFILLMENT_AGENT`（即 ADR-0311 的问法）。
    - 两条授予互不蕴含，哪一条没授予就答`未配置`。实际决定方是货主客户账户本身，合同委派不参与。
    - 点名等级常量的定义处（与 `CustomerSelfServiceAuthorityLevel` 同包）。
  - **PC CONTEXT Rules**：在「受控关闭与重开是与前述各动作并列的两个授权动作……」之后加一句：「仓配代办是与前述各动作并列的授权动作：`warehouse-fulfillment` 以货主名义提交、补充、撤回与取消来源为「仓配出库」的委托；它同样按责任法人、等级、适用范围和有效期间版本化，与资料修订互不蕴含；实际决定方是货主客户账户本身，合同委派不参与（ADR-0371）。」
  - **仓配履约 CONTEXT** 预取那句：「该货主有代办授予」改为「该货主有仓配代办与资料修订的代办授予」。
  - **UC 差距记录**：PC 授权裁定的 UC（即 UC-PS-002 那一行引的 UC-PC-003）在「给开发的交接」加一行，记新动作未做。UC-PS-001、005、006 各行在「代办等级」处补上动作名。

**2. 补充不在代办请求清单里（阻断 PS 认可，也阻断合入）**

- **文件**：
  - ADR-0371 的 H1、决定一、决定二；
  - PS CONTEXT「来源请求身份」末句；
  - 仓配履约 CONTEXT「本产品网络」那条规则；
  - CONTEXT-MAP `warehouse-fulfillment → parcel-shipment`。
- **原文**：
  - 决定一：「提交、资料修订（资料补充/更正请求）、撤回与包裹取消：请求方记出库请求所属的货主客户账户……」
  - 决定二：「没有授予时，四种请求都答`未配置`」
  - 决定三：「以货主名义提交新提交版本，补充基准取信封里的提交版本」
- **为什么**：
  - 补充是自成一口的请求。ADR-0310 的标题列了「首方客户命令五口（撤回、取消包裹、资料修订、补充、索赔）」；其决定二写「补充 = 账户绑定 + 授予 + 基准版本核对」。PS CONTEXT 也写「判断遇到客户可补充缺口 → 等待受控补充：补充形成同一委托的新提交版本」。
  - 决定三让仓配做补充，决定一、二却只列了四种请求。补充由谁请求、凭什么授权、没授权怎么答，都没有定。
  - 来源请求键也有同样的缺口。提交键是（出库请求，包裹序号），其余代办请求的键没有定。ADR-0310 决定一正是因为「提交的键是裸标识、与五口的键同在 PS 一个判重空间」，才给各命令加了前缀。
- **改法**：
  - 决定一的清单加「补充（停在等待受控补充时形成新提交版本）」，H1 与「四种」随之改。
  - 决定二写明：补充问「仓配代办」，并核对基准版本，过期答 `SUPPLEMENT_BASIS_STALE`（照 ADR-0310 决定五）。
  - 决定一再补一句：「提交之外各代办请求的来源请求键照 ADR-0310 决定一加命令前缀，不与提交键相撞」。
  - PS CONTEXT「来源请求身份」、仓配履约 CONTEXT、CONTEXT-MAP 三处的清单同样加上补充。

**3. SA 的差距记录不全（只阻断转 Confirmed，不阻断合入）**

- **文件**：UC-SA-002「给开发的交接」仓储那一行；CONTEXT-MAP `warehouse-fulfillment → parcel-pricing / settlement-accounting`。
- **原文**：
  - UC-SA-002：「未做：评价请求里没有按仓储作业收费发生项发起的 SELL 请求，也没有接它的消费门；计价那边为它立评价对象的 ADR 落地之前，也形成不了评价」，承接列为「仓配切片立票时承接，计价评价对象的 ADR 先行」。
  - CONTEXT-MAP：「计价要为它立新的评价对象（仓租还要按持有期计），另立 ADR；」
- **为什么**：第 3 项列的商业依据、确认依据与更正这三格是规则层面的差距，不只是代码没写。不记下来，那份 ADR 会被当成只属计价的事。
- **改法**：
  - UC-SA-002 差距列在原文之后补：「发生项不带接受时的商业解析，确认费用要固定的责任法人、结算相对方、结算账户、合同或责任依据与主要计费范围没有来处，不得按当前客户属性推断；内置确认依据只有包裹的`有效交付已终局`，仓储费用项目无依据可确认；发生项的更正版本怎样成为费用调整未定」。
  - 承接列改为「仓配切片立票时承接，计价评价对象与结算发起、商业依据、确认依据的 ADR 先行」。
  - CONTEXT-MAP 那句后补：「同一份 ADR 还要定结算怎样为它发起 SELL 请求、它的商业依据在哪一刻由谁固定、用什么确认依据确认」。

2. **ADR-0370 复核记录里有一处跨文件计数，也没提偏离。**

3. **「不出库确认」的定义没盖住「才能出库确认」。**
   - 文件：仓配履约 CONTEXT 出库规则。
   - 原文：定义句是「本文说的「不出库确认」都指作业端不交出」；另有两处用「才能」的写法：「只有委托已被接受、包裹没有有效取消的才能出库确认」，以及生命周期里的「更正被采用之后才能出库确认」。
   - 问题：照字面读，「才能出库确认」仍可能被读成写口拒绝。
   - 改法：「本文说的「不出库确认」「才能出库确认」，都指作业端交不交出」。
4. **决定六的「集货仓」用错了。**
   - 文件：ADR-0371 决定六。
   - 原文：「仓在起运侧（如国内的集货仓、备货仓）」。
   - 问题：集货仓收的是已成的包裹，那是节点作业的收寄；仓配履约的仓存的是货主商品库存。这个例子把两种身份混了。
   - 改法：「仓在起运侧（如国内的自营仓或代理仓）」。
5. **决定六依赖对用户原话的一种读法。**
   - 依据：票 04 写「会话的判断：这是网络服务产品——起运侧集货、干线到海外、尾程交本地小包」。

   - 这是产品 owner 一格，用户可以推翻。下次碰到用户时请他用一句话确认读法；在那之前不改。
6. **代办规则重述了三处，PS 那句位置也不妥。**
