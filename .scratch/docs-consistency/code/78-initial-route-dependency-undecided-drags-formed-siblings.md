## 现象

票 155 之后，重投推不动的那几格入账为`路由未形成`，不再连坐。依赖类未决（判断库、证据、商业适用性、交接登记读不回，取号故障，证据连续换代，成本读不回，未形成原因写不进）照旧交 `ErrRouteHandoffUndecided`，消费门整封回滚重投。`InitialRoutes.Save` 与消费门同一事务，同一交接里已判成的包裹计划随之回滚，重投时按判断键再判一次，可能判出别的结果。

UC-NR-001 `AT-NR-012`「同一委托三个包裹分别可路由、确定无路由和依赖未决——三个包裹分别保留计划、无路由和未决结果；任一结果不回滚或掩盖其他结果」里依赖未决那一件因此仍未实现。证据只记 `S`（读码）。

## 三类

机制。规模 M。租户取值：无。

## 修法候选

- **(a) 判成的包裹照常提交，未决那一件单独入队逐包裹的重试信封**（推荐）：接受决定信封入账；依赖未决的那件包裹由本上下文交一封自投的逐包裹重试信封，分区按（租户，包裹），重试预算与失败码照派发器的未决口径。要定：信封的事件类型与分区登记、重驱的原料从哪里来（判断键与交接关联在本上下文，商业解析标识回 PS 接受决定，地理投影不在 NR 落库——与票 154 同一问）。
- **(b) 逐包裹 savepoint**：同一事务里每件包裹一个 savepoint，未决那件回滚到它自己的 savepoint、其余提交。不推荐：消费门入账了，未决那件就没有东西再来问它，等于把依赖类未决变成一个更安静的永久停滞（ADR-0094 决定四的理由）；而且要让应用层看见事务边界。

## 验收

- `AT-NR-012`：同一委托三个包裹分别可路由、确定无路由和依赖未决，三件各保留自己的结果——计划与无路由判断越过提交边界、交意图，依赖未决那件依赖恢复后自己判成，不回滚、不重判另外两件。
