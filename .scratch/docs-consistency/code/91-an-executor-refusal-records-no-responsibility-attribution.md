# 91 揽收的执行方拒收不存责任归属：UC-TF-002 结果契约要保存的「责任方」没有一格

## 现象

UC-TF-002 结果契约「本次对象被拒收」要保存「对象、原因、责任方、证据和此前控制方」。code/01 立了执行方拒收一格（`EXECUTOR_REFUSED`），存了原因与证据（依据），执行方随尝试保存；「责任方」没有一格。执行方作出拒收不等于责任归执行方——包装不合格的拒收，责任多半在交运一方。

## 证据（读码，只记 `S`）

- 文档：
  - UC-TF-002 结果契约「本次对象被拒收」：必须保存「对象、原因、责任方、证据和此前控制方」。
  - UC-TF-002「给开发的交接」：「本次对象被拒收要保存责任方」一行，去处是本票。
  - GLOSSARY「物理状况观察」：损坏原因、责任方、索赔和赔付结论「由拥有相应判断的上下文形成，不能由状况观察直接推导」——同一道理，责任归属不能从「谁拒收了」推出来。
  - TF CONTEXT「揽收、派送与交付」：揽收拒收是执行方明确不接收的决定，原因与证据随拒收保存（不写责任方）。
- 代码：
  - `domain.ExecutorRefused` 头注：拒收的责任归属不由这一格推导，也不另存。
  - `domain.AttemptObjectResult` 只有尝试、对象、结果、依据、来源与时刻；`domain.FulfillmentAttempt.ExecutedBy` 是执行方，不是责任方。
  - `transport_fulfillment.pickup_attempt_result`（迁移 0002、0050）没有责任一列。

## 三类

机制：责任归属若要保存，是一格带依据的判断（谁判、凭什么）。产品策略：哪几种拒收原因默认归哪一方，若要随产品给参考配置，属产品策略。租户取值：具体归属规则与合同约定留给租户，不设默认。

## 规模

S–M：取决于裁定。只加一格「责任归属待判」占位是 S；要带判断主体、依据与版本、并接进失败尝试费或客户沟通是 M。

## 最小的诚实修法

1. 先裁「要不要另立一格、由谁判」（见下）。裁定之前不加字段，也不从执行方或原因推一个责任方。
2. 若裁为另立：责任归属作为一份带依据的判断随拒收或之后单独形成（判断主体、依据引用、时刻），不嵌进执行方报回的那一格——执行方报的是事实，归属是判断，两者来源不同。
3. 读它的消费方（失败尝试费、客户沟通、异常案件）各自声明是否依赖它；不依赖的照旧按依据判。

## 要裁的

- 责任归属要不要另立一格，还是留给拥有相应判断的上下文（结算判成本责任、全程追踪与异常判服务责任）各自形成、TF 只存事实。
- 若另立，由谁判：执行方当场报（与事实混在一起）、运营复核时判，还是按合同规则自动派生。
- UC-TF-002 结果契约「必须保存 … 责任方」那一格，是改成「原因与证据，责任归属由某上下文另判」，还是照留并由本票落一格。
