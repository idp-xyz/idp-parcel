### PS-01 新提交版本取代旧版本时，旧版本已成立的控制项占用无人释放

- **类别**：4
- **位置**：`internal/parcelshipment/application/form_new_submission_version.go` 与 `internal/parcelshipment/domain/submission_supersession.go`，两处都没有释放调用。全 `application` 包里，`ReleasePreAcceptanceControl` 只出现在拒绝、撤回、授权处置三条路上，以及 `form_acceptance_decision.go` 的 `releaseIfRejected` 里。
- **证据**：
  - PS CONTEXT 词条「控制项结果」：「任一项成立即表示提供方账本上形成了占用；接受确定未成立时必须按原业务关联请求释放，不论接受侧结论如何。」
  - 词条「授权处置」：「两者都按原业务关联释放本版本已成立各项的占用」。ADR-0132 给的理由是，选交客户补充的那一刻，这一版的接受已确定不成立。
  - 代码路径（读码推断）：
    - 可达性答资料不足时，`domain.ReachabilityCheckFor` 记 `CheckUndetermined`，但 `AdvanceAcceptanceJudgmentHandler` 记下判断后仍交 `AcceptanceJudgmentAdvanced`。
    - `AdvanceAcceptanceChainHandler` 因此照常进入财务控制并形成占用，`Decide` 再把任务停在`等待受控补充`。
    - 客户补件走新提交版本，旧版本被取代，但它的占用没有释放。`ControlReleaseRequest` 按提交版本认领，新版本的控制顶不掉旧的那一笔。
- **归类**：C
- **严重度**：高。客户的预付冻结或账期额度会被永久占住。
- **建议修法**：立代码票。新提交版本形成的同一笔里（或经续办信封），对被取代版本中 `OccupationFormed()` 为真的结果按原关联发释放，失败时按 `ControlReleasePending` 续办。补一条「资料不足 → 已占用 → 补件」回归测试。

### PS-02 面单渠道服务包裹的取消不核实际承运商收寄、终局边界和既有终局

- **类别**：4
- **位置**：`internal/parcelshipment/application/cancel_parcel.go` 的 `CancelParcelHandler.Handle`。它在提交边界上只重读 `Adoptions.FindResponsibilityStart`，也就是网络收寄的采用链；终局库和承运商首次有效收寄都不读。
- **证据**：
  - PS CONTEXT Rules：「面单渠道服务包裹只允许在实际承运商收寄前且面单服务终局边界尚未成立时取消」，以及「面单渠道服务发生实际承运商收寄或其他约定终局边界后，包裹不得回退为“已取消”」。
  - UC-PS-006 `AT-PS-086`：「包裹已有终局后请求取消｜返回既有终局」。
  - 面单渠道包裹的终局来自 `JudgeLabelServiceFinal`，不经采用链，所以这条编排在承运商收寄之后仍可能交出 `PARCEL_CANCELLED`。
  - 今天生产里取消授权停在 `AUTHORITY_UNCONFIGURED`，暂时挡住了；租户一登记授权，这条路就生效。
- **归类**：C
- **严重度**：高
- **建议修法**：立代码票。提交边界上先读当前有效终局，有终局就交既有终局；再按服务形态核边界：网络服务读采用链，面单渠道服务读承运商首次有效收寄，以及合同声明的其他终局边界。

### PS-03 收寄在业务时间上早于取消、取消先提交、收寄消息后到：三处给了两种结果

- **类别**：2
- **位置**：
  - UC-PS-003 `AT-PS-045`：「收寄事实先发生，取消消息后到 | 按业务时间保留责任起点；取消不能追溯抹去收寄」。
  - 同文件「取消与收寄并发按权威业务时间和生效边界裁决，不按消息到达顺序。」
- **证据**：
  - 代码 `adopt_network_intake.go` 在这种情况下交 `IntakeCancellationOrderConflict`（未决），测试「an intake that happened before the cancellation stalls as a conflict」断言的就是这个。
  - UC-PS-006 决定矩阵「收寄事实存在但有效性或业务顺序待确认 | 取消/处置未决」，`AT-PS-081`「取消与处置均保持未决」。
  - CONTEXT「并发收寄已经先行成立时不得提交取消，消息晚到不能改变这一裁决」里的「先行成立」可以读成业务时间在先，也可以读成提交在先。
  - 另外，代码拿取消的 `RequestedAt`（请求时间）去比，注释写的却是「取消决定」。
- **归类**：B（无 ADR 裁过，三处各执一读）
- **严重度**：高。照 `AT-PS-045` 实现，同一包裹会同时带取消终局和责任起点。
- **建议修法**：立 ADR 代决，倾向认可代码的「事实冲突、未决」，并定下比较的是哪个时刻。随后改 `AT-PS-045`、UC-PS-003 那句和 CONTEXT 那句。详见 `ps-uc.md` PS-UC-01。

### PS-04 撤回只释放「资金冻结」：CONTEXT 规则与 UC-PS-005 同病，与「控制项结果」词条、ADR-0125 和代码相反

- **类别**：2（兼 1）
- **位置**：
  - PS CONTEXT Rules：「已经形成的接受前资金冻结必须通过原业务关联请求 `settlement-accounting` 显式释放；撤回提交和释放属于可补偿编排」。
  - UC-PS-005「本用例包含」：「对已形成的接受前资金冻结发出使用原业务关联的显式释放请求。」
  - UC-PS-005 步骤 6：「按原业务关联幂等形成适用冻结释放」。
  - UC-PS-005 `AT-PS-074`：「未形成过资金冻结 | 撤回成立并保存财务补偿不适用依据」。
- **证据**：
  - 同一份 CONTEXT 的词条「控制项结果」：「任一项成立即表示提供方账本上形成了占用；接受确定未成立时必须按原业务关联请求释放」。
  - ADR-0047：账期控制形成的是信用暴露，不是冻结。
  - ADR-0125 Context 点名过这个孤儿占用（「`CREDIT_EXPOSED` 从不释放」），决定四改为按 `OccupationFormed()` 释放。
  - UC-PS-001 `AT-PS-035`：「按原关联释放已成立各项形成的占用（冻结与信用暴露）」。
  - 代码 `WithdrawShipmentRequestHandler.releaseOccupation` 的判据是 `recorded.FinancialControl.OccupationFormed()`。
- **归类**：A
- **严重度**：高。照 `AT-PS-074` 写，只做了信用校验的委托撤回后不会释放信用暴露。
- **建议修法**：
  - CONTEXT 那条改为「已成立控制项形成的占用（冻结或信用暴露）」，并引「控制项结果」词条。
  - UC-PS-005 三处同改；`AT-PS-074` 改成「未形成任何占用」，再加一行「仅信用校验成立 → 按原关联释放信用暴露」。
  - `releaseOccupation` 头注「从未形成过冻结时」一句随票改，属 C 低。

### PS-05 UC-PS-001「结果语义契约」与提交编排的实际结果对不上：缺`已提交`、`准入暂停`、两种关联指名格，又列了提交口从不交的三格

- **类别**：4（兼 2）
- **位置**：
  - UC-PS-001「结果语义契约」表共八行：已接受、已拒绝、已有结果、尚未决定、接入冲突、输入未受理、非本产品生产归属、生产归属未决。
  - 同文件 `AT-PS-101`：「答复`已提交`，逐件带回……」。
- **证据**：
  - 代码 `application.SubmitOutcome` 有九值：`SUBMITTED`、`EXISTING_RESULT`、`INGRESS_CONFLICT`、`INPUT_NOT_ACCEPTED`、`OTHER_PRODUCTION_AUTHORITY`、`OWNERSHIP_UNRESOLVED`、`ADMISSION_PAUSED`、`PRIOR_REQUEST_NOT_FOUND`、`LINK_INELIGIBLE`。
  - `OutcomeAdmissionPaused` 的头注是「与 OutcomeOwnershipUnresolved 分开，因为暂停回答的是本产品当前是否接纳新准入，而不是这个范围归谁」，`blockedOutcome` 照此分格。
  - ADR-0022 Context 也列了七种：「`已提交`、`已有结果`、`接入冲突`、`输入未受理`、`非本产品生产归属`、`生产归属未决`、`准入暂停`」。
  - ADR-0081 决定二：「HTTP 答复停在`已提交 / 尚未决定`」，接受链由信封驱动。
  - ADR-0140 决定一规定首方契约的 `outcome` 封闭词表「取应用结果枚举的原名」，所以这张表就是对外契约的语义源。
- **归类**：A
- **严重度**：高。照这张表实现首方契约或管理台，会把暂停并进归属未决（代码头注明说这样会丢失事实），还会漏掉两个关联格。
- **建议修法**：
  - 拆成两张表：「提交答复」按九格写，每格注明 UC 原名，暂停单列并写明理由；「接受判断结果」写已接受、已拒绝、尚未决定，注明由「委托已提交」信封驱动（ADR-0081）。
  - 顺手补一句「提交编排不执行接受条件判断」，让 ADR-0081 那句引用有着落（见 PS-32）。

### PS-06 `已提交`委托在决定前重组成员无路可走：CONTEXT 和 BD 简报都承诺能做，代码刻意关了这个方向

- **类别**：4（兼 1）
- **位置**：
  - PS CONTEXT Rules：「接受决定前……删除、拆分、重组成员，或者改变客户账户、合同责任范围、寄收件关系或目的服务范围时，必须形成一份或多份关联新委托并保留原成员去向」。
  - 委托生命周期：「成员重组或共享约束变化建立关联新委托」。
  - UC-PS-001 业务决策简报 BD-PS-007 边界示例：「客户可以在决定前明确重组，重组后的委托各自取得完整决定。」
- **证据**：
  - `domain.RequestLinkKind` 头注：「刻意没有「已提交」方向：待决委托的普通纠错走同一委托的新提交版本（BD-PS-005），给它开关联方向等于给绕过版本机制留门。」
  - `OutcomeLinkIneligible` 头注把客户指去「资料修订（待决）或等决定」。
  - 新提交版本要求成员集合等值：ADR-0045 第 4 条写「增删拆并是「成员重组」，CONTEXT 判给关联新委托（`AT-PS-036` 第二、三支……）」，但那两支分别是已拒绝和已接受，不是已提交。
  - 结果是只剩「先撤回、再以 `WITHDRAWN_RESUBMISSION` 重提」一条路。CONTEXT 没写这条路，也没写重组之后原委托怎么处置。
- **归类**：B
- **严重度**：高。读者会以为客户在决定前可以直接重组，接口却答 `LINK_INELIGIBLE` 并把人指错路。
- **建议修法**：立 ADR 代决两件事：
  - 原委托在重组后的去向：明定「先撤回、后关联」为唯一路径，或新增「待决重组」方向，在同一笔里停止原任务并释放占用。
  - 据裁决改 CONTEXT 委托生命周期、BD-PS-007 示例和 `request_link.go` 头注。越权风险点要写进「多了一条绕开版本机制的路」。

### PS-08 越权或跨客户请求的结果，各 UC 写法不一，与 CONTEXT「统一不可见结果」相抵

- **类别**：2（兼 6）
- **位置**：

### PS-10 ADR-0017 与 ADR-0026 在「持久化能不能写」上相抵，两份都没写停用关系

- **类别**：3
- **位置**：ADR-0017 决定：「PostgreSQL Repository 实现、迁移、事务与 Outbox 仍然阻断，仍不得建立本地框架替身。」后果节：「「无持久化」与「无事件机制」仍阻断于 Bento 闸门」。Status 行只有「Accepted」，Links 里没有 0026。

- **归类**：B。要裁的是 0026 是否构成对 0017 那一句的部分停用，以及适用场景怎么写。
- **严重度**：中
- **建议修法**：修订票代决。在 0017 的 Status 行与 Links 补部分停用：那一句的适用场景收窄为「登记为发布基线」，「仍不得建立本地框架替身」不变；0026 的 Status 行同补。写明越权风险点。

### PS-11 ADR-0081 决定六的四个「留 nil」格已全部填上，Status 行却写「其余各格仍有效」，所引原句也不逐字
