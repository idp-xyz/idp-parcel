## 高

### H1 `AT-SA-179` 仍写「补登声明之后这一份也不回补」，与 ADR-0229 的续办和同表 `AT-SA-189`、`AT-SA-195` 相反

- **类别**：2（同一类场景两条 AT 结果不同）
- **位置**：`docs/application/settlement-accounting/UC-SA-002-CALCULATE-CONFIRM-AND-ADJUST-OPERATIONAL-CHARGES.md`，`AT-SA-179`：「SELL 请求记待判断，不形成费用、不换写金额，入账不重投；补登声明之后这一份也不回补（ADR-0198 决定二）」。
- **证据**：
  - ADR-0229 决定五那张表：「价卡 | 没有在用价卡、……、取整未声明、……」，也就是说价卡登记能续办「取整未声明」；ADR-0234 决定四回答了 ADR-0229 越权风险点 6：登一版新卡并收尾旧版，收尾同笔交的那封信能续办出评价。
  - 同一张表里，`AT-SA-180`（评价失败）写「补登参数之后经续办另起新一代」，`AT-SA-195` 写「停在计价或采用那一段的请求，租户补登了解得开它的参数（价卡、映射等）| 续办出下一代」。
  - 代码：`domain.EvaluationStopCause.ResumedBy` 对 `StopAmountRoundingUndeclared` 返回 `kind == ParameterPriceCard`。
  - 根因：ADR-0229 Consequences 只列了「改记 `AT-SA-180`、`AT-SA-183`、`AT-SA-186`」，漏了 179。
- **归类**：A
- **严重度**：高。照这一行写测试会断言「补登卡后不再形成费用」，与已实现的续办相反。
- **建议修法**：`AT-SA-179` 改成「SELL 请求记`待判断`、停因取整未声明，入账不重投；登一版声明了取整的新卡并收尾旧版后，经续办另起新一代（ADR-0229 决定三、五，ADR-0234 决定四）」，并去掉「不回补」。

### H2 多份 UC 写「未登记则待判断」，而已接受 ADR 定的是「没登记答未配置」，代码交的也是 `*_UNCONFIGURED`

- **类别**：2（UC 与 ADR、代码相反）
- **位置**（逐字）：
  - UC-SA-002 主流程步 2：「发生项原因已登记「发生项形成」时，结算才提交……；没登记则待判断，不发起请求」。同一步后半又写「没登原因或没登费用项目答未配置」，一步之内自相矛盾。
  - UC-SA-001 步 6：「文法数值未登记则待判断」；UC-SA-001 输入表「商业责任」行：「未配置时保持待判断」。
  - UC-SA-003 步 2：「归属日按已登记形态判定；没登记则待判断」。
  - UC-SA-004 步 5：「上限未登记则待判断」。
  - UC-SA-006 步 3：「分法未登记则待判断，不默认按重或均摊」。
  - UC-SA-007 步 3：「文法数值未登记则待判断，不把主张直接当成金额」。
- **证据**：
  - 各 ADR 都写「没登记答未配置」：ADR-0164 决定三、ADR-0161 决定三、ADR-0162 决定四、ADR-0163 决定三、ADR-0168 决定三。
  - 代码结果码：`BUY_EVALUATION_TRIGGER_UNCONFIGURED`、`ALLOCATION_FORM_UNCONFIGURED`、`CHARGE_ATTRIBUTION_UNCONFIGURED`；另有几处在`*_UNDECIDED`结果下带未配置原因：`AUDIT_UNDECIDED` 带 `AUDIT_ESCALATION_UNCONFIGURED`，`CLAIM_UNDECIDED` 带 `CLAIM_GRAMMAR_UNCONFIGURED`，`ADVANCE_UNDECIDED` 带 `RECOVERY_GRAMMAR_UNCONFIGURED`。无论哪种写法，都没有交「待判断」的。
  - AGENTS.md 红线：租户取值「那一格如实答`未配置`」。
  - 各 UC 自己的「待判断结束」指的是「依据不足」，和「租户没登」恢复动作不同（ADR-0094、ADR-0229 按停因续办）。
- **归类**：A。附带一条待核：UC-SA-004、UC-SA-007 和 UC-SA-001 的代码把未配置收在`*_UNDECIDED`结果下当原因，另几只编排则单立`*_UNCONFIGURED`结果，结果代数不统一。这是否违反 ADR-0029 的分格，归 SA owner 看，本轮不改代码。
- **严重度**：高。读者会把「租户没登」误判成「依据不足」，新写的编排和管理台文案也会跟着出错。
- **建议修法**：上面各处统一改成「没登记答`未配置`（ADR-xxxx 决定 x），补登之后……」；UC-SA-002 步 2 前半句直接删掉，由后半句的 ADR-0208 写法替代。

### H3 CR：同一笔本金可以多次「自外部来源入账」，与 CONTEXT「资金只能自外部来源入账一次」相反；CONTEXT 也没定清楚真实到账那一层是入账还是移位

- **类别**：4（文档与代码不一致），并带 1（CONTEXT 本身没定清）
- **位置**：
  - `docs/domain/collection-remittance/CONTEXT.md` Rules：「资金只能自外部来源入账一次，且入账必须以一笔已接受的代收事实为依据」；「同一笔代收事实不得重复入账」。
  - 同文件 Lifecycles 两句各自都放行：「代收事实已接受 → 入账记账：自外部来源移入`渠道在途`或（真实到账时）`待清分`」；「`渠道在途` → `待清分`：渠道回款对应的真实资金事实已接受」。
- **证据**：
  - `internal/collectionremittance/application/post_subledger.go` 的 `PostSubledger` 只按记账标识判重放。`factPostingShapeHolds` 只核「去向等于该事实的入账位置、金额等于事实金额」，不查这条事实是否已经入过账。所以同一条事实换一个记账标识可以再入一次。
  - 收件人付款、渠道代收报告、渠道回款通知三层的 `IntakePosition` 都是`渠道在途`，每层各自全额入账，同一包裹的同一笔钱会在账上记两三遍。
  - 同一条运营企业真实到账事实可以既入账到`待清分`，又再凭它把`渠道在途`移到`待清分`；移位那一笔金额不受事实金额约束。
  - 迁移 `collection_remittance/0001_collection_subledger_and_remittance.sql` 的 `subledger_posting` 只有主键 `(tenant_id, posting_ref)`，没有按（依据种类、依据引用）的入账唯一约束。
- **归类**：B。要先裁两件事：一是四层事实里哪一层负责入账、其余层只做移位或旁证；二是真实到账遇到已由渠道层入账的本金时，走入账还是走移位。裁定之后另立代码票，补「一条事实至多入账一次、移位金额以事实为限」。
- **严重度**：高。受托保管的是客户的钱，重复入账会让`应付客户`超过真实到账。
- **建议修法**：立 ADR 代决，写明入账层与移位层；CONTEXT Lifecycles 两句随之收窄；立代码票补唯一性与金额上限。

### H4 CR CONTEXT 写「来源侧更正或撤销 → 追加更正事实与反向记账」「任一方向的错记 → 反向记账冲正」，而 ADR-0082 明写入账无法冲正，代码也拒

- **类别**：1（CONTEXT 写的现行规则与 ADR 相反）
- **位置**：`docs/domain/collection-remittance/CONTEXT.md`
  - Lifecycles「代收事实与入账」：「来源侧更正或撤销 → 追加更正事实与反向记账；原事实与原记账原样保留，当前余额由全部记账重新派生」。
  - Lifecycles「分户账资金位置」：「任一方向的错记 → 反向记账冲正」。
- **证据**：
  - ADR-0082 Consequences：「**入账无法冲正。** 去向侧没有账外位置，反向那一笔落不下来……那笔钱在账面上如何退出，本切片**不猜**」。
  - 代码 `post_subledger.go` 的 `BasisCorrection` 分支：「入账无法冲正……来源侧记错走追加更正事实，其账面处置尚无定论（本切片明确不猜，见 ADR-0082 的代价一节）」，原记账来源不在账内时答 `NOT_ACCEPTED`。
- **归类**：A
- **严重度**：高。运营照 CONTEXT 去冲正一笔错入的本金，只会被拒。作者照 CONTEXT 实现，又会造出 ADR 明确不给的出账口。
- **建议修法**：两句改成「账内位置之间的错记走反向记账冲正；入账（自外部来源）不能冲正，来源侧更正只追加更正事实，本金如何退出账面待真实退款与银行退回形态到来时另裁（ADR-0082 Consequences）」。

### H5 CR 的`短款`同时被定义为「资金位置」和「实收少于指令的差额」，与分配守恒冲突；按 CONTEXT 写出的代码会把已到账的本金挪进`短款`，客户少拿钱

- **类别**：1（CONTEXT 自身不自洽）
- **位置**：`docs/domain/collection-remittance/CONTEXT.md`
  - Language「资金位置」：「`短款`（实收少于指令的差额已确认落在此处）」。
  - Language「分配守恒」：「全部非外部资金位置的余额之和恒等于自外部来源入账的金额之和」。
  - Lifecycles：「`待清分` 或 `应付客户` → `短款`：差异事项已登记且短款结论已确认」。
- **证据**：
  - 差额那部分钱从没进账。按守恒，`短款`里的余额只能从已经到账的钱里挪过去。
  - `internal/collectionremittance/application/handler_test.go` 的短款用例就是这么做的：指令 12000，真实到账 10000 全额入到`待清分`，再把 2000 从`待清分`移到`短款`。结果只剩 8000 能进`应付客户`，而实际到账是 10000。
  - `discrepancyPostingShapeHolds` 不限来源位置。
  - Lifecycles 也没有任何一条从`短款`出去。
  - 只有「渠道层先按报告金额入了`渠道在途`、真实到账少于报告」这一种形态下，`渠道在途` → `短款` 才是守恒的。
- **归类**：B。要裁`短款`的表示法：是只记在差异事项上、不占资金位置，还是只允许从「已报告未到账」的`渠道在途`落入。这与 H3 的入账层裁定连在一起。
- **严重度**：高。直接少付客户代收本金。
- **建议修法**：与 H3 同一份 ADR 代决。CONTEXT 的「资金位置」词条与短款那条 Lifecycle 随裁定改写，改完另立代码票，限制短款记账的来源位置并修正测试。

  - SA CONTEXT：「对账周期、业务时区、截单时刻属于对账安排，付款条件属于商业结算政策。结算账户登记册不另存一份」。
- **归类**：A
- **严重度**：中
- **建议修法**：拆成两行：「结算账户」（五格）和「对账安排 / 结算政策」（周期、时区、截单时刻、付款条件，各引其权威）。

### M7 对账单纳入不核「结算归属日」，归属日判定也没接进任何进程；CONTEXT 与 UC-SA-003 写的是现行规则

- **类别**：4
- **位置**：

- **证据**：
  - `domain.CutStatementDraft` 只核 `charge.Stage() != ChargeConfirmed`（→ `CHARGE_NOT_CONFIRMED`），没有任何归属日判断。

  - ADR-0168 越权风险点 3：「截单编排不调用这次判定」。
- **归类**：C（文档是现行规则，代码未落）
- **严重度**：中
- **建议修法**：立代码票，让截单编排读已形成的归属日，或在费用确认时形成归属日。CONTEXT 在落地前加一句现状注记，指向 ADR-0168 越权风险点 3。
