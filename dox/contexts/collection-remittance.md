# 代收与清分（`collection-remittance`）

代码在 `internal/collectionremittance`，登记口在 `cmd/parcel-collection-register`。对照 main `99fc0037d`（2026-11-12）写成。

**这份文件核到什么程度**：取值表、登记与记账的十种答案、「一笔记账允许的形」、入口四处是从代码里读出来的。「规则」与「生命周期」的句子是从旧 `docs/domain/collection-remittance/CONTEXT.md` 提炼的，每条只确认了代码里有对应的机制（类型、函数、测试名或库上约束），没有逐条跑测试验证行为；旧文档写了而代码里没有的，单列在最后一节。

## 管什么，不管什么

管：运营企业受客户委托、由渠道向收件人代收的货款本金——代收指令、代收事实的接受、代收分户账及其记账、资金位置余额的派生、回汇批次、汇付主张、差异事项、认可的协议抵扣的登记。

**代收款是客户的钱，不是运营企业的收入。** 全部账面都是受托保管口径。

不管：

- COD 服务费、协议允许的抵扣金额及其认可、运营应收应付、结算账户——`settlement-accounting`。两边不共享表，只以引用交接；本金不与这些钱在账内净额。
- 包裹身份与客户代收服务要求快照——`parcel-shipment`。只引用。
- 履约侧代收证据、渠道代收报告、渠道回款通知的原件——`transport-fulfillment`。只引用。
- 客户合同与代收商业责任——`party-commercial`。
- 真实付款、银行清算、总账。本上下文只到汇付主张为止，不建支付通道集成。
- 汇率、回汇周期、手续费、支付通道。属租户取值，代码里没有任何默认值，也不做折算。

## 词

| 词 | 意思 |
|---|---|
| 代收指令 | 对一件包裹成立的一项代收义务：金额、币种、责任法人、货主客户、代收渠道，并引用客户代收服务要求。不是收款事实 |
| 代收事实 | 一次已接受的收款主张或资金事实，带金额、发生时间、来源层级与来源证据引用 |
| 来源层级 | 代收事实属于四层中的哪一层，见取值表。四层彼此独立，不得互相推导 |
| 代收分户账 | 按（货主客户，责任法人，币种，代收渠道）隔离的一本受托保管账，开立时带保管依据引用。不持有余额字段 |
| 资金位置 | 本金在账内所处的受托状态，封闭词表。外部来源不是资金位置，只作入账的来源侧 |
| 分户账记账 | 一条只追加的记录：一笔正金额自一个位置移到另一个位置，带依据种类与依据引用 |
| 入账记账 | 自外部来源把本金移入账内，本金进账的唯一形 |
| 移位记账 | 凭依据把本金从一个账内位置移到另一个账内位置 |
| 分配守恒 | 一本账内全部账内位置余额之和恒等于入账金额之和 |
| 回汇批次 | 一次周期归集：冻结分户账键与归集截点。成员就是引用它的汇付记账，不另持成员清单 |
| 汇付主张 | 对外表达「这批本金应当付给该客户」。不是真实付款 |
| 差异事项 | 实收与指令不一致时登记的待处置事项（短款或溢款）。是声明，不自行动账 |
| 认可的协议抵扣 | `settlement-accounting` 认可的、渠道按协议从回款里扣下的金额在本上下文的登记。只钉认可引用，不动账 |
| 已采用事实 | `settlement-accounting` 已采用、且已整条认作代收本金的外部资金事实。真实到账的证据引用指向它 |
| 链头 | 已采用事实此刻的最新版本及金额。到账登记时读到的版本钉在到账上 |

## 登记与记账的十种答案

每次登记或记账落在下面一格。退出码是 `cmd/parcel-collection-register` 的。

| 答案 | 什么时候 | 之后 | 退出码 |
|---|---|---|---|
| `REGISTERED` | 本次落册或落账 | — | 0 |
| `EXISTING` | 同键已在册且内容相同（重放） | — | 0 |
| `HANDED_OVER` | 本次交出汇付主张 | — | 0 |
| `ALREADY_HANDED_OVER` | 已经交出过 | 不算新的推进 | 0 |
| `NOT_ACCEPTED` | 输入缺格或形状不对 | 改请求 | 1 |
| `CONTENT_CONFLICT` | 同键异内容；或依据已支撑过另一笔；或已采用事实容不下到账 | 人核对既有登记，绝不覆盖 | 2 |
| `BASIS_MISSING` | 依据不在册，或分户账没开立 | 先把上游那一笔登进来 | 2 |
| `BATCH_CLOSED` | 批次已交出汇付主张 | 形成新批次 | 2 |
| `UNDECIDED` | 依赖故障，落没落未知 | 重跑同一命令 | 3 |
| `UNDERFUNDED` | 来源位置或该指令名下余额不足，确定没落账 | 等上游那一笔后重跑同一命令 | 4 |

重放判定先于一切按此刻状态作答的门：已落的记账重放答 `EXISTING`，不答余额不足。

## 一笔记账允许的形

| 从 → 到 | 依据种类 | 金额 |
|---|---|---|
| 外部来源 → 渠道在途 | `COLLECTION_FACT`（只认渠道代收报告） | 等于报告金额 |
| 渠道在途 → 待清分 | `COLLECTION_FACT`（只认运营企业真实到账） | 等于到账金额 |
| 待清分 → 应付客户 | `ALLOCATION`（一条代收指令） | 不超过位置余额 |
| 应付客户 → 已汇付 | `REMITTANCE_BATCH`（仍在已归集态的批次） | 不超过位置余额 |
| 渠道在途 → 短款 | `DISCREPANCY`（短款事项） | 等于事项金额 |
| 待清分 → 溢款 | `DISCREPANCY`（溢款事项） | 等于事项金额，且等于按指令算的溢款 |
| 溢款 → 应付客户 | `DISCREPANCY`（溢款事项） | 可部分 |
| 渠道在途 → 已抵扣 | `AGREED_OFFSET` | 等于登记的认可额 |
| 原记账的反向 | `CORRECTION`（被冲正的那一笔） | 等于原金额 |

记账输入里没有分户账键，也没有币种：键由依据推出，币种取自那本账。

## 规则

**代收义务与实收事实**

- 代收指令必须同时给出包裹、服务要求引用、金额与四维分户账键；缺任何一格不落册，不以默认值补齐。指令金额币种必须是那本账的币种。
- 代收事实必须声明来源层级并带来源证据引用。四层分别保存，任何一层不被另一层覆盖或推导。
- 交付证明不能替代代收事实；渠道报告已代收不等于已回款；渠道通知已回款不等于真实到账。
- 指令、事实、差异事项、认可的协议抵扣都只追加。重放同一份答已在册，同键异内容答内容冲突，不覆盖。

**真实到账**

- 运营企业真实到账只经 `settlement-accounting` 的采用进入，本上下文不自铸资金事实。它的证据引用必须指向一条已采用事实；读不到（没采用、没认作代收本金、别的租户）答依据不在册。
- 登记时按事实此刻的链头判三条：到账币种等于指令所属那本账的币种，也等于事实的币种；引用同一条事实的各条到账金额之和不超过链头金额，超出的那一条答内容冲突、不截断；一条事实对同一条指令至多一条到账。
- 登记在按事实引用取的锁下读回名下已有到账再判，并发的另一路读得到。读到的版本钉在到账上。
- 移位之前再读一次事实：结算把它更正小、容不下名下全部到账之和时，移位答内容冲突，账面不动。没有钉版本的到账答依据不在册。

**分户账与记账**

- 分户账键四维齐备且不为空。币种在键上，一本账内不发生换算。
- 记账只追加，不修改不删除。金额为正，来源与去向不同，去向必须是账内位置。
- 本金只凭已接受的渠道代收报告入账，只入`渠道在途`。收件人付款与渠道回款通知是旁证，登记在册、不记账。
- 同一条代收事实至多支撑一笔记账；换一个记账标识再凭它记账是内容冲突。
- 任一账内位置的余额不得为负；不足时答余额不足，不透支后再补。余额在取了这本账的锁之后、同一笔事务内读回再判。
- 余额只由记账派生，没有设置余额的入口。派生时核分配守恒，核不过即账面已坏。
- 账内位置之间写错，追加一笔原记账的反向同额冲正；原记账留在账上。一笔记账至多被冲正一次，第二次是内容冲突，先于余额判断。
- 入账不能冲正：去向侧没有账外位置。

**清分、汇付与差异**

- 未实际收到的代收款不得进入`待清分`、`应付客户`、`溢款`或`已汇付`。只有真实到账支持`渠道在途` → `待清分`。
- 自`渠道在途`移出的金额按指令算上限：不超过该指令名下的`渠道在途`余额，同账别的指令的在途款不算进来。不够时整笔答余额不足，不先移一部分。
- 清分凭一条在册的代收指令，只有`待清分` → `应付客户`这一跳。单凭代收事实不能让本金进`应付客户`。
- 进入`已汇付`必须引用一个仍在已归集态的回汇批次；分户账取自批次。
- 短款不通过缩小指令抹平，溢款不直接计入应付客户款：都要先有差异事项，再凭它记账。
- `短款`只从`渠道在途`落入，不超过该指令名下的`渠道在途`余额。该指令有已登记而未移位的到账时不落短款。
- `溢款`只从`待清分`落入，金额必须等于：该指令移入`待清分`的到账 − 指令金额 − 该指令已落入`溢款`的金额。报少了不受理。
- 指令金额与报告之差从没进过账，只留在差异事项上，不记账。

**认可的协议抵扣**

- 登记只钉认可引用与金额，不动账；指令必须在册，币种是指令所属那本账的币种。同一份认可落到同一条指令上至多一条记录。
- 落账只有`渠道在途` → `已抵扣`一种形，全额一次，一条认可至多一笔。该指令有未移位的到账时抵扣等着，到账先移位。
- 离开`已抵扣`只有冲正。冲正之后同一条认可不能再落，要落走新的认可。
- `已抵扣`是本金去向，不是结算余额，也不表示结算那边的应收已核销。

**回汇批次与汇付主张**

- 批次形成时冻结分户账键与归集截点；重放时这两格不同是内容冲突。没有删除、重开、取消的入口。
- 批次状态只朝一个方向走。交出汇付主张之后不再收新的汇付记账。
- 交出汇付主张不等于付款成立。

## 生命周期

- **代收指令**：登记即固定，不随实收改变。应收与已收之差由分户账与差异事项表达。
- **代收事实**：登记即固定。渠道代收报告 → 可凭它入账一次；真实到账 → 可凭它移位一次；另两层只留在册上。
- **本金在账内**：外部来源 → `渠道在途` → `待清分` → `应付客户` → `已汇付`。旁路：`渠道在途` → `短款`；`渠道在途` → `已抵扣`；`待清分` → `溢款` → `应付客户`。任何账内一跳都可被冲正一次，冲正本身也可被冲正。
- **回汇批次**：已归集 → 已交出汇付主张。要改归集范围，形成新批次。
- **差异事项**：登记 → 凭它落账。短款落账后渠道补付的，先冲正短款那一笔回`渠道在途`，再凭新的真实到账移位。
- **认可的协议抵扣**：登记 → 凭它落账。认可被撤回，冲正已落的那一笔；被更正，冲正旧的、登记并落新的认可。

## 入口

在线口只有一个只读口（路径登记在 `cmd/parcel-api/endpoints_collection_subledgers.go`）：

| 做什么 | 路径 |
|---|---|
| 运营查阅代收分户账：四维键、保管依据、七个账内位置余额、记账笔数、引用它的回汇批次；分页 | `GET /collection-subledgers` |

查阅的授权边界只有租户，没有货主客户维。接入通道没装配时拒绝，不放行。

离线口（运营在数据库网络内手跑，不监听端口；输入是 `-input` 指定的 JSON 文件，未知字段拒绝；一次调用一笔事务）：`cmd/parcel-collection-register`，命令按依赖次序为 `instruction`（代收指令） `subledger`（分户账开立） `fact`（代收事实） `discrepancy`（差异事项） `agreed-offset`（认可的协议抵扣） `batch`（回汇批次形成） `hand-over`（交出汇付主张） `posting`（分户账记账）。

没有在线写口。别的上下文也不自动往这里送指令或事实：登记全部由运营经离线口做。

## 旧文档写了、代码里还没有的

- **更正时关联原记录**：旧文档写「追加新的事实并关联原事实」「登记新的事项并关联原事项」「登记新的代收指令并关联原指令」。`CollectionFactSpec`、`DiscrepancyItemSpec`、`CollectionInstructionSpec` 都没有指向原记录的字段；全包搜 `supersed`、`corrects`、`replaces`、`原事实`，只在注释里和记账冲正（`postingBasis.corrects`）上有。追加新记录做得到，关联做不到。
- **归集截点约束成员**：旧文档写批次归的是「归集截点前已处于`应付客户`的本金」。`CollectedThrough` 只被保存、比对重放与读出，汇付记账的门（`resolveBasisForPosting` 的 `BasisRemittanceBatch` 一支）不看它。
- **差异事项的处置结论**：旧文档写「短款结论已确认」「溢款的归属经处置后确认」才落账。`DiscrepancyItem` 没有状态或结论字段，落账那一笔记账就是唯一的确认。
- **汇付主张交出到外部**：`HandOverBatch` 只把批次状态推进一格。全包搜 `outbox`、`publish`、`event` 没有结果，主张没有送往任何外部系统的出口。
- **未提供时停在未配置**：旧文档写汇率、回汇周期、手续费、支付通道未提供时「相应判断停在未配置」。代码里没有用到这四项的判断，十种答案里也没有未配置这一格。它们是整体不在，不是答`未配置`。

## 证据限制

本上下文只用合成数据（`SYN-` 前缀）走通过，证据只算 `S`。入账不能冲正这一条留着一个没裁的口子：来源侧记错的本金怎么退出账面，要等真实的渠道退款与银行退回形态出现后再定。
