#
# 这里躺着的是**此刻容忍的**未接线领域工厂，不是「应当如此」的清单。冻结它是为了让门禁能判
# 方向：名单变长要有人写一行理由，名单里的条目失效要有人剪掉。
#
# 加一条时把理由写在它上面——你在加的当下知道它归哪个 PN 切片、为什么现在还不接，而三个月
# 后来读的人不知道。

# 同日晚随审计票 14 新增两条（PS 载荷规范化摘要一对），现为 33；2026-09-01 随票 08 面单

#
# 2026-09-02 随 party-commercial-context-gaps/01 剪掉 PublishChannelAccountUseAuthorization
# （渠道账号使用授权补齐执行器，接上生产调用路径），剪后**重数实测 33**——同样是数出来的。
# 顺带一句给下一个人：34 减 1 这次恰好也得 33，但那是巧合不是方法。上面两段记的两次错，
# 错的都不是算术，是「名单被别人动过而你不知道」。
#
# 2026-09-02 随 tf-unwired-seven/03 剪掉 SummarizeHandovers（交接范围汇总读面落地，
# application/summarize_handover_scope.go 是它的生产调用方），**本笔单独作用于其父提交
# 后重数实测 33**。按本门禁报错时要求的三分先分过成因：全仓 `SummarizeHandovers` 只有一处
# 声明（domain/transport_handover.go），不存在「别处同名声明造成误判」那一种，因此是第二种
# ——真的接上了包外非测试引用。
#
# **这一笔撞上了本文件此前没记过的一种失效，写下来因为它比上面两次都难防。** 上面各句都写
# 「剪后重数实测 N」，那句话默认**树上只有一个版本的名单**。共享工作树上不成立：同一时刻可以
# 有好几处未提交的增减各自躺着，你量到的 N 是它们叠加后的数，而每个人都会把它当成自己那一笔
# 的结果。本笔实测过这一格：在共享树上量得 32，因为树上同时压着另一处未提交的剪；而本笔单独
# 作用于父提交是 33。**两个数都不假，量的不是同一个东西。**
#
# 所以记数时要连「在哪量的」一起记。要一个能给下一个人用的数，只有一处量得准——**在干净检出
# 上量**，那里不含任何人的在途改动。逐块核（`git add` 前 `git diff HEAD -- <file>`）能在提交
# 之前逼出这个区别：本笔就是在那一步才发现自己写下的 32 记的不是自己那一剪。
#
# **那个 32 又错了一格，同一种错第二次。** 2026-09-02 晚 label-channel/10 加这一条之前重数，
# 实测 31——某次增减（隔离写面那批的名单改动）只改了名单没改这句。加入登记册重建入口一条后
# **实测 32**，这个数是数出来的不是从 31 加出来的**
# ——这句逐次记增减而不是只写一个数，是因为下一次增减时只改一处会让另一处变错。
#
# **而它已经错过一次，留在这里当实例。** 2026-09-02 剪那两条之前实测条目数为 34，而上一句
# 当时写着「现为 35」——某次增减只改了名单没改这句。所以上面的 32 是**剪后实测**得来的，
# 不是拿 35 减 2 算出来的；照那句算会得 33，继续错下去。逐次流水账防不住这个，它只是让
# 错误可追；**下一个改名单的人请重数一遍再改这句**。
#
# 下面那些理由行的取证强度曾经不齐：初版逐条读过签名与调用点的只有 parcel-pricing 与
# party-commercial 两组、以及 AssessSafeHandoff 与 FormSupplierExpectedCost 两条，其余按组写。
# 2026-08-24 已逐条补核（锚 b44dd51，方法与逐条结果见 production-wiring-ratchet-gate 票 01
# Comments 末条）：组注释的语义断言逐条成立；唯一例外（DecideDisclosure 的包外测试引用）与
# 几处组注释计数失配已就地改在各组注释里。
#
# 一件初版就该说清的事：这 33 条里 25 个**连 domain 包都没出过**——不只是没有生产调用点，
# 而是没有应用层用例、没有适配器、没有端口，包外零引用。按本仓机制先行实例后到的顺序，切片
# 还没开工的能力本来就该是这样。**所以这份名单不是一张缺陷清单，是一条基准线**；它里面有多
# 少是「接过线后来烂了」、多少是「切片还没到」，本门禁分不出，也不打算分。
