0. 一页读懂

  • 是什么。卖给经营跨境出口小包网络的物流企业（租户）的多租户运营软件，把「客户委托 → 网络收寄 → 路由 → 运输履约 → 关务合规 → 追踪异常 → 计价 → 运营结算」全链数字化成可解释、可回放、可审计的系统。开发方是软件公司，不是运营企业；文档里的「运营企业」一律指购买产品的租户，锚点货主客户是租户的客户。
  • 到哪了。产品能力（机制半边）于 2026-08-28 经受托认可宣告「产品就绪」：八个首发切片 PN-01…PN-08 全部达标、十个业务上下文都有生产代码与应用编排、跨上下文接线与持久化全部换真。此后三周一直在收尾：管理台接线、端口余量、评审残差、CI 修复。真实租户参数（实例半边）为空——当前尚无租户，这是既定红线下的正常状态，不是欠账。
  • 能演示什么。管理台登记 41 页，其中 40 页对 parcel-api 真实端点接线；用隔离合成 S 数据可以从「建产品 → 配价 → 建网 → 过关规则 → 提交委托」走到委托已提交，随后如实停在三堵墙前（详见 §14 与图 25）。
  • 今天的转折。ADR-0139 草案把「产品自有的客户接入 API（首方 API）」归入机制半边——不再等某个租户的渠道证据 PAR-INT-01；配套 ADR-0140/0141/0142（契约生成、集成方沙箱、首方 webhook）同日起草，均为 Proposed，接受与否归用户。
  • 归用户的决定。ADR-0139 是否接受；docs/ux/commercial-party.md（共享树上新出现的未跟踪文件）归属；收费模型采用哪几层（§19）。

1. 产品定位与目标客户

定位（产品基线）。idp-parcel 面向自己经营国际小包网络的物流企业，支撑其面向货主客户提供国际小包服务并组织实际网络履约。它不是货主运输管理系统（TMS）的「国际运输功能包」，而是拥有独立产品责任、独立领域模型、独立业务数据库与发布边界的国际小包网络运营系统。

首发对客服务形态是两种形态的明确组合（ADR-0088）：

  • 网络服务：运营企业向货主客户承担从有效网络收寄到约定终局的端到端责任，自己组织集货、节点、干线、关务与尾程闭环，具体履约段可自营或外包。
  • 面单渠道服务：运营企业为货主客户提供渠道下单、取面单、查询、渠道作废/退款协助；责任来源于面单交易绑定的渠道账号与合同，不虚构运营企业收寄，运输观察从实际承运商收寄事实开始。

目标客户群三层（判「常规还是边缘」的输入）

层是谁常规业务形态
物流产品设计者与整合者不一定持有干线运力或场站，靠组合多家供应商渠道形成可销售物流产品同一目的国并行接多家渠道、逐票按成本择优；按客户分层配产品与价格政策；供应商涨价/爆仓时改产品—渠道映射与规则包版本并要求可追溯；纯面单渠道转售是核心形态；每票要算得出真实成本与毛利

2. 客户的痛与产品的答法

每条痛用客户的话说，答法指向本产品真实存在的机制（摘自《产品故事》）。

客户的痛产品的答法（机制）
渠道与规则碎片化：每家渠道一套计费、一套轨迹、一套异常口径，靠 Excel 与老师傅经验管产品版本化登记册：服务产品、客户合同、供应商协议、价卡、计价参考序列（燃油/汇率）、网络目录全部按不可覆盖版本受控发布；统一领域语言贯穿十个上下文
一票赚不赚钱，月底才知道：报价与成本两本账靠人拉表纯计价评价：BUY/SELL 方向隔离、逐候选评价、版本清单可复算可回放；运输收费发生项 → 供应商预期成本 → 账单匹配 → 核销的结算链（图 17）
轨迹不统一，客户问不出所以然：每家承运商一套状态码里程碑映射版本化登记；内部投影与客户视图分层；披露按客户合同分级；映射不到的事实如实标「未归类」，不硬凑时间线（图 15）
异常靠人盯：延误、丢件、卡关靠客服翻邮件信号 → 发作期 → 分诊 → 案件 → 处置请求 → 披露/通知的机制链；分诊规则版本化，自动建案只来自规则命中
对账靠人肉：供应商账单、客户账单两头对，差异说不清归属供应商账单「到达不等于应付」、匹配与审核分步；客户对账单按截单快照发布密封；真实收付显式映射后才核销
多客户数据不敢开放查询租户是最高数据隔离边界（ADR-0003）；客户查询按账户授权作用域隔离；运营查阅与客户披露分开授权；外部单号只定位候选，不是访问凭证

凭什么赢

  • 每个判断可解释、可回放：评价带版本清单、投影带版本链、决定带依据引用；重放用原版本，不读当前值。
  • 没有假默认值：未配置的参数如实答「未配置」（ADR-0055）；演示数据只以合成 S 层级出现并如实标注。
  • 机制与实例分两半：产品能力先行，租户的真实参数后填；换一个租户不改代码，填参数登记册（ADR-0016 两轨制，图 24）。
  • 边界清晰、长期可演进：各上下文拥有自己的语言与数据所有权；加真实渠道对接、加 AI、换商业形态，动的都是边缘。AI 路线立场：不预建 AI 机制——登记册、评价回放、执行记录就是将来 Agent 消费的接口。

3. 端到端业务全景（十四阶段主链）

主链从商业与网络准备开始，经委托接入、生产归属、接受判断、路由、收寄、节点作业、运输、交付到终局；关务、追踪异常与金额链并行于物理主链。阶段不是单一全局状态机：每个上下文拥有自己的生命周期，端到端摘要只能由各自有效结果派生，不能人工改写。关务是控制域——可以阻断特定动作，但不产生全程统一状态。

5. 接单主线：UC-PS-001 全流程

UC-PS-001「客户提交国际小包请求并取得生产归属或接单结果」是本仓默认主刀用例。它从原始提交到达接入边界开始，先保全来源、判重放/冲突，再对完整拟受理范围形成生产归属，只有本产品取得权威后才建立已提交委托；接受判断链由「委托已提交」信封驱动（ADR-0081），逐项取得商业解析、逐包裹可达性与财务控制结果，最终形成接受、拒绝或保持未决。

6. 履约主线：收寄 → 节点 → 运输 → 交付 → 终局

接受后，路由表达未来意图，节点与运输分别记录实际执行；三层不得互相覆盖。网络服务责任起点是有效网络收寄——由客户送站（节点收寄）或场外揽收两类来源统一解释；运输控制的转移只来自逐对象成立的权威运输交接「已交接」结果，扫描、位置、签字或装卸都不足以转移控制。

7. 关务合规控制域

customs-compliance 按监管辖区、方向、程序与法定义务范围建立稳定关务案件；申报单元是案件内独立监管对象，不能用包裹、集运单元、总单或舱单替代。首发出口/进口监管舱单由责任承运商在外部形成并提交，本产品只接收引用（UC-CC-012）；每次提交由授权业务角色逐次确认，不启用生产自动申报。技术成功、付款成功、内部限制解除都不等于监管放行。

8. 追踪、异常与客户披露

visibility-exception 只消费各源上下文已接受的事实，按版本化映射形成标准里程碑、内部投影、ETA 与按货主客户账户隔离的客户视图；异常按「信号 → 发作期 → 分诊 → 案件 → 处置请求 → 来源决定/执行 → 披露与通知」推进，异常模块只能提出请求，不改写任何源对象。

9. 计价与运营结算

parcel-pricing 在固定输入与版本清单上形成纯 PricingEvaluation，SELL/BUY/INTERNAL 方向隔离，同输入同版本清单必须复算出同结果；settlement-accounting 消费评价，但评价金额不自动成为金额责任——结算按合同责任、发生项、确认条件与主要计费范围分别形成费用、应收、预期成本、账单、核销与经营结果。真实收付款由外部财务系统拥有，本产品只做可追溯映射。

10. 技术架构与运行时

Go 模块化单体（单 go.mod、go.idp.xyz/idp-parcel、Go 1.26.5），HTTP 用 chi/v5，PostgreSQL 16 + pgx/v5 显式 SQL，跨上下文交接走 Outbox/Inbox，持久化技术合同来自 idp-bento-go v0.1.0-rc.2（不可变候选，checksum 进公共透明日志）。目录 internal/<context>/ 是所有权边界，不部署为微服务；领域包不依赖 HTTP 或 pgx。

11. 首发范围：做什么、明确不做什么

《首发试点范围》是租户上线流程模板——由开发方维护但不由开发方执行。「一个锚点客户、一条线路」指的是某个租户的客户与线路；开发方要做的是让产品具备这些能力。

已确认的范围约束

  • 网络服务只选一条真实成熟主力线路：单一起运区域、单一出口路径、单一进口路径、单一目的服务区域；面单渠道服务以登记的渠道产品与产品—渠道映射为界，不以线路表达。
  • 生产只验一个真实锚点货主客户；另建一个受控测试账户用脱敏/合成数据验客户隔离与跨客户集运，不形成第二份真实合同或应收。
  • 履约混合组织：至少一个自营集货/分拣节点 + 至少一个外部伙伴执行的干线、关务或尾程环节；外包不改变运营企业对客户的端到端责任。
  • 允许多份供应商价卡并存，逐候选形成 BUY 评价后只按成本单维择优（时效/稳定性等维度等真实数据）；这是内部成本决策，不对客户形成价格承诺。
  • 关务申报由系统校验就绪，每次提交由授权业务角色逐次确认，不启用生产自动申报；出口/进口监管舱单由责任承运商在外部形成并提交，本产品只接收引用（UC-CC-012）。
  • 只启用锚点客户当前主用的一种生产委托接入渠道；每个伙伴每类事实一种主要数据源；一个财务系统集成边界；每个主合作伙伴一种账单接入方式并验一个真实账期。
  • 上线走「历史回放 → 影子运行 → 限量生产 → 正式验收」，阶段升级由租户责任法人指定的试点业务责任角色作 Go/No-Go；限量生产同一范围只有一个权威写入方；暂停/恢复/接管是治理决定，不实现为包裹全局状态（图 26）。

明确不包含

  • 不同时实施多条试点线路。
  • 不建设完整 WMS（场站只管暂存位置、作业批次与实物控制，不管商品库存）。
  • 不建设银行账、支付清算、法定税务、总账或财务 ERP；只维护物流运营结算分户账并引用外部已确认财务事实。
  • 首发不实现 COD 代收资金账本（上下文已建，生产范围不纳入）。
  • 不建设采购过程：不向承运商询价、竞价、招标；系统从供应商最终价卡开始。
  • 不对客户形成价格承诺：报价有效期、锁价、报价接受不进首发；要让客户看到金额用「客户预估费用」，它明确不是运营应收。
  • 关闭/重开不强制双人审批、不写死岗位名称或原因码；授权用版本化业务角色与权限等级表达。
  • 不因未来可能进入的国家、客户或渠道预先实现未经确认的差异化功能。

14. 今天能演示什么，停在哪

合成 S 演示动线（docs/design/synthetic-demo-journey-script.md）：角色是租户的物流产品经理，全程在管理台里看，数据经登记 CLI 灌入本机隔离库（SYN- 前缀），任何一步都不得指向生产库。

为什么「停住」也值得演示。按 ADR-0017/0029 的口径，未配置 不是缺陷而是产品的诚实：实例半边留空、拒绝默认值是红线。一条走到墙前能说清「这不是目录为空，是这一格根本没人配过，配它要先满足什么」的动线，演示的正是机制半边已经做完；为了好看往库里塞假委托，破的恰是它要证明的那件事。空态与未配置态是两件事，管理台的四态组件（图 23）就是为这个分的；三态对照（图 22）只动一个环境变量即可当场复现「这个 403 不是写死的」。
三堵墙业务含义隔离形态生产形态的重启条件
墙一 · 委托侧入库通道各写端点默认挂 UnconfiguredIntake：客户的委托从哪条渠道、以什么凭据进来，今天没人配过已开 ADR-0091 分级开关，只放 /shipment-requests 一行（商业身份族五口本日随票 06 加入）原为等 PAR-INT-01（该租户渠道的现行流程）；ADR-0139 草案提出产品自带首方 API 属机制半边、现在就立，租户既有渠道的适配才等证据
墙二 · 生产归属「这份委托由本产品还是旧系统承接」——目录与自身权威坐标是实例半边，不代拟已开 装配注入合成值，但归属仍真的读治理登记册（删掉那条权威区间就退回 OWNERSHIP_UNRESOLVED）租户登记真实生产权威区间（PAR-GOV-*）
墙三 · 路由拿不到证据就算委托已接受，初始路由停在 RouteEvidenceNotConfigured：证据视图只读 network_definition，而目录表还没有人把它折成逐候选事实。没有路由就没有下游费用仍在解析层「目录 → 逐候选事实」，被 PAR-NET-14 阻断；ADR-0068 已接受这段「目录可写可读、尚无人读它产出事实」的时期

另一处演示前要先读的已知缺口：cmd/parcel-dispatch 对逐条投递失败全程静默；只灌治理区间不灌商业主数据时，链如实答未决、烧完预算落 ABANDONED，委托停在已提交（.scratch/first-tenant-runway/issues/07、08）。

15. 试点治理与上线阶段（PN-08）

《首发试点范围》确认的上线方式是「历史数据回放 → 影子运行比对 → 限量生产」三个执行阶段，以「正式验收」作为对限量生产证据的最终评审里程碑。阶段不按日期自动升级，每次评审形成独立 Go/No-Go 决定；限量生产同一范围、能力与事实类型只有一个权威写入方；暂停只阻止新准入，恢复与接管必须显式决定。

19. 产品自身收费模型（形态，无价位）

回答的是开发方向租户按什么计量收钱——与 settlement-accounting 管的「租户对其客户与供应商的钱」是两件事，隔着两级。软件订阅费、调用费、平台费不是包裹业务事实，不进那本账。全文不含任何价位；第一个租户的报价由商务与该租户谈定，不回写文档。

收费层计量单位主要面向价值逻辑计量事实今天在哪
平台订阅租户、场站、席位，按周期三层都适用，是底座「有这套系统可用」本身不需要产品内计量
交易计量委托、包裹、面单交易、履约执行三层都适用随租户业务规模增长有事实基础：包裹永久内部标识不因换单/改号变更；面单交易是独立聚合，重打/作废不重复计
API 用量取价、轨迹、地址与资格校验等调用要把能力嵌进自有系统的租户基础设施计量不存在：无按租户/端点/成败的调用计量
物流产品费服务产品版本数、渠道数、网络定义与规则包数物流产品设计者与整合者产品管理复杂度在版本化登记册里可数；但按版本数计费会把「维护得勤」变成罚款，要小心数的是什么
优化收益择优节省额、毛利改善有规模的租户直接绑定经营结果形状具备（逐候选评价与择优记录），量不具备——节省额需要租户接入前的历史成本基准，那在租户手里
企业合同年度合同大型物流集团与平台型租户SLA、私有化、治理与合规不需要产品内计量

明确不依赖的收入：运费价差（开发方不是运营企业，要挣它得自己持有采购关系，那是换一个生意）；只按账号/席位收费（与物流业务价值脱节，促使租户压席位）；只卖 Agent 席位（本产品不预建 AI 机制）。

20. 术语速查与图例

租户 / 责任法人 / 货主客户账户
运营集团租户是产品使用与数据隔离的最高边界；责任法人承担合同、应收与账务责任；货主客户账户是客户业务隔离与可见性边界（ADR-0003 三级）。
机制半边 / 实例半边
产品必须具备的能力 vs. 某个租户的真实客户、线路、伙伴、参数与阶段决定。前者现在就做，后者等租户（图 24）。
产品就绪 / 试点就绪
能力覆盖可演示可洽谈 vs. 某租户填满实例半边并走完 PN-08 的 Go/No-Go（图 26）。
PN-01…PN-08
首发八个纵向产品切片（不是微服务拆分）；PN-05 关务是控制域专项旁路，PN-08 是产品级试点治理编排。
UC-XX-nnn
应用用例，把已确认领域规则组织成输入/结果/编排/失败边界/验收条件；如 UC-PS-001 提交委托（图 5）。
P / R / S / N/A
验收证据层级：真实生产 / 历史回放 / 受控模拟（合成）/ 本期不适用。合成数据一律标 S，不冒充生产。
未配置态 / 空态
「这条渠道没人配过」（403 ACCESS_CHANNEL_NOT_CONFIGURED）vs.「册里没有」（200 + 空列表）。两态在页面上分开呈现，未配置态不得显示「0 条」（图 23）。
PAR-*
参数登记册条目（如 PAR-INT-01 客户委托接入渠道、PAR-NET-14 服务区域地理覆盖形态、PAR-GOV-* 治理参数）：只登真实实例状态，不定义规则。
BD-*
未确认的业务决策项，保持可配置或显式未决，不写死为生产默认；BD-PS-001…008 八项接单机制已确认，真实参数仍待登记。
生产归属
某范围在某时段由哪个系统作为唯一生产写入方；权威身份（本产品/其他/未决）× 准入控制（OPEN/PAUSED）两个正交维度。
有效网络收寄
网络服务下运营企业控制责任的起点；客户送站与场外揽收两类来源统一解释为对象级同义结果（图 9）。
正式承诺 / 预计承诺
接受时形成预计承诺；有效网络收寄并完成资格校验后形成正式承诺，后续只以带原因的新版本调整。
权威运输交接
逐对象形成的运输控制转移结果：待确认 / 已拒收 / 已交接；只有已交接转移控制（图 10）。
运输收费发生项
运输履约按供应商协议发生条件形成的「发生了什么」记录，不含金额；金额由计价评价与结算采用分别形成（图 17）。
Outbox / Inbox / 直投
跨上下文交接：发布意图与业务结果同一事务落库（Outbox），派发器按进程内路由表直投消费门（Inbox），至少一次、幂等、毒丸显式拒收（图 20）。
棘轮门禁
internal/architecture 下冻着基线的门禁：导出领域工厂的零生产调用点名单只能缩不能长。
