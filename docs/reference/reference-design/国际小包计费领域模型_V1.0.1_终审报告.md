# 国际小包计费领域模型 V1.0.1 终审报告

**审查对象：**《国际小包计费领域模型 V1.0.1 终审版》  
**上游基线：**《国际小包计费与结算平台最终解决方案 V1.2 审定版》  
**审查结论：** 通过领域模型冻结审查，可作为《Rating Runtime 计算语义规范 V1.0》的正式上游基线。

## 1. 审查范围

本次终审不是格式校对，而是从以下层面进行交叉验证：

1. V1.2 架构决策追踪；
2. 限界上下文与数据权属；
3. 聚合根、实体、值对象和事务边界；
4. BUY、SELL、Quote、Assessment、Financial 的语义隔离；
5. MeasurementFact 与 CarrierAssessmentFact 的事实隔离；

7. 关键状态机的完整性和可达性；
8. 双时间、不可变版本和 PricingRelease 原子激活；
9. 周期结算的输入去重；
10. 承运商原始账单、标准化结果、对账和争议闭环；
11. 多租户、敏感成本字段和职责分离；
12. Markdown、代码块、标题、表格和事件摘要的一致性。

## 2. 终审发现并已修正的问题

### 2.1 CalculationPurpose 与 V1.2 不完全一致

已统一为：

```text
QUOTE
ESTIMATED_COST
ACTUAL_COST
CUSTOMER_BILLING
SIMULATION
REPLAY
DISPUTE_REVIEW
```

明确 `RECONCILIATION` 是限界上下文，不是 CalculationPurpose。

### 2.2 物理测量选择曾混入承运商计费认定

已拆分：

- `MeasurementFactSelector` 只选择物理 MeasurementFact；
- `CarrierAssessmentResolver` 独立解析 CarrierAssessmentFact；
- Rating 明确记录 `SYSTEM_RECALCULATION` 或 `CARRIER_ASSESSMENT`。

### 2.3 ChargeAssessment 状态存在含糊的部分接受语义

已删除聚合级 `PARTIALLY_ACCEPTED`，改为：

```text
DRAFT → PENDING_REVIEW → FINALIZED / REJECTED / ON_HOLD
ON_HOLD → PENDING_REVIEW / FINALIZED / REJECTED
```

部分接受必须拆成独立已确认认定和独立未决认定。

### 2.4 财务冲销曾可能被理解为修改原 POSTED 文档

已明确：

- 原文档永久保持 POSTED；
- 冲销创建新的 REVERSAL 文档；
- `ReversalLink` 精确引用原文档行和冲销金额。

### 2.5 金额方向存在负金额与 Credit/Reversal 双重表达风险

已统一为：

```text
非负 Money
+
ChargeEffect: ADD / DEDUCT
+
payer/payee
+
document/assessment type
```

分析差异使用 `SignedMoneyDelta` 和 `SignedQuantityDelta`，不作为正式费用金额。

### 2.6 Settlement 可能同时消费 Assessment 和 Financial 表达

已增加：

```text
input_basis_type: ASSESSMENT_LINES / FINANCIAL_LINES
```

单次 SettlementRun 只能选择一个权威输入层，并使用经济费用去重键防止重复累计。

### 2.7 SettlementRun 与 SettlementStatement 审批职责重叠

已明确：

- SettlementRun 只负责冻结和计算；
- SettlementStatement 负责商业审批；
- 调整 Assessment 创建后 Statement 才关闭。

### 2.8 CarrierInvoice 状态机不完整

已补齐：

```text
MATCHING ↔ PARTIALLY_RECONCILED → RECONCILED
```

未关闭费用行可以在补充匹配、Credit Note 或人工处置后继续推进。

### 2.9 ReconciliationCase 存在无出口状态

已为 UNMATCHED、DISPUTED 和 ESCALATED 补齐恢复、复核、解决和关闭路径。

### 2.10 原始账单行与标准化费用行混合

已拆分：

```text
RawCarrierInvoiceLine
NormalizedCarrierChargeLine
```

原始行永久不变；映射修订创建新的标准化结果，并冻结 mapping version。

### 2.11 生产版本可能被理解为可直接激活

已明确：

- 所有正式产品、合同、价格和策略版本无公开直接激活命令；
- 生产权威激活集合是 ACTIVE PricingRelease manifest；
- release pointer/manifest 原子切换；
- 单版本 ACTIVE 状态只是生命周期元数据。

### 2.12 current/latest 指针可能污染双时间解析

已明确：

- current/latest 只是便利指针；
- 历史、追溯和未来查询必须通过业务时间、系统时间、范围和 VersionRef 解析；
- Rating 回放不得依赖当前指针。

### 2.13 正式版本的双时间与租户归属表达不统一

已增加统一 `FormalVersionEnvelope`：

```text
semantic_version
ownership_scope_snapshot
valid_time
system_time
content_hash
status
supersedes_version_id
```

### 2.14 BUY→SELL 显式引用仍缺少无环约束

已增加：

- BUY 不得引用 SELL；
- SELL 不得间接回指自身；
- SELL 引用 BUY 时冻结 Evaluation ID、版本、费用范围和转换顺序。

### 2.15 ChargeEffect 没有进入费用定义

已增加 `default_charge_effect`，并规定 Evaluation Line 默认继承费用定义；只有显式转换或认定调整可以覆盖，且必须保留原因。

### 2.16 Assessment 调整关系曾使用 supersedes

已改为：

```text
adjusts_assessment_refs
reverses_assessment_ref
```

普通补充或贷项不再错误地表示为替代原认定。

### 2.17 财务文档来源兼容性不足

已增加同一 FinancialChargeDocument 内：

- payer/payee 一致；
- 币种一致；
- accounting period 一致；
- price role 与责任方向一致；
- BUY、SELL、内部结算不得混入同一文档。

### 2.18 租户归属存在隐式推导风险

已增加：

- CarrierAssessmentFact 和 DisputeCase 的 tenant_id；
- RateTable、IndexSeries 等价格对象的 ownership scope；
- 正式版本持久化和事件必须携带 ownership scope snapshot。

## 4. 关键语义审查结果

| 主题 | 结论 |
|---|---|
| BUY 与 SELL | 独立，无隐式继承 |
| Quote 与应收 | Quote 不自动产生应收 |
| Evaluation 与 Assessment | 计算与费用认定分离 |
| Assessment 与 Financial | 业务确认与财务入账分离 |
| Measurement 与 Carrier Assessment | 物理事实与承运商认定分离 |
| Rating 与 Settlement | 单票计算与周期累计分离 |
| Scope / Basis / Method | 定义和枚举与 V1.2 一致 |
| Money 方向 | 非负金额 + ChargeEffect，方向唯一 |
| 版本激活 | PricingRelease manifest 为唯一生产权威 |
| 历史回放 | 输入和全部依赖版本冻结 |
| 承运商账单 | 原始、标准化、匹配、差异和争议分层 |
| 多租户 | tenant/ownership scope 和字段权限明确 |

## 5. 当前仍需由后续文档验证的内容

领域模型通过不等于具体计费算法已经被数学证明。以下内容必须在后续专项文档中继续冻结：

1. 尺寸排序、单位换算和边界比较的精确顺序；
2. 体积重、计费重、最低重量和舍入的精确语义；
3. FIRST_CONTINUE、TIERED_BANDED 和 TIERED_PROGRESSIVE 的算法定义；
4. 燃油、折扣、最低收费和封顶的执行顺序；
5. 多包裹聚合和分摊余数算法；
6. Decimal 精度和每个阶段的舍入点；
7. 数据库唯一约束、双时间约束和并发控制；
8. API 字段、错误码和幂等合同；
9. 真实价卡黄金案例与边界案例；
10. 性能、缓存和发布原子切换的实现验证。

这些不是当前领域模型的缺陷，而是下一阶段必须完成的验证层。

## 6. 最终结论

在领域模型层面，未发现尚未解决的结构性矛盾或与 V1.2 冲突的核心语义。V1.0.1 已达到可冻结状态。

下一步应进入：

> 《Rating Runtime 计算语义规范 V1.0》

并同步建立第一批 Golden Cases。只有计算语义规范和黄金案例全部通过后，才能对“每一种价卡计算结果正确”作进一步保证。
