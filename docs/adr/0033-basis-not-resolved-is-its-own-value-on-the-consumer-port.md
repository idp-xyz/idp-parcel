# ADR-0033: `依据未解析` 在消费方端口自占一格，既不并进`已失效`，也不在消费侧拆回两格

Status: Accepted  
Date: 2026-08-11

## Context

[ADR-0029](./0029-retrieval-failure-algebra-is-partitioned-by-recovery-action.md) 把「按标识取回原状态失败」的结果按消费方的恢复动作分格，`查无此解析`与`属于另一个客户账户`因此合并为`依据未解析`。它落地那一笔（`3affd01`）在提交信息里留了一个明确的欠账：

> `依据未解析`无落点一条 ADR-0029 没有提到：改之前「查无此解析」走`解析未决`，好歹能落到`未决`（虽然那正是上面修掉的语义错），改之后一个落点都没有。
>
> 这一项不在本次提交里，也不该由提供方侧单方面定。按恢复动作它与`已失效`同为「回第一阶段重解」，看上去该并进`已失效`；但那会让「你的依据被新修订推翻了」与「你给的标识我不认」变成同一个答案，而前者是能拿去跟客户解释的商业事实。**端口结果代数的形状属难逆转取舍，要一条 ADR 由消费侧 owner 定。**

**那个决定后来做了，但只落在代码注释里。** `parcelshipment/ports` 的 `CommercialRevalidationOutcome` 已经给了 `依据未解析` 自己的一格，`form_acceptance_decision.go` 也按它单独取未决原因，理由写在两处类型注释上。缺的不是实现，是记录：`3affd01` 点名要一条 ADR 的正是这个形状问题，而红线「改难逆转技术或产品取舍 → 新 ADR」与「交接优先于临时代码注释」都不允许它只活在注释里。

需要把两件事分开，它们此前混在同一段注释里：

- **补上落点**本身不需要新记录。[ADR-0027](./0027-multi-step-cross-context-protocol-state-held-by-the-provider.md) 已把「端口结果代数缺口」判为 [ADR-0025](./0025-cross-context-adapters-live-on-the-consumer-side.md)「翻译必须是全函数」下的端口契约缺陷，改 `ports` 即可。
- **落成什么形状**——自占一格还是并进`已失效`——才是 `3affd01` reserved 的那一问。本记录只裁这一问。

## Decision

**`依据未解析` 在消费方端口自占一格。**

**一、不并进`已失效`，尽管两者的恢复动作相同。** 恢复动作相同不等于答案相同。ADR-0029 的合并规则管的是**取回失败那一步**内部的分格；`已失效`不产生于取回失败，它是取回成功之后作出的判断。援引 ADR-0029 去合并这两个，不是应用它的规则，而是把它扩到它自己明确划出去的地方。

判据还有一条独立的：`已失效`是一桩**能拿去跟客户解释的商业事实**——你的依据被新修订推翻了；`依据未解析`说的是**本方记下的采用标识本身可疑**——权威不认它。混成一格，本方写坏一个标识就会计进失效统计，而那份统计要回答的是商业修订有多频繁。[UC-PC-002](../application/party-commercial/UC-PC-002-RESOLVE-COMMERCIAL-BASIS.md) 的结果表也把两者列为两行，「给开发的交接」更把它们并列为消费者端口必须分别返回的结构化结果。

**二、恢复路径共用，未决原因分开。** 两者同为「回第一阶段重解并换掉标识」，因此走同一条重解路径——不换标识就是死循环。但停下来的原因各占一格，因为续办引用由原因派生：共用会让两种成因的续办催到同一个人。

**三、`依据未解析` 不得在消费侧拆回两格。** 提供方把「该标识从未签发」与「它属于另一个客户账户」合并进这一格，是为了不让一串标识挨个问就能枚举同租户下别人的解析。在消费侧按任何理由拆回两格，都是把刚拆掉的预言机在这边重建一遍——ADR-0029 已点名警告过这条下场。

**四、这一格与第二阶段的同名落点各自成格。** 第二、三阶段各有自己的 `*BasisNotResolved` 未决原因。运营要知道停在哪一阶段，而续办引用由原因派生，共用会把两阶段的续办路径并成一条。

## Consequences

- 决定在本记录写下之前已经实现：`ports.CommercialRevalidationOutcome` 的 `CommercialRevalidationBasisNotResolved`、`form_acceptance_decision.go` 里走 `resolveAdoptedAgain` 而另取未决原因的那一支，以及 `judgment_continuation.go` 里第二、三阶段各自的 `*BasisNotResolved`。**本记录不改任何行为**，它把已经做出的取舍从注释挪进记录，并交代被否决的那条路。
- `ports` 上原有的论证保留在原处作为就近说明，但**权威口径以本记录为准**；那段注释里「补它们本身不需要新记录」一句只针对「补落点」，不针对形状，本记录已把两者分开。
- **`输入未受理`的落点不由本记录裁定。** 它与本记录同期补进同一个枚举，但它的来源是取回之前的短路支，与恢复动作分格无关；ADR-0027 记的那个缺口按其原样仍然有效。
- 第二、三阶段的 `*BasisNotResolved` 各自成格意味着新增一个协议阶段就要新增一格。这是有意的成本：省掉它就等于让运营从续办引用里猜阶段。

## Alternatives considered

- **并进`已失效`，理由是恢复动作相同。** 否决：见 Decision 第一条。它看上去正是 ADR-0029 的规则，但那条规则的管辖范围是取回失败这一步之内，`已失效`在它之外；而且它会把本方的标识缺陷计进商业失效统计。
- **让它继续落在`解析未决`上。** 否决：那正是 ADR-0029 修掉的语义错——把「重试一万次也没有」报成「重试可能好」，调用方据以选错恢复动作，对着一个永远不会成立的标识重试到底。
- **在消费侧拆成`从未签发`与`不属于你`两格，理由是「翻译必须是全函数」。** 否决：全函数要求的是提供方每个取值都有落点，不是要求消费方比提供方分得更细。提供方那一格本身就是合并的结果，拆开等于重建预言机。
- **不立记录，让 `ports` 上的注释作数。** 否决：`3affd01` 明写这一问要一条 ADR 由消费侧 owner 定，而红线把难逆转取舍判给 ADR、并把交接置于临时代码注释之上。注释还会随文件走，而这个取舍要管的是所有同形状的多步协议端口。
