# ADR-0067: 预期成本纠错版本整组重述一个评价的计价结果，同币种两额相等对所有版本成立

Status: Accepted  
Date: 2026-08-20

## Context

`SupplierExpectedCost` 的两扇门对同一件事给出相反答案。`FormSupplierExpectedCost` 在原币与结算币相同时要求两额相等，理由写在它自己的注释里——「同币种两个金额不一致：没有换算却造出了第二个数」。`AppendCorrection` 换掉评价引用，只重述结算金额与换算步骤，原币金额原样留着，对同币种两额是否仍相等一字未提。于是这条路径合法而它的产物过不了形成门：同币种首版经一次纠错就得到两额不等、无换算步骤的版本，把它的字段原样喂回形成门会被判为不成立。

分歧是写迁移 `0008_supplier_expected_cost.sql` 时暴露的。`supplier_expected_cost_same_currency_amounts_agree` 照形成门那句不变量抄下来，真库用例存纠错版本当场打红。两扇门的分歧本来在领域包里静静待着——各测各的门因而都绿；把同一条不变量在库里再写一遍之后，两扇门第一次被要求同时成立。

`91af99c` 的处置是把等值那一条收紧到 `prior_version IS NULL`，重建门 `RehydrateSupplierExpectedCost` 同样只对首版验。那是**适配器忠于当下领域**——领域今天能产出什么形状，持久化面就得存得下、读得回——不是对分歧的裁定。

同币种不是病灶，只是病灶第一次可见的地方。`AppendCorrection` 换了评价却只搬来新评价三件产物中的两件，把原币金额留在旧评价上，于是一份版本的三个数出自两个评价，整组不可复算。跨币种下同一个毛病一样成立：`AT-SA-054` 的采购规则更正会让原币金额停在旧价卡上，只是没有哪条 CHECK 会照出来。`OccurrenceVersion` 的注释写着「发生项有效性更正换版本，预期成本据以追加计价纠错」，而 `AppendCorrection` 并不换发生项版本——那是同一个毛病的第三处。

现在是最便宜的时刻：两个函数都没有应用层调用方，`UC-SA-002` 的预期成本形成编排尚未落地，没有已落库的生产数据按旧口径写下过。

## Decision

**一、供应商预期成本的计价纠错是一个重述全额的新成本版本，不是带借/贷方向的差额调整对象。** 客户侧的 `ChargeAdjustment` 是另一种形状，两者只共用「计价纠错」这个调整原因词。

**二、一份预期成本版本的全部计价结果，整组出自它引用的那一个 BUY `PricingEvaluation` 及其版本清单。** 纠错换评价，因此整组重述：评价引用、采购价格规则版本、供应商协议引用、运输收费发生项版本与业务时点、原币币种与金额、合同结算币金额、换算步骤。

**三、纠错不动的只有身份四件：集团租户、运输收费发生项、费用项目、合同结算币。** 前三件是这份成本是谁；合同结算币是合同交给评价的输入而不是评价的产物，计价纠错不改合同。

**四、原币与合同结算币相同时两个金额必须相等，首版与纠错版本一视同仁。** 「没有换算就没有第二个数的依据」这条理由在纠错版本上一字未变。

**五、跨币种必备评价内换算步骤这一条，按该版本自己的币种对判断，不按被它纠正的那一版。** 原币币种随评价重述，因而首版跨币种、纠错版本同币种（或反之）都是可能的形状。

## Consequences

- `AppendCorrection` 的入参要长出原币币种与金额、发生项引用、采购规则版本与协议引用；换算步骤那条检查改按新币种对判断。
- 迁移 0008 的 `supplier_expected_cost_same_currency_amounts_agree` 撤掉 `prior_version IS NOT NULL` 那一支。已施加的迁移不可改写（校验和把关），故由新文件 `DROP CONSTRAINT` 后重建，不就地改 0008。
- 重建门 `RehydrateSupplierExpectedCost` 继续单独存在——[ADR-0028](./0028-aggregate-rehydration-is-a-separate-door-that-validates-without-recomputing.md) 的重建与构造两扇门本就是独立纪律，它剩下的独有职责是校验回指与原因成对且不自指，形成门根本不接这两个字段。但它今天那段解释自己为何不走形成门的注释整段作废，必须改写：留着会把一条已废的口径钉在代码里。
- 决定二覆盖的三处引用（采购规则版本、协议引用、发生项版本）在 `UC-SA-004` 逐行匹配的读侧会露头——它按版本引用，会读到一份规则版本与首版不同的纠错版本。那是不是它要的尚未取证，故与金额那组分票实现。
- 幂等三维不受影响：`supplier_expected_cost_first_version_unique` 的 `WHERE prior_version IS NULL` 已经把纠错版本放在三维之外，纠错版本携带新的采购规则版本不撞索引。
- `CustomerCharge` 只带单一币种与金额，没有原币/结算币这一对，与 CONTEXT 的「每条费用分别保存原币金额、合同结算币金额及换算依据」对不上。本记录不裁那一处，另记。

## Alternatives considered

- **承认同币种的差，另给它一个领域概念。** 否决：那要求「原币金额」改义为「首版计价的原币金额」而不是「本版采用的原币金额」，与 CONTEXT 把三者绑成一组的写法直接冲突；`UC-SA-004` 按版本引用会读到一个不属于本版评价的数。
- **供应商侧改用客户侧的差额调整形状。** 否决：借/贷方向与账期是已确认口径进入客户对账单才有所指的东西，预期成本属预估口径，从不进对账单。`UC-SA-002` 结果契约里「供应商预期成本已形成」的必须保留项明写「版本」，CONTEXT 的经营毛利口径说的也是「当前有效供应商预期成本」——都是版本链的说法。该用例结果契约中「计价纠错/商业让利已形成」一行确实要求保留借/贷方向，但那是一行合并写法，其中「商业让利」与「账期」都只对普通客户费用成立，把整行读成对供应商侧的约束是过度解读。
- **只裁金额那组，三处引用不进本记录。** 否决：同一份源文件里三处可见的反例会当场推翻本记录写下的原则，ADR 变成一条自己都不守的话。裁断裁全、实现分票，两件事分开。
- **就地改迁移 0008。** 否决：已施加的迁移不可改写，校验和把关；`0002_fix_disposition_check.sql` 与 `0003_fact_and_episode_tenant.sql` 都是照这条以新文件重建的。
- **维持 `91af99c` 的例外，让两扇门就此定形。** 否决：那处收紧是适配器忠于当下领域产物的结果，不是判断。把它当裁定会让一条从未被判过的口径靠「代码已经这么写了」取得权威。
