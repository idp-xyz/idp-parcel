# ADR-0351：联系人社交账号作为可选多值资料随法人资料版本保存

Status: Accepted（2026-10-30，用户指出公司联系人缺少社交账号，沿本会话公司主体完整资料范围作产品实现选择；部分停用 ADR-0350 的快照形状选择句，具体作用见 Links。）
Date: 2026-10-30

## Context

跨境物流联系人常用微信、企业微信、WhatsApp、Telegram 等渠道沟通。只有电话与邮箱不能表达同一人的多个平台账号。把它们塞进电话或邮箱会丢失平台含义；为每个平台扩一列不利于支持其他市场。

## Decision

联系人可选填 `socialAccounts`，每项为 `platform`（平台名称）和 `account`（账号或资料链接）。平台名称允许租户填写，界面提供常见名称建议，不是封闭枚举。两格首尾去空白后都须非空；同一联系人内平台名称不区分大小写、账号按原大小写比较，同一组合不得重复。同平台不同账号允许。集合保留登记次序，不按账号文本推导主要联系人、平台身份、登录权限或签署授权。

社交账号随同一份完整资料修订登记，不隐式沿用上一版，不从电话生成，不增加开票门禁。缺席即未配置；历史与按时点读取保留当时值。它只保存联络资料，不保存密码、验证码或平台访问凭据，不代表账号已验证，也不触发消息发送或平台授权接入。

快照按最低可表达版本写入：没有社交账号的资料沿原有无标记形状或 LEP-2，字节和摘要保持；至少一个联系人有社交账号时写 `shape: LEP-3`，摘要为 `LEP-3:<sha256>`。平台与账号同时进入不可变快照和联系人列，并参与内容摘要。LEP-3 必须包含社交账号；无标记或 LEP-2 不得包含它，未知形状拒读。旧行不回写。发布读取构建必须认识 LEP-3，开发演示服务在停止旧进程后统一更新，回滚同样须用支持读取 LEP-3 的构建。

## Consequences

领域、HTTP、历史端口、CLI、持久化与管理台共同扩形；旧记录仍可读、可重放。平台名称建议是产品策略，具体账号由租户维护，演示值使用明确的 SYN- 标记。

## Alternatives

每个平台一个固定字段会让扩展和同平台多账号困难；只存一串自由文本不利于逐项查阅与校验；把社交账号当作平台接入凭据会混淆联系人资料和外部授权。
