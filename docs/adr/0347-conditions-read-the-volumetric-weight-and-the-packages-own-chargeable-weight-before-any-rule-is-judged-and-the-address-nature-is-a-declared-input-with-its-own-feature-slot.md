# ADR-0347：判定条件读体积重与包裹自身的计价重量——两者由包裹自己与卡的重量策略在判定任何条件之前一次算好、不含条件最低计价重量的抬高；收件地址性质是另一个特征槽与可缺的评价输入，缺席时读它的规则答待判断

Status: Accepted（2026-10-29，Claude Code 会话代产品 owner、PP owner 接受（代决）：协调方派单「计价引擎补缺口 A」，起因是完整合成价卡取证出的两处缺口——评价器从不把体积重与计价重量填进判定特征，输入快照也没有地址性质；设计由作者落笔、口径取舍在派单里点了名，用户未逐条过目，越权风险点待 PP owner 复核。接上 [ADR-0152](./0152-operator-estimate-is-a-pricing-use-case-computed-not-recorded-and-never-handed-to-settlement.md) 决定八「不做的」里地址性质那一半。）<!-- 索引注记 -->｜**判据**：读体积重或自身计价重量的条件，评价在判定第一条规则之前按重量策略一次算好填进特征（自身计价重量是派生、进位之后、条件最低计价重量抬高之前的值，所以没有环）；不读它们的卡一步不多走、评价逐字不变；抬高条件不读自身计价重量，读体积重的卡须有体积系数、阈值用价表单位，都在装配与读回时拒；地址性质是并列于偏远档位的另一个特征槽 `ADDRESS_NATURE`（封闭词商业 / 住宅）与评价输入里可缺的一格，不进规范化文档、不换号，缺席答待判断、从不套默认，来源（PS 今天没有结构化的地址性质）归 PS owner 另票。

## Context

取证于 main `7ea1aa677`，只记 `S`。

- **特征集合声明了，评价器没填。** `domain.FeatureVolumetricWeight` 与 `domain.FeatureChargeableWeight` 早在闭合的特征来源集合里，注释写「评价器必须先把算出的值填进 PackageFeatures」，`PackageFeatures.WithDerivedWeights` 也备好了——全仓没有一处生产调用。于是读它们的条件在评价里读到缺席，报特征不可用，落 `CALCULATION_FAILED`；价卡上「超过 20 千克收超重费」只能读实重，而真实承运商的超重费常按计费口径的重量收。
- **重量的派生链是固定的。** CONTEXT「计价重量」与 `CalculatePricingWeight`：派生（`ACTUAL_ONLY` 取实重，`MAX` 取实重与体积重较大者）、经适用的条件最低计价重量抬高、再按取整策略进位。抬高的触发条件由判定条件声明，所以评价先判抬高条件、后算计价重量（`resolveMinimums` 在 `CalculatePricingWeight` 之前）——条件在重量算出来之前就要判，这是「读计价重量的条件」天然会碰到的环。
- **名字：「计费重量」不是这里的词。** GLOSSARY 与 CONTEXT 把「计费重量」划给 `settlement-accounting` 的财务采用（客户计费重量、供应商计费重量），在计价一侧明令避免使用。特征标识 `CHARGEABLE_WEIGHT` 是 ADR-0015 封闭文法里已进摘要的原词，不改；在领域语言里它读的是下面决定一说的「自身计价重量」。
- **地址类型那一槽被偏远档位占着——属实。** `resolveCatalogues` 解出的偏远档位经 `WithCategories(zone, tier)` 落进 `PackageFeatures.addressType`（ADR-0109 Context 把档位对到 `FeatureAddressType`，`CatalogueKindRemoteTier` 的注释同写）；绑了档位目录的卡，该槽就是档位码，没绑的卡该槽缺席。已登的完整合成价卡 `SYN-PLAN-CN-SG-FULL-01` 的偏远一档、二档两条规则读的正是这一槽（`ADDRESS_TYPE = T1 / T2`）。后果有两种：把住宅派送费写成 `ADDRESS_TYPE = RESIDENTIAL`，在绑了档位目录的卡上读到的是档位码，规则**静默永不命中**，没有任何错误；在没绑目录的卡上槽缺席，评价落 `CALCULATION_FAILED`。两种都表达不了 CONTEXT「地址分类」词条写明的「同一票可以既命中住宅派送又落在某一偏远档位，二者同时计收」。
- **地址性质今天没有来源。** `parcel-shipment` 的地址要素是封闭名集（`AddressElementName`：邮编、国家 / 地区码，再长一格要先回 PS CONTEXT 词条），寄收件资料是 name/value 条目，没有商业 / 住宅；`network-routing` 的 `GeoResolutionProjection` 只到国家与服务区域一级；计价输入快照与试算声明（ADR-0152 决定八「不做的」：「地址性质与服务选项：输入快照今天不带这两格，随特征来源另立」）也都不带。与邮编早先的情形同形：计价不推断、不拥有，更不能在适配器里从地址文字猜。
- **规范化版本不能随手换。** 取证时 `canonicalizationVersion` 是全局一个常量，评价重放遇到不同版本一律答「结构上算不出来」（`CANONICALIZATION_VERSION_UNSUPPORTED`）；其后 [ADR-0348](./0348-a-price-card-may-declare-total-charge-bounds-and-key-a-surcharge-table-by-remote-tier-and-plans-using-them-are-written-as-ppc-6.md) 为带新键的方案另开了 `PPC-6`（其余方案仍写 `PPC-5`），本构建两版都认；[ADR-0267](./0267-a-key-added-to-an-already-canonicalized-body-is-a-shape-change-even-when-old-documents-stay-byte-identical.md) 又规定在已接规范化的册里加键（含可缺键）是形状变化。所以任何新结构先问一句：规范化文档要不要加键。
- **没有已发布卡这么写。** 读这两个重量特征、读 `ADDRESS_NATURE` 的条件此前在评价里必然失败，不可能有一份算对的评价依赖它们；仓内种子（`scripts/demo-seeds/data/pricing/`）、导入模板夹具与价卡草稿夹具都没有这样的条件，参数登记册没有租户实例。

## Decision

**一、体积重与自身计价重量，在判定任何条件之前一次算好。**

- **体积重**（`VOLUMETRIC_WEIGHT`）：卡的体积系数从尺寸算出、按系数声明的取整落点之后的值；票级 / 主单级主体上是成员清单声明的合计体积重。与实重无关，也与任何条件是否命中无关。
- **自身计价重量**（`CHARGEABLE_WEIGHT`）：按重量策略派生（`ACTUAL_ONLY` 取实重，`MAX` 取实重与体积重较大者），再按取整策略进位的值，**不含条件最低计价重量的抬高**。它是「这件包裹按这张卡的重量规则自己有多重」，不是「查表用的那个重量」——后者经抬高、可能更重，仍叫计价重量，不动。
- 两个量的单位都是价表查表单位（体积系数的取整单位与重量策略的取整单位本来就须相同）。输入单位不同时，评价照 [ADR-0346](./0346-evaluation-converts-input-weight-and-dimensions-to-the-units-the-plan-declares-by-the-built-in-unit-catalogue-and-records-the-factor-it-used.md) 先按不换算的老路算、答单位不一致才带换算器再算；这一遍做过的换算**当场记在评价上**（记录与解释行）：拒收命中、序列取值缺失待判断、抬高条件求值出错这些出口都在正式计价重量那一遍之前收尾，不当场记，换算记录就丢了，重放与同标识重复请求（只认记下的系数）会把原来的待判断或不可计价判成结果不一致。走到正式那一遍时以那一遍的记录为准、撤掉这一遍留的（带抬高的下限时保留位数可能因下限的小数位而更细），记录与解释行都只有一份。
- **只在方案有条件读它们时才算。** 拒收条款、附加费规则的触发条件、条件最低计价重量的触发条件，任一读体积重或自身计价重量，评价在特征阶段多算一遍（与正式计价重量同一件实现，`CalculatePricingWeight` 不带下限）、填进 `PackageFeatures`，之后所有条件读到同一份值；解释里多一行写明条件读到的两个值（体积重未声明系数时写 `not declared`）。方案不读它们时一步不多走，评价与此前逐字相同（决定六）。
- **缺输入答待判断，不是 0。** 单包裹主体缺尺寸，沿用既有的 `PACKAGE_FEATURES_UNAVAILABLE` 待判断；票级 / 主单级主体按 `MAX` 计价而成员清单没声明合计体积重，沿用 `DIMENSIONS_REQUIRED`；直接拿判定条件去读一份没填派生重量的特征集，仍答 `ErrFeatureUnavailable`，不会当 0 命中「小于」类条件。这两个量算不出来（尺寸没到、单位对不上）时，评价在判定第一条规则之前就按与正式计价重量同一种缺口作答，已发生的换算记录留在评价上。
- **边界。** 条件的比较运算不变：`GT` 恰等于阈值不触发，阈值之上的最小可表示值触发——自身计价重量是进位之后的值，所以「最小可表示值」是阈值加一个进位单位（进位 0.5 千克时 20.0 不触发、20.5 触发）；含端的 `GE 20` 在体积重 19.8 进位到 20.0 时成立。这是「计费口径」与读原始体积重的区别，用例钉着。

**二、读体积重的卡须声明体积系数；两个量的阈值用价表单位。装配与读回时拒。**

- 重量策略只按实重计价（没有体积系数）的卡，读体积重无从算起；方案装配（`NewPricingPlanVersion`）与读回整图重验（`plan.valid()`）同一道门拒。自身计价重量在 `ACTUAL_ONLY` 下是进位后的实重，照常可读。
- 读这两个量的条件，阈值单位必须等于价表查表单位，否则对每一件包裹都只会同一种失败（单位不一致）；装配时拒（`ErrWeightUnitMismatch`）。**这一道只管这两个派生量。** 读实重的条件阈值单位仍不受装配管（输入单位不同时按评价期的单位比较答单位不一致）；特征判定里阈值与特征的单位比较仍不换算，ADR-0346 决定六与 CONTEXT「判定中不得隐式换算」一句原样成立，**本记录不触碰。**

**三、条件最低计价重量的触发条件不得读自身计价重量；可以读体积重。**

自身计价重量不含抬高，所以让抬高条件读它**并没有环**。仍拒，是保守的取舍，两层理由：

- 词义：CONTEXT「计价重量」含抬高，「自身计价重量」不含；一条「自身计价重量超过 X 就抬到 Y」的抬高条款，读的人会按前者去读而以为它自指。真实价卡（`R24`、`R32`）里抬高由尺寸一类条件触发，今天没有任何一张需要它。
- 可逆：拒掉的东西以后放开不破坏任何已发布的卡；今天放开、日后发现要收紧，就要处理存量。

形式沿用既有的拒绝：`NewConditionalMinimumWeight` 答 `ErrConditionalMinimumReadsChargeableWeight`（是 `ErrInvalidSurchargeRule` 的一种），嵌在组合条件里的叶子同样拒；`ConditionalMinimumWeight.valid()` 也守这一条，所以读回门同样拒。体积重不取决于任何抬高，抬高条件读它合法。

**四、收件地址性质是并列于偏远档位的另一个特征槽，也是评价输入里可缺的一格，缺席答待判断。**

- **词表与特征。** 地址性质（`AddressNature`）封闭为 `COMMERCIAL`（商业）与 `RESIDENTIAL`（住宅），原词、不宽容大小写与空白。新增特征来源 `ADDRESS_NATURE`，类别量、只按相等判；期望取值不在词表内一律拒（一个拼错的 `RESIDENTAL` 会成为永远不命中的条件，少收而无人知道）。
- **`ADDRESS_TYPE` 不改指。** 它仍承载偏远档位——已发布卡与它们的内容摘要读的是这个含义，改指就改变今天已算对的评价。名字与含义的错位（「地址类型」其实装档位）是术语债，记入越权风险点 2；不在本轮改名。
- **评价输入。** 计价输入快照多一个可缺的地址性质（`WithAddressNature` / `AddressNature`），随评价快照往返（可缺键，未声明的评价不写这一键，旧快照照读）；**不进规范化文档**，与结算币种、比较币种同一种放法——它影响结果的方式只有「读它的规则命没命中」，那已落在费用行与状态上。同一评价标识、同一份卡下只差一格地址性质、而卡并不读它的两个请求，结果与摘要都相同，按同一次计算处理；卡读它时结果不同，摘要自然不同。
- **缺席答待判断，从不套默认。** 卡上有规则读 `ADDRESS_NATURE` 而输入没声明：评价待判断，问题项 `ADDRESS_NATURE_REQUIRED`（`ErrAddressNatureRequired`，是 `ErrFeatureUnavailable` 的一种，只有评价这一层把它译成待判断），不当商业也不当住宅，没有合计。**试算**在发起评价之前就按卡的实际需要点名缺项：卡读地址性质而声明没给，这张卡答「输入不全」、缺项码 `ADDRESS_NATURE`，别的卡照算，与缺分区、缺邮编路线同一种缺项。
- **试算入口。** `POST /pricing-estimates` 的载荷加可选键 `addressNature`（封闭词，缺席即未声明，不认识的值是畸形请求）；管理台试算页加下拉「收件地址性质（可不选）」。**键名不叫 `addressType`**——派单曾这样称呼，但引擎里「地址类型」那一格装的是偏远档位，同名的载荷键不进那一格会是个陷阱；线上的键名跟着特征走。试算评价标识在声明了地址性质时多派生一段，没声明时一段都不追加，既有声明的标识逐位不变。
- **来源归属：PS owner 另票，本轮不造不猜。** 地址性质若有结构化来源，只会在持有地址的 `parcel-shipment`（寄收件资料的地址要素，要先回 PS CONTEXT 词条把封闭名集加一格，再由 `adapters/parcelshipment` 与评价输入解析器译进 `WithAddressNature`）。**在那之前**，读 `ADDRESS_NATURE` 的卡走不通正式评价、受理前估价与路由比价的候选评价：这些路径的输入没有这一格，评价待判断（或试算式的输入不全）——这是如实，不是缺陷，也不是计价可以替 PS 补上的事。试算入口因为是发起方自己声明，不受影响。
- **导入模板**认 `ADDRESS_NATURE`（类别类来源、取值同样只收词表内的词），价卡才写得出住宅派送费。

**五、读体积重的阈值并入截断位数的边界（兑现 ADR-0346 越权风险点 2）。**

票级 / 主单级主体的合计体积重以另一个单位声明时会被换算并可能截断；读体积重的条件拿阈值（任意位数的有限小数）去比较它，ADR-0346 决定四「截断不改变任何比较结果」的论证只对已枚举的量成立。现在把这些阈值的最细小数位并进 `g`（`unitConverter.conditionScale`，方案不读体积重时为零、位数公式与此前逐字相同）。用例钉着：1 千克折磅是无限小数，阈值 `2.204622621848` 比不并入时的保留位数还细，不并入则截断值落到阈值之下、条件错判不成立；把这一步拿掉用例即失败。自身计价重量是进位之后的有限小数，不受影响。

**六、不改变任何今天已算对的评价；不换规范化版本。**

- 新代码只在两种情形下走：方案有条件读体积重或自身计价重量；输入声明了地址性质。其余评价走的就是引入之前的那几行代码。**证据**（见票面完成记录）：同一批夹具（逐包裹、MAX 带尺寸、附加费命中与未命中、拒收、条件最低计价重量、分区与偏远档位目录、磅与英寸换算、固定规则、重放、票级聚合）在 `git archive origin/main` 解出的树与本分支上各跑一遍，价卡内容摘要、价卡登记快照散列、评价语义摘要、评价快照散列与解释散列逐位相同；演示种子灌入真库后，第一张完整价卡与 v1 售价卡各七件包裹的试算，评价标识、摘要、费用行与解释逐字相同。
- 规范化文档**一个键都没加**：新的特征来源是既有 `source` 键的一个新取值，期望取值是既有 `category` 键的新取值，地址性质只进评价快照。ADR-0267 判据（加键、删键、改键）不触发，所以读这些特征的方案**仍写 `PPC-5`**（ADR-0348 的 `PPC-6` 只给带新键的方案，与本记录无关，两者互不依赖），**没有「只让新计划用新版本」这回事要做**：旧计划的摘要一字不变，新计划里读新特征的条件摘要自然含新取值。
- 读到含新特征来源的价卡的**旧构建**会在读回门上拒收（`invalid price card registration snapshot`，已用 origin/main 的构建对第二张完整合成价卡实测），不是静默丢键。上线前阶段（ADR-0267 决定三）没有不认新形的构建会读到新文档；进生产后若滚动发布，这是须知（风险点 7）。

## Alternatives considered

- **自身计价重量取最终计价重量（含抬高）。** 否决：抬高条件的判定先于最终计价重量，读它就是自指，只能规定「抬高条件不得读」并让条件阶段化——拒收条款也要等抬高判完才能读，评价要在两个阶段各装一次特征，同一个名字在不同阶段有不同的值；更糟的是抬高会级联：尺寸条件把 2 千克的轻件抬到 30 千克下限，随后「计价重量超过 20」的超重条款因另一条条款的抬高而成立，没有证据说哪张价卡有这种连带。
- **同一个名字两个值：抬高条件读自身的、附加费读最终的。** 否决：同名异值是解释不出的，「判定条件必须可逐条解释命中与否」读的人分不清这一条读的是哪个。
- **抬高条件也放开读自身计价重量。** 暂否（决定三）：不是有环，是保守；放开随时可做。
- **把 `ADDRESS_TYPE` 改指地址性质，偏远档位另立 `REMOTE_TIER`。** 否决：已发布卡与它们的内容摘要读 `ADDRESS_TYPE` 的现含义；改指就改变今天已算对的评价，违反本记录的第一条保证。
- **地址性质与偏远档位塞进同一个类别值（如 `T1|RESIDENTIAL`）。** 否决：发明一种没人声明过的组合取值，卡上每个档位都要写两遍。
- **缺席时默认商业（或默认住宅）。** 否决：地址性质的缺省没有「最常见」可言，默认就是在没人声明过的地方替租户收一笔钱或少收一笔钱，红线「租户取值留给租户」；缺席答待判断，补上声明就能得出价格。
- **在 PS 适配器里从收件资料的地址文字猜住宅 / 商业。** 否决：计价不拥有这个事实，适配器不是判断它的地方；猜错是静默的。PS 要提供，得是它自己的结构化要素。
- **把地址性质加进规范化文档并换号 `PPC-6`。** 否决：它影响结果的方式已落在费用行与状态上，再加一键只为让摘要「多认」一格输入；`canonicalizationVersion` 是全局常量，换号让所有旧评价的重放答「结构上算不出来」，代价远大于收益。与结算币种、比较币种的先例一致。
- **由调用方把体积重与计价重量算好传进来。** 否决：CONTEXT 明令体积重由计价按版本化系数算，不接收外部算好的值。
- **读体积重而没有体积系数的卡，留到评价期落待判断。** 否决：对每一件包裹必然同一种结果，放到评价期只会在每次评价上重复失败，且让「待判断承诺补齐事实就能得出价格」说了假话。

## Consequences

- 读体积重、自身计价重量与地址性质的条件第一次能算：超重一类按计费口径收的条款、住宅派送费都写得出，且与偏远档位同卡同票并收。此前这类卡的评价必然 `CALCULATION_FAILED`。
- `internal/parcelpricing/domain` 新增 `address_nature.go`、`package_weight_features.go`；`PackageFeatures`、`PricingInputSnapshot`、`EvaluationRequest` 的评价路径、评价快照（一个可缺键）、方案装配与读回门、导入模板、试算载荷与试算编排、管理台试算页随之改动。无迁移、无库表（快照是 JSON 文档）。
- 读这两个重量特征的方案，每次评价多一遍纯函数的重量计算与解释里一行。重放（冻结模式）时那一行里体积重的小数位，在「票级主体、合计体积重以另一个单位声明、换算结果是无限小数、卡又带抬高下限」这一格里可能比原评价多几位（冻结取记下的位数，而记下的是带下限那一遍的）；语义摘要不含解释行，只是文字差，不对齐。
- 演示租户新增第二张完整价卡 `SYN-PLAN-CN-SG-FULL-02`（范围 `SYN-SCOPE-03`）：超重费按自身计价重量超过 20 千克触发，另带住宅派送费 6 元；第一张卡与种子一字不动。
- `FeatureAddressType` 名不副实的术语债留着；ADR-0109 的对应关系与 CONTEXT「地址分类」词条照旧成立。
- 读地址性质的卡在 PS 提供来源之前，只有试算（发起方声明）走得通；这对租户上线是实施须知，不是本记录能解的。
- UC-PP-001 新立 `AT-PP-022` 至 `AT-PP-026`。

## 越权风险点

0. **自身计价重量的口径取舍（决定一）。** 取「进位之后、抬高之前」，不取 CONTEXT「计价重量」的最终值；超重等条款因此不因别的条款的抬高连带成立。若 owner 要的是最终口径（含抬高），那是另一个量，要另立特征名与一次阶段化的设计，不是改这个值。「计费重量」一词归 SA，本记录刻意不用。**命名风险**：真实承运商的「计费重量」常含最低计费重量的抬高，卡作者可能把「计费重量超过 X」抄成这个槽，而同卡有抬高时静默少触发——所以导入模板列说明与导入规格对应行都写明「不含条件最低计价重量的抬高」；标识 `CHARGEABLE_WEIGHT` 现在没有任何已发布卡依赖它（读它的条件此前在评价里必然失败），**是最便宜的改名窗口**，改不改交 PP owner。归 PP owner。
1. **抬高条件拒读自身计价重量是保守取舍（决定三）。** 没有环；owner 可放开，放开不破坏任何已发布卡。归 PP owner。
2. **特征槽与术语债（决定四）。** `ADDRESS_NATURE` 是新槽，`ADDRESS_TYPE` 仍装偏远档位，名字错位。若 owner 要改名或换指，要走规范化换号与已发布卡迁移，不在本轮。归 PP owner。
3. **PS 地址性质缺口（决定四）。** 读地址性质的卡，在 PS 没有结构化来源之前，正式评价、受理前估价与路由比价候选一律待判断 / 输入不全。交接给 PS owner 另票：PS CONTEXT 地址要素词条加第三格「地址性质」（或另立的客户申报字段），并由 `adapters/parcelshipment` 与评价输入解析器译进 `WithAddressNature`。在票立起来之前，给 `SELL` 卡写住宅派送费的租户要知道它只在试算里算得出。归 PS owner（来源）与 PP owner。
4. **新装配拒绝对已发布卡的影响（决定二、三）。** 三种写法在评价里本来必然失败，所以不会有算对的评价依赖它们；读回门与装配门同一道，若某租户实例日后登记册里有这样的卡，它在读回时被拒、所在范围的试算与评价答未决。仓内种子、夹具与导入模板夹具没有这样的写法，参数登记册没有租户实例，核实为「没有已发布卡这么写」。归 PP owner。
5. **地址性质不进规范化文档（决定四、六）。** 同标识、卡不读它、只差这一格的两个请求被当作同一次计算（比的是语义摘要）。若 owner 要摘要认这一格，须 ADR-0267 换号。归 PP owner。
6. **截断边界又多一项（决定五）。** 日后评价里再新增任何拿重量去比较的量，仍须并入 `conversionBoundaryScale` / `conditionScale`；没有测试会替它报，只有参考实现对照覆盖现有的量。归计价 owner。
7. **旧构建读到新卡（决定六）。** 拒收而非静默丢键，是 ADR-0267 要的「答不支持而不是答错」，但**波及面比「所在范围答未决」大**：读到含 `ADDRESS_NATURE` 条件（或别的新特征来源）的 `PPC-5` 卡，旧构建在读回门上只答泛化的「价卡登记快照无效」，不是「不认这个规范化版本」；序列、目录登记与复核之后的受影响范围扫描是**租户级**的（租户内任何一张读不回，整笔失败、信封回滚，波及周更燃油序列的登记与复核），价卡草稿列表也整租户报错，评价请求与售价预估在唯一适用的卡读不回时答 unavailable。**运维约束（目前只是文档约束，代码里没有门；与 ADR-0348 风险点 6 同一类）：所有读价卡的进程换成新构建之后，才登记第一张读 `ADDRESS_NATURE`（或体积重 / 自身计价重量以外别的新来源）的卡；回滚到旧构建后这张卡同样读不回。** 上线前阶段（ADR-0267 决定三）不构成问题。归 PP owner。
8. **载荷键名 `addressNature`（决定四）。** 与派单所称 `addressType` 不同，理由见决定四；若 owner 更愿意统一叫地址类型，须同时处理 `ADDRESS_TYPE` 的含义。归 PP owner。
