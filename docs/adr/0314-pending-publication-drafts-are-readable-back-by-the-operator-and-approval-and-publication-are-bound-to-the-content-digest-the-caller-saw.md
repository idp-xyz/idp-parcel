# ADR-0314：待批准的发布载体可由运营操作者读回；批准与发布都绑定调用方看到的那份内容摘要，摘要不符答「已变更」

Status: Accepted（2026-10-26，Claude Code 会话代 owner 决，用户授权代决；票 party-commercial-uiux-backend/03。裁决能力边界：读过 ADR-0126 全文、`PublicationDraft` 领域对象与载体册适配器、`SubmitPublicationDraft` / `ApprovePublicationDraft` / `PublishPublicationDraft` 三个用例、运营操作者面的载荷解码、管理台发布草稿流程；越权风险点见文末，待 PC owner 复核。）<!-- 索引注记 -->｜**入口**：ADR-0126 立了待批准载体并让批准与发布各走一口，但批准口只收（类别、对象、版本）三格，批准者既读不回载体、也无法声明「我批的是哪份内容」。**取法**：载体增两个运营查阅读口（列表、单份读回，单份带规范化文档）；批准口与发布口的载荷必带 `expectedDigest`（内容摘要）与 `expectedShellDigest`（版本壳摘要），任一个与载体此刻的不同答 `DRAFT_CHANGED`，不批、不发。
Date: 2026-10-26

## Context

- ADR-0126 决定三：批准是与录入分立的操作者动作，经一版一行的待批准载体推进。它没有给批准者一个读回载体的口：载体只在录入那一刻的答复里出现一次，管理台刷新页面、换个人批准、隔天再来，都再看不到「有什么在等我批」。今天的管理台为此把「录入 → 批准 → 发布」做成同一页内的连续流程，只有录入者本人、同一次页面会话里才走得通。
- 批准口的载荷只有（类别、对象、版本）三格。载体是「一版一行」：同一键再次录入，在待批准阶段会换掉正文快照与摘要（既有的录入语义）。于是出现一个缝：批准者看的是 A 内容，批准请求到达服务端时载体已被录入者改成 B，批准落在 B 上——批准的不是他看过的东西。批准是治理动作，批准对象必须是批准者看到的那份。
- 载体的内容摘要由服务端按册规范化算出（ADR-0126 决定一），所以「调用方看到的那份内容」有一个现成的、服务端认的身份：摘要串，自带规范化版本。不需要新造版本号或乐观锁列。
- **内容摘要只盖正文，不盖版本壳**（适用范围、有效区间、指名引用；见 `CanonicalizePublicationContent`），而待批准期间壳变了正文没变也是合法的就地修订（`SameSubmissionAs`）。只绑内容摘要，批准者看的是范围 S1、批准落在 S2 上，摘要却一字不差——所以壳要另有一个摘要一并绑。
- `ApprovalDraftChanged`（`DRAFT_CHANGED`）这一格在批准用例里早已存在，由写回时的前态比对触发（`AdvanceDraft` 发现载体已被换成别的录入），覆盖的是请求到达之后的竞态；覆盖不了「批准者读到之后、请求到达之前」载体被换掉——调用方没有办法声明自己看到的是哪一份。本记录补上调用方这一侧的前置条件，复用同一格答案。

## 候选与反方

- **只加读口，批准口不变。** 否决：读口能让批准者看到内容，却不能保证他批准的是同一份；缝仍在，只是更难踩到，没有消失。
- **载体加版本列（乐观锁），批准带版本号。** 否决：摘要已经是内容身份，且服务端认；再加一列等于给同一件事两个身份，两者不一致时还要再裁。
- **批准口收整份内容，服务端比对。** 否决：把一份可能很大的正文来回传两次，批准者的前端还要自己带着规范化文档，等于让表单持有「该批什么」的内容——与 ADR-0126「表单只呈现」相反。
- **不同则静默批准最新内容。** 否决：这正是缝本身。
- **读口挂登记写面。** 否决：读的是租户自己的在途工作，不改任何东西，且需要看列表的人不一定持登记写授予；挂操作者查阅读（`MASTER_DATA_AND_OPERATIONS_READ`），批准与发布仍各走自己的登记写口。
- **只绑内容摘要。** 否决：见 Context，壳在待批准期间可就地修订，内容摘要对此无感。
- **把壳折进内容摘要。** 否决：PCC-1 规范化文档只盖正文是 ADR-0126 的既定形状，既有册不改字节、不换号；盖进壳会让「同内容换范围」的摘要变化。
- **读口 + 批准与发布都绑定内容摘要与壳摘要（采纳）。** 

## Decision

**一、载体有两个运营查阅读口。**（机制）

- `GET /commercial-open-publication-drafts`：交出租户名下还没发布的载体（`待批准`与`已批准`），录入时刻由新到旧；不带正文；每份带版本壳、规范化版本与内容摘要、录入者与时刻、状态与批准痕迹。空列表答 200 加空数组；读失败答 5xx，不伪装成空列表（批准者会以为没有活要干）。结果码 `PUBLICATION_DRAFTS_LISTED`。
- `GET /commercial-publication-draft-readbacks/{kind}/{objectId}/{version}`：单份读回，除上述外带规范化文档 `content`——正是摘要盖住的那份（载体重建时已校验文档与摘要吻合）。不在册与别的租户的载体同形，答 200 加 `DRAFT_NOT_FOUND`（ADR-0022：状态码只说答案有没有形成）。结果码 `PUBLICATION_DRAFT_READ`。类别或标识不合法答 400。
- 路径不叫 `/commercial-publication-drafts`：那是既有录入口的路径，端点表按路径匹配、不分方法，重复会在装配时 panic。

**二、批准与发布都绑定调用方看到的那份内容。**（机制）

- 批准与发布两个命令各多 `ExpectedDigest`（内容摘要）与 `ExpectedShellDigest`（壳摘要）；用例在读到载体之后、判状态之前各自比较：非空且与载体此刻的串不同，批准答 `DRAFT_CHANGED`（沿用既有格），发布答 `DRAFT_CHANGED`（新增一格 `PublicationDraftChanged`）。内容身份先于状态：已批准的载体对着旧摘要批准，答的是「已变更」，不是「已批准」——后一个答案会让调用方以为批的是自己看过的那份。
- 壳摘要 `PCS-1:<sha256>` 盖适用范围、有效区间起止与指名引用（按载体上记下的顺序），不盖身份四元（它是键）与正文；时刻取 UTC 微秒，载体册以微秒存时刻，录入答复里算出的串与之后读回算出的串必须相等。列表、单份读回与录入、批准两口的答复都带 `shellDigest`。
- 应用层空串即不带那一半前置条件，留给手上本就握着载体的调用方（测试与装配）；**运营操作者面的 HTTP 载荷必须带 `expectedDigest` 与 `expectedShellDigest`**，缺席或只有空白逐格问题点名各自那一格（沿用载荷的逐格问题答法，400）。
- `DRAFT_CHANGED` 同其它业务结果一样答 200（ADR-0022），不译 409。

**三、管理台把「待批准」做成独立的一块。**（管理台形状，不是产品规则）

- 列表读自 `GET /commercial-open-publication-drafts`；翻看读自单份读回；抽屉里批准与发布的按钮带的是该抽屉读回的那对摘要（内容与壳），不是列表行上的，更不是前端算的；各册发布页签的五步流程带的是录入答复里的那对摘要。抽屉复述指名引用：它们在壳上、不在规范化文档里。
- 批准者与录入者是否须为不同主体、批准者须持哪一格审批职责，仍由既有的审批职责规则判（ADR-0126），本记录不动。

**四、不在本记录。** 载体撤回 / 作废的口（今天没有，录入同一键重新录入即换内容）；已发布载体的历史查阅（发布后载体行保留，但商业版本目录已是它的读面）；列表分页游标（用既有 `limit`）。

## Consequences

- `ports`：新增 `PublicationDraftRead`（`LoadDraft`、`ListOpenDrafts`），载体册适配器同时满足它；`PublicationDraftRegistry` 不动。
- `domain`：`PublicationDraft.ShellDigest`（`PCS-1`）。
- `application`：批准与发布命令各多 `ExpectedDigest` 与 `ExpectedShellDigest`；发布结果多一格 `DRAFT_CHANGED`。
- `adapters/http`：新增两个只读端点；批准 / 发布载荷多必带的 `expectedDigest`；载体发布口按结果名转写答案，新增的 `DRAFT_CHANGED` 随结果名带出，不另开转写分支。
- `cmd/parcel-api`：端点表两行（操作者查阅读面）、探针各一行、装配点接载体册读口。
- 现存的调用方（管理台、测试）凡批准 / 发布都要带摘要；管理台改读录入答复或列表行里的摘要。
- 无迁移：摘要列与状态列早已在 ADR-0126 的表里。

## 越权风险点

1. **运营操作者面的批准 / 发布载荷多了两个必带字段**（PC owner、管理台）。这是对 ADR-0126 载荷形状的收紧，不是兼容扩展：旧客户端不带摘要会得到 400。管理台是今天唯一的调用方，随本记录一并改；若另有客户端，要先补摘要。
2. **读口挂 `MASTER_DATA_AND_OPERATIONS_READ`，不挂登记写授予**（访问身份 owner）。能看列表的人未必能批准；批准仍要登记写授予与审批职责规则。若日后要把「能看在途待批准内容」收窄到审批职责持有者，需要新增一格读授予，不在本记录。
3. **比较只比两个摘要串**（PC owner）。摘要串自带规范化版本，换了规范化版本的载体摘要必然不同，旧摘要得到 `DRAFT_CHANGED`——这是对的（内容的规范化形状变了，批准者看的不是同一份），不是误报。壳摘要的算法版本 `PCS-1` 同理：日后壳的组成变了要换号，旧串得到 `DRAFT_CHANGED`。
4. **读口的规范化文档是内容的原样回显**（PC owner）。文档里可能有租户的定价、授信等商业敏感数字；读口与既有的商业目录读口同面（同一租户的操作者），不扩大可见范围，但这是第一次把「还没发布」的内容交给读面——此前只有录入者在录入答复里见过。
5. **`ListOpenDrafts` 的 `limit` 与整页失败**（PC owner）。沿用目录读口的 `limit`，按录入时刻由新到旧截断，超过上限时被藏起来的是等得最久的那批；真有这么多在途工作时需要游标或过滤，不在本记录。列表里任何一行读不回（重建门不过）整次答案未形成、答 5xx，不交缺了行的列表；本产品今天没有撤回或作废载体的口，一份坏行会让整页答不出，要靠运维修数据——撤回口是日后的事，不在本记录。
