# ADR-0090: 出向集成的结果代数按调用方的恢复动作分格，「有没有形成答案」由适配器判定且不得看 HTTP 状态码；未配置即拒，不设重试默认值

Status: Accepted  
Date: 2026-09-02

## Context

[ADR-0088](./0088-label-channel-service-enters-the-first-release-service-forms.md) 把面单渠道服务改为首发对客销售的独立服务形态，其 Consequences 点名机制半边要补「末端渠道取面单」与「末端渠道轨迹回传的事实收编」两条能力。两份只读盘点随后各自撞上同一件事：

> **本仓至今没有任何出向集成。** 按 `http\.Client|http\.Get|http\.Post|http\.NewRequest|http\.DefaultClient` 扫全仓 `*.go` **零匹配**（实测于 `9e6d53a`，这个数本身是论点）。`net/http` 的用法全部在服务端一侧——各上下文 `adapters/http/` 的处理器与 `cmd/parcel-api`。

    10|也就是说不只是「缺一个渠道客户端」，而是**连一个可供照抄的先例都没有**。[能力形状盘点](../../.scratch/label-channel-service-first-release/capability-shape-inventory.md)第二段与[轨迹源盘点](../../.scratch/label-channel-service-first-release/tracking-source-seam-inventory.md)第一段分别得出这个结论，两处都点名：取面单与取轨迹**会同时问出同一个问题**，各答一次答案就会分叉，而分叉之后再统一要动两处已经接了真渠道的适配器。

**这件事现在必须定，理由与 [ADR-0022](./0022-http-status-carries-answer-formed-not-business-verdict.md) 当初一样。** 那份记录立的是入向契约，本记录立的是出向契约；两者都属于「设计不出来就补不上」的一类，因为端口形状一旦发布，此后每一家渠道适配器都按它写。

### 出向与入向不是镜像，这是最容易看走眼的一格

ADR-0022 规定「HTTP 状态码只回答有没有形成答案」。顺手把它翻过来用在出向侧，是本记录要挡住的第一件事：**那条规则是本仓作为服务端的自律，对端不受它约束。**

能力形状盘点第二段的公开资料给了实证：UniUni 的 Platform Client API **HTTP 一律 200**，成败在响应体的 `code` 上（0 成功、1002 无效、1014 未找到）。同一段还记了 USPS 的 `LABEL_BROKER` 与 `NONE` 两种 `imageType`——「取了面单」与「回了图件」不是同一件事。若出向侧照抄 ADR-0022 去读状态码，对着 UniUni 会把每一次失败都读成成功。

    20|### 而这一步判错是有资金后果的

归档 QA 第二十二问「面单是否只是一个 PDF 文件」已由用户裁定 `A`，其确认规则里点名了这条链上的真实风险：

> 请求超时，但承运商实际上已经成功下单；客户或系统自动重试；同一包裹被重复购买多张面单。

对应到现行文档，[SCENARIOS](../domain/SCENARIOS.md)「面单渠道」一节写着「防重复、结果待确认、查询、重打、作废、替换和退款分别处理」，`parcel-shipment` 的聚合也已经为此留了 `LabelTransactionResultUncertain` 这一格与 `MarkResultUncertain` 这个转移（[ADR-0084](./0084-label-transaction-is-an-independent-aggregate-with-two-level-results.md)）。**领域侧已经承认「答案未确定」是一种状态，缺的是出向侧把它如实交出来的形状。**

### 难逆转的是分格维度，不是任何一个取值

    30|同一个出向缝会被两条链共用（取面单在 `parcel-shipment`，轨迹源在 `transport-fulfillment`），此后每加一家渠道都照抄。第一次怎么分格，后面全部继承；改一次两侧适配器与它们的结果落点都要重判。

## Decision

### 一、结果代数按调用方的恢复动作分格，不按线路上观察到的失败原因分格

这一条直接继承 [ADR-0029](./0029-retrieval-failure-algebra-is-partitioned-by-recovery-action.md) 的仲裁规则，不另立：调用方要从取值里读出的是「我接下来做什么」，不是「线路上出了什么事」。超时、连接被拒、TLS 握手失败、DNS 解不出、对端 5xx——这些是**我方观察到的现象**，把它们逐项映射成取值，等于把传输层的可见性当作编排的语言。

**恢复动作只有三个，因此只有三格：**

| 取值 | 含义 | 调用方的恢复动作 |
|---|---|---|
| `对端已答复且答复是拒绝` | 对端形成了业务答案，答案是不受理 | 不重发，交业务续办（改请求、换渠道或交人） |
    40|| `答案未确定` | 说不出对端受理了没有 | **不得重发**，只能走查询或对账 |
| `确证未受理` | 有证据表明请求未被对端受理 | 可安全重发同一请求 |

「对端已答复且答复是**接受**」不在失败代数里——那一格由各端口自己的成功类型承载，形状归 `07`/`15`，本记录不预判。

### 二、`答案未确定` 是默认格，`确证未受理` 需要举证

**说不出的时候一律落 `答案未确定`。** 只有当适配器能给出「请求未被对端受理」的实据时，才准落 `确证未受理`——例如连接根本没有建立、或对端在协议层明确回绝了该请求且该回绝不可能发生在受理之后。

这一条是 fail-closed，方向是刻意选的：判错的两个方向代价完全不对称。把 `确证未受理` 误报成 `答案未确定` 只是多走一次查询；把 `答案未确定` 误报成 `确证未受理` 会触发重发，而重发一次取面单调用**产生的是真实的供应商成本与第二个运输标识**。归档 QA 第二十二问点名要防的正是这一格。

    50|**因此超时一律落 `答案未确定`，没有例外。** 超时是本记录最常撞见的情形，也是最容易被误归的：请求已经发出去了，我方不知道对端处理到哪一步。

### 三、「有没有形成答案」由每家适配器判定，端口不得交出 HTTP 层的东西

**出向端口交回的是已经分好格的封闭代数，不是 `*http.Response`，也不是裸 `error`。** 这与 [ADR-0031](./0031-owned-repository-write-outcome-is-a-closed-algebra-not-an-error.md) 对自有仓储端口的要求同形，理由也同：代数里的每一格都要有落点，而 `error` 没有封闭集合。

**平台层不得根据 HTTP 状态码代答。** 状态码在出向侧**什么都不保证**——UniUni 恒 200 是实证，而未来每一家的约定都可能不同。把状态码解读成业务答案的那一步归各家适配器，它是适配器**唯一**不可替代的职责。

### 四、不建第二套幂等键，出向请求锚在领域已有的身份上

`outboxintent.EnqueueOnce` 是本仓内向侧的先例，它保证的是「重发同一份不出第二份」，锚点是信封自带的（来源 + 事件标识），**不是另发一个键**。出向侧对称办：出向请求的幂等锚取领域侧已有的身份（取面单一侧即面单交易自己的标识与它建立时固定的覆盖范围），不新造 `Idempotency-Key` 之类的传输层键。

    60|理由与 ADR-0022 拒绝同一样东西时一致：多一套键就会有两套键不一致的时候，而那时没有规则说谁算数。

### 五、未配置即拒，重试与超时不设生产默认值

出向缝要能表达「本渠道的出向配置尚未提供」，并在未配置时**如实拒绝发起调用**，自成一格作答——沿用本仓已成建制的未配置格形状（[ADR-0052](./0052-network-evidence-catalogue-has-an-unconfigured-grade.md)、[ADR-0054](./0054-pre-acceptance-control-policy-view-has-an-unconfigured-grade.md)、[ADR-0055](./0055-business-endpoint-intake-has-an-unconfigured-grade.md)、[ADR-0085](./0085-registry-write-faces-enter-the-endpoint-table-with-unconfigured-grade.md)），不另立形。

**超时值、重试次数与退避一律是实例参数**（`PILOT-PARAMETER-REGISTER` 的 `PAR-INT-02`），机制不内置任何一个生产默认值。这不是把问题推走：超时**必须**存在，机制的要求是「未给出超时即不得发起调用」，而不是「未给出就用 30 秒」。默认值在这里格外坏——一个猜出来的超时会把本该落 `确证未受理` 的快速失败拖成 `答案未确定`，反过来也一样。

**凭证只定位置不填值。** 账号与密钥属 `PAR-INT-02`，机制里不出现任何一个渠道的字段名、账号或频率（ADR-0088 Decision 五）。

### 六、编排不得自动重试 `答案未确定`

    70|这一格的续办路径是**查询或对账**，不是重发。因此每个出向端口在定形状时都欠一个配套的查询能力——`07`（取面单）与 `15`（轨迹源）各自要正面回答「这一家怎么查」，查不了的要如实记为「该源无查询口」，不得以重发顶替。

通用重试中间件与 HTTP 重试库对这一格一视同仁地重发，因此**不得把出向调用交给它们托管**。这笔成本记在本决定这一边。

### 七、落位与范围

出向缝落 `internal/platform/` 下的新包，两条链共用；**不得只落在某一个上下文的 `adapters/` 里**——那等于把先例藏进一处实现，而另一条链会重新发明一遍。各家渠道的适配器仍按[渠道适配缝备忘](../design/channel-adapter-seams-design-note.md)「一类数据一张票」逐家另立，落在各自所有权上下文的 `adapters/` 下。

**本记录只定失败代数、判定归属、幂等锚、未配置格与重试纪律。** 它不预判取面单端口的四处形态差异（调用次数、多份图件、批粒度、成败信号层）如何进类型——那归 `07`；也不预判轨迹源取拉取还是回调——那归 `15`。

## Consequences

- **每个出向端口必须先有一个封闭的失败代数**，三格各有落点，没有「其他」这一格可用，也不允许有。
    80|- **每个出向端口欠一个查询能力。** `答案未确定` 的续办只能是查询或对账，端口若答不出「怎么查」，这一格就是死的——聚合会积下永远停在 `LabelTransactionResultUncertain` 的交易而没有出路。
- **不能把出向调用交给通用重试库或服务网格的重试策略托管。** 它们按状态码与超时重发，正好踩中本记录要挡的那一格。
- **未配置格要一路贯到装配。** 与既有未配置格同形：生产装配未接真渠道时，出向缝如实答未配置，而不是静默失败或空实现。
- **判错的方向是把 `答案未确定` 报成 `确证未受理`。** 这是本记录唯一有资金后果的判错方向，评审出向适配器时先看这一格。
- **可诊断性属适配器，不属结果代数。** 运维要分辨超时与连接被拒，从适配器自己的日志与指标里看，不从交给编排的取值里看——这一条与 ADR-0029 的同名结论同源。
- **本记录不解除任何闸门。** Bento 持久化闸门原样有效；本记录也不承诺任何真实渠道被接入——真渠道账号属 `PAR-INT-02`，租户尚未到位，`08` 的合成替身只记 `S` 级证据。
- 新增一项判断成本：每写一家适配器都要先分清哪些回复算「对端答了」、哪些算「说不出」。这一格没法从 HTTP 层自动得出，只能逐家读对端文档。

## Alternatives considered

- **把 ADR-0022 镜像到出向侧，按 HTTP 状态码判定答案是否形成。** 否决：ADR-0022 是本仓作为服务端的自律，对端不受它约束。UniUni 恒回 200 是已取证的反例，照此实现会把每一次失败读成成功。这是本记录最想挡住的一条，因为它看起来最像「保持一致」。
    90|- **按线路失败原因分格（超时 / 连接被拒 / TLS 失败 / DNS 失败 / 对端 5xx / 对端 4xx）。** 否决：ADR-0029 已经裁过同一个岔路——恢复动作相同的两个原因不需要各占一格。更要紧的是这些原因与「对端受理了没有」**不是一一对应**：超时可能已受理，连接被拒通常未受理，而对端 5xx 两种都可能。按原因分格会让调用方拿着一个精确的现象描述，却仍然答不出该不该重发。
- **默认可安全重发，只在明确超时时才标为不确定。** 否决：fail-open，且失败方向正好是有资金后果的那一侧。归档 QA 第二十二问点名的「请求超时但承运商实际已成功下单 → 重试 → 同一包裹被重复购买多张面单」就是这条路径。
- **只定两格（成功 / 失败），把不确定压进失败。** 否决：领域侧已经把它分开了——`LabelTransaction` 有 `LabelTransactionResultUncertain` 与 `MarkResultUncertain`，SCENARIOS 也写明「结果待确认」与其余动作分别处理。出向侧压成两格，等于让适配器把一个领域已承认的状态在进入领域之前就抹掉。
- **引入成熟的弹性库（断路器、退避重试、舱壁）作为本记录的答案。** 否决：那些是**策略**，本记录要定的是**代数**。策略可以在代数之上另行引入，但它答不出「这一次到底受理了没有」，而那正是唯一难逆转的一问。反过来，先引入策略会让代数被库的抽象倒着定形。
- **给出向配置一套技术默认值（如 30 秒超时、三次重试）以便机制能自测。** 否决：违反[红线](../../AGENTS.md#红线)「未确认参数保持可配置或显式未决，不写死为生产默认」。且默认值在这里有实质危害——猜出来的超时会直接改变一次调用落在哪一格。自测由 `08` 的合成替身承担，替身可以显式给出超时，那是隔离取证不是生产默认。
- **让取面单与轨迹源各自表达一次。** 否决：这正是两份盘点各自点名的分叉风险，也是票 `02` 立票的全部理由。分叉之后再统一，要动两处已经接了真渠道的适配器。
- **不立记录，在第一个出向适配器的注释里定。** 否决：违反红线「单一权威」。另一条链的作者只能靠反推，而反推最容易得出的正是上面被否决的第一条。
- **等第一家真渠道能接入时再定。** 否决：租户尚未到位，真渠道账号属 `PAR-INT-02`，「等」的终点不可预期；而 `07`/`08`/`09`/`15`/`16` 五张票现在就卡在这一问上。同 ADR-0022 的对应条：等端开工时端点已经写好，那时改的是既有契约，不是空白。
