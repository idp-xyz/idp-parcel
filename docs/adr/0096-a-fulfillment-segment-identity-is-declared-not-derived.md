# ADR-0096: 实际履约段的身份是声明出来的，不是从任何单项事实推导出来的

Status: Accepted
Date: 2026-09-02

## Context

`transport-fulfillment` 的 CONTEXT 把实际履约段定义为「由有效收寄或权威交接事实形成的**共同运输执行与控制责任范围**」，并用一条硬句划定它何时成立：

> 载运对象通过有效收寄或权威交接进入运输方控制时，其履约参与关系和适用实际履约段才成立。扫描、订舱确认、承运接受、列入总单或舱单、车辆到场、装载分配和物理装载中的任一单项均不能替代该边界。

领域层实现了这条（`EstablishSegmentWithPickup` / `EstablishSegmentWithHandover` / `JoinWith*`），[tf-unwired-seven/01](../../.scratch/tf-unwired-seven/issues/01-actual-fulfillment-segment-registry.md) 又补上了登记册与重建门。**但接编排时撞上一个 CONTEXT 没有回答的问题：段的标识从哪来。**

实测于 `e1f9d2a`：`FulfillmentSegmentReference` 在全仓只出现于领域层、其测试与新落的适配器，**生产路径上没有任何地方签发过一个段标识**。CONTEXT 通篇也没说谁签发、按什么粒度——它只说了段是什么，没说两次控制事实何时算同一个段。

这个问题不能绕过去，因为「首个对象立段、后续对象加入既有段」这条分支要靠它判。**选错不是一个可以事后改的 bug**：把本属两个控制责任范围的对象归进同一个段，等于宣称一方对另一方的货也负着共同控制责任，而那正是这个聚合存在的全部意义。

## Decision

**一、段的身份由登记控制事实的一方显式声明，本上下文既不推导也不铸号。**

收寄登记与交接登记各收一个可选的段引用入参。给了就按它成立或加入，没给就**段不成立**——不铸一个默认号，也不拿任何单项事实顶替。

**二、三条不推导，各有其不可用的理由，不是同一条理由说三遍。**

- **不从实际承运商推导。** CONTEXT 明写「实际承运商可以在实际履约段成立时仍处于待确认」。拿一个成立时可能不存在的值当身份，等于让段在承运商确认之前无法成立——而 CONTEXT 要的恰恰是它此刻就成立。
- **不从计划履约段推导。** 它可以缺席（明确允许待路由的产品在没有可行候选时照样实际揽收），且 CONTEXT 说「任何关联都不得用实际事实覆盖原计划」——拿计划段当实际段的身份，正是用实际事实去定义原计划的一种。
- **不把交接范围或揽收任务隐式等同于段。** 这两个是**操作组织单位**，与「共同控制责任范围」重合与否是租户的运营事实。隐式等同在两者不重合时会静默地把不同控制范围的对象并进一个段——而 CONTEXT 用七项列举挡的就是这个，`交接范围` 与 `揽收任务` 不在那七项里只是因为列举不可能穷尽，不是因为它们获准替代。

**三、缺席是一种答案，不是一次失败。** 未声明段引用时，控制事实照常登记（它是已发生的物理事实，且 CONTEXT 把接货时间称为责任起点锚），编排如实交回「段未成立：未声明控制范围」。**登记不因段没成立而回滚**——那会让一次段登记故障抹掉一条已经发生的事实。

**四、粒度政策属实例半边，本产品不代租户拟。** 「两次控制事实何时算同一个共同控制责任范围」——一次揽收一个段？一辆车一趟一个段？一个承运商一段线路一个段？——是租户组织运输控制的方式，不同物流企业不同。产品提供的是**登记与判断的能力**，不是那条政策。它在参数登记册上留空并拒绝默认值。

## Consequences

- **CONTEXT 那条定义性边界在首发下仍然跨不过去，而这一次是有依据的空**：机制齐备（能登记、能判断、能如实作答未成立），缺的是租户声明。这与本仓「参数显式未配置」判据一致，**与「规则没有执行器」不是一回事**——后者是没有人能做这件事，前者是能做但没人来做。
- 消费方（`parcel-shipment` 采认收寄、`node-operations` 控制转移）读到「段未成立」时不得自行补一个段。它们本来也不拥有这个判断。
- 段引用的**格式**不在本 ADR 范围内。它是一个引用，声明方给什么就是什么；本上下文只校验非空，不校验形状——校验形状等于偷偷规定了一种粒度。
- 若他日出现「绝大多数租户都按某一种粒度组织」的实证，那时可以讨论一个**可覆盖的建议默认**。今天没有那个实证，一个租户都没有。

## Alternatives considered

- **由本上下文按交接范围铸号。** 否决，理由见决定二第三条。它最诱人，因为交接范围恰好是「这一次交接」的成员集合、而 `SummarizeHandovers` 已经按它汇总——但汇总是**派生**，把派生用的分组键升格成聚合身份，会让两者从此不能各自演进。
- **由登记册铸一个流水号，"同一个段"靠一个归集键查重。** 否决：归集键是什么，就是本 ADR 要回答的那个问题，换个位置问一遍而已。铸号只是把未决藏进了实现。
- **给段加一个「粒度种类」枚举，先开两格（按交接范围 / 按揽收任务）。** 否决：那是在没有任何租户实证的情况下先猜两种，而封闭集一旦开出去就难收；更坏的是它读起来像已经调研过。
- **段成立失败即拒绝控制事实登记。** 否决，与 CONTEXT 直接冲突：控制事实是已发生的物理事实，责任起点锚要求它先被保全。

## 裁决方的能力边界

本 ADR 由 MCP-3 受用户明确授权自决。读过：`transport-fulfillment` 的 CONTEXT 全文、`domain/actual_fulfillment_segment.go` 与其测试、八例应用编排各自调用的领域构造、`ports.go` 十二组端口、`migrations/transport_fulfillment/` 五份既有迁移。**没有读**：`node-operations` 与 `parcel-shipment` 侧对段的消费预期（它们今天没有消费段——段从来没有生产实例）、任何真实租户的运输组织方式（不存在）。

因此本 ADR 裁的是**结构**：身份由谁给、不能从什么推导、缺席怎么答。它**没有裁**具体粒度政策，那需要租户实证，本 ADR 第四条把它显式留空正是这条边界的体现。
