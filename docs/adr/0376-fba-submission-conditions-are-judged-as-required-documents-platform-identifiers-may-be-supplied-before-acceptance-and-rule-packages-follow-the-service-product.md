# ADR-0376：FBA 提交条件按「必要资料」判、缺了等客户补；平台号受理前可经受控补充补报；接单规则包随服务产品选，合同不必指名

Status: Accepted（2026-11-11，Claude Code 会话代决：用户原话「按头部系统的做法帮我决定这三件事，然后做09」，三件事即票 [declared-goods-lines/09](../../.scratch/declared-goods-lines/issues/09-cross-field-condition-executor-for-acceptance-rule-packages.md)「要先定的」三项。代小包托运、参与方与商业与产品 owner 决，越权风险点见文末，待小包托运、参与方与商业 owner 复核。起草能力边界：读过 ADR-0042、ADR-0032、ADR-0153、ADR-0157、ADR-0147、ADR-0374 与 ADR-0373 全文，UC-PS-001 判组表与 `BD-PS-001`、`BD-PS-006` 两行，PS 与 PC 两份 CONTEXT 的受理与合同各节；受理判断与商业解析的代码由子代理通读后报告。头部系统的做法凭行业通行做法与公开资料，出处见 Context 末。）部分停用 [ADR-0374](./0374-dedicated-line-fba-headhaul-is-an-ordinary-shipment-request-one-platform-shipment-one-request-one-carton-one-parcel.md) 决定四一句、[ADR-0014](./0014-versioned-canonicalization-shape-for-content-digest.md) Consequences 一句。<!-- 索引注记 -->｜**判据**：服务产品所采用接单规则包以 `CROSS_FIELD_CONDITION` 引用已发布的小包托运提交条件参考配置时，受理判断在「必要资料」组逐条判，未满足判`未定`、续办方是客户（受控补充），不拒单；不透明引用照旧不判。平台货件号、平台参考号与平台箱标号在受理前可经受控补充补报或更正，补充带平台段即这一版起的平台声明，接受后不再改。一个货主账户可以同时采用多个各带接单规则包的服务产品：规则包按申报的服务产品选（ADR-0153），客户合同不必指名接单规则包，指名了只作确认

## Context

ADR-0374 决定三把 FBA 头程的要求（平台货件号、每箱平台箱标号、装箱分配报全）放进服务产品所采用接单规则包的必填与跨字段条件（`BD-PS-006`），产品不内置、没配置不判。实现时三件事没有着落（票 09「要先定的」）：

1. 条件不满足时结果挂在哪个判组、续办方是谁。判组是本上下文的封闭集合（ADR-0042），「成员基线」「必要资料」两组至今没有生产者；规则类别 `CROSS_FIELD_CONDITION` 是规则包里的归档类别，与判组是两套东西。
2. 平台号缺了怎么补。ADR-0374 决定四让平台箱标号与客户包裹件号走同一套「随首次提交声明在委托上，不随提交版本重报」，受控补充口拒收箱标号、补充载荷没有平台货件段——缺了就补不上，只能撤回重下。
3. 一个货主账户能不能同时采用两个带不同规则包的服务产品（小包与 FBA 头程）。演示合同的外壳与正文都指名唯一一个接单规则包，闭包核对要求解出的就是它（ADR-0032），给同一账户加一个 FBA 产品就得另立合同。

头部系统的做法：

- 货代与专线的 FBA 头程下单，平台货件号与每箱箱唛是该产品的必填项；缺了不退单，单子停在「待补全 / 资料不全」，客户补录后继续，截单（入库或交运）之前都可以补或改。亚马逊自己允许货件在进入收货（Receiving）之前修改；箱唛要在提货、出口之前贴好，信息在订舱约仓之前交给货代。
- 一个货主账户同时下小包专线、FBA 空派、海派是常态。各产品各有自己的必填项与价格，客户协议覆盖多条产品线，不按产品各签一份合同。

出处（公开资料，非权威规范）：亚马逊 SP-API Fulfillment Inbound v2024-03-20 中文文档；Sellercloud FBA Inbound Shipment Wizard 说明（收货开始之前可改数量）；凤凰网科技 FBA 头程备货攻略（箱标缺失或错误是拒收主因，纸箱信息要先交货代约仓）。

本仓已有的机制正好接得上：UC-PS-001 判组表里「必要资料」一组定义为「按产品、合同、法人、服务/关务范围和有效期装配版本化资料规则」，确定性失败时「按适用规则形成拒绝、待补充或受控纠正」；受控补充（新提交版本）与「等待受控补充」的续办路已经在用；ADR-0153 决定四已按委托申报的服务产品收窄规则包，规则包版本外壳指名它的服务产品，「同一范围两个产品各配一份接单规则包」是商业解析已支持的形态。

## Decision

**一、提交条件归「必要资料」组判，未满足是`未定`、续办方是客户。**

- 服务产品所采用的接单规则包以 `CROSS_FIELD_CONDITION` 类别引用小包托运随产品发布的提交条件参考配置（`REFCFG-1:parcel-shipment/submission-conditions/…`）时，受理判断在「必要资料」组按那一版参考配置逐条判，对象是委托当前提交版本与委托上的平台声明。
- 只在规则包声明「必要资料」组适用（ADR-0042 的适用判组声明）时判。声明了适用而没有可执行的条件引用，这一组判通过：它只对已发布、本上下文读得懂的条件负责。不带 `REFCFG-1:` 前缀的不透明引用照旧不判，判成不满足等于替租户发明规则。
- 条件未满足：这一组判`未定`，续办方是客户，受理任务停在等待受控补充；客户交来新提交版本后重判。不形成拒绝——头部系统缺资料是「待补全」，不是退单；只有规则明说「缺了不允许补充」时才拒（`BD-PS-001` 原句，那是租户取值）。
- 结果逐条、逐件说清：委托级条件出一条版本级检查，逐件条件按缺的包裹各出一条。受理任务记下未满足的条件码与包裹，查阅面照实交出，客户与运营看得到缺的是哪一条、哪几箱。
- 规则包登记时，带 `REFCFG-1:` 前缀的规则引用要打开得到已发布的那一版，打不开答登记不成立（写法同 ADR-0157 决定三），不让一条拼错的引用登进去、然后永远不判。

**二、平台货件号、平台参考号与平台箱标号在受理前可经受控补充补报或更正。**

- 受控补充的载荷照提交口同形，可带平台货件段与逐件箱标号。补充重报整份内容、不从旧版本继承（既有纪律），平台段也是：带了，就是这一版起委托的平台声明；没带，就是这一版不报。形状规则与提交口相同：平台与平台货件号同在同缺，箱标号要有平台货件，委托内不重号。
- 委托接受之后平台声明不再改：关联在接受时按接受基线形成（ADR-0374 决定四），改号走撤回重下或关联新委托，资料修订口不收平台号。
- 被补充撤掉的箱标号与委托拒绝、撤回时一样，不再算歧义信号，并照样响声明撤除门铃，等着按号核对的节点重判。
- 平台声明是委托的现行声明，被补充替换掉的那一份不在聚合里另留历史；每次补充的载荷摘要在来源保全里，可以按请求追溯。

**三、一个货主账户可以同时采用多个各带接单规则包的服务产品；规则包随服务产品选，客户合同不必指名。**

- 接单规则包按委托申报的服务产品选：规则包版本的外壳指名它的服务产品，商业解析按申报产品收窄（ADR-0153 决定四）。小包与 FBA 头程是同一客户账户下的两个服务产品，各配一份规则包。
- 客户合同不再必须指名接单规则包。合同管客户关系、责任法人与结算；产品的接单要求随产品走。合同外壳指名了，照 ADR-0032 只作确认，而这只在合同只覆盖那一个产品时说得通，所以覆盖多个产品的合同不指名。合同正文的「接单规则包」一格改为可缺：没指名即不编码；已发布的合同版本照存不改。
- 这是对客户合同一册规范化形状的同号改形（`PCC-1` 不换号）。前提照 ADR-0267 决定三：首个租户实例进生产之前，已存的合同摘要只在演示库与测试夹具里，指名了规则包的旧文档逐字节同前，进生产的每个构建都认得新形。照它的写法部分停用 ADR-0014 Consequences 一句，适用场景只限这一次。
- 接受前财务控制策略仍须由合同指名（PC CONTEXT 同一句的另一半不变）：它管的是这个客户的钱，不随产品变。

**四、资料修订的规范化形状 `PAM-1` 同号加可缺键 `goods`。** 票 declared-goods-lines/06 让资料修订收委托级资料组「货物明细」，`PAM-1` 文档多一个可缺键：没交货物明细即不编码，旧载荷逐字节同前，已存摘要与重放照旧成立（钉了取证于改形前的摘要常量）。前提与决定三相同（ADR-0267 决定三，首个租户实例进生产之前）。这一次当时只写在 UC-PS-002「给开发的交接」里，按 ADR-0267 决定三不算写明，在这里补上。

- [ADR-0374](./0374-dedicated-line-fba-headhaul-is-an-ordinary-shipment-request-one-platform-shipment-one-request-one-carton-one-parcel.md) 决定四「平台箱标号与客户包裹件号走同一套：随首次提交声明在委托上，不随提交版本重报；」——改为：平台箱标号（连同平台货件号、平台参考号）随首次提交声明，受理前可经受控补充补报或更正，补充带平台段即这一版起的声明；接受后不再改。**适用场景**：受理前（委托`已提交`）。决定四的其余各句不变——接受时形成关联、`已提交`期间算歧义信号、拒绝撤回后不再算、委托内重号答形状不对、恒范围相容。客户包裹件号照旧随首次提交声明、不随提交版本重报，不在本条之内。

## Consequences

- FBA 服务产品上线时，租户在它的接单规则包里声明「必要资料」组适用并引用 FBA 头程提交条件参考配置，缺平台号或装箱的委托停下等客户补齐；小包产品不引用就不判。
- 受理任务多记一样东西（未满足的条件与包裹），查阅面多一格。
- 受控补充口多收平台段；已在用补充口、没带平台段的客户集成，补充后平台声明会清空——补充本来就是整份重报，契约照此写明。
- 客户合同正文的规范化形状多一种「不指名接单规则包」的写法，`PCC-1` 同号改形，指名了的旧文档逐字节不变；首个租户实例进生产之后再有这类改动，照 ADR-0014 换号。合同库表那一列改为可空。
- 一个范围内两个客户对同一产品要不同规则包时，靠的是规则包的适用范围（每个客户各自的范围），不是合同指名——这与今天按范围解析一致，本记录不改。

## Alternatives considered

- **条件不满足直接拒绝。** 头部系统不这样做：缺平台号是「还没给」，不是「不能运」；拒了要客户重下单、换运单号，箱子可能已经在路上。保留给规则明说不允许补充的租户。
- **条件结果挂「产品与服务」组。** 会把「客户没报全」与「产品依据解不出」混成一格，续办方一个是客户、一个是运营，合不得。
- **另立一个判组。** 「必要资料」的定义已覆盖按产品装配的版本化资料规则，另立一组要改 ADR-0042 的封闭集合，没有收益。
- **平台号缺了只能撤回重下。** 与 ADR-0374 决定四一致，代价是平台货件号录错一位就要整票重下、换运单号，与头部系统的「截单前可改」相反。
- **补充只「打补丁」平台号（没带即不变）。** 与受控补充整份重报的既有纪律相抵，同一份载荷里一段整份、一段补丁，客户集成更容易错。
- **合同按产品各指名一个规则包（引用改成多值）。** 改动更大（引用表、确认规则、合同正文都要换形），而商业解析已经按产品选规则包，合同上再写一遍是第二处权威。

## 越权风险点

1. 判组归属与续办方（决定一）：「必要资料」组的生产规则、不拒单的取舍。归 PS owner。
2. 平台号受理前可补（决定二）：部分停用 ADR-0374 决定四，节点歧义判断多一种撤除来源。归 PS 与节点作业 owner。
3. 合同不必指名接单规则包（决定三）：改 PC CONTEXT 合同不变量，合同正文换规范化版本。归 PC owner。
4. 头部系统做法的出处是行业通行做法与公开资料，不是权威规范；第一个真实 FBA 租户到来时复核（开发主线 `PA-FBA-01`）。归产品 owner。
