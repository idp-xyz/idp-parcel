# ADR-0018: 产品内客户端应用与后端共享发布边界并落在顶层 `apps/`

Status: Accepted  
Date: 2026-08-10

## Context

[Go 首个消费者切片决策简报](../design/parcel-go-first-consumer-slice-decision-brief.md)的「代码与模块边界」已定「新增进程入口与对外交付形态（额外 `cmd/` 二进制、前端或其他客户端）是加法：它们在 `internal/` 之外落位」。这句话说了不在哪儿，没说在哪儿。同节随后补的一句把落位收敛为两个位置——本仓根目录新开 `web/`，或独立前端仓——并标为尚未决定。

**那句补充按「一个前端」成形，而需要界面的地方不止一个应用。** 逐条查各上下文，需要人操作的位置分成设备与交互都不同的两类：

- **人坐在桌前。** [`visibility-exception`](../domain/visibility-exception/CONTEXT.md) 的异常分诊「进入人工复核」与处置协调；[`settlement-accounting`](../domain/settlement-accounting/CONTEXT.md) 的对账与金额核销；[`parcel-shipment`](../domain/parcel-shipment/CONTEXT.md) 在「适用规则显式要求人工业务判断时」的接受前人工复核；[`PN-08`](../design/pn-08-end-to-end-pilot-and-stage-admission-development-handoff.md) 的阶段决定与暂停恢复。
- **人站在工位上。** [`node-operations`](../domain/node-operations/CONTEXT.md) 的作业位置含「工位」，且明写「现场人员不得以覆盖、合并或『最后一次扫描为准』决定正式包裹身份」。这是手持设备连续扫描的场景，不是桌面浏览器的场景。

两类的设备、输入方式与现场约束不同，是两个应用，不是一个应用的两个页面。单个 `web/` 装不下第二个。

**`cmd/` 也装不下它们。** Go 工具链把 `cmd/<x>` 当 main 包，那是 Go 进程入口的地盘，非 Go 的客户端进不去。仓库根目录当前只有 `cmd/`、`internal/`、`docs/` 与 `.github/`，非 Go 的对外交付形态没有落点。

**`P-01` 推不出这件事。** 简报的 `P-01` 定「独立 Git 仓库、单仓库、模块化单体和单 `go.mod`」，那是 Go 侧的决定，`go.mod` 管不到非 Go 代码。「后端在一个仓」因此推不出「客户端也在这个仓」；这两件事必须分别决定，本记录补的就是后一半。

难逆转的不是目录名，是发布边界。移动一个小应用的目录成本接近零，但「产品内的端与后端同版本发布」一旦成立，CI 形态、发布流程与端的迭代节奏都压在它上面；它与 [ADR-0002](./0002-independent-data-runtime-release-boundary.md) 的独立发布边界相邻，属于必须记录的取舍。

## Decision

**客户端应用按服务对象决定归属。** 服务租户自己的作业与治理人员的客户端应用属于产品的一部分，与后端同仓、同版本发布。两类明确不在此列：租户的锚点货主客户走 `PAR-INT-01` 登记的租户**已有**接入渠道——那是租户自己的 API、标准文件或门户，本仓不建那个界面；开发方自用的演示或内部工具独立于本仓，不混入产品仓。

**产品内的客户端应用落在顶层 `apps/`，每端一个子目录，不在根目录平铺。** 顶层因此只增加一个入口，与端的数量无关；`apps/` 与 `cmd/` 构成对称的一对——`cmd/` 是 Go 进程入口，`apps/` 是面向人的应用入口。

**端之间的共享物落在顶层 `packages/`。** 生成的 API 客户端、共享类型与设计令牌属于此列。

**`cmd/` 与 `internal/` 的现有边界不变。** `cmd/` 仍只放 Go 进程入口；`internal/` 仍是限界上下文的所有权边界。客户端应用不进 `internal/`，也不得绕过应用端口直接读取任何上下文拥有的表。

**不预建空壳。** `apps/` 等到第一个真实端落地时才建，`packages/` 更等到出现第二个端且确有共享物。简报「不为将来的多端形态提前重排目录或预建空壳」继续有效，本记录只固定形状与判据，不创建目录。

## Consequences

- 第一个端落地时 CI 从单 job 纯 Go 变成多语言：现有 `gofmt`、`go vet`、`go test -race`、`go build` 四步之外要加独立 job 与工具链。这笔成本记在本决定这一边，是选「同仓」换来版本锁定所付的价。
- Go 侧不受影响：`go build ./...` 与 `go vet ./...` 忽略非 Go 目录，`gofmt -l .` 只报 `.go` 文件，`apps/` 与 `packages/` 出现后无需改动现有 CI 步骤。
- 端的发布节奏被后端锁住。想让某个端独立快跑，必须先改本记录，不能在发布流程里临时松开。
- 仓库从纯 Go 仓变成多语言仓。届时 `README` 与本机环境文档要补非 Go 的前置条件，贡献者不再只需要一套 Go 工具链。
- 新增一项判断成本：每新增一个端都要先按判据判断它服务谁。判错的方向是把租户货主客户的界面建进本仓——那会与 `PAR-INT-01` 登记的既有渠道重复，并给产品加一份它不该拥有的责任。
- 本记录不承诺任何端会被实现，也不解除 [ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 的闸门。业务 HTTP 端点当前一个都没有，端在闸门开之前无接口可调；位置定了不等于可以开工。

## Alternatives considered

- **维持「一个 `web/` 或独立前端仓」二选一。** 否决：它按一个前端成形。桌面治理界面与工位手持扫描的设备与交互都不同，是两个应用；这个形状装不下第二个，下次仍要重推一遍。
- **根目录平铺 `web/`、`mobile/`。** 否决：根目录随端数量线性增长；共享物迟早要再开一个根条目，等于用两个根条目换一层嵌套。且 `cmd/` 是 Go 进程、客户端应用不是，性质不同却并列同层，读者分不清哪边归 Go 工具链管。
- **全部放独立前端仓，本仓保持纯 Go。** 否决：CI 确实更简单，但这些端服务的是租户自己的作业与治理人员，属于产品的一部分。跨仓要另建版本锁定机制才能保证端与后端同版本，那份复杂度不比多语言 CI 少，且它落在发布流程里，比落在 CI 配置里更难查、更容易在赶工时被绕过。
- **每端一个独立仓。** 否决：协调成本按端数量增长；共享物要么在各仓复制，要么再开一个包仓，把本决定要解决的问题原样推到仓库层。
- **顶层命名为 `clients/`。** 否决：端之间最主要的共享物恰好就是生成的 API 客户端，顶层再叫 `clients/` 会与它撞词。`apps/` 同时涵盖桌面浏览器端、工位手持端与将来可能的其他形态。
- **现在就建出 `apps/` 占位。** 否决：简报明禁为将来的多端形态预建空壳，与「`partycommercial` 后续按真实切片建立，不预建空模型」是同一类约束。
- **不立 ADR，只改简报那一句。** 否决：难逆转的是发布边界而不是目录名，它与 ADR-0002 的独立发布边界、`P-01` 的单仓库相邻。就地改会把裁决理由散落进设计交接，下次同类问题无处可查；这个问题已经在三个会话里各被完整推导过一遍，正是单一权威要消除的重复。
