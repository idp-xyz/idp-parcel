# ADR-0025: 跨上下文调用的适配器落在消费侧，翻译职责由它独占

Status: Accepted  
Date: 2026-08-11

## Context

[Go 首个消费者切片决策简报](../design/parcel-go-first-consumer-slice-decision-brief.md)的代码边界只写了一句约束：「模块不能直接读取其他模块拥有的表。将来同进程调用也必须通过应用端口或已确认事件语义。」它规定了**必须走端口**，没有规定翻译代码放在哪个包、由谁写、能引用谁的类型。

至今这个空白没有代价，因为全仓一个跨上下文适配器都没有——[机制半边现状](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#横切缺口不属任何单一切片)记着「端口是纯接口，今天唯一的实现是测试用替身」。空白现在要付代价了：`UC-PC-002` 的两阶段解析与提交前重解都有了应用编排，而 `parcel-shipment` 的 `CommercialBasisResolver` 端口等的正是它。把这两头接上，本仓第一个跨上下文适配器就出现。

**接的那一刻立刻暴露两个上下文的模型并不对齐。** `party-commercial` 的 `AsOfPolicy` 刻意不携带时点值——「取值由消费方逐项形成，正是这一点让一个全局时间无法替代所有下游判断时点」；而 `parcel-shipment` 的 `DeclaredAsOf` 是带值的，`JudgmentAsOf` 干脆是它的类型别名，理由是「形成值时不得添加任何策略没有授权的东西」。两边各自成立，但合起来留下一个没人回答的问题：`UC-PC-002` 步骤 6 说的那个「消费方」，在代码里是谁，值在哪一层形成。

这类不对齐不是缺陷，是限界上下文该有的样子——[CONTEXT-MAP](../domain/CONTEXT-MAP.md) 与红线「所有权清晰」都要求各上下文表达自己的语言。真正要定的是**它们在哪里相遇**。

**难逆转的是依赖方向。** 一旦两个上下文的类型在某处相互引用，拆开要同时改两边的领域语言与全部调用点；[ADR-0001](./0001-autonomous-product-domain-boundary.md) 与 [ADR-0002](./0002-independent-data-runtime-release-boundary.md) 立的自治边界、红线「所有权清晰」，都指向同一件事，但没有一条落到「代码放哪个包、能 import 谁」。九个限界上下文两两之间都可能出现这条边，第一条边怎么走，后面几十条会照抄。

## Decision

**跨上下文调用的适配器落在消费侧，路径为 `internal/<consumer>/adapters/<provider>/`。** 消费方拥有端口，也就拥有把提供方的结论翻译成自己语言的那段代码。它与 `adapters/http`、`adapters/postgres` 并列——三者都是「把外面的东西翻译成本上下文的语言」，另一个上下文在这个意义上并不比 PostgreSQL 更内部。

**只有适配器包可以同时导入两个上下文。** 任一上下文的 `domain`、`application`、`ports` 都不得导入另一个上下文的任何包。适配器是两种语言唯一相遇的地方，因此也是唯一需要为此写测试的地方。

**端口用消费方的语言定义，提供方的类型不得出现在消费方 `ports` 的签名里。** 端口说的是「本上下文需要知道什么」，不是「那边能给什么」。让提供方的类型进来，端口就成了提供方模型的转发，而消费方从此不能独立演化自己的表达。

**适配器只翻译，不判断。** 它不得把提供方的`未决`读成`不适用`，不得在提供方没给结论时补一个，不得合并两个提供方取值。判断属编排，编排在应用层。

**翻译必须是全函数：提供方封闭集合里的每个取值都要有明确落点，不留 `default` 兜底。** 兜底那一格会成为下一次「合成一格」的入口——提供方日后新增一个取值，会被静默映射成兜底的那一个，而没有任何测试会红。

**适配器就是用例意义上的「消费方」。** 需要消费方形成的值——例如 `UC-PC-002` 步骤 6 的逐项时点值——在适配器里形成，不在消费上下文的应用编排里形成：编排拿到的应当已经是本上下文的语言。适配器为此需要的实例半边协作者，其接口定义在适配器包内，**不进消费方 `ports`**：那种接口要引用提供方的类型（如时点语义引用），进 `ports` 就会把两个上下文的类型焊死在消费方的端口契约上，而上一条正要挡住这件事。

## Consequences

- 第一个落地的是 `internal/parcelshipment/adapters/partycommercial/`，实现 `parcelshipment/ports.CommercialBasisResolver`。
- **同一个提供方被 N 个消费方使用就有 N 份翻译，重复是刻意付的。** 各消费方要的粒度与词汇本就不同，抽一份共享翻译会把差别抹平，而差别正是各上下文语言的价值所在。
- **提供方新增一个结果取值时，每个消费侧适配器都要显式决定它的落点。** 这是本记录要的成本：静默继承一个落点，等于让提供方替消费方作了业务判断。
- 适配器有自己的测试，且不能靠上下游的测试覆盖：它是最容易悄悄合并语义的地方，而那类错误在两端各自的测试里都看不见。
- **本记录不解除任何闸门。** 适配器连接的是两个应用层，两边的持久化与事件发布仍阻断于 [ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 的 Bento 闸门；适配器需要的实例半边协作者同样没有实现。
- 新增一项判断成本：每写一段映射都要先分清「这是翻译还是判断」。判错的方向是在适配器里补一个默认值——那会让一次提供方的未决变成消费方的一个确定结论，而两端的测试都不会发现。

## Alternatives considered

- **落在提供方侧 `internal/<provider>/adapters/<consumer>/`。** 否决：提供方要知道每个消费者的词汇，等于把 N 个下游的语言装进一个上游包。它还会反转依赖——提供方发布一次就要重新验证所有消费者的翻译。
- **放一个中立的 `internal/integration/`。** 否决：两个上下文的类型在一个无主的包里相遇，谁都能改、谁都不负责；且两个上下文都会依赖它，等于用一个共享包把本要隔开的两边重新连上。
- **建共享内核，让两边共用一组时点、解析结果类型。** 否决：这正是抹平差别。`party-commercial` 的 `AsOfPolicy` 不带值与 `parcel-shipment` 的 `DeclaredAsOf` 带值各有各的理由，合并要牺牲其中一条。
- **让消费方 `application` 直接调用提供方 `application`。** 否决：两个上下文的类型会直接出现在编排里，从此拆不开；且编排会被迫处理提供方的结果代数，而那不是它的语言。
- **不立记录，第一个适配器怎么写就算怎么定。** 否决：违反红线「单一权威」，且这条边后面会出现几十次——散在各适配器里的口径，下一个人只能靠读代码反推。
- **等事件机制到位后一律走事件，不做同进程调用适配器。** 否决：事件机制卡在 Bento 闸门，而机制半边不该挂在外部工件上（[ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 已就同类死锁作过裁决）。况且端口调用与事件不是二选一——简报第 82 条把两者并列，本记录只管前者，事件语义的落位留待事件机制真正落地时再定。
