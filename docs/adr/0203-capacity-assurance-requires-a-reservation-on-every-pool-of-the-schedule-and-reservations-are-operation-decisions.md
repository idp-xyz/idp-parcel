# ADR-0203：容量保障——班次挂了容量池，装载分配与确认订舱就要对每个池引用有效预占并声明分配量；预占与释放是两种运营决定，声明需求量与来源，硬上限按预占整段判、带余量拒绝、不可审批越过

Status: Accepted（2026-10-19，Claude Code 会话代决：用户原话「你作为业务和系统专家自决……解决所有的问题」；票 [demo-chain-gaps/20](../../.scratch/demo-chain-gaps/issues/20-capacity-reservation-and-release-decision-faces.md) 起草并落决定三至六，决定一、二由票 21 落装载分配那一半、票 37 落确认订舱那一半。越权风险点见文末，待 TF owner 复核，access-identity owner 知会。）

Date: 2026-10-19

## Context

- TF CONTEXT 写「确认订舱或装载分配需要容量保障时，必须引用、建立或转换明确的容量预占范围」，没写什么时候算「需要」。票 03 把这一格列为要裁的：做成内置策略，还是作租户取值。
- 容量池已能登记（票 17，ADR-0201 补记「池身份」「登记口不改池」）：池身份由（班次、维度）派生，一池一维、一个硬上限。预占、释放、消耗的编排早已在，在 cmd 下零调用，没有入口。
- 编排里的预占只有三量与有效期：说不出这份量从哪来，也不记从哪一刻起占。CONTEXT 要每次容量申请固定「成员范围、采用的测量/数量版本、各容量维数量、单位和判断时点」；本记录让预占固定后四格，成员范围落在哪里见决定三。余量按判断时点那一刻算，而预占没有起点：一份声明在后天、彼时别的预占都已过期的预占，按后天的余量放行，今天就超了硬上限。
- 释放没有身份，重交一遍就再还一份。池按值换存、读池不锁：两笔并发预占各读到同一个旧池、各按旧余量放行，后换存的那一笔把先到者整份删掉。
- 本批代决的单一权威是 [tf-chain-plan](../../.scratch/demo-chain-gaps/tf-chain-plan.md)「03 装载分配与容量」D03-3 至 D03-6 与「跨票通则」X2、X3；本记录把其中的裁定写成决定，计划此后只作索引。

## Decision

**一、保障判据（产品策略；票 21 落装载分配，票 37 落确认订舱）。** 装载分配或确认订舱所在的具体班次只要登记了至少一个容量池，就必须对该班次的每个池引用一份当前有效预占，并逐池声明分配量；没有登记容量池的班次不要求。判据只看班次挂没挂池，不看任何租户取值。已登记的池是硬限制，绕过它就是超配；不要保障的租户不登池即可，不需要第二个开关。

**二、分配关系（机制；票 21 落）。**

- 在预占上建分配关系，守恒为「已分配 ≤ 预占 − 释放 − 消耗」；分配撤回或改版时归还。形成分配时不调消耗：消耗是永久占用，撤回时还不回来。
- 池所在的班次必须等于分配所在的班次。
- 分配量逐池逐维度声明并带来源，来源与决定三的需求来源同一组封闭词；只有件数维的池可以用成员数（UC-TF-003 禁止用对象数顶替别的维度）。
- 新格：`CAPACITY_RESERVATION_REQUIRED`（挂池班次缺预占引用）、`RESERVATION_NOT_ON_SCHEDULE`（引用的预占不在本班次的池上）、`ALLOCATION_EXCEEDED`（超出预占剩余，带余量）。

**三、预占与释放是两种运营决定，都声明需求量（本票）。**

- 决定种类 `CAPACITY_RESERVATION`、`CAPACITY_RELEASE`，挂操作者渠道的「运营决定」能力面（ADR-0151 定族判据：为一个业务范围占住一段运力是生产决定，不是登记册配置）。授予的粒度等于权力的粒度：能占的不因此能放。种类是产品角色模型；谁被授予、准入对照与权威区间是租户取值，演示租户以 `SYN-` 登记。建池仍是登记册配置写（ADR-0201 决定一），不在这两口。
- 需求量是数量、单位与来源三格。来源是封闭的两种：`OPERATOR_DECLARATION`（运营人员声明的一版需求）与 `PREPARATION_DEMAND_SNAPSHOT`（运输准备结果固定下来的需求快照），引用原样保存。释放的来源说的是为什么不再需要这些量。
- 单位必须等于池的单位，按字面比，不换算、不归一大小写；不符答 `UNIT_MISMATCH` 并交回池。单位要声明出来再比，不从池上默认：把「5」默认成池的单位，声明方心里的吨就成了千克。维度不声明：一池一维，落到哪个池就是哪一维。
- 判断时点与释放时点由声明方给（ADR-0023）。
- 成员范围不在预占上另成一格。预占先于装载分配，占的时候哪些载运对象上这一班多半还没定；范围由需求来源固定——准备结果的需求快照固定了它覆盖的成员，运营声明的那一版由声明方对其范围负责——到装载分配时再逐成员落到预占的分配关系上（决定二）。所以此刻范围只经来源引用与分配关系间接可追，而来源不回读（越权风险点 3），见越权风险点 11。

**四、硬上限按预占整段判（产品策略），带余量拒绝，不可越过。**

- 预占从判断时点起占到有效期满；释放从它落下的那一刻起归还；过期后只剩已消耗的那一部分。
- 新预占要在 [判断时点, 有效期] 整段的每一刻都不超硬上限。占用只在某份预占的判断时点上涨，所以最紧的那一刻不是起点就是段内另一份预占的判断时点，逐一比过即得整段最小余量。这条只在预占与释放之间成立：消耗会让过期之后的永久占用回溯变大，它接线时的处置见越权风险点 12。
- 超出答 `CAPACITY_EXCEEDED`（HTTP 200），带整段最紧那一刻的余量（单位同池）与池。命令与载荷都没有任何越过上限的格；带审批、越过一类键的载荷在封闭解码下是坏报文（400）。软容量的受控超配仍归 psb/09，不在本记录。
- 读池在写事务里锁住池那一行（`FOR UPDATE`），判余量与换存同一笔：两笔并发预占串行判，后到者读到含先到者的池。

**五、身份与重放（机制）。**

- 预占引用在池内唯一。同一引用整份相同（数量、单位、来源、判断时点、有效期，时刻按登记册精度比）答 `EXISTING_RESERVATION` 并交回那一份；任一格不同答 `RESERVATION_CONFLICT` 并交回在册那一份，不改写。
- 释放有自己的引用，在池内唯一，不只在一份预占内唯一。同一引用、同一份预占、同内容答 `EXISTING_RELEASE`，不再还一份；改了数量、来源、时点或挪到另一份预占上答 `RELEASE_CONFLICT`，交回在册那一次。
- 重放判在单位与上限之前：池此刻已满时原样重交仍答已有，它占的就是那一份。

**六、分格与次序（机制）。**

- 预占：载荷过构造门（不成立答 `INPUT_NOT_ACCEPTED`，不读池）→ 读池（读不动答未决 `POOL_STORE_UNAVAILABLE`；不在本租户册上答 `POOL_NOT_FOUND`，他租户的池同此）→ 重放与冲突 → 单位 → 硬上限 → 落池。
- 释放：构造门 → 读池 → 释放引用的重放与冲突 → 预占在册（不在答 `RESERVATION_NOT_FOUND`）→ 单位 → 有效区间与守恒：释放时点早于那一份预占的判断时点答 `RESERVATION_NOT_YET_EFFECTIVE`，晚于有效期答 `RESERVATION_EXPIRED`，撞守恒答 `RESERVATION_OVERDRAWN`；这三格交回那一份预占，判断时点、有效期与三量在上面 → 落池。
- 池不在册、预占不在册、单位不符、释放时点早于判断时点各成一格，续办分别是先登池或改指池、改指预占、按池的单位重述数量、按那一份预占的有效区间重述释放时点，不并进`未受理`（ADR-0029）。`未受理`只说载荷单看不成立，不读池；要对着在册的池或预占才判得出的都不并进它，否则声明方拿不到改对所需的那一份。容量编排的`未受理`线上名改为 `INPUT_NOT_ACCEPTED`，与 TF 其余运营决定口与登记口同名，容量池登记口随之改名。
- 只有新预占、新释放用 201，其余都是形成了的答案（200，ADR-0022）。编排答未决时装配整笔回滚再交回答复。
- 预占与释放不入队信封：此刻没有消费者（方案 X3）。不核班次在册：池建立时已核过，池身份由班次派生。

三类：决定一的判据、决定三的来源种类与单位判法、决定四的整段判法是产品策略（内置一种）；决定三的决定种类是产品角色模型，授予、对照、区间是租户取值；硬上限不可越过是 CONTEXT 规则；决定二、五、六是机制。演示租户的预占取值只写在演示种子 README，证据只记 `S`。

## 候选与反方

- **保障做成租户可开关的内置策略。** 让租户关掉保障就是允许绕过已登记的硬上限；不要保障就不登池。否决。
- **判据看池紧不紧张。** 同一笔分配今天要预占、明天不要，判据不可复现。否决。
- **预占与释放共用一种决定。** 能占的就能放，授予粒度大过权力粒度。否决。
- **单位不声明，默认取池的。** 声明方的量纲错在任何一处都不会响。否决。
- **只按判断时点那一刻判余量**（此前的实现）。见 Context：声明在后天的预占绕过今天的上限。否决。
- **判余量取服务端时钟的此刻。** 与 ADR-0023「业务时间由提交方给」相抵，且按整段判已经不需要时钟。否决。
- **释放不带身份，按「同一预占、同量、同时点」认重放。** 同一刻对同一预占合法地放两次各 10，会被吞成一次。否决。
- **乐观并发（池上加版本列，换存时比版本）。** 要改容量池端口的签名（方案 X4 不改 `ports.go`），撞上时也只能答未决让人重交；行锁让后到者直接读到最新池作答。否决。
- **预占时回读运输准备结果，核需求快照在不在。** 准备结果册由同波票 18 立，此刻没有读口。延后，记为风险点 3。
- **给硬上限留一个带审批的越过格。** CONTEXT 明文「触及硬限制时拒绝新的预占或分配，不能以审批绕过」。否决。

## 越权风险点

1. **无池即无保护**（TF owner）。不登池的班次上，装载分配与确认订舱不受任何容量约束。
2. **需求量与分配量是声明值**（TF owner）。与实测不符（`AT-TF-087`）靠重评处置，本记录不核。
3. **需求来源不回读**（TF owner）。`PREPARATION_DEMAND_SNAPSHOT` 的引用此刻不核准备结果在不在、量对不对；运营声明的版本也只是一个引用。去处是票 [demo-chain-gaps/47](../../.scratch/demo-chain-gaps/issues/47-capacity-demand-from-a-preparation-snapshot-is-not-read-back.md)。
4. **软超配仍归 psb/09**（TF owner）。本记录只守硬上限。
5. **资源与载运位置粒度不支持**（TF owner；方案 D03-8）。池只按（班次、维度）立。
6. **判断时点由声明方给**（TF owner）。整段判法让倒填与前填都越不过硬上限，但倒填的释放会把容量提前还回去；有效期已在过去的预占不拒，它此刻什么也不占。
7. **读池一律加行锁**（TF owner）。事务外读池也会等在途的写；本记录落地时读池的只有写编排。同波票 18 的准备评估逐池经 `FindByKey` 读池，若在事务里读，就持各池行锁到事务结束、与预占串行；票 18 合入时要么不在长事务里读池，要么接受串行，并在其票面写明。
8. **逐份预占没有查阅册**（前端 owner）。查阅口只到池级三个和，管理台看不到每份预占的来源与释放明细。池行时刻随每次预占、释放换存成最后一次换存的时刻，不再是建池时刻：池登记口重放回显的 `recordedAt` 与查阅册的池行时刻都随之变（换存改写时刻是既有设计，本记录让它在生产上生效）。去处都是票 [demo-chain-gaps/46](../../.scratch/demo-chain-gaps/issues/46-capacity-reservations-have-no-per-reservation-review-registry.md)。
9. **种类粒度**（psb/07）。两种决定是本记录按「授予粒度等于权力粒度」定的。
10. **缩容之后的余量可为负**（TF owner；票 40）。容量更正把上限缩到既有预占之下时，`CAPACITY_EXCEEDED` 如实报负余量，不截成零。
11. **预占不记成员范围**（TF owner）。CONTEXT 要每次容量申请固定成员范围；预占只固定数量、单位、来源、判断时点与有效期，范围只经需求来源引用与票 21 的分配关系间接可追（决定三）。来源不回读之前，同一来源引用下的范围此刻既不存也不核；若 owner 要求预占自带范围，须加一格并改迁移与两口载荷。
12. **消耗不核硬上限**（TF owner；方案 D03-7「仍不接线」）。领域的消耗此刻未接线：有效期内它不改占用，但过期之后的永久占用随它变大，此前按整段判放行、起点在那份预占过期之后的预占可能事后超上限。消耗接线时要按消耗之后的整段重核上限，或在其决定里写明这一例外。

## 补记：票 21 落地时的补充裁定（2026-10-19，Claude Code 会话代决，待 TF owner 复核）

正文不改。决定一、二的装载分配那一半由票 [demo-chain-gaps/21](../../.scratch/demo-chain-gaps/issues/21-load-assignment-allocates-against-capacity-reservations.md) 落地；计划与正文都没裁、又必须定下的几格记在这里，越权风险点接正文编号续写。

- **分配关系存在哪**（机制）：分配量随装载分配的版本存，一版一池一行、只插不改（TF 迁移 0031），与成员行同一纪律；预占上的分配关系不另存，读池时取各分配当前那一版（没有后继、未撤回）在本池上的那一行派生。撤回版不带分配量，改版带自己重新声明的一组，所以「撤回或改版时归还」是当前版换了这件事本身，不靠哪一次写记得去改预占；旧版那一组照旧在册，分配历史不改写。派生靠版本链是一条线，0031 为此补「一版至多一个后继」唯一索引，存量有并列后继即拒绝施加，与 0021 同纪律。分配行的预占外键延迟到提交时核：池按值换存是先删后插回同一组预占，立即核会让每次预占、释放都撞在已有分配上。
- **守恒怎么算**（机制）：一行分配量对那份预占剩下的量判——预占量减已释放（全部已落的，不按时点）、已消耗，再减其他装载分配当前那一版分走的量；同一分配原有的那一份不算，它被新的一版接替。释放与消耗的守恒同样把已分配算进去：已分配的那一段要先撤分配才放得出来；消耗此刻只从未分配的余量里取，依据分配的消耗接线时要改成转换那一条分配关系（越权风险点 15）。预占口与释放口回显的预占加「已分配」一格，释放撞线时声明方看得见挡住它的是分配。形成分配不改池、不调消耗，可用容量不随它变。
- **分配时点**（机制）：一行分配量按分配时刻判那份预占的有效区间（ADR-0023 业务时间由提交方给）：早于判断时点答 `RESERVATION_NOT_YET_EFFECTIVE`，晚于有效期答 `RESERVATION_EXPIRED`，与预占口同名同义。不核预占有效期是否覆盖到班次出发（越权风险点 13）。
- **分格与次序**（机制）：构造门（分配行单看不成立答 `INPUT_NOT_ACCEPTED`，不读池）→ 同一版本重放 → 分配已形成 → 班次在册（以上三格不动，排在容量保障之前，理由同票 19）→ 按班次读池并锁池行（读不动答 `LOAD_ASSIGNMENT_UNDECIDED`，装配整笔回滚后交回）→ 指错的行答 `RESERVATION_NOT_ON_SCHEDULE`，列出那几行：指的池不是本班次的池、引用的预占不在那个池上、班次没挂池却带了行，三种并成一格（越权风险点 16）→ 缺行的池答 `CAPACITY_RESERVATION_REQUIRED`，列出那几个池 → 逐行按池身份判 `UNIT_MISMATCH`、尚未生效与过期、`ALLOCATION_EXCEEDED`（带余量、挡下的那一行、池与那份预占）。先答指错再答缺池：指向别的班次的那一行改对了，缺的那个池多半也就有了。全部答 200，只有新形成一版用 201。
- **成员数**（产品策略）：一行可以声明取成员数而不给数量，只许落在件数维的池上——维度由池身份派生，单看载荷就判得出，落在别的维度答 `INPUT_NOT_ACCEPTED`。得法单记一格（`DECLARED` / `MEMBER_COUNT`），不当作声明值存：读的人要分得出这个数是数出来的还是报上来的，变化版按新成员重数。库面 CHECK 钉住成员数只在件数池上。一池只认一行。
- **线格式**（机制）：分配口载荷加 `allocations`（可缺），每行 `pool`、`reservation`、`quantity` 或 `quantityFromMembers`、`unit`、`source`（与预占口同一形）；没有任何越过余量的键，封闭解码下带这类键是坏报文。答复回显这一版的 `allocations`，`须引用预占`带 `poolsWithoutReservation`，`预占不在本班次`带 `allocationsNotOnSchedule`，逐行各格带 `refusedAllocation`、`pool`、`reservation`，`分配超出`另带 `availableQuantity`。

越权风险点（续上文编号）：

13. **分配的保障随预占到期失效**（TF owner）。预占有效期早于班次出发时，到期那一刻已分配的那段随未消耗剩余一并归还池，分配仍在册而不再受保护，没有任何一格提示。去处是票 [demo-chain-gaps/56](../../.scratch/demo-chain-gaps/issues/56-allocation-guarantee-lapses-when-the-reservation-expires-before-departure.md)。
14. **变化与撤回没有入口**（TF owner）。归还机制已就位、真库证过，但生产上只有形成首版一口：一份分配形成之后，它占着的那段只能等预占到期才回来。变化入口接线时须走同一道容量保障判定。去处是票 [demo-chain-gaps/55](../../.scratch/demo-chain-gaps/issues/55-load-assignment-revision-and-withdrawal-entries-are-not-wired.md)。
15. **消耗与分配没有接通**（TF owner；方案 D03-7「仍不接线」）。消耗此刻只从未分配的余量里取：一份全额分配的预占上，依据那份分配的消耗也会撞守恒。消耗接线时要把它改成转换那一条分配关系的量，并在分配关系上记下已消耗的部分。
16. **三种指错并成一格**（TF owner）。池不在本班次、预占不在那个池上、没挂池却带了行，续办同是「改指本班次池上的在册预占（或先预占）」，所以并成 `RESERVATION_NOT_ON_SCHEDULE`；若 owner 要把「预占还没立」与「指到了别的班次」分开，加一格即可，载荷不变。
17. **存量分配不回补**（TF owner）。0031 之前在挂池班次上形成的分配没有分配行，不占任何预占；不替谁补一个分配量。
18. **分配量的来源不回读**（TF owner）。同越权风险点 3：`PREPARATION_DEMAND_SNAPSHOT` 的引用不核准备结果在不在、量对不对；分配量是声明值（越权风险点 2）。
19. **查阅口看不到分配关系**（前端 owner）。池级查阅册只列预占、释放、实际使用三个和，不列已分配；逐份预占的查阅册（票 [demo-chain-gaps/46](../../.scratch/demo-chain-gaps/issues/46-capacity-reservations-have-no-per-reservation-review-registry.md)）落地时应带已分配与分配关系。
