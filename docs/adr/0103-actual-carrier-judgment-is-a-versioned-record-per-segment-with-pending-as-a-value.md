# ADR-0103：实际承运商判断是按实际履约段一份的带版本记录，「待确认」是带原因的判断值而不是缺席；证据来源封闭四格，承运主体身份只引用 `party-commercial`，不铸

Status: Accepted（2026-09-03，用户经 IDP 队列通道 3 授权本会话「有全部权限」自决并向各会话派工。裁决能力边界：读过票 [tf-segment-lifecycle-closure/02](../../.scratch/tf-segment-lifecycle-closure/issues/02-actual-carrier-judgment-model.md) 全文、`transport-fulfillment` `CONTEXT.md` 的 Language「实际承运商」「实际履约段」「履约参与关系」「外部承运轨迹事实」、Rules「履约主体与承运证据」「外部承运轨迹事实」两节、Lifecycles「实际履约段与履约参与关系」、Boundaries 全节，`GLOSSARY.md` 的「实际承运商」条，`internal/transportfulfillment/domain/actual_fulfillment_segment.go` 的 `FulfillmentParticipation` / `ParticipationEntryKind` / `ParticipationEndKind` / `ActualFulfillmentSegment`，[ADR-0096](./0096-a-fulfillment-segment-identity-is-declared-not-derived.md)、[ADR-0097](./0097-segment-evolution-writes-through-narrow-doors-not-a-general-update.md)、[ADR-0102](./0102-external-fact-three-times-are-minted-by-ownership.md)；未重读 `UC-TF-002`/`UC-TF-005` 全文、`offsite_pickup.go` 与 `transport_handover.go` 的全部构造门、`party-commercial` 参与方册的读端口——本记录因此只裁**判断的主体、值域、时间归属、证据来源与身份边界**五件，不裁存储形状细节，不改段与参与关系的任何既有不变量）
Date: 2026-09-03

## Context

`transport-fulfillment` `CONTEXT.md` 把「实际承运商判断」列为本上下文拥有的对象，并用整节写了它的规则：证据不足时保持待确认；后续有效证据形成带业务时间和来源的身份判断，**不追溯覆盖原来的未知期间和判断历史**；渠道账号持有人、渠道服务方、签约服务商、底层承运商与实际承运商必须分别保存、互不推导。

代码里没有这个对象。`FulfillmentParticipation` 与 `ActualFulfillmentSegment` 上都没有承运商字段，`grep -rn "实际承运商" internal/transportfulfillment` 只命中注释里的引语。票 tf-unwired-seven/07 把它明确列为「不在本票，且不是遗漏」：它要的是一个新模型而不是参与关系上的一格——硬塞进段或参与关系就是把两个身份合成一个，而 CONTEXT 恰恰要求它们分别保存。mechanism-executor-triage 的「第四格」（CONTEXT 有语言、代码无形状）记的就是这一族：棘轮与探针在构造上都看不见它，只能先裁形状。

票 02 摆了四问，四问的答案互相牵制，所以一起裁：

**一、主体粒度。** CONTEXT 两句看似指向不同粒度：「在明确实际履约段中接收并运输载运对象的业务参与方」按段说话，「首次有效收寄必须明确关联载运对象、实际承运商、业务发生时间」按对象说话。用场景压一下：一个段里三个对象，A 由承运商收寄扫描进段（扫描指名承运商 X），B、C 由权威交接进段（交接结果只说接收方是「运输方」）。若按对象各判一份，B、C 的承运商从 A 的扫描能不能推出来？能——因为它们在**同一段**，而段按定义就是「共同运输执行与控制责任范围」；CONTEXT 又说「可验证的实际承运责任……发生变化时，结束原载运对象的履约参与关系并形成下一实际履约段」，即**承运责任变了就是另一段**。所以一段只有一个实际承运商（可待确认），按对象各判一份得到的是同一个答案的三份副本，而三份副本会分叉。反过来，若 A 的扫描说 X、B 的回传说 Y、两者却在同一段——那不是「两个对象两个承运商」，是**证据冲突**或**段的成员划错**；前者是判断的一个值（待确认·来源冲突），后者归控制事实的登记方更正（ADR-0096：段的身份由登记方声明），判断不替它改。第二句里的「载运对象」是证据的关联对象，不是判断的主体。

**二、待确认是值还是缺席。** 「不追溯覆盖原来的未知期间」要求未知期间有起止；一个空位没有起止，只有一条记录才有。所以待确认必须是判断的一个版本，段成立那一刻就有第一版。而且待确认不止一种：没有任何合格证据、有证据但互相冲突、有证据且指名了承运方但那个名字在参与方册上没有身份——三种的恢复动作各不相同（等证据 / 人裁 / 去 `party-commercial` 登记），按 [ADR-0029](./0029-retrieval-failure-algebra-is-partitioned-by-recovery-action.md) 的判据它们是三格，不是一格。

**三、证据来源。** CONTEXT 列了四种合格来源（承运商直接收寄扫描、承运商收货凭证、权威运输交接结果、保留原始承运来源的可信渠道回传），并明确把外部承运轨迹事实归入第四种「同格」；另一节逐条列了**不**构成收寄的东西（面单生成、渠道受理、预报成功、订舱接受、舱单建立、电子数据接收、车辆到场）。四种是全部——CONTEXT 说「可以包括」，但本记录把它钉成封闭集：开放集合在代码里就是一个字符串字段，而字符串字段守不住「品牌或单号不能推断承运商」那句硬话。

**四、与 `party-commercial` 的边界。** 承运方作为参与方身份归 PC（参与方册、法人册）。判断要引用一个身份；证据里常常只有一个名字或一个品牌串（外部回传尤其如此）。若本上下文据名字铸身份，就成了第二个参与方册；若因找不到身份而把名字当身份存进判断值，就是 CONTEXT 明禁的「从品牌或单号推断」。两头都不行，中间那条路是：身份未登记本身成为待确认的一个原因，名字作为素材随依据保留，PC 登记之后凭同一份证据形成新版本。

**时间。** [ADR-0102](./0102-external-fact-three-times-are-minted-by-ownership.md) 把外部事实的时间按归属分铸。判断不是外部事实，但它依据外部事实，同一条纪律直接适用：判断的**业务时间**取自依据的来源事实（那是源的），**判断形成时间**由本上下文铸（那是本仓的）。两者分开，「不追溯覆盖未知期间」才量得出来：未知期间是按判断形成时间说的知识史，承运主体自何时起承运是按业务时间说的事实史。业务时间早于段成立时间的证据说的是段成立之前的事——它要么属于前一段，要么与段成立事实矛盾，两种都不是本段承运主体的依据。

## Decision

**一、判断以实际履约段为单位，一段一份判断历史；逐对象的收寄、交接、履约事实是输入不是主体。** 同段内不同对象的证据指向不同承运主体时，形成待确认（来源冲突）并保留全部依据，不为对象分别判断，不挑一个，不由到达先后或来源种类自动裁。段的成员划错由控制事实登记方更正，判断不替它改。

**二、判断是带版本的追加记录，「待确认」是判断值，段成立即有第一版。** 每个版本固定：判断值、业务时间、判断形成时间、依据的来源事实引用。判断值封闭为：已识别（承运主体引用）或待确认，待确认的原因封闭三格——无合格证据、来源冲突、承运主体身份未登记。新版本只追加；已识别之后又来相反证据，形成新的待确认（来源冲突）版本，原版本与原未知期间保留。判断**不是段或参与关系上的一格**，不修改 `ActualFulfillmentSegment` 与 `FulfillmentParticipation`；它是独立的聚合，键是（租户，实际履约段引用）。

**三、判断值里的承运主体分两支：外部参与方引用、自营运营法人引用。** 走哪一支由证据决定——证据是自营执行方的作业事实则为自营法人，证据是外部承运方的收寄、凭证、交接或回传则为外部参与方——**不由运输委托的有无推断**（CONTEXT：不虚构外部供应商，也不因签约而成为实际承运商）。

**四、证据来源封闭四格，记在版本的依据上。** 承运商直接收寄扫描、承运商收货凭证、接收方为承运主体的`已交接`权威运输交接结果、保留原始承运来源的可信渠道回传（外部承运轨迹事实同格）。CONTEXT 逐条排除的那些（面单生成、渠道受理、预报成功、订舱接受、舱单建立、电子数据接收、车辆到场）与运输委托、承运接受、品牌、单号都不是来源。加一种来源先改 CONTEXT 再改封闭集。

**五、时间按归属分铸，业务时间不得早于段成立。** 业务时间取自依据的来源事实（源的），判断形成时间由本上下文铸；业务时间早于段成立时间的证据不作为本段依据。

**六、承运主体身份只引用 `party-commercial`，不铸。** 证据里的名称在参与方册上找不到身份时，形成待确认（承运主体身份未登记），名称作为素材随依据保留；PC 登记之后凭同一份证据形成新版本，不追溯改写未登记期间。`party-commercial` 不因某参与方被判为实际承运商而改变其任何商业角色。

**七、段结束后判断历史封存**，只接受来源事实更正引起的重新派生；重新派生保留原版本，不倒填。

**八、不做的，逐条写明。** 不在段或参与关系上加承运商字段或「当前承运商」指针；不给判断开「改判」口——改判就是新版本；不由运输委托、订舱、承运接受、渠道品牌、单号推断承运主体；不为不可验证的外部内部转包虚构承运商或段（CONTEXT 原句）；不在本记录定存储的列名与索引。

## Alternatives considered

- **按载运对象一份判断。** 否决：段按定义是共同控制责任范围，一段一个承运商；按对象判得到同一答案的多份副本，副本之间的不一致没有任何东西能拦。对象证据是输入。
- **按对象 × 段一份。** 否决：与上一条同理，且键里多出的对象维会让「这段是谁在运」这个问题没有一处能答。
- **把承运商做成段上的一个可空字段（空 = 待确认）。** 否决：空位没有起止，「不追溯覆盖未知期间」无从成立；三种待确认压成一个 NULL，恢复动作丢失；段的写口按 ADR-0097 是三个窄门，加一个「改承运商」门等于开了通用 Update。
- **待确认作为判断缺席（没有记录就是待确认）。** 否决：同上；且「段成立了但还没有判断」与「判断是待确认」在库里同形，读的人分不出是没跑到还是没证据。
- **证据来源开放（字符串标注来源）。** 否决：开放字段守不住「品牌或单号不能推断」那句硬话，新来源静默混入。
- **本上下文按名称铸承运方身份。** 否决：第二个参与方册；身份归 PC 是 CONTEXT-MAP 的边界。
- **判断值里直接存名称串而不引用身份。** 否决：那正是「从品牌或单号推断」；名称只能作素材随依据保留。
- **裁成「留空」（如 ADR-0098 对揽收↔委托连线那样）。** 否决：那一条留空的理由是「建它等于在无租户实证下先定一种采购组织方式」——组织方式是租户的事；而实际承运商判断的形状全部由 CONTEXT 硬句推得出来，没有一格依赖租户取值，机制半边该现在就做。
