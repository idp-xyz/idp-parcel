# ADR-0028: 聚合的重建与构造分属两扇门，重建只校验不重算；聚合携带版本，保存按预期版本写入

Status: Accepted  
Date: 2026-08-11

## Context

`parcel-shipment` 的领域包里，凡是判断的**输入**都有公开构造函数，凡是判断的**产物**都没有。不可重建的有八个：`ShipmentRequest`、`SubmissionVersion`、`AcceptanceDecisionTask`、`AcceptanceDecision`、`AcceptanceBaseline`、`ExpectedCommitment`、`Withdrawal`、`ActiveRejection`。这不是疏漏，是成建制的立场——`AcceptanceDecisionSpec` 刻意不收派生字段，理由写在 `Decide` 上：让调用方传进来，一个谎报的已完成就能换一次接受。

至今这个立场没有代价，因为没有持久化。现在有了：`PBC-02` 要证 Repository 合同，而它要的是一个**带版本的聚合**，唯一能顶的是 `ShipmentRequest`。于是两处同时卡住。

**第一处是重建入口不存在。** 能产出 `ShipmentRequest` 的只有 `SubmitShipmentRequest`，其余全是已有聚合上的状态转移；字段未导出，`internal/parcelshipment/adapters/postgres` 在另一个包里设不了。拿 `SubmitShipmentRequest` 反推也不行——它会重跑提交门禁，还会丢掉 `withdrawal`、`sourceDataVersions` 这些已存事实。

**第二处在端口签名上。** `ShipmentRequest` 不带聚合版本，`ShipmentRequestRepository.Save` 也不收预期版本。框架合同要跑的乐观版本冲突，当前签名根本表达不了。只补重建入口的话，`PBC-02` 会走两步又停。

**看起来有第三条路，但它是陷阱。** [ADR-0005](./0005-source-facts-effective-events-derived-state.md)「由来源事实形成有效事件并派生状态」听起来正是背书重放模型：不存产物，存来源事实，读时重放。**但 `Decide` 是重算而不是恢复**——`accepted`、`manualReview`、`state`、`waitingOn`、`baseline`、`commitment` 全由它从入参算出，`AcceptanceDecisionSpec` 一个都不收。所以重放拿到的是「今天的代码会判成什么」，不是「当时判成了什么」。接单规则一改，已落库的历史就被静默改写，而本产品整套证据姿态禁止这件事。

**难逆转的是这扇门开在哪、以什么强度约束。** 一个能造出任意状态的公开构造器，就是一个绕过全部不变式的口子；而本包的不变式正是接受语言本身。八个类型、两个上下文的 Repository 都会照着第一个的写法来。

## Decision

**重建与构造分属两扇门。** 构造是「此刻发生的事，受规则约束」；重建是「已经发生过、当时已经受过约束的事」。合在一起判就只能二选一：要么持久化做不成，要么不变式可绕过。这与 [ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 按阻断理由分别裁决、[ADR-0026](./0026-persistence-written-for-consumer-proof-precedes-gate-passage.md) 把实现与登记分开裁是同一手法。

**隔离靠导入门禁，不靠注释。** 重建入口所在的包，只允许持久化适配器及其测试导入，由 `internal/architecture` 的导入边界测试强制。注释拦不住下一个人。

**门禁与校验是互补的，不是替代的。** 门禁拦**业务代码断言结论**；校验拦**一行坏数据、或适配器自己的 bug 变成一个看起来合法的聚合**。少一个，另一个都补不上。这条要写死，因为「反正只有适配器能调，这几条校验可以省」是一个迟早会被提出、听起来还很合理的推论。

**重建只校验，不重算。** 它把已判定的产物当**数据**收下，绝不从输入重新推导 `accepted`、`state`、`baseline` 或任何派生字段。这是与 `Decide` 的分界，也是本记录与重放模型的分界。

**重建要返回 `error`。** 它不是「不校验、无 error 的 Restore」。库里读出的东西同样得过一遍不变量——那正是校验拦坏数据的地方。

**跨字段一致性要头一回写成显式命题。** 今天没有任何函数在检查它，一致性是 `Decide` 构造式保证的：`state = 已接受` 配 `decisionFormed = false`、`decision.accepted = true` 配任务未完成、`waitingOn` 有值而决定已形成——这些组合在今天的代码里造不出来，因此也没人写过拦它们的条件。重建入口一开，它们全都造得出来。**这不是把现有校验搬一份，是头一回把「合法状态」写下来。**

**聚合携带版本，`Save` 收预期版本，而推进版本是仓储的事。** 这一条不是取舍，是框架合同规定的：未持久化为 0、插入从 1 起、成功更新严格递增 1，而 `PBC-02` 要跑那份合同。

**状态转移一律不动版本。** 一次保存对应一次推进，而两次转移之间只保存一次；由转移各自加一会让版本跳号，合同当场不成立。聚合只记自己是从哪一版读出来的。转移以值接收者复制整份聚合再返回，版本天然被带下去，不必逐个改。

因此要守的风险不是「忘了带」，而是日后某个转移改成重新构造一个 `ShipmentRequest{...}`——那会把版本悄悄刷回零，随后一次按预期版本的写入会被当成并发冲突失败，或者更糟，覆盖掉别人的写入。由一条遍历全部转移的性质性用例守住「转移一律不变」；「六处都要记得」守不到第七个转移出现那天。同一手法本包已用过：`JudgmentPendingReason.resumePath()` 写成原因的全函数而不是调用点上的常量，理由一字不差。

**`EventBuffer` 暂不加。** `PBC-03` 由应用层在同一个事务里入队即可满足，聚合不必自带缓冲。现在加是推测，而且会把重建面扑大——重建一个带待发事件的聚合是什么意思，没有答案。

**本记录不改 [ADR-0005](./0005-source-facts-effective-events-derived-state.md)。** 它管的是作业事实那一支：来源事实不可变、有效事件由它形成、可见状态由事件派生。接受判断的产物不在那条链上——它是一次**判断**的结论，不是一串事实的投影，重放它会让规则变更追溯改写历史。两者的分界就是「这个东西是被观察到的，还是被判定的」。

## Consequences

- 领域包多一个只对持久化适配器开放的重建面，`internal/architecture` 多一条门禁与它的分类用例。
- **头一回要把「哪些状态组合是合法的」写下来。** 这是本记录里最花时间、也最容易写漏的部分；写漏的方向是让一个业务上不可能的聚合通过校验，而它此后看起来与真的一样。
- `ShipmentRequest` 多一个版本字段，六个状态转移与 `ShipmentRequestRepository.Save` 的签名随之改，波及应用层每个调用点。
- **重建入口是本包唯一一处「相信输入」的地方。** 它此后是审计与评审的固定关注点，任何放宽都要回到本记录。
- 判错的方向是把重建入口做成公开构造器图省事。那样门禁形同虚设，而绕过不变式的调用点不会有任何测试变红——本包的不变式恰恰是构造式保证的，没有断言在守。

## Alternatives considered

- **存来源事实、读时重放，不存产物。** 否决：`Decide` 重算而非恢复，重放得到的是今天的规则会判成什么。接单规则一改，已提交的历史被静默改写，而 `UC-PC-002` 与本产品的证据姿态都要求已提交决定保留原快照。
- **照归档谱系写 `RestoreShipmentRequest`：不校验、无 `error`、全位置参数，约束只写在注释里。** 否决：约束只在注释里等于没有约束，而本仓现在有导入门禁这个更硬的手段。不校验那一半另行否决——见下一条。
- **只上门禁，省掉跨字段校验（「反正只有适配器能调」）。** 否决：两者拦的不是同一件事。门禁拦业务代码断言结论，拦不住一行坏数据或适配器自己的 bug；一个不校一致性的重建入口，即便只有适配器能调，仍然能造出业务上不可能的聚合，而它此后与真的无从分辨。
- **把 `Repository` 接口移进 `domain`，让实现同包因而够得着未导出字段。** 否决：那要求领域包认识持久化，与 [ADR-0025](./0025-cross-context-adapters-live-on-the-consumer-side.md)「适配器落在消费侧、领域不认识外面」相反；且它把口子对整个领域包敞开，比一个受门禁约束的重建面更宽。
- **给每个字段加导出的 setter。** 否决：那等于把聚合摊成一个结构体，中间态可观察，且没有任何一处能对「这一组字段合起来是否成立」作判断。
- **聚合不带版本，靠时间戳或内容比对做并发控制。** 否决：框架合同要的是严格递增的版本；时间戳分辨不出同毫秒内的两次写入，内容比对认不出「改回原值」的丢失更新。
- **等第一个真实并发冲突出现再加版本。** 否决：`PBC-02` 现在就要跑那份合同，而端口签名改动会波及已写的 SQL 与合约测试——晚改比早改贵。
