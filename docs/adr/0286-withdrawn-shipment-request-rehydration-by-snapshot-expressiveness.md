# ADR-0286: 已撤回委托的重建门按快照表达能力开门

Status: Accepted（2026-10-26，票 [docs-consistency/code/36](../../.scratch/docs-consistency/code/36-withdrawn-shipment-requests-cannot-be-read-back-from-the-store.md)。Claude Code 会话在用户「你作为业务和系统专家自决」的授权下代 PS owner 裁定；协调方分诊定了存量口径（已撤回而没带撤回决定的存量行按坏数据响亮拒绝、不推回）与推进写法，对账表、坏数据判据和任务处置的互斥格由作者代决。越权风险点见文末，待 PS owner 复核。）<!-- 索引注记 -->｜**推进** [ADR-0061](./0061-accepted-shipment-request-rehydration-by-snapshot-expressiveness.md) 决定一里`已撤回`那一半：快照补上撤回决定（决定标识、授权引用、请求方、结构化原因、决定时刻）之后，重建门开到`已撤回`，四个状态全开；正文有`已撤回`的对账表与坏数据判据（撤回决定五格缺任一格、边界未越过、带接受或拒绝决定及其产物、任务未停止，以及其余三个状态带着撤回，都是坏数据）。补表达前写下的已撤回行没有撤回决定，按坏数据拒绝、不推回。**接受链**在第一步之前见到`已撤回`即停，答`已决定`、不带决定，不为撤回之后才消费的提交信封占资金｜**读法限定**（不是停用）：决定六「守卫是未加锁的先读后判：读到未撤回之后、占用形成之前撤回成立的窗口，由 PS 申报视图对已撤回的状态过滤（估价读不到已撤回委托，冻结形不成）和票 docs-consistency/code/99（撤回、拒绝、处置与接受链取委托行锁与控制作用域锁次序相反）兜住；不为本票补并发用例。」一句里的「兜住」按 [ADR-0290](./0290-an-acceptance-chain-round-that-finds-the-request-withdrawn-or-rejected-releases-the-occupation-it-formed.md) 的 Context 读——它覆盖估价读之前撤回成立的窗口与锁序，不覆盖估价之后到链提交之前的窗口；后者由 ADR-0290 决定一在形成决定那一步关上。本记录正文不改写，其余内容不变。

Date: 2026-10-26

## Context

[ADR-0061](./0061-accepted-shipment-request-rehydration-by-snapshot-expressiveness.md) 决定一把重建门开到`已接受`，`已拒绝`与`已撤回`继续挡在外面；[ADR-0188](./0188-rejected-shipment-request-rehydration-by-snapshot-expressiveness.md) 把`已拒绝`那一半开了，`已撤回`留在原处：「撤回在快照里还没有表达，撤回口属客户渠道，另立票」。

那张名单只挡住了读，写侧照常落`已撤回`行。于是出了两件事：

- **撤回决定在落库那一刻丢了。** 快照里只有状态列一个数字。`WithdrawByCustomer` 形成的撤回决定（决定标识、授权引用、实际请求方、结构化原因、决定时刻）没有字段可写，也不进决定槽位：撤回不是接受也不是拒绝，PS CONTEXT 明禁二者互相冒充，聚合因此给撤回自带槽位。PS CONTEXT 委托生命周期要求「原提交、版本、判断、撤回决定和补偿关系继续保留」，保留下来的只有一个状态码。
- **读回走不到门。** 凡按来源身份读那份委托的编排都在重建门以 `ErrRehydrationStateNotSupported` 报错：客户重发同一撤回（`AT-PS-068`）读不回原撤回，只能答未决；以 `WITHDRAWN_RESUBMISSION` 关联原委托的新提交（`AT-PS-076`，[ADR-0255](./0255-a-submitted-request-is-regrouped-only-by-withdrawing-it-and-submitting-linked-new-requests.md) 决定一定为决定前重组的唯一路径）在关联指名处报读不到原委托；客户原样重放那份被撤回的提交也读不回。应用层测试用内存仓储，读得回撤回，所以这一格在单元测试里看不出来。领域代数是全的，断在持久化。

撤回口在生产装配下的采信身份仍属实例半边，撤回授权的请求映射也还没有租户取值，所以今天生产库里没有由编排写下的已撤回行；接上撤回口的那一刻起才有。按 [ADR-0030](./0030-rehydration-admits-one-state-at-a-time-by-snapshot-expressiveness.md) 的两步顺序，先补表达再放出门，本记录回答`已撤回`这一格现在开不开。

## Decision

**一、重建门开到四个状态。** 快照的 `withdrawal` 一格补上撤回决定，写入与读回都经领域公开访问器与构造函数；重建面新增一个受限标识 `RehydrateWithdrawalSpec`。`ErrRehydrationStateNotSupported` 因此今天没有状态落入；它留着，是因为 ADR-0030 的两步顺序对日后新增的委托状态仍然成立。

**二、`已撤回`的对账表。** 重建只校验、不重算（[ADR-0028](./0028-aggregate-rehydration-is-a-separate-door-that-validates-without-recomputing.md)）。`validForRehydration` 照下表校验。

| 聚合字段 | `已撤回` | 其余三个状态 |
|---|---|---|
| 撤回决定 | 五格齐全：决定标识、授权引用、请求方、结构化原因、决定时刻 | 一格都不得在场 |
| `decisionFormed` | 真。撤回与接受、拒绝共用这一条决定边界 | 照各自的表 |
| 接受或拒绝决定（含校验明细、依据、复核状态、主动拒绝留痕、决定时刻的任何残片） | 缺席 | 照各自的表 |
| 接受基线、预计承诺、客户资料版本 | 缺席 | 照各自的表 |
| 任务状态 | `已停止`，不在等待 | `已提交`运行中，`已接受`与`已拒绝`已完成 |
| 任务处置记录 | 缺席或`交客户补充`；`拒绝`自己就形成拒绝决定，越过边界之后撤回走不到，是坏数据 | 照各自的表 |
| 处理记录、复核完成度 | 照收 | 照收 |
| 历史版本与任务、关联出处、客户包裹件号 | 与`已提交`同样收、同样校验 | 同左 |

三个时间戳之间刻意不设关系，理由同 `validForRehydration` 头注：撤回决定时刻与提交时刻、版本建立时刻的先后不是已确认的规则。

**三、坏数据判据。** 照 ADR-0061 决定三：门已经开到`已撤回`，下列形状是这一行立不起来，走 `ErrInvalidRehydratedShipmentRequest`，不折成「本期不支持」。

1. 状态是`已撤回`而撤回决定整个缺席。
2. 撤回决定五格缺任一格。适配器侧决定标识、授权、请求方、原因任一为空，包着同一个哨兵上抛；决定时刻缺席由领域侧拒绝。
3. 没越过决定边界。
4. 决定槽位上有任何东西，或带接受基线、预计承诺、客户资料版本。
5. 任务不是`已停止`，或仍在等待；任务处置记录为`拒绝`。
6. 其余三个状态带着撤回决定，整份或半截都是。按「五格齐全」判在场会把只剩一格的残片当成没有撤回放过去，所以这一条看有没有任何一格。

**四、存量：缺撤回决定的已撤回行按坏数据拒绝，不推回，不补默认值。** 补表达之前写下的已撤回行只有状态列，没有撤回决定。不从别处推回：授权引用、请求方与原因是当时的事实，没有第二个来源可推；补默认值等于替客户说了一句没说过的话，而 UC-PS-005 明禁默认任何撤回授权。首发前只有演示租户，靠 `--reset` 重灌。种子里没有会撤回委托的步骤，不受影响。

**五、写入侧单独置上决定边界。** `AcceptanceDecision()` 对已撤回委托报告缺席，所以写入不能再拿「决定在场」推 `decisionFormed`；撤回在场时同样置上，读回才过得了「已撤回越过边界」这一条。

**六、接受链见到`已撤回`即停。** 链在第一步之前读到已撤回的委托，三步都不走，答`已决定`、状态`已撤回`、不带决定。门开之前这一格靠读错误挡着，门开之后必须自己拦，否则撤回之后才消费的「委托已提交」信封会为已撤回的委托占下资金；落点与理由见 Consequences。守卫是未加锁的先读后判：读到未撤回之后、占用形成之前撤回成立的窗口，由 PS 申报视图对已撤回的状态过滤（估价读不到已撤回委托，冻结形不成）和票 docs-consistency/code/99（撤回、拒绝、处置与接受链取委托行锁与控制作用域锁次序相反）兜住；不为本票补并发用例。

**七、文档处理照 ADR-0030 → ADR-0061 → ADR-0188 的先例写成「推进」。** 本记录推进 ADR-0061 决定一里`已撤回`那一半；ADR-0061 的 Status 注记与 Links、ADR-0188 的 Status 注记与 Links 各加前向指针，ADR-0030 的 Links 加一条推进指针，各份正文与其余各条不变。不在 ADR-0061 后面追加复核记录来开门，理由同 ADR-0188 决定四。

## Consequences

- `ShipmentRequestRepository.FindBySourceIdentity` 对已撤回行交回带撤回决定的聚合。各编排本来就有的分支从此走得到：撤回口重发同一撤回与换一个来源身份再撤，都答`决定已形成`并带原撤回和原补偿关联（`AT-PS-068`）；提交口对已撤回原委托的 `WITHDRAWN_RESUBMISSION` 关联成立，方向与终态不符的关联答 `LINK_INELIGIBLE`（`AT-PS-076`）；客户原样重放被撤回的提交答`既有结果`。ADR-0255 Consequences 里「已撤回委托今天在真库上读不回」的缺口由此补齐，那条路径不变。
- 其余按来源身份读委托的编排撞上已撤回委托时，走领域转移的既有闸门（撤回即越过决定边界，后到的决定只能读取既有结果），不再先在读回处失败。
- **接受链必须自己拦已撤回的委托（决定六）。** 「委托已提交」信封在撤回成立之后才被消费时（异步投递，窗口真实存在），链读到的委托此前读不回、停在读错误上；门开了之后它读得回，而信封指名的仍是委托的当前版本，三步会照常走：财务控制为一份已撤回的委托占下资金，而撤回成立时已按原关联放过各版占用，这笔新占用没有任何路径再放；形成决定那一步还会耗掉一个决定标识。所以链在第一步之前见到`已撤回`就停，答`已决定`、状态`已撤回`、不带决定——与形成决定那一步撞上既有终局时的同一格，消费门按处理完毕入账，不需要新的结果格（ADR-0025）。
- 委托查阅读面（`ShipmentRequestViews`）不经重建门，直读投影列与快照文档，早就如实交代`已撤回`的状态与任务停止；它不带撤回决定摘要，这一格不在本记录，见越权风险点。
- 快照是 jsonb 文档，撤回决定作为文档字段进快照，库面没有要加的列、约束或索引，不占迁移号。
- 重建面新增一个受限标识 `RehydrateWithdrawalSpec`，登记在重建面门禁的受限名单里。
- 门开到四个状态之后，`TestEveryNamedShipmentRequestStateIsAdmittedByTheDoor` 让日后新增的委托状态在没有快照表达时变红。

## Alternatives considered

- **缺撤回决定的存量行从状态列推回、或补一个默认撤回。** 否决：违反 ADR-0028 的只校验不重算；撤回的授权、请求方与原因没有第二个来源，补出来的是编造的事实。
- **把撤回决定放进决定槽位，复用主动拒绝留痕的快照格。** 否决：PS CONTEXT 明禁撤回与拒绝互相冒充，聚合已经给撤回自带槽位；塞进决定槽位会让下游把一次客户取消读成运营拒绝。
- **给撤回决定加库面投影列。** 否决：没有读口按撤回字段查，投影列要与快照同笔写，是一处新的两处各说各话；迁移 0026 的客户包裹件号同一先例，只在快照里查。
- **只开门，撤回决定下一期补。** 否决：先开门再补字段，正是 ADR-0030 要修的「宣称四个、其实一个」；重建出的聚合缺撤回，而它此后看起来与真的一样。
- **缺撤回决定仍报 `ErrRehydrationStateNotSupported`。** 否决：违反 ADR-0029 分格。门已经开到这个状态，缺的是这一行的数据，恢复动作是查库里那一行，不是等门开。
- **退役 `ErrRehydrationStateNotSupported`。** 本记录不做：它今天无状态落入，但 ADR-0030 的两步顺序对新增状态仍然成立，是否删它由 PS owner 在有第五个状态之前定。

## 越权风险点

1. **缺撤回决定的存量行响亮拒绝。** 协调方分诊定的口径。若首发前有演示租户之外的已撤回行，读它们的编排都会答读不回，要 `--reset` 重灌或人工补；本记录不提供补登路径，因为没有第二个来源可补。
2. **任务处置与撤回的互斥格。** 处置`拒绝`自己形成拒绝决定，已撤回而处置为`拒绝`判为坏数据；处置`交客户补充`的任务可以在等待补充时被撤回，照收。这两条来自领域转移的现状（`WithdrawByCustomer` 要求决定边界未越过），PS owner 若日后允许别的撤回时机，对账表要改。
3. **查阅详情不带撤回决定。** `ShipmentRequestDetailRecord` 与 HTTP 详情体只有接受或拒绝决定摘要，没有撤回摘要。快照现在有这一格，补上它是读面与接口契约的改动，不在本票。
4. **取消包裹与终局结果两只编排没有委托生命周期闸门。** `CancelParcelHandler` 与 `FormParcelFinalHandler` 只核成员属当前版本，不核委托是否`已接受`；已撤回（同样已拒绝、已提交）委托的包裹走到它们时不会被拦在读回处，门开了之后由它们自己答。今天生产装配里取消的授权角色未配置、没有责任结果会为从未接受的包裹送达，所以是潜在的而不是现行的；它不是撤回特有的缺口（已拒绝自 ADR-0188 起同样），不在本记录，留给 PS owner 定是否立票。
5. **人工复核完成与授权处置先问授权再核状态。** 对已撤回委托答`任务已完结`的那一格，在授权未配置或不可用时到不了，客户或运营拿到的是未决而不是`任务已完结`。次序是这两只编排原有的，与撤回无关。
6. **`ErrRehydrationStateNotSupported` 成了无人产出的哨兵。** 是否退役由 PS owner 在出现第五个委托状态之前定。
