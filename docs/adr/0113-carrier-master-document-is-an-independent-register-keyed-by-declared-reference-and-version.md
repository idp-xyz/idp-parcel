# ADR-0113: 总单在 `transport-fulfillment` 立独立登记册——身份是登记方声明的（租户，总单引用，版本），与运输舱单、外部承运凭证分表；撤销、替代与关联重述都是回指前版的新版本，替代显式指名替代者，关联逐条挂在版本上；登记口沿 `parcel-api` 端点不开 CLI，读面在查阅页加一格

Status: Accepted
Date: 2026-09-07

## Context

[CONTEXT-MAP](../domain/CONTEXT-MAP.md) 把「承运总单、运输舱单及外部承运凭证的身份和版本」判给 `transport-fulfillment`；[GLOSSARY](../domain/GLOSSARY.md)「总单」词条要求「关联必须明确且可追溯」；[TF CONTEXT](../domain/transport-fulfillment/CONTEXT.md) 写着「总单、运输舱单和外部承运凭证具有不同业务身份……不能合并为一张可覆盖运输单」「总单、舱单或外部凭证撤销不能删除已经发生的装载、交接和运输事实；替代凭证必须建立显式替代关系」。而票 [tf-carrier-master-document-register/01](../../.scratch/tf-carrier-master-document-register/issues/01-carrier-master-document-register-does-not-exist.md) 量到：领域、端口、迁移里一个总单类型都没有，两处读面头注写着「无处可登」，[ADR-0111](./0111-shipment-and-mawb-level-billing-units-are-evaluation-subjects-in-parcel-pricing-and-settlement-allocates.md) 的主单级评价停在「身份来源缺」。

票面列了三种形状（独立登记册 / 与运输舱单同表按种类分格 / 首发只登身份与版本不登关联与替代）与三条开工前置（「总单」与「承运总单」是否同一词条、三词条身份边界怎么落成键、替代与关联怎么记）。前置的答已随 `/domain-modeling` 落进 TF CONTEXT「总单」词条与 GLOSSARY「总单」别名行：三处写法是同一个词，本上下文内用「总单」。本记录定形状。

## Decision

**一、独立登记册（票面形状 1），与运输舱单、外部承运凭证各自分表。** 总单自立一张表，主键（租户，总单引用，版本）。不与运输舱单同表按种类分格：两者的版本语义不同——舱单的版本是成员快照随草稿→提交→外部回执演进，总单的版本是适用关系与关联的追加——同一张表上装两套版本规则就得让一半列对另一半永远为空，「同表不等于同身份」在读法上守不住，硬句「不能合并为一张可覆盖运输单」正是拦这一格。不并进外部承运凭证：凭证的标识对象封闭集是运输委托、订舱、班次、载运对象、实际履约段，GLOSSARY 写明「外部承运凭证不统一等于……总单」，把总单塞进去等于扩一个封闭集去装一件被它明确排除的东西。运输舱单的册本记录不立，它仍是「无处可登」。

**二、身份由登记方声明，本上下文不铸、不解析（ADR-0096 同一判据）。** 总单引用由登记方给出——它通常就是签发方分配的总单号，但号码格式、号段与校验规则属实例半边，本上下文不解析、不校验、不在仓内写任何真实总单号。签发方引用 `party-commercial` 已登记的参与方身份，本上下文不为承运方铸身份（与凭证的分配方、实际承运商判断的判断值同一条纪律）。主运输凭证范围是登记方声明的范围引用，不从 `network-routing` 的线路或计划履约段推导（ADR-0004：不用计划推事实，也不用事实反推身份）。运输委托与订舱引用可缺（CONTEXT「总单可以引用运输委托或订舱关系」是「可以」）。

**三、版本链只插不改，新版本封闭三格：撤销、替代、关联重述。** 首版没有回指也没有改变时间；此后每一版回指前版、带改变的业务时间，原版本一字不动，「当前版」按回指派生（没有任何版本回指它），表上没有 current 列——与迁移 `0012`（凭证）、ADR-0112 / 0117 同形。撤销与替代改变适用关系：撤销之后适用关系结束；替代必须指名替代它的那份总单，且不能是自己。**关联重述**是第三格：总单仍有效时关联的对象集变了，形成新版本回指前版，适用状态照旧有效。要这一格的理由是不要它的代价：没有它，改一条关联就只能撤销整份总单再登一份新的——而现实里那份主运单号没变，等于为同一份真实凭证铸第二个身份，正是 GLOSSARY「关联必须明确且可追溯」要防的那种不可追溯。已撤销或已替代的总单不再接受任何新版本：领域门拒，编排答「已不适用」并带回撞上的当前版。替代者只作引用不设外键、不要求已登记：签发方先作废旧单再签新单的先后不受本上下文控制，登记顺序也不该受它约束；非自指与非空由 CHECK 守。

**四、关联逐条成子表挂在版本上，种类封闭三格。** 子表键（租户，总单引用，版本，关联种类，关联引用），复合外键指向版本行。种类取 GLOSSARY「集运单元、包裹或运输履约范围」三项：`CONSOLIDATION_UNIT`（`node-operations` 身份）、`PARCEL`（`parcel-shipment` 身份）、`FULFILLMENT_SEGMENT`（本上下文的实际履约段——「运输履约范围」在本上下文里就是这个词）。不对被关联对象设外键：三种对象分属三本册，且关联是历史事实——对象后来被拆并、段后来关闭，都不改「它曾列入这一版总单」。首版允许零关联（总单先签、集运单元后列是常态）。关联不证明装载、交接或运输（CONTEXT 硬句），列面与领域都不从关联派生任何控制事实。

**五、登记口沿 `parcel-api` 端点，不开 `parcel-tf-register` CLI。** TF 今天的登记全走 `parcel-api` 端点与 dispatch 家族（凭证、有效时间规则、四个 admin 写面都如此），单为总单开一个 CLI 会让 TF 有两种登记入口而理由只是「别的上下文有」。按 ADR-0101 决定八自裁：这本册结构简单（六件事一行一版、关联逐条）、低频（运营配置员登一份主运单或改它的关联），是逐字段表单候选，不走模板导入与草稿。两个端点：首版登记 `/transport-fulfillment-carrier-master-document-registrations`，后续版本 `/transport-fulfillment-carrier-master-document-revisions`——撤销、替代、关联重述是同一条命令的三个取值，续办同一个（去看当前版是谁、什么时候改的），不各立端点；改变口不叫 `-corrections`，理由同凭证：改变的是适用关系或关联，不是更正一个判断。写准入不另立形，同挂字面量 `UnconfiguredIntake{}`（ADR-0085）。

**六、读面接进查阅页刻意留空的那一格。** `ReviewCatalogueRead` 补 `ListCarrierMasterDocuments`，查阅端点册名封闭集加 `carrier-master-document`，一行一版本、版本链在册面完整可见；空册照 ADR-0077 决定四答空列表——从今天起那一区的空态是「登记册为空」不再是「无处可登」，头注与页面文案随之改口。管理台那一区拆成两格：总单接册；运输舱单保留「无登记册」的如实呈现，不与总单共用一份空态措辞。

## Consequences

- ADR-0111 主单级评价的「身份来源缺」有了落点：PP 快照里的承运总单引用从此可以指向本册的（总单引用，版本）；PP 不改，票 [price-card-shape-gaps/03](../../.scratch/price-card-shape-gaps/issues/03-shipment-and-mawb-level-billing-units-have-no-evaluation-subject.md) 主单级那一半可解阻。PP 引用哪一版（首版还是当前版）由 PP 定，本记录不替它定。
- 代价：TF 迁移 `0017`（主表 + 关联子表）；领域一个聚合两种引用类型三格状态；端口一本登记册；两个端点、一个读面方法、装配表一行入参、装配测试探针两条；`MECHANISM-INVENTORY.md` 的迁移份数、端口与端点计数都变。
- 「总单号是外部标识」（GLOSSARY「外部标识」）在本册以「总单引用 + 签发方」承载，不另立外部标识行；若日后要把总单号与产品侧引用分成两列，是新一版迁移，不是改本记录。
- 不在本记录内：运输舱单登记册；总单与运输舱单、装载分配、实际装载之间的差异比较（CONTEXT「短装、多装或错装差异」）；`customs-compliance` 对总单引用的消费形状；PP 主单级评价怎么读本册。

## 越权风险点

本记录由 owner 授权自决而成，下列各点是自决时拿不准或触及跨上下文归属的，逐条单列供复核；不认可的走 supersede，不改写本记录。

1. **「关联重述」作为第三种版本**：CONTEXT 原文只点名撤销与替代，这一格是本记录增写并同笔落进 CONTEXT 规则节与生命周期节。若 owner 认为关联变化该另立「更正」词条或该走撤销再登，那两处 CONTEXT 句子与迁移 CHECK 一并改。
2. **「运输履约范围」落成实际履约段**：GLOSSARY 那三个字也可能读作运输委托或订舱所覆盖的范围；本记录选实际履约段，因为它是本上下文自己拥有的范围身份，且总单对委托 / 订舱的引用已另有两列。
3. **主运输凭证范围是不透明引用**：不结构化为起讫地或航班——那会碰 `network-routing` 的线路语言与 `PAR-NET-*` 实例参数。若 owner 要结构化，是加列不是改键。
4. **签发方引用 `party-commercial` 身份但不校验其在册**：与凭证分配方同形，登记时不查参与方册；未登记的签发方是「登了一个查不到的引用」，不是拒绝。这一格与实际承运商判断的「承运主体身份未登记」处置不同，属有意为之——登记册不是判断。
5. **替代者不要求已登记**：见决定三末句。若 owner 要求替代者必在册，加一道编排读回即可，不动表。
