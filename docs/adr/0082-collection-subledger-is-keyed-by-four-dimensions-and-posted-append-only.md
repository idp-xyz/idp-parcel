# ADR-0082: 代收分户账按四维立键、余额只由追加式记账派生，回汇批次形成即冻结

Status: Accepted
Date: 2026-08-28

## Context

[admin-remainder-mechanism-batch/04](../../.scratch/admin-remainder-mechanism-batch/issues/04-collection-remittance-context-bootstrap.md) 把 `collection-remittance` 从零建起：此前它只有 [CONTEXT-MAP](../domain/CONTEXT-MAP.md) 一节所有权占位，无 `CONTEXT.md`、无 `internal/` 包、无迁移。准入依据是本批的 COD 形态裁定（基线 `PA-CR-01`）——「承运或渠道代收货款并周期回汇」是目标客户群的常规商业形态，机制半边现在就做，实例值一律留空。

从零建一个上下文时，有两类取舍在写下第一张表的那一刻就难以逆转，其余的都能后补：

- **分户账的粒度。** 余额按键派生，键定了余额就定了。事后按更细的维拆分，要重演全部记账历史并把已经形成的汇付批次重新归属；而合并反过来同样不成立——两本账合成一本之后，「哪一笔是谁的」在余额上再也读不出来。
- **不可覆盖的形状。** 记账能不能改写、回汇批次能不能重开，决定了「账面对不对」是一个结构性质还是一件要靠对账去查的事。这两者一旦按可改写建起来，后面所有的守恒论证都得改成「我们查过了」。

`settlement-accounting` 是最近的邻居也是最容易被合并进去的一个：它已经有分户账、余额、核销与对账的整套词。CONTEXT-MAP 的两句所有权划分（结算**不拥有**代收货款本金、渠道在途代收款、待清分款、应付客户款或代收汇付结果；代收与清分不拥有 COD 服务费或经营口径收入）要求两边不共享表、以引用交接，因此本记录不重议归属，只裁 CR 这一侧的形状。

## Decision

**一、分户账按（货主客户，责任法人，币种，代收渠道）四维立键，四维齐备才构成一本账。** 依据是 CONTEXT-MAP 的所有权句「代收本金在客户、责任法人、币种和代收渠道之间的隔离与对账关系」——四维就是那句话里的隔离维，少任何一维都会让两笔本该分开的钱记进同一个余额。租户不在键上：它是入参，本上下文不做接入认证。

**二、币种在键上，因此一本账内不发生换算。** 本上下文没有汇率也没有折算入口。跨币种关系由两本分别成立的分户账加外部换算依据表达。汇率口径由 `party-commercial` 的商业价格政策声明（[CONTEXT-MAP](../domain/CONTEXT-MAP.md) 的 `parcel-pricing ↔ 外部数值来源` 一条），不由本上下文发明第二套。

**三、余额不落字段，只由追加式记账派生。** `subledger_posting` 只有 INSERT，没有 UPDATE 也没有 DELETE；各资金位置余额是它的求和结果。写错走反向记账冲正，原记账原样留在账上。

这一条买的是**分配守恒成为结构性质而不是对账结论**：非外部位置余额之和恒等于自外部来源入账之和。它由记账的形状交付——每一笔同时从来源位置扣、往去向位置加，金额不在过程中产生或消失。留一列可改写的余额就等于给绕过记账的写入路径开门，而那扇门开着的时候，账对得上与对不上在读的人眼里没有区别。

**四、资金位置封闭六值，外部来源只在来源侧，去向侧没有账外位置。** 本金只能凭一笔已接受的代收事实进账；`已汇付`是账内的终局位置而不是出口。于是全账总额恒等于入账之和，守恒在一条求和上核得完。

**五、四条依据门做进结构（迁移 CHECK 与领域构造门各一份）**：入账必须凭代收事实；`应付客户`**不得**凭代收事实到达；进入`已汇付`必须凭回汇批次；进入`短款`或`溢款`必须凭差异事项。第二条是「未实际收到的代收款不得进入可付客户余额」这句禁令的落点——一层来源事实说的是「有人报了这笔钱」，说不出「它是谁的」，归属要另有一笔凭代收指令的清分记账。

**六、分户账键不是记账的输入，由依据推出。** 记账命令里没有键：代收事实经指令解出键、代收指令自带键、回汇批次自带键、差异事项经指令解出键、原记账自带键。让调用方传键的写法在库里看不出错——一笔记错账的行与记对的行逐列合法，而余额已经被改了。

**七、回汇批次形成即冻结分户账键、币种与归集截点；状态单向推进，没有取消格也没有重开格。** 改变归集范围走新批次。归集截点由登记方给出，不据周期推算：回汇周期属实例半边。

**八、批次成员就是「引用该批次的汇付记账」，不另立第二份成员清单。** 两份成员口径必然在某一次部分失败后彼此不一致，而对得上与对不上在读面上长着同一张脸。成员只增不改的界划在「交出汇付主张」那一刻——之后再收成员，主张交出去之后金额还会变。

**九、汇付主张不等于真实付款。** 本上下文只到主张为止；付款执行、清算与到账由外部支付与银行系统拥有，本切片不建支付通道集成。

## Consequences

- **入账无法冲正。** 去向侧没有账外位置，反向那一笔落不下来。这是决定四的直接代价，本记录明认下来：来源侧记错走「追加更正事实并关联原事实」，而那笔钱在账面上如何退出，本切片**不猜**——它取决于真实的渠道退款与银行退回形态，属实例半边。有真实参数时按新记录裁，不在这里预留一个猜出来的位置。
- **余额每次按键扫全量记账。** 没有物化余额，读一本账的余额就是读它的全部历史。索引 `subledger_posting_by_subledger` 是为它建的；这本账的记账量由代收笔数决定，量级成为问题时的处置是加派生视图并让它由记账重算，不是回头给账加一列可写余额。
- **四维粒度改动要重演历史。** 这正是把它写进 ADR 的原因：它不是一个可以「先这样、不行再改」的选择。
- **批次错了只能冲正其汇付记账再形成新批次。** 没有取消格意味着一个形成得过早的批次会永久留在册上；留着的那一行是如实的——它确实被形成过，而已依它落账的汇付记账也确实存在。
- **`settlement-accounting` 与本上下文各自有一本「分户账」，同名不同物。** 前者是运营结算余额，后者是受托保管账；两者不得合并展示为一个「客户余额」。这条要求读面在措辞上分开，本记录只裁数据形状，页面口径由读面那一侧承担。
- **COD 服务费与协议抵扣不在本上下文内与本金净额。** 抵扣要通过明确记账依据表达，且抵扣后的组成仍逐笔可追溯。

## Alternatives considered

- **分户账按（客户，币种）两维立键，责任法人与代收渠道降为记账上的属性列。** 否决：CONTEXT-MAP 的隔离句点名了四维；降为属性之后同一客户在两个责任法人下的本金落进同一个余额，而「这本账现在有多少钱」正是要按责任法人回答的问题。事后拆分要重演全部历史——这恰是决定一想避免的那件事。
- **分户账带一列物化余额，记账与它同笔更新。** 否决：同一件事两个口径，两者不一致时谁也不知道该信哪一个；且余额一旦可写，就必然出现「只改余额不记账」的紧急修复路径。
- **复式记账（每笔两行借贷、和为零）。** 否决：本上下文只有一类受托资产账，位置迁移用「从—到」一行表达得完整；引入借贷科目会带来一整套与本上下文业务词不对应的名词，而它买回来的守恒，一行式已经用「同时扣与加」给出了。
- **回汇批次另立成员表。** 否决：见决定八——第二份成员口径从出生起就要与第一份对账。
- **回汇批次带取消格或重开格。** 否决：同一行前后给出两种答案，而已依它落账的汇付记账不会跟着回退。要改归集范围就形成新批次，这在册面上也更诚实。
- **把代收本金并入 `settlement-accounting` 的结算账户与运营余额。** 否决：CONTEXT-MAP 明句——结算不拥有代收本金、渠道在途、待清分、应付客户款与汇付结果，代收本金也不是经营口径物流收入或普通运营结算余额。并进去之后，「运营企业自己的钱」与「替客户保管的钱」在同一个余额上，而这两者的可动用性完全不同。
- **代收事实不分来源层级，只登一个「已收金额」。** 否决：GLOSSARY「代收货款」的硬句要求四层分别保存且不得互相推导。合成一格之后，「渠道说收到了」与「钱真的到了」在账上没有区别，而决定五的第二条门就无从立起。
