# ADR-0019: 产品自带面向租户的作业与治理界面，跨租户运维后台不属于产品

Status: Accepted  
Date: 2026-08-10

## Context

「前端放哪」已在三个会话里各被完整推导过一遍，[ADR-0018](./0018-product-clients-share-release-boundary-under-apps.md) 据此固定了落位与发布边界。但「放哪」预设了「要建」，而**「产品是否自带界面」从未被决定过**。

这处空白是可查的：`docs/product` 下搜「界面」「门户」「前端」，唯一命中是 [`PAR-INT-01`](../product/PILOT-PARAMETER-REGISTER.md) 的「API、标准文件或门户」——那是**租户面向它自己客户**的既有接入渠道，不是本仓要建的东西。没有任何权威文档承诺过产品自带作业界面，也没有任何一份排除它。

缺这一层的后果有实据：ADR-0018 的备选清单里没有「只交付 API、界面由租户自建」。那不是起草疏漏——**「不建」不会成为「放哪」的备选**。一个决定立错了层，漏掉的备选连成为备选的资格都没有。同理，该记录把「桌面治理界面与工位手持扫描是两个应用」当作事实写入，也是因为在落位这一层，端的数量必须先假定。

**这一层现在可以定。** 按 [ADR-0016](./0016-product-delivery-and-tenant-pilot-as-parallel-tracks.md) 的两半划分，「产品是否自带界面」是**机制半边**——它问的是产品卖的是什么，属产品定位；「界面有哪些屏、给哪个角色、长什么样」才是**实例半边**。此前以「没有租户、没有确定的角色界面需求」为由推迟，是把实例半边的缺失当成了机制半边的阻塞，而那正是 ADR-0016 要解除的死锁。

判据不另造，用[开发主线](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md)已有的两条：能力范围判据「必须能指出一类真实存在的承运或渠道商业模式需要它，且该模式在目标客户群里是常规形态」，以及产品就绪定义中的「可以演示、可以进入商务洽谈」。

## Decision

**产品自带面向租户的作业与治理界面。** 至少包含两类：租户自己管理人员使用的管理面，以及一线作业人员使用的作业面。它们直接操作本产品拥有的领域对象，属于产品的一部分。

**作业面同时覆盖手持与桌面两种设备。** 做成一个响应式应用还是两个独立应用，属实现取舍——便宜且可逆，不在本记录固定，留给第一个端落地时按实际交互决定。

**租户的锚点货主客户界面不属于产品。** 他们走 `PAR-INT-01` 登记的租户**已有**渠道。这一条承 ADR-0018 不变，因为它最容易与上一条混淆，混了就会得出「我们要做个客户门户」的错误结论。

**开发方的跨租户运维后台不属于本产品，且本记录不放行它。** 它不卖给租户，因此不是产品；更要紧的是它必须跨越 [ADR-0003](./0003-group-tenant-legal-entity-customer-account.md) 确立的**运营集团租户即最高数据隔离边界**。跨租户读取的授权模型、可见范围与审计留痕是一项独立决定，必须单独作出；在此之前不得建立任何跨租户读取路径，也不得因为「顺手」而与产品内的端一同建立。

**落位与发布边界沿用 ADR-0018 的结论**：产品内的端落在顶层 `apps/`，每端一个子目录；端之间的共享物落在顶层 `packages/`；与后端同仓、同版本发布；`cmd/` 与 `internal/` 的现有边界不变；两个目录都等第一个真实端落地时才建，不预建空壳。

## Consequences

- ADR-0018 由本记录取代。它的**结论**有效并在此重述，但其前提此前未经决定；理由现在由本记录承担，不再依赖「桌面与手持是两个应用」这一推断——端为复数已由产品定位直接确立。
- 产品就绪的「可以演示」不再需要一个仓外的演示物来满足：产品自带的作业面本身就是可演示的。这消除了 ADR-0018 遗留的一处张力——按其判据，达到产品就绪所需的演示物反而被排除在仓外。
- **跨租户运维后台成为一项显式未决。** 它挡住的是最容易顺手做出来的东西：一个「先加个能看所有租户的列表页」的改动，会在没有任何决定的情况下穿透 ADR-0003 的隔离边界。
- 每新增一个端仍要按「服务谁」判断归属，现在多一条硬性排除：**凡需要跨租户可见性的，一律不属于产品内的端。**
- 多语言 CI、发布节奏被后端锁住、仓库不再只需一套 Go 工具链等代价，沿用 ADR-0018 已记录的部分，本记录不重复。
- 本记录不承诺任何端的实现时间，也不解除 [ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 的闸门。业务 HTTP 端点当前一个都没有，端在闸门开之前无接口可调。

## Alternatives considered

- **只交付后端与 API，界面由租户或集成商自建。** 否决：产品定位已确认自带管理面与作业面。此外这条并不省掉界面工作——产品就绪要求「可以演示」，而拿 API 向物流企业买家演示工位扫描说服力接近零；选它仍要做一个界面，只是那个界面不算产品的一部分，于是既付了成本又失去与后端的版本锁定。
- **混合：只自带作业面，管理面只给 API。** 否决：管理面同样直接操作本产品拥有的对象，把它推给租户自建等于要求他们把本产品的领域模型在前端重实现一遍——那不是集成，是复制。
- **把开发方运维后台一并纳入产品内的端。** 否决：它不卖给租户，且要跨越租户隔离边界。与产品内的端同仓同版本，会让一次产品发布同时改变跨租户访问面，而这两件事的评审门槛完全不同。
- **继续推迟，只记录触发条件。** 否决：这正是 ADR-0016 要解除的死锁。推迟的代价已经显现——同一问题在三个会话里各被完整推导一遍；再推一次，答案会以「第一个被写出来的演示界面落在仓外」的形式被默认掉，而不是被决定。
- **维持 ADR-0018 不动，只补一条备选。** 否决：「只交付 API」不是一种放法，而是一种产品范围。把它塞进落位决定的备选并写一句否决理由，等于记下一个没有人做过的决定，比漏掉它更糟。
- **本记录一并决定跨租户运维后台。** 否决：它牵动 ADR-0003 的隔离边界、授权模型与审计要求，与「产品是否自带界面」不是同一个决定。合并会让一个已经清楚的结论替一个尚未讨论的问题背书。
