# ADR-0022: HTTP 状态码只回答「有没有形成答案」，业务判别一律进响应体

Status: Accepted  
Date: 2026-08-11

## Context

[开发主线的机制半边现状](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#机制半边现状)把「HTTP 面只有 `/healthz` 与 `/version`，没有任何业务端点」列为四项横切缺口之一，并注明**四项里只有这一项现在没有闸门挡着**——[ADR-0017](./0017-admission-gates-judged-by-blocking-cause.md) 说它「在应用层成型后自然解除」，而应用层已成型到十例。

但动手补它，立刻要回答一组在任何现行文档里都没有答案的问题：应用结果怎么变成 HTTP 响应、幂等键从哪来、`!found` 那六处技术错误怎么映射、离线客户端凭什么判断本地队列里那条能不能出队。

**这组问题的核心是一个数量错配。** `UC-PS-001` 一个用例的提交编排就有七种应用结果——`已提交`、`已有结果`、`接入冲突`、`输入未受理`、`非本产品生产归属`、`生产归属未决`、`准入暂停`。HTTP 拿不出七个语义匹配的码，任何映射都必须合并其中至少两种。而合并正是本仓反复付过代价的失误：[ADR-0019](./0019-product-ships-tenant-facing-operator-clients.md) 与 [ADR-0020](./0020-tenant-admin-client-in-product-workers-are-processes.md) 记的两次推断错误同源，`UC-PS-001` 反复强调暂停「不是第四种权威身份，不是客户业务拒绝」，`UC-PS-002` 要求未获授权、未登记与不允许「分成三种答案而不合成一格」。十例编排各有粗细不同的封闭枚举，[机制半边现状](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#横切缺口不属任何单一切片)已经指出这种粗细差异「是各自领域模型深浅不同的合理结果」，抹平它就抹掉了各上下文语言的差别。

**[ADR-0021](./0021-frontline-operations-client-is-part-of-the-product.md) 让这件事必须现在定。** 它写明一线作业客户端的离线与弱网容忍「会反过来约束业务端点的形状——幂等、冲突合并语义、本地队列与重放」，且「离线是设计不出来就补不上的那类要求，事后加代价极高」。离线客户端最基本的动作是判断队首那条能不能出队，而这个判断今天没有依据。

难逆转的不是任何一个状态码，是**客户端据以行动的契约**。产品内两个端都会按它写重试、去重与错误呈现；改它要同时改端，而端与后端按 ADR-0021 同版本发布。

## Decision

**HTTP 状态码只回答「服务端有没有形成答案」，不回答「答案是什么」。** 这条镜像应用层自己的 `(Result, error)` 签名：返回 `Result` 就是形成了答案，返回 `error` 就是没形成。传输层不比应用层多知道什么，也不再自行归类。

三类，客户端据以行动：

| 类别 | 含义 | 离线客户端动作 |
|---|---|---|
| 2xx | 应用层形成了业务答案 | 出队，按 `outcome` 呈现给操作员 |
| 4xx | 调用方的错，重发不会改变结果 | 出队，交给人，不自动重发 |
| 5xx | 服务端没能形成答案 | 留在队里，按退避重发 |

**业务判别一律进响应体的 `outcome` 字段。** 它的取值与该编排的应用结果枚举一一对应，用同一套稳定字符串，传输层不合并、不新造、不改名。`outcome` 字段的存在本身表示应用层答过了：**4xx 与 5xx 响应不得携带该字段**。

**2xx 内部只区分有没有新建对象**：新建了用 `201`，其余已形成的答案用 `200`。这不是业务判别的后门——它区分的是 HTTP 本来就在区分的东西，且给离线客户端一个不必解析响应体就能确认建单成立的信号。

**不新造幂等键。** 来源身份与载荷摘要已经是领域层拥有的幂等机制，重放与接入冲突由它判定。禁止引入 `Idempotency-Key` 之类的传输层键：多一套键就会有两套键不一致的时候，而那时没有规则说谁算数。

**`!found` 一律映射为对应上下文的`统一不可见结果`，用 `404`。** 不得区分「不存在」与「属于别的租户或客户账户」——端口以完整来源身份为键，否定结果本来就不携带这个差别，在传输层把它分开等于凭空造出一条跨租户存在性泄露通道。它是 4xx 而非 5xx：指名一份看不见的对象是调用方的错，让离线客户端无限重试它只会把队列堵死。

**接入认证与规范化摘要是两项显式未决，本记录不决定，并禁止在它们决定前落地任何默认实现。** 来源信封整组按 `UC-PS-001` 的输入语义契约「客户不可声明」，其权威来源是接入适配器的认证结果；采信客户自报的租户号会穿透 [ADR-0003](./0003-group-tenant-legal-entity-customer-account.md) 的最高数据隔离边界。真实接入渠道的认证方式属 `PAR-INT-01` 待提供的实例参数。载荷摘要须覆盖规范化业务内容，而 `parcel-shipment` 侧的规范化形状尚未实现（[ADR-0014](./0014-versioned-canonicalization-shape-for-content-digest.md) 只约束了摘要形状要带版本号，没有给出这一处的形状）。两项未决期间，业务端点可以存在并由测试替身驱动，但不进 `cmd/parcel-api` 的装配。

## Consequences

- **每个业务端点必须先有一个封闭的 `outcome` 词汇表。** 加一种应用结果就要同时加一个取值；传输层没有「其他」这一格可用，也不允许有——那一格会成为下一次合成一格的入口。
- **客户端不能只看状态码。** 这是刻意付的代价：七种答案里有五种要给操作员看不同的东西、给不同的下一步动作，只看状态码本来也不够。
- **通用中间件与重试库对 2xx 一视同仁。** `接入冲突`不再触发它们对 `409` 的特殊处理，重复检测也不能靠代理层。凡是需要按业务答案分流的地方都得读响应体，这笔成本记在本决定这一边。
- **监控按 `outcome` 维度统计，不按状态码。** `UC-PS-001` 的可观测性一节本来就要求分别统计九类结果且「原因维度引用稳定规则或判断标识，不使用自由文本聚合」；按状态码聚合会把其中六类并成一条曲线。
- **[机制半边现状](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#横切缺口不属任何单一切片)记录的六处 `!found` 出口，接 HTTP 时由适配器映射为 `404`，不得原样 500。** 其中撤回重放路径那一处旁边没有就地注释，是六处里最容易漏的。
- **本记录不解除任何闸门，也不承诺任何端点被实现。** Bento 持久化闸门原样有效，业务端点后面今天没有真实存储。
- 新增一项判断成本：每加一个端点都要先分清哪些失败是调用方的错（4xx）、哪些是没形成答案（5xx）。判错的方向是把依赖不可用报成 4xx，那会让离线客户端把一条本该重试的请求丢掉。

## Alternatives considered

- **按语义把每种结果映射到最贴近的状态码（`409` 冲突、`422` 输入未受理、`503` 暂停等）。** 否决：七种答案对不上七个码，`非本产品生产归属`与`生产归属未决`只能挤进同一个，而它们回答的是不同问题。`503` 更糟——它会让通用重试库自动重发`准入暂停`，而 `UC-PS-001` 明写「原因解除、指标恢复或健康检查通过都不自动恢复；一致性核对、在途盘点和明确恢复决定完成前仍保持 `PAUSED`」。让传输层默认值去推翻一条治理规则，是这份记录最想挡住的事。
- **只给`接入冲突`一个 `409`，其余进响应体。** 否决：它确实最贴合，但一旦开口，下一个端点就会问「那`输入未受理`为什么不是 `422`」，规则退化成逐例裁量，一年后没人说得清依据。规则的价值在于不留裁量口。
- **全部用 `200`，新建也不用 `201`。** 否决：更整齐，但丢掉的信息是真的——离线客户端确认建单成立是最高频的判断，让它必须解析响应体才能知道，等于为整齐付一笔天天付的成本。且 `201` 区分的不是业务判别。
- **引入 `Idempotency-Key` 请求头。** 否决：`UC-PS-001` 明写「客户参考号不能未经确认直接充当全局幂等键」，而来源身份加载荷摘要这套机制由领域层拥有并已实现重放与冲突判定。再加一个传输层键会出现两套键，两套键分歧时没有规则说谁算数。
- **换 gRPC 或其他传输以规避状态码的表达力问题。** 否决：产品内两个端是浏览器与手持设备，且这是把一个映射问题换成一个技术栈问题——换完仍要决定错误码怎么分类。
- **不立记录，逐端点在适配器注释里定。** 否决：这正是红线「单一权威」要消除的重复，且两个客户端会按它写重试逻辑——散在十个适配器里的口径，端那边只能靠试出来。
- **等第一个端真正开工时再定。** 否决：ADR-0021 已判定离线是设计不出来就补不上的那类要求。等端开工时端点已经写好，那时改的是已有契约，不是空白。
