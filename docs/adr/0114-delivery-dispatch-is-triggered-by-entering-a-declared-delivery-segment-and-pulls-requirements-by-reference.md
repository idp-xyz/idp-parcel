# ADR-0114: 末端派送任务由「对象凭`已交接`进入登记方声明为末端派送的段」触发——段服务动作在段成立时由控制事实登记方声明、不推导；触发是异步一拍的跨上下文内部执行器，派送要求三条输入按 ADR-0025 消费侧拉引用与时间窗、不拉地址本体、缺席即待形成

Status: Accepted
Date: 2026-09-07

## Context

[UC-TF-006](../application/transport-fulfillment/UC-TF-006-PERFORM-DELIVERY-AND-CAPTURE-POD.md) 的触发行原写「尾程实际履约段到达派送范围」，而它自己的首句写「从明确载运对象已经由尾程履约方取得运输控制……开始」。票 [tf-segment-lifecycle-closure/09](../../.scratch/tf-segment-lifecycle-closure/issues/09-arrival-triggers-dispatch-task.md) 的裁决（MCP-3，2026-09-04，owner 授权）钉了四件：① 「到达」= 对象凭`已交接`进入尾程实际履约段，不是班次到达——移动事实挂班次，从班次到达经装载分配推「哪些对象到了」正撞 CONTEXT 硬句「装载分配不证明节点已经完成物理装载，也不证明运输控制已经转移」；「尾程」怎么认由登记方声明，同 [ADR-0096](./0096-a-fulfillment-segment-identity-is-declared-not-derived.md)；② 不立「派送范围」词，不读 `network-routing` 服务区域；③ 触发不在移动事实编排也不在交接编排同事务——七件里地点、时间窗、条件三样都不在 TF，同事务会让一条控制事实登记编排去读三个外部上下文；④ 七件各有所有者，TF 只拥有对象集。裁决留给建模的两格：「派送段」的声明怎么落成词条，与三条外部输入怎么到 TF 手里（消费侧拉 vs 随信封携带）。本记录定这两格与它们的形状。

## Decision

**一、「段服务动作」是段上由登记方声明的一格，封闭三值，成立时固定、之后不改。** 控制事实登记（交接与收寄）各收一个可选的段服务动作声明；段由首个对象的控制事实成立时随之固定为场外揽收、节点间运输或末端派送之一。声明为末端派送的段就是派送段。未声明是一种答案（ADR-0096 决定三同一格）：段照常成立、加入、结束，只是不触发依赖服务动作的派生。后续对象加入既有段时给出与已固定值矛盾的声明是领域正当拒绝（`SEGMENT_SERVICE_ACTION_CONFLICT`），不留续办引用——重试一万次都一样；给出一致的或不给都照常加入。不从计划段位置推「尾程」：那是 `network-routing` 的知识，走它就把本记录挂到 `PAR-NET-14` 实例半边上。不给段加「更正服务动作」的门：声明错了是登记方另立新段的事，段登记册没有通用 Update（ADR-0097）。

**二、触发是一个异步一拍的内部执行器，输入是「对象凭`已交接`进入派送段」这一事实，输出是调既有 `OpenDispatchTask`（签名不动）。** 它读回段（必须是派送段、对象必须是在场参与——凭链尾判，被替代或已离场的参与不触发），按派送要求取齐七件，调 `OpenDispatchTask`。控制事实先如实落库，任务在下一拍形成；形成失败重跑本拍，不回滚交接。一拍一对象一任务：任务的对象集是该对象自己——同一派送段里的对象各有目的地，把它们并成一任务的合并规则是租户的运营政策（实例半边），本记录不代拟。任务引用由执行器按（段，对象，入场依据）确定性铸出，重跑同一拍撞`已在册`而不重建。执行器的生产入口（谁按拍调它）随第一条派送要求缝的实施票立，形同收编执行器「生产入口随第一家真源的拉取节拍票立」的先例；本记录只落执行器与它的缝。

**三、派送要求三条输入按 ADR-0025 由 TF 消费侧适配器拉，拉的是引用与时间窗，不拉地址本体。** 三条各一个 TF 侧端口：收件地点引用（`parcel-shipment`）、计划履约段时间窗口（`network-routing`）、交付条件引用（`party-commercial`）。选拉不选携带的判据在触发源：ADR-0075 让地址随判断请求携带是因为那里有一个外部请求在过界；这里触发源在 TF 内部（对象进段），没有任何请求可以顺路带东西，PS / NR / PC 也不知道对象何时进段。ADR-0075 要防的是「不拥有地址的上下文长期持有明文地址」——本记录守的是同一条：拉到的是**地点引用**，落进任务的 `Place` 也是引用（`AttemptPlaceReference` 本就是引用），地址本体留在 `parcel-shipment`，需要地址的一线作业端按引用向所有者取。任一端口未接线时执行器答`未决`并点名哪条缝（`DELIVERY_PLACE_SOURCE_NOT_WIRED` 等），不造替身、不填默认；接了线而所有者答「没有」时任务保持待形成（`REQUIREMENT_MISSING`），也不填默认。

**四、三条缝各立票，票 09 转父票。** 缝的落法（PS 那条读哪个读面、NR 那条对没有计划段的对象怎么答、PC 那条条件引用指哪一版）各在其票里定，与所有者对齐；本记录只钉端口形状与缺席答法。

## Consequences

- UC-TF-006 触发行随本记录改口为「明确载运对象凭`已交接`进入登记方声明为末端派送的实际履约段」（已同笔）。
- 代价：TF 迁移 `0018`（段表加 `service_action`）；`RegisterTransportHandoverCommand` / `RegisterOffsitePickupCommand` 各加一个可选声明字段；`SegmentEntryRefusal` 加一格；`ports` 加三条派送要求端口；`application` 加一个触发执行器与其结果代数。既有 `RecordMovementFact` / `OpenDispatchTask` / `FindByKeyAndVersion` 签名不动。
- 不在本记录内：三条缝的适配器（票 12–14）；执行器的生产入口与拍频；多对象合并成一任务的政策；「派送范围」一词（不立）。

## Alternatives considered

- **在移动事实（`ARRIVAL`）落库后触发。** 否决：班次到达推不出对象到达，推导链要经装载分配，那是执行意图不是事实（ADR-0004；裁决①）。
- **在交接登记编排同事务触发。** 否决：七件里三件不在 TF，同事务要读三个外部上下文；票 06 把结束参与放进同事务的判据「输入全在 TF」在这里恰好不成立（裁决③）。
- **PS / NR / PC 把派送要求随信封推过界。** 否决：它们不知道对象何时进派送段，推等于让三个上下文各自维护一份「TF 什么时候需要」的知识；且 ADR-0075 的判据是「有请求在过界就随请求带」，这里没有那个请求。
- **拉全地址落进任务。** 否决：TF 不拥有地址，任务表里落地址本体就是 ADR-0075 要防的第二份地址存储。
- **一拍把同段所有在场对象并成一任务。** 否决：同段对象目的地各异，合并规则是运营政策，没人声明过；先一对象一任务，合并作后续显式规则。

## 越权风险点

1. **服务动作三格的词**（场外揽收 / 节点间运输 / 末端派送）取自 CONTEXT 首段列的运输动作；若 owner 认为「节点间运输」还该细分（干线 / 支线）或该另有一格，改封闭集与 CHECK。
2. **收寄登记也收声明**：裁决只说「交接登记时声明」；本记录让两条控制事实来源都能声明，因为段由两者任一成立，只让一条能声明会让收寄成立的段永远无法成为派送段——但这也意味着一次多对象揽收成立的段可被声明为派送段，owner 可复核是否合理。
3. **一对象一任务**：见决定二；若 owner 认为合并该是机制半边的默认，改执行器的分组一处。
4. **地点引用的粒度**（收件地址引用还是目的地节点引用）留给票 12 与 PS owner 定；本记录只钉「引用不是地址本体」。
