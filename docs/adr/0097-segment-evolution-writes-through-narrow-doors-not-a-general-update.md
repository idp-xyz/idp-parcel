# ADR-0097: 段成立之后按动作分窄写口，不开通用 Update

Status: Accepted
Date: 2026-09-02

## Context

[tf-unwired-seven/01](../../.scratch/tf-unwired-seven/issues/01-actual-fulfillment-segment-registry.md) 落了实际履约段登记册，端口上**只有首登与读回**，没有任何更新方法。当时的理由写在端口注释里：段成立之后的演进（对象加入、逐对象离场、关段）属票 02 与票 07 的编排，在还没有调用方时先猜一个写入形状会猜错。

现在要接那两票，形状必须定下来。CONTEXT 对这个聚合的持久化提了三条硬约束：

> 已经成立的实际履约段及履约参与关系不能被取消、删除或回写为未发生。

> 共享实际履约段中的每个载运对象分别成立、结束和更正，不能由整段结果覆盖成员差异。

> 已结束的参与也不重开：再次进入是新的段。（领域 `join` 注释，对应 UC-TF-002 一致性）

领域层已经把这三条守住了——`ActualFulfillmentSegment` 是值类型，类型上没有任何取消或回退方法。**问题在持久化那一侧：端口开成什么形状，决定了这三条是"靠调用方守"还是"根本表达不出来"。**

## Decision

**一、按动作开三个窄口，不开 `Save(segment)` 那样的整段重写。**

- `Join` —— 只 INSERT 一条参与关系；撞主键即「该对象已在段内」，是业务答案不是错误（ADR-0031）。
- `EndParticipation` —— 只 UPDATE 离场三列，且 `WHERE ended_at IS NULL`。
- `CloseSegment` —— 只 UPDATE 关闭两列，且 `WHERE closed = false`。

**二、这三条的价值不在"窄"，在于被禁的那些操作在这个口上根本表达不出来。**

逐条对上面三句 CONTEXT：

- **回写为未发生**：`Join` 只插不改，`EndParticipation` 的 `WHERE` 让离场无法被清空或改写，`CloseSegment` 同理。**没有一条路径能把已发生的写回未发生**——不是不该，是没有那个入参。
- **整段结果覆盖成员差异**：三个口没有一个接受"整段成员集合"。想覆盖别人的成员差异，得逐个对象调 `EndParticipation`，而每一次都被它自己的 `WHERE` 挡在已离场的那一条之外。
- **已结束的参与不重开**：`Join` 的主键冲突已经答了。

而整段重写口做不到这些。`Save(segment)` 能表达任何状态**包括倒退**，挡住倒退的只有"调用方碰巧传了一个向前演进过的聚合"——那是纪律不是结构。本仓的两级处方明写：能把区别做进结构就做进结构。

**三、不设乐观并发版本列。** 三个口各自的 `WHERE` 已经承担了并发下的正确性：两个对象同时加入互不冲突（主键分开）；同一对象被两次离场，第二次因 `ended_at IS NULL` 不匹配而落空并如实答「已离场」；关段同理。**加一个版本列会把这三处已经精确的冲突判定，换成一个"有人动过"的粗判**，而那个粗判还得让调用方重试一次它本来不需要重试的事。

**四、写口交回封闭的结果取值，不交回受影响行数。** 行数是实现细节，`0` 在这三个口上各有不同含义（已在段内 / 已离场 / 已关闭），压成一个数字就要调用方去猜。

**五、`ErrSegmentStillActive` 仍不下沉到库。** 关段前必须无在场参与——那是跨行条件，`CloseSegment` 的 `WHERE` 守不住它。它留在领域（转换门与重建门各守一次），**且编排必须先读回整段、走领域的 `CloseSegment` 再落库**，不得直接调写口关段。这一条是本 ADR 里唯一一条靠纪律而非结构的约束，如实标出。

## Consequences

- 票 02 与票 07 的编排形状随之确定：读回整段 → 走领域转换门 → 调对应的窄写口。领域仍是判断的唯一所在，写口只落已经判完的那一步。
- **端口变宽了但语义变窄了**，这是有意的：三个方法比一个 `Save` 多，而它们各自能做的事比 `Save` 少得多。方法数不是复杂度的度量。
- 与本上下文既有的 `*Store` / `*Registry`（`FindByKey` + `Save`）形状不同。**那些聚合是一次成型的**（一次交接判断、一次有效交付、一份委托），首登即终态，更正走新版本新行；段不是——它在生命期里逐对象演进。**形状不同是因为聚合不同，不是本上下文出现了两套风格。**
- 代价是加一个新的演进动作就要加一个口。这正是想要的：新动作应当被迫说清它改哪几列、在什么前置下改，而不是搭一次 `Save` 的便车。

## Alternatives considered

- **`Save(record)` 整段重写。** 否决，理由见决定二。它还有一处更隐蔽的坏：整段重写要求调用方持有全部成员，于是每次加入一个对象都要先读回整段——而在共享段承载多对象时，两个并发加入会各自基于一份旧快照重写，**后写的那个静默丢掉先写的成员**，且两次写入都"成功"。
- **事件溯源（参与关系表只追加，离场写第二行）。** 否决：它确实让"回写为未发生"更加不可表达，但代价是每次读回都要折叠事件流，而领域侧 `FulfillmentParticipation` 是**状态**不是事件序列——重建门得先把事件折成状态，那一步就是第二个口径的温床。当前的窄口已经守住了同一条不变量，不必为此改变聚合的形状。
- **在参与关系表上加 `UPDATE` 触发器禁止清空 `ended_at`。** 否决：与 `ErrSegmentStillActive` 不下沉同一条理由——把一条不变量分裂到领域与触发器两处，领域改一次判据、触发器那份会悄悄漂移。窄口已经在应用侧把它做进了结构。
- **给段加乐观锁版本列。** 否决，理由见决定三。

## 裁决方的能力边界

本 ADR 由 MCP-3 受用户明确授权自决，与 [ADR-0096](0096-a-fulfillment-segment-identity-is-declared-not-derived.md) 同批。读过：CONTEXT 全文、段与参与关系的领域实现及其全部转换门、票 01 落地的迁移与适配器（本人所写）、本上下文既有十二组端口的形状。**没有读**：`node-operations` 与 `parcel-shipment` 侧未来对段写口的调用预期（今天没有调用方）。

因此本 ADR 裁的是**写口的形状与它必须表达不出什么**。它**没有裁**每个动作各自的编排细节（谁调、失败怎么续办），那属票 02 与票 07，届时按 UC 走。决定五那条靠纪律的约束已如实标出，不掩饰成结构性保证。
