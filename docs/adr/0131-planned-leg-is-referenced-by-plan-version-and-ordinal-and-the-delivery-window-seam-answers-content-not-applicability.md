# ADR-0131: 计划履约段对外以「路由计划版本 + 段序位」引用、没有独立段身份；派送时间窗口缝按该引用取**引用所钉那一版**的段内容，计划适用性四态不折进窗口答案；没有计划段的对象答`要求缺失`，`network-routing` 不给兜底窗口

Status: Accepted
Date: 2026-09-09

## Context

票 [tf-segment-lifecycle-closure/13](../../.scratch/tf-segment-lifecycle-closure/issues/13-delivery-window-seam-network-routing.md) 是 ADR-0114 决定三拆出的三条派送要求缝之二：末端派送任务七件里的**时间窗**归 `network-routing`，TF 侧端口 `ports.DeliveryWindowSource` 已随触发执行器立住（按载运对象问，答窗口或`要求缺失`），适配器停在 NR owner 的三问上——按什么键取、取哪一版计划、没有计划段的对象怎么答。本记录以 NR owner 口径答这三问（用户 2026-09-09 经 IDP 队列通道 1 授权代裁，越权处单列）。

对照物上的事实：

- NR 领域里**计划履约段没有自己的身份**。`PlannedLeg` 是 `InitialRoutePlan` 有序段链里的一个值（起点、终点、责任方、`PlannedTimeWindow`、是否外部不透明），由 `FormInitialRoutePlan` 的「段链必须连续且至少一段」保证顺序与连续；计划本体不可变，`PlanApplicability` 另立一份记录——代码自注原句「同一份计划的『说了什么』与『现在还算不算数』是两个问题，改后者不得动前者」。
- NR 计划里**没有服务动作一格**。哪条段是「派送段」，ADR-0114 决定一明说由控制事实登记方声明、不从计划段位置推。
- TF 履约参与关系上的 `PlannedSegmentReference` 是登记方声明的不透明必填串，可缺席（待路由产品此刻没有计划段）；CONTEXT 硬句「任何关联都不得用实际事实覆盖原计划」。触发执行器 `TriggerDeliveryDispatchHandler` 在问缝之前已经手握该对象的当前参与，`participation.PlannedSegment()` 就在手边。
- NR 现有读面没有一个按计划版本交回段内容：两个判断口按完整判断键取单行（TF 不持有那把键——它引用的是包裹身份，不是委托 × 接受基线 × 声明包裹 × 服务目的），`RoutePlanCatalogueRead` 只上检索列面、明写不从 jsonb 抠字段；`PlanApplicabilityStore.FindByPlan` 已按计划版本取行，说明「计划版本」本就是 NR 对外可用的键。改路成的新计划本体不在初始路由判断行里，在复核判断行的 `new_plan` 列。
- NR CONTEXT 三句管住了「哪一版」：「改路只能改变尚未执行的剩余旅程。已经执行的计划前缀、实际事实和原计划依据永久保留；包裹运输途中时，新计划从下一个重新取得有效控制权的节点生效」；「已失效或已被替代的计划不得原地恢复为当前有效」；「明确允许待路由但接受后仍无可行候选时保持无当前有效路由，不建立空路由、默认路由或占位计划」。

用候选语言走过的三个场景：

1. **改路替代了原计划后对象进派送段。** 包裹在节点 B 被改路，v2 替代 v1，v2 的段链从 B 之后的下一个可控节点起算。对象随后凭`已交接`进入一个派送段，登记方在参与关系上声明了它执行的计划段。若声明指 v2 的尾段，窗口就是 v2 那段的；若登记方拿的是旧指令、声明指 v1 的尾段，窗口缝仍交 v1 那段的内容——对象实际走了一条与当前有效计划不一致的段，这是**路由偏离**，NR 有自己的判断口说它，不借窗口缝的「没有窗口」说。两种情形下任务的工作范围都来自登记方声明的那一段。
2. **待路由产品没有计划段就实际揽收、进段。** 参与关系上 `PlannedSegment` 缺席。NR 这一侧根本没有一版计划可指，也不得为它造一个窗口——`PlannedTimeWindow` 必须带 `WindowBasisReference`（「窗口不带依据就复算不了」），一个不来自任何计划版本的窗口在 NR 里没有出处。答`要求缺失`，任务待形成；运营要给显式窗口走票 07 的 admin 写面「建派送任务」。
3. **同一委托多包裹不同拍进段。** 「路由以包裹为计划单位……委托只能汇总成员判断」，每个包裹一版自己的计划、一条自己的参与关系、一个自己的 `PlannedSegment`；ADR-0114 决定二一拍一对象一任务。每拍各按自己的引用取窗口，不存在委托级窗口，也不存在「同段其他对象的窗口顶上」。

## Decision

**一、计划履约段对外以「路由计划版本标识 + 段在段链中的序位（自首段起计）」引用；NR 不另铸段身份。窗口按这个引用取，不按对象取。** 版本不可变、段链连续由构造门保证，「版本 + 序位」已经是完整且稳定的身份，再铸一个段标识只是给同一样东西第二个名字。按对象取要 NR 回答「这个对象的派送段是哪条」——计划里没有服务动作，ADR-0114 决定一禁止从段位置推「尾程」；而对象此刻在执行哪条计划段，本来就是 TF 参与关系上登记方声明的事实，不是 NR 的判断。因此 TF 的 `PlannedSegmentReference` 就是这个复合引用的不透明载体：TF 只存不解读；引用的拼写由 NR 领域里一个值类型一处定义（往返 `String`/解析，暂名 `PlannedLegReference`），路由指令与登记方只搬运。NR 为此开一个**窄读口**：（租户，计划履约段引用）→（该段的计划时间窗口，是否找到）。读的是内容——把计划本体按判断口的装载纪律重建后取那一段，无论该版本躺在初始路由判断行的 `plan` 列还是复核判断行的 `new_plan` 列；租户作用域经判断行承担（ADR-0003，与 `RoutePlanCatalogueRead` 的联查同理）。TF 端口 `DeliveryWindowSource.LoadDeliveryWindow` 随票 13 改收计划履约段引用（TF 地盘内的拓宽，走三步法）。

**二、取的是引用所钉的那一版——即参与关系成立时登记方关联的版本；计划适用性（当前有效 / 已被替代 / 已失效 / 已结束）不折进窗口答案，四态一律交回该版本的段内容、答 `RESOLVED`。** 理由三条。其一，段序位跨版本没有对应：改路的新版本段链从下一个可控节点起算，v1 的第 n 段与 v2 的第 n 段说的不是同一段路，拿「当时当前有效」的版本去解一个钉在 v1 上的序位是把两版计划的内容拼在一起。其二，对象凭`已交接`进了派送段，这一段就在执行中；CONTEXT 说改路「只能改变尚未执行的剩余旅程」、新计划「从下一个重新取得有效控制权的节点生效」，此后任何适用性变化说的都是剩余旅程，说不到这一段——这一段的窗口只有一版存在过。其三，「任何关联都不得用实际事实覆盖原计划」的反面同样成立：不得用后来的计划覆盖已登记的关联。至于「这一版还算不算数」，NR 有无当前有效路由与路由偏离两个口专门回答，各有各的消费方；把「已失效」读成「没有窗口」会让一个关于整条剩余旅程的判断伪装成一件缺失的输入，把「已被替代」读成「照用新版本」会让任务窗口取决于这一拍什么时候跑。窗口进任务只作工作范围（ADR-0004），任务形成后就是一份抄件，改约是「新尝试不是新任务」——形成那一刻取哪一版，引用已经替它答了。

**三、参与关系上没有计划履约段引用的对象，适配器不问 NR，直接答 `RequirementMissing`；引用指向的版本或段在本租户下不存在，同样答 `RequirementMissing`。NR 不对无计划对象给「兜底窗口」。** 兜底窗口就是 CONTEXT 禁止的「占位计划」换了个名字，且在 NR 里造不出来（窗口必带形成依据）。「没有」是所有者的业务答案不是错误（`ports.RequirementResolution` 的自注），任务保持待形成、不填默认，与 ADR-0114 决定三同一格。悬空引用也答「没有」而不是「读不到」：`UNAVAILABLE` 在执行器那里是「原样重跑本拍就可能过」，一条指错的引用重跑一万次也不会长出那一段来；它该显示为 `REQUIREMENT_MISSING / DELIVERY_WINDOW`，由人去核参与关系上的声明。

## Consequences

- `network-routing`：领域加计划履约段引用值类型（版本 + 序位，唯一拼写）；`ports` 加窄读口；postgres 适配器按引用重建计划取段，覆盖 `plan` 与 `new_plan` 两处；不加 HTTP 端点（消费方是 TF 进程内适配器）。落票 [nr-route-evidence-views/03](../../.scratch/nr-route-evidence-views/issues/03-planned-leg-window-read-face-by-reference.md)，票 13 以它为阻塞边。NR CONTEXT「路由形成与选择」加一条规则，GLOSSARY「路由计划」词条加一行（已同笔）。
- `transport-fulfillment`：`DeliveryWindowSource.LoadDeliveryWindow` 改收计划履约段引用；适配器落 `internal/transportfulfillment/adapters/networkrouting/`，只翻译不判断，翻译是全函数：引用缺席 → `MISSING`（不出 TF）；NR 答未找到 → `MISSING`；NR 答找到 → `RESOLVED` 带窗口两端；读失败 → error。适用性四态在这条缝上是常函数，适配器**不读**适用性表——不是留 `default`，是本记录裁定四态对窗口答案无差别。执行器把 `participation.PlannedSegment()` 交给端口，缺席那一格由适配器答（执行器不改判断逻辑）。
- 不在本记录内：计划履约段引用怎样随路由指令到达登记方手里（`network-routing` 拥有路由指令，指令「必须关联来源路由计划版本」，携带段序位是它的自然延伸，但指令的载体与现场流程是实例半边）；集运单元作为载运对象进派送段（与票 12 同一边界，只管包裹）；票 07 admin 写面给显式窗口的路；任何真实时间窗取值（`PAR-NET-14`）。

## Alternatives considered

- **按对象取，由 NR 在当前有效计划里找「派送段」。** 否决：NR 计划没有服务动作一格；从段位置推「尾程」是 ADR-0114 决定一明禁的推导；对象在执行哪条段是 TF 登记方声明的事实，NR 代答等于用计划伪装实际执行。
- **取当时当前有效的那一版。** 否决：段序位跨版本不对应；改路只改剩余旅程、对正在执行的这一段无话可说；任务窗口会取决于这一拍什么时候跑。
- **已失效 / 已结束的版本答 `MISSING`。** 否决：把整条剩余旅程的适用性判断折成一件缺失的输入；对象已在派送段里却形不成任务、也说不出诚实的理由；NR 对适用性另有专门的口。
- **NR 为每条计划履约段铸独立标识。** 否决：段是计划内容里的值不是实体，版本 + 序位已经完整；第二个名字只增加一处要对齐的地方。
- **对无计划对象给兜底窗口。** 否决：即占位计划；且 NR 造不出没有形成依据的窗口。
- **第二分量用「起点节点 → 终点节点」而不是序位。** 未采：节点对可读性好，但一条路径原则上可以回访同一节点，序位在任何段链上都无歧义；见越权风险点。

## 越权风险点

1. **适用性四态对窗口答案是常函数**（决定二）。owner 若认为`已失效`或`已结束`的版本不该再交窗口，改的是 TF 适配器里一条分支加本记录决定二一句；NR 侧窄读口不必动（它交内容，加不加适用性是消费方的事）。
2. **悬空引用答 `MISSING`**（决定三）。owner 若要把「引用指错」与「所有者说没有」分格，要拓宽 TF 的 `RequirementResolution` 封闭集——那是 TF 的决定，本记录只指出两格今天同答。
3. **第二分量选段序位而非节点对**（决定一）。两者都完整；选序位是为无歧义，代价是人读引用时看不出走的是哪两个节点。
4. **引用怎样到登记方手里**未裁。路由指令携带段引用属自然延伸，但指令载体（分拣码 / 标签 / 现场识别）与登记方录入流程是 NO / TF 现场半边，本记录没有替它们定。
5. **本记录由通道 5 代裁**，读过 NR CONTEXT 全文、TF CONTEXT 相关词条、ADR-0114 / 0004 / 0025、`initial_route_plan.go` / `plan_applicability.go` / `reroute.go` / `route_plan_read.go` / `delivery_requirement.go` / `trigger_delivery_dispatch.go`，没读 UC-TF-006 全文与 NR 复核编排 `reassess_route.go`——若那里对「改路后旧段窗口」另有措辞，以 CONTEXT 硬句为准、以本记录为落法。
