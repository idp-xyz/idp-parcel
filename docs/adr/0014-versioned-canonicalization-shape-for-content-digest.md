# ADR-0014: 为内容摘要的规范化形状引入版本号

Status: Accepted  
Date: 2026-08-07  
Amended by: [开发主线的产品就绪里程碑与能力范围判据](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md)（限定下文 Alternatives considered 中否决「按行业形态先把三族与分段进位的结构定死」时所用的「在结构层写死未确认内容」这一条理由：该理由对自营系统成立，对面向市场的产品不成立。该替代仍不能取代本记录的 Decision——版本号与建哪些族是两个独立问题。Decision 与 Consequences 不变，本记录正文不改写）

## Context

`internal/parcelpricing/domain/fingerprint.go` 的 `canonicalPricingPlan` 与评价侧的各规范化文档都是封闭结构体，逐字段列出构成，**规范化本身没有版本号**。每引入一个结构概念，所有方案与评价的内容摘要都会改变；而[小包计价上下文](../domain/parcel-pricing/CONTEXT.md)规定「版本引用相同但内容摘要不同，视为版本内容冲突，不得继续重放或静默替换」。两者相乘的后果是：任何一次结构加宽都会让已保存的摘要失配，历史评价回放一律报冲突。

[计价规则模型最终设计](../design/pp-pricing-rule-model-final-design.md)据此要求「模型与规范化形状一次定死」，当时这是对的，而且零成本——仓库尚无持久化层，不存在已保存的方案或评价，摘要每次运行重算。

之后首发范围变了。[参数登记册](../product/PILOT-PARAMETER-REGISTER.md)的 `PAR-NET-16` 已确认供应商比价择优进入首发，判据里的「权威价卡」不再是手上那一张，而是候选集合。候选集合按行业实际形态需要三个价表族并存——首重加续重、计费重乘单价、重量段阶梯——而现有 `RateTableFamily` 只有 `WEIGHT_ZONE` 一个取值，`RateEntry` 只能表达重量段阶梯，`canonicalPricingPlan` 的 `RateTable` 字段还是单个内嵌结构而非集合。同一渠道内按重量分段进位是第二处缺口，`canonicalWeightPolicyDocument` 目前只有一组进位模式与进位单位。两处都改规范化结构，不是加枚举取值。

关键在于**这两处新形状的确切构成目前无法确定**。支撑它们的只有行业形态：三族并存、体积系数逐份、进位可分段。形态足以证明现有结构不够用，却不足以回答首重步长是否随分区变化、续重是否分段递减、进位分段的段界按实重还是按计价重——这些要看真实价卡。仓库红线要求未确认参数保持显式未决、不写死为生产默认；按行业形态先把三族结构定下来，是把同一条红线在结构层再踩一次，只是踩的不是金额而是形状。

于是「一次定死形状」与「不得硬化未确认内容」直接冲突。**这个冲突只因为规范化没有版本号才存在**：有了版本号，形状就可以随证据分批加宽而不使历史摘要失效，两条要求同时成立。

## Decision

**规范化形状获得显式版本标识，并随内容摘要一同保存。** 内容摘要只在同一规范化版本内可比。

- 每个已保存的内容摘要必须携带产生它的规范化版本；不携带版本的摘要视为不完整。
- 回放按原评价记录的规范化版本重新规范化，再比对摘要。摘要不一致**只有在规范化版本相同时**才构成版本内容冲突；规范化版本不同不是冲突，也不得据此判定重放失败。
- 规范化版本的变化必须来自规范化结构的变化，且逐次可追溯到引入它的结构概念。规范化版本不表达业务规则变化，也不替代定价方案、价表或规则工件各自的版本。
- 已保存评价的规范化版本不被追溯改写。既有评价永远按其原规范化版本重放。

**本记录不确定任何新形状。** 价表族的取值集合与进位分段的结构保持未决，直到取得真实价卡；取证要求见 `PAR-SET-03`。

**`PN-07` 的价卡取证要求不放松，但理由改变。** 此前的理由是形状必须趁尚无已保存评价时一次定死，因而取证是形成第一条真实评价之前的硬期限。该期限随本决定解除。取证仍是 `PN-07` 生产候选的准入条件，依据改为登记册既有的那一条：只有已被真实证据证明的价表族才能被激活。没有证据的族不得进入生产候选，无论规范化能否容纳它。

## Consequences

- 多出一层需要长期维护的规范化版本，回放路径按版本分支。这是本决定的真实代价，不假装它只是一个字段。
- 两处形状缺口可以保持显式未决而不阻塞 `PN-07` 开工；`PN-07` 的开始时间不再取决于一次没有期限的取文件动作。
- 「一次定死形状」从硬门禁降为倾向。仍应尽量减少结构变化——每次变化都要新增一个规范化版本并长期支持它——但一次结构变化不再等于历史回放全面失效。
- 代价在此刻支付最低：仓库仍无持久化层，不存在已保存的摘要需要迁移。晚于 `PN-07` 形成第一条真实评价再引入，就要同时处理存量摘要的归属版本。
- 不改变任何计价语义。价格方向隔离、四个评价出口、解释完整性、参考序列解析与不可覆盖各条均不受影响；本决定只改变摘要的可比范围。
- [ADR-0009](./0009-go-modular-monolith-and-versioned-bento-contracts.md) 的版本化技术合同取向与此一致：规范化形状是一份被消费的结构契约，契约变化用版本表达而不是就地改写。

## Alternatives considered

- **按行业形态先把三族与分段进位的结构定死。** 快，且立刻恢复「形状此后不变」的承诺。否决理由是它在结构层写死未确认内容，与仓库红线第一条冲突；且真实价卡与所定形状不符时仍要改，届时已无零成本窗口，等于既担了风险又没省下代价。
- **维持现状，等真实价卡到位后再一次定死形状。** 与 `PAR-SET-03` 原有措辞一致，也不硬化未确认内容。否决理由是它把 `PN-07` 的开工时间挂在一次没有期限的人工取文件动作上，而且只要规范化仍无版本号，将来任何一次结构变化——不限于这两处——依旧是灾难性的。它治不了病因。
- **宣布形状永久冻结，此后不再加宽。** 不可信。参考设计与行业形态都表明价表族不止一种，冻结只会把变化推到规范化之外，形成一套绕开内容摘要的影子结构。
- **给定价方案与价表各自的工件版本加号，而不给规范化加号。** 无效。工件版本已经存在，问题不在工件的版本，而在把工件映射为字节的那个函数的形状；同一工件版本经不同形状规范化会得到不同摘要，正是需要被区分的情形。
