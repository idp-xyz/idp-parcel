# ADR-0029: 按标识取回原状态失败时，结果代数按消费方的恢复动作分格，不按提供方的失败原因分格

Status: Accepted  
Date: 2026-08-11

## Context

[ADR-0027](./0027-multi-step-cross-context-protocol-state-held-by-the-provider.md) 把跨上下文多步协议的中间状态判给提供方，消费方只回指解析标识，提供方「按标识取回原闭包」。它同时要求「取回后必须重校调用方身份与该解析键的租户、客户账户是否一致，不一致按`输入未受理`处理：解析标识不得成为一张能力凭证，否则 `AT-PC-028` 的越权探测会从这里进来」。

**那条防线堵住了读取，没堵住回答。** `party-commercial` 两个取回步骤都照它实现了，也都拒绝了越权调用，但三种取不到各自落在不同取值上：

- `FormJudgmentAsOfHandler` 的 `loadPrior`：读不回 → `解析未决`，查无此解析 → `依据未解析`，范围不符 → `输入未受理`。
- `ValidateCommercialBasisHandler` 的 `loadPrior`：读不回与查无此解析合并 → `解析未决`，范围不符 → `输入未受理`。

于是同一租户下的调用方拿一个标识去问，凭答案就能分出「这个标识从未签发」与「它存在，只是不属于你」。**拒绝本身泄露了存在性。** 两处都有；前者三个取值全分开，因而更锐。这条泄露有一条可执行证据，它随本记录一同落地：`TestAProbeCannotTellAMissingResolutionFromOneOwnedByAnotherCustomer` 用同一个入侵者、同一个标识，只切换取回端口里有没有那份解析。**在下面的 Decision 改格之前**，它两次分别得到 `INPUT_NOT_ACCEPTED` 与 `RESOLUTION_PENDING`，那正是本节所述的泄露；改格之后它断言两者必须相等，因此它此后一直通过。本节写的是被本记录终结的局面，不是现状。

**声称与实现在这里是反的。** 本记录落地之前，两处取回的注释都写着本上下文「说不出它是不存在还是不属于你」，而代码说得出。更要紧的是 `TestARevalidationNamedByAnotherCustomerIsNotAccepted` 与第二阶段的同名守卫：两条当时都以 `AT-PC-028`「不泄露候选」为由，要求越权探测返回`输入未受理`——**两条声称在守护该验收项的测试，恰好是保证泄露的那两条。**

**[UC-PC-002](../application/party-commercial/UC-PC-002-RESOLVE-COMMERCIAL-BASIS.md) 给`输入未受理`的定义本来就不覆盖这一支。** 用例的结果表把它定为「最小租户、客户、范围或锚点身份无法建立」，对应的是身份或标识为空时不查询那一步；「标识有效但属于另一个客户账户」不在其内。`AT-PC-028` 允许答案是`输入未受理`或范围拒绝，它要的是**不泄露候选**，而泄露恰恰来自它与「不存在」可区分。

### 真正要裁的是两条既有原则拉反方向

这不是一次看走眼。仓里有两条都成立、在这一步却互相拉扯的原则，而此前没有任何一处说过冲突时以哪条为准：

- [ADR-0025](./0025-cross-context-adapters-live-on-the-consumer-side.md)「**翻译必须是全函数**：提供方封闭集合里的每个取值都要有明确落点，不留 `default` 兜底」——它奖励把失败原因分得更细，因为每合并一次都可能抹掉一个调用方需要的区别。
- `AT-PC-028`「**不泄露候选**」——它要求分得更粗，因为每多一个可区分的取值，就多回答一个调用方无权知道的问题。

顺着第一条读这两处代码，三分会显得是优点；顺着第二条读，同样的三分是缺陷。**两条都没错，缺的是一条说明它们在哪个维度上不冲突的规则。**

**难逆转的是分格维度。** 结果代数一旦发布，消费侧适配器要为提供方封闭集合里的每个取值写落点，取值改一次两边都要改，已写下的翻译要重判。九个限界上下文之间的多步协议都会出现同一个取回步骤——关务申报重取、路由重判、结算重算——第一次怎么分，后面会照抄。

## Decision

**按标识取回原状态失败时，结果取值按消费方据以选择的恢复动作划分，不按提供方观察到的失败原因划分。** 消费方要从取值里读出的是「我接下来做什么」，不是「你那边出了什么事」。后者是提供方的内部观察，把它逐项映射成取值，等于把提供方的可见性当作消费方的语言。

**这条同时满足上面两条原则，因此也是它们冲突时的仲裁规则。** 恢复动作相同的两个失败原因本就不需要各占一格：合并它们不抹掉任何调用方能用上的区别，所以不违反全函数；而合并之后可区分性正好消失，所以满足不泄露。**冲突只在按「原因」分格时出现；换成按「恢复动作」分格，冲突不存在。**

**取回失败只有两个恢复动作，因此只有两格：**

- **重试同一次调用** —— 读取本身没完成。
- **回第一阶段重新解析** —— 手上这个标识不指向一份本调用方可用的原解析。

**「查无此解析」与「范围不符」落同一格。** 两者的恢复动作相同：调用方没有可用的原解析，必须重新解析。让它们可区分，就是回答了一个调用方本无权知道的问题。合并不是把信息藏起来，是**这两种情形对调用方本就是同一件事**。

**`输入未受理`保留它的另一个职责，不并入上面两格。** 身份或标识为空时，取回步骤在**任何查询发生之前**短路拒绝。那一支的答案不依赖任何解析存不存在——它在还没去看之前就决定了——因此不构成预言机，也仍然符合 `UC-PC-002` 对`输入未受理`的定义。**它与本记录合并掉的那一支是两回事，不要一起合。**

**本记录只管「按标识取回原状态」这一步。** 不做这一步的用例不受影响：`ResolveCommercialBasis` 收的是解析键而不是解析标识，没有取回，也就没有取回失败。

### 三个阶段各自的落法

| 阶段 | 有无按标识取回 | 本记录要求 |
|---|---|---|
| `ResolveCommercialBasis` | 无（入参是解析键） | 一字不改 |
| `FormJudgmentAsOf` | 有 | 「查无此解析」与「范围不符」合并为`依据未解析`；`输入未受理`保留给短路支 |
| `ValidateCommercialBasis` | 有 | 「读不回」与「查无此解析」拆开（读不回归重试格），「查无此解析」与「范围不符」合并；`输入未受理`保留给短路支 |

第三阶段那一拆同时修好一个既有缺陷：读不回与查无此解析原本压在`解析未决`加`权威不可读`上，把一个「重试一万次也没有」报成了「重试可能好」，调用方据以选错恢复动作。**病因正是按原因分格时的另一种误并——合并了恢复动作不同的两个原因。** 本记录的规则两个方向都管：恢复动作相同必须合，不同必须分。

### 消费侧应当长成什么样

消费侧由该上下文自己改（[ADR-0025](./0025-cross-context-adapters-live-on-the-consumer-side.md)：翻译归消费方）。本节写明形状，避免两侧各判一次：

- 合并后那一格落在消费方「回第一阶段重解」的取值上。`parcel-shipment` 侧即 `ports.JudgmentAsOfBasisNotResolved`。
- **不得删除 `ports.JudgmentAsOfInputNotAccepted`。** 它在提供方仍有来源——短路支。只把「范围不符」从它名下移走。判断一个取值有没有源必须查提供方，只看接收端查不出来。
- **`ports.CommercialRevalidationOutcome` 要补一个`输入未受理`落点**，方向与上一条相反。它今天只有`仍然成立`/`已失效`/`未决`三个真值，而提供方第三阶段的短路支会产出`输入未受理`——ADR-0027 已把这个漏项记为「ADR-0025『翻译必须是全函数』下的端口契约缺陷」，本记录不关闭它，因为短路那个源仍在。
- **消费侧不得保留一个只能由「不属于你」产生的落点。** 留着只有两种下场：成为永不可达的分支加一条永不发生的断言，看着像覆盖其实不是；或者日后有人为了「把它用起来」在消费侧重新区分两者，把刚拆掉的预言机在消费侧重建一遍。

**注释与测试不得声称一个取值集合做不到的隐蔽性。** 若日后有人恢复某种可区分性，与之配套的注释和验收描述必须同时改；写着「本上下文说不出」而代码说得出，比不写更坏——读的人会据此以为这一层已经守住。

## Consequences

- 两个取回步骤同时改，只改一处会让泄露从另一处漏出去。
- **提供方损失一部分自我诊断能力。** 运维要分辨「标识从未签发」与「标识属于别的客户账户」，只能从提供方自己的日志与审计里看，不能从交给调用方的结果里看。这是本记录明知的代价：可诊断性属提供方，不属结果代数。
- **两条既有原则的优先关系从此有出处。** 遇到「分细还是分粗」时不再逐案重判：先问恢复动作是否相同。这条比本次修的两个函数值钱——每个多步协议都会遇到同一个岔路。
- 消费侧要改的不止一处，且方向相反（一处保留取值但换来源，一处补一个从未有过的落点）。两侧不同轮次改会让中间态既不全函数也不隐蔽。
- 同类取回此后照本记录办。判错的方向是「多分一格更精确」——每多分一格，就多回答一个调用方没资格问的问题。
- 本记录不解除任何闸门，也不改变 [ADR-0027](./0027-multi-step-cross-context-protocol-state-held-by-the-provider.md) 关于中间状态归属与端口按阶段分方法的任何一条。它只收窄那条记录里「不一致按`输入未受理`处理」一句所指的取值：越权那一支改落「回第一阶段重解」的取值，而该句要防的「解析标识不得成为一张能力凭证」由本记录加强——原先只挡读取，现在连回答也不泄。

## Alternatives considered

- **给枚举新增一格`查无此解析`，让三种失败各有各的取值。** 否决：这是最直觉的一步，也正好把预言机做锐——`FormJudgmentAsOf` 已经这么做了，泄露就出在那里。精确描述失败原因与不泄露存在性在按原因分格时直接冲突，而 `AT-PC-028` 已经裁定哪一边优先。
- **保持可区分，改为在标识本身上防御（如不可猜的随机标识）。** 否决：把一条访问控制不变量降级成一个关于标识熵的假设。标识会出现在日志、审计、消费方凭据与交接引用里，任何一处泄漏都让防线归零；而 ADR-0027 已明确「解析标识不得成为一张能力凭证」，靠标识难猜正是把它当成了凭证。
- **越权探测一律返回技术错误。** 否决：违反 [ADR-0022](./0022-http-status-carries-answer-formed-not-business-verdict.md) 与本上下文一贯的分界——那是一个业务答案而非故障，译成错误会让消费方的续办路径变成内部重试，对着一个永远不会成立的请求重试到底。
- **合并成一格，但在结果里附一个只有运维可读的诊断码。** 否决：那个码会随结果穿过端口，消费方读得到它就等于没合并；读不到则它不属于结果代数，应当留在提供方的审计里，而审计本就该记。
- **连`输入未受理`的短路支也一并合并，让取回失败只有两格。** 否决：短路支在查询发生之前就决定了答案，不依赖任何解析存不存在，因此不构成预言机；合并它只会抹掉一个调用方用得上的区别（改自己的请求 vs 回第一阶段重解），那正是全函数那条要挡的。
- **不立记录，只修这两个函数。** 否决：违反红线「单一权威」。分格维度是这条边上第一次被明确回答，散在两个函数里，下一个写取回步骤的人只能靠反推，而反推最容易得出的正是被本记录否决的第一条。
