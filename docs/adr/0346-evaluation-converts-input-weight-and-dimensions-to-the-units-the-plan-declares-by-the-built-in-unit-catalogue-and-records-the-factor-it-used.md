# ADR-0346：评价把输入实重与尺寸按内置单位目录精确换算到方案声明的单位，换算系数随评价记下、重放只认记下的系数；无限小数按取整边界保留足够位数并如实记截断

Status: Accepted（2026-10-29，Claude Code 会话代产品 owner、PP owner 决（代决）：用户要补「基础数据」第二轮，把 ADR-0335 留下的单位换算接进计价评价；设计由协调方代决、作者落笔，用户未逐条过目，越权风险点待 PP owner 复核。部分停用 [ADR-0335](./0335-countries-currencies-and-units-are-product-built-in-read-only-reference-data-released-with-the-code-and-unit-conversion-keeps-precision-and-is-not-yet-wired-into-pricing.md) 决定四一句。）<!-- 索引注记 -->｜**判据**：评价里输入实重 / 尺寸的单位与方案声明的单位（价表查表单位、体积系数的长度单位）不同时，按 `refdata` 目录的精确系数换算后再走原有取整规则，不再答单位不一致；单位一致的评价先走原函数、字节不动；换算的原值、换算值与系数随评价记下，重放只认记下的系数；换算结果不是有限小数时保留的位数由取整边界推出并如实记截断，含 `NONE` 段的取整策略不收截断；只接重量与长度，特征判定里的阈值单位比较与体积、件数单位不在内。

Date: 2026-10-29

## Context

取证于 main `b8fe76a42`，只记 `S`。

- **评价里的单位比较。** `EvaluatePricing` 在算计价重量时，把输入实重的单位对方案价表的查表单位、把尺寸的长度单位对体积系数声明的长度单位逐一比（`CalculatePricingWeight`、`VolumetricFactor.Apply`），对不上就报 `ErrWeightUnitMismatch` / `ErrLengthUnitMismatch`，评价落「冲突」，问题项 `WEIGHT_UNIT_MISMATCH` / `LENGTH_UNIT_MISMATCH`，文字就是错误原文。
- **方案构造时的自洽检查是另一回事。** 取整策略的进位单位须等于价表单位、附加费声明的重量单位须等于价表单位、体积系数的取整单位须等于重量策略的取整单位；一张方案内部各处单位对不上就立不起来。这是方案自己的矛盾，不是输入与方案之间的单位差，不在本记录范围。
- **特征判定另有一处比较。** 拒收、条件最低重量、附加费这类条件拿包裹特征（输入的实重与尺寸）对阈值比，单位不同同样报单位不一致；CONTEXT 写「换算规则必须版本化声明，判定中不得隐式换算」。这一处本记录不动。
- **输入的单位从哪来。** 申报测量与实测经适配器译成计价的封闭单位表（重量 `G` `KG` `OZ` `LB`，长度 `CM` `IN`）原样进输入快照；表外的单位整件当没有测量，适配器不换算。于是一件申报 5 磅的包裹遇到按千克查表的卡，今天一律是冲突，哪怕磅与千克的关系是定义值。
- **ADR-0335 留了口。** 它把 `refdata.Convert`（精确有理数，不取整、不截断、不经浮点）做出来，同时写明不接计价评价，「接不接、接在评价的哪一步、哪些口径允许，是单独的裁决」。本记录就是这个裁决。
- **谁消费这个答复。** 全仓没有任何代码按问题项 `WEIGHT_UNIT_MISMATCH` / `LENGTH_UNIT_MISMATCH` 这两个码分支，管理台也没有。下游只按评价**状态**分支：结算的采用适配器把「冲突」译成 `StopEvaluationConflict` 停因，小包托运的渠道候选成本把「冲突」译成 `ChannelCostConflict`（候选不可估价），计价自己的编排原样透出。

## Decision

**一、评价把输入的实重与尺寸换算到方案声明的单位，而不是答单位不一致。**

- 输入实重（票级 / 主单级主体上是成员合计实重）的单位与价表查表单位不同：按 `refdata` 目录的精确系数换算到查表单位，再走原有的「派生、抬高、进位」。票级 / 主单级主体声明的合计体积重同理，与合计实重用同一对单位、同一个系数。
- 尺寸的长度单位与体积系数声明的长度单位不同：把三边换算到系数声明的单位再算体积重。换的是尺寸不是除数——除数只对它声明的那个单位成立（CONTEXT「系数只对它声明的那一对单位成立」仍然成立），换算后的尺寸仍落在这个单位上。
- 取整规则一字不改：模式、进位单位、分段、条件最低重量的抬高顺序都原样；换算只是换了喂给它们的那个数。
- 换算只发生在 `EvaluatePricing`。直接调 `CalculatePricingWeight` 的人单位对不上仍然得到单位不一致，不会被悄悄换算。
- 答不出的换算仍是原来的业务格：目录里没有的单位、跨类别（把长度当重量）、冻结模式下没记过的系数，一律答 `ErrWeightUnitMismatch` / `ErrLengthUnitMismatch`，评价落「冲突」，问题项编码与文字和此前逐字相同。领域的 `WeightUnit` / `LengthUnit` 是封闭小集合，这两格从输入走不到，守的是记录与目录这些外来数据。
- 没有任何默认单位：方案没有声明的单位不会被补出来；方案的单位仍由价卡自己声明（租户取值），目录只回答「一个单位折多少另一个单位」。

**二、单位本来就一致的评价一个字节不动；受影响的只有此前答单位不一致的那些。**

`EvaluatePricing` 先按不换算的老路算，只有老路答了单位不一致才带着换算器再算一遍。所以单位一致的评价走的就是改动之前的那个函数，评价、语义摘要、快照字节都与改动之前逐字相同（作者在 main `b8fe76a42` 与本分支上对同一组夹具取同一份摘要与快照散列对照，单位一致与「缺尺寸待判断」「查无费率待判断」各路径全部一致，见票面完成记录）。受影响的路径只有两条：输入实重（含票级合计）单位 ≠ 查表单位；尺寸单位 ≠ 体积系数的长度单位。它们此前是冲突，现在按换算结果评价——完成，或换算之后才暴露的缺口（如实重换算了而尺寸还没到，答待判断 `DIMENSIONS_REQUIRED`）。

**三、换算记进评价，重放只认记下的系数，不重新查目录。**

- 评价上新增一份换算记录，每条：被换算的量（`ACTUAL_WEIGHT`、`TOTAL_VOLUMETRIC_WEIGHT`、`DIMENSIONS`）、原单位与目标单位、系数、原值与换算值、换算值是否精确与截断的小数位。系数是「1 个原单位折多少个目标单位」的精确有理数文本：有限小数写十进制（`0.45359237`），否则写既约分数（`100000000/45359237`），取自目录、不经浮点；记录里只收规范写法。评价输入快照仍保留原值与原单位，解释里加一行，写明原值原单位、换算值目标单位与系数——与汇率换算「保留原币与所引序列版本」同一纪律。
- 重放（`NewReplayEvaluationRequest`）与同标识的重复请求（编排层 `settleAgainstExisting`）把请求置为**冻结**：换算只认原评价记下的系数，目录此刻怎么说都不看。目录随发版可能修订，而重放要重现的是当初那次评价。
- 冻结且没有记录时不换算，照旧答单位不一致。所以换算接入之前答过「单位不一致」的评价，重放与同标识重复请求仍得到同一个冲突、同一个摘要，而不是此刻换算后改判；它们要重算，走新的评价标识（新一代）。
- 换算记录在失败路径上同样留着：换算了实重之后才待判断（尺寸没到、费率落空）的评价，重放要靠这条记录才走得到同一个待判断。
- 记录随评价快照往返，读回门逐条重验：两端单位在目录里且与被换算的量同类别、系数是规范写法的正有理数、换算值等于原值乘系数（精确或按记下的位数向零截断）、原值与输入对得上、换算后的实重与计价重量里的实重对得上。系数本身不对照当前目录。

**四、换算结果不是有限小数时：保留足够位数并如实记截断，不收会改金额的截断。**

目录系数是有理数，但 `Decimal` 是定标十进制：1 磅折 0.45359237 千克是有限小数，1 千克折磅（`100000000/45359237`）、1 厘米折英寸（`50/127`）不是。

- **重量。** 换算结果恰是有限小数就精确落成 `Decimal`。不是有限小数时，向零截断到 `S` 位，`S` = 精确值既约分母的十进制位数 + `g` + 1，`g` 是此后拿这个重量比较或落点的所有有限小数里最细的小数位——取整进位单位（再加一位，`HALF_UP` 的中点）、分段上界、条件最低重量、体积系数的进位单位、成员清单声明的合计体积重。论证：设精确值 W 的既约分母为 Q，任一小数位不超过 `g` 的有限小数 B，只要不等于 W，就有 |W−B| ≥ 1/(Q·10^g)；`S` 位截断值 Wt 满足 0 ≤ W−Wt < 10^−S，而 10^−S 小于这个下界，所以没有 B 落在 [Wt, W] 之间，W 与 Wt 对每个 B 的大小关系相同——比较、选段、`CEILING` 与 `HALF_UP` 的取整结果与不截断时逐一相同。这个论证由用例钉着：用独立的有理数参考实现，在 1 千克折磅的临界点（k × 0.226796185 千克恰是 k × 0.5 磅）两侧各取 1e-12、1e-9、1e-6 的偏差，加一批随机重量，评价算出的进位后重量逐一等于对精确商取整的结果；把 `S` 砍小用例即失败。
- **含 `NONE` 段的取整策略不收截断。** `NONE` 不进位，截断的值会直接进查表与乘单价，那是静默改金额，所以这类策略下无限小数的换算答单位不一致（冲突）；能精确换算的（磅折千克）照常评价。
- **尺寸。** 体积重由精确有理数一步算到体积系数的进位单位：三边乘系数的立方得精确体积，除以除数，落到声明的进位单位上，取整判法与 `Decimal.DivRoundToIncrement` 共用同一个内核（`roundsUp`）——与那个函数同一个理由：精确商不一定是有限小数，先把三边各自截成十进制会给中间结果强加一个没人声明过的精度。解释与记录里展示的换算后三边，不是有限小数时按 16 位向零截断，只供阅读，不参与计算，记录里如实标不精确。
- 解释里写明：不是有限小数、截断到几位、取整在截断值上做而结果与对精确商取整相同。

**五、换算记录只进快照，不进规范化文档；评价语义摘要的形状不变。**

换算后的值已经落在摘要覆盖的计价重量里（`pricing_weight` 的实重、体积重、进位后重量与单位），换算前的值在摘要覆盖的输入里，所以换算对结果的全部影响本来就进了摘要；同一输入、同一方案、同一时点得同一摘要。记录本身只进快照——与回指和问题项涉及序列那两格同一种放法（只进快照、不进规范化文档，旧快照没有这一格照样读回）。规范化文档的键集不变，既有评价的摘要与规范化版本一个字节不动，不换号（[ADR-0267](./0267-a-key-added-to-an-already-canonicalized-body-is-a-shape-change-even-when-old-documents-stay-byte-identical.md) 加键即换号的规则在这里不触发，因为没有加键）。方案内容摘要同样不变：换算需要什么由方案单位与输入单位推出，方案没有为它多声明任何东西。

**六、本轮范围：重量与长度，仅限评价里的实重与尺寸。**

- 只接重量与长度两类。体积、件数单位目录里有，评价里没有对应的输入，不接。
- 特征判定里的单位比较（条件阈值对包裹特征）不换算，CONTEXT「判定中不得隐式换算」一句留作现行，只在后面加一句限定它不涉查表重量与体积重的换算。
- 适配器的译码口径不放宽：目录里有而计价封闭表里没有的单位（吨、毫克、毫米、米、英尺、码）仍是表外，整件当没有测量。要接这些，得先放宽 `WeightUnit` / `LengthUnit` 这两个封闭集——方案声明单位用的也是它们，是另一份决定。

## Alternatives considered

- **维持报错。** 否决：磅与千克的关系是定义值，让一个本来能精确算出的评价停在「冲突」，等于要租户为每个单位对各配一张卡；且 ADR-0335 已把换算做成精确的、等着这个裁决。
- **换算规则放进价卡，版本化声明（CONTEXT 此前的口径）。** 否决：磅等于 0.45359237 千克不是价卡的取值，更不是租户取值——ADR-0335 已论证它们是公开标准与物理常数；放进卡里，同一磅在不同卡上可以折出不同的千克，等于让同一件包裹在不同卡上多出一条会算错钱的自由度。声明的是单位（价卡本来就声明），换算只是目录回答的事实。
- **在适配器里先把输入换成千克（或某个默认单位）。** 否决：适配器不知道方案的查表单位，只能选一个默认单位——那是写死租户取值；换了之后输入快照丢了原值原单位，评价读不出当初申报的是什么。
- **在 `EvaluatePricing` 开头把输入一次换到方案单位。** 否决：拒收、条件最低重量、附加费的条件在计价重量之前就拿输入的实重与尺寸比阈值，开头就换会让今天按输入单位判得对的评价（阈值写的就是输入的单位）改判成单位不一致——违反「不改变今天已算对的评价」。换算放在计价重量那一步，条件判定读到的仍是原输入。
- **把换算记录纳入规范化文档并换号。** 否决：换算的全部影响已在摘要覆盖的字段里，再加一键只为让摘要「多认」一个系数，代价是新规范化版本要长期支持（[ADR-0014](./0014-versioned-canonicalization-shape-for-content-digest.md)），且读回门已逐条重验记录与输入、计价重量的一致。风险点 5 记下它的边界。
- **无限小数一律拒。** 否决：美制小包价卡按磅查表、重量按千克申报是最常见的跨境组合，一律拒等于这个组合仍然不能用。
- **无限小数固定保留若干位（如 6 位）。** 否决：位数不由取整边界推出就是静默截断——临界点两侧偏差够小时，固定位数会把本该进到下一档的重量留在上一档。
- **浮点。** 否决：同 ADR-0335，0.45359237 经二进制走一圈往返不再精确。
- **重放按目录重新查系数。** 否决：目录随发版修订，重放就会得出另一个数，被判成冲突，而评价并没有错。

## Consequences

- `internal/parcelpricing/domain` 新增单位换算（换算器、换算记录、读回自洽门）；`EvaluationRequest` 多一对冻结字段，`PricingEvaluation` 多一份换算记录与访问口，评价快照多一个可缺的键。无迁移、无库表（快照是 JSON 文档）。
- 此前因单位不一致落「冲突」的评价路径现在按换算结果评价：完成，或暴露出换算之后才有的缺口（待判断）。已在册的冲突评价不改写。
- 结算与渠道比价按状态分支：此前被单位不一致挡在「冲突」的请求与渠道候选，用新评价标识重算时会得出金额。同标识重放得到旧答复，这是有意的。
- `refdata.Convert` 的调用方不再是零；`Convert` 收到 nil 现在报 `ErrNilValue` 而不是 panic（上一轮评审的非阻断余项）。
- 评价解释多出「unit conversion」行，仅在发生换算时出现。
- 管理台与 HTTP 响应不新增字段：换算在解释文字里可读，结构化记录在评价快照里。

## 越权风险点

0. 目录系数随发版变（决定三）。物理定义值不该变，但目录一旦修订，同一输入在新旧构建上的首次评价会得出不同的换算值；回放与同标识重复请求靠记下的系数不受影响。需要「目录修订后既有未结评价重算」的流程，另立决定。归计价 owner。
1. 范围只到实重与尺寸（决定六）。特征判定里阈值与特征的单位比较仍不换算，真实参数里「阈值以公制声明而价表用 `LB` / `IN`」（`R40`）的那一格仍待换算规则的声明形式；体积、件数不接；吨、毫克、毫米、米、英尺、码在目录里但适配器仍当表外。归计价 owner。
2. 无限小数的论证依赖 `g` 枚举得全（决定四）。`g` 现在由取整策略的进位单位与分段上界、条件最低重量、体积系数的进位单位、成员合计体积重推出；日后评价里若新增了任何拿计价重量去比较或落点的量，必须并入 `conversionBoundaryScale`，否则论证失效而没有测试会报——参考实现对照只覆盖现有的量。归计价 owner。
3. 「单位不一致」这一业务答复的语义变了（决定一、二）。此前这两格是冲突，下游按状态译成停因与候选不可估价；现在同样的输入得出金额，或得出换算之后才暴露的待判断。没有代码按问题项编码分支，所以没有下游会因为码变少而坏；但「我们不接受磅申报」若曾被租户当作隐含的拒单手段，现在不再成立——要拒是价卡的拒收条款的事。归计价 owner 与结算 owner。
4. 此前答冲突的评价不自愈（决定三）。冻结且无记录时同标识重放仍答冲突；要按换算重算得走新标识。这是为让既有评价的重放与摘要不变，代价是存量冲突要人或编排重新发起。归计价 owner。
5. 摘要不含换算记录（决定五）。记录的系数与换算值同时被改且自洽、而改动没有改变实重或体积重的摘要字段时，摘要看不出；读回门只验记录内部与对输入的一致，不对照目录。若要摘要认系数，得走 ADR-0014 / 0267 换号。归计价 owner。
6. 展示精度 16 位（决定四）与 `S` 的公式是作者的取舍：前者只用于解释与记录里换算后三边的阅读，不进计算；后者由论证推出的是下限，取下限加一。owner 可改，改了要同步用例。归计价 owner。
7. 同一对单位在一份评价里用同一个系数（决定三）：实重与合计体积重换算时共用，读回门拒同对单位不同系数的记录。若日后某个量要用不同的取值时点，得另立。归计价 owner。
