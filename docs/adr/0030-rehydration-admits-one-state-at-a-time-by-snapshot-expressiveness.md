# ADR-0030: 聚合重建按状态逐个开门，一个状态只有在快照能表达它可达的全部字段时才准进

Status: Accepted  
Date: 2026-08-11

## Context

[ADR-0028](./0028-aggregate-rehydration-is-a-separate-door-that-validates-without-recomputing.md) 开了重建这扇门，并预先点名「把哪些状态组合是合法的写下来」是其中最花时间、最容易写漏的部分，写漏的方向是让一个业务上不可能的聚合通过校验。门落地之后第一次逐字段对账的结果比那句预警更靠前一步：**这扇门宣称能重建四个状态，实际只能重建一个，而且连那一个都不完整。**

`ShipmentRequest` 十三个字段，`RehydrateShipmentRequestSpec` 表达得出其中六个半：

- 顶层缺六个：`decision`、`decisionFormed`、`baseline`、`commitment`、`withdrawal`、`sourceDataVersions`；
- 接受判断任务那一层缺两个：`processingAttempts`、`reviewCompletion`。

**`validForRehydration` 那十处拒绝点一条都拦不住这八个。** 它们检查的都是「填进来的东西对不对」，而这八个**根本没有字段可填**。缺字段与填错字段在校验面前不是同一类问题：后者拦得住，前者连拦的位置都没有。

至少三处会真改变业务结果：

1. **次零基线拒掉全部指名成员的资料更正。** 已接受委托重建后 `baseline` 为空，而 `SourceDataScopeOutsideAcceptanceBaseline` 拿它去问「这个成员在不在接受时固定的集合里」，答案恒为否，于是 `AmendCustomerSourceData` 把每一次指名成员的更正都拒成 `ErrParcelOutsideAcceptanceBaseline`。一份空基线比没有基线更坏：它是个会回答的权威，只是每次都答错，而调用方拿到的是一个确定性的业务拒绝，不是一处看得见的故障。
2. **已经做完的人工复核被再要求一次。** `manualReviewState` 由规则包的声明与任务上的完成事实合成，完成事实丢了就从`已完成`退回`已要求`，`Decide` 据此停在 `ResumeByManualReview`。
3. **「复核只能一次」的不变式失效。** 同一处丢失让 `CompleteManualReview` 的重复闸门在重建之后放行第二次补签——而那条不变式存在的理由正是不让换人补签静默覆盖第一次的留痕。

**难逆转的是这扇门按什么粒度开。** 一次开齐要为六个产物造九个 `Rehydrate*Spec`，而它们的形状由一份还不存在的持久化模式决定：`adapters/postgres` 今天只有 `source_submission.go`，`ShipmentRequestRepository` 一个真实现都没有。造出来的九个类型是**永久的重建面**，而 ADR-0028 把重建面定为「本包唯一一处相信输入的地方」，此后每宽一格都要回到那份记录。反过来，不开齐就必须回答一个更难的问题：**一扇只开一半的门，凭什么不是今天这个样子——宣称四个、其实一个。**

八个不可重建类型、两个上下文的 Repository 都会照第一扇门的粒度来。

## Decision

**重建按状态逐个开门，不按聚合整体开门。**

**准入判据是快照的表达能力：一个状态只有在快照类型能表达它可达的全部字段时，才准从这扇门进来。** 判据落在表达能力上而不是「我们这一期打算支持哪些」——后者是一句意图，只能靠人记得；前者是可以逐字段对账的事实，而本记录正是从一次这样的对账里长出来的。

**今天只开`已提交`。** 补上 `processingAttempts` 与 `reviewCompletion` 之后，快照对`已提交`就是全的：另外六个顶层字段在`已提交`下**必然缺席**，而这一条由转移各自证明——`decision`、`baseline`、`commitment` 只由 `Decide` 的接受支写下，`withdrawal` 只由 `WithdrawByCustomer` 写下，`decisionFormed` 由三条终态路径写下，`sourceDataVersions` 的唯一入口 `AmendCustomerSourceData` 要求`已接受`。**它们不是被推迟的缺口，是这个状态下不存在的东西。** 这正是`已提交`满足准入判据、另外三个状态不满足的分界，也是本期与今天这个「宣称四个、其实一个」的分界。

**没开的状态由入口显式拒绝，且用一个与「这行数据不可能」不同的哨兵。** 依 [ADR-0029](./0029-retrieval-failure-algebra-is-partitioned-by-recovery-action.md)：两者的恢复动作不同——一个是等这扇门开到那个状态，一个是去查库里那一行或写它的适配器。压成同一个取值，运维会照着一份完好的数据去找一处不存在的损坏。

**快照仍然收 `State` 字段，不改成「这扇门只产出`已提交`」。** 后者省得掉一个哨兵，代价是适配器读到一行`已接受`时会静默拿到一份`已提交`聚合，连自己错了都不知道；收下再拒绝，错处当场说得出口。

**两个嵌套字段收成品类型，不另造 `Rehydrate*Spec`。** `ProcessingAttempt` 与 `ManualReviewCompletion` 是判断的**输入**而非产物：本就有公开构造函数，字段未导出，包外造不出半截的一份。重建面因此一格都不宽。**这同时给出下一期的判别式——一个东西要不要新 Spec，看它有没有公开构造器；没有的才是产物，才要新面。**

## Consequences

- **重建面本期不长。** 导出标识符仍是那四个 `Rehydrate*`，只多一个错误哨兵；`internal/architecture` 的重建面名单不必为本期新增入口。
- **下一期的入口条件是明确的，不是「有空再说」。** 某个状态要开门，先补齐它可达字段的表达，再把它从拒绝名单里放出来；两步顺序反了就回到今天这个样子。
- **`ShipmentRequestRepository.Save` 仍未收预期版本。** ADR-0028 那一半不在本记录范围内，它波及应用层每个调用点，与本记录各自成切片。
- **一个状态的门开着，不等于它的跨字段不变式已经写全。** 本记录管的是「哪些状态准进」，`validForRehydration` 管的是「进来的这一份成不成立」，两者都要，缺一个另一个补不上——与 ADR-0028 门禁与校验互补同一形状。
- 判错的方向是把准入判据读成一句进度声明，于是新状态先放进来、字段以后补。那样这扇门会退回本记录要修的原样，而且此后有一份记录替它背书。

## Alternatives considered

- **一次把八个字段补齐，四个状态一起开。** 否决：六个产物要九个 `Rehydrate*Spec`，形状由一份不存在的持久化模式决定，而 `ShipmentRequestRepository` 今天没有任何真实现来说明那些行长什么样。ADR-0028 已用同一条理由否掉 `EventBuffer`（「现在加是推测，而且会把重建面扑大」），本条与它一字不差；差别只在这次要扑大的是九个类型，而重建面每宽一格都是永久的。
- **只补两个嵌套字段，不加状态闸门。** 否决：那修好了`已提交`，却让另外三个状态继续静默地少六个字段——次零基线那一条恰恰发生在`已接受`上，是三处业务结果改变里最重的一处。修完最容易看见的那半、留下最贵的那半，还会让下一个人以为这扇门已经对过账了。
- **状态闸门与坏数据共用 `ErrInvalidRehydratedShipmentRequest`。** 否决：违反 ADR-0029 的分格规则。恢复动作不同的两件事共用一个取值，等于让适配器作者拿着一行完好的数据去找损坏；而这两者的可区分性不泄露任何东西，没有任何理由合并。
- **对没开的状态「尽力重建」，缺的产物留零值并在文档里写明。** 否决：这正是今天的行为，也正是本记录要修的东西。ADR-0028 已判过这个方向——「写漏的方向是让一个业务上不可能的聚合通过校验，而它此后看起来与真的一样」；把它写进文档不改变任何一行代码的行为，只是给同一个缺陷换了个位置存放。
- **不立记录，只改代码。** 否决：违反红线「单一权威」。「一扇门可以只开一部分状态」是本仓第一次回答，而另外七个不可重建类型与第二个上下文的 Repository 都会遇到同一个岔路；散在一个 `switch` 里，下一个人只能反推，而最容易反推出的正是上一条被否决的那个。
