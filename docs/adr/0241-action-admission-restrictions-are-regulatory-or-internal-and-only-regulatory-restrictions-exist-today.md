# ADR-0241：动作准入的「限制」一源分监管限制与内部合规限制两种，互不改名、互不解除；代码里的限制是监管限制，内部合规限制随 UC-CC-011 另立模型

Status: Accepted（2026-10-21，Claude Code 会话代决：用户原话「需要修改文档，确保自洽，正确」与常设授权「你作为业务和系统专家自决」；票 docs-consistency/03，代 CC owner 裁定审计 cc H3。部分停用 [ADR-0206](./0206-customs-action-admission-judgement-folds-three-sources-and-judges-cross-zone-by-node-customs-zones.md) 决定四、决定五各一句，见「对已接受记录的作用」。越权风险点见文末，待 CC owner 复核。）<!-- 索引注记 -->｜**两种限制**：监管限制由已接受的监管过程决定（扣留等）对明确范围形成，只能凭责任来源接受的监管结果整条解除；内部合规限制是运营企业的内部决定，覆盖项逐项、由限制责任来源部分或全部解除。不互相改名、不互相解除，外部放行不自动解除任一种。**代码对位**：`RegulatoryRestriction` 是监管限制，不在它上面长责任来源解除或部分解除；内部合规限制随 UC-CC-011 另立对象与册。**准入**：任一种在动作时点有效且约束本动作即阻断；内部合规限制的适用性答待确认或冲突时该动作答未决并指名那条限制，技术未形成照读不动办。**实现现状**：准入今天只读监管限制册，内部合规限制尚无模型与写口，这一格不读成「无内部限制」；首发范围仍要求内部合规限制（PILOT-SCOPE、关务专项基线切片 1），缺口随 UC-CC-011 实施补上，接线的同一笔并进准入（code/27）

## Context

- 审计 cc H3（`.scratch/docs-consistency/audit/cc.md`，钉 `6b0074d0`；2026-10-21 按 main `205eb254` 复核，现象仍在）：动作准入判断三源之一在 CC CONTEXT「动作准入判断」词条、Rules 与 ADR-0206 决定五里写作「内部合规限制」，代码里参与准入的却是 `domain.RegulatoryRestriction`——头注「作用于明确对象范围的监管限制」，挂 `Decision RegulatoryDecisionID`，唯一解除入口 `ReleaseByRegulatoryOutcome` 只收 `RegulatoryReleaseReference`（「指名责任来源接受的监管结果——它是解除限制的唯一依据类型」），没有覆盖项、限制责任来源、解除条件与部分解除，适用性只有可继续 / 被阻断两格。`ports.RestrictionStore`：「保存监管限制并按范围盘出参与准入判断的限制」。
- CC CONTEXT 本来就有两样东西。其一，Rules「申报就绪、授权与提交」：「扣留决定与隔离、控制或移交执行事实分别保存。执行方形成的控制或隔离事实不能解除扣留，只有责任来源接受的监管结果才能解除相应监管限制。」——这是代码那一种。其二，「内部合规限制」词条与 Rules「监管凭证、限制与处置」：「每项内部合规限制必须明确责任来源、依据、适用对象、受限动作、开始时间和解除条件，并逐项保存限制覆盖。只有原限制责任来源在当前授权内可以形成解除」「外部放行不自动解除内部限制」——这是 UC-CC-011 那一种，代码里没有。UC-CC-003 `AT-CC-061` 已把两种并列：「内部合规限制或外部监管限制仍有效并覆盖当前范围和拟提交动作」「其中一类限制解除不能替代另一类限制」。
- GLOSSARY「限制」条：「“内部合规限制”仅指运营企业依据贸易合规规则形成的内部业务决定；监管扣留……属于外部监管事实……不能互相改名或相互推导」。代码与 CONTEXT 合起来正好把两者叫成了同一个名字。
- 今天不出生产事故：`ManageRestrictionHandler` 在 `cmd/` 下没有装配（ADR-0206 越权风险点 1），限制册在生产上是空的，阻断只来自门禁与外部放行。但 UC-CC-011 一开工就会撞上：要么在 `RegulatoryRestriction` 上加责任来源解除，让监管限制可以不凭监管结果解除；要么照代码让外部结果解除内部限制。两条都违反 CONTEXT 硬句。

## Decision

**一、限制分两种，各有各的解除依据。**

- **监管限制**：依据已接受的监管过程决定（扣留等）对明确对象范围形成、明确列出所约束的方向性动作的阻断事实。只有一份指名「责任来源接受的监管结果」的解除才能解除它；执行方的控制、隔离或移交事实不能。今天整条解除。
- **内部合规限制**：UC-CC-011 的对象——运营企业依据贸易合规规则形成的内部阻断决定，带限制责任来源、依据、覆盖项与解除条件；只有原限制责任来源在当前授权内形成的解除决定才改变它，可部分解除；适用性判断分有效限制、无内部限制、待确认、冲突，技术未形成另成一类结果。
- 两种互不改名、互不解除：监管限制解除不解除内部合规限制，内部合规限制解除也不解除监管限制；外部放行结果不自动解除任一种——监管限制要另有一份引用已接受监管结果的解除，内部合规限制要限制责任来源的解除决定。

**二、代码里的 `RegulatoryRestriction` 是监管限制。** 它的模型（挂监管决定、凭监管结果整条解除）对得上第一种，留着不动；它不长覆盖项、限制责任来源、解除条件、部分解除或待确认与冲突两格——那些是内部合规限制的，长在它身上就让监管限制可以不凭监管结果解除。内部合规限制随 UC-CC-011 的实施另立领域对象与登记册，不复用 `RegulatoryRestriction`，也不复用限制册的表。代码注释里把它称作「内部限制」「内部合规限制」的地方改称监管限制（code/27）。

**三、动作准入的「限制」一源由两种合成。** 逐动作、逐范围（对象自身与各当前单元）读两种限制：

- 任一种在动作时点有效且约束本动作：`阻断`，来源是那条限制的标识。
- 内部合规限制的适用性在动作时点答待确认或冲突：该动作答`未决`，依据指名那条限制——它既不是一条有效限制（阻断要指得回一条有效限制），也不能读成无内部限制（CONTEXT「不得按无记录、最后消息或人工备注推导无内部限制」）。
- 内部合规限制的适用性技术未形成，与「任一来源读不动时判断不形成」同办。
- 压制次序照 ADR-0206 决定五：阻断压过未决。

**四、实现现状与缺口：内部合规限制还没有模型、没有写入口。** 这是实现缺口，不收窄首发范围——[PILOT-SCOPE](../product/PILOT-SCOPE.md) 要求验证内部合规限制与外部监管扣留或放行独立存在、只能由来源责任方解除，[关务专项开发基线](../product/CUSTOMS-FIRST-RELEASE-DEVELOPMENT-BASELINE.md)切片 1 含内部限制，首发照旧要求它。动作准入的限制一源今天只读监管限制册，而监管限制册也没有生产写入（ADR-0206 越权风险点 1）。这一格不是「当前无内部限制」的结论：产品里还没有这一类事实，准入不读它、也不替它作答。UC-CC-011 实施的同一笔把内部合规限制并进准入；缺口补上之前，不得对外宣称内部合规限制会挡住动作。

**五、监管限制由谁形成不在本记录。** 形成与解除监管限制的命令就是今天的 `ManageRestrictionHandler`；它该由 UC-CC-008（扣留决定的协作）还是由 UC-CC-006 接收扣留结果时派生来驱动，归接线那张票，本记录只定它是哪一种限制。

## 对已接受记录的作用

部分停用 [ADR-0206](./0206-customs-action-admission-judgement-folds-three-sources-and-judges-cross-zone-by-node-customs-zones.md) 两句：决定五「限制：动作时点有效且约束本动作的限制一律`阻断`，来源是限制标识。外部放行不解内部限制。」扩成两种限制合成、外部放行不自动解除任一种，并加内部合规限制待确认与冲突答`未决`一格；决定四「限制按对象自身和各当前单元两种范围读：内部限制可以直接落在包裹上。」里的「内部限制」改读作两种限制。**适用场景**：只限限制一源的构成与内部合规限制的待确认、冲突两格；「动作时点有效且约束本动作的限制一律`阻断`，来源是限制标识」、两种范围的读法与 ADR-0206 其余各条不变。

## 候选与反方

**甲 · 把 `RegulatoryRestriction` 改成 CONTEXT 的内部合规限制模型（加覆盖项、责任来源解除、部分解除、四格适用性）。** 审计给的两条路之一。反方：一个对象两种解除依据——扣留派生的那条只能凭监管结果解除，内部决定只能凭责任来源决定解除——要么在类型上靠一个「种类」字段分支，等于把两样东西塞进同一个名字（GLOSSARY「不能互相改名」）；要么让扣留也可以由责任来源决定解除，违反「只有责任来源接受的监管结果才能解除相应监管限制」。否决。

**乙 · 准入只认内部合规限制，监管扣留只经放行门禁核对或外部放行读。** 反方：扣留是监管机构对动作的直接约束，不是租户登记的门禁条件；只经门禁读，就得要租户在门禁目录里登一道「扣留」才挡得住扣留，没登的租户被扣留的货照走。CONTEXT「尚未放行或存在方向性限制时，必须阻断其明确约束的出库、装载出发、跨关务区域移动或交付」把方向性限制与未放行并列，没有让它绕道门禁。否决。

**丙 · 准入只认监管限制，内部合规限制不进准入。** 反方：UC-CC-011 要向 `node-operations`、`transport-fulfillment` 提供范围化当前限制，CONTEXT「只有作用于当前对象和拟执行动作的全部阻断性限制均已解除，相应动作才可继续」管的是全部限制；准入是 ADR-0206 定的唯一折叠处，内部合规限制若另走一路，同一决定就有了两处定义。否决。

**丁 · 内部合规限制待确认或冲突答`阻断`。** 偏保守。反方：阻断的依据要指回一条有效限制，续办是等解除；待确认的续办是去确认来源，冲突的续办是去裁冲突——恢复动作不同就分格（ADR-0029）。`未决`同样不放行，不违反「不得推导无内部限制」。否决。

## Consequences

- CC CONTEXT：Language 加「监管限制」词条，「内部合规限制」「动作准入判断」两条与 Rules「动作准入判断」一节照本记录改写；UC-CC-011 写明它的对象不是代码里的 `RegulatoryRestriction`、今天尚无模型与写口（实现缺口，首发范围仍要求它）、UC-CC-013 是它按动作时点读的消费方；UC-CC-013 三源的措辞与 `AT-CC-418` 随之改。
- 代码票 [docs-consistency/code/27](../../.scratch/docs-consistency/code/27-customs-restriction-comments-call-the-regulatory-restriction-internal-and-internal-restrictions-have-no-model.md)：注释改称监管限制（R3）；内部合规限制的模型、册与并进准入列为 UC-CC-011 接线前必修。
- GLOSSARY「限制」「内部合规限制」「动作准入判断」三条的措辞交票 docs-consistency/10。

## 越权风险点

1. **监管限制整条解除**（CC owner）。真实程序若只解除扣留的一部分范围（只放 P1 的扣留），`RegulatoryRestriction` 表达不了；要么拆成逐范围多条限制，要么给监管限制补部分解除。本记录不裁，等 `PAR-CUS-01/02` 给出扣留与解除的范围语义。
2. **内部合规限制待确认答未决、不答阻断**（CC owner、TF owner）。未决同样不放行，但动作执行方对未决照记还是挡由执行方定（ADR-0205）；执行方若把未决当可走，待确认的限制就漏了。
3. **准入今天不读内部合规限制**（CC owner）。这是实现缺口，首发范围仍要求它；缺口补上之前，租户在产品之外作出的内部限制，产品挡不住，产品对内部合规限制只能如实说「未实现」，不能以此宣称首发已验证内部合规限制。
4. **监管限制没有生产写入**（CC owner，与 ADR-0206 越权风险点 1 同一件事）。今天扣留挡不住动作，挡的只有门禁与外部放行；谁来形成监管限制见决定五。
5. **两种限制的命名进 GLOSSARY**（交票 10）。GLOSSARY 今天只说内部合规限制与监管扣留不能互推，没有「监管限制」一词；本记录在 CC CONTEXT 里立了它，横切文件改动交出。
