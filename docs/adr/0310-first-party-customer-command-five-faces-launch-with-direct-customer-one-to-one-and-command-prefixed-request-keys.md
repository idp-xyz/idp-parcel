# ADR-0310：首方客户命令五口（撤回、取消包裹、资料修订、补充、索赔）按直客 1:1 上线；来源请求键加命令前缀；补充基准版本由提交回执带回；索赔以（账户、批次、项）为自然键；取消授权规则是租户取值；首发不做客户状态读与限流

Status: Accepted（2026-10-26，Claude Code 会话 `tops-20` 代 owner 决：用户 2026-10-26「都需要」（首个租户上线时客户经首方 API 要能撤回、取消、修订、补充、索赔）、「每个客户系统只代表它自己的账户（直客），只考虑这个吧」、「首发不要客户状态读口」、「首发不做限流」，其余技术取舍用户答「你帮我决定吧」；票 first-party-api/06。裁决能力边界：读过 [ADR-0139](./0139-first-party-customer-api-channel-is-a-product-owned-access-channel-family.md) 决定二、五、八与越权风险点 1–5、`internal/accessidentity` 的 `customer_client_*.go` 与 `registration.go` 的 `RequestKeyDerivation`、`CustomerCapability` 词表、access_identity 迁移 0010 至 0017 的能力 CHECK、PS 的提交回执与补充命令、首方 API 契约稿、票 first-party-api 摸底报告；未读各口领域编排的全文（UC-PS-002、005、006 与索赔用例只读摸底报告的转述）——领域侧细节让位于各口落地那一票。）<!-- 索引注记 -->｜**取舍 A 到 F**：A 请求键加命令前缀，B 直客 1:1 的授权，C 取消授权规则是租户取值，D 首发不做状态读，E 补充基准由回执带回，F 索赔自然键｜**对 ADR-0139 的作用**：扩展，不停用——决定二的词表增五词、决定五的推导增五个命令前缀、决定八的形状版本为五口各定名；越权风险点 5 的 1:N 首发取 1:1
Date: 2026-10-26

## Context

**首个租户上线时，客户经首方 API 要能撤回、取消、修订、补充、索赔，今天五口全挂未配置。** `cmd/parcel-api` 里这五口都是 `UnconfiguredIntake{}`；铸造器只有提交、送站预报两口、交接确认与追踪视图查阅；`RequestKeyDerivation.DeriveWithdrawalRequestKey` 答推导不出，其余四口没有推导；五口的规范化形状与形状版本没定（ADR-0139 决定八：未定形状的口不开首方渠道）。

**要裁六格，都是各口票开工前必须先定的。** 一，五口的来源请求键怎么推、与提交那一串怎么区分（ADR-0139 越权风险点「撤回、取消、补充、资料修订、索赔提交各命令的来源请求键推导」）；二，授权：谁有权撤回、修订、补充；三，取消的授权规则谁定；四，客户读回；五，补充要的基准版本从哪里来；六，索赔的唯一性。

## 候选与反方

### A 来源请求键

- **各命令一律取裸的接入请求标识，靠各自的判重册隔开。** 反方：PS 的撤回、修订、补充、取消各有自己的身份类型，但接入请求标识在客户系统那一侧是同一个字段；客户系统用同一个编号体系发请求是常态，同一个标识先提交后撤回若落进同一判重空间，撤回会被判成提交的重放（`RequestKeyDerivation` 头注担心的事）。分册可以挡住这件事，却把「不撞」押在每个下游册都分得对上；摊到五口、五个下游，漏一个就是静默吞单。否决。
- **契约要求客户系统给每个命令用互不相交的标识。** 反方：把产品的幂等语义压给客户的编号纪律，违反的后果是静默的。否决。
- **命令前缀加去两端空白的接入请求标识。** 即决定一。

### B 授权

- **直客 1:1：一个客户系统只代表它自己的账户，册上绑定即授权。** 即决定二。
- **代理人 / 平台 1:N：请求里认领账户、按授予集核对。** 用户已限定本轮只做直客；它需要认领账户、委派册与更重的越权面，归 first-party-api/01，不在本轮。

### C 取消授权规则

- **产品代拟默认规则（如「收寄前客户可取消」）。** 反方：UC-PS-006 明禁默认放行或默认拒绝；谁能在哪个阶段取消是租户的业务规则（ADR-0146 租户取值），产品代拟等于替租户定业务条款。否决。
- **租户取值，没登记答未配置。** 即决定三。

### D 客户读回

用户定：首发不做客户委托状态读口。客户靠写口回执、同请求重放与客户追踪视图。

### E 补充的基准版本

- **客户补充前先读当前版本。** 反方：首发没有状态读口（D），读不到。
- **由提交回执返回。** 即决定五。

### F 索赔唯一性

- **以接入请求标识判重。** 反方：接入请求标识逐请求唯一（ADR-0139 决定五），客户换标识重发同一笔索赔就是第二份——同一批次同一项被索赔两次，赔付风险在这里。否决。
- **（账户、批次、项）为自然键，接入请求标识只管传输重放。** 即决定六。

## Decision

**一、来源请求键加命令前缀（取舍 A）。** 撤回、取消包裹、资料修订、补充、索赔五口的来源请求键 = 命令前缀 + 去两端空白的接入请求标识：`withdrawal:`、`parcel-cancellation:`、`source-data-amendment:`、`supplement:`、`claim:`。提交与送站预报两口不带前缀，已登的键不改。标识缺席或全空白答推导不出（`ErrRequestKeyNotDerived`，400）。契约写明：标识只在命令内唯一；同一标识跨命令不撞，命令内再发即重放。`DeriveWithdrawalRequestKey` 取代原来的「推导不出」；`RequestKeyDerivation` 接口不扩：其余四个推导只是 `customerAPIRequestKeys` 的方法（送站预报两口同例），免得租户既有渠道适配族凭空多出四个必须实现的未决方法。

**二、授权（取舍 B）：直客 1:1。** 客户系统在册上绑定唯一（租户，客户账户），铸造出的信封账户取自册，客户只指名「原提交的接入请求标识」；他账户的标识在带账户条件的查找下天然找不到，各口答「找不到」、不泄露存在。撤回、取消无 PC 裁定环节，授权 = 账户绑定 + 授予 + 准入范围；补充 = 账户绑定 + 授予 + 基准版本核对；资料修订保留 PC 裁定（UC-PS-002、ADR-0116），请求方即客户本人、不涉委派。

**三、取消授权规则是租户取值（取舍 C）。** 产品不代拟。演示租户登参考配置「客户系统可在收寄前取消」；首个真实租户上线实施时登记本租户的取值，没登答`未配置`，取消口对该租户不开。

**四、首发不做客户状态读口与按客户端限流（取舍 D，用户定）。** 客户的读回靠写口回执、同请求重放与客户追踪视图。按客户端限流归 first-party-api/02，不在本轮。

**五、补充的基准版本由提交回执带回（取舍 E）。** 提交回执（`POST /v1/shipment-requests`）在指名委托时带 `submissionVersionId`：该委托此刻的当前提交版本标识，与 `shipmentRequestId` 同在同缺；只加不改，既有字段与状态码不动。补充载荷带回它作基准，过期答 `SUPPLEMENT_BASIS_STALE`。重放在补充之后读回的是补充形成的当前版本，不是首个版本——补充基准要的正是当前版本。回执原本就带 `shipmentRequestId`，取消口按它指名委托（取舍 E 对取消口的附带结论）。

**六、索赔以（账户、批次、项）为自然键（取舍 F）。** 接入请求标识只作传输重放，不决定索赔是否同一笔。同一（账户、批次、项）再来一份索赔，是同一笔的重复，不是第二笔；怎么答（既有结果还是内容冲突）归索赔口那一票按 VE 领域规则定。

**七、能力词与形状版本。** `CustomerCapability` 增五词：`SHIPMENT_REQUEST_WITHDRAWAL`、`PARCEL_CANCELLATION`、`SOURCE_DATA_AMENDMENT`、`SHIPMENT_REQUEST_SUPPLEMENT`、`CLAIM_SUBMISSION`，一份迁移（access_identity 0024）一次登完；五口都是生产写，铸造侧判准入范围（能力 `CUSTOMER_COMMAND`、事实类型取这一口的词）。五口的规范化形状版本（ADR-0139 决定八）：撤回 `PWD-1`、取消 `PCN-1`、资料修订 `PAM-1`、补充 `PSU-1`、索赔 `VCL-1`；只定名与版本，字段由 07（撤回）、11（取消）、10（修订）、08（补充）、09（索赔）各自那一票填，填之前对应的首方口不开。

## 对已接受记录的作用

扩展 ADR-0139 的三处（决定二词表、决定五推导、决定八形状版本）与越权风险点 5 的首发取值（1:1），不停用其任何条款。ADR-0139 正文不改，只在 Status 行索引注记与 Links 加前向指针。

## Consequences

- 铸造底座就位，各口票（07 撤回、08 补充、09 索赔、10 资料修订、11 取消）只剩领域译命令与端点装配；在它们落地之前，五词授了也只答`未配置`。
- 客户系统要在契约里读到：标识只在命令内唯一、五个命令前缀对客户不可见（键是服务端推导的）、回执带 `submissionVersionId`。契约补章归 first-party-api/12。
- 登记指引：五个新词的授予是租户取值（`PAR-INT-13`）；取消口的授权规则是另一件租户取值，不随授予一起登。

## 越权风险点

1. **前缀是产品词，一旦有已存键就不能改。** 今天五口没有已存的来源请求键，现在定最便宜；日后改前缀等于把已登的键全部变成「新请求」，重放会重复办理。
2. **「标识在命令内唯一」靠契约，不靠结构。** 客户系统在同一命令内复用标识换内容，得到的是内容冲突或既有结果，不是静默吞单，但客户可能不解。
3. **直客 1:1 的隔离靠身份构造。** 各口必须钉「他账户的标识答找不到、不泄露存在」；任何一口按裸委托标识（不带账户条件）查找，就破了隔离。取消口尤其：取消命令只有自己的身份与委托标识，应用层今天不核账户，要由 Intake 反查或 PS 补闸（摸底报告 1.2）。
4. **回执的版本标识是「此刻的当前版本」，不是「你提交的那一版」。** 客户拿旧回执去补充，会得到基准过期；这是设计，不是缺陷，但契约要写明。
5. **索赔自然键中的「批次、项」的定义**由 VE 领域给，本记录只定「接入请求标识不是唯一性来源」。若领域日后认为同一（账户、批次、项）允许多笔（如分次赔付），本记录决定六要改。
6. **取消口对没登规则的租户整体不开。** 这是 UC-PS-006 禁默认的直接后果；首个租户上线实施清单必须含「登记取消授权规则」，漏了的表现是取消口答`未配置`，不是出错。
7. **没读的部分。** 各口领域编排全文、UC-PS-002、005、006 与索赔用例原文、`docs/api` 契约稿全文；与它们原文有出入处以原文为准，本记录让位。
