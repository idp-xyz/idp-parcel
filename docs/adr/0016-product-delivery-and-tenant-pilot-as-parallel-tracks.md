# ADR-0016: 产品交付与租户试点作为两条并行验收轨道

Status: Accepted  
Date: 2026-08-07

## Context

本仓的产品文档体系假设读者就是运营企业。[首发试点范围](../product/PILOT-SCOPE.md)写「运营企业向货主客户承担从有效网络收寄到约定终局的网络服务责任」，[参数登记册](../product/PILOT-PARAMETER-REGISTER.md)登记「真实锚点客户、线路、伙伴、合同」，`PN-08` 的正式 `Go/No-Go` 由「责任法人明确指定的试点业务责任角色」作出。

领域模型说的是另一回事。[ADR-0003](./0003-group-tenant-legal-entity-customer-account.md) 与 [`party-commercial`](../domain/party-commercial/CONTEXT.md) 把**运营集团租户**定义为「一个自营国际小包物流企业集团在本产品中的最高业务配置和数据隔离边界」——运营企业是买这套软件的租户，不是开发方。`idp-parcel` 是卖给物流企业的软件产品。

**产品文档跳过了租户这一层**，直接从产品谈到锚点货主客户，而那是租户的客户，与开发方隔着两级。登记册里没有任何一行问「首个租户是谁」。

后果有三处，都不是措辞问题：

- 登记册三十余行 `待提供` 全部挂在一个它从未要求过的前置条件上。价卡是租户与其供应商之间的文件，客户合同是租户与其货主之间的文件，开发方不是任何一方的当事人，因此这些行不可能因开发方的努力变成 `已确认`。
- `PN-01..PN-08` 是唯一路线图，终点 `PN-08` 按定义不由开发方作出。路线图没有可达终点。
- 证据阶梯把 `S` 写成「待升级为 `R`/`P`」。对开发方 `S` 是终态，不是欠缺。

[开发主线](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md)已于同日立了「产品就绪 / 试点就绪」二分，但只给了产品就绪一个定义，没给它路线图位置和判据。定义不带判据就用不上，因此每次遇到参数问题仍会退回「等真实证据」的口径。

## Decision

**产品交付与租户试点是两条并行验收轨道，不是同一条轨道上的先后两段。**

**每个 `PN-*` 切片含机制半边与实例半边。** 机制是规则、判断、版本化、门禁与记录形态，属产品交付；实例是某租户的真实客户、线路、伙伴、参数与阶段决定，属租户上线。划分在切片内部而非切片之间——`PN-01` 的「建立阶段与证据参数」是机制而「固定一个锚点客户」是实例，`PN-08` 的治理记录能力是机制而实际执行回放与作出 `Go/No-Go` 是实例。

**产品交付轨道**的验收对象是能力覆盖，判据三项：骨架完整、受控案例可复算、参数显式未配置。产品就绪 = 八个切片的机制半边全部达标。

**租户试点轨道**的验收对象是真实业务证据，按[验收场景矩阵](../product/PILOT-ACCEPTANCE-MATRIX.md)形成 `P`/`R` 并由 `PN-08` 作出 `Go/No-Go`。主体是租户。

**`PILOT-SCOPE`、`PILOT-ACCEPTANCE-MATRIX`、`PILOT-PARAMETER-REGISTER` 定性为每租户上线模板。** 开发方维护其结构，不填其值；租户出现后按模板逐租户建立实例登记，不在模板里混填。

**证据红线不放松。** 隔离合成 `S` 仍只记为 `S`。「生产通过只来自登记册证据 + `PN-08` `Go`」限定作用对象为**某租户实例进入生产**，不约束产品版本发布。

**两条轨道不互相替代。** 机制达标不使任何租户获准上生产；租户实例为空也不阻塞机制实现。

## Consequences

- 登记册的 `待提供` 不再是缺陷指标，正确读法是「该项在租户上线时必须有真实证据」，空值是模板的正常状态。开发方对它的责任从填值变成审结构：多一行就是多一道租户准入门槛，少一行就是让租户带着缺口上生产。
- 以「待业务方确认」为处置的既有工作单需要重新确定收件人。开发方无法代租户回答的问题只有两条出路——按产品判断自行裁决，或如实结论为取不到；继续挂着等一个不存在的答复不是选项。
- 产品就绪不产生任何生产授权。它支持演示与商务洽谈，不支持任何租户上生产。
- 每引入一个租户就要复制一份实例登记，模板结构变化必须同步到已有实例登记。这是本决定新增的维护成本，随租户数量线性增长。
- 目标客户群一旦放宽，据其成立的能力范围判据结论必须重新评估。该条款已在开发主线，本记录不另设第二处。

## Alternatives considered

- **归档 `PILOT-*` 三份文档，等有租户再重建。** 否决：内容是对的，只有主体标错。`PILOT-SCOPE` 那五十余条描述的是产品必须支持的业务形态——服务形态、责任起点、客户隔离、终局规则——归档会连带丢掉一批已确认的领域约束，代价远大于改主体。
- **把开发方当作假想租户，自己填合成参数。** 否决：合成实例会混进本该只登真实证据的台账，直接违反「证据层级诚实」；且假想租户的参数选择会悄悄变成产品默认值，而那正是能力范围判据要防的事。
- **只承认试点就绪一条轨道，等第一个租户再谈产品验收。** 否决：没有产品就绪谈不下租户，没有租户取不到参数，没有参数不可能试点就绪。这三步互相等待正是本记录要解除的死锁。
- **维持现状，把矛盾当作措辞问题逐处打补丁。** 否决：矛盾在主体而不在措辞，逐处打补丁会让同一件事在多个文档里出现口径略有差异的解释，违反单一权威。
