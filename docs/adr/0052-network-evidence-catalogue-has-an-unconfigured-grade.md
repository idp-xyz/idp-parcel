# ADR-0052: 网络证据端口增设「未配置」格，网络定义登记册的模式属机制半边

Status: Accepted（**部分停用**：Decision 四的第一句「它要能承载……全部事实族」已由 [ADR-0053](./0053-network-fact-families-are-derived-not-registrable.md) 停用——九族是每次判断的推导结果，不可登记；其余各条不变）  
Date: 2026-08-17

## Context

派发组合根卡在发布通道上（[ADR-0049](./0049-publish-channel-is-in-process-delivery-until-load-evidence.md) 已裁定进程内直投），而直投按那份记录不得配着空路由表上线——它必须与首批消费者同批落地。全仓今天只有一个消费者 `nrinbox.AcceptanceConsumer`，接它进组合根要先构造 `CreateInitialRouteHandler`，后者的七个依赖里 `InitialRouteEvidenceView` 没有生产实现。同族的 `NetworkEvidenceView` 与 `AutoRerouteFactsView` 同样没有。

三件事拦在这里，逐条说清楚，因为它们的性质不同：

**一、端口形状说不出「未配置」。** `AutoRerouteFactsView` 有三格（事实、`configured bool`、error），编排也已诚实用它——目录未配置时失效照常落库、改路评估整段不做、三态保持未评估。另外两个只有两格：`(证据, error)`。今天没有租户，网络定义一行都不会有，而这两个端口的调用方只能收到「一份空证据」或「一个错误」：

- 交回空证据，领域会照常评估，得到`无当前有效路由`或候选空间未决——**那是从缺配置里编出一个业务结论**。用例明写`无当前有效路由`、`未决`与`已形成`三者不能合并，而这条路把「没人登记过网络」讲成了「我们判过了，没有路」。
- 交回 error，编排译 `RouteEvidenceUnavailable` 未决——**那是把未配置伪装成依赖故障**，端口注释自己反对相邻的一种混淆（「把技术故障装扮成一个证据缺口」），反向同样成立：运维会去查一个没有坏的依赖。

**二、`network-routing` 没有任何网络定义表。** 六份迁移全是判断与计划侧（可达性判断库、路由判断库、改路耦合、候选状态、计划适用性、交接日志与计划签发）。服务区解析、路由要求、路径可执行性、硬约束发现、候选段链、时间投影、分值、排序准则、策略引用——一张表都没有。所以这不是「补一个适配器」，是先要有一个登记册。

**三、`ports` 包的包注释写着不得先写默认实现**（「其生成、过滤与排序规则属 `PAR-NET-14`，登记册状态待提供，因而不得先写一份默认实现」）。那句话仍然对，本记录不推翻它——它禁的是**替租户拟一份网络定义**。读一个空登记册并如实答「未配置」不是默认实现，恰恰是它想保护的东西。

分歧因此不在「要不要等 `PAR-NET-14`」，而在**机制与实例的切线画在哪里**：登记册的模式、空册的语义、修订标识的派生方式属机制半边（产品怎么表达网络定义），登记册里的行属实例半边（这个租户的网络长什么样）。按[开发主线](../product/PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md)的两半划分，机制现在就做。

## Decision

**一、`NetworkEvidenceView` 与 `InitialRouteEvidenceView` 各增一格 `configured bool`，与 `AutoRerouteFactsView` 同形。** 三格语义固定：事实在场即证据；`configured=false` 即**网络定义登记册对这个判断范围未配置**；error 仍只表示依赖调不通。空登记册一律走第二格，绝不折成空证据。

**二、`未配置`在应用层占自己的未决原因，不与依赖不可用共用一格。** `RouteUndecidedReason` 增设一个专格（与既有 `RouteEvidenceUnavailable`、`RouteCandidateEvidenceIncomplete` 并列）。判据是恢复动作不同：未配置要租户去登记网络定义，依赖不可用要运维去救那个依赖，候选证据不全要补事实。混格会把恢复动作指错，这条纪律在本仓已复现多次。

**三、`未配置`绝不译成`无当前有效路由`。** 后者是领域判断，必须由「全部候选确定性淘汰」得出；前者是「还没人告诉我们网络长什么样」。同理不译`不适用`——那是商业侧对「要不要路由」的回答，属 `RoutingApplicabilityView`。

**四、网络定义登记册的模式属机制半边，本记录圈定它的范围而不定义它的列。** 它要能承载 `NetworkEvidence` 与 `InitialRouteEvidence` 两个结构今天已声明的全部事实族：服务区解析、路由要求、路径可执行性、硬约束发现、候选段链、时间投影与承诺边界、分值、排序准则、策略引用。两条约束现在就定死：

- **修订标识由登记册派生，不由调用方传入。** 端口注释要求「事实与修订一次取回」，理由是两次取回之间视图一变，事实与它标的修订就不再来自同一版；派生方式因此必须在登记册这一侧，且同一次取回的全部事实族共用同一个修订。
- **空册与「登记了一个空集合」是两回事。** 前者是未配置；后者是租户明确声明「这个范围没有服务区」，是业务事实，走第一格。登记册必须能区分这两者，不能靠「查出零行」推断。

**五、逐候选事实的生成、过滤与排序规则仍属 `PAR-NET-14`，本记录一条都不定。** 适配器只按范围取行、不评估、不排序、不补默认——[ADR-0046](./0046-route-candidate-evaluation-lives-in-the-domain.md) 把评估判给领域，本记录不动那条线。

## Consequences

- `nrinbox.AcceptanceConsumer` 的依赖闭包可以被真实实现填满，派发组合根因此具备「与首批消费者同批落地」的前提。这是本记录要解的那把锁。
- 两个端口的签名改动会波及 `CreateInitialRouteHandler`、`AssessParcelReachability` 与它们的测试替身。属「会让旧调用点对不上」那一类，按[并行会话](../agents/parallel-sessions.md)的做法在频道先说一声，或走三步法。
- `ports` 包注释里那句「不得先写一份默认实现」保留，但要补一句本记录的分界：读空册答未配置不是默认实现。
- 首发路径因此稳定停在**未配置**：没有租户就没有网络定义，逐包裹结果是带专格原因的未决，而不是一个看起来判过了的`无当前有效路由`。这是本记录最想守住的东西。
- 登记册模式本身仍要一份设计与迁移，本记录只圈范围，不替它拍列。

## Alternatives considered

- **交回空证据，让领域照常评估。** 否决：见 Context 一。它把缺配置讲成业务结论，且不可分辨——事后没有任何东西能把这次`无当前有效路由`与一次真的判过区分开。
- **交回 error，复用 `RouteEvidenceUnavailable`。** 否决：同上。它把恢复动作指向运维，而该做事的是租户；且依赖健康度指标会被一个没坏的依赖污染。
- **换一个依赖闭包更浅的消费者作为首批，绕开 NR。** 未否决，是一条**并行**的路：它能更早接通派发，但不解决本记录的问题——NR 证据视图迟早要做，而形状问题不会因为绕开而消失。两者可以分别推进。
- **等 `PAR-NET-14` 落地再一次做完。** 否决：那是实例半边，租户数为零时无从取得；而端口形状、空册语义与修订派生都是机制半边，等它等的是一件不会到来的事。
- **给两个端口各造一个「空网络」的默认适配器。** 否决：这正是 `ports` 包注释所禁，也是本记录 Decision 四第二条要区分的两件事。
