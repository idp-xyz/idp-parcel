# 代收与清分（`collection-remittance`）

Status: Confirmed

本上下文管理运营企业受客户委托、由承运或渠道向收件人代收的货款本金，从代收义务成立、实收事实接受、受托保管账记账、周期归集到汇付客户的全过程。它回答“这笔代收款属于谁、现在在什么位置、还差多少、什么时候以什么依据付给了客户”。

**代收款是客户的钱，不是运营企业的收入。** 本上下文的全部账面都是受托保管口径：代收本金不是经营口径物流收入、不是客户预付余额、也不是普通运营结算余额。COD 服务费与有效协议允许的运费抵扣属 `settlement-accounting`，它们是运营企业自己的钱，与本上下文的本金分账并存，不在本上下文内相互净额。

本上下文不建支付通道集成，也不拥有银行流水、支付清算、总账与法定会计余额。汇率、回汇周期与手续费属运营企业的商业与实例参数，不由本上下文的机制预设。

本文件是 `collection-remittance` 语言、规则与生命周期的权威来源。跨上下文术语以[统一领域语言](../GLOSSARY.md)为准，所有权关系以[领域上下文地图](../CONTEXT-MAP.md)为准。本上下文还没有 UC，规则与实现的差距见文末「给开发的交接」。

## Language

**代收指令**
依据客户代收服务要求，对明确包裹范围成立的一项代收资金义务：应向收件人收取的金额、币种、承担该义务的责任法人、受托保管的货主客户与执行代收的渠道。客户代收服务要求快照由 `parcel-shipment` 拥有，代收指令只引用它并声明本上下文据以记账的义务边界。代收指令不是收款事实，也不是已确认的应付客户款。

**代收事实**
一次已被本上下文接受的收款主张或资金事实，携带金额、币种、发生时间、来源层级与来源证据引用。**四个来源层级彼此独立、不得互相推导**：收件人付款（来自 `transport-fulfillment` 的履约侧代收证据）、渠道代收报告、渠道回款通知、运营企业真实到账。交付证明不证明代收款已收取；渠道报告已代收不等于渠道已回款；渠道已通知回款不等于运营企业真实到账。

**代收分户账**
按（货主客户，责任法人，币种，代收渠道）隔离的一本受托保管账。四维齐备才构成一本账：少任何一维都会让两笔本不该混的钱记进同一个余额，而事后按更细的维再拆分需要重演全部历史。分户账不持有可改写的余额字段——余额是分户账记账的派生结果。

**资金位置**
代收本金在分户账内所处的受托状态，封闭词表：`渠道在途`（渠道已代收但尚未回到运营企业）、`待清分`（资金已回但归属尚未落到具体客户应付）、`应付客户`（已可汇付给客户）、`已汇付`（已依回汇批次付出）、`短款`（渠道已报告代收、真实到账没到、经差异事项确认的那部分本金，只从`渠道在途`落入）、`溢款`（实收多于指令、经差异事项确认的那部分已到账本金，只从`待清分`落入）。外部来源不是资金位置，它只作为入账记账的来源侧出现。

**分户账记账**
在一本分户账内追加的一条不可覆盖记录：一笔正金额自一个来源位置移到一个去向位置，并携带依据种类与依据引用。记账只追加，不修改也不删除；账内位置之间写错走反向记账冲正，原记账原样留在账上，入账不能冲正（见「分户账与记账」一节）。各资金位置的余额由记账派生。

**分配守恒**
一本分户账内，全部非外部资金位置的余额之和恒等于自外部来源入账的金额之和。它由记账的形状交付——每一笔记账同时从来源位置扣、往去向位置加，金额不在记账过程中产生或消失。任何一次清分、汇付或差异确认都不得凭空创造或蒸发本金。

**回汇批次**
一次周期归集与汇付主张：把某一本分户账在归集截点前已处于`应付客户`的本金归为一批，形成对该客户的一次汇付。批次一经形成即冻结分户账键、币种与归集截点；成员只通过引用该批次的汇付记账体现，批次不另持第二份成员清单。批次不接受删除、重开或改写，改变走新批次。回汇周期、汇付通道与手续费不由本上下文决定。

**差异事项**
实收与代收指令不一致时登记的待处置事项：短款或溢款，携带金额、币种、观察时间与依据引用。差异事项是需要处置的声明，不是自动冲销——它不改写代收指令，也不自行把差额记进任何资金位置；落账要另有一笔带该差异事项为依据的分户账记账。差额从没进过账的（渠道报告本身就少于指令的那部分），只记在事项上，不记账。

**汇付主张**
本上下文对外表达“这批本金应当付给该客户”的结果。它不是真实付款：付款执行、银行清算与到账事实由外部支付与银行系统拥有，本上下文只登记主张及其依据，并等待相应的真实资金事实回来。

## Rules and invariants

### 代收义务与实收事实

- 代收指令必须引用客户代收服务要求依据，并同时给出金额、币种、责任法人、货主客户与代收渠道；缺任何一格都不得以默认值补齐后落册。
- 代收事实必须声明自己属于哪一个来源层级并携带来源证据引用。收件人付款、渠道代收报告、渠道回款通知与运营企业真实到账分别保存，任何一层都不得被另一层覆盖，也不得由另一层直接推导成立。
- 有效交付结果与交付证明都不能替代代收事实。没有已接受的代收事实时，代收指令的应收状态保持未实收，不得按已交付推定已代收。
- 代收事实追加式登记且不可覆盖。来源侧更正或撤销时追加新的事实并关联原事实，原事实与原判断继续保留。
- 同一笔代收事实不得重复入账。重放同一份登记只交回“已在册”，同键异内容一律冲突而不覆盖。

### 分户账与记账

- 分户账键四维（货主客户，责任法人，币种，代收渠道）齐备且不为空。不同客户、不同责任法人、不同币种或不同代收渠道的本金不得记入同一本分户账。
- 币种在分户账键上，因此一本账内不发生换算。跨币种的关系通过分别成立的两本分户账加外部换算依据表达，本上下文不持有汇率也不做折算。
- 记账只追加。任何已落账的记账都不得被修改或删除；账内位置之间的更正通过追加反向记账表达，原记账及其依据原样保留。
- 入账不能冲正：去向侧没有账外位置，反向那一笔落不下来。来源侧记错只追加更正事实并关联原事实，那笔本金如何退出账面待真实的渠道退款与银行退回形态到来时另裁（[ADR-0082](../../adr/0082-collection-subledger-is-keyed-by-four-dimensions-and-posted-append-only.md) Consequences）。
- 每一笔记账金额为正，来源位置与去向位置不同，且两侧同属一本分户账。金额、位置、依据种类与依据引用缺一不得落账。
- 代收本金只凭已接受的渠道代收报告自外部来源入账：入`渠道在途`，金额等于报告金额，一条报告至多一笔。收件人付款与渠道回款通知是旁证，登记为代收事实、不记账。没有已接受的渠道代收报告就没有本金，账上不得出现无来源的金额（[ADR-0271](../../adr/0271-collection-principal-enters-the-ledger-only-on-the-channel-collection-report-and-shortfall-comes-only-from-in-transit.md)）。
- 凭代收事实的记账按依据判重：同一条事实至多支撑一笔记账，同一记账标识重放答已有结果，换一个记账标识再凭同一条事实记账是内容冲突，不记账。
- 任一资金位置的余额不得为负。清分、汇付与差异确认都以“当前该位置余额足够”为前提；不足时判断停在待处置，不得透支后再补。
- 分配守恒在每一笔记账后仍然成立。任何写入路径都不得绕过记账直接改动余额。

### 清分、汇付与差异

- 未实际收到的代收款不得进入`待清分`、`应付客户`、`溢款`或`已汇付`。渠道代收报告只支持本金停在`渠道在途`；只有已接受的运营企业真实到账事实才支持把`渠道在途`移到`待清分`，金额等于到账金额、一条到账至多一笔。`渠道在途`不够移时停在余额不足，等对应的渠道代收报告入账，不先凭到账入账、事后再补报告（[ADR-0271](../../adr/0271-collection-principal-enters-the-ledger-only-on-the-channel-collection-report-and-shortfall-comes-only-from-in-transit.md)）。
- 汇付记账必须引用一个已形成的回汇批次，且该批次的分户账键与币种与记账所在分户账一致。没有批次依据的资金不得进入`已汇付`。
- 回汇批次的分户账键、币种与归集截点在形成时冻结，此后不接受改写；批次不得删除、不得重开。归集范围需要改变时形成新批次，原批次及其成员记账继续有效。
- 汇付主张不等于真实付款。批次形成、汇付主张交出、外部付款执行与客户真实收到是四件分别记录的事，本上下文只拥有前两件。
- 实收与指令不一致时登记差异事项。短款不得通过缩小代收指令抹平，溢款不得直接计入应付客户款；两者都要先有差异事项，再由一笔以该事项为依据的记账把差额落到`短款`或`溢款`。`短款`只从`渠道在途`落入，`待清分`、`应付客户`里已到账或已归属客户的本金不得落入`短款`；报告本身就少于指令的那部分没进过账，只记在差异事项上。`溢款`只从`待清分`落入，渠道多报而钱还没到的部分留在`渠道在途`（[ADR-0271](../../adr/0271-collection-principal-enters-the-ledger-only-on-the-channel-collection-report-and-shortfall-comes-only-from-in-transit.md)）。
- 代收本金不得与 COD 服务费、运费或其他运营应收在本上下文内相互净额。抵扣只能依据 `settlement-accounting` 拥有的、有效协议允许的抵扣金额，通过明确记账依据表达，且抵扣后的组成仍然可逐笔追溯。

### 与结算的分界

- 本上下文拥有代收本金及其汇付；`settlement-accounting` 拥有 COD 服务费、有效协议允许的抵扣金额、运营应收应付与经营核算。两边不共享表，只以引用交接。
- 代收本金不计入经营口径物流收入，也不进入普通运营结算余额；`settlement-accounting` 的结算账户余额与本上下文的分户账余额是两个不同口径的量，不得合并展示为一个“客户余额”。
- 本上下文不形成、不修改、也不重新解释客户合同、客户代收服务要求、包裹身份与履约侧原始收款证据。它引用这些依据并保存实际采用的引用，不回写来源。

## Lifecycles

### 代收指令

- 客户代收服务要求成立 → 登记代收指令：固定金额、币种、责任法人、货主客户与代收渠道，并保存所引用的要求依据。
- 代收指令在册 → 实收事实陆续接受：指令本身不随实收改变，应收与已收之差由分户账与差异事项表达。
- 服务要求在来源侧变化 → 登记新的代收指令并关联原指令；原指令与已依它形成的记账继续有效，不被覆盖。

### 代收事实与入账

- 收到来源证据 → 登记代收事实：声明来源层级、金额、币种、发生时间与证据引用。
- 渠道代收报告已接受 → 入账记账：自外部来源移入`渠道在途`，金额等于报告金额，依据引用指向该事实。收件人付款与渠道回款通知已接受，只留在册上，不记账。
- 运营企业真实到账已接受 → 移位记账：`渠道在途` → `待清分`，见「分户账资金位置」一节。
- 来源侧更正或撤销 → 追加更正事实并关联原事实；原事实与原记账原样保留。依原事实形成的账内移位走反向记账冲正，入账不能冲正（「分户账与记账」一节），当前余额由全部记账重新派生。

### 分户账资金位置

- `渠道在途` → `待清分`：运营企业真实到账事实已接受，金额等于到账金额，一条到账至多一笔；`渠道在途`不够时停在余额不足。
- `待清分` → `应付客户`：本金归属已落到具体货主客户，且对应的代收指令范围明确。
- `渠道在途` → `短款`：差异事项已登记且短款结论已确认，金额等于事项金额。`待清分`与`应付客户`不落入`短款`。
- `待清分` → `溢款`：差异事项已登记且溢款结论已确认，金额等于事项金额。
- `溢款` → `应付客户`：溢款的归属经差异事项处置后确认属该客户。
- `应付客户` → `已汇付`：引用一个已形成的回汇批次完成汇付记账。
- 账内位置之间的错记 → 反向记账冲正；位置余额随之回退，原记账不消失。入账不在此列。

### 回汇批次

- 形成批次：固定分户账键、币种与归集截点；此时批次尚无成员。
- 批次已形成 → 汇付记账逐笔引用它：成员集合只增不改，每一笔都受分配守恒与余额非负约束。
- 批次已形成 → 交出汇付主张：主张交出后仍不等于付款成立，外部付款与到账由外部系统拥有。
- 归集范围需要改变 → 形成新批次；原批次不重开、不删除、不改写。

### 差异事项

- 观察到实收与指令不一致 → 登记差异事项（短款或溢款），携带金额、币种、观察时间与依据。
- 差异事项在册 → 处置结论形成 → 以该事项为依据追加记账，把差额落到`短款`（自`渠道在途`）或`溢款`（自`待清分`）；差额从没进过账的只留在事项上。
- 差异事项被更正 → 登记新的事项并关联原事项；已依原事项形成的记账走反向记账冲正，不被删除。短款确认之后渠道补付的，先这样冲正短款那一笔回到`渠道在途`，再凭新的真实到账移位。

## Boundaries and ownership

- `collection-remittance` 拥有代收指令、代收事实的接受判断、代收分户账及其全部记账、资金位置余额的派生、回汇批次、汇付主张与差异事项。
- `parcel-shipment` 拥有包裹身份与客户代收服务要求快照；本上下文引用它们建立代收指令，不修改要求内容，也不取得包裹身份。
- `transport-fulfillment` 拥有履约侧代收证据、渠道代收报告与渠道回款通知；本上下文引用它们形成代收事实，但这些来源都不等于运营企业真实到账，本上下文也不改写履约侧证据。
- `party-commercial` 拥有客户合同、代收商业责任与结算约束的版本；本上下文保存实际采用的依据引用，不选择也不修改商业版本。
- `settlement-accounting` 拥有 COD 服务费、有效协议允许的抵扣金额、运营应收应付、结算账户与经营指标；本上下文拥有代收本金与汇付。两边不共享表，通过引用交接，且不得把未实际收到的代收款提前确认为可付客户余额。
- 银行、支付与财务系统拥有真实付款、清算、总账与法定会计余额；本上下文只登记汇付主张与已接受的资金事实引用，不与外部系统共同维护一个可覆盖余额。
- 汇率、回汇周期、手续费与支付通道属运营企业的商业与实例参数。本上下文的机制不内置任何默认值，未提供时相应判断停在未配置，不以零值或当前时间兜底。
