# 小包托运（`parcel-shipment`）

Status: Confirmed

本上下文管理客户委托、包裹身份与组成、委托接受基线、客户资料快照、面单交易、面单继续尝试决定、外部标识关系和客户承诺生命周期。它保存服务请求及身份连续性，但不拥有节点作业、实际运输、正式关务申报、全程追踪投影或最终结算结果。

本文件是 `parcel-shipment` 语言、规则与生命周期的权威来源。跨上下文术语以[统一领域语言](../GLOSSARY.md)为准，所有权关系以[领域上下文地图](../CONTEXT-MAP.md)为准。

## Language

**提交批次**  
客户一次提交或导入多份委托的处理归组。提交批次可以包含不同收件人、服务产品或责任范围的委托，但不取得这些委托的服务责任，也不成为一个多包裹委托。

**委托**  
客户要求运营企业为一个或多个包裹提供同一项约定国际小包服务的业务请求。同一委托中的包裹共享客户账户、合同责任法人、合同与服务产品依据、寄收件关系和目的服务范围。

**委托提交版本**  
委托在尚未形成接受或拒绝决定期间，对客户当前请求内容形成的不可覆盖版本。纠错或补充可以在同一委托下形成新的提交版本，但原版本、成员、原因、提交主体和判断历史必须保留；同一委托同一时刻只有一个待判断的当前提交版本。

**委托接受**  
运营企业在客户提交后，完成商业有效性、服务适用性、必要资料和成员基线校验，并明确同意承担该服务请求的业务决定。数据到达、批量导入或实物收寄本身都不等于委托接受。

**接受判断任务**  
针对一份已提交委托及其当前提交版本形成的、可追溯并可续办的接受判断工作。它记录判断阶段、尚缺的权威结果、采用版本、最近处理结果和续办关系，但不是委托的新领域状态；任务未完成时委托仍为`已提交`。

**接受前财务控制采用结果**  
本上下文对一次接受前财务控制所保留的采用引用：`settlement-accounting` 交回的逐项控制项结果、策略声明的共同通过条件，以及本上下文按该条件形成的接受侧结论——成立、业务限制，或合同明确无控制（带商业不适用依据）。结论只从逐项结果按条件形成，不由提供方交入；「执行了哪些控制、各自成不成立」以逐项结果为准，结论只答按条件成没成立。本上下文只记引用与结论，不拥有冻结、信用暴露或金额。

**控制项结果**  
接受前财务控制采用结果中的一项：策略正文里一项控制（预付冻结或信用校验）执行后的结论——成立，或带该项自身原因的业务限制——连同它在策略里的判断顺序。任一项成立即表示提供方账本上形成了占用；接受确定未成立时必须按原业务关联请求释放，不论接受侧结论如何。未执行的项不是一项结果，本上下文不记它。

**委托撤回**  
客户或其当前有效授权代表在委托尚未形成接受或拒绝决定时，明确终止整份待决服务请求的业务决定。撤回不是运营企业拒绝，也不删除原始提交、提交版本、判断历史或已经形成的财务控制结果。

**委托接受基线**  
委托接受时形成的不可覆盖快照，记录客户声明的包裹成员、客户与责任法人、合同与服务产品、寄收件资料、服务要求以及适用商业依据。后续取消、更正或物理身份演化不能改写该基线。

**客户原始资料**  
客户对寄件人、收件人、货物、申报和服务要求作出的声明性来源资料。它是 `parcel-shipment` 保存的客户来源，不等于节点实测、正式申报资料、监管结果或最终计费资料。

**保价要求**  
客户在服务要求中声明的一项可选服务要求：要求对明确包裹按其声明价值保价，包含声明价值与币种。它是客户声明的事实，随客户原始资料版本演进；运营企业不采纳或改写这个值，只在委托接受时依适用的保价条件判断它能否受理，并把要求与所依据的保价条件引用一并固定进委托接受基线。保价要求不是保费、不是赔付金额、不是保险单，也不等于运营企业向保险方投保。

**客户原始资料版本**  
针对明确委托、包裹、字段或资料范围形成的不可覆盖客户来源版本。版本保留原始请求、基础版本、补充/更正原因、对象范围、来源、业务时间和适用关系；新版本不删除或覆盖旧版本。

**资料补充/更正请求**  
客户或授权运营角色请求形成客户原始资料新版本的业务请求。请求意图不是资料事实，必须与目标范围、请求方、授权和基础版本分别记录。

**资料修订阶段**  
一份已接受委托或其包裹在资料补充/更正请求到达时所处的生命周期位置，是判断「此刻允许改什么」的维度之一。封闭六格：已接受尚未收寄、已收寄或已测量、已制签或已装袋、关务资料形成中尚未提交、已提交关务、案件已关闭或服务已完成；多格事实同时成立时以靠后的一格为准，作用于整份委托的范围取其成员中最靠后的一格。阶段由 `parcel-shipment` 按自有事实（接受基线、有效网络收寄采用、面单交易包裹结果、终局服务结果）与邻接上下文交出的事实（`node-operations` 的装袋，`customs-compliance` 的申报资料形成、提交与案件关闭）判断；任一所需事实不可知时判断不成，修订请求停在未决，不得默认为最早阶段。允许什么由所采用接单规则包版本的资料修订允许声明说，本上下文不自带矩阵。

**来源发生时间（`occurredAt`）**  
来源方声明请求或事件发生的时间。它属于来源信封元数据，用于溯源、迟到和因果判断，不进入规范化业务内容摘要；不同值不能单独把同一请求分类为冲突。

**系统接收时间（`receivedAt`）**  
本系统实际收到来源请求的时间。它属于本地观察和审计元数据，用于重试、迟到和处理顺序分析，不进入规范化业务内容摘要；每次重试可以不同，不能单独把同一请求分类为冲突。

**客户请求生效时间（`requestEffectiveAt`）**  
客户声明请求在何时具有业务适用性。它属于规范化业务内容；其值以及缺失或显式存在的状态必须进入 `PayloadDigest`。它不能由 `occurredAt` 或 `receivedAt` 默认补齐。

**规范化业务内容摘要（`PayloadDigest`）**  
对规范化后的客户请求内容形成的稳定摘要，覆盖成员、范围、基础版本、服务要求以及 `requestEffectiveAt` 的值/存在状态，不覆盖 `occurredAt` 或 `receivedAt`。它用于同一来源身份下的重放与冲突分类。

**来源请求身份**  
由租户、客户账户、来源和来源请求键组成的完整复合身份。它只用于来源重放与冲突分类，不授予查询或操作权限，也不能替代委托、包裹或其他业务身份。

**授权查询作用域**  
由共享身份认证/授权技术能力已经判断并传入的可见范围引用。`parcel-shipment` 消费该引用并按自身对象边界过滤结果，不拥有企业身份主数据、凭据验证或通用授权策略。

**统一不可见结果**  
对象不存在、对象在其他租户/客户范围内或调用者未获授权时，对外使用同一不可见语义，不暴露对象存在、内容、范围、客户或冲突状态。

**当前客户资料版本采用判断**  
依据客户原始资料版本、来源更正/撤销关系、对象范围、业务有效时间和并发顺序派生的当前消费引用。它可以表示已采用、待补充、冲突或未决，不是可手工覆盖的全局资料状态。

**收件地点引用**  
本上下文为一份已接受委托的收件资料范围对外交出的复合引用，由租户、委托、收件资料范围与资料版本锚四段组成；锚是接受基线（该范围上尚无修订版本）或当前采用的那份客户原始资料版本。消费方（如 `transport-fulfillment` 的派送任务）落「地点」一格只用它，地址本体留在本上下文，持引用方按引用向本上下文取。它不是地址文本、不是目的地节点，也不另立地点身份——收件地址的版本就是客户原始资料版本，引用只指向它；引用一经交出含义不变，旧锚永远解析到那一版内容。
_Avoid in this context_: 目的地节点、派送地址、地点 ID

**包裹**  
在小包网络中具有独立身份并可被分别收寄、跟踪、处理和形成服务结果的物理服务件。包裹不是委托行、面单交易、外部号码或集运单元。

**包裹身份谱系**  
真实物理拆分、合并或其他身份替代形成的新旧包裹来源关系。谱系保留原包裹和新包裹的永久身份、变化原因、发生依据和适用时间。

**当前有效包裹**  
在包裹身份谱系中仍代表当前服务件身份、尚未被后续拆分或合并结果替代的包裹。在适用取消边界前形成取消结果不会删除该身份；委托完成按当前有效包裹的终局服务结果汇总，被替代的来源包裹不得重复计数。

**面单交易**  
通过明确渠道账号、合同和服务条件向渠道服务方发起的一次渠道业务请求及其责任结果。一笔面单交易可以覆盖一个或多个明确包裹；一个包裹也可以因失败、作废或换单先后关联多笔交易。

**面单交易包裹结果**  
一笔多包裹面单交易对其中某个明确包裹形成的业务结果，包括该包裹是否被受理、取得的包裹级标识及适用渠道作废、替代或渠道退款结果。它不能由整笔交易结果或其他包裹结果推断。

**面单交易定案**  
面单交易级及其相关包裹级的受理、失败和面单当前适用性结果已经明确，不再处于结果待确认状态。成功且仍有效的面单交易可以已经定案，但会继续阻止受控关闭路径形成终局；渠道退款、对账、运营结算和法定财务处理不属于交易定案条件。

**面单继续尝试决定**  
针对明确包裹当前完整面单服务范围形成的追加式、版本化业务决定，用于控制未来是否允许发起新的面单重试、替代或换单。受控关闭决定必须固定生效时间、权威业务截断边界、原因、请求方（如有）、实际决定方、关闭责任来源、授权角色和授权依据快照；重开决定必须填写原因、关联此前关闭并且只面向未来生效。登录操作人可以作为操作证据，但不能替代实际决定方和授权角色。

**权威业务截断边界**  
`parcel-shipment` 在受控关闭生效时形成的稳定领域边界，用于将面单交易建立决定与关闭决定排出明确、可审计的前后关系。生效时间表达关闭在业务上从何时适用，截断边界裁决并发的新尝试是否合法；客户端时间、消息到达时间、数据库写入时间或外部墙钟均不能单独替代该边界。

**外部标识**  
由外部参与方分配、用于标识明确业务对象的号码或代码。外部标识必须记录标识类型、分配方、被标识对象、适用范围和替代关系，不能全部解释为包裹的“当前运单号”。

**责任起点**  
依据服务产品和客户合同，使明确包裹进入适用服务责任阶段的业务边界。网络服务以有效网络收寄结果及适用资格校验为依据；客户送达节点时由 `node-operations` 提供节点收寄结果，上门揽收或场外接货时由 `transport-fulfillment` 提供揽收交接结果。面单渠道服务以渠道确认受理面单交易及适用资格校验形成面单交易责任，但不产生运营企业实物控制，运输观察仍从实际承运商收寄事实开始。

**面单服务终局边界**  
由适用服务产品和客户合同定义的、使面单渠道服务包裹从可取消服务阶段进入非取消终局结果的业务边界。渠道确认受理、面单文件返回和正式承诺生效本身不默认构成该边界；允许实际承运商收寄前取消的产品，其终局边界不得早于约定取消权结束。

**终局服务结果**  
依据适用服务产品和客户合同，表明运营企业对明确包裹承担的本次服务责任已经形成最终业务结果。网络服务和面单渠道服务可以具有不同终局结果，实际交付不是所有服务形态的统一完成条件。

**包裹取消决定**  
针对已接受委托中的明确包裹，在其适用取消边界前由有权主体形成的终止该包裹服务决定。取消保留包裹身份、接受基线、请求、授权和既有交易或作业历史，并以取消结果参与委托汇总。

**收寄后服务处置决定**  
包裹越过适用取消边界后，针对继续、拦截、改送、退运、服务终止或其他后续责任形成的明确业务决定。该决定必须固定对象、目的、决定来源、实际决定方、授权、原因、生效时间和责任范围；它不等于执行已经发生，也不直接形成包裹终局服务结果。

**委托完成**  
固定服务范围内所有当前有效包裹均已形成终局服务结果后派生的委托汇总结论。委托完成不代表异常案件、客户索赔、供应商追偿、运营结算或法定财务处理已经关闭。

## Rules and invariants

- 委托是多件服务请求，不是提交批次、集运单元、总单、舱单或结算批次；批量提交不同收件人或不同服务的包裹时，必须形成各自的委托。
- 提交批次只能在同一集团租户内形成处理归组，可以包含不同客户账户的委托，但客户可见回执和查询必须继续隔离。批次内委托业务身份按租户、客户账户和委托标识区分；来源请求身份只负责来源重放与冲突，不能使同一客户下重复的委托业务身份合法化。
- 来源请求身份必须按租户、客户账户、来源和来源请求键整体比较；相同外部键跨任一作用域段均不得复用来源、重放结果或归属结果。同一客户账户下不同来源仍须按完整来源身份隔离，查询不得省略来源后回退到另一条记录。
- 查询只消费共享身份/授权能力传入的授权查询作用域；未授权、越权和不存在对外返回统一不可见结果。合成日志和证据索引只保留作用域引用、对象引用、结果类别、版本、判断时间和证据索引，不记录客户原文或其他租户内容。
- 同一委托中的包裹必须共享客户账户、合同责任法人、合同与服务产品依据、寄收件关系和目的服务范围。具体渠道、实际承运商、路由和实际结果可以按包裹不同。
- 客户提交与委托接受是两个业务事件。只有商业关系与服务产品有效、必要资料和包裹成员基线满足接受条件时，才能形成明确接受决定。
- 每份已提交委托必须针对当前提交版本形成或续办独立的接受判断任务。依赖不可用、权威判断尚未形成、并发冲突或可恢复处理失败时，任务保持未决，委托保持`已提交`；技术或依赖未决不得伪装成业务拒绝。
- 客户可补充的资料缺口、系统内部查询或重试、规则要求的人工复核、运营企业尚未登记的适用参数必须使用不同原因和续办路径。四者的续办方分别是客户、系统、授权复核角色和运营企业的登记动作，合并其中任意两者都会让等待对象弄错——内部重试推进不了一次人工复核，不该因为依赖抖动去催客户补件，而对着一个从未登记过的参数重试，等的是一件重试永远产不出的东西。只有适用服务产品或客户合同的版本化规则明确规定补充期限及届满后果时，届满复核才可以形成确定性拒绝；否则只能保持未决或交由授权角色处置。
- 当前适用的版本化硬规则、商业限制和所需权威判断全部通过时，系统自动形成接受决定；只有适用规则显式要求人工业务判断时才进入人工复核。人工处理不得绕过硬规则或把缺少的权威结果改成通过。
- 运营企业主动拒绝尚未接受的委托时，必须由适用责任法人授权的业务角色形成，并保存结构化原因、证据、适用范围、授权依据、实际决定方和决定时间。普通备注、口头意见或未经授权的操作不能形成拒绝事实。
- 主动拒绝不为全部委托增加人工等待窗口，只能在委托仍为`已提交`时与自动接受竞争同一个决定提交边界。当前提交版本只能有一个合法决定；接受或拒绝提交后，另一方只能读取既有结果，不能追加相反决定。
- 客户撤回只能作用于仍为`已提交`且尚无接受或拒绝决定的整份委托。撤回、接受和拒绝竞争同一个不可覆盖决定边界；已经合法提交的首个决定获胜，后来到达的请求只能读取既有结果或转入相应后续用例。
- 委托撤回不能伪装成运营企业拒绝，也不能删除来源或判断历史。已经形成的接受前资金冻结必须通过原业务关联请求 `settlement-accounting` 显式释放；撤回提交和释放属于可补偿编排，不要求跨上下文分布式事务。
- 一份委托的当前提交版本只形成一个委托级接受或拒绝决定，不支持成员级部分接受。任一成员确定性不满足接受条件时，整份当前提交版本不能接受；不得静默删除失败成员后接受其余成员，也不得先部分接受再补做拆分。
- 接受决定前，普通资料纠错或补充在同一委托下形成新的提交版本并重新判断；删除、拆分、重组成员，或者改变客户账户、合同责任范围、寄收件关系或目的服务范围时，必须形成一份或多份关联新委托并保留原成员去向。已拒绝后的修正建立关联新委托，不把终局拒绝原地重开；已接受后的更正、变更、取消或新增服务件进入各自独立用例。
- 接受校验必须按服务产品、客户合同、责任法人、服务或关务范围和有效期装配版本化规则，并保存实际采用的规则、输入事实版本和结构化结果。接入渠道字段和外部错误只能映射为稳定业务语义及来源证据，不能成为永久领域规则；正式关务判断仍由 `customs-compliance` 拥有。
- 适用客户合同必须提供版本化接受前财务控制策略。`parcel-shipment` 只采用预付冻结、信用校验、明确无控制或合同明确组合所形成的权威结果与依据，不拥有价格、余额、冻结或信用暴露；任何必需结果无法确定时保持`已提交`，不得按默认放行处理。
- 接单分别保存来源发生时间（`occurredAt`）、系统接收时间（`receivedAt`）、客户请求生效时间（`requestEffectiveAt`）、判断依据时点和接受或拒绝决定时间。前两者是来源信封元数据，不进入 `PayloadDigest`，不建立 `occurredAt <= receivedAt` 硬约束，也不能单独造成接入冲突；`requestEffectiveAt` 及其缺失/显式存在状态属于规范化业务内容并进入摘要，可以参与服务日历和可达性判断，但不能通过回填恢复已经失效的商业资格。取得本产品生产归属并建立委托后，`parcel-shipment` 必须依据所采用接单规则包的版本化时点策略，为当前提交版本逐项解析接受判断的 `asOf` 语义和值；各权威判断上下文必须校验并回显实际采用值，不能用一个全局时间替代不同判断的时点语义。
- 接受或拒绝提交前，所有关键判断必须仍覆盖其声明的判断依据时点，且没有被当前有效限制、替代版本或并发决定推翻。依据失效时必须重新判断，暂时无法完成时保持未决；已经合法提交的决定不因后续规则变化被静默改写。
- 委托接受时至少包含一个客户声明包裹，并固定委托接受基线、预计承诺以及适用的产品、合同、映射和授权依据；后续变化不得静默覆盖这些历史。
- 草稿阶段可以增删声明包裹。委托接受后，客户不得自由删除或追加成员；对已有包裹只能请求取消或停止服务，并通过包裹取消或收寄后服务处置表达，新增服务件形成关联的新委托。
- 委托接受后，客户原始资料补充或更正必须通过受控请求形成新的客户原始资料版本；请求、版本和当前资料采用判断分开保存。接受基线、旧资料版本和下游正式资料不得被覆盖。
- 接受后资料版本必须明确关联委托、包裹、字段或资料范围、基础版本、原因、请求方、实际决定方、授权快照和业务/适用时间。省略字段表示不变，显式清空必须由版本化字段和阶段规则允许。
- 接受后不得以资料更正方式新增或删除委托成员，也不得改变客户账户、责任法人、合同、服务产品、寄收件共享关系、目的服务范围或包裹身份；这些变化进入取消、身份谱系或关联新委托路径。
- 客户原始资料、节点实测、正式申报资料和结算资料具有不同来源与所有权。客户版本可以触发其他上下文重新判断，但不能覆盖节点实测、实际作业、监管事实、正式申报、提交版本或最终金额。
- 已收寄、制签、装袋、运输、申报、提交、案件关闭或服务完成后收到的客户更正仍只形成新来源版本；是否换单、重包、改路、重新申报、后续案件或费用调整由相应上下文另行决定，不由本上下文自动完成。
- 同一完整来源请求身份（租户、客户账户、来源、来源请求键）与相同规范化内容摘要返回已有结果；同一身份携带不同内容、范围、基础版本或 `requestEffectiveAt`（包括缺失与显式存在的差异）形成冲突。`occurredAt` 或 `receivedAt` 变化即使跨越不同时间也仍是重放，只能追加本次观察；过期基础版本与当前版本重叠时不得按最后到达覆盖；迟到版本按业务/适用时间重新派生，不倒改历史。
- 客户资料更正与内部合规限制、监管放行、节点安全限制、异常关闭和案件关闭分别判断；资料版本不自动解除限制、恢复就绪、形成放行或重开案件。
- 委托接受基线冻结的是客户声明的服务范围，不禁止真实物理事实形成身份谱系。物理拆分或合并必须由明确来源事实触发，不能成为接受后任意加件的通道。
- 每个包裹独立判断适用服务责任起点、正式承诺和终局服务结果。取消或依据适用终局规则形成的包裹级失败结果可以在责任起点或正式承诺尚未形成时成为终局，单笔面单交易的包裹级失败不在此列；不能强制所有终局路径经过同一状态链。一个包裹未到件、被取消或发生异常，不自动阻塞同委托中已经满足条件的其他包裹。
- 多包裹面单交易可以具有共同交易结果，也必须分别保存每个包裹的业务结果；部分成功、部分失败或不同作废范围不得压缩成一个无法解释的通用状态。
- 面单交易成功、面单文件返回和面单服务正式承诺生效只表示渠道交易责任已经形成，不自动构成包裹终局服务结果；面单服务终局边界必须来自适用服务产品和客户合同。
- 服务产品不得同时承诺“实际承运商收寄前可取消”并把更早发生的渠道受理或面单返回定义为不可回退终局；终局边界与取消权发生冲突时不得接受该产品配置。
- 首个面单渠道服务产品默认跨同一包裹的全部相关面单交易判断终局。除已经形成的有效取消结果外，实际承运商首次有效收寄即形成终局；否则，只有在当前受控关闭已经生效且未被重开、全部相关面单交易均已定案，并且不存在任何有效或结果待确认的面单结果时，才依据明确失败、成功作废或接受时固定规则下的不可逆失效形成终局。
- 交易级失败不能推导包裹失败，单笔交易中的包裹级失败、渠道作废或失效也不自动形成包裹终局。受控关闭只将包裹级继续尝试判断派生为不允许新增尝试，不修改交易结果、不使既有面单失效，也不直接形成包裹终局；自然失效必须来自渠道确认或接受时固定的有效期规则。渠道退款和对账不作为包裹终局的前置条件。
- 受控关闭决定以包裹为范围，必须追加保存决定类型、生效时间、权威业务截断边界、原因、请求方（如有）、实际决定方、关闭责任来源、授权角色、授权依据快照及与前序决定的关系，不能覆盖为一个布尔值。包裹级继续尝试判断只由有效的关闭、重开决定及当前有效终局结果派生；同一业务时点的冲突必须保存稳定、可审计的领域顺序。
- 权威业务截断边界前已经形成交易建立决定或已经提交的交易，即使其事实迟到到达，仍属于既有交易并继续参与终局判断；关闭生效后只拒绝把该包裹纳入边界后的新重试、替代或换单交易，不阻断既有交易的查询、确认、重打、渠道作废、渠道退款、对账和定案。客户端时间、消息到达时间、数据库写入时间或外部墙钟不能单独裁决前后关系；关闭也不得通过回填过去的生效时间，追溯把此前已经合法接受的交易变成违规交易。多包裹交易中，目标包裹关闭不关闭其他包裹或整笔交易。
- 关闭期间若仍发现已经实际提交的边界后交易，`parcel-shipment` 必须形成违反截断边界的业务判断并保留该交易，继续保存外部结果、费用和责任；不得丢弃，也不得因后来重开而追溯合法化。任何已经实际形成且归属该包裹的面单结果都必须参与终局判断；如需建立后续异常案件，案件仍由 `visibility-exception` 拥有。
- 只有当前不存在有效终局服务结果时，才能依据适用授权追加重开决定；重开生效前若已经形成当前有效终局，该决定不得生效，并且不得因该终局后来失效而追溯生效。重开只允许未来形成新交易，不删除原关闭历史，也不复活已经失败、成功作废或不可逆失效的旧交易；当前有效终局服务结果存在时，正常业务必须拒绝重开原服务范围，后续新服务需求进入关联的新委托。
- 迟到的渠道或运输事实可以按业务发生时间和适用时间改变交易归类、面单交易定案或终局判断，但不能自行形成关闭或重开决定。关闭或重开决定自身的来源事实被更正或撤销有效性，以及终局有效性变化时，包裹级继续尝试判断都依据剩余有效决定历史和更新后的终局结果重新派生：当前无有效终局且没有生效关闭时派生为开放，仍有生效关闭时保持受控关闭。这类重新派生不是业务重开，不自动形成重开决定或新的面单交易，也不得静默改写原决定历史。
- 关闭和重开决定必须由运营企业责任法人授权的业务角色明确形成，系统不得自动形成；货主、渠道服务方和代理商只能提出请求，除非客户合同或明确授权把其纳入可直接形成决定的授权角色范围。关闭权限可由授权运营角色单独使用；重开必须由同级或更高授权角色形成并带原因；“同级或更高”指版本化授权规则中的重开权限等级，不是人事职级。因货主指令形成的关闭，重开还必须有同一货主账户新的有效授权；因运营企业操作形成的关闭，按适用的同级或更高重开权限规则处理。
- 监管、禁限运、安全暂停、渠道账号撤销或到期等硬限制，属于原关闭责任来源或明确覆盖拟重开的完整面单服务范围时，必须先由其来源责任方形成有效解除；只覆盖单一渠道的限制不阻止包裹级重开，但继续禁止该渠道的新交易。解除不自动重开，业务角色不得以重开绕过仍适用的限制。受控关闭也不因预计复核时间到达或授权规则后来到期而自动恢复；预计复核时间只形成提醒、待办或升级。
- 批量关闭或重开只是操作归组，不是提交批次，也不拥有关闭状态。`parcel-shipment` 必须为每个包裹分别形成决定、授权快照、适用边界和结果，并允许部分成功；一个包裹被拒绝、已终局或受限，不回滚其他包裹已经合法形成的决定。
- 渠道产品商业适用性、产品—渠道映射或渠道账号授权的范围变化分别由其来源表达，不等于包裹级受控关闭。包裹级继续尝试判断为开放，只表示包裹层面未阻止未来尝试，不保证当前存在可用渠道；每笔实际新交易仍须独立通过当前适用硬限制、渠道产品、产品—渠道映射、渠道账号授权和其他资格校验。渠道恢复可用只恢复候选资格，也不自动重开已经受控关闭的包裹。
- 包裹内部标识在同一物理服务件持续存在期间保持不变。换单、改号、换渠道、改路、退运和一对一重新包装都不更换该标识。
- 一个物理包裹被真实拆成多个需要分别处理、跟踪或交付的服务件时，必须创建新的包裹身份并保留拆分谱系；来源包裹不再代表后续实物。
- 同一委托、同一客户账户、同一合同责任和服务范围内的多个包裹被真实合成一个不再独立履约的服务件时，必须创建新的包裹身份并保留合并谱系；不能任意选择一个原包裹身份代表合并结果。
- 跨委托、跨客户账户或跨合同责任范围的包裹不得形成同一包裹身份谱系；共同装入袋、笼、箱或其他运输容器时只能形成集运关系。
- 装袋、拆袋、换袋、混装或装入共同外箱但仍分别跟踪和交付，只改变集运或作业关系，不构成包裹拆分或合并。
- 一笔面单交易按一次真实渠道业务请求划分，可以关联一个或多个明确包裹；一个包裹可以关联多笔具有重试、替代、作废或换单关系的交易。
- 渠道结果不确定不等于失败。原结果澄清前不得通过无关联重试创建新包裹或隐藏的第二笔有效交易。
- 查询、重打、渠道作废、替换和渠道退款是不同业务动作。重打同一有效结果不改变包裹身份；换单形成新的面单交易并显式关联被替代交易。
- 外部标识必须关联其真实标识对象：客户参考号关联委托，渠道订单号或主号按其语义关联面单交易，包裹件号或尾程件号关联包裹；总单号、舱单号和监管编号继续归相应源上下文。
- 外部标识作废、失效或被替代只改变适用关系，不删除历史标识，也不改变本系统拥有的委托或包裹身份。
- 网络服务包裹只允许在有效网络收寄结果形成前取消。面单渠道服务包裹只允许在实际承运商收寄前且面单服务终局边界尚未成立时取消；已经形成面单交易结果时，包裹取消不能代替渠道作废或渠道退款结果。
- 网络服务发生有效网络收寄后，或面单渠道服务发生实际承运商收寄或其他约定终局边界后，包裹不得回退为“已取消”；后续停止服务必须通过服务终止、退运或其他明确处置表达。
- 委托或包裹取消不能撤销节点收寄、场外揽收、物理作业、运输履约、关务申报或其他已经发生的源事实，也不能直接终止其他上下文拥有的对象。
- 取消请求、取消决定、下游释放或停止请求、实际执行结果和终局服务结果必须分别记录。形成取消决定前必须在同一决定提交边界重新核验当前有效收寄及终局事实；并发收寄已经先行成立时不得提交取消，消息晚到不能改变这一裁决。
- 收寄后服务处置必须按包裹形成明确决定；客户消息、异常信号、拒收、无路由或运输停止本身都不能自动生成退运或服务终止。处置决定只向路由、节点、运输、关务或结算等对象所有者提出范围化请求，各上下文分别形成承接和执行结果。
- 委托撤回请求或包裹取消/服务处置的批量操作都只形成操作归组。委托撤回按整份待决委托裁决；接受后的取消和处置按包裹逐件裁决并允许部分成功，一个包裹的结果不得回滚其他包裹已经合法形成的决定。
- 委托的当前状态和完成结论依据固定接受基线、包裹身份谱系及当前有效包裹结果派生，不能由人工直接设置为部分完成或已完成。
- 被拆分或合并替代的来源包裹保留历史身份和结果，但不与其后继包裹同时进入完成汇总；取消且未被替代的包裹仍以其终局取消结果参与汇总。
- 网络服务按合同约定的交付、退运或其他网络责任结果判断终局；面单渠道服务在面单服务终局边界成立或形成有效取消结果时判断终局，不默认等待实际运输交付，也不把渠道受理成功直接当作终局。
- 委托完成、异常闭环、客户索赔、供应商追偿和财务闭环分别判断，任何一个后续流程不得回写委托接受基线或源业务事实。委托完成后发生的正常渠道作废、渠道退款或费用调整不使委托回退为“已取消”；新接受的迟到事实、源事实更正或事件有效性变化可以按业务发生时间和适用时间形成新的派生判断版本，不能按消息到达顺序覆盖。
- 客户寄收件、货物和申报原始资料在接受时形成快照。后续更正形成新版本；节点实测和正式关务申报分别由其源上下文拥有，不能覆盖客户原始资料。
- 收件地点引用按（租户，包裹身份）答，委托与接受基线只是本上下文内部走到答案的路：经接受基线成员关系（含包裹身份谱系回到来源包裹）走到委托，取该委托收件资料范围上查询时刻的当前资料版本采用判断——范围上无修订版本答带接受基线锚的引用，`已采用`答带该版本锚的引用，`待复核`不给引用而答收件地点未定，对象不属任何已接受委托的成员集合（含集运单元与不可见对象）按统一不可见结果答没有收件地点。资料修订形成新版本后本上下文不推送、不改旧引用，只让新查询拿到换了锚的引用；地点变了是不是新任务由消费方判。已形成派送任务不是资料修订阶段的事实，不因它多加一道修订门。
- 客户要求代收货款时，委托接受基线保存代收币种、金额、付款对象和适用服务要求快照；该要求不证明收件人已经付款，也不使 `parcel-shipment` 拥有代收、清分或汇付资金。
- `parcel-shipment` 只拥有委托与包裹的服务身份、承诺和商业生命周期，不维护“运输中、清关中、派送中”等全程运营主状态。

## Lifecycles

### 委托

- 草稿 → 已提交：客户确认并提交服务请求；提交不代表运营企业已经接受。
- 已提交期间形成新提交版本：只允许仍属于同一委托边界的纠错或补充；新版本成为唯一待判断版本，旧版本及其判断历史继续保留。成员重组或共享约束变化建立关联新委托。
- 已提交 → 已接受：当前提交版本的商业有效性、服务适用性、必要资料、成员基线及适用财务控制全部通过，且规则要求的人工复核已经完成；此时固定完整成员接受基线并形成预计承诺。
- 已提交 → 已拒绝：版本化规则确定接受条件不成立，或授权角色依据结构化原因和证据决定不承担该服务请求；拒绝不产生实物责任起点，也不得原地重开为已提交。
- 已提交 → 已撤回：客户或其当前有效授权代表在接受或拒绝决定提交前撤回整份请求；原提交、版本、判断、撤回决定和补偿关系继续保留。已撤回委托不得原地恢复，后续服务需求形成关联新委托。
- 已拒绝后的修正建立关联新委托；已接受后的资料更正、服务变更、成员取消或新增服务件分别进入受控更正、取消或关联新委托路径，不覆盖原决定或接受基线。
- 已接受 → 已取消：仅当固定服务范围内所有当前有效包裹均已在各自适用取消边界前形成终局取消结果，且没有包裹形成非取消终局结果时成立；面单渠道服务已经形成的受理、渠道作废、渠道退款及结算责任继续独立保留和处理，不因委托取消而被抹除。
- 已接受 → 已完成：所有当前有效包裹均形成适用终局服务结果；各包裹可以具有不同结果。正常渠道作废、渠道退款或费用调整不触发“已完成 → 已取消”。
- 部分收寄、部分承诺、部分取消和部分完成是依据包裹结果形成的委托汇总，不是可以脱离包裹事实单独维护的状态。

### 接受判断任务

- 委托进入`已提交` → 建立当前提交版本的接受判断任务：保存采用版本、当前阶段、已形成结果和仍缺权威结果。
- 判断遇到客户可补充缺口 → 等待受控补充：补充形成同一委托的新提交版本或按成员边界形成关联新委托；原任务和判断历史不覆盖。
- 判断遇到依赖失败、并发冲突或权威一时答不出 → 等待内部续办：从已保存阶段查询或重试，不把原因改写为客户缺失或委托拒绝。它只覆盖会自行恢复的那一类；某个适用范围此刻一条现行规则或参数都没有登记时不属此格，见下面`等待运营登记`。
- 全部所需权威结果已经到齐通过、但适用规则要求的人工复核尚未完成 → 等待人工复核：由适用规则授权的角色按证据完成复核。它与前两个等待态分开，是因为续办方是第三方——内部重试推进不了它，客户也补不出它；复核完成本身不形成决定，决定仍由判断任务按适用规则形成。
- 判断所需的适用参数在该范围内一条都没有登记 → 等待运营登记：由运营企业按该参数自己的登记路径补齐，任务保持未决，委托保持`已提交`。它与`等待内部续办`分开，是因为查询与重试永远产不出一次登记——权威并不是答不出，是根本没有可答的东西；也与`等待受控补充`分开，因为要补的不是客户的资料而是运营企业自己的配置。登记完成本身不形成决定，决定仍由判断任务按适用规则形成。
- 判断任务 → 已完成：只有接受或拒绝决定已经越过提交边界时完成；任务超时、通知发送或人工升级本身不形成业务决定。
- 委托撤回决定成立 → 判断任务已停止：保留已执行阶段和结果，不再形成接受或拒绝；撤回补偿失败只续办原补偿，不恢复判断任务。

### 客户原始资料版本

- 已接受委托 → 收到补充/更正请求：先保全请求、来源和业务时间；请求未受理、业务拒绝、待补充/冲突和技术未形成不等同于资料版本已形成。
- 请求已受理 → 客户原始资料版本已形成：固定目标范围、基础版本、原因、请求方、实际决定方、授权快照和适用时间；版本追加保存，不覆盖接受基线或旧版本。
- 版本已形成 → 当前资料版本采用判断：依据版本关系、来源更正/撤销、业务有效时间和并发顺序派生；当前判断可以是已采用、待下游判断、待补充、冲突或未决。
- 当前资料版本采用判断变化 → 下游重新判断：`customs-compliance`、`node-operations`、`network-routing`、`settlement-accounting` 和异常上下文分别消费新版本并形成自己的结果；本上下文不代替这些决定。
- 已提交、已关闭或已完成后收到的迟到更正仍保留版本与关系；不能追溯改写接受基线、正式申报、提交、运输或结算历史。案件是否重开或建立后续案件由 `customs-compliance` 决定。

### 包裹身份与服务

- 声明包裹在委托接受时进入固定成员基线，并保持永久内部标识。
- 适用取消边界前 → 已取消：客户或运营企业终止尚未进入不可回退阶段的该包裹服务；原身份和取消原因继续保留，既有面单交易另行形成渠道作废或渠道退款结果。
- 适用取消边界后 → 不得取消：后续请求只能依据当前产品、合同、事实、限制和授权形成收寄后服务处置决定、保持处置未决或被明确拒绝；不得建立一个可以覆盖运输事实的通用“停止中”包裹状态。
- 收寄后服务处置决定形成 → 各对象所有者分别承接：尚未消耗的计划、委托、预占或作业范围可以被请求释放，已经发生的控制、交接、移动、申报、费用和责任继续保留；只有后续权威执行结果满足终局规则时才形成终局服务结果。
- 网络服务有效网络收寄结果形成且适用资格校验完成 → 正式承诺生效：客户送达节点时结果来自 `node-operations`，上门揽收或场外接货时结果来自 `transport-fulfillment`；`parcel-shipment` 统一解释结果并形成包裹级正式承诺。
- 面单渠道确认受理且适用资格校验完成 → 面单服务正式承诺生效：该结果不表示运营企业已经收寄，也不默认形成包裹终局；实际承运商收寄后，由 `transport-fulfillment` 提供运输观察事实。
- 当前受控关闭已经生效且未被重开，全部相关面单交易均已定案为明确失败，并且不存在有效或结果待确认的面单结果 → 终局失败结果。
- 当前受控关闭已经生效且未被重开，全部相关面单交易均已定案，不存在仍可使用或结果待确认的面单结果，并且已有成功结果均已成功作废或依据接受时固定的规则不可逆失效 → 终局服务结果。
- `transport-fulfillment` 提供实际承运商首次有效收寄事件 → 面单渠道服务非取消终局结果：该服务不统一等待实际交付。
- 客户合同明确的其他面单服务终局边界成立 → 非取消终局服务结果：边界成立后不得再通过客户取消回退。
- 原包裹 → 被拆分替代：真实拆分产生两个或多个新包裹身份及来源关系，原身份退出当前有效包裹集合。
- 多个原包裹 → 被合并替代：真实合并产生一个新包裹身份及组成关系，原身份退出当前有效包裹集合。
- 当前有效包裹 → 终局服务结果：结果依据适用服务产品和合同形成；网络服务与面单渠道服务不强制共享同一结果集合。

### 面单继续尝试

- 当前不存在有效终局，且尚无生效的受控关闭或最近适用决定为重开 → 开放：包裹级允许依据适用规则申请新的重试、替代或换单；实际新交易仍需通过当前硬限制、渠道和账号资格校验。
- 开放 → 受控关闭：授权决定达到其生效时间和权威业务截断边界；边界后的新尝试被拒绝，边界前既有交易继续处理和定案。
- 受控关闭 → 开放：当前不存在有效终局，且适用授权形成的重开决定已经生效，或者原关闭决定被更正为无效且不存在其他生效关闭。显式重开不删除关闭历史、不复活旧交易，也不追溯认可关闭期间的违规交易；因决定有效性更正形成的开放是重新派生，不是重开决定，也不自动形成新的面单交易。
- 当前有效终局服务结果存在 → 禁止业务重开：源事实更正或事件有效性变化使终局失效后，依据剩余有效决定历史重新派生开放或受控关闭；此前因终局被拒绝的重开决定不追溯生效。真正的新服务需求在当前有效终局存在期间进入关联的新委托。
- 受控关闭不会因预计复核时间到达或授权规则到期自动转为开放；提醒、待办和升级不改变生命周期。
- 批量操作不形成独立的包裹生命周期；每个包裹分别沿上述转换判断，允许批量部分成功。
- 单渠道范围资格变化不改变包裹级继续尝试生命周期；只有有效的包裹级决定或当前有效终局结果改变包裹级继续尝试判断。

### 面单交易

- 建立交易 → 已提交渠道：交易固定所覆盖包裹、渠道账号、参与方角色、合同、费率和责任依据。
- 已提交渠道 → 结果不确定：暂时无法确认渠道是否受理；该结果不得直接按失败处理。
- 已提交渠道或结果不确定 → 成功、部分成功或失败：同时保存整笔交易结果和各包裹结果，不能由一个层次覆盖另一个层次。
- 任何交易级结果或单笔交易中的包裹结果都不直接推动包裹终局；`parcel-shipment` 必须跨该包裹全部相关交易及实际承运商收寄事实形成包裹级判断。
- 原交易 → 被替代：失败后的新申请、换单或明确重新下单形成新交易，并保留重试或替代关系。
- 查询和重打作用于原交易及其既有结果，不自行形成新的交易身份。
- 渠道作废、渠道退款和替代是针对明确交易范围或包裹范围形成的后续业务动作及结果，可以与未受影响包裹的原结果并存；它们不构成一条覆盖整笔交易的统一线性状态。

### 客户承诺

- 委托接受 → 预计承诺形成：保存当时产品、合同、资料和服务条件依据。
- 网络服务有效网络收寄结果形成且适用资格校验完成 → 正式承诺形成：每个包裹独立判断，不等待同委托其他包裹；结果可以来自节点收寄或场外揽收，但必须具有一致的对象级业务语义。
- 面单渠道确认受理且适用资格校验完成 → 面单服务正式承诺形成：该承诺只覆盖合同约定的面单渠道责任，不虚构运营企业实物收寄或端到端运输责任。
- 正式承诺后发生允许调整的情况时，形成带原因的新版本；计划、预测或实际事实不得覆盖原承诺。

## Boundaries and ownership

- `parcel-shipment` 拥有提交批次的业务归组、委托、委托提交版本、接受判断任务、接受或拒绝决定、委托接受基线、客户声明成员关系、包裹身份、包裹身份谱系和当前有效包裹判断。
- `parcel-shipment` 拥有面单交易、交易覆盖范围、交易级与包裹级渠道结果、面单交易定案、包裹级关闭或重开请求证据、面单继续尝试决定、请求方与实际决定方证据、关闭责任来源、批量操作的逐包裹结果、权威业务截断边界及包裹级继续尝试判断，以及委托、面单交易和包裹所使用的外部标识关联。
- `parcel-shipment` 拥有客户寄收件、货物、申报原始资料、服务要求、商业依据和客户承诺的任务级快照，但不拥有其来源主数据或后续源上下文事实。
- `parcel-shipment` 拥有客户原始资料补充/更正请求、客户原始资料版本、版本关系、当前资料版本采用判断及其请求方/实际决定方/授权审计；其他上下文只能消费版本引用和适用范围，不能回写客户来源。
- `party-commercial` 拥有客户、合同、服务产品、接单规则包、接受前财务控制策略、接受与主动拒绝授权、面单服务终局规则、责任法人授权治理、角色权限等级、合同委派、关闭责任来源规则、渠道产品、映射、约束和账号授权的版本生命周期；`parcel-shipment` 保存实际采用依据并形成委托决定，但不能临时发明商业规则或授权。形成关闭或重开决定时仍须重新校验当前角色与客户授权，并在重开时确认原关闭责任来源对应或覆盖完整面单服务范围的限制已经解除。
- 共享身份认证与授权技术能力拥有凭据验证、通用授权策略和授权作用域签发；`parcel-shipment` 只消费已授权作用域并执行自身对象过滤，不建立企业身份主数据、授权引擎或跨客户查询层。
- `node-operations` 拥有客户送达节点形成的节点收寄、测量、重新包装及真实物理拆分或合并事实；`parcel-shipment` 根据被接受的事实决定包裹身份和谱系，不修改作业事实。
- `transport-fulfillment` 拥有上门揽收或场外接货、节点与运输方的权威交接结果、实际承运商收寄、运输、交付和运输凭证事实；`parcel-shipment` 将节点收寄和场外揽收统一解释为适用的有效网络收寄结果，并据实际承运商收寄事实另行判断面单渠道服务的取消边界和运输观察，但不把渠道结果当作实际承运事实。
- `network-routing` 拥有路由计划和改路历史；计划变化不修改委托身份、包裹身份或客户承诺。
- `customs-compliance` 拥有正式申报、监管编号、监管结果和关务限制；`parcel-shipment` 只提供客户原始资料快照，不能撤销或覆盖正式申报。
- `visibility-exception` 拥有全程追踪投影、异常信号和异常案件；`parcel-shipment` 不复制一套运输、清关或派送主状态。
- `settlement-accounting` 拥有接受前估价、资金冻结、信用暴露和其他财务控制的实际结果，以及费用、运营应收、审核应付、客户费用退款、供应商费用贷项、赔付、成本和经营指标；`parcel-shipment` 只保存接受时采用的结果与依据并独立形成委托决定，不拥有金额、余额或冻结。
- `collection-remittance` 拥有代收货款的应收、实收、渠道在途、清分、应付客户和汇付结果；`parcel-shipment` 只拥有客户代收要求及其任务级快照。
