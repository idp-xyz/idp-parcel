# 全程追踪与异常（`visibility-exception`）

Status: Confirmed

本上下文基于各源上下文已经接受的事实，形成包裹全程追踪投影、标准追踪里程碑、预计到达时间和客户可见信息，并管理异常信号、异常案件、处置协调、责任证据、客户索赔及供应商或保险追偿关系。它回答“目前可以确认发生了什么、可能发生什么风险、谁在处置、依据什么形成责任结论”，但不拥有节点、运输、关务等源事实，不解除来源限制，也不拥有赔付、追偿或费用的最终金额。

本文件是 `visibility-exception` 语言、规则与生命周期的权威来源。跨上下文术语以[统一领域语言](../GLOSSARY.md)为准，所有权关系以[领域上下文地图](../CONTEXT-MAP.md)为准。来源事实、有效事件和派生状态遵循 [ADR-0005](../../adr/0005-source-facts-effective-events-derived-state.md)，客户承诺、计划、预测和实际事实的分离遵循 [ADR-0004](../../adr/0004-separate-commitment-plan-actual.md)。

## Language

**全程追踪投影**  
面向明确包裹及其身份谱系，对节点、运输、关务、路由和托运上下文已经接受的事实进行语义化编排后形成的只读旅程视图。它可以重新派生，但不保存第二套源事实，也不覆盖任何源上下文状态。

**来源事实替代关系**  
源上下文在自己的事实谱系内形成的「新版本取代旧版本」关系。它由被取代事实的所有者随更正一并给出，指名被取代的那一份已接受事实；本上下文只登记和引用这层关系，不判断谁取代谁，也不因此使任何源事实失效。它不同于处置请求替代、客户全程追踪视图替代和客户异常通知替代——那三者是本上下文自己形成的意图或发布关系，这一层是源上下文已经作完的判断。

**标准追踪里程碑**  
把不同节点、渠道、承运商和监管来源的有效事件映射为统一业务语义后形成的追踪结果。来源原文、来源代码、映射版本及事实引用始终保留；无法明确映射时保持未归类。

**追踪摘要**  
依据物流进展、控制范围、关务进展、交付或退运进展、异常影响和预测等并行维度形成的当前简要说明。摘要用于阅读和检索，不是一条覆盖各维度的统一状态机。

**客户全程追踪视图**  
面向已授权货主客户账户，对该账户有权查询的包裹展示标准追踪里程碑、适用的客户可见 ETA、客户服务终局和更正关系的普通查询视图。它不同于内部全程追踪投影，也不同于客户可见异常和客户异常通知；查询或展示本身不产生异常披露决定或主动通知结果。

**运营追踪查阅**  
面向租户内运营人员，对本上下文拥有的全程追踪投影及其留存版本进行的只读查阅。它是客户全程追踪视图那句「它不同于内部全程追踪投影」的另半边：面向投影的全部并行维度、冲突与替代关系，不经客户披露删减；追踪摘要用于阅读和检索，运营追踪查阅就是摘要与各维度在租户内的阅读和检索口。它的作用域是租户级——租户是最高数据隔离边界（[ADR-0003](../../adr/0003-group-tenant-legal-entity-customer-account.md)），投影是租户内部对象，查阅不跨租户，也不按货主客户账户分区。查阅本身不产生判断、派生、披露决定或通知，也不构成客户可见性。

**客户归属**  
某包裹此刻可确定的货主客户账户。同一委托中的包裹共享客户账户，因此客户归属由 `parcel-shipment` 的当前已接受委托给出；本上下文只按包裹反查和引用，不发明账户，也不在多份同时声明该包裹的已接受委托之间择一。它与身份谱系分别回答两个问题——身份谱系回答「这是哪一件包裹」，客户归属回答「这件包裹属于哪个货主客户账户」；定位包裹候选时两者分别核对，不能互相替代。

**追踪说明**  
为解释已知事实、信息缺口或正在核实的情况而发布的文字说明。追踪说明不能制造到达、交接、放行、妥投或其他业务事实。

**预计到达时间（ETA）**  
在明确预测时点，针对包裹或未来里程碑形成的版本化时间预测。它具有输入事实、规则或模型版本、预计时间范围和可信程度，不是客户承诺、路由计划或实际时间。

**可见性缺口**  
在适用服务或履约段明确预期某项观察，但超过观察窗口仍未取得相应信息的情况。可见性缺口只证明预期数据尚未获得，不证明包裹停止移动、运输延误或已经遗失。

**异常信号**  
依据预测、版本化规则或有效事实识别出的风险、偏差或疑似问题。关务相关信号通过 [UC-VE-001](../../application/visibility-exception/UC-VE-001-COORDINATE-CUSTOMS-EXCEPTIONS-AND-CUSTOMER-DISCLOSURE.md) 消费关务所有者已经接受的事实和判断形成。信号用于分诊和提示，可以确认、变化或解除；它不是异常案件、责任结论或执行限制。

**信号发作期**  
同一对象、信号类型、因果条件和连续影响期间的一次信号生命周期。连续命中更新同一发作期；明确恢复后再次命中形成关联的新发作期。

**异常分诊**  
对异常信号的可信度、影响、重复关系、资料完整性及处置必要性进行判断，以决定关联既有案件、自动建立案件、进入人工复核或不建案的过程。

**异常案件**  
围绕同一因果链和处置范围，对需要持续响应、调查、协同、责任判断或闭环处置的问题建立的业务案件。案件可以由信号、参与方上报或其他上下文的明确事实触发。

**案件影响范围**  
案件在某一版本中明确覆盖的根对象及受影响对象集合。范围可以包含包裹、集运单元、实际履约段、班次或关务案件等引用，但成员关系、装载关系或同批关系不会使对象动态、隐式继承案件。

**严重度**  
对异常已经造成或可能造成的业务影响程度所作的判断。严重度描述影响，不表示处置顺序，也不产生执行限制。

**处置优先级**  
综合严重度、剩余干预时间、客户承诺、影响范围和可恢复性形成的处理紧迫性判断。优先级驱动队列、时限和升级，不推定原因或责任。

**案件责任团队**  
对开放案件持续承担接单、协调、推进和闭环责任的内部团队。案件责任团队及当前处理人不是原因方、履约责任方或赔偿责任方。

**异常响应策略**  
依据异常类型、优先级、服务产品、客户合同、责任团队和运营日历，确定首次响应、下一行动、客户更新及解决目标的版本化规则。

**处置请求**  
异常案件向源业务上下文提出的结构化业务请求，例如改路、拦截、重作业、重新履约或重新申报。请求必须具有稳定身份、范围、意图版本、受理有效期（如适用）和替代关系；请求已发送、源上下文已接受、取消/替代意图、目标方取消结果和实际动作已完成是不同结果。

**客户可见异常**  
依据服务产品、客户合同、信号可信度、预计客户影响和披露规则，从内部信号或案件形成的客户账户隔离视图。它不暴露其他客户、内部调查或未经确认的责任信息。

**客户异常通知**  
针对明确客户、对象范围和内容快照形成的披露决定。通知决定、消息渠道接受、实际送达和客户确认分别存在。

**证据项**  
用于支持事实核实、原因分析、责任判断、客户索赔或外部追偿的可追溯材料及其业务说明。证据项保存来源、提供方、取得时间、适用范围、版本、有效性和访问范围；材料被提交不表示其内容已经被认定为事实。

**责任结论**  
依据事实、合同和证据，针对明确对象及责任方向形成的版本化业务判断。事实原因、运营处置责任、客户合同责任、供应商责任和保险追偿依据分别表达，不压缩为一个最终责任方。

**索赔提交批次**  
客户一次提交一个或多个索赔项的业务归组。批次保留原始提交范围和时间，但不拥有统一受理、责任或赔付结果。

**客户索赔项**  
一个货主客户账户依据明确合同责任，针对一个包裹或明确服务责任范围提出的独立补救请求。每个索赔项分别进行资格审核、责任裁定和复核；最终赔付金额由 `settlement-accounting` 管理。

**追偿事项**  
运营企业依据供应商、实际承运商、保险或其他外部责任关系，针对明确责任范围发起并管理的独立追偿主张。追偿事项拥有自己的通知期限、资格、证据和责任结论，不等待客户索赔或赔付完成。

**追偿通知或主张动作**  
追偿事项下，依据供应商协议、保险条款或其他责任依据向明确相对方实施的一次外部业务动作。预先通知、正式主张和补充主张可以是不同动作，各自具有内容快照、提交期限以及“已提交、已送达或已确认”等合同要求的完成条件；准备完成不等于已经对外提交。

## Rules and invariants

### 追踪投影与里程碑

- 全程追踪投影只能消费各源上下文已经接受的事实和有效性变化。来源消息、原始扫描或外部状态码未经业务所有者接受前，不得直接改变投影。
- 投影必须引用来源事实，不得复制形成含义不同的第二套节点、运输、关务、路由或托运事实。任何运营人员和集成来源都不能直接编辑当前追踪摘要或标准追踪里程碑。
- 来源原文、来源代码、业务发生时间、有效时间和接收时间分别保存。标准追踪里程碑映射必须具有版本和适用范围；无法可靠映射时保持未归类，不能为了得到完整时间线强行映射为“运输中”或其他宽泛结果。
- 已接受事实必须携带源上下文拥有的事实类型；标准里程碑映射按源上下文与事实类型版本化登记，一行覆盖此后同类型事实，不得按单条事实引用建目录。
- 多个有效事实冲突时，依据事实类型、对象身份、控制范围、业务发生时间、有效时间、因果顺序和源上下文权威范围形成版本化投影判断，不采用全局来源排名或最后消息覆盖。
- 冲突仍无法裁决时，必须保留各项事实及冲突关系，投影保持信息待确认并形成适用异常信号；本上下文不得自行使源事实失效。
- 全程追踪并行表达最后确认的物流进展、位置或控制范围、关务进展、交付或退运进展、异常影响及预测信息。追踪摘要由这些维度派生，不得用摘要反向覆盖任一维度。
- 包裹身份、外部标识和身份谱系由 `parcel-shipment` 提供。真实拆分或合并后，各当前有效包裹分别形成后续投影，来源包裹保留共同历史；集运、装载或同批关系不合并包裹身份和客户轨迹。
- 迟到事实、来源更正或事件有效性变化可以重新派生当前投影，但原来源、原映射、原投影判断和已经发布的客户信息必须保留关系。终局事实有效性变化也不能被伪装为人工重开。
- 来源事实替代关系只能由源上下文给出，且只在同一源上下文、同一事实引用的版本之间成立。本上下文不得从业务时间、到达先后或任何其他线索自行推断谁更正了谁；跨源上下文或跨事实引用的分歧仍是冲突，按冲突裁决处理，不得借替代关系代为裁决。
- 被替代的已接受事实不删除、不改写，其有效性仍归源上下文。「已被替代」是替代关系的派生问答——一份已接受事实处于已被替代，当且仅当另一份已接受事实指名它为前身；本上下文不为它另存可变标记，因而替代先于被替代到达也不改变结论。
- 同一份已接受事实被两份以上事实同时指名为前身时，替代链分叉，本上下文不得择一。分叉按冲突处理：保留各项事实及其关系，投影保持信息待确认并形成适用异常信号。
- 被替代的条目继续留在投影版本内并标明替代关系；标准追踪里程碑、各追踪维度和追踪摘要只由当前有效即未被替代的条目派生。保留是为了可追溯，不参与派生是为了不同时呈现两个互斥结果。
- 投影版本只增不改写。重新派生形成新的当前投影版本，原版本连同其条目、所用映射版本和派生时间继续可按版本读回；指向一份已经读不回的原版本不算保留关系。
- 外部不透明履约段只展示已知入口、出口、交付范围和实际获得的里程碑，不得依据经验虚构合作方内部节点、位置或移动。
- 运营追踪查阅必须核对请求方身份与租户，其授权作用域是租户级，不按货主客户账户分区；认证与授权由共享身份能力提供并传入结果，本上下文只消费该结果，不拥有凭据验证或通用授权策略。
- 运营追踪查阅面向投影的全部并行维度、冲突关系与被替代条目；「投影未形成」对租户内已授权的运营查阅如实作答。「对未授权对象的外部响应不得泄露对象是否存在或属于其他客户」约束的是对外部账户的作答，不因运营查阅松动，也不反过来把合并作答强加给租户内的运营查阅。
- 运营查阅结果不构成客户披露。内部维度内容要进入客户全程追踪视图、客户可见异常或客户异常通知，仍必须按「客户可见性与通知」的适用规则形成版本化决定。

### ETA 与可见性缺口

- 每次 ETA 必须明确预测对象、目标里程碑、预测时点、输入事实、规则或模型版本、预计时间范围和可信程度。信息不足时允许不形成 ETA，不得以计划时间或客户承诺填充。
- 承运商提供的预测与运营企业派生的预测分别保留来源和口径。新的 ETA 形成新版本，不覆盖历史预测，也不修改客户承诺、路由计划或实际事实。
- 客户是否可见 ETA、展示点值还是时间范围以及何时停止展示，必须依据版本化客户可见性策略判断。
- 只有适用产品或履约段明确预期某项观察，且版本化观察窗口已经届满时，才能形成可见性缺口信号。无扫描不能直接形成延误、停止移动或遗失结论。
- 来源系统整体中断时，优先按共同原因建立来源级信号或案件并明确关联受影响对象范围，不为每个包裹重复建立相同处置案件。

### 异常识别、分诊与分级

- 异常信号与异常案件始终保持独立。每个信号必须保存对象、类型、规则版本、判断时间、事实依据、可信度、当前发作期和变化历史。
- 关务相关异常只能消费 `customs-compliance` 已经接受且范围明确的事实或判断。原始监管消息、截图、自由备注、客户意见和消息超时本身不能直接成为关务异常事实；查验、扣留、税费或内部限制等正常程序事实也只有命中已登记异常或客户影响规则时才形成异常信号。
- 高可信、高影响且命中版本化分诊规则的信号可以自动建立或关联案件；低可信、资料不足、可能重复或关联不明确的信号必须先进入分诊。
- 同一对象、类型、因果条件和连续影响期内的重复命中更新同一信号发作期。条件明确解除后，该发作期结束；再次发生时建立关联的新发作期。防抖、宽限和恢复边界必须具有规则版本。
- 异常识别规则必须具有生效范围和版本。新版本默认只作用于生效后的事件和明确的当前业务范围；历史或存量重评必须声明时间、客户、产品和对象范围，并继续执行去重、关联和分级建案。
- 规则重评、规则停用或来源更正不得删除历史信号、案件或判断依据。规则停用只停止适用范围内的新判断，或者触发带依据的当前信号复核。
- 严重度依据实际或潜在业务影响形成；处置优先级综合严重度、干预窗口、客户承诺、影响范围和可恢复性形成。两者分别保存判断依据和历史。
- 信号形成、严重度提高、优先级提高或案件升级都不自动产生业务限制，也不自动认定履约失败、遗失或赔偿责任。

### 案件身份、范围与隔离

- 同一因果链和共同处置范围原则上保持在同一异常案件中。独立原因、独立责任范围或已经分离的处置责任建立关联的新案件。
- 每个案件必须具有一个根对象和显式、版本化的影响范围。范围扩大、缩小、排除或拆出都必须保留依据和历史，不得根据对象当前所在集运单元、舱单、班次或客户分组动态继承。
- 同一网络事故可以在租户内形成一个跨客户内部案件，但受影响对象必须按货主客户账户和责任法人分区。客户可见异常、通知、索赔项和责任结论分别形成授权范围；任何客户都不能推断其他客户的存在、业务量或案件内容。
- 不同法人或客户已经产生独立处置、责任或关闭范围时，必须建立关联案件，不能为了维持单一案件而混合责任和授权。
- 误建的重复案件通过受控归并处理：指定主案件继续处置，其他案件以“已归并”结论关闭并关联主案件。原编号、分派、响应、证据、通知、处置请求、响应目标、响应周期及其绩效历史不得删除或重置。

### 案件责任、响应与闭环

- 每个开放案件始终必须有一个内部案件责任团队，并可以指定当前处理人。责任团队转交只有在接收方接受后生效，原分派和交接历史永久保留。
- 案件责任团队和处理人只承担处置协调责任，不得据此推断异常原因、履约责任、客户赔偿责任或外部追偿责任。合作伙伴可以承担调查或处置任务，但不能使运营企业内部案件失去责任团队。
- 异常案件采用 `待响应 → 处理中 → 已关闭` 的精简主生命周期。等待客户、合作伙伴、监管或内部团队，以及监控中、已升级等作为当前工作条件和下一行动管理，不扩展为互斥主状态。
- 异常响应策略按适用范围分别形成首次响应、下一行动、客户更新和解决目标；不适用的目标可以不存在。优先级变化或批准延期形成新的时限版本，原目标和变更依据保留。
- 必须分别记录风险条件首次成立、信号生成、案件建立、分派、接单、首次行动、客户更新、解决和关闭时间。转派、信号归并和案件归并不得重置原响应周期。
- 案件重开形成新的响应周期并保留原周期绩效。后续新增受影响对象按其被确认受影响的时间记录，不倒填为事故最初发生时间。
- 只有异常已经恢复、确认无法恢复、判定不成立，或者剩余事项已明确移交到独立业务对象，并且案件内必需动作已经完成，保存结论、依据、影响范围和未决事项后，案件才能关闭。
- 案件关闭不修改源事实，不解除任何来源限制，也不等待委托完成、客户索赔、赔付、供应商或保险追偿、运营结算或法定财务处理完成。
- 关闭后出现足以影响原结论的新事实，且仍属于同一因果链、责任范围和处置范围时，受控重开原案件；原关闭决定、依据和重开原因永久保留。高可信且命中版本化规则的事实可以自动重开，其余进入分诊。
- 独立的新原因、新责任范围或新的异常事件建立关联新案件。重开异常案件不得自动重开委托、路由计划、关务案件、限制、面单交易或财务事项。

### 原因、责任与处置协调

- 原始异常现象、直接原因、根本原因和促成因素分别表达。原始信号类型不得被最终根因覆盖；原因结论允许多个促成因素、部分确认或无法确认，并保存版本和证据。
- 原因结论不自动形成责任结论。事实原因、内部运营处置责任、客户合同责任、供应商责任和保险追偿依据必须按方向和对象范围分别判断。
- 责任结论必须保存适用对象、责任参与方、合同或其他依据、证据、决定方、有效历史和当前结论；允许部分成立、多个参与方分别承担或暂时无法认定。
- 处置请求必须明确目标对象、请求动作、原因、证据、请求方、接收上下文和期望时限。请求发送、源上下文接受、拒绝、部分接受、要求补充以及实际执行结果分别记录。
- `visibility-exception` 只能拥有处置请求及协调关系。改路、重作业、重新履约、重新申报、放行、限制解除和费用调整是否成立，由相应对象所有者决定。
- 案件不能因处置请求已发送或已接受而推定实际动作已经完成。部分接受或部分执行只关闭已经完成的明确范围，其余范围继续处置或明确移交。
- 案件范围缩小、改派、归并或关闭前必须盘点全部未完成处置请求。每个范围必须继续等待、明确移交，或形成取消/替代意图并取得目标上下文结果；案件状态变化不能静默使旧请求失效。
- 处置请求取消或替代只改变未来意图，不撤销已经发生的源业务事实。目标上下文必须分别返回取消已接受、部分取消、已无法取消或拒绝取消；已经开始或完成的范围继续按事实返回执行结果。
- 受理有效期届满后，尚未被目标上下文接受的范围不得再按旧请求启动；已接受范围的期望完成时限届满只形成逾期和升级，不自动取消正在执行的动作。

### 客户可见性与通知

- 客户全程追踪视图只基于当前有效的全程追踪投影、获准对客展示的 ETA、`parcel-shipment` 提供的客户服务终局，以及已经批准披露的客户可见异常形成。它不得从内部案件、原始来源消息或单一交付扫描自行推导终局、责任或异常披露。
- 每次普通追踪查询必须同时核对请求方身份、货主客户账户和目标对象授权。运单号、客户参考号或其他外部标识只能用于定位候选对象，不能单独证明查询权限；对未授权对象的外部响应不得泄露对象是否存在或属于其他客户。
- 客户全程追踪视图只展示适用服务与授权允许的公开里程碑、地点粒度、ETA、终局和说明，不暴露其他客户、内部节点控制、未公开线路、供应商商业信息、内部调查或敏感监管信息。
- 普通追踪查询、门户展示、客户可见异常和主动通知是不同结果。查询不会自动形成异常披露或消息意图；门户展示能否满足特定通知义务，仍由客户合同和通知策略另行判断。
- 来源更正、事实有效性变化、身份谱系变化、ETA 新版本或终局更正必须重新派生客户视图并形成追加更正或明确替代关系。原已发布版本保留，但不再有效的内容不得继续显示为当前事实。
- 客户全程追踪视图以客户归属可确定为前提。客户归属迟于该包裹的源事实确立时，必须在确立时按当前有效投影形成该账户的客户视图，不得等待下一份源事实；归属不可确定期间不形成视图，也不得发明账户或把它表达为无轨迹。同一包裹被多份当前已接受委托同时声明时仍是标识冲突，按待确认处理，不择一。
- 内部信号、内部案件和客户可见异常不是同一对象。客户可见性必须根据服务产品、客户合同、信号可信度、影响范围、预计客户影响和信息披露规则形成版本化决定。
- 客户视图只包含当前货主客户账户及其授权对象范围，不得暴露其他客户、内部调查、敏感安全信息或未经确认的责任判断。跨客户内部案件必须按客户分别形成披露内容。
- 已经向客户发布的里程碑、ETA、异常说明或通知出现更正时，必须以追加更新或明确替代关系表达，不得静默删除或改写历史披露。
- 客户异常通知必须保存通知对象、内容快照、披露依据、目标客户、要求时限和适用渠道。门户展示与主动通知是不同结果，是否可以互相满足由客户合同和通知策略决定。
- 通知已生成、已提交消息渠道、渠道已接受、已送达、失败和客户确认必须分别记录。合同要求送达或确认时，只有相应结果成立才满足通知义务；失败按策略重试或升级。
- 客户通知、客户确认或客户异议都不能直接修改源事实、异常案件责任、限制或索赔结论。
- 关务事实涉及受限监管原因、跨客户共同范围、内部调查或未确认责任时，客户披露必须使用经批准的最小范围和内容。异常案件存在不自动要求披露，披露条件不成立或授权不足时分别形成暂不披露或待授权结果。

### 证据、客户索赔与追偿

- 证据项必须保存来源、提供方、取得时间、适用对象、证据类型、版本、有效性和访问范围。源上下文拥有的事实和文件继续由源上下文拥有，本上下文只拥有证据引用、评价和案件关系。
- 同一证据项可以被异常案件、客户索赔项和追偿事项分别引用。对外披露必须形成明确披露范围或脱敏版本，不能复制出来源不明、内容不一致的附件。
- 客户或合作伙伴提交证据只表示材料已经收到，不证明其陈述、事实或责任成立。证据冲突必须保留并进入适用调查或裁决。
- 客户可以通过一个索赔提交批次提交多个索赔项。每个索赔项必须固定一个货主客户账户、合同责任范围、目标包裹或明确服务范围及索赔类型，并独立受理、审核和形成结论；批次允许部分成功。
- 收到客户索赔、通过资格审核和确认赔偿责任是不同判断。系统必须先保留原始提交事实，再按申请人授权、客户账户、合同版本、索赔时限、目标范围、重复关系和最低材料要求判断资格。
- 客户首次索赔期限、资料补充期限和结论复核期限是三个独立期限。每个期限必须保存适用规则版本、起算事件、业务时区或日历、截止时间和适用范围；不能用其中一个期限代替或重置另一个期限。
- 资料不足时，索赔项进入限期补充，并固定缺少材料、补充范围、通知依据和当前截止时间。材料已提交只表示收到，必须重新判断是否达到最低材料要求；受理不表示责任成立，也不表示已经同意赔付。
- 补充延期申请、内部批准和有效延期是不同结果。只有合同或规则允许，且由有权决定方批准明确范围和新截止时间时，延期才生效并形成新的期限版本；原期限和批准依据保留，延期不得倒填为原本按时，也不得重置首次索赔期限。
- 补充期限届满只触发资格复核。合同或规则明确规定届满后果时，才可依据现有材料形成不予受理或继续审核；未规定后果、延期尚待确认或届满事实有争议时，保持待决定并升级给授权角色，不能默认拒赔。
- 客户可以对尚未形成最终责任结论的索赔项提出逐项撤回。撤回必须校验申请人、客户账户、授权和范围；有效撤回终止该索赔项的后续资格与责任审核，但保留原提交、材料和撤回依据，不表示异常不成立，也不取消已经独立发起的供应商或保险追偿。
- 最终责任结论或结算金额已经形成后，撤回请求不得删除或覆盖既有结论和金额。确需改变当前责任时必须通过适用复核形成新责任版本，金额调整由 `settlement-accounting` 处理；重新提出请求仍按新索赔项执行原索赔期限和重复检查。
- 同一目标包裹、索赔类型和责任范围内出现有效异议或关键新证据时，只有在适用复核期限和授权范围内才能进入复核。复核期限的起算必须引用合同规定的结论通知、送达或可获取事实；无法确认起算事实时保持期限待判断，不得默认从内部结论时间起算。
- 复核形成新的索赔结论版本，关联原结论、异议或补充证据、复核理由、决定方和时限判断；原结论不得覆盖。超过复核期限且不存在有效延期或其他恢复依据时，形成有依据的不受理复核，不改变原责任结论。
- 新增包裹、索赔类型或责任范围时，建立关联的新索赔项，不能借复核绕过重复检查、索赔期限或形成重复赔付。
- 供应商或保险追偿在相应通知或主张条件成立时即可独立发起，无需等待客户提出索赔、客户责任结论或客户赔付。一个异常案件可以关联多个追偿事项，各自拥有资格、时限、证据和责任结论。
- 每个追偿事项必须按责任相对方和责任依据分别固定运营责任法人、协议或保险条款版本、责任范围、证据范围、适用期限及所需外部动作。预先通知和正式主张不能合并为一个模糊的“已追偿”。
- 每个追偿通知或主张动作必须分别记录准备完成、对外提交、渠道接受、送达、对方确认、提交失败和送达失败。哪一个结果满足期限义务必须来自适用协议或条款；准备完成、渠道接受和内部审批都不能默认满足对外通知或主张义务。
- 提交或送达失败是外部动作结果，不是对方拒绝责任。期限内可以按规则重试或更换获准渠道，所有尝试和内容版本保留；对方未响应也不得自动解释为拒绝或责任成立。
- 追偿延期只有在适用协议或保险条款允许，并取得条款要求的有权相对方确认或其他有效依据时才生效。内部批准、口头预期或发送延期请求不能单独延长外部期限；有效延期形成新的期限版本，保留原截止时间、范围和依据。
- 追偿期限届满必须按该动作要求的提交、送达或确认结果进行失权复核。只有当前有效依据足以证明权利丧失时才形成失权结论；送达事实、延期效力或条款解释仍有冲突时保持待判断，不能仅因系统时钟到期自动认定失权。
- 对方响应必须区分已接收、要求补充、审核中、全部接受、部分接受、拒绝和无响应，并保存响应方、范围、理由、证据和版本。对方响应是 VE 形成或复核外部责任结论的依据，不是最终追偿金额或真实到账结果。
- 客户合同责任、供应商责任和保险追偿责任不得合并为净责任结论。客户赔付不等待追偿完成，追偿结果也不得覆盖原客户赔付、异常事实或责任历史。
- 客户请求金额可以作为索赔来源资料保存，但客户赔付、供应商或保险追偿及其调整的最终金额由 `settlement-accounting` 形成。责任案件不得通过只保存净额隐藏未追回损失。
- `visibility-exception` 只拥有追偿通知/主张、对方响应及外部责任结论；`UC-SA-007` 唯一形成赔付和追偿金额。真实到账事实仍由财务、银行或支付来源拥有，只有 `UC-SA-005` 可以在本产品内采用该事实并形成运营到账映射与核销；前述任一步骤都不得笼统标记为“追偿成功”。

## Lifecycles

### 全程追踪投影

- 源上下文接受事实或有效性变化 → 按标准追踪里程碑映射、权威范围、业务时间和因果关系形成新的投影版本。
- 有效事实之间可以可靠排序或替代 → 重新派生各追踪维度和摘要，原投影版本继续保留。
- 有效事实冲突且无法裁决 → 投影保持信息待确认并形成适用异常信号，不虚构唯一位置或状态。
- 迟到事实、来源更正或映射版本适用性变化 → 形成新的当前投影；已经发布的客户信息通过追加更正处理。
- 源上下文随更正给出替代关系 → 登记该关系，被指名的前身条目转为已被替代并继续保留，各追踪维度按当前有效条目重新派生；原投影版本继续可按版本读回。
- 替代链分叉（同一前身被多份事实指名） → 投影保持信息待确认并形成适用异常信号，本上下文不择一，也不使任何一方失效。
- 包裹身份拆分或合并 → 来源身份保留历史，当前有效后继包裹分别继续投影；共同历史不得在多个后继包裹间被解释为重复履约。
- 授权的运营追踪查阅 → 按租户作用域读回当前投影或按版本读回留存版本；查阅不形成新投影版本，也不产生披露决定、通知或任何业务事实。

### 客户全程追踪视图

- 当前投影、客户可见 ETA、客户服务终局或已批准披露内容首次满足展示条件 → 形成货主客户账户隔离的客户视图版本。
- 客户归属确立（`parcel-shipment` 的当前已接受委托使该包裹的货主客户账户由不可反查变为可反查） → 按当前有效投影形成该货主客户账户的客户视图版本；不重放已入账的源事实，也不等待下一份源事实。
- 授权客户查询 → 按请求方、客户账户和目标对象范围返回当前有效视图；外部标识只用于定位，不能替代授权。
- 某一维信息待确认或不可披露 → 只对该维返回待确认、暂不可用或不展示，不虚构里程碑、ETA、终局或异常说明。
- 来源更正、有效性变化、身份谱系变化、ETA 新版本或终局更正 → 形成新的客户视图版本并标明更正或替代关系；原发布历史保留。
- 客户读取或门户展示 → 形成查询/展示结果，不自动形成异常披露决定、主动通知、送达或客户确认。

### 异常信号发作期

- 规则或事实首次满足条件 → 建立信号发作期，保存规则版本、范围、依据和可信度。
- 同一连续影响期重复命中 → 更新判断历史、严重度或其他信号属性，不建立重复发作期。
- 条件不再成立且满足恢复边界 → 结束当前发作期并保存解除依据；关联案件不因此自动关闭。
- 恢复后再次满足条件 → 建立关联的新发作期；是否建立或重开案件重新经过分诊规则。

### 异常案件

- 建立案件 → 固定根对象、初始影响范围、责任团队、初始优先级和响应策略，主状态为待响应。
- 待响应 → 处理中：责任团队或处理人明确接单；首次响应时间形成，后续等待、监控和升级作为工作条件管理。
- 处理中 → 已关闭：案件内必需动作已完成，问题恢复、确认无法恢复、判定不成立或剩余事项明确移交，并保存关闭结论、依据、影响范围和未决事项。
- 已关闭 → 处理中或待响应：同一因果链和处置范围出现足以影响原结论的新事实，形成受控重开及新的响应周期；原关闭历史保留。
- 待响应或处理中 → 已关闭（关闭结论：已归并）：发现重复案件时，指定主案件并核对影响范围、未决事项、证据、通知和处置请求；归并案件关闭但不删除。
- 原因、责任或处置范围分离 → 建立关联新案件并明确拆出范围；不得通过修改原案件历史制造从未共同处置的假象。

### 处置请求

- 案件形成请求 → 待源上下文处理：固定目标、动作、范围、原因、证据和时限。
- 源上下文处理 → 接受、部分接受、拒绝或要求补充：结果只表达请求判断，不证明实际执行。
- 已接受范围 → 等待实际结果：由源上下文形成重作业、改路、履约、关务或其他业务事实。
- 实际结果返回 → 对已完成范围关闭请求；失败、差异或剩余范围继续处置、重新请求或明确移交。
- 待处理且到达受理有效期 → 已到期：该范围不得再被新接受；继续需要该动作时形成关联新请求。
- 待处理或已接受范围 → 提出取消/替代意图：固定原因、目标范围、新请求（如有）和生效边界；提出意图本身不表示旧请求已经停止。
- 目标上下文处理取消 → 取消已接受、部分取消、已无法取消或拒绝取消：只有明确取消成功的未消耗范围停止未来执行，其余范围继续等待执行、实际结果或升级。

### 客户异常通知

- 披露条件成立 → 形成客户隔离的通知决定和内容快照。
- 提交消息渠道 → 分别记录渠道接受、送达、失败或客户确认；任何前一步结果都不自动生成后一步。
- 投递失败 → 按适用策略重试其他渠道或升级；原尝试和内容快照保留。
- 已发布内容需要更正 → 形成追加更正或替代通知，不覆盖原通知。

### 客户索赔项

- 客户提交 → 记录原始索赔项及所属提交批次，不自动视为已经受理。
- 资格审核 → 等待补充、不予受理或进入责任审核：结果保存合同、首次索赔期限、授权、重复关系和材料依据。
- 等待补充 → 收到材料后重新判断最低材料要求；获批延期形成新补充期限版本，原期限保留。
- 补充期限届满 → 按适用规则复核届满后果；规则明确时形成不予受理或按现有材料继续审核，规则缺失或延期效力未决时保持待决定并升级。
- 最终责任结论前收到有效撤回 → 索赔项以已撤回结束后续审核，保留提交和证据；撤回不取消异常案件或独立追偿事项。
- 责任审核 → 全部成立、部分成立、不成立或当前无法认定：结论按明确责任范围和证据形成，金额结算独立处理。
- 同一责任范围在复核期限内出现有效异议或关键新证据 → 形成受控复核和新的结论版本；原结论保留。
- 复核期限届满且无有效延期或恢复依据 → 后续复核请求形成有依据的不受理，不改变原责任结论。
- 最终责任结论或金额形成后收到撤回 → 不覆盖既有结果；需要改变责任时进入受控复核，金额差额交由 `settlement-accounting`。
- 新增包裹、索赔类型或责任范围 → 建立关联新索赔项，不修改原项身份。

### 追偿事项

- 外部通知或主张条件成立 → 按供应商、实际承运商、保险或其他责任关系分别建立追偿事项，固定责任依据、范围、期限和证据；不得因客户索赔尚未结束而延迟到超过外部期限。
- 所需通知或主张动作准备完成 → 保存相对方、内容快照、依据、范围、截止时间和要求的完成条件；仍未满足对外义务。
- 动作对外提交 → 分别记录渠道接受、送达、对方确认、提交失败或送达失败；失败可以在期限内按规则重试，原尝试保留。
- 合同允许且有效延期获得确认 → 形成新的期限版本；仅有内部批准或延期请求时仍采用原期限。
- 期限届满 → 按适用动作的提交、送达或确认要求进行失权复核；依据充分时形成失权结论，事实或条款有冲突时保持待判断。
- 对方响应 → 分别记录要求补充、审核中、全部接受、部分接受、拒绝或无响应，并据此形成或复核责任结论；无响应不自动等于拒绝或接受。
- 当前外部责任结论形成 → 向 `UC-SA-007` 提供责任版本和证据依据以形成金额；金额形成不表示已经收到资金。
- 已确认外部资金事实到达 → 只能由 `UC-SA-005` 形成运营到账映射和核销；VE 保留引用，不把通知、响应、责任接受或金额形成改写为到账。
- 后续证据或外部响应变化 → 形成新的责任结论版本，不覆盖客户赔付、其他追偿方向、原外部动作或原响应。

## Boundaries and ownership

- `visibility-exception` 拥有全程追踪投影、标准追踪里程碑、追踪摘要、客户全程追踪视图、ETA、可见性缺口判断、异常信号及发作期、异常分诊、异常案件、案件影响范围、严重度、处置优先级、响应周期、处置请求、客户可见异常、客户异常通知决定及其内容快照。
- `visibility-exception` 拥有案件内原因分析、责任结论、证据引用与评价、索赔提交批次、客户索赔项、追偿事项、追偿通知/主张动作、对方响应及其相互关系；它不拥有赔付、追偿或费用的最终金额，也不拥有实际到账和运营核销。
- `party-commercial` 拥有货主客户账户、参与方、责任法人、服务产品、客户合同、供应商协议和商业规则版本；本上下文引用这些依据形成响应、披露、索赔和责任判断快照，不修改商业版本。
- `parcel-shipment` 拥有客户委托、包裹身份及谱系、外部标识关系、客户承诺和终局服务结果；本上下文按这些身份和结果形成追踪投影，不决定委托取消、完成或包裹服务终局。
- `network-routing` 拥有网络、路线、路由计划、计划时间窗口、路由偏离和受控改路；本上下文消费计划及偏离结果形成预测、信号和案件，只能提出改路请求。
- `node-operations` 拥有节点收寄、位置、测量、扫描、状况观察、集运成员、封签和物理作业事实；本上下文引用这些事实，不认定节点动作已经发生，也不修改节点控制。
- `transport-fulfillment` 拥有场外揽收、班次、运输委托、订舱、容量、装载分配、权威交接、实际移动、实际承运商、交付结果和交付证明；本上下文不从外部状态码自行制造运输事实。
- `customs-compliance` 拥有关务案件、申报、合规判断、监管结果、关务限制及其解除；本上下文通过 `UC-VE-001` 只消费已接受事实形成异常信号、案件协调和客户披露，异常关闭、客户授权或通知结果均不能代替关务放行、限制解除、处置核对或关务案件关闭/重开。
- `settlement-accounting` 通过 `UC-SA-007` 拥有客户赔付、供应商或保险追偿、费用退款及其他运营金额的计算、版本和结算关系，并通过 `UC-SA-005` 独立采用外部资金事实、形成运营到账映射与核销；本上下文只提供当前有效责任结论、外部动作、对方响应和证据依据，不决定金额、到账或核销。
- 消息能力拥有短信、邮件、接口或其他渠道的技术提交和投递结果；本上下文拥有客户披露决定、内容快照和通知义务是否满足的业务判断。
- 身份认证、审计、文件和配置等公司级技术组件可以提供通用能力，但不得取得异常案件、证据评价、客户索赔、责任结论或全程追踪投影的业务所有权。
- 本上下文不拥有源业务事实、客户委托、包裹身份、路由计划、节点作业、运输履约、关务决定、业务限制及解除、客户服务终局、最终结算金额、银行资金或法定会计结果。
