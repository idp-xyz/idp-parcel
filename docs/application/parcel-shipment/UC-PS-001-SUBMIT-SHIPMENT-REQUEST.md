# UC-PS-001 客户提交国际小包委托并取得接受决定

状态：开发基线草案；稳定业务骨架来自已确认领域规则，生产决策点见“待确认业务决策”

## 目标与边界

本用例从货主客户确认提交一份国际小包服务请求开始，到 `parcel-shipment` 对每份委托形成可追溯的接受或拒绝决定，或者明确记录本次尚未形成业务决定为止。

本用例包含：

- 保全原始提交及来源信息，识别重复、重试和受控纠错。
- 将一次提交归组为提交批次，并按业务边界建立一份或多份委托及声明包裹。
- 校验客户与商业有效性、服务适用性、必要资料和委托成员基线。
- 对标准网络服务逐包裹取得接受前可达性判断。
- 接受时冻结不可覆盖的接受基线、商业依据和预计承诺，拒绝时保留原因与判断依据。

本用例不执行：

- 面单渠道交易、渠道选择或面单文件生成。
- 接受后的初始路由计划、班次选择、容量预占、订舱或装载分配。
- 节点收寄、场外揽收、实际运输、正式关务申报或监管提交。
- 正式承诺、终局服务结果、费用确认、对账或收付款处理。

## 参与者与上下文协作

| 参与者或上下文 | 本用例职责 | 明确不负责 |
|---|---|---|
| 货主客户 | 确认提交服务请求，提供客户声明资料 | 不能以提交动作代表运营企业已经接受 |
| 接入适配器 | 认证接入来源，保全原始内容和来源语义，转换为统一输入 | 不决定商业有效性，不直接写入已接受或已拒绝 |
| `parcel-shipment` | 建立委托与声明包裹，拥有接受或拒绝决定、接受基线和预计承诺 | 不修改客户合同、网络判断、实际履约或结算事实 |
| `party-commercial` | 提供适用时点有效的客户账户、责任法人、服务产品、合同、映射、授权及商业限制 | 不接受或拒绝具体委托 |
| `network-routing` | 对标准网络服务逐包裹形成接受前可达性判断 | 不接受委托，不锁定班次、容量或运输资源 |
| `settlement-accounting` | 在合同和信用政策明确要求时提供信用暴露、余额或资金冻结结果 | 不拥有委托接受决定；是否进入首发接受事务仍待确认 |
| 试点准入控制 | 在限量生产时决定完整委托是否由本产品承接 | 不得把试点排除或暂停伪装成客户业务拒绝 |

## 输入语义契约

下表定义稳定业务语义，不是 API、文件或数据库字段清单。客户声明是业务输入，不能直接成为客户账户、合同、产品或授权的权威事实。

| 输入组 | 客户可声明 | 权威来源 | 最低业务语义 |
|---|---|---|---|
| 来源信封 | 否 | 接入适配器与接入来源 | 接入渠道身份、来源系统或主体、接入请求标识、来源发生时间、系统接收时间、原始内容或其不可变引用、关联与重试信息 |
| 客户范围 | 仅可提供业务引用 | 接入身份与 `party-commercial` | 集团租户、货主客户账户、提交主体及其当前授权上下文必须由权威身份和商业关系解析 |
| 服务请求 | 是 | 客户原始提交；适用性由 `party-commercial` 判断 | 客户委托参考、请求的服务产品或服务要求、请求生效时间及客户明确约束 |
| 寄收件范围 | 是 | 客户原始提交 | 同一委托声明的寄件关系、收件关系、地址和目的服务范围 |
| 声明包裹 | 是 | 客户原始提交；内部身份由 `parcel-shipment` 建立 | 一个或多个客户声明成员及各自客户侧引用、声明测量、货物和服务资料 |
| 申报原始资料 | 是 | 客户原始提交 | 品名、数量、价值、币种、原产地及适用监管资料；具体必填字段由真实产品和关务区域决定 |

一次提交可以包含多份委托。提交批次只负责处理归组，每份委托独立取得结果。每份委托必须至少包含一个包裹，且其全部成员共享客户账户、合同责任法人、合同与服务产品依据、寄收件关系和目的服务范围。

具体接入渠道、请求标识范围、字段格式、枚举、必填条件和传输回执等待 `PAR-INT-01` 及真实产品、合同和线路参数确认。

### 协作判断结果

| 结果 | 权威方 | 最低业务语义 |
|---|---|---|
| 商业解析结果 | `party-commercial` | 客户账户、合同责任法人、服务产品版本、客户合同版本、适用规则、映射和账号授权；确实不适用时记录不适用原因 |
| [包裹可达性判断](../network-routing/UC-NR-002-ASSESS-PARCEL-REACHABILITY.md) | `network-routing` | 明确包裹的可达、不可达或资料不足结果，以及判断版本、依据和淘汰原因 |
| 商业限制结果 | 适用商业策略责任方；金额和余额事实由 `settlement-accounting` 提供 | 信用暴露、余额、冻结或其他接受限制的当前判断；是否启用取决于合同和 `BD-PS-003` |
| 试点生产归属结果 | 试点准入控制 | 完整拟接受成员范围由本产品承接或排除；它不是委托接受或拒绝 |

所有协作结果必须返回其判断标识、版本、判断时点、业务适用时点或区间。接受决定选择哪个业务有效时点以及提交时如何处理已过期结果，由 `BD-PS-008` 确认。

## 结果语义契约

| 结果 | 业务含义 | 必须返回或可查询的依据 | 禁止行为 |
|---|---|---|---|
| 已接受 | 运营企业明确同意承担该委托的服务请求 | 委托与包裹内部标识、接受时间、接受基线、预计承诺、商业依据及可达性判断引用 | 不得同时虚构收寄、正式承诺、路由计划、容量或实际履约 |
| 已拒绝 | 已确认接受条件不成立，或运营企业依据有效权限和理由明确不承担请求 | 委托标识、拒绝时间、结构化原因、规则与证据版本、失败范围 | 不得删除原始提交，不得把技术故障或试点排除写成拒绝 |
| 已有结果 | 当前输入被识别为已有逻辑提交的重复或重试 | 原委托标识、已有接受/拒绝/未决结果和原请求关联 | 不得创建第二份无法解释的委托 |
| 尚未决定 | 依赖不可用、并发冲突、处理失败或尚未形成权威判断，导致本次不能形成业务决定 | 委托或提交标识、当前处理阶段、未决原因、已有判断和安全续办引用 | 不得写成已拒绝，也不得创建虚假可达或默认商业依据 |
| 接入冲突 | 相同逻辑请求身份携带与原版本不一致的内容 | 原请求引用、冲突范围和纠正入口 | 不得静默覆盖原始内容或按重试再次建单 |
| 输入未受理 | 原始内容无法确定客户范围、委托边界或最小成员身份，因而尚不存在可接受或拒绝的委托 | 接入请求标识、原始内容引用、解析规则版本和确定性错误 | 不得创建占位委托或记录为委托已拒绝 |

`尚未决定`是应用处理结果，不是新增的委托终局状态。已经建立委托时，当前建议是保持`已提交`并追加判断与处理尝试；尚未建立最小委托身份时，只保留接入处理记录。最终续办语义由 `BD-PS-001` 确认。

## 接受条件

接受基线覆盖委托的完整声明成员，提交批次内各委托分别判断。单个成员不满足条件时应拒绝整份委托、允许接受前纠正或重组，还是支持成员级部分接受，仍由 `BD-PS-007` 确认；确认前不得静默删除失败成员或把试点整体准入规则当作领域接受依据。

| 校验组 | 应用反应 | 确定性不通过时 | 无法完成判断时 | 权威依据 |
|---|---|---|---|---|
| 客户关系与业务授权 | 取得权威客户账户、商业关系和适用授权 | 按适用规则拒绝 | 尚未决定 | `PC-RULE`、`PS-RULE` |
| 法人与合同 | 取得明确责任法人和当前适用客户合同版本 | 按适用规则拒绝 | 尚未决定 | `PC-RULE`、`PS-RULE` |
| 产品与服务 | 取得已发布服务产品版本并判断客户要求与适用范围 | 按适用规则拒绝 | 尚未决定 | `PC-RULE`、`PS-RULE` |
| 成员基线 | 验证至少一个包裹及同一委托共享约束 | 不得接受当前声明版本；后续处置见 `BD-PS-007` | 尚未决定 | `PS-RULE` |
| 必要资料 | 按适用产品、合同和监管范围执行版本化资料规则 | 拒绝、待补充或纠正方式由适用规则和 `BD-PS-001` 确定 | 尚未决定 | `PS-RULE` |
| 商业或信用限制 | 执行合同、信用政策及适用结算模式要求的接受限制 | 拒绝或待处置，取决于 `BD-PS-003` | 尚未决定 | `PC-RULE`、`BD-PS-003` |
| 标准网络可达性 | 为每个相关包裹保留三值判断原结果 | 明确不可达时当前声明版本不能直接接受；允许待路由产品除外，成员处置见 `BD-PS-007` | 资料不足不得映射为不可达；接受、拒绝、待补充或未决由产品、合同及 `BD-PS-001` 确定 | `NR-REACH`、`PS-RULE` |

只有服务产品明确允许待路由并保留该商业依据时，才可以在没有可行候选的情况下接受。接受后由 `network-routing` 形成`无当前有效路由`，不得创建空路由、默认路由或占位计划。

|---|---|---|---|---|

| 2 | 接入适配器 / `parcel-shipment` | 按当前接入规则识别首次提交、重复、重试或内容冲突 | 重复返回已有结果；冲突进入受控纠正，不覆盖原内容 | `ADR-FACT`、`ACCEPTANCE` |

| 3B | `parcel-shipment` | 建立提交批次、委托和声明包裹，将客户确认的请求记录为`已提交` | 数据到达或批量导入本身不形成接受 | `PS-LIFE` |
| 4 | `parcel-shipment` / `party-commercial` | 按待确认的业务有效时点解析并校验客户、法人、产品、合同、规则、映射和授权 | 保存判断标识、版本、适用区间和实际采用依据 | `PC-RULE`、`BD-PS-008` |
| 5 | `parcel-shipment` | 校验寄收件、货物、申报原始资料、服务要求和完整成员基线 | 确定性失败按适用规则处理；不能判断则保持未决 | `PS-RULE`、`BD-PS-001`、`BD-PS-007` |

| 8 | `parcel-shipment` | 通过明确的接受决定机制形成一次接受、拒绝或尚未决定结果 | 决定主体和自动/人工边界见 `BD-PS-002` | `PS-LIFE`、`BD-PS-002` |

## 决定提交边界与后续交接

- 接受状态转换、接受决定、接受基线、预计承诺和对应事件发布意图必须形成同一个最小业务提交结果，不能出现已经接受却没有基线或预计承诺的中间事实。
- 拒绝状态转换、拒绝决定、原因与证据引用、审计和对应事件发布意图必须形成同一个最小业务提交结果。
- `party-commercial`、`network-routing` 和 `settlement-accounting` 的判断由各自上下文独立形成；本用例保存所采用结果的引用与快照，不要求跨上下文分布式事务。
- 决定提交后，事件投递失败只触发关联同一发布意图的安全重试，不回退或重复形成接受、拒绝决定。
- 接受后的初始路由、关务建案及其他后续用例使用接受事件和基线引用续办；交接失败必须可重试，不得回写接受基线或把委托改为拒绝。

## 状态、记录与事件语义

### 必须持久保留的业务记录

- 原始提交及来源信封，每次纠错或重提均保留版本与原因。
- 提交批次与其包含的委托处理结果，但提交批次不拥有服务责任。
- 委托、声明包裹及提交时资料版本。
- 每项商业、资料、成员、可达性和适用限制判断的版本与依据。
- 接受或拒绝决定；未决处理尝试不得伪装为业务决定。
- 接受时不可覆盖的接受基线、预计承诺和商业依据快照。

### 业务事件语义

| 事件语义 | 最低关联内容 | 说明 |
|---|---|---|
| 委托已提交 | 来源提交、委托、声明成员和资料版本 | 不表示已经接受 |
| 委托已接受 | 接受决定、接受基线、预计承诺、商业与可达性依据 | 不能只发布一个状态字符串 |
| 委托已拒绝 | 拒绝决定、原因、规则和证据版本 | 不表示试点排除或技术失败 |

事件类名、Schema、主题、版本、投递保证和事务实现不在本用例中确定。

## 一致性、幂等与并发

- 同一逻辑提交的重复或重试不得创建第二份委托。具体请求标识组合和有效范围由真实接入渠道确定，客户参考号不能未经确认直接充当全局幂等键。
- 同一逻辑请求身份与相同内容返回已有结果；相同身份与不同内容形成接入冲突或受控纠正，不覆盖原版本。
- 一份委托的同一提交版本只能形成一个当前有效接受或拒绝决定。并发处理必须能够返回同一结果或明确冲突，不能一边接受一边拒绝。
- 接受决定必须保存来源发生时间、系统接收时间、请求生效时间、判断依据时点和决定时间各自语义，并引用实际采用的商业和判断版本。具体依据时点选择由 `BD-PS-008` 确认；提交时发现依据不再有效不得静默接受，应重新判断或形成未决结果。
- 接受结果响应丢失时，调用方必须能够通过稳定请求关联查询原结果，不能通过再次建单恢复。
- 提交批次允许各委托独立成功、拒绝或未决，不使用全批回滚掩盖已经合法形成的单份委托决定。
- 人工纠错必须形成新资料或提交版本、原因和操作审计，并重新经过适用校验；不能成为绕过主入口规则的第二条接单路径。

## 权限、隐私与审计

- 接入身份必须解析到明确集团租户、货主客户账户和提交授权，任何查询和回执均按客户账户隔离。
- 委托接受或主动拒绝的实际决定主体、授权角色和依据必须留痕；具体自动或人工边界尚待确认。
- 审计至少关联原始提交、标准化版本、来源与接收时间、校验规则版本、跨上下文判断、决定、操作主体、决定时间和返回结果。
- 客户寄收件与货物资料按最小必要原则处理；日志、错误信息、导出和跨客户批次回执不得泄露其他客户的存在、业务量或内容。
- 人工操作不得直接覆盖接受基线、判断历史、原始提交或派生状态。

## 可观测性与非功能验收占位

- 从接入请求、提交批次、委托、包裹、接受判断尝试到各上下文判断结果必须使用可追溯的关联标识，不能只依赖日志文本查找。
- 分别观测接入保全、去重、解析、商业校验、资料校验、可达性判断、决定提交和结果投递的耗时与失败位置。
- 分别统计输入未受理、接受、拒绝、未决、重复、接入冲突、纠正和依赖失败，原因维度引用稳定规则或判断标识，不使用自由文本聚合。
- 记录事件发布积压、重试和最终投递结果；发布延迟不得被解释为接受决定尚未形成。
- 日志、指标和追踪不得包含不必要的寄收件、地址、货物或申报明文，也不得形成跨客户可见关联。
- 可用性、响应时间、批处理窗口和恢复目标由 `PAR-NFR-06` 及验收矩阵 `NFR-02` 参数化，本文件不填写未经真实数据确认的数值。

## 首发试点叠加条件

本节只约束首发运行，不改变长期用例：

- 仅由 `PAR-INT-01` 确认的锚点客户当前主用渠道进入生产接入；其他渠道只做设计或模拟验证。
- 在委托接受前按版本化准入规则判断完整委托是否进入 `idp-parcel`。同一委托及其拟接受成员必须整体纳入或整体排除。
- 试点排除、暂停或旧系统承接是生产归属结果，不是客户业务拒绝。生产交接方式由 `BD-PS-004` 和 `PAR-GOV-03` 确认。
- 已纳入的委托不因后续试点暂停或回退被自动取消、拆分或迁回旧系统。

## 验收示例

| ID | 场景 | 预期结果 |
|---|---|---|
| `AT-PS-001` | 有效客户、合同和标准网络产品；多包裹资料完整且每包可达 | 整份委托被接受，成员基线和预计承诺冻结；没有虚构收寄、正式承诺、容量或实际履约 |
| `AT-PS-002` | 同一提交批次内两份委托，一份有效，另一份含不满足条件的成员 | 两份委托分别判断；不得因批次关系全批回滚，也不得静默删除失败成员后接受，具体成员处置见 `BD-PS-007` |
| `AT-PS-003` | 同一逻辑请求以相同内容重试 | 返回原委托和原结果，不创建第二份委托 |
| `AT-PS-004` | 同一逻辑请求身份携带不同内容 | 返回冲突或进入受控纠正；原始提交和原决定不被覆盖 |
| `AT-PS-005` | 标准网络服务的任一包裹明确不可达 | 当前声明版本不能直接接受；保存包裹级不可达判断和淘汰依据，不创建占位路由，委托成员处置见 `BD-PS-007` |
| `AT-PS-006` | 可达性判断为资料不足 | 保留资料不足原结果且不映射为不可达；接受、拒绝、待补充或未决按适用产品、合同和 `BD-PS-001` 处理 |
| `AT-PS-007` | 产品明确允许待路由且当前无可行候选 | 委托可以接受并保存允许依据；接受后形成无当前有效路由，不创建空路由 |
| `AT-PS-008` | 商业或路由依赖超时 | 本次不形成接受或拒绝；已建立委托时按 `BD-PS-001` 的当前建议保持已提交并安全续办 |
| `AT-PS-009` | 接受后客户合同或产品发布新版本 | 既有接受基线继续引用原版本，新版本不追溯覆盖历史 |
| `AT-PS-010` | 试点准入规则排除整份委托 | 本产品不取得该委托生产权威；不得记录为客户业务拒绝或只纳入部分包裹 |
| `AT-PS-011` | 接受成功后检查下游对象 | 可以触发后续路由与关务用例，但本用例没有创建实物收寄、正式申报、班次、费用或终局结果 |
| `AT-PS-012` | 原始内容无法确定客户范围、委托边界或最小成员身份 | 形成输入未受理并保留接入依据，不创建占位委托或委托拒绝决定 |
| `AT-PS-013` | 接受决定提交成功但事件首次投递失败 | 委托仍为已接受且基线、预计承诺完整；重试同一发布意图，不重复接受或回退决定 |

## 开发拆分建议

在上述决策未全部关闭前，可以先实现：

1. 渠道中立的提交命令与原始来源保全接口。
2. 提交批次、委托、声明包裹和资料版本的稳定身份模型。
3. 可替换的去重策略接口、同键冲突保护和结果查询。
4. `party-commercial` 商业依据查询与快照契约。
5. [`UC-NR-002`](../network-routing/UC-NR-002-ASSESS-PARCEL-REACHABILITY.md) 定义的包裹级可达性请求、三值判断与应用未决契约。
6. 委托级接受决策编排，以及接受基线和预计承诺的不可变持久化边界。
7. 接受、拒绝和未决三类应用结果及对应审计；只把前两类写成业务决定。
8. 本文验收示例的领域与应用测试骨架，真实字段和阈值使用显式未配置状态，不使用虚构默认值。

在 `BD-PS-001` 至 `BD-PS-008` 及相关试点参数确认前，不应宣称真实生产接单流程已经完整，也不应发布固定渠道 Schema、拒绝码或客户 SLA。
