# UC-PS-005 撤回尚未决定的客户委托

状态：稳定业务骨架待实现；真实撤回授权、客户回执和财务补偿参数待提供

## 目标与边界

本用例从客户或其当前有效授权代表请求撤回一份仍为`已提交`的委托开始，到 `parcel-shipment` 形成不可覆盖的撤回决定、返回已经先行形成的接受/拒绝结果、保持业务未决，或明确本次请求未受理为止。

撤回只终止整份尚未决定的服务请求，不是运营企业拒绝，也不删除原始提交、提交版本、接受判断历史或财务控制结果。委托已经接受后，客户对一个、多个或全部包裹提出的取消或停止服务请求转入 [`UC-PS-006`](./UC-PS-006-CANCEL-PARCEL-OR-COORDINATE-POST-INTAKE-DISPOSITION.md)；委托已经拒绝或撤回后产生的新服务需求形成关联新委托。

本用例包含：

- 保全撤回请求、目标委托、来源、请求方、授权、原因和业务时间。
- 在同一决定提交边界裁决撤回、接受和拒绝的并发竞争。
- 停止尚未完成的接受判断任务，并保留已有阶段和结果。
- 对已形成的接受前资金冻结发出使用原业务关联的显式释放请求。
- 区分撤回已成立、已有决定、未决、输入未受理和技术未形成。

本用例不执行：

- 删除客户来源、提交版本、判断记录、估价、冻结或审计历史。
- 将撤回记为运营企业拒绝，或为客户制造拒绝原因。
- 对已接受委托形成撤回决定、取消单个已接受包裹、修改接受基线或回退已发生事实。
- 直接修改 `settlement-accounting` 拥有的冻结；本用例只发出并续办关联释放请求。

## 输入与结果语义

| 输入或结果 | 最低业务语义 | 约束 |
|---|---|---|
| 撤回请求 | 租户、客户账户、委托、来源请求身份、请求方、授权、原因、来源发生/接收时间 | 客户备注或连接中断不构成撤回 |
| 当前委托决定 | 当前提交版本、接受判断任务、接受/拒绝/撤回决定及其提交边界 | 不按缓存状态或消息到达顺序裁决 |
| 财务控制引用 | 原估价、冻结、控制策略、业务关联和当前有效性 | 不新建零金额释放或跨账户补偿 |
| 撤回已成立 | 撤回决定、决定时间、请求/授权依据、任务停止和发布意图 | 不生成拒绝决定 |
| 已有决定 | 已先行提交的接受、拒绝或撤回引用 | 后到请求不覆盖原决定 |
| 撤回未决 | 已知事实、缺口、判断版本和续办入口 | 不默认撤回或接受 |

## 应用流程

| 步骤 | 责任方 | 应用动作 | 结果与下一步 |
|---:|---|---|---|
| 1 | 接入适配器 | 保全撤回来源、请求身份、对象、请求方和业务时间 | 重复返回原处理；冲突不覆盖 |
| 2 | `parcel-shipment` | 校验租户、客户账户、委托范围和请求方当前授权 | 越权不泄露其他客户对象 |
| 3 | `parcel-shipment` | 读取当前提交版本、接受判断任务和已提交决定 | 非`已提交`委托返回已有结果或正确后续入口 |
| 4 | `parcel-shipment` | 在决定提交边界重新检查并提交撤回 | 与接受/拒绝竞争，只有一个决定成立 |
| 5 | `parcel-shipment` | 同一提交保存撤回、任务停止、审计和发布意图 | 不删除判断历史 |
| 6 | `settlement-accounting` | 按原业务关联幂等形成适用冻结释放 | 失败时续办原补偿，不回滚撤回 |
| 7 | 接入适配器 | 返回撤回、已有决定、未决或未受理结果 | 响应丢失时按稳定请求关联查询 |

## 规则、补偿与并发

- 撤回只作用于整份待决委托。对当前提交版本删除成员或改变共享服务范围，应形成符合边界的新提交版本或关联新委托，不能借撤回部分成员绕过判断。
- 撤回、自动接受、人工接受和主动拒绝竞争同一不可覆盖决定边界。首个合法提交结果获胜；事务开始顺序、客户端时间和消息到达顺序都不能单独裁决。
- 撤回提交成功后不等待财务释放才生效。释放失败形成可续办补偿；不得为了保持表面原子性恢复接受判断或把委托改回`已提交`。
- 接受已经合法提交但回执或事件失败时，后到的决定前撤回请求不得释放合法冻结；应返回接受结果并由客户选择 `UC-PS-006` 的后续路径。
- 相同来源请求身份与内容重复时返回原撤回或原已有决定；同身份不同内容形成来源冲突，不重复撤回或释放。
- 已撤回委托不能原地恢复。客户重新提出服务需求时建立关联新委托并重新执行生产归属与接受判断。

## 首发试点叠加条件

- `PAR-INT-01` 必须明确撤回来源身份、客户回执和结果查询契约。
- `PAR-COM-14` 必须明确客户及运营代表的撤回授权、原因语义和有效期间。
- `PAR-COM-15` 必须明确撤回成立时适用冻结的释放条件、补偿责任，以及无财务控制或未形成冻结时的不适用依据；`PAR-SET-01/02` 只提供原冻结采用的结算账户和销售价格依据。实际释放和补偿核对仍由 `settlement-accounting` 按原业务关联幂等形成，参数不拥有释放结果。
- 参数未确认时可以实现状态竞争、幂等、显式未配置和补偿任务骨架，不得默认任何角色有撤回权或伪造释放成功。

## 给开发的交接

实现必须把“撤回来源 → 授权判断 → 唯一决定提交 → 接受任务停止 → 财务释放补偿”保留为可追溯关系。撤回提交和财务释放不得通过分布式事务绑成一个可阻塞决定，也不得把释放失败改写为撤回失败。
