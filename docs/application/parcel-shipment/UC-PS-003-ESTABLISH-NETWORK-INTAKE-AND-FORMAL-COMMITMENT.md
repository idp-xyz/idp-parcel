# UC-PS-003 形成有效网络收寄与正式承诺

状态：稳定业务骨架已形成；真实收寄资格、承诺规则、来源与非功能参数待提供

## 目标与边界

本用例从 `parcel-shipment` 收到一项可关联到明确包裹的节点收寄或场外揽收结果开始，到它逐包裹形成有效网络收寄采用结果、责任起点和正式承诺，或者形成不适用、资格未决、来源冲突或不采用结果为止。

客户送站和场外揽收保留不同事实所有者：

- 客户直接送达节点的节点收寄由 `node-operations` 通过 [`UC-NO-002`](../node-operations/UC-NO-002-RECEIVE-CUSTOMER-DELIVERED-PARCEL.md) 形成。
- 上门揽收或场外接货由 `transport-fulfillment` 通过 [`UC-TF-002`](../transport-fulfillment/UC-TF-002-PERFORM-OFFSITE-PICKUP.md) 形成。
- `parcel-shipment` 不复制物理事实，只把合格来源统一解释为网络服务的有效网络收寄，并形成客户责任结果。

本用例包含：

- 校验来源所有者、包裹、接受基线、业务时间、控制依据和当前有效性。
- 根据接受时固定的产品、合同和服务规则完成适用资格判断。
- 使用物理收寄实际发生时间形成责任起点，而不是使用消息或处理时间。
- 逐包裹形成正式承诺并保留预计承诺。
- 处理重复、迟到、冲突、更正、取消并发和结果投递失败。

本用例不执行：

- 节点收寄、场外揽收、扫描、测量、位置或运输控制事实。
- 委托接受、拒绝、成员级重新接受或接受基线修改。
- 路由计划、ETA、班次、容量、装载、运输、关务或结算。
- 以正式承诺覆盖预计承诺，或以计划、预测和实际结果修改客户承诺。
- 包裹终局服务结果；正式承诺生效不等于服务已经完成。

## 关键业务区分

| 概念 | 所有者 | 形成条件 | 不能替代 |
|---|---|---|---|
| 委托接受 | `parcel-shipment` | 接单硬规则和权威结果成立 | 实物收寄、责任起点 |
| 节点收寄 | `node-operations` | 客户直接送站且节点明确接收、取得控制 | 场外揽收、正式承诺 |
| 场外揽收 | `transport-fulfillment` | 运输履约实际接收对象并取得控制 | 节点收寄、正式承诺 |
| 有效网络收寄 | `parcel-shipment` | 合格物理来源、接受基线、包裹和适用资格共同成立 | 原物理事实、终局结果 |
| 预计承诺 | `parcel-shipment` | 委托接受时形成 | 正式承诺、ETA |
| 正式承诺 | `parcel-shipment` | 有效网络收寄及适用资格成立 | 路由计划、ETA、实际结果 |

委托接受仍按当前提交版本形成整份委托决定；有效网络收寄和正式承诺按包裹独立形成。一个包裹已经收寄不等待同委托其他包裹，也不能替其他包裹形成责任起点。

## 启动条件

- 目标委托已经合法接受，接受决定、接受基线、预计承诺和目标包裹引用完整。
- 来源是 `node-operations` 的节点收寄或 `transport-fulfillment` 的场外揽收，而不是普通扫描、卸载、车辆到场、任务创建或面单结果。
- 来源包含对象、实际发生时间、地点、控制依据、结果版本和来源当前有效性。
- 接受时适用的产品、合同和正式承诺规则可以解析；真实资格组成未配置时保持未决。

已经取消、已经终局或被身份谱系替代的包裹仍可产生真实节点或运输事实。该事实必须保全，但不能自动重开服务、恢复路由或形成新的正式承诺。

## 适用资格判断

资格判断至少分别核对：

1. 来源所属租户、客户账户、责任法人和包裹与接受基线一致。
2. 包裹是网络服务接受范围中的当前适用身份，来源发生时没有更早生效的合法取消或终局结果。
3. 来源所有者、收寄模式、地点、控制依据和业务时间符合锚点产品及合同规则。
4. 物理来源结果当前有效且没有未解决的身份、对象范围或证据冲突。
5. 产品和合同规定的收寄阶段硬资格已经形成；缺失、过期或冲突不能默认通过。

资格目录和时点规则必须由 `PAR-COM-16` 实例化。本用例不得把路由可用、班次存在、ETA、费用已算或消息已送达添加成隐藏资格。

合同或产品在委托接受后发生普通版本变化时，不追溯替换接受基线。具体收寄仍使用接受时固定的服务责任依据及其明确规定的收寄阶段条件；是否存在必须按收寄时重新判断的资格，必须在该规则版本中显式声明。

## 结果语义契约

| 结果 | 业务含义 | 必须保存 | 禁止行为 |
|---|---|---|---|
| 正式承诺已形成 | 来源和资格成立，包裹进入网络服务责任范围 | 有效网络收寄采用结果、来源引用、责任起点、正式承诺版本、预计承诺引用、规则和业务时间 | 覆盖预计承诺、复制物理事实或形成终局 |
| 资格判断未决 | 来源存在，但身份、规则、限制或权威结果不足 | 已知来源、判断阶段、缺口、采用版本和续办入口 | 默认形成承诺、伪装业务拒绝或丢弃实物事实 |
| 来源不采用 | 来源真实存在，但不属于该包裹当前网络服务责任起点 | 来源、原因、取消/终局/身份或范围依据及业务时间 | 删除源事实、回写节点/运输结果或自动处置实物 |
| 不适用 | 目标服务不是运营企业承担网络责任的服务形态 | 产品、合同、包裹和不适用依据 | 用不适用代替来源缺失或资格失败 |
| 已有结果 | 同一来源版本已形成采用或不采用结果 | 原结果、承诺或未决引用和当前有效性 | 重复责任起点、正式承诺或发布意图 |
| 来源冲突 | 同一采用身份携带不同包裹、来源版本或内容 | 原请求、冲突范围、来源和纠正入口 | 覆盖原结果或以最后到达为准 |

`资格判断未决` 是本用例的处理结果，不是包裹服务生命周期状态。节点或运输履约已经成立的控制不会因本用例未决而消失。

| 2 | `parcel-shipment` | 识别首次、重复、冲突、迟到或来源新版本 | 重复返回已有结果；冲突保留原结果 |
| 3 | `parcel-shipment` | 核验来源类型、所有者、对象、控制依据、地点、业务时间和当前有效性 | 普通扫描或任务结果不能升级为收寄 |
| 4 | `parcel-shipment` | 核验包裹在来源发生时的接受、身份谱系、取消和终局边界 | 更早取消/终局或被替代身份不自动重开 |

| 6B | `parcel-shipment` | 来源真实但不属于当前服务责任起点时形成不采用 | 保留物理事实并交明确处置入口 |
| 6C | `parcel-shipment` | 证据或规则不足时保存未决任务和续办位置 | 不形成正式承诺 |
| 7 | `parcel-shipment` | 同一提交保存有效网络收寄采用结果、责任起点、正式承诺、审计和对应发布意图 | 任一步失败不产生半份客户责任结果 |

## 正式承诺形成规则

- 正式承诺以明确包裹为对象，保存责任方、受益客户、产品、合同、服务范围、承诺内容、来源、版本和生效边界。
- 生效业务时间来自被采用的实际节点收寄或场外揽收时间。处理时间、消息到达时间和事件发布时间不能替代。
- 正式承诺必须引用预计承诺，但不能覆盖预计承诺。预计承诺、正式承诺、路由计划、ETA 和实际结果分别存在。
- 路由计划、预计到达或现实履约变化不能静默修改正式承诺。允许调整时必须形成带原因的新版本并保留原承诺。
- 事件投递失败不回退正式承诺；只重试同一发布意图。
- 正式承诺不等待具体班次、容量、节点实测、ETA、关务提交或运输开始，也不表示包裹已经终局。

## 一致性、幂等与并发

- 同一包裹、同一来源类型和同一来源结果版本只能形成一个有效网络收寄采用结果。
- 客户送站与场外揽收都指向同一包裹时不能形成两个责任起点。先合法形成者保留，后续来源作为重复、冲突或后续物理事实处理。
- 多包裹委托逐包裹提交；一个成员未决或不采用不回滚其他成员已经形成的正式承诺。
- 取消与收寄并发按权威业务时间和生效边界裁决，不按消息到达顺序。已经发生的物理事实始终保留。
- 来源更正、撤销或身份关系变化形成新的采用判断版本。原责任判断和承诺历史不能删除；当前承诺影响通过带原因的新版本表达。同来源更正以来源所有者声明的更正关系识别——新版本自报更正的恰是该包裹当前采用的那一版；来源种类相同而无更正声明的新版本按上一条作竞争处理（[ADR-0117](../../adr/0117-same-source-correction-forms-a-superseding-adoption-version-chained-to-the-current-responsibility-start.md)）。
- 提交结果不确定时按稳定关联查询原采用结果、承诺和发布意图，不盲目重复提交。

## 权限、隔离与审计

- 采用判断必须在明确租户、客户账户、责任法人、委托、包裹和来源范围内执行。
- 自动判断只能使用已发布且适用的产品和合同规则。人工处理不能绕过硬资格、伪造来源或修改物理事实。
- 批量处理和查询不泄露其他客户来源、包裹、合同或承诺内容。
- 审计至少关联接受决定、基线、预计承诺、包裹、来源所有者、物理结果、业务时间、控制依据、资格规则、逐项判断、正式承诺、决定方和发布状态。
- 客户地址、联系人、货物和申报明文只按最小必要使用，不进入普通日志、指标或测试输出。

## 首发试点叠加条件

- `PAR-NET-13` 必须明确首发真实收寄模式、生产启用范围和各来源所有者。
- `PAR-COM-05`、`PAR-COM-06` 和新增 `PAR-COM-16` 必须提供锚点产品、合同、有效网络收寄资格、责任起点和正式承诺规则。
- 客户送站分支消费 `PAR-NET-04..06`；场外揽收分支消费 `PAR-NET-07` 和外部来源适用时的 `PAR-INT-03`。
- `PAR-NFR-01/02/06` 提供真实观察期、业务量和正式承诺处理/恢复目标。
- 未确认时可以实现强类型来源联合、逐项资格、重复/冲突、逐包裹提交、显式未配置和安全续办；不得填写默认资格、承诺时效、责任起点或来源优先级。

| `AT-PS-052` | 跨租户或客户提交来源采用请求 | 拒绝越权且不泄露目标来源、包裹或承诺 |

## 给开发的交接

实现必须保留“物理来源 → 来源采用判断 → 有效网络收寄 → 责任起点 → 正式承诺”的关系，不能把节点或伙伴状态直接写成包裹 `received/committed` 状态。

当前代码只存在建单前身份、来源重放/冲突和最小委托候选；尚无已接受聚合、包裹服务、收寄采用、正式承诺、持久化事务或 Outbox。可以先建立纯业务端口、结果类型和命名夹具，但真实写入必须等待 PN-02 前置、`PAR-COM-16`、`PAR-NET-13` 和技术门槛。

完成本用例只闭合网络服务责任起点和正式承诺，不证明路由仍适用、节点作业完成、运输已经开始或包裹已经终局。
