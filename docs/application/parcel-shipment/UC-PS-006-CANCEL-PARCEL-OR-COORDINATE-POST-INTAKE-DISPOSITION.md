# UC-PS-006 取消包裹或协调收寄后服务处置

状态：稳定业务骨架待实现；真实取消授权、收寄后处置规则、伙伴能力和费用参数待提供

## 目标与边界

本用例从客户或授权运营角色请求取消已接受委托中的一个或多个包裹，或请求停止其后续服务开始。`parcel-shipment` 逐包裹核验当前有效事实：尚未越过适用取消边界时形成包裹取消决定；已经越过边界时明确拒绝回退取消，并依据当前产品、合同、限制和授权形成收寄后服务处置决定、保持处置未决或明确拒绝。

取消决定、收寄后处置决定、下游承接、实际拦截/改送/退运/终止执行以及最终服务结果是不同事实。本用例不建立跨上下文的“停止中”总状态，也不直接改写路由、节点、运输、关务或结算对象。

本用例包含：

- 保全请求方、实际决定方、授权、原因、目标包裹、期望处置和业务时间。
- 逐包裹核验接受基线、当前身份谱系、终局、有效网络收寄和适用取消边界。
- 在边界前形成取消终局；在边界后形成明确处置决定、未决或拒绝结果。
- 向各对象所有者发送范围化释放或执行请求，并分别保存承接与执行关联。
- 对批量请求允许逐包裹部分成功，不以整单状态覆盖成员差异。

本用例不执行：

- 删除包裹、接受基线、面单、节点作业、交接、移动、申报、费用或其他已发生事实。
- 把客户消息、异常、拒收、无路由、停运或限制自动解释为取消、退运或终止决定。
- 直接作废面单、释放容量、修改路由、关闭关务案件、安排车辆或确认退运完成。
- 通过服务变更原地替换客户账户、责任法人、合同、产品、寄收件关系或新增服务件；这些需求形成关联新委托。

## 决定矩阵

| 当前包裹事实 | 本用例可以形成 | 本用例不得形成 |
|---|---|---|
| 已接受，尚无有效网络收寄或其他适用非取消边界 | 授权成立时形成包裹取消决定和取消终局 | 删除身份、接受基线或既有交易 |
| 收寄事实存在但有效性或业务顺序待确认 | 取消/处置未决，续办事实核对 | 先取消后等事实，或按消息晚到忽略收寄 |
| 有效网络收寄已经先行成立 | 收寄后服务处置决定、未决或拒绝 | 回退为已取消 |
| 已有终局服务结果 | 返回既有终局；新服务需求建立关联委托 | 重开原结果或追溯取消 |
| 包裹已被谱系后继替代 | 对当前有效后继重新明确请求范围 | 把来源包裹决定自动扩散给后继 |

## 规则、一致性与并发

- 取消权按包裹判断。一个委托的部分包裹取消、部分已经收寄或部分已经终局时，各自结果并存；只有全部当前有效包裹均为取消终局且不存在非取消终局时，委托才派生为`已取消`。
- 取消决定提交前必须重新读取当前有效收寄和终局版本。收寄与取消并发时，以不可覆盖业务决定边界及权威事实的业务发生顺序裁决，不以消息到达或客户端时间最后写入覆盖。
- 收寄后处置决定必须引用当前产品、合同、客户授权、责任法人、限制及可执行性依据。任何必要依据缺失时保持未决，不默认退运、销毁、继续或免除费用。
- 处置决定只能请求尚未消耗范围释放或未来动作。已经形成的面单交易、节点控制、权威交接、实际移动、申报、监管决定和费用责任分别按其所有者规则保留。
- 监管、安全或其他硬限制的来源责任方拥有解除和适用动作决定；客户服务处置不能绕过仍有效限制。监管退运使用 `UC-TF-001`，普通/商业退运使用 `UC-TF-007`。
- 重复请求返回原逐包裹结果；同一请求身份内容冲突不覆盖。提交结果不确定时按稳定关联查询原决定和发布意图。

## 给开发的交接

实现必须保留“取消或停止服务请求 → 边界核验 → 取消或收寄后处置决定 → 下游独立承接与执行 → 包裹终局”的关系。禁止提供一个可以把已收寄包裹直接改为`cancelled`的通用接口，也不得以批量操作、异常案件或运输状态替代逐包裹业务决定。
