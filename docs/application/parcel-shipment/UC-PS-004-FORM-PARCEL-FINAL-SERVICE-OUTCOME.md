# UC-PS-004 依据履约结果形成包裹终局服务结果

状态：稳定业务骨架待实现；真实网络服务终局规则、退运责任和其他合同责任结果参数待提供

## 目标与边界

本用例从权威源提供明确包裹的有效交付、退运完成、服务终止、监管处置执行或其他可验证责任结果开始，到 `parcel-shipment` 依据接受时固定的服务产品、客户合同和当前有效终局规则，逐包裹形成终局服务结果、保持终局未决或明确不采用该来源为止。适用取消边界前的包裹取消由 [`UC-PS-006`](./UC-PS-006-CANCEL-PARCEL-OR-COORDINATE-POST-INTAKE-DISPOSITION.md)形成并直接进入终局汇总，不由本用例从履约结果反推。

各来源上下文只拥有自己的监管决定、节点执行、运输交接、实际移动、派送尝试、POD、有效交付或处置事实；`parcel-shipment` 唯一拥有包裹服务终局。任何单一来源是否足以形成终局都由适用服务产品和合同规则决定；班次完成、运输段关闭、POD 上传、外部状态码、异常案件或客户通知不能单独形成终局。

本用例包含：

- 接收并保全履约结果、来源版本、对象范围、业务时间和当前有效性。
- 校验包裹身份、接受基线、服务产品、客户合同、身份谱系和既有终局历史。
- 按版本化终局规则逐包裹形成终局、未决、不采用、重复或冲突结果。
- 对多包裹委托派生部分完成/全部完成摘要，不建立脱离包裹事实的委托完成状态。
- 处理迟到、重复、冲突、POD 更正、履约结果失效和发布失败。

本用例不执行：

- 创建或修改运输交接、实际履约段、派送尝试、POD、有效交付或退运旅程。
- 修改接受基线、预计/正式承诺、路由计划、ETA、异常案件、客户通知、索赔或结算。
- 把完成后的正常费用调整、渠道作废或退款改写为委托取消。
- 由人工按钮直接把包裹或委托设置为已完成。

## 终局形成规则

- 包裹终局以明确包裹和适用服务产品为对象，保存责任法人、客户、合同、终局类型、来源、版本和生效边界。
- 网络服务按合同约定的有效交付、退运完成、服务终止、监管处置执行或其他网络责任结果判断终局，不统一规定一个跨产品终局结果集合；来源矩阵只定义责任分层，不把任何候选来源默认配置为终局。
- 有效交付通常同时结束相应运输控制，但是否形成包裹终局仍由本用例按合同判断；POD 上传、班次关闭、轨迹“妥投”或通知送达不能替代。
- 退运决定、退运旅程开始和退运执行完成分别存在；只有满足合同终局规则的责任结果才可形成包裹终局。
- 包裹发生真实拆分/合并后，来源身份继续保留但退出当前有效包裹集合；终局汇总使用当前有效身份和谱系，不能重复计算来源与后继。
- 一个包裹终局不等待同委托其他包裹；委托部分完成是逐包裹结果的派生摘要。
- 终局形成后不得回退为取消。后续费用调整、异常、索赔、追偿或客户通知有独立生命周期。
- 来源更正或有效性变化保留原事实、原终局判断及当时派生历史，形成新的当前判断版本；这不是删除历史或业务重开。

## 一致性、幂等与并发

- 同一包裹、来源身份和来源版本只能形成一个终局采用判断。
- 多包裹委托逐包裹提交；一个成员未决、冲突或不采用不回滚其他成员合法终局。
- 交付、退运、服务终止和来源更正并发时按权威业务时间、适用边界和当前有效事件裁决，不按消息到达顺序。
- 当前有效终局只能由规则支持的来源有效性变化重新派生；人工角色不能直接删除或改写终局。
- 提交结果不确定时查询原判断、委托派生和发布意图，不重复形成终局。
- 批量查询、导出和完成摘要按租户、客户账户、责任法人、委托和包裹隔离。

## 给开发的交接

实现必须保留“运输履约来源 → 来源采用判断 → 包裹终局服务结果 → 委托完成派生”的关系。禁止把外部 `DELIVERED`、班次完成、实际段结束、POD 文件存在或通知送达直接写成包裹 `completed`。

完成本用例只闭合包裹服务终局及委托完成派生；追踪、异常、索赔、供应商追偿、客户费用和经营结算仍由各自上下文独立形成。
