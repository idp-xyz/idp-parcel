# UC-PS-001 生产接单业务决策简报

状态：批量建议，待业务确认；本文件中的建议不得视为已确认领域规则

## 目的

本简报集中处理 [`UC-PS-001`](./UC-PS-001-SUBMIT-SHIPMENT-REQUEST.md) 中阻塞真实生产接单的八项业务决策。它给出可以整体确认的推荐口径，避免继续逐项问答；在业务责任方明确确认前，开发只能保留扩展点和测试骨架，不能把推荐值固化为产品规则。

本简报不确定 API、字段、错误码、技术超时、重试次数、客户 SLA，也不填写真实客户、合同、线路、关务区域或资金参数。

## 批量建议摘要

| ID | 推荐结论 | 当前状态 | 确认后的主要落点 |
|---|---|---|---|
| `BD-PS-001` | 建立独立的接受判断任务；依赖未决不伪装为拒绝，确定性资料不合格按适用规则处置 | 待确认 | 应用任务、续办、通知与状态投影 |
| `BD-PS-002` | 版本化硬规则全部通过时自动接受；主动拒绝仅允许授权角色按结构化依据形成 | 待确认 | 接受命令、权限、审计与事件 |
| `BD-PS-003` | 合同明确选择预付冻结、账期信用校验或接受前无财务控制；只执行被选模式 | 待确认 | 接单与结算协作及补偿 |
| `BD-PS-004` | 在领域接受前判定试点生产归属；排除默认由仍具权威的旧系统承接，不能安全交接时保持归属未决 | 待确认 | 新旧系统入口路由与生产权威 |
| `BD-PS-005` | 已提交未决采用同一委托的新提交版本；已拒绝后修正建立关联新委托；已接受后走独立变更用例 | 待确认 | 身份、版本、幂等与客户回执 |
| `BD-PS-006` | 按产品、合同、关务区域和有效期组合版本化校验规则；渠道错误映射为稳定业务原因 | 待确认 | 规则装配、校验器与错误语义 |
| `BD-PS-007` | 不支持委托成员级部分接受；失败成员必须在接受前显式纠正或重组 | 待确认 | 委托不变量、接受基线与重组流程 |
| `BD-PS-008` | 分离五类时间；由服务端控制判断依据时点，提交前失效的依据必须重新判断 | 待确认 | 版本选择、并发裁决与审计 |

八项决策的落点不同：`BD-PS-001`、`BD-PS-002`、`BD-PS-005`、`BD-PS-007` 和 `BD-PS-008` 是长期接单机制；`BD-PS-003` 和 `BD-PS-006` 只能先确认通用机制，真实合同模式和字段仍由证据决定；`BD-PS-004` 是试点运行治理，不写成长期领域不变量。

## 逐项推荐口径

### `BD-PS-001` 未决接受判断如何续办

**推荐决定**

- 为已经建立的委托创建独立、可追溯的接受判断任务；任务是应用处理机制，不新增委托领域状态。
- 依赖不可用、权威判断尚未形成、并发冲突或可安全恢复的处理失败时，本次返回`尚未决定`，委托保持`已提交`，并从已保存阶段继续判断。
- `network-routing` 返回`资料不足`时必须保留原语义。适用产品、合同和资料规则可以决定补充、纠正或确定性拒绝，应用层不得统一把它映射为不可达或固定拒绝。
- 客户可补充的资料缺口进入待补充动作；系统依赖故障进入查询或重试，两者使用不同原因和续办方式，不能都归为“等待客户”。
- 判断任务必须保存当前阶段、缺少的权威结果、已经采用的版本、最后处理结果和可安全续办引用。只有版本化产品或合同规则明确规定补充期限及届满后果时，届满复核才可以形成确定性拒绝；否则只能升级给授权角色继续处置。通知渠道、补充时限和升级参数等待真实合同与 `PAR-NFR-06` 参数化。
- 无法建立最小委托身份的输入继续使用`输入未受理`，不能为了进入任务机制创建占位委托。

**边界示例**

商业规则服务暂时不可用时保持未决并重试；适用规则已经明确某项必要资料缺失且该产品不允许补充时，才形成确定性业务拒绝。

### `BD-PS-002` 自动接受与主动拒绝边界

**推荐决定**

- 当前适用的版本化硬规则、商业限制和包裹级可达性要求全部通过后，由系统自动形成接受决定，不再增加无业务依据的人工审批门槛。
- 规则未通过时按权威规则形成拒绝、待补充或未决结果；人工操作不能把硬规则失败改成通过，也不能跳过缺少的权威判断。
- 只有适用规则本身明确要求人工业务判断时，才进入人工复核；人工复核不是所有委托的默认步骤。
- 运营企业主动拒绝只允许适用责任法人授权的角色形成，并必须记录结构化原因、证据、适用范围、授权依据、实际决定方和决定时间。
- 主动拒绝只作用于尚未接受的委托。已经接受后的停止服务、取消或变更进入各自独立用例，不回写为接单拒绝。
- 是否针对某个产品或客户保留人工接受门槛，必须作为版本化商业规则显式配置；默认不创建一条隐藏的人工接单路径。

**边界示例**

规则全部通过但运营企业因已授权且有证据的风险原因不承担请求时，可以主动拒绝；普通客服备注或临时口头决定不能产生拒绝事实。

### `BD-PS-003` 接受前财务控制模式

**推荐决定**

- 每个适用合同版本必须明确选择`预付冻结`、`账期信用校验`或`接受前无财务控制`之一，不同时运行互相冲突的门槛；未配置不能被解释为默认放行。
- 预付模式在接受前取得版本化估价并形成足额资金冻结结果；冻结失败时不得接受。接受提交失败时必须按同一业务关联请求释放冻结，不能遗留无委托责任的占用。
- 预付冻结在委托被拒绝、放弃或冻结依据失效时也必须显式释放；重复查询、重试和补偿不得形成重复冻结或重复释放。
- 账期模式在接受前校验适用信用额度、信用暴露、逾期或暂停规则；除非合同另有明确约定，账期校验不同时冻结资金。判断不通过时按合同政策拒绝或进入授权处置，不能用人工备注绕过。
- 接受前无财务控制模式必须保存合同版本和明确的“不适用”依据；它不代表后续不计费、不结算或没有信用治理。
- 任何必需的财务判断无法确定时保持未决，不得按余额充足、额度可用或无需控制处理。
- 金额、余额、冻结和信用暴露由 `settlement-accounting` 提供，价格和商业政策仍由其权威上下文提供，`parcel-shipment` 只保存接受时采用的结果与依据。
- 跨上下文采用可补偿编排，不要求分布式事务。接受决定只有在适用商业前置结果成立后才能提交；接受提交完成后，事件投递失败不得释放已经合法占用的资金或回退接受决定。

**边界示例**

预付冻结成功但接受提交并发失败时执行关联释放；接受已经提交但回执丢失时查询原决定，不得再次冻结或再次接受。合同明确选择接受前无财务控制时，本用例记录不适用，不调用冻结或信用判断冒充额外门槛。

### `BD-PS-004` 试点生产归属与业务接受分离

**推荐决定**

- 在进入 `idp-parcel` 的领域接受流程前，对完整拟受理委托形成版本化生产归属结果。
- 未纳入试点或暂停新准入时，不建立 `idp-parcel` 的业务拒绝决定。推荐默认交给仍是该范围唯一生产权威的旧系统；无法证明请求可以安全交接时，只保留`生产归属未决`的接入记录，不向任一系统伪造接受或拒绝。
- 客户首先取得渠道中立的接收或查询关联，最终业务结果由被选中的唯一权威系统返回。旧系统交接、结果回传和失败兜底由 `PAR-GOV-03` 至 `PAR-GOV-07` 及上线方案参数化。
- 同一逻辑委托在同一业务时点只能有一个生产权威接受方。入口必须携带稳定关联，禁止同时向新旧系统投递后由结果先到者决定归属。
- 归属规则按完整委托及拟接受成员判断，不以包裹级拆分规避试点范围。已经由 `idp-parcel` 接受的委托不因后续暂停被迁回或改写。

**边界示例**

试点容量已满时，该输入可以由旧系统继续处理，但 `idp-parcel` 不能记录“客户委托已拒绝”，也不能只接受其中部分包裹。

### `BD-PS-005` 纠错、重提与委托身份

**推荐决定**

- 委托处于`已提交`且尚未决定时，客户纠错在同一委托下形成新的提交版本并重新判断；原始版本、变更原因、提交主体和判断历史永久保留。
- 同一委托同一时刻只有一个待判断的当前提交版本；旧版本继续可追溯，但不能与新版本并行取得接受决定。
- 只有客户范围、委托边界和最小成员身份仍可确认属于同一业务请求时，才沿用原委托身份。改变客户账户、合同责任范围、寄收件关系或目的服务范围的修正必须重新确定委托边界。
- 普通资料补充可以沿用原委托；为了剔除失败成员、拆分成员或改变成员共享约束而进行的重组，必须形成一份或多份关联新委托，并明确原成员去向，不能伪装成同一委托的字段纠错。
- 委托已经`已拒绝`后，修正请求建立关联的新委托，并明确来源、替代或重提关系；不把终局拒绝原地重开为已提交。
- 委托已经`已接受`后，资料更正、服务变更、成员取消或新增服务件进入独立变更、取消或关联新委托用例，不复用接单纠错通道覆盖接受基线。
- 去重应区分同一版本的重试与明确的新提交版本。相同版本返回已有结果，不同版本必须保留关联并重新校验。

**边界示例**

已提交委托补充缺少的申报资料可以形成新提交版本；已拒绝委托补齐资料后建立关联新委托；已接受委托新增包裹必须形成关联新委托。

### `BD-PS-006` 可执行校验规则与稳定原因

**推荐决定**

- 建立由服务产品、客户合同、关务区域、适用法人、服务范围和有效时间共同选择的版本化校验规则组合。组合只装配各权威上下文拥有的规则，不建立一个可以覆盖其他上下文事实的“万能规则库”。
- 规则组合至少区分接入最小身份、委托通用不变量、产品与合同资料、监管原始资料和跨字段条件五层；正式关务判断仍由 `customs-compliance` 拥有，不能前移为接单字段校验。
- 每次判断保存实际采用的规则标识、版本、有效区间、输入事实版本和结果；新版本不追溯改写既有接受或拒绝依据。
- 每项结构化结果至少表达适用对象或字段范围、结果确定性、是否可纠正、建议处置和客户可见消息键；`输入未受理`、业务拒绝和未决使用不同原因目录。
- 对外接入字段由适配器映射为稳定业务语义。渠道字段名、枚举和临时错误不能进入核心领域模型成为永久规则。
- 业务结果使用稳定、可分级的原因标识，并保留原渠道或外部错误作为来源证据；不得用自由文本代替可统计原因，也不得丢失原始返回。
- 必填字段、跨字段条件和真实原因目录只能在锚点产品、合同、线路及关务参数提供后发布，当前不得用行业经验填充默认值。

**边界示例**

两个渠道用不同字段表达同一申报价值时，适配器分别映射到同一业务语义；具体产品规则决定是否必填，渠道字段名不进入接受不变量。

### `BD-PS-007` 多包裹委托是否部分接受

**推荐决定**

- 不支持成员级部分接受。一份委托的当前提交版本只形成一个委托级接受或拒绝决定，接受基线覆盖该版本的全部声明包裹。
- 任一成员确定性不满足接受条件时，整份当前提交版本不能接受；可纠正问题按 `BD-PS-001` 和 `BD-PS-005` 形成补充版本或关联重提。
- 某个成员不满足接受条件时，不得静默删除该成员后接受剩余成员，也不得先接受再补做拆分。
- 客户或授权运营角色可以在接受决定前显式纠正成员；需要删除、拆分或重新组合成员时，必须按委托共享约束形成一份或多份关联新委托，并保留原提交、成员去向、重组原因和关联。
- 重组后的每份委托分别校验和决定。提交批次仍允许不同委托分别接受、拒绝或未决，不扩大为整批原子处理。
- 本项确认后，应先把“不支持成员级部分接受”及接受前重组边界写入 [`parcel-shipment` 权威上下文](../../domain/parcel-shipment/CONTEXT.md)，再把 `UC-PS-001` 中的引用改为已确认规则。

**边界示例**

三个包裹中一个明确不可达时，系统不能只接受另外两个。客户可以在决定前明确重组，重组后的委托各自取得完整决定。

### `BD-PS-008` 判断有效时点与提交失效

**推荐决定**

- 分别记录来源发生时间、系统接收时间、客户请求生效时间、判断依据时点和接受/拒绝决定时间，不使用一个通用“业务时间”代替。
- 来源发生时间和系统接收时间用于溯源、去重和因果排序；客户请求生效时间可以参与服务日历、地址范围和可达性判断，但不能单独控制商业资格版本。
- 客户关系、合同、产品、授权、信用和接受权限必须在服务端形成接受决定的业务时点有效。各类判断依据时点由服务端依据版本化产品和合同政策选择，客户不能通过回填时间恢复旧合同资格或绕过当前限制。
- 每个跨上下文判断必须返回判断时间、明确的 `asOf` 语义、采用版本、有效区间和当前修订标识；`parcel-shipment` 保存实际采用的引用与快照。
- 决定提交前复核所有关键判断仍覆盖所选依据时点且当前未被有效限制推翻。依据失效、被替代或出现并发冲突时重新判断；暂时无法完成时返回未决，不以旧结果接受。
- 已经合法提交的接受或拒绝不因规则后来更新而被静默重写；纠错或有效性变化通过新版本和明确关系处理。

**边界示例**

可达性判断完成后、接受提交前线路被有效关闭时，必须重新判断；接受提交完成后才发布的新线路版本不能追溯改写原接受依据。

## 组合后的接单机制

八项建议整体采用后，接单编排形成以下稳定顺序：

1. 入口先判定生产归属并保全原始提交；同一委托只进入一个生产权威。
2. 建立委托及提交版本，创建或续办接受判断任务。
3. 按服务端控制的判断依据时点取得商业、资料、可达性和适用资金/信用结果。
4. 失败成员在决定前显式纠正或重组，不进行成员级部分接受。
5. 硬规则全部通过时自动接受；确定性不通过按适用规则处置，依赖未决保持已提交。
6. 主动拒绝只由授权角色按结构化依据形成。
7. 接受、拒绝、未决、纠错和重提都保留来源、版本、决定与事件发布关联。

该顺序是业务机制，不等于 API 调用顺序、数据库事务布局或消息拓扑。

## 确认与落地规则

- 业务责任方可以一次性确认本简报全部建议，也可以只列出例外项；未被明确确认的项目继续保持`待确认`。
- 确认后，先更新拥有相应不变量或生命周期的权威领域文档，再更新应用用例和验收示例，避免本简报成为第二套领域定义。
- `BD-PS-003`、`BD-PS-004` 和 `BD-PS-006` 即使业务机制确认，仍需真实合同、上线方案和试点参数才能进入生产。
- 任何确认都不自动批准真实金额、阈值、角色名单、渠道 Schema、超时、重试次数或 SLA。
