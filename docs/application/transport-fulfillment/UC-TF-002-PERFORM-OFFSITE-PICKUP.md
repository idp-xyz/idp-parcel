# UC-TF-002 执行场外揽收并形成运输控制

状态：稳定业务骨架已形成；真实揽收模式、履约方、来源与非功能参数待提供

## 目标与边界

本用例从一份已接受网络服务中的明确包裹需要上门揽收或场外接货开始，到 `transport-fulfillment` 建立揽收任务、记录每次实际尝试，并逐载运对象形成场外揽收成功、失败、拒收或待确认结果为止。

成功场外揽收必须证明运输履约范围已经实际接收明确实物并取得控制。预约成功、车辆到场、司机扫描、预报、订舱或电子数据接收都不能替代该结果。

本用例包含：

- 将需要完成的揽收任务与每次实际到场尝试分开。
- 对多包裹任务逐对象保存成功、失败、拒收和待确认结果。
- 成功时形成运输控制、履约参与关系和适用实际履约段起点。
- 对已经实际发生且满足外包协议事实条件的失败或成功尝试形成运输收费发生项，供结算独立判断供应商成本。
- 保全重复、迟到、冲突、更正和外部来源不确定性。
- 将对象级场外揽收结果交给 `parcel-shipment` 判断有效网络收寄和正式承诺。

本用例不执行：

- 委托接受、包裹取消、正式承诺或终局服务结果。
- 客户送站形成的节点收寄。
- 节点收货、测量、分拣、集运、封签或节点与运输方之间的后续权威交接。
- 班次绑定、干线订舱、容量预占、装载分配、正式关务申报或费用确认。
- 失败后的自动重试、自动终止或自动退运；后续动作必须来自适用产品、合同和授权规则。

## 参与者与协作

| 参与者或上下文 | 本用例职责 | 明确不负责 |
|---|---|---|
| 揽收运营 | 依据当前服务和执行条件建立或安排任务 | 不以任务状态形成实际揽收 |
| 实际执行方 | 提供到场、点验、接收、拒收、失败和控制证据 | 不决定客户服务终局或合同规则 |
| `transport-fulfillment` | 拥有任务、尝试、逐对象结果、运输控制和实际履约参与 | 不形成客户承诺或节点收寄 |
| `parcel-shipment` | 提供包裹身份、接受基线、服务要求和当前取消/终局结果；后续统一解释有效网络收寄 | 不修改揽收尝试、控制或履约事实 |
| `network-routing` | 提供当前适用计划揽收段、地点和时间窗口；后续消费实际接货位置 | 不认定实际揽收或运输控制 |
| `party-commercial` | 提供自营或外包责任、伙伴协议和服务条件版本 | 不认定具体任务已经完成 |

自营揽收保存真实运营法人和执行责任，不虚构供应商协议。外包揽收保存合作伙伴、实际采用协议与履约条件快照，但签约服务商、渠道品牌或代理商不能自动被认定为实际承运商。

## 启动条件

- 委托已经接受，目标包裹属于接受基线中的当前有效包裹，并具有可追溯场外揽收服务要求。
- 任务能够引用适用服务产品、合同、责任法人、揽收地点、时间窗口和对象范围。
- 当前路由计划、计划揽收段或明确的待路由揽收政策能够支持本次动作；没有依据时不得用默认目的节点安排揽收。
- 自营或外包执行责任、来源身份和证据规则可明确解析；真实值未确认时保持未配置。

包裹取消、限制或路由变化与实际揽收并发时，先保全已经发生的来源事实，再按业务发生时间和各自边界判断。系统不能删除已经实际取得控制的事实，也不能用迟到消息追溯合法化不应执行的新任务。

## 结果语义契约

| 结果 | 业务含义 | 必须保存 | 禁止推导 |
|---|---|---|---|
| 场外揽收已形成 | 明确载运对象已被运输履约实际接收并进入控制 | 任务、尝试、对象、地点、业务时间、执行方、证据、控制起点、履约参与和来源版本 | 正式承诺、节点收寄、到站、干线装载或服务终局 |
| 本次尝试失败 | 对象未被接收且运输方未取得控制 | 任务、尝试、对象、失败原因、地点、时间和证据 | 任务结束、委托拒绝、取消、退运或终局 |
| 运输收费发生项已形成 | 已实际发生的尝试满足采用协议要求的成本来源条件 | 采购责任法人、伙伴、协议、尝试、对象范围、原因、数量/单位、业务时间和来源 | 客户费用、供应商金额、账单主张、应付或付款 |
| 本次对象被拒收 | 执行方明确未接收该对象且未取得控制 | 对象、原因、责任方、证据和此前控制方 | 其他对象拒收、客户服务终局或费用结论 |
| 揽收结果待确认 | 已有来源但不足以证明接收、控制或对象范围 | 已知事实、冲突、当前控制、缺口和查询入口 | 默认成功、默认失败或创建实际履约段 |
| 已有结果 | 相同任务/尝试来源和内容已经处理 | 原结果、来源和当前有效性 | 重复控制、重复履约参与或重复正式承诺 |
| 来源冲突 | 同一来源身份携带不同对象、时间或结果 | 原来源、冲突内容、证据和纠正入口 | 最后到达覆盖 |
| 来源未受理 | 提交自身矛盾或最小身份不全（如成功缺控制依据、失败带控制依据、对象集为空），未进入处理 | 拒绝答复与纠正入口 | 保存半份尝试、形成任何结果或发布意图；与依赖故障的未决混为一格 |

任务汇总只能由各对象结果派生。一项任务可以同时包含成功、失败、拒收和待确认对象，不能用“部分成功”遮蔽成员结果。

## 任务、尝试、控制与履约

- 任务说明需要完成什么，尝试说明某次实际上门发生了什么，场外揽收结果说明对象是否被实际接收，四者不能合并为一个状态。
- 车辆到场、司机签到、拍照、扫描或客户签字中的任一项都不是跨场景绝对充分条件。证据规则必须按真实揽收模式登记。
- 成功对象取得运输控制并形成履约参与；失败、拒收或待确认对象保持此前已确认的控制关系。
- 一次失败不自动结束任务。是否再次尝试、改约、终止或交由客户送站，必须使用适用产品、合同和授权规则。
- 一次失败尝试不自动等于应收费或免费。外包协议要求的到场、等待、拒收或失败事实满足时，本上下文形成范围和原因明确的运输收费发生项；供应商预期成本和审核应付由结算形成。
- 后续重试、改约或成功揽收是新的尝试和新的成本来源范围，不能覆盖第一次失败尝试，也不能把多个尝试压缩为一笔无来源成本。
- 场外揽收成功不等于包裹已经进入节点。后续到站、卸载和节点侧扫描只是来源证据，节点控制必须等待 `transport-fulfillment` 的权威交接结果。

## 一致性、幂等与并发

- 同一尝试来源身份和内容返回已有结果；同一身份不同内容形成冲突。
- 同一对象在同一尝试中只能有一个当前有效结果；更正或来源撤销形成新判断版本。
- 同一实际控制范围不能因伙伴重投、任务重建或批量重试重复建立履约参与。
- 取消先有效且实物尚未取得控制时不得继续新增揽收；揽收事实先发生时必须保留，由 `parcel-shipment` 按业务边界判断服务影响。
- 结果提交不确定时先查询任务、尝试、控制和发布意图，不盲目重放揽收成功。
- 外部伙伴状态迟到时按业务发生时间采用；无法证明实际接收和控制时保持待确认。

## 权限、隔离与审计

- 任务建立、改约、终止和结果纠正必须在明确责任法人、伙伴、服务范围和授权内执行。
- 执行人员可以提交来源证据，不得自行修改客户合同、正式承诺、包裹身份或路由。
- 多客户同车揽收允许执行归组，但客户账户、合同、结果和可见数据逐对象隔离。
- 审计至少关联任务、尝试、对象、接受基线、路由版本、地点、窗口、执行方、伙伴/法人、业务时间、来源、证据、控制、结果和发布状态。
- 日志、指标和测试不得保存不必要的客户地址、联系人、货物或申报明文。

- `PAR-NET-13` 明确首发启用客户送站、场外揽收或两者，以及各自生产范围和权威来源。
- 场外揽收分支必须取得 `PAR-NET-07` 的履约方、方式、责任与交接证据；外部来源还必须取得 `PAR-INT-03`。

- `PAR-COM-05`、`PAR-COM-06` 必须提供真实产品、合同和揽收服务范围；`PAR-COM-16` 由下游 `UC-PS-003` 消费，缺失时阻断正式承诺，不阻止本用例如实保存已经发生的揽收来源事实。

## 给开发的交接

实现必须保留“揽收任务 → 履约尝试 → 对象级揽收判断 → 运输控制与履约参与”的层次，不能使用一个 `pickup_status` 覆盖。

当前仓库尚无 `transport-fulfillment` 代码、真实伙伴接入、任务持久化或事件闭环。先实现纯业务骨架和命名夹具时，外部伙伴、地点、证据、重试、时限和容量必须保持显式未配置。

完成本用例只形成场外揽收的权威来源和适用运输收费发生项。`parcel-shipment` 仍须通过 `UC-PS-003` 判断有效网络收寄与正式承诺，`settlement-accounting` 独立形成供应商成本，后续进入节点控制必须通过 PN-04 的权威运输交接。
