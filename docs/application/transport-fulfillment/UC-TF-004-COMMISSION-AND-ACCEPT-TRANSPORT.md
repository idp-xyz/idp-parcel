# UC-TF-004 建立运输委托、订舱并取得承运接受

状态：稳定业务骨架待实现；真实供应商协议、订舱来源、承运接受和容量授权参数待提供

## 目标与边界

本用例从 [`UC-TF-003`](./UC-TF-003-PREPARE-TRANSPORT-OPPORTUNITY.md) 提供运输机会和容量准备范围开始，到 `transport-fulfillment` 对明确对象形成运输委托、订舱申请及其处理结果、承运接受、容量预占和装载分配准备为止。

本用例只处理运输执行的商业与容量准备。承运接受不等于实际承运，订舱不等于实物收寄，装载分配不等于物理装载或权威运输交接。实际控制由 [`UC-TF-005`](./UC-TF-005-ESTABLISH-HANDOVER-AND-ACTUAL-FULFILLMENT.md) 形成。

本用例包含：

- 形成运输委托并固定实际采用的供应商协议、履约条件和责任快照。
- 对订舱申请形成待确认、候补、部分确认、确认、拒绝、取消或失效结果。
- 对承运接受逐对象/逐范围形成接受、部分接受、待补充或拒绝。
- 按容量维度建立、转换、释放和到期预占，避免同一范围重复扣减。
- 形成总单、运输舱单或外部承运凭证的业务引用和版本，但不把单证成员视为已装载。
- 对订舱、取消和已发生运输准备范围形成可供结算消费的运输收费发生项，但不形成价格、供应商预期成本或审核应付。
- 处理重复、迟到、冲突、更正、外部不透明和发布失败。

本用例不执行：

- 节点物理装载、节点侧交出或节点与运输方的权威交接。
- 实际承运商最终身份、实际履约段、出发、移动、到达或交付。
- 路由计划或客户承诺修改、关务申报/放行、异常案件或费用结算。

## 业务规则

- 申请量、接受量、预占量、分配量、释放量和实装量分别存在；部分结果不能压缩为一个最终数量。
- 订舱申请不自动扣减容量；只有当前有效预占或明确转换关系才影响可用容量。
- 硬容量和法规限制不可通过人工授权突破。软容量超配必须引用版本化规则、影响范围和授权决定。
- 运输委托或订舱取消只停止尚未消耗范围；已形成承运接受、预占、分配、交接或履约事实继续保留。
- 签约服务商、渠道品牌、代理商、底层承运商和实际承运商分别保存；没有有效收寄/交接证据时实际承运商可以待确认。
- 运输单证草稿、提交、外部接受、拒绝、撤销和更正分别保存；提交后成员变化建立新版本。
- 外部接口返回“已发送”或“已接收”只证明来源处理层，不自动表示承运接受、装载或移动。
- 同一对象可以因容量不足部分接受并在后续机会继续处理；不得因为部分拒绝而删除已接受范围。
- 订舱确认、取消请求、取消已接受、取消被拒绝和服务已经开始分别保存；任何单一结果都不能直接推导供应商金额为应付或为零。
- 运输收费发生项必须固定本次实际采用的协议、原因、主要业务范围、成员、数量与单位、业务时间及来源。后续伙伴或协议变化不能把发生项搬到当前伙伴或当前旅程。
- 订舱和取消可以分别形成发生项；取消只停止尚未发生的范围，不删除原订舱发生项或已经开始的服务范围。金额、免收条件和贷项由结算按采购规则判断。

## 一致性、幂等与并发

- 同一委托/订舱/外部结果版本只能形成一个采用结果；相同身份内容不同形成冲突。
- 取消、释放、承运接受和节点交接并发时以业务时间和有效边界裁决；已发生事实不回退。
- 容量释放只能归还尚未消耗的有效预占；实装和已交接范围不得被释放动作覆盖。
- 结果提交不确定时查询原结果和发布意图，不盲目重复外部提交或创建第二份委托。
- 批量请求逐对象/逐维度隔离，部分成功不回滚其他对象；跨客户查询遵循最小授权。
- 来源更正、外部凭证替代和承运商身份补充形成新版本，原来源、原判断和历史保持可追溯。

## 给开发的交接

实现必须把“运输委托、订舱、承运接受、容量预占、装载分配和单证”分别建模。不要用一个 `booking_status` 或 `accepted` 状态代表所有结果，也不要以订舱或承运接受直接创建实际履约段。

完成本用例只证明运输准备、承运接受和运输收费发生事实可被追溯；可执行价格和纯评价由 `parcel-pricing` 形成，供应商预期成本、账单主张和审核应付由 `settlement-accounting` 形成，权威运输交接、实际承运、移动、交付和包裹终局由后续用例分别形成。
