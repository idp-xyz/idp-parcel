# UC-TF-006 执行派送并形成交付证明

状态：稳定业务骨架待实现；真实尾程履约方、交付方式、POD 规则和失败处置参数待提供

## 目标与边界

本用例从明确载运对象已经由尾程履约方取得运输控制，或适用路由要求建立末端派送任务开始，到 `transport-fulfillment` 形成派送任务、每次实际履约尝试、逐对象交付/失败/拒收/待确认结果，以及满足规则的有效交付和交付证明（POD）为止。

有效交付是收件方边界的专用权威运输交接结果。外部“已妥投”状态、到场、照片、签名或消息送达中的任一单项都不自动构成有效交付；必须结合适用服务产品、客户合同、交付方式和证据规则判断。

本用例包含：

- 把派送任务与每次实际尝试分开，并按包裹记录对象级结果。
- 保存执行方、计划窗口、到场地点、实际业务时间、尝试原因和来源证据。
- 按交付方式校验本人签收、安全投放、智能柜、邻居代收、验证码或其他合格 POD。
- 对部分交付、失败、拒收、地址错误、无人、证据不足和外部结果冲突形成独立结果。
- 对已经实际发生且满足外包协议事实条件的派送尝试形成运输收费发生项，不把失败、成功或重试直接解释为金额。
- 将有效交付和未完成对象交给 `UC-PS-004` 或后续退运/替代处置。

本用例不执行：

- 末端伙伴采购、路线计划、班次容量或干线实际履约。
- 自动重派、自动退运、客户赔付、异常案件、通知送达或结算。
- 包裹取消、包裹终局或客户承诺修改。

## 结果语义契约

| 结果 | 业务含义 | 必须保留 | 禁止行为 |
|---|---|---|---|
| 派送任务已形成 | 固定地点、时间范围、规则和对象 | 目标对象、窗口、执行责任、版本和原因 | 不表示已到场或已交付 |
| 尝试已成功 | 该次尝试对对象完成了可接受动作 | 到场、对象、结果、证据和业务时间 | 不一定等于有效交付 |
| 尝试失败 | 未完成对象交付动作 | 失败原因、证据、对象和重试入口 | 不自动等于退运或终止 |
| 运输收费发生项已形成 | 已实际发生的派送尝试满足采用协议要求的成本来源条件 | 采购责任法人、伙伴、协议、尝试、对象范围、原因、数量/单位、业务时间和来源 | 客户费用、供应商金额、账单主张、应付或付款 |
| 尝试拒收 | 收件方/执行方明确拒绝本次交接 | 对象、拒收方、原因和时间 | 不等于已签收或已退回 |
| 尝试待确认 | 证据不足或来源冲突 | 全部来源、当前控制和复核入口 | 不按外部最后状态码裁决 |
| 有效交付已形成 | 适用规则和 POD 满足，控制转移到收件方 | 对象、尝试、承运方、时间、地点、方式、接收方、POD 和规则版本 | 不由通知送达或单个状态码替代 |
| 交付证据待补充 | 有动作但证据尚未满足规则 | 已知动作、缺口和期限/入口 | 不先形成有效交付 |
| 交付结果更正 | 原证据失效、补充或被替代 | 原证据、原判断、新版本和影响范围 | 不删除历史或按最后消息覆盖 |

## 派送与交付规则

- 一个任务可以覆盖多个对象，但每个对象的成功、失败、拒收、待确认和交付结果分别成立；任务汇总只能派生。
- 每次实际到场形成新尝试。改约、重派或替代不能重开或覆盖旧尝试。
- 无人、地址错误、包装不合格、收件人拒收或证据不足不构成有效交付；当前运输方继续承担已成立的控制责任。
- 有效交付必须关联明确对象、实际履约段/尝试、业务时间、地点、接收方、交付方式和符合当时规则的 POD。
- 安全投放、智能柜、邻居代收、本人签收、验证码和其他方式只能在适用产品、国家地区和客户合同允许时使用。
- 外部承运商状态码、照片、签名、扫描或客户通知中的单项不能自动形成有效交付；冲突时保持待确认。
- 失败尝试不自动结束任务、实际履约段或客户服务；是否重试、改约、退运或终止由适用产品、合同和授权决定。
- 失败、拒收、成功交付和再次派送都不自动等于应收费或免费。外包协议要求的实际到场、等待、失败原因或交付范围满足时，本上下文形成运输收费发生项；`parcel-pricing` 形成 BUY 纯评价，`settlement-accounting` 再形成费用金额责任。
- 每次实际尝试分别保留成本来源范围。后续成功、重派或退运不能删除第一次失败尝试，也不能把多次尝试压缩为一笔无法追溯的供应商成本。
- POD 被更正或失效时保留原证据和判断，形成新版本并重新派生当前交付与控制结果。

## 一致性、幂等与并发

- 同一任务、尝试、对象和来源版本只能形成一个结果；相同内容重复回传返回原结果。
- 交付与退运/重派、取消、异常并发时按业务时间和有效边界裁决；已形成交付不被消息顺序回退。
- 部分对象交付不自动结束任务或其他对象的控制；每个对象分别交给终局或后续处置。
- 证据保存成功但交付派生或发布失败时，从同一证据恢复，不重复到场或要求执行方再次签收。
- 任何人工更正保存决定方、授权、原因和生效时间，不能直接编辑 `delivered` 状态绕过 POD 规则。
- 跨客户派送任务只提供当前执行所需的最小对象和地址信息；查询、导出和照片访问按授权隔离。

## 首发试点叠加条件

- `PAR-NET-09`、`PAR-NET-15` 提供真实尾程履约方、交付方式、控制边界和 POD 规则；`PAR-INT-03/07` 提供外部交付/证据来源及更正语义。
- `PAR-COM-05/06` 提供产品、合同、收件范围、交付责任和服务终局边界。
- 外包尾程费用分支还必须取得 `PAR-SET-03` 的真实供应商协议、尝试费用发生条件与结算责任；缺失时如实保存尝试，但不得默认金额或应付。
- `PAR-NET-11` 仅在真实退运路径纳入时提供拒收/退运责任；否则失败只形成受控待办或 `S` 验证结果。
- `PAR-NFR-02/04/06` 提供尾程量、证据放大、新鲜度和恢复目标。
- 未确认时可以实现任务/尝试/逐对象结果、POD 证据集合和显式待确认；不得默认签名、照片、验证码或自动妥投规则。

## 给开发的交接

实现必须把“派送任务 → 履约尝试 → 逐对象结果 → POD → 有效交付 → 控制转移”分开建模。不能用一个 `delivery_status` 代替失败、拒收、待确认和有效交付，也不能把消息送达或外部状态码直接写成包裹终局。

完成本用例只证明运输履约形成了可解释的交付结果和适用运输收费发生项；`parcel-shipment` 是否据此形成终局服务结果由 [`UC-PS-004`](../parcel-shipment/UC-PS-004-FORM-PARCEL-FINAL-SERVICE-OUTCOME.md) 独立判断，供应商成本由 `settlement-accounting` 独立形成。
