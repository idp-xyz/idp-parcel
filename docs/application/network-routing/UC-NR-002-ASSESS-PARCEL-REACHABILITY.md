# UC-NR-002 评估包裹接受前可达性

状态：开发基线；三值判断、服务端判断时点和提交前失效重判机制已确认，真实网络与时点参数仍待登记

## 目标与边界

本用例由 `parcel-shipment` 在委托接受判断期间按包裹发起，到 `network-routing` 形成`可达`、`不可达`或`资料不足`的包裹级可达性判断，或者明确记录本次尚未形成领域判断为止。

本用例包含：

- 使用明确委托、提交版本和包裹身份建立判断范围。
- 引用客户地址、声明测量、货物资料、服务要求及商业资格，不取得这些来源事实的所有权。
- 按判断适用时点解析服务区域，装配网络、服务日历、可用性调整、关务资格、硬限制和路由策略版本。
- 评估是否至少存在一条满足当前服务要求和硬约束的逻辑路径，并保存候选与淘汰依据。
- 严格区分三值业务判断、应用处理未决、重复、冲突和不适用。
- 把独立判断及其证据交回 `parcel-shipment`，由后者决定委托是否接受。

本用例不执行：

- 委托接受、拒绝、待补充、成员重组或客户回执决定。
- 接受后的初始路由计划、当前有效路线选择或无当前有效路由判断。
- 班次选择、容量判断或预占、运输委托、订舱、装载分配和实际履约。
- 正式关务建案、申报资料定稿、监管提交、监管受理或放行。
- 客户承诺、ETA、费用、异常案件或客户通知。

## 三组结果必须分离

| 阶段 | 所有者 | 结果 | 业务含义 |
|---|---|---|---|
| 接受前可达性 | `network-routing` | 可达、不可达、资料不足 | 当前证据下是否存在满足服务要求和硬约束的逻辑路径 |
| 委托接受 | `parcel-shipment` | 已接受、已拒绝；应用层也可尚未决定 | 运营企业是否承担客户服务请求 |
| 接受后初始路由 | `network-routing` | 初始路由计划、无当前有效路由；应用层也可判断未决 | 已接受包裹当前准备按什么路径履约，或者当前没有有效计划 |

## 启动条件

- `parcel-shipment` 已经建立最小委托身份、当前提交版本和明确包裹身份；无法建立这些身份的输入仍由 `UC-PS-001` 处理为输入未受理。
- 接受前只能使用当前提交版本和声明快照。虽然上下文地图的跨阶段关系同时列出声明快照和接受基线，但本用例发生时接受基线尚未形成，不能提前引用或构造。
- 请求能够关联客户账户、责任法人、服务产品或服务要求，以及需要判断的服务目的。商业解析暂时不可用时，本用例可以接收请求，但不能伪造商业资格。
- 请求提供由 `parcel-shipment` 按接单规则包时点策略为本次可达性判断解析的明确 `asOf` 语义和值或可追溯引用；`network-routing` 必须校验并回显实际采用值。客户请求生效时间可以参与服务日历判断，但不能自行恢复已失效的商业资格或限制，也不得用一个全局时间代替可达性判断的时点语义。
- 仅提供面单渠道服务且运营企业不控制端到端网络时，本用例不适用；网络服务或明确允许待路由的产品仍可请求判断。
- 委托尚未形成与本提交版本冲突的接受或拒绝决定。迟到请求仍需保留处理记录，但不得覆盖已经采用的判断或接受依据。

## 结果语义契约

| 结果 | 业务含义 | 必须返回或可查询的依据 | 禁止行为 |
|---|---|---|---|
| 可达 | 至少存在一条已经完整验证、满足当前服务要求和硬约束的逻辑路径 | 判断、包裹、提交版本、适用时点、网络与规则版本、至少一个合格候选及评估依据 | 不得表示委托已接受、路线已选定、承诺已形成或资源已锁定 |
| 不可达 | 候选范围和必需权威证据完整，所有可能候选均被确定性淘汰 | 判断、包裹、提交版本、适用时点、完整候选范围及逐候选淘汰依据 | 不得直接形成委托拒绝，不得用空路线或默认路线表达 |
| 资料不足 | 已经形成有效业务判断，但缺少或无法确定的业务证据使当前不能证明可达或不可达 | 判断、包裹、缺少的业务证据、受影响候选、已采用版本及再次判断条件 | 不得映射为不可达，不得用技术异常、超时或程序错误冒充 |
| 已有判断 | 相同请求身份、相同输入版本和相同判断适用时点已经形成结果 | 原判断及其输入、结果、版本和当前适用性 | 不得重复创建同一判断或用较晚响应覆盖它 |
| 未形成判断 | 依赖超时、计算失败、持久化失败、提交冲突或输入版本已经失效，导致本次没有形成三值领域结果 | 请求、处理阶段、失败或冲突位置、已有输入和安全续办引用 | 不得伪装为资料不足、不可达或可达 |
| 可达性请求冲突 | 同一请求身份携带不同输入、提交版本、包裹或适用时点 | 原请求、冲突范围、来源版本和纠正入口 | 不得静默覆盖原请求或原判断 |
| 可达性请求未受理 | 请求主体无权、租户或客户范围不一致，或者无法关联最小包裹判断身份 | 请求与来源、权限或身份错误及处理依据 | 不得创建占位判断或修改委托 |
| 不适用 | 适用服务不要求运营企业判断网络可达性 | 包裹、服务产品和明确不适用依据 | 不得以不适用代替不可达，也不得虚构运营网络 |

`可达`、`不可达`和`资料不足`是 `network-routing` 拥有的领域判断。其余结果是本用例的应用处理结果，不得进入三值统计或被 `parcel-shipment` 当作可达性事实。

`资料不足`形成后，由 `parcel-shipment` 按适用产品和合同规则进入客户补充、内部核实、确定性拒绝或保持委托尚未决定；客户补充与内部查询或重试使用不同原因和续办路径。本用例只返回缺失证据及再次判断条件。

## 证据判定矩阵

| 当前证据状态 | 本用例结果 | 判定要求 |
|---|---|---|
| 至少一个候选已经完整验证为满足服务要求和全部适用硬约束 | 可达 | 任何仍缺少的全局证据都不能推翻该候选；否则仍为资料不足 |
| 候选空间已经闭合，所有候选均由有效权威依据确定性淘汰 | 不可达 | 必须证明不存在尚未评估、证据未知或版本失配的可能候选 |
| 没有候选被证明可达，且地址、声明、资格、限制或候选证据存在明确业务缺口 | 资料不足 | 必须指出缺少什么、影响哪些候选以及补充后如何重新判断 |
| 权威依赖无法调用、计算中断、持久化失败、并发冲突或输入已过期 | 未形成判断 | 没有三值领域结果，使用原请求安全重试或取得新版本 |
| 已发布服务区域明确排除目的地址，且相关版本和解析依据完整 | 不可达 | 这是确定性覆盖结论，不是地址资料不足 |
| 客户地址缺少完成服务区域解析所需的业务信息 | 资料不足 | 不得假设默认区域或直接判断不可达 |
| 必需网络版本未发布、配置损坏或无法读取 | 未形成判断 | 系统配置或技术可用性问题不能伪装为业务资料不足 |

若部分候选已经被淘汰、剩余候选仍因业务证据不足无法判断，整体结果是`资料不足`，不是`不可达`。只有存在一个不会被缺失全局证据推翻的完整合格候选时，才可以在其他候选尚未确定的情况下形成`可达`。

## 候选评估规则

| 层次 | 判断内容 | 结果影响 | 明确边界 |
|---|---|---|---|
| 1. 判断范围 | 包裹、服务目的、提交版本、判断适用时点和租户/客户边界 | 无法建立范围时请求未受理或未形成判断 | 不得跨包裹、跨客户或跨提交版本复用结果 |
| 2. 商业适用 | 责任法人、服务产品、合同、网络使用资格和有效约束 | 确定不适用时淘汰候选；依赖失败时未形成判断 | `network-routing` 不更换产品、合同或责任法人 |
| 3. 服务区域 | 地址解析、起止服务区域、节点覆盖、方向和业务时区 | 明确不覆盖时淘汰；地址业务证据不足时资料不足 | 客户地址仍由 `parcel-shipment` 拥有 |
| 4. 逻辑路径 | 网络连接、线路、服务日历、截单、临时可用性及服务时间要求 | 形成可能候选并排除不可执行路径 | 不选择当前有效路线，不绑定具体班次 |
| 5. 硬约束 | 禁限运、关务资格、节点/线路/法人资格和其他有效限制 | 适用限制淘汰候选；状态未知时资料不足或未形成判断 | 由证据缺口还是依赖失败决定结果，限制只能由来源责任方解除 |
| 6. 存在性结论 | 检查是否存在完整合格候选，或者全部候选是否确定性淘汰 | 形成可达、不可达或资料不足 | 不进行最终路线排序、选择或生效 |

客户提出的线路、节点、口岸或渠道要求只有在服务产品或合同明确承诺时才成为约束。普通偏好不得使本来可达的包裹变成不可达，也不得绕过硬限制制造可达结果。

| 9 | `network-routing` | 提交判断、输入版本、候选与淘汰依据、审计和对应事件发布意图 | 提交后向 `parcel-shipment` 返回或发布独立判断 | `ADR-FACT` |
| 10 | `parcel-shipment` | 引用判断及其版本继续委托接受编排 | 是否接受、拒绝、待补充或未决由接单规则决定 | `PS-ACCEPT`、`CTX-REL` |

一次委托可以批量请求多个包裹，但每个包裹分别形成判断。批量归组不拥有一个可以覆盖成员差异的委托级可达性结果，也不因一个包裹失败而回滚其他包裹已经合法形成的判断。`parcel-shipment` 不支持成员级部分接受：任一成员确定性不满足条件时，整份当前提交版本不能接受；本用例仍只返回包裹判断，不整单拒绝、自动拆单或重组成员。

## 判断内容与责任边界

每个三值判断至少表达以下业务内容：

- 判断标识、包裹、服务目的、委托及提交版本、请求关联和判断适用时点。
- 客户声明、服务要求、商业资格和关务资格的实际采用版本或引用。
- 服务区域解析、网络拓扑、线路、服务日历、时区、截单、网络可用性调整和路由策略版本。
- 被评估的候选范围、每个候选的合格、淘汰或证据未知结果，以及稳定原因。
- 三值结果、判断时间、适用区间、当前修订标识、再次判断条件和与前后判断版本的关系。
- 资料不足时缺少的业务证据及影响范围；不可达时完整的排除依据；可达时至少一个完整合格候选。

判断不得包含或暗示：

- 委托已经接受或拒绝，或者某个包裹已经被成员级接受。
- 某条候选已成为当前有效路由、客户承诺或 ETA。
- 班次、容量、订舱、装载、运输方接受或实际履约已经形成。
- 正式关务案件、申报、监管受理、放行或限制解除已经发生。
- 客户地址、测量、产品、合同、限制或其他来源事实已经由路由上下文修改。

## 提交边界与后续交接

- 三值结果、判断输入版本、候选范围、合格/淘汰/未知依据、审计和对应事件发布意图必须形成同一个最小业务提交结果。
- 处理失败且尚未提交完整判断时只保存请求与处理尝试，不能发布可达、不可达或资料不足事件。
- 跨上下文商业资格和关务限制由各自所有者独立形成；本用例保存实际采用引用，不要求与委托接受形成分布式事务。
- 判断提交后事件首次投递失败只重试同一发布意图，不删除、重复或改写已经形成的判断。
- `parcel-shipment` 只能引用已提交判断继续接受编排。判断投递失败不得促使其构造默认可达或不可达结果。
- 判断结果不与委托接受原子提交。接受提交前必须复核关键判断仍覆盖其 `asOf` 且未被有效限制、替代版本或并发决定推翻；失效时重新判断，无法及时取得新结果时委托保持未决。

## 一致性、幂等与并发

- 同一判断请求身份、相同包裹、提交版本、输入版本和适用时点重复到达时，返回原判断或原未决处理关联，不创建重复结果。
- 同一请求身份携带不同包裹、提交版本、输入或适用时点时形成冲突；明确纠错或补充形成关联的新请求版本，不能覆盖原判断。
- 同一请求版本并发处理时只能有一个完整三值判断越过提交边界；其他处理读取已有结果或报告冲突。
- 新地址、声明、商业版本、网络、日历、可用性、限制或规则依据需要形成新判断版本。新版本不覆盖原判断，旧判断也不得按消息到达顺序覆盖新输入结果。
- `parcel-shipment` 保存实际采用的判断引用。提交接受决定前发现判断版本过期、适用区间不覆盖或修订标识变化时，必须重新请求；无法取得新结果时保持委托尚未决定。
- 同一委托各包裹可以同时得到可达、不可达、资料不足或未形成判断。`network-routing` 不据此形成委托级接受结论。
- 响应或事件丢失时通过稳定请求关联查询原判断，不通过新的无关联请求猜测结果。

## 权限、隔离与审计

- 只有代表明确委托接受编排、并具有相应租户和客户范围的调用主体可以请求和查询判断；客户不能直接指定或覆盖三值结果。
- 判断输入、候选和结果必须按集团租户、客户账户、委托和包裹隔离。批量请求、错误信息、查询和指标不得泄露其他客户的存在或网络资格。
- 审计至少关联请求主体、委托与提交版本、包裹、输入来源、商业与规则版本、适用时点、全部候选、判断、处理尝试、提交时间和发布结果。
- 地址、货物和申报资料按最小必要原则参与判断；日志、指标和追踪不保存不必要的明文。
- 人工操作不能直接把资料不足改为可达或不可达，也不能删除候选、淘汰依据、原判断或来源版本。若未来引入人工业务判断，必须先由权威规则定义其权限和证据边界。

## 可观测性与非功能验收占位

- 从接单请求、委托、提交版本、包裹、可达性请求、协作判断到三值结果必须具有稳定关联。
- 分别观测请求校验、商业资格、服务区域解析、网络版本装配、关务资格、候选生成、硬约束评估、判断提交和结果投递的耗时与失败位置。
- 分别统计可达、不可达、资料不足、未形成判断、重复、冲突、未受理和不适用；资料不足按业务证据分类，未形成判断按技术或依赖阶段分类。
- 监控无淘汰依据的不可达、无完整候选的可达、技术故障被写成资料不足、判断直接创建路由计划或接受决定等不变量违规。
- 可用性、响应时间、新鲜度、批量窗口和恢复目标由 `PAR-NFR-06` 及验收矩阵 `NFR-02` 参数化，本文件不填写未经证据确认的数值。

## 首发试点叠加条件

本节只约束首发验证，不改变长期用例：

- 首发使用 `PAR-COM-01`、`PAR-COM-03`、`PAR-COM-05` 和 `PAR-COM-06` 最终确认的锚点客户、责任法人、服务产品和合同版本。
- 只使用 `PAR-NET-01` 至 `PAR-NET-06` 登记的真实成熟线路、服务区域、节点和作业边界；不得因为试点只有一条主线路就在模型中删除候选范围和淘汰依据。
- 关务候选与限制只引用 `PAR-CUS-01` 至 `PAR-CUS-04` 已确认的真实程序、角色、资格和规则来源，不创建默认国家、口岸或申报路径。
- 真实服务区域、日历、时区、截单、网络可用性和适用规则未登记前，只能完成骨架与受控测试，不能宣称 `OPS-01` 生产证据成立。
- 不可达、资料不足、重复、迟到和依赖失败可以使用脱敏历史回放或隔离模拟验证，不得通过主动中断真实网络或制造监管失败取得证据。

## 验收示例

| ID | 场景 | 预期结果 |
|---|---|---|
| `AT-NR-016` | 权威输入完整，至少一个逻辑候选满足服务要求和全部硬约束 | 形成可达判断并保存完整候选依据；没有接受委托、创建路由计划或占用资源 |
| `AT-NR-017` | 候选空间完整，所有候选都被已生效硬限制确定性淘汰 | 形成不可达判断及逐候选原因；不直接把委托写成已拒绝 |
| `AT-NR-018` | 客户地址缺少完成服务区域解析所需的业务信息 | 形成资料不足，指出缺少内容和再次判断条件；不使用默认区域或记录不可达 |
| `AT-NR-019` | 商业、网络或关务权威依赖调用超时 | 未形成三值判断，保留请求和安全续办依据；不伪装为资料不足 |
| `AT-NR-020` | 相同请求身份、输入版本和适用时点重试 | 返回已有判断，不创建第二个结果 |
| `AT-NR-021` | 相同请求身份携带不同提交版本或输入 | 形成请求冲突或关联的新请求版本；原输入和判断不被覆盖 |
| `AT-NR-022` | 同一委托三个包裹分别具备合格候选、全部被排除和地址资料缺口 | 分别形成可达、不可达和资料不足；不创建委托级统一可达状态 |
| `AT-NR-023` | 已发布服务区域明确不覆盖目的地址，地址和覆盖版本完整 | 形成不可达而不是资料不足，保存服务区域解析和排除依据 |
| `AT-NR-024` | 部分候选已淘汰，剩余候选因业务证据缺失无法判断 | 整体形成资料不足；不得仅依据已淘汰候选形成不可达 |
| `AT-NR-025` | 一个候选已被完整证明合格，其他候选仍有局部非全局证据缺口 | 形成可达；保留其他候选未知依据，且缺口不得能够推翻已合格候选 |
| `AT-NR-026` | 客户偏好某线路，但产品和合同没有把它设为承诺 | 普通偏好不成为硬约束，不使其他合格逻辑路径变成不可达 |
| `AT-NR-027` | 某次班次容量申请、订舱或装载失败 | 不据此改写逻辑可达性；本用例不创建或处理这些履约对象 |
| `AT-NR-028` | 判断形成后网络、日历或限制版本发生变化 | 新请求形成新判断版本并保留原判断；迟到结果不按到达顺序覆盖 |
| `AT-NR-029` | 服务产品明确允许待路由，当前判断为不可达 | `network-routing` 返回不可达原结果；是否接受由 `parcel-shipment` 依据产品规则决定 |
| `AT-NR-030` | 三值判断提交成功但结果事件首次投递失败 | 判断和全部依据保持不变；重试同一发布意图，不重复判断或构造默认结果 |
| `AT-NR-031` | 关务权威依据淘汰一个候选，另一个候选仍完整满足全部约束 | 形成可达并保存两条候选各自依据；不绕过关务限制，也不建立正式关务案件 |
| `AT-NR-032` | 标准网络服务得到不可达结果 | 本用例只返回不可达；`parcel-shipment` 决定当前提交版本不能直接接受，不创建无当前有效路由 |

## 开发拆分建议

判断时点与失效重判机制已经关闭；在真实参数未提供前，可以先实现：

1. 渠道中立的包裹级可达性请求、输入版本和稳定关联模型。
2. 商业资格、服务区域、网络版本和关务资格的只读协作契约。
3. 候选生成、硬约束评估和完整候选/淘汰/证据未知记录。
4. 可达、不可达、资料不足、未形成判断、不适用、重复、冲突和未受理结果。
5. 三值判断与证据的不可覆盖持久化边界，以及事件发布意图和安全重试。
6. 包裹级幂等、并发提交保护、版本化重判和结果查询。
7. `AT-NR-016` 至 `AT-NR-032` 的应用与领域测试骨架；真实参数保持显式未配置，不建立默认路线或默认区域。

完成本用例只闭合接受前逻辑可达性。委托接受继续由 `UC-PS-001` 拥有，接受后的初始路由继续由 [`UC-NR-001`](./UC-NR-001-CREATE-INITIAL-ROUTE.md) 拥有。
