# UC-NR-001 为已接受包裹形成初始路由

状态：开发基线草案；稳定业务骨架来自已确认领域规则，真实网络与非功能参数待提供

## 目标与边界

本用例从 `parcel-shipment` 已经接受一份适用网络服务的委托开始，到 `network-routing` 对接受基线中的每个适用包裹形成当前有效的初始路由计划、明确的`无当前有效路由`判断，或者记录本次路由判断尚未完成为止。

本用例包含：

- 使用不可覆盖的委托接受基线和预计承诺作为路由业务输入。
- 按包裹解析服务区域，装配适用网络、日历、可用性、关务资格和路由策略版本。
- 先过滤硬约束，再判断承诺、截单和衔接可行性，最后按适用策略排序候选。
- 形成包含计划节点、计划履约段和计划时间窗口的包裹级初始路由计划。
- 在已经完成权威判断但没有候选时形成`无当前有效路由`，并保留完整淘汰依据。
- 在依赖或证据不足时保留判断未决，支持幂等续办和并发裁决。

本用例不执行：

- 委托提交、接受、拒绝、取消或客户服务变更。
- 客户承诺调整；路由计划只能引用适用承诺，不能覆盖预计承诺或正式承诺。
- 具体班次选择、容量申请或预占、运输委托、订舱、装载分配和实际装载。
- 节点收寄、测量、分拣、运输交接、实际移动或正式关务申报。
- 接受后的网络收寄复核、到站实测复核或后续受控改路；它们属于后续独立用例。

## 参与者与上下文协作

| 参与者或上下文 | 本用例职责 | 明确不负责 |
|---|---|---|
| `parcel-shipment` | 提供委托接受决定、不可变接受基线、包裹身份、客户地址与声明、服务要求及预计承诺 | 不选择路线，不把接单可达性结果直接当作初始路由计划 |
| `party-commercial` | 提供接受时适用的法人、产品、合同、网络使用资格和客户已承诺约束依据 | 不为具体包裹选择候选或创建路由计划 |
| `network-routing` | 解析服务区域、评估候选、形成包裹级计划或无当前有效路由判断，并保存完整依据 | 不接受或取消委托，不修改客户承诺，不认定实际履约 |
| `customs-compliance` | 提供适用关务区域、口岸、申报路径资格和当前硬限制判断 | 不选择最终路线，不因内部资料准备形成监管放行 |
| `transport-fulfillment` | 在已有真实能力数据时提供班次可用性和容量风险信号 | 不因本用例请求而预占容量、接受运输委托或创建装载分配 |
| `visibility-exception` | 可消费无路由或后续偏离结果，协调显式处置 | 不直接生成路由、解除限制或修改计划 |

`transport-fulfillment` 的班次可用性和容量风险属于候选评估信号，不是本用例形成计划的资源承诺。信号不可用是否阻塞候选，必须由适用路由策略明确，应用层不得自行假定。

## 启动条件

- 委托已经形成唯一、可追溯的接受决定，并且接受状态、接受基线、预计承诺和事件发布意图完整。
- 路由交接能够关联接受决定、接受基线版本以及其中的明确包裹身份；只有状态字符串而没有基线引用时不得继续。
- 服务产品属于运营企业需要形成网络路由的范围。仅提供面单渠道服务且不控制端到端网络时，本用例明确返回不适用，不虚构网络节点。
- [`UC-NR-002`](./UC-NR-002-ASSESS-PARCEL-REACHABILITY.md) 形成的接受前可达性判断只作为接受依据引用，不能直接复制为初始路由计划。初始计划必须使用接受后本次判断时适用的网络与限制版本重新评估。

## 结果语义契约

| 结果 | 业务含义 | 必须返回或可查询的依据 | 禁止行为 |
|---|---|---|---|
| 初始路由已形成 | 某包裹已经有一个当前有效的初始路由计划版本 | 包裹、接受基线、计划版本、生效边界、计划节点、计划履约段、时间窗口、策略与全部选择依据 | 不得同时创建班次、容量预占、订舱、装载或实际履约 |
| 无当前有效路由 | 权威输入齐备并完成候选评估后，当前没有满足适用硬约束和服务要求的候选 | 包裹、判断时点、适用版本、被评估候选及逐项淘汰依据、关联接受基线 | 不得创建空路线、默认路线或占位计划；不得自动取消委托、修改承诺或形成终局失败 |
| 路由判断未决 | 必需依赖、证据或并发条件不足，尚不能证明存在或不存在可行候选 | 包裹、处理阶段、缺少或冲突的权威结果、已有判断和安全续办引用 | 不得伪装为无当前有效路由，也不得选取缺少依据的默认候选 |
| 已有结果 | 重复或重试交接已经对应同一接受基线和包裹的初始路由结果 | 原计划或无路由判断引用、原处理关联和当前适用性 | 不得再次创建一个并行有效的初始计划 |
| 路由交接冲突 | 同一交接身份或同一接受基线引用携带不一致的包裹或服务内容 | 原交接、冲突范围、来源基线和纠正入口 | 不得静默覆盖接受基线、原计划或判断历史 |
| 不适用 | 适用服务不要求运营企业形成该包裹的网络路由 | 包裹、服务产品与不适用依据 | 不得以不适用替代无路由，也不得为面单渠道服务虚构端到端网络 |

`路由判断未决`和`不适用`是应用处理结果，不是路由计划生命周期状态。`无当前有效路由`是已经完成业务判断后的明确领域结果，三者不能合并为一个通用失败状态。

## 候选判断规则

候选评估必须按以下层次执行并保留逐层结果：

| 层次 | 判断内容 | 不通过时 | 说明 |
|---|---|---|---|
| 1. 适用范围 | 服务产品、责任法人、网络使用资格、起止服务区域及业务时区 | 淘汰候选；缺少权威依据则未决 | 不得临时更换产品、合同责任法人或客户渠道锁定 |
| 2. 硬约束 | 禁限运、关务资格、节点与线路资格、网络关闭和其他有效限制 | 淘汰候选；限制状态不明则未决 | 自动和人工选择都不能绕过，只有来源责任方可以解除 |
| 3. 时间可行性 | 预计承诺、服务日历、截单、节点处理时间、衔接缓冲和计划窗口 | 淘汰不满足候选 | 不得用尚未分配的精确班次时间伪装计划确定性 |
| 4. 策略排序 | 版本化策略规定的时效、可靠性、成本、容量风险和已承诺偏好优先级 | 选出排序最高的候选 | 应用层不得自行发明固定权重或行业默认阈值 |

只有前述权威输入齐备且所有候选均被确定性淘汰时，才能形成`无当前有效路由`。依赖超时、版本无法解析、关务资格未知、候选计算失败或证据冲突只能形成`路由判断未决`。

## 应用流程

| 步骤 | 责任方 | 应用动作 | 结果与下一步 | 权威依据 |
|---|---|---|---|---|
| 1 | 路由接入 / `network-routing` | 接收委托接受交接，校验接受决定、接受基线和包裹关联完整性 | 无法验证时保持未决；不以状态字符串创建计划 | `PS-BASE`、`ADR-FACT` |
| 2 | `network-routing` | 按交接关联识别首次处理、重复、重试或内容冲突 | 重复返回已有结果；冲突保留原结果并进入受控纠正 | `ADR-FACT` |
| 3 | `network-routing` | 判断服务是否适用运营企业网络路由 | 不适用时形成可追溯结果，不创建虚假路由 | `NR-RULE` |
| 4 | `network-routing` | 按接受基线逐包裹建立独立判断范围 | 同一委托不同包裹分别处理，不创建委托级统一执行路线 | `NR-RULE`、`CTX-REL` |
| 5 | `network-routing` | 解析地址与服务区域，选择判断时点适用的网络、线路、日历、可用性和路由策略版本 | 保存解析及版本；缺少权威依据时保持未决 | `NR-RULE` |
| 6 | `network-routing` / `customs-compliance` | 取得候选关务区域、口岸、申报路径资格及当前限制 | 仅保留合格候选；不能判断时保持未决 | `NR-RULE`、`CTX-REL` |
| 7 | `network-routing` | 生成候选并依次执行硬约束、时间可行性和策略排序 | 保存全部候选、排序和淘汰依据 | `NR-RULE` |
| 8A | `network-routing` | 至少一个候选可行时选定排序最高候选，形成计划节点、计划履约段和计划时间窗口 | 准备提交一个包裹级当前有效计划 | `NR-LANG`、`NR-LIFE` |
| 8B | `network-routing` | 权威判断完整且没有可行候选时形成无当前有效路由 | 不创建计划；阻止需要下一跳依据的后续动作 | `NR-LIFE`、`E2E-01` |
| 8C | `network-routing` | 判断无法完成时保存未决阶段和续办依据 | 不形成计划或无路由领域结果 | `ADR-FACT` |
| 9 | `network-routing` | 提交包裹级结果、完整判断依据、审计和对应事件发布意图 | 结果提交后交给节点、履约、追踪等后续能力使用 | `ADR-LAYERS`、`ADR-FACT` |

一次委托交接可以并行处理多个包裹，但每个包裹独立形成结果。某个包裹未决或无路由不回滚其他包裹已经合法形成的计划，也不能被一个委托级“已路由”状态掩盖。

## 计划内容与责任边界

每个初始路由计划至少表达以下业务内容：

- 计划所针对的包裹、服务目的、接受决定和接受基线版本。
- 计划版本、判断时间、生效边界和当前适用性。
- 按顺序排列的计划节点和计划履约段，以及每段已知责任边界。
- 计划节点或计划履约段的时间窗口、节点处理时间和衔接缓冲依据。
- 路由策略、网络拓扑、线路、服务日历、网络可用性、服务区域解析、关务资格和测量依据版本。
- 所有被评估候选、选择顺序、淘汰原因，以及客户约束是合同承诺还是一般偏好。
- 外包合作方内部网络不可可靠观察时，只使用外部不透明履约段表达已知交接点、责任方、服务条件和返回控制边界。

计划不得包含或暗示以下已经发生的事实：

- 具体班次已经分配、容量已经预占、订舱已经成功或运输方已经接受。
- 包裹已经收寄、到站、测量、分拣、装载、交接、出发、到达、清关或交付。
- 客户预计承诺或正式承诺已经因路线选择而改变。
- 外包伙伴内部存在未被可靠观察的节点、扫描或运输段。

## 决定提交边界与后续交接

- 一个包裹的初始计划版本、计划节点、计划履约段、计划时间窗口、候选选择依据、审计和对应事件发布意图必须形成同一个最小业务提交结果。
- `无当前有效路由`判断、完整淘汰依据、审计和对应事件发布意图必须形成同一个最小业务提交结果。
- 判断未决只保存处理尝试、已有输入和续办依据，不发布“无路由”业务事实。
- 跨上下文资格和限制由其所有者独立形成，本用例保存实际采用的引用与快照，不要求分布式事务。
- 结果提交后，事件投递失败只重试同一发布意图，不回退计划、不重复创建计划，也不把无路由改成未决。
- 下游班次、容量、装载和作业用例只能引用当前有效路由版本继续处理；需要下一跳依据的动作在无当前有效路由时必须受阻。

## 一致性、幂等与并发

- 同一接受基线、同一包裹和同一初始路由目的只能形成一个当前有效初始路由结果。重复交接返回已有结果，不创建第二个并行计划。
- 路由计划按包裹独立版本化。同一委托的包裹可以采用不同路线，也可以同时出现有计划、无路由或判断未决。
- 同一包裹并发计算得到不同候选时，只能有一个结果越过提交边界；失败方读取已提交结果并返回已有结果，或者在其依据已不适用时触发后续重评，不能覆盖胜出版本。
- 判断保存明确的业务判断时点和所有输入版本。提交前发现网络、日历、限制、关务资格或策略依据已经失效时，必须重新判断；暂时无法完成时保持未决。
- 接受前可达结果和接受后初始路由结果分别保留身份和依据。两者不同不自动表示数据错误，应能解释接受后网络、限制或版本变化。
- 事件响应丢失时调用方通过稳定交接关联查询原结果，不以再次发送不同内容的交接来恢复。
- 网络恢复或新候选出现只触发重新评估资格，不原地恢复旧计划，也不自动撤销已经形成的无路由历史。

## 权限、隔离与审计

- 路由判断必须在明确集团租户、运营责任法人、客户账户和包裹范围内执行；批量处理、查询和错误信息不得泄露其他客户的包裹或业务量。
- 自动路由只能使用已发布且在适用范围内有效的策略版本。人工选择即使后续引入，也不能绕过硬限制，并必须记录实际决定方、授权、原因和被替代的自动结果。
- 审计至少关联接受决定、接受基线、包裹、输入版本、判断时点、服务区域解析、全部候选、硬约束、关务资格、策略排序、结果、提交主体和发布状态。
- 客户地址、货物和申报资料按最小必要原则参与判断；日志、指标和追踪不记录不必要的明文。
- 任何操作不得覆盖接受基线、候选历史、原计划、无路由判断或其他上下文拥有的事实。

## 可观测性与非功能验收占位

- 从委托接受交接、接受基线、包裹到每次路由判断、候选和结果必须具有稳定关联，不能只依赖日志文本。
- 分别观测交接校验、服务区域解析、网络版本选择、关务资格、候选生成、硬约束过滤、时间可行性、策略排序、结果提交和事件投递的耗时与失败位置。
- 分别统计计划形成、无当前有效路由、判断未决、重复、冲突、不适用和重新判断；原因维度使用稳定规则、限制或淘汰标识。
- 监控同一包裹并行有效计划、缺少选择依据、占位路线、无来源节点和计划误绑资源等不变量违规；一旦发现不得用自动覆盖掩盖。
- 可用性、处理时延、批量窗口、新鲜度和恢复目标由 `PAR-NFR-06` 及验收矩阵 `NFR-02` 提供，本文件不填写行业估计数值。

## 首发试点叠加条件

本节只约束首发验证，不改变长期领域模型：

- 首发只实例化 `PAR-NET-01` 登记的一条成熟主力线路，以及 `PAR-NET-02` 至 `PAR-NET-06` 提供的真实区域、节点和作业边界。
- `PAR-NET-14` 提供本次初始路由采用的候选过滤/排序、服务日历、时区、截单、网络可用性和策略有效期；未配置时不得形成生产路由或使用默认权重。
- 一条试点主线路不代表领域模型永远只有一个候选。候选集合、排序、淘汰和版本结构仍按多路径能力实现，测试可使用受控模拟或历史回放覆盖替代候选。
- 关务候选和限制只使用 `PAR-CUS-01` 至 `PAR-CUS-04` 已确认的真实程序、角色、资格和规则来源，不创建默认口岸或默认报关路径。
- 真实网络、日历、截单、时区、可用性和策略版本未登记前，可以完成骨架和受控测试，但不得宣称 `OPS-01` 生产验收通过。
- `OPS-02` 的无路由与改路条件可以使用历史回放或隔离模拟验证；不得为了制造证据主动中断真实在途业务。

## 验收示例

| ID | 场景 | 预期结果 |
|---|---|---|
| `AT-NR-001` | 已接受标准网络委托的一个包裹存在多个合格候选 | 先过滤硬约束，再按时间可行性和适用策略排序；只形成一个当前有效计划并保留所有候选依据 |
| `AT-NR-002` | 同一已接受委托包含两个包裹，因服务区域或限制不同应走不同路线 | 分别形成两个包裹级计划；不存在覆盖所有成员的委托级执行路线 |
| `AT-NR-003` | 同一接受交接以相同内容重复投递 | 返回已有包裹结果，不创建第二个并行有效计划或重复无路由判断 |
| `AT-NR-004` | 同一包裹发生并发初始路由计算 | 只有一个结果越过提交边界；其他处理返回已有结果或基于新事实进入后续重评 |
| `AT-NR-005` | 权威输入完整，所有候选均被有效硬限制淘汰 | 形成无当前有效路由并保存逐候选淘汰依据；不创建默认或占位路线 |
| `AT-NR-006` | 关务资格服务暂时不可用，无法判断候选是否合法 | 形成路由判断未决并安全续办；不得记录为无当前有效路由或选择未经验证的口岸 |
| `AT-NR-007` | 产品明确允许待路由，委托已接受但当前仍无可行候选 | 形成无当前有效路由；不取消委托、不修改预计承诺、不形成终局失败 |
| `AT-NR-008` | 候选参考某班次可用性和容量风险后被选中 | 计划只保存使用的能力信号；没有创建班次绑定、容量预占、订舱或装载分配 |
| `AT-NR-009` | 接受基线对应仅提供面单渠道服务，运营企业不控制端到端网络 | 返回不适用并保留产品依据，不虚构节点、线路或实际承运商网络 |
| `AT-NR-010` | 候选选出后、提交前适用线路被有效关闭 | 原候选不得提交为当前计划；使用新依据重新判断，不能完成时保持未决 |
| `AT-NR-011` | 路由计划提交成功但事件首次投递失败 | 当前有效计划及全部依据保持不变；重试同一发布意图，不重复形成计划 |
| `AT-NR-012` | 同一委托三个包裹分别可路由、确定无路由和依赖未决 | 三个包裹分别保留计划、无路由和未决结果；任一结果不回滚或掩盖其他结果 |
| `AT-NR-013` | 客户声明偏好某线路，但合同和产品未承诺该偏好 | 偏好不能绕过硬约束或取得最终决定权；按适用策略选择并保存未采用原因 |
| `AT-NR-014` | 外包伙伴内部网络不可可靠观察 | 只形成具有已知交接点、责任和时间窗口的外部不透明履约段，不虚构内部节点 |
| `AT-NR-015` | 初始计划时间窗口与接受时预计承诺存在差异 | 两者分别保留；本用例不回写承诺，差异进入后续显式处置而非覆盖 |

## 生产参数与未决风险

下列内容不是新的领域决策，但在真实值提供前阻塞生产路由：

| 参数范围 | 当前状态 | 对本用例的影响 |
|---|---|---|
| `PAR-NET-01` | 待核验锚点线路的受控真实映射、完整范围和成熟性证据 | 无法确认首发线路身份和完成 `OPS-01` 生产证据 |
| `PAR-NET-02` 至 `PAR-NET-06` | 待提供真实区域、节点和作业边界 | 无法实例化首发网络和完成 `OPS-01` 生产证据 |
| `PAR-CUS-01` 至 `PAR-CUS-04` | 待提供真实程序、角色、资格和规则来源 | 无法证明候选关务路径合法可用 |
| `PAR-NET-14` | 待提供路由策略、服务日历、截单、时区、网络可用性、冻结边界和重算规则 | 无法发布可执行候选过滤、排序和后续复核规则 |

不得用虚构国家、节点、线路、口岸、班次、策略权重或阈值填补上述缺口。

## 开发拆分建议

真实参数未齐备前，可以按以下顺序实现：

1. 接受交接、接受基线读取和包裹级路由判断身份。
2. 版本化网络、服务区域、日历、可用性和策略读取契约。
3. 候选生成及“硬约束 → 时间可行性 → 策略排序”的可解释判断管线。
4. 当前有效计划、计划节点、计划履约段、时间窗口和候选依据的持久化边界。
5. 无当前有效路由、路由判断未决、不适用、重复和冲突结果。
6. 包裹级幂等、并发提交保护、事件发布意图和安全重试。
7. `AT-NR-001` 至 `AT-NR-015` 的应用与领域测试骨架；实例参数使用显式未配置状态，不使用默认真实值。

完成本用例不表示运输执行已经完成设计。班次、容量、订舱、装载和实际履约应继续在 `transport-fulfillment` 的后续应用用例中展开。
