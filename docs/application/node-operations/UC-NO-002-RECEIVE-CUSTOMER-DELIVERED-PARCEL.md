# UC-NO-002 接收客户送达节点的作业实物

状态：稳定业务骨架已形成；真实节点、作业方式、授权与非功能参数待提供

## 目标与边界

本用例从客户或其授权交付方把实物直接送达一个物流节点开始，到 `node-operations` 对每件实物分别形成节点收寄、未形成收寄、待确认或待识别结果，并如实记录节点控制、位置、状况和来源证据为止。

本用例解决“节点实际接到了什么、是否取得控制、能否关联正式包裹”三个问题。它不决定客户委托是否接受、是否形成有效网络收寄、是否形成正式承诺，也不因为一次扫描、卸载或页面操作推导服务责任。

本用例包含：

- 先保全交付、扫描、点验、签收、拒收和现场观察等来源事实。
- 逐件识别正式包裹、身份冲突或待识别实物。
- 对客户直接送站范围形成节点收寄及节点控制结果。
- 如实接收已取消、已经终局、无当前有效路由或存在限制的实物，同时保持原服务结果和限制。
- 将节点收寄结果交给 `parcel-shipment` 判断有效网络收寄和正式承诺。

本用例不执行：

- 委托接受、拒绝、取消、重开、正式承诺或终局服务结果。
- 场外揽收、节点与运输方之间的权威交接、实际运输或交付。
- 路由选择、改路、班次、容量、订舱或装载分配。
- 正式关务申报、监管决定、费用、库存可用量或库存价值。
- 方向性分拣、集包出运或交出；这些动作需要后续当前有效路由指令。

## 参与者与协作

| 参与者或上下文 | 本用例职责 | 明确不负责 |
|---|---|---|
| 客户或授权交付方 | 交付实物并提供可验证的交付范围和身份线索 | 不通过交付动作直接形成委托接受或正式承诺 |
| `node-operations` | 保全来源，识别作业实物，形成节点收寄、控制、位置和状况事实 | 不决定正式包裹身份、客户责任或路由 |
| `parcel-shipment` | 提供包裹身份、接受基线、外部标识关联和当前服务结果；后续解释有效网络收寄 | 不修改节点收寄、位置或控制事实 |
| `network-routing` | 提供当前路由计划和路由指令；后续消费实际节点控制 | 不以路由存在与否决定节点是否如实接收 |
| `visibility-exception` | 消费身份冲突、异常到站和状况事实并协调处置 | 不替节点形成收寄或控制结果 |

客户直接送站与运输方交接必须分开。实物由运输方交给节点时，节点只形成节点侧证据，跨边界权威交接结果由 `transport-fulfillment` 形成，不得调用本用例冒充客户送站。

## 启动条件

- 节点身份、经营责任和本次收寄作业范围可以追溯。
- 本次交付具有稳定来源身份、发生时间、接收时间和对象范围。
- 节点能够记录未识别、冲突、拒收或待确认结果，不要求所有实物先匹配正式包裹。
- 真实收寄资格、证据和安全规则未配置时只能运行稳定骨架或受控 `R/S`，不得写入默认节点、客户或判断值。

委托尚未接受、已取消、已终局、无当前有效路由或存在限制都不能阻止节点保存已经发生的物理事实。它们只影响后续服务采用和方向性作业。

## 输入语义契约

下表定义业务语义，不是 API、消息或数据库字段清单。

| 输入组 | 权威来源 | 最低业务语义 | 使用约束 |
|---|---|---|---|
| 交付来源 | 客户接入或节点现场 | 来源身份、业务发生时间、系统接收时间、交付方、节点和交付范围 | 迟到、重复和冲突必须保留；不能以最后消息覆盖 |
| 作业实物 | 节点现场 | 每件可区分实物、当前外部标识观察、位置和状况 | 外部条码只是线索，不自动等于正式包裹 |
| 包裹身份依据 | `parcel-shipment` | 租户、客户账户、正式包裹、接受基线、当前身份与外部标识关联 | 节点只读引用，不能自行创建或合并正式包裹 |
| 服务结果引用 | `parcel-shipment` | 已接受、已取消、终局、当前有效包裹等结果及版本 | 只决定后续交接语义，不允许删除物理事实 |
| 节点与作业资格 | 网络、节点运营 | 节点身份、经营法人、收寄范围、现场能力和有效期 | 缺少时保持未决或限制后续动作，不使用默认节点 |
| 当前限制与路由 | 各限制源、`network-routing` | 当前适用限制、路由计划与路由指令引用 | 接收和安全作业可继续；方向性作业另行受控 |

## 结果语义契约

| 结果 | 业务含义 | 必须保存 | 禁止推导 |
|---|---|---|---|
| 节点收寄已形成 | 明确作业实物由客户或授权交付方直接交付，节点已经接收并取得控制 | 实物、正式包裹关联或候选、节点、交付方、发生时间、证据、控制起点和结果版本 | 委托接受、有效网络收寄、正式承诺、计费或库存入库 |
| 待识别实物已建立 | 节点已经发现或控制实物，但不能可靠关联正式对象 | 永久作业实物身份、位置、状况、控制、全部候选和冲突 | 临时包裹、最后扫描即身份或方向性作业授权 |
| 节点收寄未形成 | 本次交付明确未被节点接收并且节点未取得控制 | 实物或范围、原因、交付尝试、证据和实际控制方 | 客户委托拒绝、包裹取消或服务终局 |
| 收寄判断待确认 | 物理事实已保存，但交付方、身份、证据或并发结果不足以形成确定收寄判断 | 已知事实、控制现状、缺口、限制和续办引用 | 默认收寄、默认拒收或删除实物记录 |
| 已有结果 | 同一来源和内容已经处理 | 原来源、原节点收寄或待识别结果及当前有效性 | 重复控制起点、重复作业实物或重复业务事件 |
| 来源冲突 | 同一来源身份携带不同对象、时间或内容 | 原来源、冲突内容、现场事实和纠正入口 | 覆盖原来源或选择最后一次输入 |

节点收寄是 `node-operations` 的物理业务结果；是否被 `parcel-shipment` 采用为网络服务的有效网络收寄，是后续独立判断。即使包裹已经取消或终局，节点仍可形成真实接收与控制事实，但不得据此重开服务。

## 应用流程

| 步骤 | 责任方 | 应用动作 | 结果与下一步 |
|---|---|---|---|
| 1 | 节点接入 | 保全本次交付来源、原始引用、业务时间、接收时间、节点和交付方 | 后续解析失败不删除来源 |
| 2 | `node-operations` | 识别首次、重复、冲突或迟到交付 | 重复返回原结果；冲突停止自动采用 |
| 3 | `node-operations` | 对现场每件可区分实物建立或关联作业实物 | 批量交付不使用一个整批状态吞并成员差异 |
| 4 | `node-operations` / `parcel-shipment` | 使用正式包裹和外部标识引用核对身份 | 唯一且证据充分时关联；未知或冲突时建立待识别实物 |
| 5 | `node-operations` | 保存点验、状况、位置、实际交付和控制证据 | 扫描或卸载本身不等于节点收寄 |
| 6A | `node-operations` | 明确接收且节点取得控制时，逐件形成节点收寄结果 | 交给 `parcel-shipment` 判断有效网络收寄 |
| 6B | `node-operations` | 明确未接收且未取得控制时，形成未收寄结果 | 不形成客户拒绝、取消或终局 |
| 6C | `node-operations` | 证据不足或并发冲突时，保存待确认及当前控制 | 只续办原判断，不伪造确定结果 |
| 7 | `node-operations` | 对已取消、终局、无路由或受限实物标记相应引用并限制后续动作 | 事实保留；不自动恢复服务或路由 |
| 8 | `node-operations` | 原子提交收寄判断、控制、审计和对应发布意图 | 投递失败只重试原发布意图 |

一个交付批次可以包含多个包裹，但每件实物独立形成结果。部分收寄不回滚其他实物已合法形成的事实，也不得把未收寄成员从来源中删除。

## 控制、身份与后续作业

- 只有明确节点收寄或权威运输交接的“已交接”结果可以建立节点控制。位置、扫描、车辆到达、卸载和操作按钮不能单独建立控制。
- 待识别实物可以具有节点控制、位置、状况和安全作业事实，但在正式身份确认前不得执行需要包裹路由的方向性作业。
- 身份后来确认时建立版本化关联，原待识别实物、候选、冲突和既有事实永久保留。
- 已取消、终局或无当前有效路由的实物仍可被安全接收、隔离、测量和核对；分拣到下一方向、集包出运、装载和交出必须等待明确处置或当前有效路由指令。
- 形成节点收寄不自动创建集运单元、路由计划、班次、费用、库存项目或异常案件。

## 一致性、幂等与并发

- 同一来源身份和内容返回已有处理结果；同一身份不同内容形成冲突，不能覆盖。
- 同一实物同一客户交付边界只能形成一个当前有效节点收寄判断和一个控制起点；更正形成新判断版本。
- 批量中的结果逐实物提交或按可证明的成员范围提交；整批重试不能重复创建已成功成员。
- 迟到事实按业务发生时间参与判断，不按消息到达顺序改写控制历史。
- 收寄、取消、身份更正或终局并发时，各上下文保留自己的结果；`parcel-shipment` 按业务时间和适用边界判断服务影响，节点不覆盖任何一方。

## 权限、隔离与审计

- 收寄和身份核对必须在明确集团租户、客户账户、节点和作业责任范围内执行。
- 操作岗位可以提交来源和作业证据，但不得通过修改状态形成委托接受、正式包裹身份、客户承诺或异常责任。
- 跨客户批量作业只允许最小必要信息；查询、错误和日志不得泄露其他客户是否存在或业务内容。
- 审计至少关联来源、交付方、节点、作业实物、正式身份或候选、业务时间、证据、控制、决定方、版本和发布状态。
- 客户地址、联系人、货物和申报内容不进入不必要的日志、指标或测试夹具。

## 首发试点叠加条件

- `PAR-NET-13` 必须确认客户送站在本次客户、产品、合同、节点和有效期间内已经启用，并确认其权威来源属于 `node-operations`。
- `PAR-NET-04`、`PAR-NET-05` 和 `PAR-NET-06` 必须提供真实节点、经营责任、收寄作业、设备/SOP 和数据来源证据。
- `PAR-COM-05`、`PAR-COM-06` 必须能证明锚点产品、合同和客户送站范围；不能从页面配置推断。
- `PAR-NFR-02`、`PAR-NFR-04` 和 `PAR-NFR-06` 分别提供真实规模、扫描放大和节点关键流程目标。
- 真实参数未确认时可以实现强类型身份、来源保全、重复/冲突、逐件结果、待识别实物和显式未配置分支；不得写入默认客户、节点、条码规则或自动收寄条件。

## 给开发的交接

实现必须保留“来源事实 → 作业实物 → 身份判断 → 节点收寄判断 → 控制派生”的层次，不能压成一个 `received=true`。

当前代码只覆盖建单前身份、来源重放/冲突和最小委托候选，尚无 `node-operations` 代码、持久化、事务或事件闭环。本用例可以先实现命名夹具和纯业务判断骨架；真实节点写入必须等待参数证据和适用技术门槛。

完成本用例只形成客户送站的权威节点来源。`parcel-shipment` 仍须通过 `UC-PS-003` 判断有效网络收寄与正式承诺，`network-routing` 仍须通过 `UC-NR-003` 使用实际位置和控制依据复核路由。
