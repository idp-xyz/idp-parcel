# UC-WF-014 代办仓配出库的委托

状态：用例已写成，待实现（PN-09，首发之外的可选能力）；仓配代办、资料修订与包裹取消的授权待租户提供

## 目标与边界

本用例从一份要走本产品网络的出库请求需要委托开始，到本上下文以货主名义提交、补充、修订、撤回或取消，并按小包托运交来的信封推进装箱记录为止。请求方、授权、未配置的答法、来源键与接受判断，以[仓配履约 CONTEXT](../../domain/warehouse-fulfillment/CONTEXT.md)「出库请求与发出」「仓配出库提交」与小包托运 CONTEXT 为准，本用例只组织输入、结果、流程与验收，不另写一份代办规则。

本用例解决「仓替货主把这份出库请求交给小包托运」一个问题。拣货与出库确认不在本用例。

本用例包含：

- 每个包裹一份委托，来源「仓配出库」，来源请求键是（出库请求，包裹序号）。
- 平台备货整份出库请求一份委托，键是（出库请求，提交轮次），不预取面单。
- 预取面单时在波次释放先提交一个包裹，打包后补正声明测量。
- 消费接受决定、委托待受控补充、资料版本已形成、包裹取消已记录。来源不是「仓配出库」的，入账收工，不答未决。
- 面单只取引用。本体存放没配置时答未配置。

本用例不执行：

- 小包托运自己的接受判断。本上下文不绕过任何接受规则（`WF-RULE`）。
- 自备面单与自提：不形成委托。
- 货主经客户渠道自己提交的委托。那一路的消费者不是本用例；来源不是「仓配出库」的信封在这里入账收工。

## 启动条件

- 部署已打开仓配开关时，来源「仓配出库」的各信封由本用例接。关着时，本用例各口不提供业务答复；「委托待受控补充」由派发登记的收工路接：来源不是「仓配出库」的入账，来源是「仓配出库」的显式失败（`ADR-OPT` 决定三、四）。
- 代办授予、资料修订与包裹取消的授权没登记时，预取不发生，打包后的提交答未配置（`WF-RULE`）。答法以小包托运 CONTEXT 为准，本用例不另写。
- 一个仓都没登记的租户没有出库请求可提交，提交答未配置。

## 结果语义契约

| 结果 | 业务含义 | 必须留下 | 明确不是 |
|---|---|---|---|
| 委托已提交 | 小包托运已收下这一来源请求 | 装箱记录指名委托与包裹 | 还没被接受 |
| 委托已接受 | 接受决定信封到达 | 可以进入出库确认的前提之一 | 本上下文不自己判接受 |
| 待货主补正 | 委托停在等待受控补充 | 本上下文向货主要补正 | 货主不直接补 |
| 未接受 | 拒绝、撤回或有效取消 | 拆包回库，或换新包裹序号；平台备货整份办 | 同一来源请求键不复用 |
| 未配置 | 面单本体没配置，或代办授予没登记 | 这个包裹不出库确认 | 不编一份假面单 |
| 已入账收工 | 来源不是「仓配出库」 | 不改装箱记录 | 不答未决 |

## 应用流程

1. 打包完成，或预取被选中：按 `WF-RULE` 提交。平台备货等整份打包完，按提交轮次提交一份，带全部包裹。
2. 接受决定信封到达：推进装箱记录。不读委托内部状态。
3. 委托待受控补充：向货主要补正，再以货主名义提交新版本。
4. 资料版本已形成：待补充的由本上下文补；冲突按更正不放行；待复核或未决的等。等待时限没登记答未配置，包裹停在仓里（`WF-RULE`）。
5. 包裹取消已记录：这一件进放行条件，按出库截单成立办（UC-WF-016）。
6. 归属未决：原样重发同一来源请求。生产归属落在别处或暂停新准入：按未接受办。

## 一致性、幂等与并发

- 提交按来源请求键认重放，重放规则以小包托运 CONTEXT 为准。同一键不复用在下一轮提交上，平台备货用下一提交轮次。
- 信封按小包托运给出的身份认。重复到达答已有结果，不推进两次。
- 来源不是「仓配出库」的每一种信封各入账一次，不形成业务答复。

## 权限、隔离与审计

- 实际提交方记本上下文，请求方记货主客户账户。授权以小包托运 CONTEXT 的代办授予为准。
- 货主看得到哪一笔是代办提交的。
- 面单本体不进本上下文的册，只留引用。
