# UC-CC-001 为已接受包裹建立关务案件

状态：开发基线草案；稳定案件边界来自已确认领域规则，真实监管程序、责任角色和生产参数待提供

## 目标与边界

本用例从一组已接受包裹出现明确的监管履责需要开始，到 `customs-compliance` 按一个固定的监管辖区、进出口方向、监管程序和法定义务范围建立关务案件，关联适用包裹并保存初始关务参与方角色与资格快照，或者明确记录本次没有形成案件为止。

本用例包含：

- 使用不可覆盖的委托接受基线、当前有效包裹身份及其来源关系建立拟建案范围。
- 判断服务产品和运营责任是否要求运营企业在当前监管程序下建立关务案件。
- 固定关务案件的监管辖区、进出口方向、监管程序和法定义务范围。
- 关联属于该案件范围的明确包裹，并保存客户归属和来源资料引用，不复制或覆盖源事实。
- 分别确认初始关务参与方角色、关系、资格和账号授权依据；不从企业类型或代理关系自动推导角色。
- 严格区分案件已建立、条件不足、技术未形成、重复、冲突、未受理和不适用。

本用例不执行：

- 委托提交、接受、拒绝、取消、客户承诺或服务变更。
- 申报单元组建、受控跨客户合报、正式申报资料定稿或字段级专业裁决。
- 申报就绪判断、提交授权、监管凭证占用、正式提交或提交尝试。
- 技术回执、监管接收、业务受理、查验、扣留、放行、税费核定或监管处置。
- 路由选择、班次、容量、装载、节点作业、运输履约、异常案件或运营结算。

关务案件是一个监管责任容器，不是“清关中”状态，也不是一份已经可以提交的申报。建立案件后，申报单元、正式申报资料、就绪、授权和提交必须由后续独立用例形成。

## 四层对象必须分离

| 层次 | 对象 | 本用例是否形成 | 业务含义 |
|---|---|---|---|
| 客户服务范围 | 委托接受基线与包裹 | 否，只引用 | 运营企业已经接受的客户服务请求及客户声明范围 |
| 监管责任范围 | 关务案件 | 是 | 在一个固定监管辖区、方向、程序和法定义务范围内组织后续监管履责 |
| 申报处理范围 | 申报单元 | 否 | 按监管规则作为一次申报、审查、查验、放行或重报对象的业务集合 |
| 物理与运输范围 | 集运单元、总单、运输舱单、班次 | 否，只可引用已知事实 | 物理归组、运输单证或实际履约范围 |

同一委托、同袋、同总单、同舱单、同班次或同一路由都不能自动证明应建立同一个关务案件或申报单元。一个包裹可以先后进入出口、进口或其他独立监管程序，因此可以关联多个彼此独立的关务案件。

接受前可达性和初始路由使用的是不依赖正式案件的关务区域、口岸或申报路径资格判断；该前置判断不建立关务案件，也不形成申报或监管结果。本用例在委托接受后建立正式案件，因此不存在“必须先建案才能路由、又必须先路由才能建案”的循环。只有具体监管程序确实把当前路径作为案件身份成立依据时，路径尚未确定才阻塞建案。

| `party-commercial` | 提供参与方、法人、报关服务商关系、委派、账号持有人和使用授权的当前版本 | 不为具体案件分配角色，不形成关务资格或提交决定 |

| `node-operations` / `transport-fulfillment` | 仅在已经存在有效物理或运输事实时提供引用 | 本用例不等待尚未发生的收寄、实测、装载或运输事实，也不创建这些事实 |

## 启动条件

- 至少存在一个可以关联到明确委托接受决定和接受基线的包裹；只有提交版本而尚未接受的范围不得通过本用例建立正式关务案件。
- 请求必须说明本次拟履行的监管责任范围，并能够取得监管辖区、进出口方向、监管程序和法定义务范围的权威业务依据。
- 一次案件只能固定一个前述监管范围组合。出口、进口或其他独立监管程序必须分别建案，不得为了表达端到端旅程而合并。
- 当前服务产品、客户合同和运营责任必须要求运营企业在该范围承担关务处理或留痕责任。仅提供面单或外部渠道且运营企业不承担该关务范围时，返回不适用，不虚构案件。
- 当前路由、口岸或申报渠道尚未确定，不一定阻止建立案件；它们只有在适用规则把其作为案件身份成立条件时才阻塞。未知值不得用默认国家、口岸或渠道填充。
- 委托已接受不表示包裹已经收寄、测量、装袋、装载或运输。本用例不得把尚未发生的物理事实作为统一前置条件。

## 输入语义契约

下表定义稳定业务输入，不是 API、事件 Schema 或数据库字段清单。

| 输入组 | 权威来源 | 最低业务语义 | 使用约束 |
|---|---|---|---|
| 建案请求 | 请求方 / 上游编排 | 稳定请求关联、触发来源、拟建监管范围、明确包裹范围和业务发生时间 | 重复请求可查询；客户端时间或消息到达时间不能单独决定适用版本 |
| 接受依据 | `parcel-shipment` | 接受决定、接受基线、委托、客户账户、责任法人、合同、服务产品与服务要求引用 | 只读引用，不把接受解释为关务就绪或监管接受 |
| 包裹与来源资料 | `parcel-shipment` | 当前有效包裹身份、来源谱系、寄收件和客户原始货物及申报资料引用 | 不复制为正式申报资料，不覆盖客户原始值 |
| 固定监管范围 | 适用规则 / 关务责任方 | 监管辖区、进出口方向、监管程序、法定义务范围、依据版本和适用时点 | 缺少任一案件身份要素时不创建占位案件 |
| 服务与责任依据 | `party-commercial` / `parcel-shipment` | 运营责任法人、产品和合同下的关务责任、服务方关系及适用期间 | 不从网络服务、企业类型或技术账号访问能力推导责任 |
| 参与方资格来源 | `party-commercial` | 参与方、法人、委派、报关服务商关系、渠道账号持有人与使用授权版本 | `customs-compliance` 按角色逐项形成案件快照，不能把代理商等同申报人或责任主体 |
| 拟采用关务路径 | `network-routing` 或关务编排 | 已知的关务区域、口岸、申报路径、路由版本和适用时间 | 只是待关务确认的输入；缺少时是否阻塞由当前程序规则决定 |
| 已有物理或运输事实 | `node-operations` / `transport-fulfillment` | 已经形成的有效实测、控制、运输单证或移动事实引用 | 仅使用已经发生且适用的事实，不等待或发明未来事实 |

每项跨上下文依据必须可识别来源、版本、适用时间和当前修订状态。案件提交前发现接受基线引用、包裹身份、监管范围、责任关系或资格依据失配时，必须重新判断；不能用较早读取结果覆盖当前权威版本。

## 结果语义契约

| 结果 | 业务含义 | 必须返回或可查询的依据 | 禁止行为 |
|---|---|---|---|
| 关务案件已建立 | 已针对一个固定监管范围建立稳定案件，并关联明确包裹和初始角色资格快照 | 案件、固定范围、包裹关联、触发来源、角色与资格快照、采用版本、决定时间和审计 | 不得暗示申报单元、正式申报、就绪、授权、提交或放行已经形成 |
| 部分范围已建立 | 一次操作归组中的部分独立监管范围已经建案，其他范围仍条件不足或未形成案件 | 每个范围的案件或未决结果、逐包裹归属、缺口和续办引用 | 不得用汇总成功掩盖未决范围，也不得回滚已经合法建立的案件 |
| 已有案件 | 相同建案请求和相同业务内容已经形成案件 | 原请求、原案件、固定范围、包裹关联和当前适用性 | 不得创建第二个重复案件或重置原案件历史 |
| 建案条件不足 | 业务资料不足以固定案件身份、适用责任或必要初始角色 | 缺少或冲突的业务依据、受影响范围、已有输入和再次判断条件 | 不得创建“待确认国家”“默认出口”等占位案件，也不得伪装成技术错误 |
| 未形成案件 | 依赖超时、处理失败、持久化失败、并发冲突或输入版本失效导致本次未提交案件 | 请求、处理阶段、失败或冲突位置、已采用输入和安全续办引用 | 不得伪装为建案条件不足、不适用或案件已建立 |
| 建案请求冲突 | 同一请求身份携带不同包裹、监管范围、接受基线或责任内容 | 原请求、冲突范围、来源版本和纠正入口 | 不得静默覆盖原请求、案件或包裹关联 |
| 建案请求未受理 | 请求主体无权、租户或客户范围不成立，或者无法关联最小业务身份 | 请求来源、权限或身份错误和处理依据 | 不得创建占位案件或泄露其他客户是否存在 |
| 不适用 | 当前服务和责任范围不要求运营企业建立该关务案件 | 包裹、产品、合同、责任范围和不适用依据 | 不得以不适用代替资料不足，也不得解释为客户服务被拒绝 |

`建案条件不足`和`未形成案件`都是应用处理结果，不是关务案件生命周期状态。前者表示可以明确指出缺少的业务依据，后者表示本次没有完成权威业务判断或提交；二者都不能通过建立空案件规避。

`部分范围已建立`只是批量应用汇总，不是关务案件生命周期状态。批量请求按固定监管范围分别返回结果；一个范围失败或未决，不回滚其他范围已经合法建立的案件，汇总结果不能覆盖逐范围、逐包裹结果。

## 案件范围判断规则

| 层次 | 判断内容 | 不满足时 | 明确边界 |
|---|---|---|---|
| 1. 最小身份 | 租户、接受决定、接受基线、包裹和请求来源可关联 | 请求未受理或未形成案件 | 不以客户参考号、外部单号或提交批次代替包裹身份 |
| 2. 服务适用 | 产品、合同和运营责任是否要求当前关务处理 | 确定不承担时不适用；证据缺失时条件不足 | 网络服务、面单服务或渠道账号都不能单独推导关务责任 |
| 3. 固定监管范围 | 辖区、方向、程序和法定义务范围均可确定 | 条件不足 | 任何身份要素变化形成独立案件，不原地修改 |
| 4. 包裹归属 | 每个包裹是否属于该固定范围，并保留客户和来源关系 | 不属于的包裹排除并返回原因 | 排除不取消包裹、不拒绝委托，也不自动建立另一案件 |
| 5. 初始责任角色 | 适用角色、关系、资格和账号授权能逐项解释 | 必要角色不明时条件不足 | 同一参与方可兼任多个角色，但必须逐角色确认 |
| 6. 案件提交 | 当前输入版本仍适用，且不存在重复或冲突案件提交 | 重新判断、返回已有结果或未形成案件 | 不以包裹和监管范围组合永久去重；独立后续义务可以建立关联新案件 |

案件只固定监管责任范围，不固定未来所有申报单元、口岸、渠道、资料版本或监管结果。后续路径或资料变化是否仍属于原案件，必须依据该案件固定范围和适用监管规则判断；不能为了省事随意修改案件身份，也不能遇到任何变化都建立无关联新案。

## 应用流程

| 步骤 | 责任方 | 应用动作 | 结果与下一步 | 权威依据 |
|---|---|---|---|---|
| 1 | 建案接入 / `customs-compliance` | 接收建案请求并校验请求主体、租户、客户范围、接受基线和包裹关联 | 无权或最小身份不成立时请求未受理 | `ADR-SCOPE`、`ADR-FACT` |
| 2 | `customs-compliance` | 识别首次请求、相同重试、内容冲突或明确关联的新监管义务 | 重复返回已有案件；冲突不覆盖；独立义务保留关联来源 | `CC-RULE`、`ADR-FACT` |
| 3 | `customs-compliance` / `parcel-shipment` | 核验委托已接受、接受基线完整，并取得当前有效包裹及原始资料引用 | 尚未接受或身份无法解释时不建立案件 | `PS-BASE`、`CTX-REL` |
| 4 | `customs-compliance` / `party-commercial` | 判断产品、合同、责任法人和服务责任是否要求运营企业建案 | 不承担时返回不适用；依据缺失时条件不足 | `PC-ROLE`、`CTX-REL` |
| 5 | `customs-compliance` | 按适用规则确定监管辖区、进出口方向、监管程序和法定义务范围 | 任一身份要素不确定时返回条件不足，不创建占位案件 | `CC-LANG`、`CC-RULE` |
| 6 | `customs-compliance` | 把一次请求中的包裹按固定监管范围识别和分离 | 每个范围独立处理；不属于当前范围的包裹返回排除原因 | `CC-RULE` |
| 7 | `customs-compliance` / `party-commercial` | 逐角色取得参与方、关系、资格、委派和账号授权依据并形成初始快照 | 必要角色无法解释时条件不足；不从企业类型推导 | `CC-RULE`、`CTX-REL` |
| 8 | `customs-compliance` | 在适用时引用拟采用关务路径和已经发生的物理或运输事实 | 仅保存来源和判断用途，不取得路线或事实所有权 | `CTX-REL`、`ADR-FACT` |
| 9 | `customs-compliance` | 建立稳定关务案件，固定案件身份，关联包裹、来源触发和初始角色资格快照 | 准备提交案件最小业务结果 | `CC-LIFE` |
| 10 | `customs-compliance` | 提交案件、关联、采用依据、审计和对应事件发布意图 | 提交后进入申报单元与资料准备的后续用例 | `ADR-FACT` |

若一批包裹同时包含出口、进口或其他独立程序，应用可以在同一操作归组内分别建立多个案件，但每个案件仍有独立身份、提交结果和失败处理。批量操作本身不是关务案件。

## 案件内容与责任边界

每个关务案件至少表达以下业务内容：

- 稳定案件身份、集团租户和运营责任法人。
- 固定监管辖区、进出口方向、监管程序和法定义务范围。
- 建案触发来源、业务发生时间、判断时间及实际采用规则版本。
- 明确关联的包裹、客户账户和接受基线引用，以及包裹来源关系。
- 初始关务参与方角色、参与方身份、资格、委派、服务方关系、账号授权依据和适用时间。
- 已知关务路径、物理或运输事实的来源引用，以及它们是否参与本次判断。
- 重复、替代、后续或其他案件关系的已知依据；没有依据时不得猜测关系。

案件不得包含或暗示：

- 已经形成申报单元，或者多个客户已经取得合报资格。
- 客户原始资料已经成为正式申报资料，或者归类、原产地、价值和监管凭证已经确认。
- 资料已经就绪，提交已经授权，申报已经发送或监管机构已经收到。
- 包裹已经收寄、测量、装袋、装载、出发、到达、清关或放行。
- 运营企业、报关服务商、代理商、账号持有人、申报人、法定义务人和实际付款方可以互相推导。

## 提交边界与后续交接

- 一个案件的固定身份、包裹关联、初始角色资格快照、来源依据、审计和对应事件发布意图必须形成同一个最小业务提交结果。
- 一次请求包含多个独立监管范围时，每个案件分别越过提交边界；不能用一个批量事务把已经合法成立的其他案件全部回滚。
- 跨上下文接受、商业资格、路线和来源事实由其所有者独立形成。本用例保存实际采用引用，不要求分布式事务，也不回写来源。
- 处理失败且案件最小结果尚未完整提交时，只保存请求和处理尝试，不发布“关务案件已建立”业务事实。
- 案件提交成功后事件首次投递失败，只重试同一发布意图，不删除案件、不重复建案，也不把案件改为条件不足。
- 下游只能引用已经提交的案件继续组建申报单元和准备正式申报资料。案件存在不能被当作申报就绪或方向性运输动作已经获准的门禁结果。

## 一致性、幂等与并发

- 接受交接身份和关务案件身份必须分离。一个接受交接可以产生多个独立案件；一个案件也可以关联来自多个接受交接的明确包裹，但这不自动形成申报单元或跨客户合报资格。
- 同一建案请求身份携带相同接受基线、包裹、监管范围和责任内容重复到达时，返回已有案件或原未决处理关联，不创建重复案件。
- 同一请求身份携带不同业务内容时形成冲突。明确纠正或独立监管义务必须使用关联的新请求，不覆盖原案件。
- 不得仅以“包裹 + 辖区 + 方向 + 程序”作为永久唯一规则；同一包裹以后可能因独立法定义务、撤销重报或后续监管事项建立关联的新案件。
- 同一请求并发处理时只能有一个完整案件越过提交边界；其他处理读取已有结果或报告冲突。
- 请求处理期间接受基线、包裹身份、责任关系、资格、规则或固定监管范围依据发生适用变化时，提交前必须重新判断；暂时无法确认时不创建案件。
- 后续商业关系、角色资格、账号授权或规则变化不能覆盖已经形成的案件快照。后续提交仍必须重新取得当时适用资格。
- 响应或事件丢失时通过稳定请求关联查询原处理结果，不通过无关联新请求猜测案件是否存在。

## 权限、隔离与审计

- 只有代表明确运营责任范围、并拥有相应租户和关务建案权限的主体可以发起建案；具体角色名称和授权范围必须来自版本化业务授权，不写死为“管理员”或固定岗位。
- 案件、包裹关联、原始资料引用和处理结果必须按集团租户、责任法人和客户账户隔离。集团统一运营不允许客户账户之间互相查询资料。
- 同一关务案件未来可能包含多个客户的申报范围，但本用例只建立案件关联，不据此授予跨客户查看权，也不证明允许跨客户合报。
- 审计至少关联请求主体、操作主体、接受决定与基线、包裹、客户账户、固定监管范围、采用规则、角色与资格快照、来源版本、判断时间、处理尝试和发布结果。
- 地址、货物和申报原始资料按履行当前监管义务所需的最小范围参与建案；日志、指标、追踪、查询和批量错误不得泄露不必要的明文或其他客户的存在。
- 人工操作不能直接修改案件固定身份、删除包裹关联历史、覆盖来源资料或把条件不足强制改为案件已建立。身份要素变化必须进入关联新案件或受控纠正流程。

## 可观测性与非功能验收占位

- 从接单请求、委托、接受决定、接受基线、包裹、建案请求到关务案件必须具有稳定关联。
- 分别观测请求校验、接受依据读取、服务适用判断、监管范围确定、包裹分组、角色资格装配、案件提交和结果投递的耗时与失败位置。
- 分别统计案件已建立、已有案件、条件不足、未形成案件、冲突、未受理和不适用；条件不足按缺失业务依据分类，未形成案件按技术或依赖阶段分类。
- 监控跨程序混案、无接受基线建案、缺少固定身份要素的占位案件、从企业类型推导角色、案件直接生成申报或监管结果等不变量违规。
- 可用性、响应时间、批量窗口、恢复目标和数据新鲜度由 `PAR-NFR-06` 及验收矩阵 `NFR-02` 参数化，本文件不填写未经证据确认的数值。

## 首发试点叠加条件

本节只约束首发验证，不改变长期用例：

- 只对 `PAR-COM-01`、`PAR-COM-03`、`PAR-COM-05` 和 `PAR-COM-06` 最终登记的锚点客户、责任法人、网络服务产品和合同范围建立生产案件。
- 出口和进口分别使用 `PAR-NET-02`、`PAR-NET-03`、`PAR-CUS-01` 和 `PAR-CUS-02` 登记的真实监管区域、程序、服务方和渠道依据，不填充默认国家、口岸或程序。
- 初始角色、主体资格、委派、账号授权、规则和凭证来源只采用 `PAR-CUS-03`、`PAR-CUS-04` 的已确认依据。
- 首发生产提交仍须由授权业务角色逐次确认且不启用自动申报；本用例本身无权形成提交授权或提交尝试。
- 正常出口、进口建案采用真实生产证据；复杂跨客户范围只按验收矩阵允许的隔离模拟或自然生产事实验证，不为验收向监管渠道提交虚假资料。
- 真实参数未登记前可以实现通用骨架和受控测试，但不能宣称 `CUS-01`、`CUS-08` 的生产证据成立。

## 验收示例

| ID | 场景 | 预期结果 |
|---|---|---|
| `AT-CC-001` | 已接受网络服务包裹具有完整出口监管辖区、方向、程序、法定义务和责任依据 | 建立出口关务案件，关联包裹与初始角色资格快照；没有形成申报单元、就绪或提交 |
| `AT-CC-002` | 同一包裹需要先后履行出口和进口监管程序 | 分别建立两个案件并保留包裹关联；不得建立覆盖端到端旅程的单一清关案件 |
| `AT-CC-003` | 一次操作包含两个身份完整的出口包裹和一个进口程序尚无法确定的包裹 | 出口范围合法建案，进口范围返回条件不足；汇总为部分范围已建立，不回滚出口案件或创建进口占位案件 |
| `AT-CC-004` | 同一固定范围内关联多个同一客户包裹 | 案件可以关联明确包裹并分别保留来源；不据此自动形成一个申报单元 |
| `AT-CC-005` | 同一固定范围内包含不同客户账户的包裹 | 持续保留逐包裹客户隔离；案件关联不证明允许跨客户合报或共享客户资料 |
| `AT-CC-006` | 多个包裹已同袋、同总单、同舱单或同班次 | 物理或运输归组仅作为来源引用，不自动决定同案、合报或申报范围 |
| `AT-CC-007` | 建案请求缺少监管辖区、方向、程序或法定义务范围之一 | 返回建案条件不足和明确缺口，不创建默认或占位案件 |
| `AT-CC-008` | 当前服务只提供外部面单渠道，运营企业不承担该关务范围 | 返回不适用并保存产品、合同和责任依据；不虚构关务案件 |
| `AT-CC-009` | 相同请求身份和相同业务内容重复到达 | 返回已有案件或原处理关联，不创建第二个案件 |
| `AT-CC-010` | 相同请求身份携带不同包裹或监管范围 | 返回请求冲突并保留原请求与案件，不静默覆盖 |
| `AT-CC-011` | 两个处理并发尝试提交同一建案请求 | 只有一个案件越过提交边界；另一处理查询已有结果或报告冲突 |
| `AT-CC-012` | 报关服务商存在，但申报人、法定义务人或账号使用授权无法解释 | 必要角色不明时返回条件不足；不得从“报关服务商”自动推导其他角色 |
| `AT-CC-013` | 渠道服务方是底层监管渠道的代理商 | 分别记录服务方关系、账号持有人、申报人和责任角色；代理关系不合并角色 |
| `AT-CC-014` | 固定监管范围完整，但路由尚未选定最终口岸或申报渠道 | 当前程序规则不要求其作为案件身份时可以建案并保留待后续确认；不得填默认口岸或把案件解释为就绪 |
| `AT-CC-015` | 案件建立后参与方关系、资格或账号授权发生变化 | 原案件快照不被覆盖；后续申报准备和提交重新校验当前资格 |
| `AT-CC-016` | 读取商业资格或监管规则时依赖超时 | 未形成案件并保留安全续办引用；不伪装成条件不足或不适用 |
| `AT-CC-017` | 案件最小结果提交成功，但结果事件首次投递失败 | 案件、包裹关联和快照保持不变；重试同一发布意图，不重复建案 |
| `AT-CC-018` | 建案完成后检查下游对象 | 只存在案件及其关联；申报单元、正式申报资料、就绪、授权、提交和监管结果均未被提前创建 |
| `AT-CC-019` | 正式申报所需字段尚不完整，但案件四项固定身份、适用责任和初始角色均可确定 | 可以建立案件并保留原始资料引用；字段缺口留给后续资料准备，不把案件写成申报就绪 |
| `AT-CC-020` | 交接只有“已接受”状态字符串，没有可验证接受决定和接受基线 | 请求未受理或未形成案件；不得依据状态字符串创建案件 |
| `AT-CC-021` | 接受前可达性或初始路由只请求关务路径资格判断 | 只形成独立资格判断，不触发本用例，也不创建正式案件 |
| `AT-CC-022` | 建案后出现不同监管方向、程序或独立法定义务 | 建立有关联的新案件并保留原案；不得修改原案件四项固定身份吸收新义务 |

## 生产参数与待决风险

下列内容不改变稳定案件边界，但在真实值提供前阻塞生产建案：

| 参数或决策 | 当前状态 | 对本用例的影响 |
|---|---|---|
| `PAR-COM-01`、`PAR-COM-03`、`PAR-COM-05`、`PAR-COM-06` | 真实客户、责任法人、网络服务产品和合同待最终登记 | 无法实例化服务责任和客户隔离范围 |
| `PAR-NET-02`、`PAR-NET-03` | 真实始发和目的监管区域待提供 | 无法实例化出口、进口案件范围 |
| `PAR-CUS-01`、`PAR-CUS-02` | 真实出口、进口程序、服务方和渠道待提供 | 无法发布生产建案适用规则 |
| `PAR-CUS-03`、`PAR-CUS-04` | 真实参与方角色、资格、授权和规则来源待提供 | 无法形成可用于生产的角色资格快照和程序依据 |
| 案件划分与触发规则 | 待随真实监管程序确认：哪些业务范围共用一个案件、何时建立关联新案、何时由接受或路径结果触发 | 通用请求与案件模型可开发，但不能固化自动建案和案件复用策略 |
| `PAR-NFR-06` | 关务关键流程目标待提供 | 无法确定响应、新鲜度、批量窗口和恢复验收门槛 |

不得用一个包裹一个案件、一个委托一个案件、一个国家一个案件或一个运输批次一个案件作为未经监管依据确认的通用默认。案件划分规则必须在固定身份不变量内由真实监管程序和运营责任决定。

## 开发拆分建议

真实参数未齐备前，可以按以下顺序实现：

1. 渠道中立的建案请求、稳定处理关联和原始触发保全。
2. 接受决定、接受基线、当前包裹身份和客户原始资料的只读协作契约。
3. 服务责任适用判断，以及固定监管辖区、方向、程序和法定义务范围的校验器。
4. 参与方、法人、委派、报关服务商关系和账号授权的只读协作及角色快照模型。
5. 关务案件、包裹关联、来源依据和案件关系的不可覆盖持久化边界。
6. 案件已建立、已有案件、条件不足、未形成案件、冲突、未受理和不适用结果。
7. 幂等、并发提交保护、事件发布意图、结果查询、租户与客户隔离。
8. `AT-CC-001` 至 `AT-CC-022` 的应用与领域测试骨架；真实区域、程序、角色和规则使用显式未配置状态。

完成本用例只闭合关务案件建案。下一业务用例为[组建申报单元并形成正式申报资料](./UC-CC-002-FORM-DECLARATION-UNIT-AND-DATA.md)，负责形成字段级可追溯的资料准备结果；申报就绪、提交授权、实际提交和监管结果仍应继续分层实现。
