# UC-CC-006 接收、查询并分层记录申报外部结果

状态：开发基线草案；来源保全、权威分层、本产品原提交或承运商外部监管舱单引用的互斥关联、结果待确认、安全再次发送和部分范围边界已确认，真实渠道来源矩阵、代码映射、查询语义及监管凭证定案参数待提供

## 目标与边界

本用例从申报渠道、报关服务方、承运商受控来源或监管机构产生的一项同步响应、异步消息、查询响应，或者一个`原提交结果仍待确认`的查询续办开始，到 `customs-compliance` 保全来源响应，将结果关联到本产品原提交或 [UC-CC-012](./UC-CC-012-RECEIVE-AND-RELATE-EXTERNAL-REGULATORY-MANIFEST.md) 已接受的承运商外部监管舱单引用，按来源权威语义形成一个或多个分层外部结果，或者明确保持待关联、解释未决、来源响应冲突、外部结果冲突或原提交结果仍待确认为止。

本用例包含：

- 在解释之前保全可验证的来源身份、原始业务语义、来源时间、接收时间、业务关联和完整性依据。
- 把技术回执、监管接收、业务受理、监管过程决定、监管核定税费、放行结果和监管处置决定分别形成，不用一个“清关状态”覆盖。
- 只允许在对应结果层具有权威语义的来源形成该层事实；报关服务方或技术中介的响应不自动升级为监管机构事实。
- 将来源响应关联到明确的关务案件、申报单元、结果适用范围，以及互斥的本产品提交版本/提交尝试或承运商外部监管舱单引用；无法安全关联时保留待关联，不创建占位提交或猜测归属。
- 处理重复投递、同标识内容冲突、迟到消息、来源更正、乱序到达、一个响应包含多个结果和批量逐项部分处理。
- 对结果待确认的原提交发起受控查询；查询沿用原外部业务关联，不形成新提交版本、提交尝试或授权使用。
- 在权威结果和真实规则同时满足时，形成监管凭证占用的释放或核销关系；结果未知时继续保持占用。
- 形成面向后续更正/补充/撤销重报、查验/扣留/处置、税费、放行门禁和异常协调的明确交接，但不代替这些流程执行。

本用例不执行：

- 建立或修改关务案件身份、申报单元、正式申报资料、申报就绪判断、提交授权、提交版本或既有提交尝试。
- 因收到响应、查询无记录或操作员点击而自动重发申报；受控新尝试仍由 [UC-CC-005](./UC-CC-005-FREEZE-SUBMISSION-AND-INITIATE-ATTEMPT.md) 形成。
- 从技术成功推导监管接收，从监管接收推导业务受理，从业务受理或付款推导放行，或者因为高层结果到达而补造缺失的低层事实。
- 使用 HTTP 状态、接口调用成功、文件到达、自由文本或未经确认的渠道代码直接生成监管结果。
- 修改或删除原始来源响应、旧解释、旧外部结果、提交内容、客户原始资料、节点实测或运输事实。
- 决定申报资料如何更正、是否补充、是否撤销重报，或者建立替代申报单元和替代案件。
- 执行查验、隔离、开封、重封、销毁、退运装载或其他物理处置。
- 形成实际付款、退款、补缴、客户税费代垫回收、服务费用或运营结算结果。
- 直接形成或解除内部合规限制；已接受的外部结果如被登记规则采用，只能作为 `UC-CC-011` 的限制形成或解除依据引用。
- 直接发布客户通知、关闭异常案件、关闭或重开关务案件。

来源响应只是外部输入；只有完成来源资格、关联、结果层次、适用范围和时效判断后，才形成已接受外部事实。来源被保全、响应到达、渠道技术成功和监管业务结果是不同事情。

## 外部结果层次

| 结果层 | 合格来源语义 | 最低适用范围 | 该结果证明 | 该结果不证明 |
|---|---|---|---|---|
| 技术回执 | 申报渠道对连接、报文接收或技术校验的明确反馈 | 提交尝试及技术动作 | 对应技术层发生的成功、失败或其他明确结果 | 监管接收、业务受理、监管决定或放行 |
| 监管接收 | 监管机构确认收到明确申报，或合格中介明确转述该监管确认 | 提交版本或监管方确认的申报范围 | 监管机构已收到该范围 | 已进入实质程序、内容被接受或已经放行 |
| 业务受理 | 监管机构确认明确申报进入适用监管程序 | 提交版本及受理范围 | 对应范围已进入该程序 | 查验结束、税费完成、处置完成或放行 |
| 监管过程决定 | 监管机构提出补充资料、查验、扣留、更正要求或其他过程义务 | 决定明确覆盖的单元、包裹、货物或动作 | 对应范围产生明确监管要求 | 物理动作已执行、内部限制已解除或案件已关闭 |
| 监管核定税费及税费后续决定 | 监管机构对明确申报范围和法定义务人形成税费结果、监管补缴要求或监管税费退回决定 | 税费范围、义务人、币种、金额/退回范围、版本和适用时间 | 法定监管税费义务或其后续调整已按该版本形成 | 实际付款、资金退回、客户回收或已经放行 |
| 放行结果 | 监管机构形成全部、部分或附条件放行 | 放行明确覆盖的申报或货物范围及条件 | 对应范围取得该放行事实 | 同单其他范围放行、内部限制解除或货物已实际移动 |
| 监管处置决定 | 监管机构形成隔离、移交、销毁、退运、没收等处置要求 | 明确对象或范围及依据，以及来源实际提供或适用程序要求的数量、期限和条件 | 对应范围获得处置决定 | 物理执行已经发生、本次执行范围已核对覆盖或监管义务已经终结 |

一个来源响应可以承载多个层次，但每个层次必须分别形成事实、分别保存来源语义和范围。真实程序中的“拒收”“退单”“不受理”“改单通知”等代码必须按其权威业务语义映射；在参数未确认前不得统一塞入“技术失败”或虚构一个通用“清关失败”。

## 启动条件

- 接收路径能够区分申报渠道、报关服务方、监管机构或其他真实来源身份，并保存该来源在当前结果层的权威角色；具体认证方式由真实渠道合同提供。
- 对来源消息至少可以保全其稳定来源关联或来源声明的业务标识、原始业务语义、业务发生/适用时间、接收时间和完整性判断。
- 已发起提交应当能够通过提交版本、提交尝试、渠道、账号和稳定外部业务关联进行确定性匹配；缺少某一标识不等于允许按最近案件或客户猜测。
- 关联承运商外部监管舱单的结果必须引用 `UC-CC-012` 已接受的外部身份、来源版本、程序、方向和明确范围；该分支不要求也不得补造本产品提交版本或提交尝试。
- 查询必须引用一个已经形成的提交版本和提交尝试，以及原渠道允许使用的原业务关联；不存在原提交时不得建立占位提交用于查询。
- 原提交查询、安全再次发送和 `UC-CC-005` 受控新尝试只适用于本产品实际发起的申报；承运商外部监管舱单由承运商负责形成与提交，本用例不得对其建立本地查询或再次发送分支。
- 结果代码、来源角色、适用范围和更正语义只有在 `PAR-CUS-01`、`PAR-CUS-02` 及真实规则映射确认后才能生产解释；未知代码进入解释未决。
- 监管凭证释放和核销只在 `PAR-CUS-04` 已登记何种权威结果代表“未使用”或“最终使用成立”时执行。

| 凭证使用规则 | `customs-compliance` / 规则来源 | 原占用、凭证版本、范围、何种结果构成最终使用或未使用及部分处理方式 | 技术成功或查询无记录不自动触发核销/释放 |

## 来源接受与关联规则

- 接入先执行不读取候选业务内容的来源身份、租户、完整性和接入范围最小安全校验。通过后，来源响应必须先形成不可覆盖的完整来源记录，再形成关联、分类和有效性判断；失败时只形成最小安全审计记录。业务处理失败不能要求外部来源构造一个不同消息身份重发。
- 同一来源消息身份、版本和内容重复到达时，只增加必要的投递观察或返回已有处理结果，不创建第二份相同外部事实。
- 已通过最小接入安全校验的输入中，同一来源消息身份和版本携带不同内容时形成来源响应冲突，不按最后到达覆盖；如果来源明确声明更正或替代，则形成新来源版本和更正关系。
- 关联必须优先使用来源与本产品原提交或已接受外部监管舱单引用共同认可的稳定业务关联。只有按真实来源契约要求的关联条件得到唯一候选，且来源已提供的身份、渠道/责任承运商、程序、方向和范围信息均无冲突时，才可形成关联；不得把某个来源未提供的字段伪装成已匹配。
- 无法唯一关联时形成`来源响应已保全待关联`。待关联响应不创建占位案件、提交版本或尝试，也不改变任何候选提交的当前结果。
- 后续人工或自动关联必须保存采用证据、决定方式、责任角色和时间；修正错误关联时保留原关系和原解释，形成新的有效性判断。
- 一个批量来源信封可以包含多个本产品提交、多个外部监管舱单引用或多个结果项。信封只表达传输归组，每项结果仍分别关联业务目标和范围；一项待关联、解释未决、冲突或未形成外部结果不回滚其他已接受项。
- 回执先于本地提交事件或外部监管舱单引用投影到达时，按稳定关联保全并等待业务目标可见，不丢弃、不猜测创建第二提交或占位外部引用。

## 结果语义契约

| 结果 | 业务含义 | 必须返回或可查询的依据 | 禁止行为 |
|---|---|---|---|
| 分层外部结果已形成 | 来源、本产品原提交或外部监管舱单引用、结果层、明确范围和时效均可确定，形成一个或多个已接受外部事实 | 来源记录、关联、解释规则、业务结果目标、结果层、范围、业务时间和接受时间 | 不得补造缺失层次、覆盖旧结果或用单一清关状态替代 |
| 来源响应已保全待关联 | 来源可接受，但尚不能唯一关联本产品原提交、外部监管舱单引用或结果范围 | 来源、候选关联（如有）、缺口、接收时间和续办入口 | 不得猜测案件、按最近提交/舱单匹配或泄露候选客户 |
| 外部结果解释未决 | 业务结果目标已关联，但来源角色、代码、层次、时效或范围无权威解释 | 原始语义、已有规则、缺少的映射/决定、影响范围和续办入口 | 不得按成功/失败默认值或人工自由文本改变业务结果 |
| 原提交结果仍待确认 | 当前没有足够权威依据判断原尝试是否已在目标监管程序中形成可继续有效的外部申报身份；该判断与查询执行状态及后续受理、查验、税费、放行或处置等待分别存在 | 原提交、全部已知尝试、已有来源响应、查询能力/历史、当前缺口和下一续办条件 | 不得创建新提交、释放凭证占用或把查询失败、无查询能力、无记录直接当作申报失败或未提交 |
| 原提交安全再次发送条件已确认 | 合格来源与真实规则共同证明原尝试没有在目标监管程序中形成可继续有效的外部申报身份，且按渠道防重、查询及时效规则，再次发送同一提交版本不会造成重复申报 | 原提交、全部尝试和外部身份、查询/结果证据、来源权威、规则版本、判断时间及允许再次发送的版本、渠道和范围 | 本用例不得直接创建新尝试；只可请求 `UC-CC-005` 受控处理，也不得把该判断解释为原尝试从未发生或作为凭证释放依据 |
| 已有来源处理结果 | 相同来源身份、版本和内容已经完成保全及业务处理 | 原来源、重复投递、原关联、原结果及当前有效性 | 不得重复形成外部事实或触发第二次下游动作 |
| 来源响应冲突 | 同一来源消息身份和版本携带不同内容，无法确定哪份内容代表该来源消息 | 全部冲突输入、来源身份、消息身份/版本、接收时间和复核入口 | 不得选择最后到达内容、继续解释冲突输入或删除任一输入 |
| 外部结果冲突 | 不同的合格来源事实在同一结果层、范围和业务事项上相互矛盾，且无法按权威、更正或时效规则裁决 | 全部来源事实、结果层、范围、业务时间、解释规则、冲突前当前有效判断和复核入口 | 不得按到达顺序或操作员偏好选定结果，不得由任一冲突来源直接改写当前有效判断，也不得在未确认冲突门禁规则时自行阻断或放行业务动作 |
| 来源信封逐项处理汇总 | 批量信封中的各项目分别形成分层外部结果、待关联、解释未决、来源响应/外部结果冲突或未形成外部结果；该汇总不是监管部分放行或部分处理事实 | 信封、逐项关联、逐范围结果及非监管汇总 | 不得用整批状态覆盖逐项结果、回滚已接受事实或把汇总发布成监管结果 |
| 来源响应未受理 | 来源身份、租户、完整性、渠道或接入范围不合法，不能进入业务解释 | 最小来源证据、校验依据、未受理原因和接收时间 | 不得形成外部业务事实，也不得泄露候选提交或客户 |
| 未形成外部结果 | 来源已经安全保全，但关联、解释、持久化或事件提交因技术原因未完成 | 来源记录、失败阶段、已完成步骤和安全恢复引用 | 不得要求来源换标识重发、伪装成解释未决或丢失来源 |

`外部结果解释未决`表示业务语义尚无权威规则，`未形成外部结果`表示技术处理没有完成。二者都不是监管拒绝、技术失败或清关失败。

## 来源权威与解释规则

- 申报渠道只对其明确技术层反馈负责。只有来源契约明确证明某字段转述监管机构确认时，该字段才可以另行形成监管接收、业务受理或其他监管事实。
- 报关服务方、代理商、渠道账号持有人和监管机构是不同角色。服务方能够查询或转发消息，不等于它拥有监管决定权。
- 一个响应同时包含“报文接收成功”和“监管已接收”时，可以引用同一来源记录分别形成技术回执与监管接收，但必须分别保存语义依据。
- 监管接收、业务受理、过程决定、税费、放行和处置必须有对应监管权威语义；系统内部规则、人工勾选、付款结果、节点作业或异常关闭不能代替。
- 更高层结果先到达时，接受该合格事实但不补造较低层事实。例如业务受理先到达，可以形成业务受理，不能虚构技术回执或监管接收。
- 同一层次和业务事项的后续明确更正形成新结果及更正关系；原结果保持历史。更正范围变化时，按新旧范围的交集和差集分别判断：交集按明确更正语义处理，未被新结果覆盖的旧范围保持原判断，新扩展范围独立校验来源权威和适用性；不得用新范围整体覆盖旧范围。没有更正语义的矛盾结果保持冲突。
- 不同层次的结果不因表面成功/失败不同而相互覆盖。监管接收可以证明业务申报已经到达监管方，但不会删除一项冲突的技术回执。
- 代码映射必须版本化并绑定来源、程序和生效范围。新映射可以形成新的解释判断，但不能修改原始代码或把历史解释伪装成从未存在。
- 无法解释的“成功”“失败”“拒收”“退单”等自由文本保持未决，直到真实程序提供权威语义；不从中文/英文关键词猜测结果层。

## 原提交查询规则

- 查询只针对一个明确提交版本、原提交尝试和原外部业务关联；批量查询也必须逐原提交返回结果。
- 查询触发可以来自通信超时、预期结果缺失或经授权的人工核对，但具体等待窗口、日历、次数和升级规则由真实渠道与 `PAR-NFR-06` 提供，不写死通用轮询周期。
- 查询请求、查询尝试和查询响应必须可追溯，但查询不是提交尝试，不使用新的申报业务标识，不重新消费提交授权或监管凭证额度。
- 查询响应按照与主动推送相同的来源接受、关联、分类、时效、重复和冲突规则处理；查询接口返回成功本身不形成申报结果。查询响应必须区分新发生事件与截至明确时间的状态快照；重复快照只形成来源观察和当前解释，不重复制造监管事件，快照变化也不自动成为来源更正。
- 查询返回“无记录”“未找到”或空结果时，只有来源权威和真实规则共同证明原尝试没有在目标监管程序中形成可继续有效的外部申报身份，且再次发送同一版本不会造成重复申报，才可形成安全再次发送条件；否则原提交结果继续待确认。
- 查询失败、超时或暂时不可用只记录查询执行状态和查询技术结果，原提交继续待确认，不把查询技术失败写成申报失败。
- 待确认期间收到推送结果时接受推送来源事实，并按当前结果决定是否停止后续查询；已经发生的查询历史继续保留。
- 渠道没有原提交查询能力时进入受控人工核对与剩余风险，不得以新标识试探性重报。
- 只有`原提交安全再次发送条件已确认`时，才向 `UC-CC-005` 提出关联原版本的受控新尝试请求；本用例不直接发送。该判断必须持续关联原尝试及全部后续尝试；迟到结果证明早期尝试已形成可继续有效的外部申报身份时，必须使该判断不再有效。

## 时间、乱序、更正与当前判断

- 每项来源分别保存来源业务发生时间、规则声明的适用时间、消息生成时间（如有）、系统接收时间和解释时间，不能统一用最后更新时间代替。
- 迟到响应仍按来源语义和业务/适用时间参与判断；案件已关闭、查询已停止或包裹已移动都不是丢弃来源事实的理由。
- 新到消息不自动成为当前结果。当前解释由来源权威、结果层、明确范围、业务时间、来源版本和更正关系共同决定。
- 查询响应、主动推送和人工取得的来源证据可以到达顺序不同；它们只在同一层次、同一范围和同一业务事项上比较，不跨层相互覆盖。
- 来源明确撤销或更正旧结果时，形成新来源事实、与旧结果的更正关系及新的当前判断；不得删除旧结果或回写提交版本。
- 两个合格来源对同一层次和范围给出无法裁决的相反结果时保持外部结果冲突，不得由任一冲突来源直接改写当前有效判断。是否将依赖该层的动作转为受控阻断，必须由已确认的冲突门禁规则形成新的有效判断；规则未登记时显式保持门禁判断未决，不能按来源到达先后或操作员偏好裁决。
- 结果事件提交成功但下游发布首次失败时，外部结果保持有效，只重试同一发布意图，不重新解释来源或重复触发监管动作。

## 明确范围、部分结果与跨客户隔离

- 技术回执通常关联提交尝试；监管结果必须关联来源明确覆盖的提交、申报单元、包裹、货物、申报行、数量或动作范围。具体可用范围由真实程序确定。
- 一个申报单元可以出现部分查验、部分扣留、部分放行或附条件放行。系统逐范围保存结果并派生当前门禁，不维护一个可以吞并成员差异的单元级“已清关”事实。
- 未被结果明确覆盖的范围保持原有判断或待确认，不从同单、同袋、同舱单、同班次或同一客户关系扩大结果。
- 跨客户合报的外部响应可以包含监管所需共同范围，但客户视图、查询、错误、导出和通知只能披露该客户有权看到的成员与结果。
- 批量信封处理允许逐项形成分层外部结果、待关联、解释未决、来源响应/外部结果冲突或未形成外部结果；批量汇总不具有监管事实效力。
- 放行结果只使其明确范围满足对应的放行前置条件，不形成任何限制解除事实；其他监管扣留、未完成处置、方向性限制和内部合规限制继续由各自责任来源独立判断和解除。
- 监管过程决定或处置决定只形成授权/义务及范围，节点或外部执行方的实际动作和关务核对结果继续独立形成。

## 监管凭证定案

- 技术回执、监管接收、业务受理或放行中的任何一层都不预设为通用凭证核销时点；真实程序必须明确哪个权威结果代表使用成立。
- 当已接受权威结果和 `PAR-CUS-04` 规则共同证明凭证使用最终成立时，针对原占用的明确凭证版本、申报范围和次数/额度形成核销关系。
- 当权威结果证明申报未使用该凭证，且规则明确允许释放时，针对原占用形成释放关系；“查询无记录”只有满足已确认权威语义时才可作为依据。
- 结果待确认、来源待关联、解释未决、同层冲突或只有技术失败时，原占用保持，不得释放或核销。
- 监管只确认部分范围使用时，只核销明确使用范围；其余范围按规则保持占用或形成部分释放，不以一个当前余额覆盖历史。
- 迟到权威结果或后续监管更正改变凭证使用结论时，形成新的调整、释放或补充核销关系，原占用和既有定案历史不被覆盖。如果此前释放的额度已被其他提交占用，不得覆盖后续占用或制造负余额；必须形成可追溯的凭证额度冲突或超用判断，阻止受影响凭证的新增占用并交接受控处理。

任何交接失败都只重试同一已形成事实的发布意图，不能重新接收来源、重发申报、重复核销凭证或把下游执行失败改写成监管结果无效。

## 应用流程

| 步骤 | 责任方 | 应用动作 | 结果与下一步 | 权威依据 |
|---|---|---|---|---|
| 1 | 关务结果接入 | 先完成不读取业务内容的最小接入安全校验；通过后保全完整来源信封、原始语义、来源时间、接收时间和完整性依据 | 完整保全成功后才进入解释；不合法来源只留最小安全审计并未受理 | `ADR-FACT`、`ADR-SCOPE` |
| 2 | 关务结果接入 / `customs-compliance` | 识别首次消息、相同重复、同身份内容冲突或明确更正版本 | 重复返回已有；冲突不覆盖；更正关联旧来源 | `ADR-FACT`、`ADR-INGEST` |
| 3 | `customs-compliance` | 使用稳定外部业务关联匹配互斥的本产品提交版本/尝试或外部监管舱单引用，并匹配案件和候选结果范围 | 唯一匹配才关联；否则待关联，不创建占位提交或外部引用 | `CC-SUBMIT`、`CC-MANIFEST`、`CC-RULE` |
| 4 | `customs-compliance` | 选择来源、程序和适用时间对应的结果解释规则版本 | 规则缺失或代码未知时解释未决，不填默认状态 | `CC-RULE`、`ADR-FACT` |
| 5 | `customs-compliance` | 按来源权威语义拆分技术、监管接收、业务受理、过程决定、税费、放行和处置结果 | 各层各范围分别形成；缺失层不补造 | `CC-LANG`、`CC-LIFE` |
| 6 | `customs-compliance` | 结合既有同层结果、业务时间、更正关系和范围形成当前判断 | 迟到不丢弃；冲突保持；不按最后到达覆盖 | `ADR-FACT`、`CC-RULE` |
| 7 | `customs-compliance` | 按已确认凭证规则判断保持占用、释放、核销或部分定案 | 只有权威结果和规则均成立才改变使用关系 | `CC-RULE`、`CC-LIFE` |
| 8 | `customs-compliance` | 提交来源接受判断、分层结果、当前解释、审计和发布意图 | 形成不可覆盖结果；发布失败只重试原意图 | `ADR-FACT`、`ADR-INGEST` |
| 9A | 原提交查询能力 | 对待确认原提交形成查询请求并调用原渠道查询，分别记录请求、尝试和技术结果 | 只查询原关联；查询执行状态独立，失败、无能力或无确定结果时原提交结果继续待确认 | `CC-SUBMIT`、`CC-LIFE` |
| 9B | 关务结果接入 | 将查询响应作为来源响应重新进入步骤 1 至 8 | 查询接口成功本身不形成申报结果 | `ADR-FACT`、`CC-RULE` |
| 10 | `customs-compliance` | 向后续业务提供范围明确的已接受结果和处理请求 | 下游拥有各自决定/执行；不得回写外部事实 | `CTX-REL`、`E2E-05` |

一个来源信封包含多个结果项时，逐项执行步骤 3 至 8。一个项目形成待关联、解释未决、来源响应/外部结果冲突或未形成外部结果，不回滚同一信封中其他已经合法接受的结果；信封处理完成不等于所有项目都形成监管事实。

## 最小业务提交边界

- 来源响应、来源身份与时间、原始内容引用、重复/更正关系、本产品原提交或外部监管舱单引用的互斥关联、解释规则、分层结果、明确范围、接受判断、凭证定案（如有）、审计和发布意图必须形成可恢复的受保护业务结果。
- 原始来源保全成功但后续解释失败时，恢复必须继续处理同一来源记录，不要求外部系统换消息标识重发，也不创建第二来源事实。
- 分层结果已完整形成但事件首次投递失败时，只重试同一发布意图；不得重新查询、重新解释、在本用例直接形成或解除内部限制，或重复定案凭证。需要限制判断时只向 `UC-CC-011` 提供同一外部事实引用。
- 查询请求、查询尝试、查询技术结果和查询响应分别保留；响应只有重新经过来源接受和解释后才改变业务结果，查询状态快照保存截至时间并去重，不能让查询调用或执行状态直接写申报当前结果。
- 外部结果和由其派生的当前判断分别保存。更正或冲突解决改变当前解释时，原来源和旧判断继续可查。

## 一致性、幂等与并发

- 同一来源身份、消息版本和内容并发到达时，只能形成一份来源记录和一组有效分层结果；其他处理返回已有结果。
- 同一响应被同步调用、异步回调和查询重复返回时，按照真实来源身份及业务语义去重，不能仅按传输方式分别形成三份结果。
- 同一消息身份不同内容必须形成来源响应冲突；不同消息身份内容相同是否为重复，由真实来源的消息版本和重发语义判断，不预设全文相等即重复。
- 关联、解释或凭证定案期间出现新的来源更正时，不提交基于过期输入的当前判断；保留处理尝试并按新来源版本重新解释。
- 并发查询不得产生无界重复请求；相同原提交和同一查询窗口的归并规则由真实渠道参数提供，但任何查询都不得生成新申报。
- 待确认提交同时收到推送与查询响应时，两者作为独立来源投递接受，再按来源身份、业务时间和更正语义形成当前结果，不按线程先后裁决。
- 已依据 A1 形成安全再次发送判断并发起 A2 后，如果 A1 迟到形成可继续有效的外部申报身份，必须使原安全再次发送判断不再有效，关联 A1、A2 及全部外部身份，停止继续尝试和错误释放凭证，并交接重复申报的更正、撤销或其他受控处理；不得选择一份结果覆盖另一份。
- 部分放行、部分查验和部分凭证使用必须逐范围形成；并发结果不能通过整单状态覆盖彼此。
- 响应、查询或结果事件丢失时通过稳定来源和原提交关联恢复，不以人工改状态、无关联重报或删除待确认解决。

## 权限、隔离与审计

- 自动来源接入以来源身份和接入范围校验；人工关联、人工解释复核、冲突处置、查询发起和结果导出使用分别授权的业务权限。
- 人工操作只能形成带证据的关联或解释判断，不能修改原始响应、伪造监管来源、补造缺失结果、解除限制、制造放行或把待确认改成失败。
- 来源响应、提交关联、监管结果、查询、凭证使用和错误结果按集团租户、责任法人、案件、客户账户及明确监管范围隔离。
- 跨客户合报只向有权关务角色展示履责所需完整范围；客户、客服和一般运营视图不得看到其他客户存在、资料、业务量、结果或查询内容。
- 审计至少关联来源身份与角色、消息身份/版本、渠道/账号、原始内容引用、各类时间、认证与完整性、提交版本/尝试、解释规则、结果层、范围、重复/冲突/更正、人工决定、凭证定案、查询和发布结果。
- 日志、指标和错误不得记录不必要的寄收件、货物、凭证、税费、监管原因或跨客户明文；来源未受理和待关联必须保持最小披露。

## 可观测性与非功能验收占位

- 从提交版本与尝试、来源信封、原始响应、关联、解释、分层结果、当前判断、查询、凭证定案到下游交接必须具有稳定关联。
- 分别观测来源保全、去重、关联、映射、分层、冲突判断、结果提交、查询发起/响应、凭证定案和事件投递的耗时与失败位置。
- 分别统计各结果层、待关联、解释未决、原提交结果待确认、安全再次发送条件、重复、来源响应冲突、外部结果冲突、来源信封逐项汇总、未受理和未形成结果；查询执行状态另行统计，不得只统计清关成功率。
- 监控技术成功制造监管接收、业务受理制造放行、高层结果补造低层结果、最近提交猜测关联、未知代码默认成功、最后到达覆盖、查询无记录盲目重报、部分结果整单扩大、跨客户泄露和重复凭证定案等不变量违规。
- 恢复盘点必须区分未通过接入安全校验、已完整保全待处理、待关联、解释未决、结果已形成待发布、原提交结果待确认、各查询执行状态和已交接下游。
- 可用性、来源新鲜度、查询等待/间隔、积压、批处理窗口和恢复目标由真实渠道与 `PAR-NFR-06` 提供，本文件不填写未经证据确认的数值。

## 首发试点约束

- 只处理 `PAR-COM-01`、`PAR-COM-03`、`PAR-COM-05` 和 `PAR-COM-06` 最终登记范围内的真实提交与监管结果。
- 出口和进口分别使用 `PAR-CUS-01`、`PAR-CUS-02` 登记的真实来源角色、外部关联、代码映射、同步/异步语义、查询能力、更正和部分结果范围；不填充默认国家、程序、状态码或监管来源。
- 监管凭证使用定案只采用 `PAR-CUS-04` 已登记的权威结果和规则，不把技术成功、受理或放行预设为通用核销时点。
- 正常申报的技术回执、监管接收或业务受理以及正常放行使用真实生产结果验证；拒收、超时、冲突、乱序、迟到更正、部分查验和部分放行等未自然发生场景使用 `PAR-CUS-05` 允许的历史回放、正式测试环境或隔离模拟。
- 历史回放和隔离模拟不得向生产监管渠道发查询或提交，不形成真实监管结果、凭证使用、节点指令、税费、付款或结算金额。
- 真实来源矩阵和映射未登记前可以实现来源保全、待关联、解释未决、分层骨架、查询接口、幂等和审计，但不能宣称真实监管结果解释已经生产就绪。
- 没有原提交查询能力时必须登记受控人工核对和剩余风险，不能通过自动重报填补能力缺口。

| `AT-CC-162` | 来源身份认证失败、租户不匹配或内容完整性校验失败 | 来源响应未受理，只保留安全审计所需最小证据；不读取候选提交或形成业务事实 |
| `AT-CC-163` | 操作员上传截图或手工录入“海关已放行” | 保存为人工来源证据或待复核输入，不冒充监管来源；无合格来源规则时不能形成放行 |

| `AT-CC-166` | 查询返回“无记录”，但真实渠道未证明原尝试不存在可继续有效的外部申报身份或再次发送不会重复 | 继续`原提交结果仍待确认`；不允许再次发送、不释放凭证占用 |
| `AT-CC-167` | 查询调用失败、超时、渠道不可用或没有查询能力 | 只记录查询能力或执行状态，原提交结果继续待确认；不改成申报失败或未提交 |
| `AT-CC-168` | 查询响应明确返回原提交的监管接收或业务受理，或返回截至某时点的相同状态快照 | 事件按来源规则形成对应分层事实；重复快照只保存观察和当前解释，不重复制造监管事件，查询成功本身不另造申报结果 |
| `AT-CC-169` | 合格来源和真实规则共同证明 A1 未形成可继续有效的外部申报身份，且再次发送同一版本不会造成重复申报 | 形成`原提交安全再次发送条件已确认`并请求 `UC-CC-005` 受控新尝试；本用例不直接发送，也不把 A1 改写为从未发生或据此释放凭证占用 |
| `AT-CC-170` | 原提交仍待确认时，操作员要求换外部标识重新申报 | 拒绝盲目重报并返回原提交查询入口；不创建第二提交或释放原占用 |
| `AT-CC-171` | 分层结果已完整提交，但结果事件首次投递失败 | 原结果保持有效，只重试同一发布意图；不重新解释来源、重复查询或重复触发下游 |
| `AT-CC-172` | 原始来源已保全，但关联或解释处理因技术故障中断 | 返回`未形成外部结果`并从同一来源记录恢复；不要求来源换消息身份重发 |
| `AT-CC-173` | 已接受权威结果和凭证规则共同证明监管凭证的明确额度已经使用成立 | 针对原占用、凭证版本和明确范围形成核销；不覆盖占用历史或扩大额度 |
| `AT-CC-174` | 权威结果证明申报未使用凭证且规则明确允许释放 | 针对原占用形成可追溯释放；不删除占用或把释放写成从未占用 |
| `AT-CC-175` | 只有技术失败、待关联、解释未决、来源响应冲突、外部结果冲突或结果待确认 | 原凭证占用保持，不释放也不核销 |
| `AT-CC-176` | 监管结果只确认部分申报范围使用凭证，或后续权威更正改变既有使用结论且已释放额度被其他提交占用 | 只核销明确使用范围，其余范围按规则保持占用或部分释放；更正形成调整、释放或补充核销，发生额度冲突时保留全部关系、阻止新增占用并交接受控处理，不覆盖后续占用或压缩为一个余额 |
| `AT-CC-177` | 查验、扣留、补充资料或处置决定已经接受并发布下游 | 只证明监管决定和明确范围；不证明节点执行、资料已补、处置完成或关务案件关闭 |
| `AT-CC-178` | 关务案件关闭后收到迟到更正、补税或稽核消息 | 保全并形成合格外部事实；交由 `UC-CC-010` 按原关闭决定、逐项原关闭责任来源和当前授权判断受控重开或建立关联后续案件；不忽略、不覆盖原关闭和历史提交 |
| `AT-CC-179` | 检查本用例产生或修改的业务对象 | 不创建或修改提交版本、提交尝试、正式申报资料、实际付款、节点执行或运输事实，也不直接关闭/重开案件 |
| `AT-CC-180` | A1 被判断可安全再次发送后已经形成 A2，随后 A1 迟到取得监管接收或其他可继续有效的外部申报身份 | 使原安全再次发送判断不再有效，关联 A1/A2 及全部外部身份，停止继续尝试和错误释放凭证，交接重复申报的更正、撤销或其他受控处理；凭证已经释放时形成调整或补充核销，额度又被占用时形成冲突/超用判断并阻止新增占用；不选择一份结果覆盖另一份 |

## 生产参数与待决风险

下列内容不改变来源保全和分层边界，但在真实值提供前阻塞对应生产解释或自动续办：

| 参数或决策 | 当前状态 | 对本用例的影响 |
|---|---|---|
| `PAR-COM-01`、`PAR-COM-03`、`PAR-COM-05`、`PAR-COM-06` | 真实客户、责任法人、服务产品和合同责任待最终登记 | 无法实例化生产隔离、查询和结果披露范围 |
| `PAR-CUS-01`、`PAR-CUS-02` | 出口/进口来源角色、消息身份、外部关联、代码层次、业务时间、部分范围、更正、查询和重试语义待提供 | 可以保全来源，不能宣称生产结果映射、查询或重试判断成立 |
| `PAR-CUS-03` | 人工关联、解释复核、冲突处置、查询和导出权限待提供 | 无法开放生产人工处理或证明最小权限 |
| `PAR-CUS-04` | 规则、凭证使用成立/未使用的权威结果、部分核销、释放及更正规则待提供 | 不能生产形成凭证释放或核销 |
| `PAR-CUS-05` | 重复、冲突、乱序、迟到更正、部分结果、关闭后消息和查询恢复环境待提供 | 无法验证复杂分支、重开交接和防覆盖控制 |
| `PAR-CUS-06` | 关闭后事实分类、原关闭责任来源、重开和后续案件权限待提供 | 可以保全迟到事实并交给 `UC-CC-010`，不能形成生产重开或后续建案决定 |
| 来源权威矩阵 | 各渠道、服务方和监管来源分别能证明哪些结果层待确认 | 无法把中介响应升级为监管事实 |
| 结果代码映射 | 代码版本、适用程序、层次、范围、成功/失败/拒收语义及更正关系待确认 | 未知代码只能保持解释未决 |
| 原提交查询规则 | 触发条件、等待窗口、查询标识、查询事件/状态快照语义、来源序列、快照截至时间、无记录语义、频率、停止与人工升级规则待确认 | 不得预设轮询周期、把快照制造成重复事件或把无记录当未提交 |
| 同层冲突裁决 | 来源优先、序列、更正、人工复核、冲突前当前有效判断和依赖动作门禁规则待确认 | 冲突保持，不允许最后写入覆盖；门禁规则未登记时不得自行阻断或放行依赖动作 |
| 部分与附条件结果 | 真实程序允许的范围粒度、条件结构和门禁作用待确认 | 只能实现范围中立模型，不能写死包裹/申报行粒度 |
| 迟到结果续办 | `UC-CC-010` 已形成稳定流程，真实原案重开、后续案件和既有事实保护的权限参数待确认 | 可以保全事实并进入待分类，不能自动重开或建后续案件 |
| `PAR-NFR-06` | 来源新鲜度、查询等待/间隔、积压、批处理和恢复目标待提供 | 无法确定生产查询节奏和性能验收门槛 |

不得以行业常见状态码、报关服务方页面文案、HTTP 成功、消息到达顺序或操作员经验替代真实来源权威和程序映射。当前稳定实现策略是：来源先保全、关联可追溯、未知保持未决、冲突不覆盖、结果逐层逐范围形成。

## 开发拆分建议

真实参数未齐备前，可以按以下顺序实现：

1. 渠道中立的来源信封、不可覆盖原始响应和来源身份/时间/完整性保全。
2. 来源去重、同身份冲突、更正版本、稳定原提交关联和待关联处理。
3. 版本化来源权威矩阵与结果代码解释接口，未知参数显式进入解释未决。
4. 技术回执、监管接收、业务受理、过程决定、税费、放行和处置的独立结果模型与范围模型。
5. 迟到、乱序、同层冲突、更正和当前解释派生，不按最后到达覆盖。
6. 原提交查询、查询事件/快照响应重新接入、结果仍待确认和安全再次发送条件的受控交接，以及原尝试迟到生效后的重复申报防护。
7. 监管凭证保持、释放、核销和部分定案接口，未确认规则不产生默认结果。
8. 批量逐项处理、跨客户最小披露、权限、审计、事件发布和故障恢复。
9. 与后续更正/补充/撤销重报、查验/处置、税费和案件闭环用例的结果交接；不在本用例执行下游动作。
10. `AT-CC-140` 至 `AT-CC-180` 的应用、领域、接入和恢复测试骨架；真实来源、代码、查询、凭证及非功能参数使用显式未配置状态。

完成本用例只闭合外部来源到分层关务事实的可信转换，以及本产品原提交的查询；承运商外部监管舱单只通过 `UC-CC-012` 提供引用和关系，本用例不得代表承运商查询或再次发送。已接受的补充资料、更正、撤销重报或重复申报处理要求交给 [UC-CC-007：管理申报后续动作与替代关系](./UC-CC-007-MANAGE-POST-SUBMISSION-ACTIONS-AND-REPLACEMENT.md)，由其形成后续动作目标和替代关系；查验、扣留与处置决定交给 [UC-CC-008：协作查验扣留并核对监管处置执行](./UC-CC-008-COORDINATE-INSPECTION-DETENTION-AND-RECONCILE-DISPOSITION.md)，税费与案件闭环继续按各自责任边界展开。
