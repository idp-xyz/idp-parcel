# 产品自身收费模型

状态：形态结论，非已确认参数。本文回答**开发方把 `idp-parcel` 卖给物流企业时按什么计量收钱**，只写计量形态与口径，不写任何价位。

它服务的是[产品就绪](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#产品就绪与试点就绪)定义里「可以进入商务洽谈」那一半——洽谈的第一个问题是「怎么收费」，在本文之前本仓对此零口径。卖给谁、解决什么痛以[产品故事](./PRODUCT-STORY.md)为准，客户群分层以[开发主线的「目标客户群」](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#目标客户群)为准，本文只引用不复制。

## 它与结算上下文是两件事

[结算与经营核算上下文](../domain/settlement-accounting/CONTEXT.md)管的是**租户对它自己的货主客户与供应商**的钱：客户费用、供应商预期成本、账单匹配、对账单、核销。本文管的是**开发方对租户**的钱。两者之间隔着两级——开发方卖软件给租户，租户经营网络服务它的客户。

因此软件订阅费、调用费与任何平台费**不是包裹业务事实，不进那本账**：它们不由委托产生、不随履约推进、不参与客户对账单的截单快照，也不形成运营应收。反过来，租户付给开发方的钱在租户自己的财务系统里是一笔采购成本，那是租户的账，本产品不拥有它。

把两者混在一起的具体代价是所有权错位：租户的应收账本会长出一列所有权在开发方这边的「平台费」，而那本账的每一条都受租户的客户合同与结算政策版本约束——平台费不受任何一份客户合同约束，放进去只能靠例外条款躲开不变量。

## 收费层

结构借自[产品战略与产品蓝图 V1.0（参考）](../reference/IDP_Parcel_Product_Strategy_Blueprint_V1.0.md)第 10 章「商业模式与单位经济模型」的多层收费模型表，**只借结构不借数字**。原表的 EER / Agent 一层不收进来：[产品故事](./PRODUCT-STORY.md)的 AI 路线立场是不预建 AI 机制，没有可卖的执行实例或 Agent 席位，登记一层卖不出去的东西只会让洽谈时答不上来。蓝图非本仓权威，其余章节不因本文被采纳。

「主要面向」一列指的是[开发主线「目标客户群」](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#目标客户群)的三层，那里是唯一权威。

| 收费层 | 计量单位 | 主要面向 | 价值逻辑 | 依据强度 |
|---|---|---|---|---|
| 平台订阅 | 租户、场站、席位，按周期 | 三层都适用，是其余各层的底座 | 付的是「有这套系统可用」本身 | 竞品公开事实已核实（台账 `S2`，2026-09-02）；分档口径属行业形态，无一手合同 |
| 交易计量 | 委托、包裹、面单交易、履约执行 | 三层都适用 | 随租户业务规模增长 | 竞品公开事实已核实（台账 `S2`、`S13`，2026-09-02） |
| API 用量 | 取价、轨迹查询、地址与资格校验等调用 | 要把能力嵌进自有系统的租户，各层都可能 | 基础设施计量 | 竞品公开事实（台账 `S2` 与 `S10` 为`已核实`；`S7` 行状态`部分未核`，所引为其行内标注已核实的计量口径，2026-09-02） |
| 物流产品费 | 服务产品版本数、渠道数、网络定义与规则包数 | 物流产品设计者与整合者 | 产品管理复杂度 | 本仓推断，无外部已核实证据 |
| 优化收益 | 择优节省额、毛利改善 | 有规模的租户 | 直接绑定经营结果 | 本仓推断，无外部已核实证据；另见下文的基准问题 |
| 企业合同 | 年度合同 | 大型物流集团与平台型租户 | SLA、私有化部署、治理与合规 | 竞品公开事实已核实（台账 `S2` 的定制档，2026-09-02） |

各层可叠加，本文不预设组合，也不预设哪一层是主收入。**采用哪几层是商业决定，不是本文的结论**；本文只保证每一层的计量口径说得清、与本仓已有事实对得上。

## 各层的计量事实今天在哪里

采用某一层的前提是这个系统数得出它要的量。逐层如实记：

- **平台订阅与企业合同不需要产品内计量。** 租户数与合同期在商务侧，产品不必参与。
- **交易计量有事实基础。** 每个包裹有本系统拥有的永久内部标识且不因换单、改号或渠道变化而更换（[产品基线](./PRODUCT-BASELINE.md)），面单交易是独立聚合、交易级与包裹级结果分开判断（[ADR-0084](../adr/0084-label-transaction-is-an-independent-aggregate-with-two-level-results.md)）。「本期成立了多少笔」因此数得准，且不会因重打、作废或替换被重复计。
- **API 用量的事实不存在。** 业务 HTTP 接入面已按 [ADR-0055](../adr/0055-business-endpoint-intake-has-an-unconfigured-grade.md) 带「未配置即拒」的 Intake 进装配，但没有任何按租户、按端点、按成败的调用计量。选这一层要先决定计不计失败调用——外部参照里有「只计成功调用」的做法（见下文），而「未配置即拒」这一格算不算一次失败调用，是本产品特有的问题。
- **物流产品费的事实基础在版本化登记册。** 服务产品、客户合同、供应商协议、价卡与网络目录全部按不可覆盖版本受控发布，「租户登记了多少个产品、多少条渠道」可数。但要小心数的是什么：不可覆盖版本意味着改一次产品就多一个版本，按版本数计费会把「维护得勤」变成罚款。
- **优化收益的形状具备，量不具备。** `network-routing` 对同一票逐候选形成 `BUY` 评价后按成本单维择优（首发只按成本单维，`PAR-NET-16`），「本可以走哪条、实际走了哪条」这两侧都在评价与择优记录里。差额本身不是本产品记录的量，而且**这一层最容易起争议**：节省额要有双方认可的基准，而基准只能来自租户接入本产品之前的历史成本，那份数据在租户手里、不在本产品里。没有基准就没有分成。

**交易计量、API 用量、物流产品费与优化收益这四层都要计量，而它们各自的计量记录形态今天一个都不存在。** 这不是缺陷——本产品从来没有把「向租户计费」当作自己的领域。它的意思是：任何一层一旦选定，都要按[能力范围判据](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#能力范围判据)单独立票走一遍，而不是顺手加个计数器。计量记录一旦要长期留存、要对账、要争议时可回放，它就是一个有自己不变量的东西，不是一列整数。

## 不建议依赖的收入

- **不把运费价差当作收入形态。** 蓝图把这条列为不建议时给的理由是需要规模采购、信用资金与承运商关系；本仓的理由在它之前且更硬——**开发方不是运营企业**（[开发主线](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#产品就绪与试点就绪)）。价差是租户经营网络挣到的钱，开发方要挣它就得自己持有采购关系与承运商合同，那是换一个生意做，并使[产品基线](./PRODUCT-BASELINE.md)「本产品是具有独立产品责任的软件产品」这条定位失效。
- **不只按账号或席位收费。** 与物流业务价值脱节：本产品的价值随委托量与产品复杂度增长，按席位收不但不随之增长，还会促使租户压席位数——把系统用得更少变成省钱的办法，这与产品要证明的东西正相反。
- **不只卖 Agent 席位。** 与[产品故事](./PRODUCT-STORY.md)的 AI 路线立场同向：本产品不预建 AI 机制，登记册、评价回放与执行记录才是将来 Agent 消费的接口。先卖席位等于先收一笔本产品今天不提供的东西的钱。

## 外部形态参照

引用规则按[竞品公开事实台账](./COMPETITOR-FACT-LEDGER.md)：只引已核实的事实，连核对日期与核对状态一起引；行状态为`部分未核`时只引该行内明确标注已核实的那部分，并把行状态一并写出，免得读的人以为整行都核过。台账全文明写**不得作为本产品定价或成本假设的依据**；本节引它只为说明「按什么计量」在市场上有哪些已在用的形态，不取任何数。

- **计量点可以只落在产生外部成本或不可逆动作的那一次调用上。** Easyship 的 MCP Server 随任何账号免费，取价、列单、追踪与分析调用不消耗额度，只有购买面单或预订取件才消耗（台账 `S13`，`已核实`，核对日期 2026-09-02）。
- **读类调用也可以逐次计量。** Shippo 把与面单无关的调用（轨迹、取价、地址验证）按另一套 API 价目单独计量（台账 `S2`，`已核实`，2026-09-02）。它与上一条相反，两条并存说明读类调用计不计费**不是行业定论，是形态选择**——这也正是本文把它留作未决而不给建议的原因。
- **含额加超额、超额不中断服务、只计成功调用。** Easyship 的高级 API 端点按用量计费，付费档为含额加超额，超出含额不中断服务而只按次收超额（台账 `S10`，`已核实`，2026-09-02）；「端点逐个计量」与「只计成功调用」出自 `S7` 行内标注已核实的部分，该行整体为`部分未核`，未核的是各档订阅月费（2026-09-02）。「只计成功」这一条对本产品尤其有用：它把「未配置即拒」这类诚实拒绝天然排除在计量之外。
- **客户自带承运商账号时平台仍按面单收费，这一形态存在。** 台账「核完之后」一节写明 LYOC 形态存在已核实、**具体费率本仓未核**：形态出自 `S7` 行内的套餐矩阵行（该行整体`部分未核`），费率所在的 `S9` 为`未取到`（2026-09-02）。引这条只能引形态，不能引费率。

**两条明确不引**：Shippo 的轨迹与地址验证单价（台账 `S1`，`部分未核`，2026-09-02）与 Easyship 的各档订阅月费（台账 `S7`，`部分未核`，2026-09-02）。台账写明`未取到`与`部分未核`不得被引用为已核实，这两条属此列。

## 不写价位

**本文全文不含任何具体价位，也不含比例、折扣档、含额数字或超额单价，哪怕标成「示例」。**

理由与[能力范围判据](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#能力范围判据)那条硬边界同源：形态决定支持什么结构，实例值永远等真实合同。标成「示例」的数字尤其危险——它会被当成起谈锚点带进第一次洽谈，而它的来源只是写文档那天的手感。

第一个真实租户的报价由商务与该租户谈定，落进那次交易的合同，**不回写本文**。本文永远只有形态。

## 本文的登记纪律

**本文不进[参数登记册](./PILOT-PARAMETER-REGISTER.md)。** 登记册只登真实实例；本文是形态结论，性质同[开发主线「产品需求假设」](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#产品需求假设)一节的条目，纪律沿用那里：按依据强度标注，第一个真实客户到来时必须复核。那一节是该纪律的唯一权威，本文不复述其内容。

复核触发四项，任一成立即须重走一遍上面的依据强度列：

- 第一个真实租户的商务洽谈开始——届时全部依据强度都要复核，「本仓推断」两层尤其要拿真实反馈换掉。
- [目标客户群](./PARCEL-NETWORK-FIRST-RELEASE-DEVELOPMENT-BASELINE.md#目标客户群)的分层变化——「主要面向」一列随之失效。
- 台账某条的状态或核对日期变化——本文引它的那句连带复核。台账自记「超过一个季度未重核的条目视为过期」，本文的引用不比被引条目更新鲜。
- 决定采用某一层——该层的计量记录形态按能力范围判据单独立票，届时本文该层由「候选形态」改记为「已采用」。
