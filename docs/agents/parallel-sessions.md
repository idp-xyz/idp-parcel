# 多个会话共写一棵工作树

几个 agent 会话同时开在**同一个工作目录**上时的做法。单人单会话不必读本文。

下面每一条都来自 2026-08-11 那天的实际事故，不是设想。写下反面教材是有意的：只写成功经验的方法论，下一个人复现不出来。

## 先分地盘，这一步只有人能做

**一个目录一个写入方，开工时就说清。** 那天四个通道共写一棵树，全天无人**覆盖**别人的工作——共享工作树能活下来靠的是这一条，不是锁。

注意措辞：不是「无人写进别人的文件」。索引类文件被两个会话各写过一次，那是下面单说的第三类。

地盘无法从代码里推出来，也没法靠 agent 之间协商可靠地形成：每个会话只看得见自己的任务。**必须由人在开工时分派。** 分完之后，越界前先在频道里说一声，对方让位再动。

### 释号要和占号一样显式，尤其是占回自己释过的那张

2026-09-02 晚的一次重复工，**两边全程都按纪律在频道里说了话，而纪律没拦住它**。

经过：一个会话广播「本轮我不做这张票，谁拿都行」；人随后把「没人管的」那批派给另一个会话，
后者广播认领并开工；几分钟后，第一个会话广播占号同一张票。后者让位（票面取证是前者写的，
争比让贵），但那几分钟的活白做了。

现有的占号纪律只覆盖两个动作——**占住**与**释号**，没覆盖**释号之后重新占住**。而后者恰恰
最容易发生：让出去的那一刻你对它没有计划，几分钟后计划变了，重新拿起来在自己看来根本不是
一次「占号」，只是「继续做本来就是我的活」。**对方看到的却是一次撞车。**

两条，都便宜：

- **释号与占号同样显式**：「我释出 X，谁拿都行」而不是顺带一句「我本轮不做 X」。含糊的让出
  会让人拿不准该不该接，于是要么没人接、要么接了心里没底。
- **占回一张自己释过的票之前先问一声「这张有人拿了吗」**，别直接广播占号。你释出到你想拿回
  之间那段时间里发生了什么，你这一侧看不见。

这与本文反复出现的那个形状同族：**你手上的状态是过期的，而它长得不像过期的**——「我释出的
票」读起来像是仍然无主，正如 `origin/main` 读起来像是远端。

**同一个漏法还有第二个面：开窗通知发出之后发现做不了。** 上面「会让旧调用点对不上」那条要求
动手前在频道报一声「接下来几分钟全仓可能编不过」，**却没说报完之后放弃了该怎么办**。

2026-09-02 晚有一次正例：一个会话报了窗口，开工前把调用点核完发现范围比估的大、本轮余量
不足以一次做完再验完，于是**收回通知**——「窗口没开，我一行没改，要跑全仓构建的直接跑」。
它值得写下来是因为不收回的代价很实：**别人会为一个永远不会到来的窗口挂起自己的构建，而那个
等待从外部看与「他正在改」完全同形**——又是本文那个形状。

所以：**开窗通知与完工报成对，做不成也要报一声「窗没开」。** 与上面释号那条同构——占号纪律
只覆盖了「占住」与「释号」，漏掉「占了又没做」；开窗纪律只覆盖了「要开」与「已完工」，
漏掉「说了要开但没开」。**两处漏的是同一格：状态回退没有出声的义务，而只有出声的那些状态
才是别人看得见的。**

**第三个面：在共享树上做 TDD 的 red 中间态，同样要开窗。** 上面「会让旧调用点对不上」那条
写的是签名变更，而一个引了还不存在的符号的测试文件照样让全仓 `go vet` / `go test` 变红。

**它比签名变更更需要报，理由不是它更红而是它更没道理可循。** 签名变更的红有解释——谁都知道
改一个导出签名会拆掉调用点，别人看到就能猜出发生了什么、去问谁；而一条
`undefined: SomeSpec` 出现在一个陌生包的未跟踪测试文件里，在别人眼里是一条**来历不明的
全仓红**，唯一的处置只能是停下来查。2026-09-02 晚实际发生过一次：一个会话把 TF 的 red
中间态留在共享树上没说，另外两个会话各自撞上并去查了归属。

顺带一条：**红着的那段时间也别只想着快，想想要不要干脆去隔离 worktree 做。** 上面那次事后
复盘的结论是「本该走 worktree」——TDD 的 red 到 green 之间可以是几分钟也可以是半小时，而它
在共享树上的可见性与半小时的签名改动没有区别。

会话数量本身要克制。那天十一个通道里只有两个在写，另外几个空转，而**空转的只读会话会互相仲裁**——同一件事套了四层，没有一层该发。

### 派号不是占号；而占号广播拦不拦得住人，取决于收的人什么时候读

2026-09-03 的一次撞号，**两边都按纪律办了，还是撞了**——这一次没有任何一方可以靠多广播一句
来避免它，所以它不归上面那条「说清楚」的处方管。

经过（钉在 `a01cee4`，仅作此刻取证）：会话 A 问会话 C「你的收口还会碰 `cmd/parcel-api/` 吗，
不碰我就占这张票开工」，C 答「不碰，你占」，还附了三条接线细节。A 查 `git status`，
`cmd/parcel-api/` 干净，于是开始读上下文。约五分钟后 A 写下第一片 red（端点表里一行探针）
跑测试，编译器报的却是 `duplicate key`——同一张票的整笔后端接线已被会话 B 写进同五个文件，
mtime 距查看 25–70 秒。而 B 的占号广播完整、地盘逐字列清，就在 A 那条撞号广播的**上一条**。

两格，分开记，因为处方落在不同的人身上。

**一、派号不是占号。** C 能回答的只有「我不碰 `cmd/`」，那句话完全属实；读成「那就没人碰」
是 A 自己加的一步。**能让号的只有正占着的那个人，而 C 从来没占过它。** 指派活的人不拥有那张
票时，它给出的是一条关于它自己的事实，不是一次分配。

**二、占号广播能不能拦住人，取决于收的人什么时候读，不取决于发的人多及时。** A 读上下文、
写第一片 red 的那五分钟里，B 的占号就躺在 A 的队列里，**而 A 的下一次收信要等这一轮干完才
发生**。发的一侧已经没有改进余量：B 广播了，内容完整，时机也不晚。

因此这一格的处方两条都落在收的一侧：

- **开工前排一次队列。** 拿到任务与真正落笔之间隔着读上下文的那几分钟，那几分钟恰好是别人
  占号的窗口。
- **落笔前再排一次**，尤其是共享接线文件。这与上面「这一查要贴着 `push` 跑，不是贴着
  `commit` 跑」是同一个形状：**窗口在你查与你写之间。**

还有一句是关于事后怎么讲这件事的。A 在撞号广播里写的是「真正占住它的人从未在频道里出声」
——**那句是假的**，B 出过声。A 把「我没看见」写成了「没人说过」，而两者要人做的事正相反：
前者要收的人排队列，后者要发的人多广播，而照后者改一条纪律，一行也拦不住这一次。是旁听的
会话当场把原文贴回来才更正的。这是本文「写证据不写结论」在人身上的那一面——**「没人说过」
是个结论，「我的队列里当时没有」才是证据**，而后者当场查得了。

### 派发前先点名，只派给窗口内答了的通道

来自 2026-09-04 上午。全部会话 11:42 重启过一次，之后一小时内频道里出现的，是几个会话各自按
**重启前**的名单在说话：一条占号广播把「MCP-3 在途的 `mechanism-executor-triage/03`」列为不碰
项，而 MCP-3 那一侧此刻是一个刚起来、没有任何在途记忆的新会话；另一条广播问共享树上两块未提交
词条「是谁的请认领」，而写下它们的那个会话前一晚 20:29 就已经结束（会话存档可查）。两条广播
各自都对——它们写的都是重启前为真的事。**过期的不是某一条消息，是每个人手里那份「谁还在、
各拿着什么」的名单。**

派任务是按这份名单做的决定，所以派之前重取一次，不拿上一轮的。

**先看工具已经给了什么，别重造。** `check_messages` 的工具说明写着它在等待期间持续写每通道的
`heartbeat.json`；`dispatch_task` 不传 `toChannel` 时「自动选一个在线空闲通道」（原话，怎么判
「在线」它没说）；`broadcast({ activeOnly: true })` 只发给近期有活动的通道。**但「活跃」不含
正在干活的通道**：12:05 实测，MCP-2 11:55 刚广播过一整段占号，`activeOnly` 仍匹配到零个通道。
正在干活与已经关掉，在它眼里长同一张脸——又是「不同的『绿』」那一节的形状。所以工具答得出的
是「此刻空闲且在线」，答不出的是这个通道占着哪块地盘、余量还够不够、手上那张票和要派的会不会
撞。点名只为这几件设计，不为「活没活」。

做法：

1. `list_sessions` 看有哪些通道。
2. `broadcast({ message: "[点名 ← 通道 M · 截止 HH:MM] 要派 <票号>，空闲的报状态" })`，截止给
   2–3 分钟。`activeOnly` 别开——它会漏掉忙着的通道，而你恰恰要知道谁在忙。
3. 只对**截止前**送到的 `[应答]` 派 `dispatch_task({ toChannel })`；派之前把应答里的地盘与要派
   的票对一遍。
4. 未应答的记「截至 HH:MM 未应答」，不记「已死」——正在干活的通道要到本轮结束才读到点名，
   窗口内不答是它的正常形态。截止后到的应答不算认领，名单在截止那一刻定死。

派发记录带时刻：「HH:MM 点名，N 个应答，派给通道 X」。它只作此刻取证，下一轮重点。

**派之前还要查一样点名答不出的东西：这张票的地盘上，分支里有没有人做过一半。** 来自 2026-09-07
晚：pc-gaps/09 在 19:4x 从通道 5 改派给通道 6，改派消息到得比对方开工晚，通道 5 在 20:18 把自己那份
09（ADR-0119 + 迁移 0026）提交到了 `mcp5-pcgaps08` 上；通道 6 的版本 21:5x 进 main，通道 5 那两笔成了
同号不同名同题的孤儿，约一小时白做。点名答的是「谁空闲」，答不出「哪条分支上已经躺着这张票的半成品」
——新会话没有在途记忆，它自己也不知道。所以派单第 0 步是推送方查分支，不是让接收方查：

```powershell
# 在途分支、各树未提交、这块地盘上 main 尚无的提交，一页算出来（脚本只读；前缀约定见「拆工作树」一节）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/branch-state.ps1 -Path <地盘目录>
```

查到半成品，派单里要写明是「从 `<分支>@<SHA>` 接着做」还是「不看它、另起」，两者都算答案，不写才是错——
不写的结果就是两个人各做一版。同一脚本不带 `-Path` 就是会话开工第一眼该看的状态页：main 与 origin 是否一致、
哪几棵树有未提交、哪些分支在途且推没推 origin。它算的是 git，不是谁的记忆。

接收方那半（收到 `[点名]` 必须立刻按固定格式应答）写在 `.cursor/rules/idp-mcp-messenger.mdc`——
它 `alwaysApply`，每个会话都加载，应答纪律只有放在那里才轮得到每个通道。

### 第三类：索引文件不属任何人

`docs/adr/README.md`、`AGENTS.md` 这类索引与登记文件既不是你的地盘也不是别人的，却**每新增一份 ADR 或权威文档就必然要碰一次**——可预测、高频，而且不算越界。那天两个会话在同一个 hunk 的连续两行上各加了一条 ADR 目录项。

它们靠的不是地盘划分，是另一套做法：**先在频道说一声、只改自己那一行、不动邻行**。冲突真出现时也别自己合并——问那一行的作者。

一个连带后果要接受：**你的东西可能先落地、它的索引条目后落地。** 那天 ADR-0026 的目录项卡在别人正在改的 README 里，只能在提交信息里写明「索引随该文件另行提交」，等对方带走。这比替他提交一份写到一半的文件好。

### 盲覆盖：报告防不住它

「不动邻行」不只对索引文件成立，任何被两个会话先后各追加过一次的同一处都算。那天 ADR-0027 的 Status 行就是：一个会话先补了一条坐标告警，另一个会话随后改同一行，匹配串写得太短、跨过了那句告警，一次「成功」的替换把它吞掉，同时把告警写成了两遍。

**它不是并发编辑，报告拦不住。** 两次写入先后发生，各自都合法，第二个人也确实在频道里说过。冲突提示不会出现——工具视角里根本没有冲突，它只是照给定的匹配串替换了一段，而那段里混着别人的字。

做法是把匹配串锚在**你自己写下的字**上，改完立刻重读那一段确认邻居还在。那天是作者自己复核时发现并修回的，没有任何机制在守；下一次没人复核，那句话就没了，而且不会有任何东西变红。

## 工作树也会被阻断，而它不按文件所有权发生

上面三类（地盘、索引文件、共享接线文件）分的都是**文件归谁**。这一类按文件所有权看完全合规，却照样把所有人阻住。

来自一次跨文件签名改动：`ports.go` 上的 `LoadRecordedJudgments` 加了一个租户参数，八个调用点分几次跟上。**在头一次编辑与最后一个调用点之间，整棵共享树对所有人都编不过。**改动方的构建循环里那只是个中间态，在别人那里是一次原因不明的全仓红——那天另一个会话记下的是「`go build` 全仓不过，但断在 `parcelshipment`」，它得先分辨那是不是自己的错。**没有一行被提交，也没有碰任何人的文件。**

**全仓验证协议把它放大了。**推之前跑 `go test -count=1 ./...` 意味着每个人的验证都依赖其他所有人此刻的树状态；只跑自己那几个包时碰不到这一类。

**判据在改动类型上，不在文件名上。** 危险的是「会让旧调用点对不上」的那一类：拓宽或改名导出符号、给接口增删方法、改结构体字段。按文件认反而认不准——同一个 `ports.go` 上的纯注释改动一点风险没有，而给某个 domain 结构体加一个字段照样能让别处编不过。上面那次的文件恰好是 `ports.go`，那是巧合不是特征。

这类改动有两条路，各有代价，按调用点数量与是否跨地盘选：

- **三步法（expand / migrate / contract）**：先加一个新名字的方法或新接口带新签名、旧的不动，再逐个调用点迁移，最后删旧的。**任何一刻停下来都编得过**，代价是三倍改动量与一个中间态的重名。调用点多、或跨了别人的地盘时值这个价——那种场合你本来也没法一口气改完。
- **单独 worktree 改完验绿再一次性应用**：改动量不变，窗口从几分钟压到几秒。调用点少且全在自己地盘时更划算。

两条路都要在**开工前于频道说一声**「我要改 X 的签名，接下来几分钟全仓可能编不过」。上面那次没说，代价就是别人替你排查。

碰到不在自己地盘的编译错：**不要去修**（见「报什么，不报什么」），也**不要当成自己验证失败**。按 SHA 在临时 worktree 里验证天然免疫于这一类——它检出的是提交，不含任何人的未提交改动。这是「推经验证的确切 SHA」那一节的第二个理由。

## 提交：精确暂存，且推之前验提交状态

一条总的判据：**以整棵树为输入的操作，在共享树上都是错的。** 它的输入包含别人写到一半的部分，产出因此没人要。下面两条都是它的实例。

**逐文件 `git add`，绝不 `git add -A`。** 树上同时躺着别人写到一半的东西，一次全量暂存就是替他提交未完成的工作。

### 但逐文件 `add` 守不住：索引也是共享的

上面那条默认了**索引是你一个人的**。共享工作树上不成立，而这一格 2026-09-02 晚被两个会话从两侧各撞一次。

一次出了事：一个会话全程只 `git add` 自己的路径、一次 `-A` 都没跑，提交出来却多带了另一个会话九个文件、1271 行在途代码。另一次没出事，但**没出事的原因不是写法守得住**——那个会话同一晚两笔用的是同一个不安全写法（逐文件 `add` 后不带 pathspec 的 `commit`），只因每次都顺手把暂存集打印出来看了一眼才干净，而他因此根本不知道自己一直站在那个暴露面上。

> **`git commit` 提的是整个索引，不是「你刚刚 add 的那几个」。**

别人为自己那笔做好暂存之后，那些文件就躺在索引里等着；谁先 commit，谁就把它们一起带走。

处方两条，**但它们不同级，别并列记**：

- **纪律（第一级，做进结构）：提交带 pathspec。**

  ```powershell
  git commit -F <msg> -- .scratch/你的目录/ internal/你的包/
  ```

  `--` 后面给路径时 git 只提这些路径，**不管索引里此刻还摆着谁的东西**。代价是把路径再写一遍。

- **诊断（第二级，退让不是等价物）：`git diff --cached --name-only`。** 它用来查「此刻索引里摆着谁的东西」，不能当防线——**你查与你 commit 之间，别人还能再放一批进去**。这与本文「提交竞态」、与「贴着 `push` 跑而不是贴着 `commit` 跑」是同一个形状，写下来是因为它在本文里已经出现第三次了。并列写会让下一个人以为二选一，而便宜的那个正是守不住的那个。

还有一格只有诊断守得住，pathspec 不管用：**同一个文件里混了两个人的改**。给了路径也照样把那个文件的当前全部内容提走。它归上面「共享接线文件」那条的处方——`git add` 前 `git diff HEAD -- <file>` 逐块核，有外来 hunk 就停：要么等对方提交，要么把暂存内容做成「HEAD ＋只有自己的块」。后者用 plumbing 几行就够：

```powershell
cmd /c "git show HEAD:<file> > %TEMP%\base.txt"   # 取 HEAD 版，避开 PowerShell 重定向的编码坑
# 在 base.txt 上只打自己的改动，然后：
$blob = git hash-object -w "$env:TEMP\base.txt"
git update-index --cacheinfo "100644,$blob,<file>"
```

它不碰工作树，因此对方的在途改动原样留着等他自己提。

再加一道，来自同一晚的另一次实拦：**提交前确认 `HEAD` 没在你暂存期间往前走。** 它当场拦下过一次真错——主干被推进一笔之后，差一步就提交一份对不上新代码的清点报告。

### 数一份共享文件里的条目，要连「在哪数的」一起记

同一晚还撞出一种本文与被数的那份文件都没记过的失效，形状与上面同源。

`internal/architecture/production_wiring_baseline.txt` 的头部是一段流水账，逐次记「剪后重数实测 N」，并再三叮嘱下一个改名单的人重数而不要拿上一个数加减——它自己已经为「只改名单没改那句」栽过两次。**而重数这条纪律本身还漏一格**：那句话默认**树上只有一个版本的名单**。

实测：一个会话剪掉一条后在共享树上重数得 32 并写进了流水账，`git add` 后逐块核才发现**那个 32 记的不是自己那一剪**——它量的树里同时压着另一个会话未提交的另一剪。该笔单独作用于父提交是 33。**两个数都不假，量的不是同一个东西。**

所以：**记数时把「在哪量的」一起记**（「本笔单独作用于其父提交后实测 N」而不是裸写「现为 N」）。要一个能给下一个人用的数，只有一处量得准——**在干净检出上量**，那里不含任何人的在途改动。

**而「在干净检出上量」还不够，要连那个 SHA 一起记。** 同一晚同一份文件的数过期了三次，三次成因各不相同：一次是共享树 vs 干净检出、一次是压着别人未提交的改、**第三次是纯粹的时间**——一个会话在自己那笔上量得的真值被写成「重数时基准是 34」发出去，读到时另外两笔各剪了一条，已经是 32。**干净检出本身每几分钟就是一个新的。**

第三次那个尤其要看清：**没有人量错**。它是在自己那笔上量的真值，坏在被写成了一句**给下一个人用的基准**，而那类句子在多会话节奏下的保质期以分钟计。这与本文「断言有保质期」那节是同一条，只是这里的载体是个数字，而数字读起来比句子更像事实。

两条落地做法：

- **报数一律带 SHA**（「钉在 `<sha>` 上量得 N」），并写明它只作此刻的取证、不作别人的基准。
- **要用一个数时自己重取**，别拿别人报的。`git show <sha>:<path>` 取内容再数，不走 PowerShell 管道（中文按 GBK 解会把多行并成少行，见 [workflow.md 的本机环境](./workflow.md#本机环境)）；验暂存内容用 `git diff --cached --numstat`，**别用带 `^` 锚的 `Select-String`**——同一个编码坑会让锚失配、命中为零，而那个失效方向恰好是「看起来没生效」，人会因此去重做一遍或换回不安全的写法。

这与本文「断言有保质期」那节同族，但它更阴：那节讲的断言过期之后至少还指向一个曾经为真的时刻，**而这个数从来没有对应过任何一笔改动**，它是几个人的在途改动叠加出来的一个谁都不拥有的中间态。

**全仓派生态命令不得单方面跑。** `go mod tidy`、全树格式化、codegen——凡是「扫当前树再写回去」的工具都算。那天依赖还是 `// indirect` 时，任何人跑一次 `tidy` 都会静默删掉它，只能专门广播一次禁令；另一个会话跑 `gofmt -w internal` 时也扫进了别人的目录。

这与「改了公共东西要报」不是一回事：那一条是**要报**，这一条是**根本不能自己跑**。真需要跑，先约定谁跑、什么时候跑。

**推之前另在临时 worktree 里检出提交状态跑一遍。** 这一条比上一条更容易被跳过，而它防的是一类看不见的失败：

> 你本地跑的是**含别人未提交改动**的树，而你的提交里装的是别人**已提交的旧版本**。本地全绿证明不了提交状态能编译。

尤其当你的新代码建在别人正在改的类型上时。做法：

```powershell
# 先 commit，再验；此处的 HEAD 就是你刚做完、即将推的那个提交。
git worktree add --detach "$env:TEMP\verify" HEAD
# 在 $env:TEMP\verify 里跑 gofmt / go build / go vet / go test
git worktree remove "$env:TEMP\verify"   # 不加 --force，理由见下「拆工作树」
```

顺序不能反：提交前跑这段，验的是**上一个**提交，一样给绿，而且绿得毫无意义。

它不碰共享工作树，因此不打扰任何人。那天两次推送前都这么验过，第二次尤其必要。

**提交信息里写清你**没有**带走什么。** 那天 ADR-0026 的索引条目卡在别人正在改的 `docs/adr/README.md` 里，无法一并提交；提交信息写明了这一点，才不至于日后被当成漏登。

### 推送：推经验证的确切 SHA

上一条的做法在多人共树下漏了一格，来自 2026-08-14 的一次实际推送。那段配方里写着「此处的 `HEAD` 就是你刚做完、即将推的那个提交」——**这句话默认只有你一个人在提交**。共享树上不成立：`HEAD` 会在你验完到推出去之间往前走。

那天推送方在临时 worktree 上验的是 `f2c4b88`，执行 `git push` 时 `HEAD` 已经到了 `a5095ae`——另一个会话的提交插在验证与推送之间落地。**推上去的因此包含一笔谁都没验过的提交。** 补验之后是干净的，但那是运气，不是纪律：验证与推送之间没有任何东西把两者钉在同一个对象上。

做法是推那个不会动的东西：

```powershell
# 验哪个 SHA 就推哪个 SHA，不推会动的分支名。
git push origin <已验 SHA>:main
```

后落的提交自然留到下一轮，由下一次验证覆盖。

**但那只挡住了落在你后面的那些。** 推 `X:main` 发布的是 **`X` 的整条未推祖先链**，不是 `X` 一个提交——别人的提交只要落在你这一笔**之前**，它就是你的祖先，跟着一起上远端。实测一次：`05b5b8b` 与其父 `305d372` 相隔 **23 秒**、作者不是同一个会话，推前者时把后者一并发布了，而写它的人当时并没打算自己推。那次结果无害（对方本就要发，两笔又都是 `.md`），但**「发布时机」这个决定已经替他做了**，且推的人事前不知道有这一笔。

**而这一格恰恰在「没什么可验的」时最容易漏。** 上面那段配方要求先在临时 worktree 里验那个 SHA——真验了，别人那笔的内容也就一并看见了。跳过它的理由通常是「纯 `.md`，编译不了也跑不坏」，而那正是你连自己在发布什么都没看一眼的场合。**改动是不是 `.md` 决定要不要跑构建，不决定要不要看一眼你这一笔底下压着谁的东西**：`git log --oneline <上次已推 SHA>..<X>`，一行的事，有别人的就先问。

**而这一查要贴着 `push` 跑，不是贴着 `commit` 跑**——两者之间就是窗口。`1c71203` 那次在提交前查过一遍、为空，于是提交信里写下「其下无他人提交」；而 `a720828` 在它落盘前 **6 秒**才进来，那句话写下时就已经不成立了，真拦住它的是推之前又查的那一遍。所以提交信里这类话要带时刻（「于某时查为空」），别写成无时限结论。这与上面「提交竞态」是同一件事：**窗口在你查与你写下之间，任何对树的检查都看不见几秒后才落的提交。**

**这条一旦成立，验证就可以外包。** 既然验的是一个不动的对象，就不必由推的人亲自验：交活时附上一个自己验过的 SHA，推的人只按那个 SHA 推。共享树上只有一个人有权推，但不必只有一个人有能力验——单点因此拆掉了。

**验证一律带 `-count=1`：`go test -count=1 ./...`。** 它关掉测试缓存，于是「绿」一定等于这一跑真跑过。代价是固定花十几秒，换掉的是一整类没法靠看输出分辨的问题。

**附 SHA 时报一件：自上一个已验 SHA 以来有没有动过 `.go` 或 `.sql`。** 不必报耗时——那条判据试过，见下节，它会误报。

#### 全量只跑一次：作者跑受影响范围，推送方那一跑是 main 真值的唯一来源（2026-09-08 起，用户裁定）

09-08 量到的一格浪费：同一张票的全量至少跑了三四遍——作者在自己分支 `go test -p 1 -count=1 ./...` 两遍、推送方重放后一遍、
评审若照抄再一遍；同一份代码、同一只 55432 库，结果不会变。慢的也不是包的数目，是**带 DSN 的包串行（`-p 1`）**：纯单元
包各只要几十毫秒，PS `adapters/postgres` 一个包实测 51 秒，全量的时长基本就是几个真库包首尾相接。三层各干各的：

- **作者**：`go build ./...` 与 `go vet ./...` 仍是全仓——几秒钟，签名改坏了谁都在这两步露出来；`go test -count=1` 只跑**动过的包及其反向依赖**，
  外加 `./internal/architecture/...`（接线基线、可达性、事务闭包这些门禁扫的是全仓，但本身很快）。动了 `adapters/postgres` 或
  `migrations/` 才带 DSN——**但反向依赖里的 `cmd/*` 包一律带 DSN 跑**（2026-09-09 用户授权通道 1 代裁）：那些包的真库用例无 DSN 时 `t.Skip`，
  是仓里唯一一处「跑过了、绿了、其实一条没跑」的地方。实测：awf/13 与 awf/15 把一册接进服务端规范化，对账门随之对该册开门，
  `cmd/parcel-commercial` 夹具里随手写的 `sha256:…` 摘要在含 DSN 时红——作者自验与两份非作者评审都只跑了 PC 包组 + `cmd/parcel-api`、
  无 DSN，三处全绿，红到推送方全量才露出来。判据不是「我动了 postgres 没有」，是「我改的东西会不会改变一条真库用例的答案」，
  而后者作者事先答不出，所以规矩定在包上不定在判断上。反向依赖用命令反查，不靠记忆：

  ```powershell
  # 谁（生产构建）依赖 P：列出 ImportPath 与其传递依赖，筛出含 P 的那些（实测于 6ae24ae2：PS ports 反查出 21 个包，含三个 cmd）
  go list -f '{{.ImportPath}} {{.Deps}}' ./... | Select-String -SimpleMatch '<P 的 import path>' | ForEach-Object { ($_ -split ' ')[0] }
  ```

  模板里别写 `{{join .Deps " "}}`——PowerShell 会把内层双引号拆成两个参数，`go list` 报 `unclosed action`；`{{.Deps}}` 打成
  `[a b c]` 一整段，对 `-SimpleMatch` 够用。`.Deps` 看不见只在 `_test.go` 里的导入，所以动了 `ports.go` 这类被测试替身实现的
  接口时，把 `cmd/...` 也带上。**不跑两遍**：
  没有已知 flaky 用例时第二遍是零信息，有的话该做的是把它修掉或点名。
- **评审**：只跑派单点名的包组（上节「评审者只读……不跑全仓」那句已经这么说）。
- **推送方**：重放到 tip 之后带 DSN 全量**一次**（上节步骤 4），这是唯一一跑「验的就是要推的那个对象」，不能省；下一形态里由 PR 上的
  CI 接管（见「落 main 的下一形态」）。

再往下省时间要动的是夹具，不是隔离粒度。`internal/platform/pgtest` 已经给**每个用例**一个物理库（`CREATE DATABASE` → 跑真实迁移计划 →
`DROP DATABASE … WITH (FORCE)`），隔离没有可再加的；`-p 1` 在那里也不是防逻辑相撞，是防同一只实例上的 I/O 争用——建库、迁移、DROP
逼出的 checkpoint 在多包并行时互相等（`ci.yml` Test 步的注释用 run 号钉着那几笔账）。真库包慢在**每个用例都付一遍固定夹具费**：
`internal/parcelshipment/adapters/postgres` 实测于 `6ae24ae2`——143 个用例、总 45.2 秒、中位 0.31 秒、最慢 0.42 秒，均匀到看不出哪个
用例重，说明时间几乎全在建库 + 全套迁移 + 删库上，不在用例正文。有先例的解法是**模板库**：每个测试进程只迁移一次到一个模板库，
之后每用例 `CREATE DATABASE … TEMPLATE …`（文件级拷贝），隔离语义与「证的是随产品发出的那份 SQL」一字不变，改动只落在 `pgtest`
一个文件、`Pool(t)` 的签名不动。不要走关 `fsync` 或事务回滚包裹那两条路：前者 `compose.yaml` 明写为保事务可见性证据不关，后者会把
Outbox 交接与事务闭包那些用例要证的提交语义包掉。先量再改：拆出「建库 / 迁移 / 用例正文 / 删库」四段各占多少，再做模板库，再回头
量 `-p 1` 能不能放——放不放以 `ci.yml` 那种带 run 号的实测为据，不凭推。这是一张票的量，不是顺手改。

#### 别人分支上的活怎么进 main：推送方重放，不在共享树上 rebase

来自 2026-09-04。一个会话在专用 worktree 的分支（`mcp5-pr08`）上做完三笔、自验后报了 SHA；共享 `main` 在它开工后已经前进了若干笔。合入走的是这条路，每一步都是在那一天实际发生过的：

1. 推送方在**隔离 worktree** 里把那三笔重放到 `main` tip 上（`cherry-pick` 或 `rebase --onto`，效果相同）：三笔内容原样、SHA 换了——分支上的 `de28399 / 32e6b43 / c4e6586` 在 `main` 上成了 `51e3c84 / 0a67406 / cdd1897`，作者不必再动。
2. 在新 tip 上重生成机制清点、单独成笔（`f148759`，见「生成物不占号」那节）。
3. 把共享 `main` **快进**到那个 tip（ff，不产生新对象）。
4. 在隔离树上对那个 SHA 跑全仓 `-p 1 -count=1`（含 DSN），绿了 `git push origin <sha>:main`。
5. 广播「远端 main = 某 SHA」，作者据此把票面转 resolved，票面写 `main` 上的 SHA、分支上的 SHA 作封存出处并列。

**共享树上绝不 `rebase main`**，理由不是操作风险，是本文整套纪律的支点：每个人报的都是 SHA，验的是 SHA，推的是 `<sha>:main`，票面记的是 SHA。改写 `main` 的历史等于让所有人已经报出去、写进票面、写进任务台账的那些 SHA 同时指向不存在的对象，而那些记录不会跟着更新。重放别人的分支只换那几笔的 SHA，且换之前它们还没被任何人当基准引用过；推送方在广播里把新旧 SHA 对照写出来，作者的封存记录才对得回去。步骤 1 与 3 之间若 `main` 又前进了，重放要在新 tip 上重来——推送方先核中间那几笔有没有与这三笔重叠的 `.go`/`.sql`，无重叠才直接重放，有就让作者重验。

#### 合入前独立评审（2026-09-08 起，用户裁定）

09-07 复盘时量到的最大专业度缺口：每张票一个会话写、同一个会话自验，推送方只核「内容对不对得上」和跑测试，
不逐行审语义——合入前没有第二双眼睛看 diff。当天唯一两次跨人核对（「先写自己的 red 再读对方现场」）都在接手
现场时发生，不在常规路径上。自 2026-09-08 起，**代码票进 main 前必须有一份非作者的评审报告**，规矩如下。

- **谁评**：作者交完工报时，推送方指定一个**非作者、当下空闲**的通道评审；没有空闲通道时推送方自己用
  `/code-review` 的隔离子代理跑，不由作者自评。评审者与作者不能是同一会话，换过会话的同一通道也算同一人。
- **评什么**：隔离检出（`git worktree add --detach $env:TEMP\idp-review-<票> <分支 tip>`）上跑
  `/code-review <基线 SHA>`，spec 指到票面。两轴照 skill：**Standards**（AGENTS.md 红线、该上下文 CONTEXT/词表、
  所引 ADR 的决定）与 **Spec**（票面完成判据、裁决节、验收对照）。评审者只读，不改作者分支，不跑全仓——验证是
  作者与推送方的事，评审看的是编译器和测试看不见的那一半：语义对不对、有没有做票面没要的、该有的有没有缺。
- **报什么**：写进票面 Comments 一条「评审 ← 通道 N · 钉 `<tip>` · HH:MM」，三格：**阻断**（合入即错：语义与
  ADR/票面相反、不变式被绕过、红线被碰、缺完成判据点名的东西）/ **非阻断**（可改可不改、或另立票）/ **无发现**。
  每条锚文件 + 符号名 + 为什么，每轴 400 字内。时限 20 分钟；到时未交，推送方改派或自跑，不等。
- **门**：推送方只在评审为「无阻断」时重放。有阻断回作者在**同一分支**修，修完只重跑受影响的那一轴；非阻断随票
  记、不挡合入，作者可另立票。评审结论与 SHA 写进「进 main 记录」。
- **不评什么**：纯 .md 簿记、清点重生成、`chore(salvage)` 封存笔、一行 ci.yml 这类——推送方自审，票面写「自审」两字
  即可，不装样子。
- **评审者的纪律**：写证据不写口味——「建议重构」「可读性差」这类没判据的话不写；每条要能回答「按哪条规矩、
  哪句票面、哪个不变式」。发现对方**能编过但语义不对**的东西是评审唯一真能提供的价值（见「报什么，不报什么」）。

#### 度量：tasks.md 每节末尾五个数（2026-09-08 起）

09-07 一天 CI 红三次、通道 1 换五次会话、重复开发一次——这些数都是事后手数出来的。此后 tasks.md 每个会话节
（`## <日期时间> 通道 1 …接续`）**末尾固定一行五个数**，格式与量法如下，缺的写「未量」不写 0：

`**本节五数**：CI main 绿/总 a/b · 集成时延中位数 m 分（完工报→推出，n 票）· 重放笔数 k · 重复开发 d 次 · 会话重置 r 次`

- CI：`gh run list -R <origin> -b main --created <本节起止>`，绿 = success，总 = 不含被 concurrency 顶替的 cancelled。
- 集成时延：每票「完工报到达时刻 → 广播已推时刻」，取中位数并写票数；被用户提问打断的也算，不剔除。
- 重放笔数：本节推送方 cherry-pick 进 main 的提交数（不含清点与 tasks.md）。
- 重复开发：同一票在两条分支上各有实现、其一成孤儿的次数（判据见「派发前先点名」末段）。
- 会话重置：本节里各通道自报「新会话、无在途记忆」的次数 + 用户报 crash 的次数，含通道 1 自己。

一周看一次趋势，不看单节；哪个数连着两周不动或变坏，那一格的规矩就该改。

#### 分支每笔提交后推到 origin（2026-09-07 起，用户裁定）

`main` 只有推送方推，**自己的分支自己推，每笔提交后就推**：`git push -u origin <分支>`。CI 只在 `push: main` 与
`pull_request` 上触发，推分支不起 run，没有成本。买的是两样：本机丢盘或 `.git` 损坏时不丢活（09-07 一天里各通道
崩溃十余次，活全靠「每小步提交」留住，但都还只在这一块盘上）；换会话、换人接手时 `git fetch` 就能看见对方分支
的最新状态，不必等广播。`merged/`、`salvage/` 前缀的本地指针不推——它们只为事后补验留着，远端不需要。

#### 落 main 的下一形态：作者自落，PR + CI 把门（切换条件写明，未到之前仍走上面的重放）

它挡的是「没走落地流程就推 main」，挡不了有意绕过（`--no-verify`）——那一层只能靠升级套餐或转公开仓，归用户。

### 不同的「绿」在输出上长着同一张脸

上面两条与下面这条是同一个毛病的若干个面：**性质完全不同的「绿」，在终端里看不出区别。**

再一个面是真库门禁。`internal/platform/pgtest` 在未设 `IDP_PARCEL_POSTGRES_DSN` 时诚实跳过——这句话本身没错，但**跳过在 `go test` 的默认输出里就是一个 `ok`**。2026-08-14 有个会话的门禁容器已经健康跑了一个多小时，而它自己 shell 里那个变量是空的，于是它的「全仓绿」不含任何真库证据，而「真库适配器不实跑不推」在本人毫不知情的情况下就被破了。CI 缺 DSN 会 `t.Fatal`，本机不会，所以本机这一层没有任何东西在守。

判别不能靠读 `ok`。可靠的办法是单跑一个真库用例，看 `-v` 下是 `PASS` 还是 `SKIP`：

```powershell
$env:IDP_PARCEL_POSTGRES_DSN = "postgres://parcel:parcel@127.0.0.1:55432/postgres?sslmode=disable"
go test ./internal/settlementaccounting/adapters/postgres/ -run TestFreezeScopesAreInvisibleToEachOther -count=1 -v
```

**别拿耗时当判据。** 这条绕了三轮才落定，过程比结论有用。

先是有人实测：同一个提交（改动只有一个 `.md`）带 DSN 加 `-count=1` 是 25.5 秒，带 DSN 允许缓存 42.6 秒，不带 DSN 3.5 秒，据此写下「真库用例开 TCP 连接、Go 不缓存，所以只要 DSN 设着全仓跑就快不了」，并进一步推出「跑进 20 秒以内就说明真库门禁没跑」。另一个会话随即在同一 SHA、同一台机器、同样带 DSN 上跑出 5.4 秒——于是前一个人反过来怀疑他其实没设 DSN。

**两边都不必怀疑对方，那个机制根本不成立。** 一条命令就能看到：

```powershell
$env:IDP_PARCEL_POSTGRES_DSN = "postgres://parcel:parcel@127.0.0.1:55432/postgres?sslmode=disable"
go test ./internal/settlementaccounting/adapters/postgres/   # 13.9s
go test ./internal/settlementaccounting/adapters/postgres/   # (cached)
```

**真库用例的结果照样进缓存**，`(cached)` 就印在那里。所以带着 DSN 的全仓跑完全可以只花几秒，5.4 秒那一跑是一次正当的缓存命中，没有任何人报错了自己的环境。

那三组数据错在哪：**`-count=1` 不写缓存**，因此「先 `-count=1` 再允许缓存」这个顺序下第二跑无缓存可命中，慢得理所当然——它测的根本不是缓存有没有生效。测缓存要连跑两次不带 `-count=1`。**一个错的机制加一组自洽的数字，比没有数据更能骗人**：数字全是真的，实验设计错了。

于是又有人提出退一步的版本：耗时至少能守 DSN 缺失吧——「全仓跑落在 20 秒以下基本只有一个成因」。也不成立，一个反例就够：

```
DSN 已设，库可达（同一刻单跑真库用例是 PASS 不是 SKIP）
全仓 go test ./...（缓存已暖）：1 秒，56 个包报 (cached)
```

结论因此是耗时**什么也守不住**：带 DSN 可以很快（缓存命中），不带 DSN 也可以很快（跳过），两种快在秒表上一模一样。两格各自用开关守——`-count=1` 守缓存，`-v` 下的 `PASS`/`SKIP` 守 DSN。这与 DSN 那件是同一条教训的两个实例：**能用开关守的就不要留给人去看。**

这条前后反复了四轮：先按一个错机制立起来，用真实但设计错的数据加固，被一组冲突数据以错误的理由推翻，又被同一个错机制救回来，最后死于一个一秒钟的反例。**留下经过是因为下一个人会重走它**——看到一快一慢两个数字时，把它归给缓存或归给 DSN 都是很自然的解释，而这两条自然解释当时各错了一次。要判缓存就连跑两次看 `(cached)`，要判 DSN 就看 `PASS`/`SKIP`，都不要看秒表。

这几条合起来的教训只有一句：**报「绿」的时候要说清是哪一种绿。** 「绿（含真库）」与「绿（未设 DSN，PG 用例跳过）」是两个强度不同的断言，而它们在屏幕上都只是 `ok`。

**而这个形状不止出现在「绿」上。** 后来陆续撞到的都是它的同族：跳过看着像通过、替身看着像实现、未接线看着像已接线、接错看着像接对（漏掉一道守卫，答出来的恰好就是当前唯一走得到的那一格正确答案）、推测看着像取证。共同点是**两种状态的可观察签名完全相同**——不是难分辨，是没有任何东西可供分辨；而它们各自要人做的事往往相反。所以这一节不必凑数，见到新的一面就归到这里。

处方分两级，先试第一级：**能把区别做进结构就做进结构**——用开关守（`-count=1` 守缓存、`-v` 下的 `PASS`/`SKIP` 守 DSN），或者让两种状态在类型上就分得开，读的人不必去分辨。**做不进结构时才退到第二级：写证据，不写结论**，把那一步判断连同它的依据一起交给读的人。第二级是退让不是等价物——它守得住诚实，守不住下一个人会不会照做。

#### 又一面：接手别人在途产出时，镜像测试与真测试在绿的时候完全同形

**接手另一个会话在途的实现时，先写自己第一片 red，再去读对方的代码。**

先读后写的测试是那份实现的**镜像**：它照着代码此刻的形状长，于是**行为错了它不会红，而对方重构一次它就碎**——两件事都跟它该干的相反。而它绿起来跟一片真测试**一模一样**，这正是本节那个形状：没有任何东西可供分辨。

把读推后一步，它就从「模板」变成「交叉验证」，而且两种结果都比直接拿过来值钱：形状对上了是一次独立印证；对不上则恰好指出一处两人其中一个想错了的地方，**而那一处不推后就永远不会暴露**——先读的人会不自觉地把对方的理解抄进自己的断言里。

这条的处方落在第一级（做进结构）而不是第二级：**顺序本身让镜像不可能发生**，不需要谁事后去分辨自己写的是哪一种。

对测时**对判据**（各自钉的是哪一条规则），**不对断言条数**。条数不同是正当的——两个人从不同的入口读同一条规则，切法本来就不一样；判据对不上才是信号。

来源：2026-09-02 票 12 一次撞号后的产出转交，这句是接收方提的接收条件。

### 未提交现场：活的和死的在 `git status` 里长着同一张脸

本仓已经被「未提交现场被抹掉」咬过三次。但真正难办的不是抹掉，是**判不出该不该动**。

共享树上出现一份不属于你的改动时，`git status` 只会给你 ` M` 或 `??`。**有人此刻正在写**和**某个已结束的会话留下的死现场**，在那份输出里逐字相同。唯一分得开两者的是 mtime，而**mtime 只在很短的窗口内分得开**：2026-08-21 那天树上同时躺着两份，一份 mtime 停在某次 `rebase --autostash` 弹回的那一刻、整场会话再没动过（死的，可以封存），另一份距查看仅 75 秒（活的，碰不得）。两份在 `git status` 里一模一样。再过一阵，那 75 秒也会变成半小时，就谁也分不出了。

所以判之前先量 mtime，别凭 ` M` 与 `??` 猜。但**结论不是「多量 mtime」**——那又是一条会随时间失效的纪律，跟本文反复在换掉的东西同类。结论是：

> **写到一个可提的点就先提。** 提了就不需要任何人去分辨。

攒着不提，你的工作就变成了别人的判断题，而那道题只在最初几分钟有解。

真要替别人封存一份死现场时：**原样入库，一字不改，自己的改动另起一笔**——归属才清楚（仓内先例 `3aa7075`、`9021454`，提交信都写明非集成候选、仅防丢）。

**提交信里写证据，不写结论。** 那两条先例都写的是「封存某某死会话未提交现场」，而其中一个被封存方当天晚些时候就报到了——人没死，只是那阵子没响应。「谁已死」是个会过期的断言，而提交信不会跟着更新，于是一句当时合理的话永久留在了历史里。写「mtime 停在某时、自某时起未响应，据此按死现场封存」，同样说清了为什么动它，且过多久都不会变成假话。

**封存一篇未完成的 ADR 还要多一步：处理 `Status:`。** 封存一条票面条目与封存一份决策记录分量不同——ADR 记的是难逆转的取舍，一篇半成品若带着 `Accepted` 进库，下一个人会拿它当已生效的约束去改代码。没写完就让 `Status:` 如实说没写完。

### 拆工作树：先比内容，分支指针留到最后

来自 2026-08-21 一批票交活时的连续拆树。**拆掉一棵树前比内容，不是只看 SHA 在不在日志里。**

日志好看证明不了内容进去了：合入常走 cherry-pick，**掉一个 hunk 而日志照样是三笔齐全**。这个失效模式恰好发生在「拆掉唯一副本」的前一秒——那棵树没了，比对就无从做起。

```powershell
git diff <你验过的 tip> origin/main -- <本票所有文件>   # 必须为空
git status --short
git status --untracked-files=all                        # 与上一条都要零行
git worktree remove <path>                              # 永不加 --force
```

`--untracked-files=all` 不可省：普通 `git status --short` 对被忽略目录只显一行，你会看着一行输出以为只差一个文件。

**永不加 `--force`。** 本仓三次未提交内容丢失全部发生在孤儿 worktree 被 `--force` 拆掉。上面那段验证配方原先带着 `--force`，已去掉——而它的问题不止是「换个场合会要命」这种推测，**它在自己那个场合里就已经在屏蔽反馈**：验证树会正当地积下日志与产物，一次集成用的验证树里就躺着一份未跟踪的 `verify.log`（全量测试输出）。不加 `--force` 时 git 会如实拒绝，**而那声拒绝正是该看见的东西**——被迫看一眼再删，好过无声抹掉。多一步删日志不算麻烦，算诚实。

**分支指针留着，别跟树一起删。** 拆树可以，删分支要慎，理由是**分支指针是事后补验的唯一凭据**。上面那批票里有一棵树是在「先比内容」这条定下来之前拆的，当时只查了 `git status`；因为分支指针留着，事后仍然跑得完整对比（六个代码文件与新增票面 `git diff` 全空，cherry-pick 没掉 hunk），才确认了那次拆除没有掩掉东西。**树拆了还能补救，分支一删就真的比不成了。**

**留着的指针要改名，让 `git branch` 一眼分得出在途 / 已合 / 只防丢。** 来自 2026-09-07 晚：本地 53 条
未加前缀的分支，`git cherry main <分支>` 条条有 `+`——绝大多数只是清点笔或 README 上下文差，真正没进 main
的不到十条，但两者在分支列表里长同一张脸，「这棵树的活合回去了吗」每次都得翻 tasks.md 才答得出。当晚按下面
的量法逐条判过后改名，此后照此维护：

- `merged/<原名>`：分支改过的每一份非簿记文件（簿记 = 清点、ADR README、tasks.md、接线基线），其分支 tip
  上的 blob 都在 `main` 该文件的历史里出现过——内容进了 main，main 之后再改过也算。量法：
  `git log main --format=%H -- <file>` 逐笔比 `git rev-parse <commit>:<file>` 与 `git rev-parse <分支>:<file>`。
  只差 `unwired_orchestration.go` / 票面 .md 且 `git diff <分支> main -- <file>` 只有加行没有减行的，也算。
- `salvage/<原名>`：封存现场、被重切或 v2 取代的旧版、分工改派后的孤儿、清单裁「不合」的那半——只为防丢
  留着，**不是集成候选**，重放前不必再量。
- 不加前缀：在途，或归用户的（`mcp4-tf03`）。

改名用 `git branch -m`，指针一个不删；集成方在完工重放、拆树那一步顺手改，别攒。分支名带 `/` 的照样加前缀
（`merged/mcp5/admin-skeleton-0506`）。判 ABSORBED / NOT-ABSORBED 不必手算：
`scripts/branch-state.ps1 -Classify` 对所有未加前缀的分支跑上面那套量法；`-Audit` 再把不在任何 ref 上的游离提交按
patch-id 与 blob 两级核一遍（慢，几分钟）——09-07 夜里 398 笔游离提交就是这么审出「无一丢失」的。

`git worktree remove` 的退出码两个方向都不可信，收尾要逐格查而不是读退出码——那属本机环境的坑，配方记在 [workflow.md 的本机环境](./workflow.md#本机环境)，此处不复述。

**带 `node_modules` 的工作树是那条坑的另一个面：删一半就停。** 2026-09-04 一棵 `apps/admin-web` 装过依赖的 worktree（`D:/tops/idp-pr08`），拆前核过 `status` 空、本方文件与 `main` 逐文件一致，`git worktree remove`（未加 `--force`）退 255 报 `Directory not empty`——登记已从 `.git/worktrees` 摘掉、树里的 `.git` 链接文件已删，**而树的大半还在**，卡在 `apps/admin-web/node_modules/.pnpm` 下的超长路径上。上面那条配方写的是「只剩最后一层空目录」，这次剩的是半棵树，同一个退码。判依据照旧不是退码，是三样各自查：**树里 `.git` 链接文件在不在、`git worktree list` 里在不在、分支指针在不在**（`git rev-parse <分支>`）。三样都对——链接已删、登记已无、指针仍在——才清壳，且要用长路径前缀：`Remove-Item -LiteralPath '\\?\D:\path' -Recurse -Force`，普通路径在那些文件上删不动。分支指针留着，理由见上一段。

### 共享接线文件：占号、同笔、逐块核

来自 2026-08-13 持久化批的一串连环事故。`migrations/migrations.go` 与 `internal/platform/migrate/plan.go` 是第三类文件里最凶的一种：**每个新迁移模块都必然要碰同一行**（嵌入指令、计划装配、schema 清单），且改动之间存在编译级耦合——嵌入了目录而目录里没有文件，整个仓一起红。

那天它连断远端构建两次，两次成因不同：

1. **`add` 卷带**：一个会话暂存共享文件时，树里已混着另一个会话的在途接线（其 SQL 尚未提交）——提交推送后，远端在一个不存在的嵌入目录上编译失败。
2. **提交竞态**：两个会话相隔 35 秒各自提交同一对文件，后提交者的暂存快照取自前者落地**之前**——`git commit` 不做合并，快照直接把先落地那份接线又剥掉了。随后两边就地互改，又撞出重复常量的编译错。

三条纪律，即日生效（已由全频道采纳）：

- **占号**：改这两个文件前先在频道说一句「占 `migrations.go`：目的」，推送后释号。占号期间对方不碰。
- **同笔提交**：新迁移模块的目录（含首个 SQL）、嵌入行、模块函数与计划接线**同一笔提交**——四件缺一，干净检出就编不过。
- **`add` 前逐块核**：`git add` 共享文件前先 `git diff HEAD -- <file>` 逐块看，有外来 hunk 就停：要么等对方提交，要么把暂存内容做成「HEAD＋只有自己的块」。

提交竞态那一次的复盘只有一句：**逐块核防的是「卷走别人的」，防不了「盖掉别人刚提交的」——后者只有占号能防**，因为竞态窗口在你暂存与提交之间，任何对树的检查都看不见别人 35 秒后才落地的提交。

#### 占号守得住「谁在改」，守不住「这一笔带走了什么」

来自 2026-09-04 下午，两份 `internal/architecture/*_baseline.txt` 被三个会话各剪自己那一组。占号纪律全程照办——每一笔改前都在频道说了、也都只改自己那一段——同一天里还是撞出三件事，三件成因各不相同。

**一、共享工作副本上同时躺着两个人的 hunk，pathspec 提交会把两份一起带走。** `git commit -F <msg> -- <path>` 提的是**工作副本**上那份文件的全部内容，而占号只让人别去改同一段，并不让人别在同一时刻改同一份文件——两段不同的 hunk 落在同一个工作副本上是常态。一个会话的处置是**不碰共享副本**：把自己那一版 blob 造成「HEAD＋只有自己的块」，经临时索引成笔（`git show HEAD:<path>` 取底，打自己的 hunk，`hash-object -w` → `update-index --cacheinfo` → `write-tree` / `commit-tree`），共享副本上别人的 hunk 原样留给别人提。本文上面「HEAD＋只有自己的块」那段配方就是它——那段是为「同一个文件里混了两个人的改」写的，这一天它的用场正是这个。

**二、`git diff --cached --name-only` 要贴着 `commit` 跑，不是贴着 `add` 跑。** 同一天有人在提交前一秒重看了一眼暂存清单，发现共享索引里躺着另一个会话已暂存、未提交的七件——照原样 `git commit` 会把那七件一起带走；改走临时索引才躲开。这句话本文「但逐文件 add 守不住」那节写过，那节把它列为第二级诊断；今天它当场拦下了一次，于是补一句它的用法：**看的时刻决定它守不守得住**——`add` 完看一眼再去写提交信，这几十秒里别人的 `add` 就进来了。

**三、「他带走了我的 hunk」是个断言，先量再说。** 一个会话广播说另一笔提交（`616646d`）带走了它剪基线的那几行，请推送方别单验那一笔；几分钟后更正：那一笔是干净的，成因是用带 `^` 锚的 `Select-String` 在 `git show` 管道上查零命中——中文按 GBK 解会让锚失配、命中为零，[workflow.md 的本机环境](./workflow.md#本机环境)点名过这条，读过它的人照样踩了。更正那条广播比误判那条更值得记：它写明了误判的量法，收信的人因此知道该信哪一条。**所以对共享文件的指控，附上取数命令**——读的人分得出「量出来的」与「想出来的」，两种失效方向相反，而写下来之后长得一模一样（见「断言有保质期」那节）。

### 生成物不占号，但只在干净检出上生成

`docs/product/MECHANISM-INVENTORY.md` 由 `tools/mechanism-inventory` 生成，CI 那道「Mechanism inventory is current」在 tip 上重跑生成器、与提交的文件不一致就红。它是全仓派生态命令的产物，但与本文上面禁止单方面跑的 `tidy`/`gofmt -w` 不同属：那些写回源码，这个写回一份谁都不拥有的清点。2026-09-04 一天里撞出三格：

- **一次推送没带重生成**（`a3adb75`，随后在 `efdbad7` 补）——四笔各自新增了文件或迁移，没有一笔重跑过生成器，CI 那道在那个 SHA 上红。
- **在共享树上跑生成器，数进去的是别人的在途件。** 生成器数的是文件面、迁移份数、端口与端点声明数，共享树上此刻躺着谁的未提交文件它都算——那份数字对任何一笔提交都不成立，谁都不该提。
- **共享索引里出现过一份无人认领的陈旧清点**：已暂存、与 HEAD 差 6/8 行、工作副本与它一致，被问到的几个会话都否认是自己的；14:2x 由推送方 `git restore --staged` 后 `git checkout -- <path>` 复原到 HEAD。它的来历是某一次早已被后续快进盖过的重生成留在索引里没提，留着会挡下一次带清点的 ff，也会被不带 pathspec 的 `commit` 卷走。

收成两句：**各笔在自己那笔的干净检出上重生成、随笔提（或紧随一笔）；推送方在 tip 上重生成兑底。** 干净检出是 detached worktree 检出父提交＋本笔文件（本文「推之前另在临时 worktree 里检出提交状态跑一遍」那套），生成器对着它跑，产物拷回共享树只 `add` 这一件。该文件不占号：它是生成物，**谁的笔在后谁的数字盖前面**，这是预期内的——两笔各自在自己检出上生成的数字不同，不是谁量错了。

## 报什么，不报什么

**只报对方从自己构建里看不到的事。** 四类：

- 你改了公共东西会拆到他（新门禁、共享签名、`go.mod`）
- 决策类事实（ADR 编号、被否决的方案、闸门状态）
- 他的代码**能编过但语义不对**——这是旁观者唯一真能提供的，编译器拿不到
- 地盘与顺序协调

**别人包里的编译错一律不报。** 他本地的构建循环比消息快。那天四个会话先后报了三套不同的失败坐标，三套当时都对，读到时全已作废，还驱使拥有者去看一个健康的文件。

## 断言有保质期，但设计建议没有

**共享树上关于当前状态的任何断言都有保质期，文档不例外。** 「某文件第几行写着什么」「某包编不过」「某个东西不存在」——这类结论型消息发出前重新取一次证据，成本比一轮仲裁低得多。

**「某个会话已死」也是这一类，而且比上面几类阴得多。** 上面几类过期了会自己露馅：你去看那个文件、去跑那个构建，当场就发现和描述对不上。「已死」不会——它一旦写进交接档，下一任**当先验事实读，根本不会想到要取证**，因为「谁还在」看着像背景设定而不像一条待核的断言。2026-08-21 的交接档写着两个会话已死，当天两条**均为假**，两人都在正常干活；而按那份档去分派，等于把他们手上的东西当无主物处置。

写法照旧是把结论换成证据：**「截至某时未响应」**。它同样够你做决定（要不要替他封存、要不要把活重派），而且过多久都不会变成假话。同一条毛病在工作树上的形态见上面「未提交现场」那节——判一份改动是活是死，靠的同样是一个会过期的信号。

**过期的还不只是你写下的结论，也可能是你读到的那个值。** `git rev-parse origin/main`、`git log origin/main` 这些**都不联网**：`origin/main` 是本地远程跟踪 ref，读的是上一次 `git fetch` 缓下来的东西。共享树上远端每几分钟就往前走，不 fetch 就问它，拿到的是旧值而不是远端事实，而它长得跟新值一模一样。

```powershell
git ls-remote origin main        # 报远端状态用这个，它真的问远端
git fetch origin; git rev-parse origin/main   # 要用 origin/main 就紧跟在 fetch 之后
```

2026-08-21 同一次对话里两个人**方向相反地掉进同一个坑**：一个写下了会过期的**结论**（「`origin/main` = 某某」，发出时为真，读到时已不是），另一个读到了会过期的**缓存**（未 fetch 就 `rev-parse`，据此判定对方报错了）。两半凑齐才是完整的处方——**写的一侧写证据不写结论，读的一侧确认自己读的是远端不是缓存。**

**而「我比过一次，两个值对得上」不能当判据。** 缓存读数大多数时候是对的，它只在你最需要它准的那一刻偏旧——别人刚推完、你还没 fetch；一次相符只说明你今天恰好 fetch 过，不说明下次也是。**它给你的不是「无数据」，是上次 fetch 那一刻的一个真实 SHA**：具体、像模像样，不以任何形式提示自己是缓存。它能呈现的几种外观——看着像没人动过、看着像刚同步过、以及真的就是对的——在终端里没有任何可供分辨之处，这是上面「不同的『绿』」那一节的又一个面。

**而 fail-open 出在比法上，不出在那个值上，所以这条不需要「滞后只有一个方向」这类全称。** `origin/main..HEAD` 把一个只在 fetch 时才前进的 ref 当成了远端。实测一次：缓存 `ce494ca`、`rev-list --count origin/main..HEAD` 为 `0`，而真实远端已在 `68d2202`——「无待推」这一半碰巧是真的，人从它读出来的「我是最新的」是假的。远端被回退时（force-push、分支删后重建）它**也**给 `0`，那一次连「无待推」都是假的：你手上有对方没有的提交。**两种失效方向相反，却都落在「不用动」这一侧**，这才是它 fail-open 的原因。本仓靠约定不 force-push，所以后一种罕见——**但罕见是约定给的，不是机制给的**，而读的人分不出自己靠的是哪一种。判据因此只能落在命令上：**报远端状态一律走 `ls-remote`，不看它跟缓存一不一致。**

**最难防的那一类不是写错的事实，是把推出来的东西写成了断言——而那句断言又恰好没人会去验。** 写错一个事实还有人撞得上：他去看那个文件、跑那个命令，当场就对不上。推出来的「应该不会」没人撞，因为它读起来已经是结论，而要推翻它得重做一遍原作者当初省掉的那次观察，没人会为一句听着合理的话专门去做。

本文上面 `--force` 那段就栽过一次：原先写着「一棵刚建来跑只读构建的 detached 树本来就是干净的」——那不是量出来的，是推的（只跑只读构建 → 应该不会脏）。后来在一棵真的验证树里发现了未跟踪的 `verify.log`，整句才换掉。它能被拆穿，只是因为恰好有人亲手踩过。

**落笔前分一次：这句是量出来的，还是想出来的。** 想出来的要么去量一次，要么就写成预期而不是事实。这是上面「不同的『绿』」那一节的又一个面——两种状态可观察签名相同，而**推测与取证在写下来之后长得一模一样**。

**而「查不到」这种断言要多问半句：是真查过，还是没想到能查。** `68d2202` 的提交信里写着「两处都没留会话标识，事后也补不回」，并拿它当拆掉一个会话计数的理由之一。拆是对的，这条理由是错的：**git 树上核不出，不等于补不回来**——会话存档里留着，拿那组数里的一个秒数检索一遍，当初哪几个会话各自跑过什么就都钉得出来。错话已经进了提交信改不掉，而它比一般的过期断言更阴：**它劝的是「别去查」，于是没人会去撞它**。

**而存档这条路自带一个把人引向错数的坑：转引与复现在检索结果里长着同一张脸。** 那次检索命中三份存档，独立跑过的却是两份——第三份只是引用了别人的数。按命中的文件数数会把转引也算进去；**而反过来，跑过却没把数字写进存档的那一次根本数不到**——回一句「同数」就够了，**而这一头在构造上就不可观测**：没写下来的东西，任何检索都确认不了也否认不了。转引只增不减是检索这件事的机制，但它不是唯一误差源，两头都可能，**所以这个数根本不是复现次数**，不必去判它偏哪边。判别照旧不能看命中数，要打开看那一份是自己跑的还是抄来的。

**而换一套引擎交叉验证，只防得住引擎的错，防不住口径。** 一次 `docs/` 下的命中统计，在 `31b0c43` 上用 `git grep` 与 ripgrep 各量一遍：**文件数一致（都是 12），行数不一致**——前者数命中行，后者那个模式数命中次，同一个文件一个报 1 一个报 2。两个数都对，**相减就错**。多会话互核时这一格最容易滑过去：两人报的数不一样，第一反应是有人量错了，而常见的真相是两人问的根本不是同一个量。

**而过期断言真正的代价不是它错，是它会被下一个人当取证结果引用。** 实测有一次：一句注释里的计数早已过期，读到的人把它当当前事实转给另一个会话，**差一步就写进了一篇 ADR**——而 ADR 记的是难逆转的取舍，一旦引进去，后面的人会拿它当已经验过的前提。失手不在写下它的人，在于那句话被引用时，身上没有任何东西说明它是谁、在哪个时点、用什么方法量的。**这也是「写证据不写结论」为什么值那几个字**：证据带着这些，结论不带。

**但同一样东西也让它更难被推翻。** 带着时点、方法与 SHA 的数看上去已经验过，下一个人不会再问它量的是不是那件事。2026-08-21 同一句话的两个版本给了个对照：赤裸的全称（「本仓文档与注释全是中文」）当轮就被作者自己标出来；换成带锚实测（「实测于某 SHA：`docs` 下 201 份 `.md` 全部含中文」）之后反而活了两轮——**而拆它的不是重跑那条命令**（重跑仍得 201，字符区间在 `git grep -E` 下把所有非 ASCII 都包了进去，真值是 198），**是回去问那个判据到底在匹什么**。所以：**复核一个带锚的数，要重导它的问题，不是重跑它的命令。** 这不是叫你少锚——是锚完之后还欠一步。

**但这条管不了关于「还不存在的东西」的设计建议。** 「你选的这个取舍有一类语句装不进去」无法预先查新，因为它指向的是尚未写下的代码。两类并成一条，结论会滑到「什么都别建议」——而设计建议恰恰是只读会话产出的全部价值。

## 只读会话要派具体任务，否则是负收益

那天最有价值的三个发现全来自只读会话：归档谱系当年怎么解决同一个重建问题、领域包「判断的输入有构造函数、产物没有」的成建制立场、以及框架校验器在 `internal/` 下根本导入不了（实测，非推断）。

**而它们在被派活之前一条都没出现。** 写入方说了三次「没有能分的活」，直到一个阻塞把关键路径切出三块具体问题。回头看那些任务更早就存在。

好任务的形状：**只读、边界清晰、结论能直接改变写入方的下一步**。典型是「去归档里查当年怎么做的，只报事实不提方案」「从源码逐字段抠出规则，以代码为准不以文档为准」「把同类问题一次列全，免得写入方一个个撞」。

派任务时写明**不要做什么**——不写代码、不改文件、不替别人设计方案。否则调研会变成第二份实现。

## 决定权

**要么归 owner，要么被人明确授权。** 那天领域包的 owner 拒绝擅自开一个绕过不变式的口子并上报，是对的：难逆转的取舍按 [AGENTS.md](../../AGENTS.md) 要走 ADR。

被授权替别人拍板时，**把自己的能力边界写在裁决里**：读过哪些文件、没读哪些、因此裁的是结构还是具体不变式。那天的裁决只定方向与约束强度，ADR 与实现留给 owner——他知道那三百多行里的不变式，裁决方不知道。
