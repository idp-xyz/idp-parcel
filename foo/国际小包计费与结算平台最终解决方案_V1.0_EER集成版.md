# 国际小包计费与结算平台最终解决方案

**文档版本：** V1.0  
**文档状态：** 最终架构方案 / 可进入领域模型与技术设计阶段  
**适用范围：** 国际小包、国际专线、国际快递、海外仓尾程、多段物流成本、客户报价、承运商结算与账单复核  
**核心定位：** 以合同、价卡和费用账本为核心，以确定性 Rating Runtime 为执行内核，以结算与对账为业务闭环的国际小包定价基础设施

---

## 1. 文档目的

本方案用于解决国际小包业务中以下核心问题：

1. 不同承运商、渠道、仓库、国家、Zone 和重量段拥有不同价卡；
2. 不同客户合同使用不同体积重系数、计费重量算法、舍入方式和附加费规则；
3. 承运商采购成本、平台内部结算价、客户销售价和最终账单金额需要分离；
4. 价卡频繁变更且必须支持版本管理、历史重算、灰度发布和影响分析；
5. 包裹实际重量、体积重量、仓库测量和承运商复称之间存在差异；
6. 住宅、偏远、超重、超尺寸、不规则包装、燃油、签名等费用存在复杂依赖与叠加规则；
7. 承运商账单可能在出货后延迟产生复称费、地址修正费、退件费和其他调整；
8. 系统必须能够解释“为什么得到这个价格”，并支持客户补扣款、承运商申诉和财务对账；
9. 绝大多数价卡和客户差异应通过配置完成，少数特殊算法通过受控插件扩展；
10. 单票计费必须保持确定性、高性能、可重放，不能依赖 AI 推理或工作流引擎实时决策。

本方案不将系统设计成面向所有行业的“万能规则引擎”，而是建设一个高度贴合国际小包业务的领域化计费与结算平台。

---

## 2. 最终结论

国际小包最合适的完整方案是：

> **固定宏观计费阶段 + 阶段内受控费用依赖图 + 版本化合同价卡 + 参数化客户覆盖 + 有限价表家族 + 计费重量策略 + 标准附加费模型 + 决策表 + 受控函数扩展 + 不可变费用账本 + 周期性结算引擎 + 承运商账单复核。**

核心边界如下：

```text
渠道产品决定：能不能走
合同策略决定：使用哪套规则
价卡目录决定：基础价格和费率是多少
计费策略决定：重量、Zone、燃油、折扣和附加费如何计算
Rating Runtime 决定：当前请求的确定性计算结果
Charge Ledger 记录：为什么是这个结果
Settlement Engine 决定：周期返利、最低承诺和月度调整
Carrier Reconciliation 决定：承运商实际扣费是否正确
EER/工作流负责：导入、审批、发布、异常、争议和补扣款流程
```

## 3. 设计原则

### 3.1 领域化优先

系统专注于以下业务：

- 国际小包；
- 国际专线；
- 国际快递；
- 海外仓尾程；
- 国内揽收；
- 出口报关；
- 国际干线；
- 目的国清关；
- 海外仓操作；
- 尾程派送；
- 退件；
- 客户报价；
- 承运商结算。

首期不建设面向薪酬、保险、税务等所有业务的通用计算平台。

### 3.2 确定性优先

相同的以下内容必须产生完全一致的结果：

- 输入快照；
- 产品版本；
- 合同版本；
- 价卡版本；
- 重量策略版本；
- Zone 版本；
- 邮编版本；
- 燃油版本；
- 汇率版本；
- 舍入版本；
- 自定义函数版本。

### 3.3 配置优先，但不追求绝对零代码

能力分为四层：

| 层级 | 适用范围 | 建议占比 | 维护角色 |
|---|---|---:|---|
| 标准价表与标准策略 | 重量段、Zone、体积系数、燃油、附加费 | 65% | 运营 |
| 参数化合同差异 | 客户系数、费率、费用启停、继承覆盖 | 20% | 运营/产品 |
| 决策表 | 多条件匹配、地区差异、特殊合同条款 | 10% | 高级运营/产品 |
| 受控函数插件 | 极少数特殊算法 | 5% | 研发 |

业务人员不得直接执行任意 JavaScript、Python、SQL 或网络调用。

### 3.4 成本、售价、应收和应付分离

不能只保存一个 `freight_amount`。必须区分：

- 预估采购成本；
- 承运商实际成本；
- 标准销售价；
- 客户合同销售价；
- 客户预报价；
- 客户最终应收；
- 承运商应付；
- 补扣款；
- 冲销款；
- 周期返利；
- 汇兑差异。

### 3.5 结果账本化

计算结果必须拆成不可变费用行，并能够追溯到：

- 输入字段；
- 测量来源；
- 命中策略；
- 价卡条目；
- 燃油指数；
- 汇率；
- 舍入过程；
- 规则版本；
- 自定义函数版本。

### 3.6 单票计费与周期结算分离

单票计费不能依赖月累计业务状态。

- `Transactional Rating Engine`：处理单票确定性费用；
- `Accrual & Settlement Engine`：处理月度返利、货量阶梯、最低承诺和周期调整。

## 5. 领域边界

### 5.1 Product & Eligibility：渠道产品与准入

负责回答：

> 这票货是否可以使用这个渠道？

核心对象：

```text
Carrier
CarrierAccount
ServiceProduct
ServiceRoute
OriginWarehouse
DestinationCoverage
ServiceConstraint
ProductCapability
RestrictedCommodityRule
```

产品准入规则包括：

- 起运国家和仓库；
- 目的国家和邮编；
- 住宅、商业、PO Box；
- 最低和最高重量；
- 最长边、次长边、周长和体积限制；
- 单件、多件限制；
- 禁限运品；
- 是否支持签名、成人签名；
- 是否支持退件、拦截、改址；
- 渠道生效和停用时间。

准入检查应先于价格计算。不满足条件时返回结构化原因：

```json
{
  "eligible": false,
  "reason_code": "MAX_LENGTH_EXCEEDED",
  "message": "最长边超过渠道允许范围",
  "actual": {"value": 112, "unit": "IN"},
  "limit": {"value": 108, "unit": "IN"}
}
```

### 5.2 Pricing Catalog：价格目录

负责管理：

- 基础运价；
- 附加费价格；
- 燃油指数；
- 汇率；
- Zone 和邮编区域；
- 承运商费用代码映射；
- 生效期和版本。

### 5.3 Contract Policy：客户合同策略

负责回答：

> 对当前客户、合同和渠道，应使用哪些价卡和策略？

包括：

- 客户合同；
- 产品授权；
- 采购价绑定；
- 销售价绑定；
- 计费重量策略；
- 舍入策略；
- 燃油策略；
- 费用启停；
- 费用加价或折扣；
- 最低毛利保护；
- 报价有效期；
- 生效时间语义。

### 5.4 Rating Runtime：单票确定性计费

负责：

- 解析合同；
- 加载编译计划；

## 7. 有限价表家族

不采用运行时高度动态的通用 EAV 多维矩阵，而采用有限价表家族。

### 7.1 WEIGHT_ZONE

适用于 UPS、FedEx 等：

```text
计费重量 × Zone → 金额
```

### 7.2 COUNTRY_WEIGHT

```text
目的国家 × 计费重量段 → 金额
```

### 7.3 REGION_WEIGHT

```text
国家组/区域组 × 计费重量段 → 金额
```

### 7.4 FIRST_CONTINUE

```text
首重价格 + 向上取整(超出重量 / 续重单位) × 续重价格
```

### 7.5 PER_UNIT

```text
数量 × 单位价格
```

数量可以是 KG、LB、件、票、托、天或申报价值。

### 7.6 PROGRESSIVE_TIER

累进阶梯：

```text
0–5 KG部分 × 20
5–10 KG部分 × 18
10 KG以上部分 × 16
```

### 7.7 FLAT

固定金额。

### 7.8 INDEXED

基于外部版本化指数：

- 燃油指数；
- 汇率；
- 航空旺季指数。

### 7.9 CUSTOM_LOOKUP

用于少量无法归入标准家族的特殊价表，但必须有固定输入 Schema 和发布时校验。

价表在发布时应编译为专门的查找结构，避免运行时动态拼装复杂 SQL。

## 8. 客户合同继承与覆盖

### 8.1 分层结构

```text
Carrier Standard Plan
        ↓
Platform Buy Plan
        ↓
Standard Sell Plan
        ↓
Customer Contract Plan
        ↓
Customer Amendment
```

### 8.2 差异化保存

客户只保存与上层不同的部分，不复制整套方案。

```text
平台标准销售方案
├── 体积除数 5000
├── 住宅费 2.5 USD
├── 燃油官方费率 × 80%
└── 标准销售价卡 V3

客户 A 修订
└── 住宅费豁免

客户 B 修订
└── 体积除数 6000

客户 C 修订
├── 替换基础销售价卡
└── 燃油官方费率 × 70%
```

### 8.3 明确合并语义

| 对象 | 合并方式 |
|---|---|
| 参数 | 子层覆盖父层 |
| 基础价卡 | 继承或整体替换 |
| 费用规则 | 新增、禁用、替换 |
| 决策表 | 追加、替换指定规则 |
| 重量策略 | 参数覆盖或策略替换 |
| 舍入策略 | 指定字段覆盖 |
| 燃油策略 | 覆盖 |
| 周期条款 | 独立追加 |

不得使用无业务语义的通用 JSON Merge。

### 8.4 规则匹配顺序

先按特异度排序：

```text
客户 + 合同 + 产品 + 仓库 + 目的区域
>
客户 + 合同 + 产品
>
客户 + 产品
>
客户
>
产品 + 仓库
>
产品
>
承运商默认
>
平台默认
```

同一特异度再比较：

1. 显式优先级；
2. 生效时间；
3. 版本；
4. 发布顺序。

完全相同优先级且互斥的规则必须在发布阶段报错。

## 9. 测量事实模型

国际小包不能只保存一个重量和一组尺寸。

### 9.1 Measurement Fact

```text
MeasurementFact
├── measurement_id
├── shipment_id
├── package_id
├── source_type
├── source_system
├── measured_at
├── actual_weight
├── length
├── width
├── height
├── unit
├── equipment_id
├── confidence
├── evidence_uri
├── supersedes_measurement_id
└── status
```

### 9.2 来源类型

```text
CUSTOMER_DECLARED
ORDER_IMPORTED
WAREHOUSE_MANUAL
WAREHOUSE_DWS
CARRIER_SCAN
CARRIER_INVOICE
MANUAL_AUDIT
```

### 9.3 按计算目的选择来源

| 计算目的 | 优先测量来源 |
|---|---|
| QUOTE | 客户申报 |
| ESTIMATED_COST | 仓库测量，其次申报 |
| ACTUAL_COST | 承运商扫描或承运商账单 |
| CUSTOMER_BILLING | 合同约定的计费来源 |
| DISPUTE_REVIEW | 人工复核或证据确认 |

选择结果必须被写入计算快照，不能在历史重算时自动切换到最新测量数据。

## 10. 计费重量策略

### 10.1 Weight Profile

```yaml
code: UPS_GROUND_CUSTOMER_A
version: 3

standard_unit:
  dimension: IN
  weight: LB

actual_weight:
  selection_policy: WAREHOUSE_THEN_DECLARED

volumetric_weight:
  method: DIVISOR
  divisor: 250

billable_weight:
  method: MAX
  candidates:
    - actual_weight
    - volumetric_weight
    - conditional_minimum_weight

rounding:
  stage: AFTER_COMPARISON
  mode: CEILING
  increment: 1
  unit: LB
```

### 10.2 体积重方法

```text
DIVISOR
长 × 宽 × 高 ÷ 除数

DENSITY
体积 × 约定密度

FIXED_FACTOR
标准体积重 × 调整系数

CUSTOM_FUNCTION
受控自定义函数
```

### 10.3 计费重量比较策略

```text
MAX
取实重、体积重和条件最低重量中的最大值

ACTUAL_ONLY
只使用实重

VOLUMETRIC_ONLY
只使用体积重

THRESHOLD_MAX
体积重与实重比例达到阈值后才使用体积重

PARTIAL_DIMENSIONAL
只收取泡重差额的一定比例

BLENDED
实重和体积重按权重组合
```

### 10.4 示例：部分泡重

```text
当 体积重 / 实重 <= 1.5：
    计费重量 = 实重

当 体积重 / 实重 > 1.5：
    计费重量 = 实重 + (体积重 - 实重) × 70%
```

这类策略优先通过标准模板和参数表达，而不是创建客户专属代码。

### 10.5 条件最低计费重量

支持：

- 默认最低计费重量；
- 超尺寸最低重量；
- 超大包裹最低重量；
- 渠道最低重量；
- 客户合同最低重量。

## 11. 舍入策略

舍入规则必须独立建模。

```yaml
weight_rounding:
  stage: AFTER_COMPARISON
  mode: CEILING
  increment: 1
  unit: LB

component_amount_rounding:
  mode: HALF_UP
  scale: 4

invoice_line_rounding:
  mode: HALF_UP
  scale: 2
```

需要明确：

- 实重是否先舍入；
- 体积重是否先舍入；
- 比较前还是比较后舍入；
- 重量增量是 0.1 KG、0.5 KG、1 KG 或 1 LB；
- 单项费用何时舍入；
- 票级金额何时舍入；
- 汇率转换前还是转换后舍入；
- 每件、每票还是汇总后舍入。

系统中的金额统一使用 Decimal，禁止使用二进制浮点数。

## 17. 单票计费与周期性结算

### 17.1 Transactional Rating Engine

处理单票可立即确定的费用：

- 基础运费；
- 包裹级附加费；
- 票级附加费；
- 燃油；
- 单票折扣；
- 最低收费；
- 封顶；
- 汇率；
- 舍入。

### 17.2 Accrual & Settlement Engine

处理依赖周期累计的数据：

- 月度货量返利；
- 月度重量阶梯；
- 月度最低消费；
- 最低承诺补差；
- 承运商返点；
- 客户返点；
- 周期佣金；
- 账期奖励；
- 汇总调整。

### 17.3 分离原因

如果实时计费直接读取月累计状态，将产生：

- 并发竞争；
- 订单顺序影响价格；
- 历史重算不稳定；
- 结算期间结果变化；
- 对账困难。

因此单票账本先记录基础事实，周期结算再生成独立调整账本。

## 29. 幂等、并发与一致性

### 29.1 幂等

计费请求包含：

```text
idempotency_key
request_hash
calculation_purpose
```

相同幂等键和相同请求哈希返回原结果；相同幂等键但请求不同应报冲突。

### 29.2 版本一致性

计算开始后，所有版本必须冻结，不能在执行中切换到新价卡或新燃油率。

### 29.3 发布一致性

价卡发布使用原子切换：

```text
旧编译计划 ACTIVE
新编译计划 READY
→ 原子切换
旧计划 RETIRED
```

### 29.4 历史结果

历史账本永远引用当时使用的版本，不自动迁移。

### 32.1 Rating Engine 负责

- 单票确定性计算；

- 计费重量；
- Zone；
- 基础价；
- 附加费；
- 燃油；
- 折扣；
- 舍入；
- 费用账本。

### 32.2 EER/工作流负责

```text
价卡上传
→ 解析
→ 歧义确认
→ 测试
→ 审批
→ 定时发布
```

```text
承运商账单到达
→ 匹配
→ 差异检测
→ 自动判责
→ 人工复核
→ 补扣款
→ 争议关闭
```

```text
燃油指数更新
→ 影响分析
→ 新版本生成
→ 审批
→ 发布
```

### 32.3 禁止边界

不能让 EER、Agent 或 LLM 在每票计费时临时推理：

- 是否收费；
- 应收多少钱；
- 使用哪个公式；
- 是否覆盖合同。

AI 可以辅助识别价卡和发现异常，但最终规则必须经过结构化确认、测试和审批。

## 36. 主要风险与控制措施

### 36.1 过度抽象

**风险：** 尚未验证业务，就建设万能平台。  
**控制：** 第一阶段只实现有限价表家族和标准计费策略。

### 36.2 配置爆炸

**风险：** 每个客户复制整套规则。  
**控制：** 分层继承、参数覆盖和费用启停。

### 36.3 决策表失控

**风险：** 大量决策表成为另一种代码。  
**控制：** 优先使用标准策略和参数，决策表只处理复杂匹配。

### 36.4 脚本失控

**风险：** 任意脚本破坏安全、性能和确定性。  
**控制：** 只允许受控函数注册。

### 36.5 价卡歧义

**风险：** Excel 备注不清导致错误计费。  
**控制：** 歧义项阻止发布，必须人工确认。

### 36.6 历史不可重现

**风险：** 重算自动使用最新价卡。  
**控制：** 冻结输入和全部规则版本。

### 36.7 对账无法自动化

**风险：** 承运商代码和内部费用不统一。  
**控制：** 建立 Canonical Charge Code 和映射版本。

### 36.8 周期规则污染实时计费

**风险：** 月累计导致实时结果不稳定。  
**控制：** 单票 Rating 和周期 Settlement 分离。

## 37. 最终产品定位

本系统不是一个简单的运费计算模块，也不是一个通用规则引擎。

最终定位是：

> **国际小包定价基础设施：以渠道产品和客户合同为业务入口，以版本化价卡和策略为配置基础，以确定性 Rating Runtime 为计算内核，以不可变 Charge Ledger 为事实记录，以周期结算和承运商对账形成完整商业闭环。**

它能够覆盖：

- UPS、FedEx、USPS 等海外尾程；
- 国际专线；
- 国际快递；
- 国家和区域重量价；
- 首重续重；
- 阶梯价；
- 客户差异化体积重；
- 住宅、偏远、超重和超尺寸；
- 燃油；
- 采购成本和客户售价；
- 多币种；
- 多段成本；
- 月度返利；
- 承运商复称；
- 账单补扣和争议。

## 39. 最终决策建议

本方案已经具备进入下一阶段的条件，建议冻结以下核心原则：

1. 不建设万能规则引擎；
2. 固定宏观计费阶段；
3. 阶段内采用受控费用依赖图；
4. 价表采用有限家族；
5. 客户差异采用继承和参数覆盖；
6. 单票计费与周期结算分离；
7. 测量数据建模为版本化事实；
8. 成本、售价、应收和应付分离；
9. 所有计算结果进入不可变费用账本；
10. 承运商对账是平台核心闭环，而不是外围功能；
11. EER 负责编排，Rating Engine 负责确定性计算；
12. AI 只辅助识别和分析，不直接决定正式价格。

基于这些原则，可以正式进入：

```text
领域模型冻结
→ 数据模型设计
→ API 合同设计
→ Rating Runtime 技术设计
→ MVP 开发
```
