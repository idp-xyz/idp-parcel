# 0. 文档控制与 V1.2 一致性审查

## 0.1 文档目标

本文件将 V1.2 总体方案中的业务能力进一步转换为可实施的领域模型，明确：

1. 限界上下文及其职责；
2. 聚合根、实体、值对象和领域服务；
3. 每个聚合的业务不变量；
4. 命令、状态机和领域事件；
5. 上下文之间的依赖、数据权属和集成契约；
6. 计算结果、费用认定和财务费用的严格分层；
7. 规则版本、业务时间和系统时间的语义；
8. 单票计费、周期结算和承运商对账的事务边界；
9. 研发实现中不得突破的领域约束。

本文件不定义最终数据库 DDL、OpenAPI 字段级规范、缓存实现或代码包结构；这些内容应在后续专项文档中冻结。

## 0.2 与 V1.2 的权威关系

两份文档的关系如下：

```text
V1.2 总体解决方案
定义：系统定位、业务边界、架构原则和核心语义
        ↓
本领域模型 V1.0.1
定义：限界上下文、聚合、不变量、状态和领域协作
        ↓
后续专项设计
计算语义规范 / 数据模型 / API Contract / Runtime 技术设计
```

当两份文档出现表述差异时，遵循以下规则：

1. 系统范围、价格域分离、结果三层模型、确定性和不可变版本等架构决策，以 V1.2 为准；
2. 聚合边界、命令、事件、不变量和上下文协作，以本文件为准；
3. 本文件不得隐式改变 V1.2 已冻结的核心语义；
4. 若未来确需改变 V1.2 的架构决策，必须先发布 V1.2 的正式变更记录，再更新本领域模型。

## 0.3 V1.2 前置审查结论

本领域模型编写前，对 V1.2 完成了以下审查。

### 0.3.1 已确认自洽的核心决策

以下决策保持不变并直接继承：

- 本项目是独立国际小包计费与结算系统；
- 不建设万能规则引擎；
- 采购定价和销售定价是两个独立价格域；
- 销售价引用采购结果时必须显式声明，不允许对象继承；
- Rating Evaluation、Charge Assessment 和 Financial Charge Ledger 必须分层；
- Scope、Basis 和 Method 必须分离；
- 物理测量事实与承运商计费认定事实必须分离；
- Geometry Profile、Weight Profile 和 Rating Aggregation Profile 必须独立；
- 单票计费与周期结算必须分离；
- 正式规则版本不可变；
- 历史计算必须冻结输入与全部依赖版本；
- 承运商对账、Credit Note、Debit Note 和差异调整属于核心业务闭环；
- 多租户、采购成本保护和职责分离属于生产环境硬约束。

### 0.3.2 本文件统一的术语

为避免 V1.2 中技术组件名称与领域名称混用，本文件统一如下：

| 统一术语 | 含义 | 不再作为同义词使用的表述 |
|---|---|---|
| PricingPlan | 一个价格方案的业务身份与版本谱系 | RateTable、单张费率表 |
| PricingPlanVersion | 不可变的正式价格方案版本 | 可修改价卡 |
| RateTable | PricingPlanVersion 引用的费率查找表 | PricingPlan 本身 |
| Rating | 限界上下文 | Rating Runtime 作为上下文名称 |
| Rating Runtime | Rating 上下文中的确定性执行组件 | 工作流引擎 |
| RatingEvaluation | 纯计算结果 | 财务账本、应收应付 |
| ChargeAssessment | 业务费用认定 | 纯报价结果、总账凭证 |
| FinancialChargeDocument | 财务费用子账文档或向 ERP 提交的入账文档 | 企业总账 |
| MeasurementFact | 物理测量事实 | 承运商账单计费重量 |
| CarrierAssessmentFact | 承运商对重量、Zone、地址和费用的计费认定 | 物理测量事实 |
| CustomerPricingContract | 计费合同与商业策略绑定 | CRM 法律合同全文 |
| PricingRelease | 一组可原子发布的价格与策略版本 | 任意运行时配置 |

### 0.3.3 对 V1.2 的模型化补充

本文件新增但不改变 V1.2 语义的内容：

- 明确“业务身份聚合”和“不可变版本聚合”的双层模式；
- 明确每个上下文的聚合事务边界；
- 明确分类事实必须携带策略版本与证据；
- 明确 Quote 接受不自动等同于费用认定；
- 明确 ChargeAssessment 最终确认后不可直接修改；
- 明确 Financial Charging 既支持平台子账模式，也支持 ERP 入账指令模式；
- 明确大型价表和大型账单采用逻辑聚合，不要求单次加载全部明细；
- 明确领域事件和跨系统集成事件相互分离。

### 0.3.4 V1.0.1 终审修订结论

终审在不改变 V1.2 核心架构决策的前提下，进一步消除了可能导致研发分歧的语义缺口：

- CalculationPurpose 与 V1.2 枚举完全对齐，明确 `RECONCILIATION` 是上下文而非计算目的；
- MeasurementFact 选择与 CarrierAssessmentFact 解析彻底分离；
- ChargeAssessment、FinancialChargeDocument、SettlementRun、SettlementStatement、CarrierInvoice 和 ReconciliationCase 状态机补齐闭环；
- 金额统一采用“非负金额 + 业务方向/费用效果”表达，避免 Credit、Reversal 与负数双重表达；
- Settlement 明确单次运行只能选择一个权威输入层，防止 Assessment 与 Financial Line 重复累计；
- 承运商原始账单行与标准化费用行分离，映射修订不覆盖原始数据；
- PricingRelease 成为生产激活的唯一入口，禁止公开命令绕过发布包直接激活版本；
- 双时间环境下的 `current_version_id` 只作为运行便利指针，历史解析不得依赖该指针；
- BUY→SELL 显式引用增加无环约束和来源 Evaluation 固定要求；
- Tenant 本位币改为引用版本化 CurrencyPolicy，不在 Tenant 根上直接覆盖历史配置。

# 第一部分：领域愿景、边界与统一语言

## 1. 领域愿景

平台的核心使命是：

> 对给定客户、合同、渠道产品、业务时间和包裹事实，使用可追溯的正式版本，产生确定、可解释、可回放的成本或销售价格，并将实际业务费用、财务费用、周期调整和承运商差异形成闭环。

核心价值链：

```text
产品是否可承运
        ↓
选择正确合同与价格方案
        ↓
冻结输入与事实
        ↓
确定性计算
        ↓
形成报价或预估结果
        ↓
业务费用认定
        ↓
财务应收应付
        ↓
承运商账单复核与周期结算
```

## 2. 领域范围

### 2.1 范围内

- 承运商、账号、服务产品和路由；
- 渠道重量、尺寸、地址和禁限运准入；
- 公布价、采购净价、销售价和内部价；
- 重量、Zone、国家、区域、首重续重和阶梯价；
- 体积重、计费重量、尺寸边界和多件聚合；
- 基础费、附加费、燃油、折扣、最低收费和封顶；
- 正式报价及价格锁定；
- 实际成本和客户收费认定；
- 财务费用子账或 ERP 入账指令；
- 月度返利、最低承诺和周期调整；
- 承运商账单、复称、复测、贷项、借项、差异和争议；
- 价格导入、测试、审批、发布、回滚和追溯影响分析。

### 2.2 范围外

- 订单履约主状态；
- 仓内作业和库存；
- 运输轨迹主数据；
- CRM 客户主档；
- 企业总账和法定会计；
- 通用税务引擎；
- 通用工作流平台；
- 任意行业规则执行平台；
- 非确定性模型自动决定正式价格。

## 5. 领域模型总原则

1. **业务身份与版本分离：** 可持续存在的对象使用身份聚合；正式规则使用不可变版本聚合。
2. **聚合内强一致，聚合间最终一致：** 不通过跨聚合数据库事务维持业务一致性。
3. **正式版本不可修改：** 发布后只能新建版本、退休版本或创建修订关系。
4. **计算是纯函数式语义：** 同输入快照和同版本引用必须得到同结果。
5. **计算不等于收费：** RatingEvaluation 不得直接形成应收应付。
6. **收费不等于总账：** ChargeAssessment 必须经过财务入账边界。
7. **事实与认定分离：** 物理测量不能被承运商账单认定覆盖。
8. **报价接受不自动收费：** 是否产生费用认定由业务事件和合同条款决定。
9. **金额、数量和单位为强类型：** 禁止使用无单位 Decimal 和二进制浮点数。
10. **所有关键决定可解释：** 每个费用行必须追溯到基数、方法、规则和版本。

## 8. Context Map 模式

| 上游 | 下游 | 关系模式 | 说明 |
|---|---|---|---|
| Product & Eligibility | Rating | Published Language | 发布产品版本、限制和准入契约 |

| Charge Assessment | Financial Charging | Customer/Supplier | 只有已最终确认的认定可申请入账 |

| Charge Assessment / Financial Charging | Accrual & Settlement | Published Language | 周期规则必须选择唯一权威输入层，禁止重复累计同一经济费用 |

| Pricing Governance | Pricing Catalog | Conformist + Approval | Governance 管生命周期，不改变价格业务语义 |

## 9. 外部系统集成边界

### 9.1 CRM / Customer Center

提供：

- tenant、organization、customer 标识；
- 客户法律主体和状态；
- 合同主体引用。

平台不复制 CRM 全量客户模型，只保存计费所需引用和快照。

# 第三部分：共享内核和值对象

## 11. 共享内核边界

共享内核仅包含跨上下文必须一致的稳定类型，不包含业务聚合或可变业务规则。

允许进入共享内核：

- 标识类型；
- Money、Quantity、Unit；
- 时间区间；
- 版本引用；
- 租户与组织引用；
- 通用事件信封；
- 错误和验证结果结构。

禁止进入共享内核：

- CustomerContract；
- PricingPlan；
- ChargeDefinition；
- RatingEvaluation；
- 承运商专属规则；
- 可变业务枚举。

## 12. 标识值对象

每个标识必须为独立强类型，禁止使用一个通用字符串 ID 贯穿全部领域。

```text

SettlementRunId
CarrierInvoiceId
ReconciliationCaseId
PricingReleaseId
```

不变量：

- 标识创建后不可修改；
- 外部标识必须与内部标识分离；
- 跨租户不得复用内部业务标识；
- 对外 API 不暴露数据库自增主键。

## 13. Money

```text
Money
├── amount: Decimal
└── currency: ISO-4217 CurrencyCode
```

不变量：

1. amount 使用 Decimal；
2. 加减必须币种相同；
3. 不允许隐式汇率转换；
4. 舍入必须由 RoundingPolicy 显式执行；
5. 正式 Evaluation、Assessment 和 Financial Line 中的 `Money.amount` 必须为非负数；
6. 增加、扣减、贷项和冲销通过 `ChargeEffect`、payer/payee 与文档类型表达，不以负数和文档方向双重表达；
7. 分析差异使用独立的 `SignedMoneyDelta`，不得把差异值直接当作正式费用金额。

```text
ChargeEffect: ADD / DEDUCT
SignedMoneyDelta: signed Decimal + CurrencyCode
```

## 14. Quantity

```text
Quantity<TDimension>
├── value: Decimal
├── unit: UnitCode
└── dimension: MASS / LENGTH / VOLUME / COUNT / TIME
```

不变量：

- 不同维度不能直接运算；
- 同维度运算必须先显式转换单位；
- 物理测量通常不得为负；
- 正式费用数量必须为非负；冲销、贷项和扣减由 ChargeEffect 表达；分析差异使用 SignedQuantityDelta。

## 16. TimeRange 与 BitemporalRange

```text

├── valid_from
└── valid_to

SystemTimeRange
├── recorded_at
└── superseded_at
```

不变量：

- 同一业务身份的 ACTIVE 版本在相同适用范围内不得发生未解决重叠；
- 追溯版本不得覆盖原系统记录时间；
- 历史计算按当时冻结的版本引用回放，而非重新解析“当前有效版本”。

## 17. VersionRef

```text
VersionRef
├── aggregate_type
├── aggregate_id
├── version_id
├── semantic_version
├── content_hash
└── valid_time
```

`content_hash` 用于保证发布工件、缓存和历史回放引用的内容一致。

### 17.1 版本便利指针语义

聚合中的 `current_version_id`、`latest_version_id` 等字段只是运行和管理界面的便利指针：

- `latest_version_id` 表示最新创建版本，不代表当前有效；
- `current_version_id` 表示平台“当前系统时间 + 默认业务时间”下的便利指针；
- 历史计算、追溯查询、未来生效查询和双时间解析不得依赖这些指针；
- 权威解析必须使用业务时间、系统知识时间、适用范围和不可变 VersionRef；
- 指针失效不得影响历史回放。

### 17.2 FormalVersionEnvelope

所有正式规则、产品、合同、价表、费用定义、分类集合和周期规则版本，无论后续结构图是否省略重复字段，都必须包含统一版本信封：

```text
├── semantic_version
├── ownership_scope_snapshot
├── valid_time
├── system_time
├── content_hash
├── status
└── supersedes_version_id（可选）
```

不变量：

- `ownership_scope_snapshot` 必须为 GLOBAL、TENANT 或 ORGANIZATION，缺失不等同 GLOBAL；
- valid time 与 system time 必须同时可查询；
- ACTIVE 后业务内容不可修改；
- 追溯修订创建新版本并通过 supersedes 关联；
- RatingEvaluation 的 version manifest 必须引用实际执行版本的 content hash；
- 实现层应将 tenant/ownership 作为物理分区和授权条件，即使版本可通过父聚合推导归属。

2. COST_PLUS、TARGET_MARGIN 和 PASS_THROUGH_WITH_OVERRIDE 只能出现在允许引用采购结果的角色；
3. 价格方案引用图必须无环，BUY 不得引用 SELL，SELL 不得间接回指自身；
4. 引用采购 RatingEvaluation 时必须声明：
   - source price role；
   - source charge codes；
   - source evaluation id/version policy；
   - transformation order；
5. ACTIVE 后不可修改；
6. 所有绑定的 RateTableVersion 和 ChargeDefinitionVersion 必须已通过校验；
7. 有效期范围内不得存在无法解析的同等优先级冲突；
8. currency 必须与直接费率一致，跨币种必须显式绑定 CurrencyPolicy；
9. 生产环境的 ACTIVE 切换必须由受治理的 PricingRelease 激活流程完成。

状态机：

```text
DRAFT → VALIDATED → TESTED → APPROVED → SCHEDULED → ACTIVE → RETIRED
  ├──────────────→ REJECTED
  └──────────────→ CANCELLED（仅生效前）
```

## 28.1 职责

# 33. 即时报价流程

## 33.1 目标

对客户提交的运单和包裹信息，返回可承运产品、销售价格、有效期和完整解释，但不形成业务收费或财务债权。

## 33.2 流程

```text
OMS/前端提交报价请求
        ↓
Facts: 创建 RatingInputSnapshot
        ↓
Product: 评估可承运产品
        ↓
Contract: 解析客户合同策略
        ↓
Facts: 选择测量事实并生成分类事实
        ↓
Rating: 执行 SELL RatingEvaluation
        ↓
Quote: 创建并 OFFER Quote
        ↓
返回价格、有效期、限制与解释
```

## 33.3 一致性规则

- Snapshot 创建后不可修改；
- 准入失败的产品不得进入计费；
- Quote 必须引用 COMPLETED SELL/PUBLIC Evaluation；
- Quote 创建失败不影响已完成 Evaluation；
- Quote OFFERED 事件通过 Outbox 发布；
- 未被接受的 Quote 永不进入 Financial Charging。

## 33.4 失败处理

| 失败点 | 处理 |
|---|---|
| 输入无效 | 不创建正式 Snapshot 或创建 REJECTED 请求诊断 |
| 无可承运产品 | 返回结构化 EligibilityFailure |
| 无合同策略 | 返回 NO_APPLICABLE_POLICY |
| 无价格条目 | 返回 NO_RATE_FOUND，并进入价卡治理监控 |
| 规则冲突 | 返回 AMBIGUOUS_POLICY，不随机选取 |
| Quote 创建失败 | Evaluation 保留，可幂等重试 Quote 创建 |

## 34.3 强制约束

- SELL Evaluation 不能直接读取可变的“当前成本”；
- SELL 必须引用具体 BUY Evaluation；
- BUY 后续被新版本重算，不自动改变既有 SELL；
- 毛利分析是 BUY 与 SELL 两个结果的查询投影，不是一个聚合字段；
- 采购成本权限与销售价格权限独立。

---

# 35. 报价接受与履约重定价流程

```text
Quote OFFERED
        ↓ 客户接受
Quote ACCEPTED
        ↓
根据 PriceLockPolicy 判断
        ├── LOCK_ON_ACCEPTANCE：后续引用原 Evaluation
        ├── REPRICE_ON_LABEL_CREATION：标签创建时重算
        ├── REPRICE_ON_WAREHOUSE_SHIP：出库时重算
        └── REPRICE_ON_CARRIER_ACCEPTANCE：交承运商时重算
```

## 35.1 重要边界

- QuoteAccepted 只表示商业承诺，不表示运输已发生；
- 重量、尺寸、地址变化是否导致 Quote 失效由合同策略决定；
- 重报价必须创建新的 RatingEvaluation 和 QuoteVersion；
- 不得覆盖原报价版本；
- 原报价与实际费用差异后续由 Charge Assessment 处理。

---

# 36. 实际客户收费认定流程

## 36.1 典型流程

```text
Shipment/Package 实际履约事实到达
        ↓
Facts: 选择合同约定的最终测量和分类
        ↓
Rating: CUSTOMER_BILLING Evaluation
        ↓
Charge Assessment: 创建客户收费候选
        ↓
应用报价锁定、补扣和容差策略
        ↓
人工或自动审核
        ↓
ChargeAssessment FINALIZED
        ↓
Financial Charging: 形成应收文档或 ERP 入账指令
```

## 36.2 不变量

- Quote 金额不能直接复制为应收，必须经 Assessment；
- 若合同锁定价格，Assessment 需明确锁定费用与可变费用；
- 复称、地址修正和超尺寸后收费必须保存证据；
- 客户补扣不得超过合同允许范围；
- 最终应收与原报价的差异必须有 reason code。

---

# 37. 承运商实际成本认定流程

```text
Carrier API 或 Invoice 到达
        ↓
Reconciliation: 标准化原始账单
        ↓
Facts: 生成 CarrierAssessmentFact
        ↓
Rating: 可选执行 ACTUAL_COST 重算
        ↓
Reconciliation: 比较预估、实际和已认定成本
        ↓
Charge Assessment: FINALIZE BUY_COST_ASSESSMENT
        ↓
Financial Charging: 形成应付
```

## 37.1 语义约束

- CarrierAssessmentFact 不覆盖 MeasurementFact；
- 承运商账单金额与系统重算金额都保留；
- 账单可被接受，不代表平台认可其物理测量为真实事实；
- 争议中的费用可以暂挂，不得静默入账；
- Credit Note 必须形成贷项 Assessment 和财务调整。

---

# 38. 承运商对账与客户补扣流程

```text
CarrierInvoiceLine
        ↓ 匹配
Shipment / Package / Expected Charge
        ↓
ReconciliationDifference
        ↓
责任判断
        ├── ACCEPT_CARRIER
        ├── CHARGE_CUSTOMER
        ├── PLATFORM_ABSORBS
        ├── REJECT_CARRIER
        └── OPEN_DISPUTE
```

## 38.1 CHARGE_CUSTOMER

```text
ReconciliationCase RESOLVED
        ↓
创建 Supplemental Customer ChargeAssessment
        ↓
合同补扣规则校验
        ↓
FINALIZED
        ↓
FinancialChargeDocument / 客户账单
```

## 38.2 PLATFORM_ABSORBS

- 形成 BUY 成本认定；
- 不形成客户补扣；
- 毛利投影体现损失；
- 可生成内部原因分析标签。

## 38.3 OPEN_DISPUTE

- 创建 DisputeCase；
- 对应差异保持未决；
- 是否暂估应付由财务政策决定；
- 承运商正式 Credit Note 到达后再完成账务闭环。

---

# 39. 周期结算流程

```text
结算期结束
        ↓
SettlementRun 按规则选择唯一输入层：已冻结的 Assessment facts 或 Financial facts
        ↓
冻结 input manifest
        ↓
执行返利、阶梯、最低承诺和佣金规则
        ↓
生成 SettlementStatement
        ↓
审批
        ↓
生成独立 Adjustment ChargeAssessment
        ↓
进入 Financial Charging
```

## 39.1 规则

- 不修改原单票 Evaluation 或 Assessment；
- 结算重跑生成新 Run 并 supersede 原结果；
- 结算输入 cutoff 明确；
- 延迟费用进入哪个周期必须有政策；
- 分摊明细必须可回溯到原业务费用。

---

# 40. 追溯调价流程

```text
8月10日收到承运商通知
valid_from = 8月1日
recorded_at = 8月10日
        ↓
Pricing Governance 创建追溯 ChangeSet
        ↓
影响分析识别 8月1日至8月10日的 Evaluation/Assessment
        ↓
发布新 PricingPlanVersion
        ↓
按政策执行 Simulation / Replay
        ↓
需要时创建补充或贷项 ChargeAssessment
```

不允许：

- 覆盖原 PricingPlanVersion；
- 直接修改历史 RatingEvaluation；
- 静默修改已经 POSTED 的财务文档。

---

# 41. 价格发布流程

```text
ImportJob / 人工建模
        ↓
创建候选正式版本
        ↓
PricingChangeSet
        ↓
Schema/区间/单位/冲突校验
        ↓
Golden Case
        ↓
历史影响分析
        ↓
职责分离审批
        ↓
PricingRelease
        ↓
构建 CompiledPricingPlan
        ↓
原子切换 ACTIVE PricingRelease manifest / pointer
```

发布失败时：

- 旧 release 继续服务；
- 新 release 状态 FAILED；
- 不允许部分激活；
- 修复后创建新 release 或重新执行尚未激活的同一工件。

# 第六部分：事务、一致性、事件与并发

# 42. 聚合事务边界

## 42.1 原则

- 一个命令事务只修改一个聚合根；
- 跨聚合流程由应用服务、Saga/Process Manager 或事件驱动协调；
- 不使用跨上下文数据库外键维持业务一致性；
- 引用其他上下文对象时保存强类型 ID 和 VersionRef；
- 历史不可变对象可以被多个上下文安全引用。

## 42.2 典型事务

| 命令 | 单事务聚合 |
|---|---|
| Validate/Approve PricingPlanVersion | PricingPlanVersion |
| Activate PricingRelease | PricingRelease |
| Capture RatingInputSnapshot | RatingInputSnapshot |
| Complete RatingEvaluation | RatingEvaluation |
| Accept Quote | Quote |
| Finalize ChargeAssessment | ChargeAssessment |
| Post FinancialChargeDocument | FinancialChargeDocument |
| Seal CarrierInvoice | CarrierInvoice |
| Resolve ReconciliationCase | ReconciliationCase |
| Approve SettlementStatement | SettlementStatement |

## 42.3 跨聚合流程示例

`ChargeAssessmentFinalized` 后：

1. Outbox 发布事件；
2. Financial Charging Inbox 幂等接收；
3. 创建 FinancialChargeDocument；
4. 创建失败不回滚 Assessment；
5. 通过重试和待办恢复。

---

# 43. 一致性模型

## 43.1 强一致

必须在聚合内强一致：

- 状态转换；
- 版本不可变；
- Assessment 行与总额；
- Quote 当前版本；
- Financial 文档余额；
- Invoice seal 与总额；
- PricingRelease manifest 与 ACTIVE release pointer。

## 43.2 最终一致

允许最终一致：

- PricingRelease 原子激活后缓存刷新；
- QuoteAccepted 到 OMS；
- Assessment 到 Financial Charging；
- Financial posting 到 ERP；
- Reconciliation 结果到客户补扣；
- Settlement 结果到 Assessment。

## 43.3 不允许的伪一致性

- 用数据库触发器跨上下文修改业务状态；
- 用共享表让多个上下文直接写同一记录；
- 在 Rating 热路径同步调用 ERP；
- 通过“读取最新配置”补偿版本冻结缺失。

---

# 44. 幂等

## 44.1 命令幂等

所有外部写命令至少包含：

```text
idempotency_key
request_hash
tenant_id
command_type
```

规则：

- 相同 key + 相同 hash：返回原结果；
- 相同 key + 不同 hash：IDEMPOTENCY_CONFLICT；
- 幂等记录必须覆盖业务结果，不只覆盖 HTTP 响应。

## 44.2 导入幂等

CarrierInvoice 使用：

```text
carrier
carrier_account
invoice_number
invoice_revision
source_file_hash
```

MeasurementFact 使用外部事实 ID 或来源指纹去重，但允许明确 supersede。

## 44.3 财务幂等

ERP posting 使用：

```text
financial_document_id + posting_revision
```

技术重试不得产生重复应收应付。

---

# 45. 乐观并发与版本控制

适用于可变聚合：

- Quote；
- ChargeAssessment；
- ReconciliationCase；
- PricingChangeSet；
- PricingRelease；
- SettlementRun。

每个聚合保存：

```text
aggregate_version
updated_at
last_command_id
```

并发冲突必须返回显式版本错误，不静默覆盖。

正式不可变版本不通过并发修改，而通过新版本创建。

---

# 46. 领域事件与集成事件

## 46.1 领域事件

领域事件表达聚合内部已经发生的业务事实，可包含较丰富内部引用。

## 46.2 集成事件

集成事件是对外稳定契约，必须：

- 最小必要数据；
- 不泄露采购敏感字段；
- 有独立 schema version；
- 可幂等消费；
- 支持向后兼容演进。

## 46.3 事件信封

```json
{
  "event_id": "...",
  "event_type": "RatingEvaluationCompleted",
  "schema_version": 1,
  "tenant_id": "...",
  "aggregate_id": "...",
  "aggregate_version": 3,
  "occurred_at": "...",
  "correlation_id": "...",
  "causation_id": "...",
  "trace_id": "...",
  "payload": {}
}
```

## 46.4 Outbox / Inbox

- 聚合写入和 Outbox 同事务；
- 消费者使用 Inbox 去重；
- 不声称消息中间件提供业务 exactly-once；
- 业务 exactly-once 通过幂等语义实现。

## 46.5 事件保留

需要长期保留：

- 正式价格激活；
- RatingEvaluation 完成；
- Quote 接受；
- ChargeAssessment 最终确认；
- Financial posting；
- Settlement approval；
- Reconciliation resolution；
- 权限与发布审批。

# 47. Process Manager

以下流程适合 Process Manager：

## 47.1 PricingReleaseActivationProcess

协调：审批、编译、缓存预热、原子激活、健康检查和回滚。

## 47.2 AssessmentPostingProcess

协调：Assessment finalized、Financial document 创建、ERP posting 和失败重试。

## 47.3 CarrierReconciliationProcess

协调：Invoice seal、匹配、差异、人工审核、争议和调整 Assessment。

## 47.4 SettlementProcess

协调：收集、冻结、计算、审批、调整认定和财务入账。

Process Manager 不拥有核心业务事实，只保存流程状态和关联 ID。

```text
ChargeDefinitionVersion(s)
```

- 版本不可覆盖；
- 必须有 Golden Case。

# 49. CQRS 边界

建议建立独立读模型：

# 50. RatingExplanation 模型

解释输出至少包括：

```text
1. 输入事实
2. 选用了哪个测量事实以及原因
3. 尺寸如何标准化
4. 体积重如何计算
5. 计费重量如何得到
6. Zone/偏远/住宅如何分类
7. 使用了哪张价格表和哪一行
8. 每个费用为何命中或未命中
9. 燃油包含哪些费用
10. 折扣、最低收费和封顶的顺序
11. 汇率与舍入过程
12. 最终总额
13. 全部版本引用
```

解释不得依赖自然语言模型临时生成事实；自然语言可以对结构化轨迹进行展示，但结构化轨迹是权威证据。

# 51. Margin 投影

毛利是查询投影：

```text
SELL RatingEvaluation / Customer ChargeAssessment
-
BUY RatingEvaluation / Buy Cost Assessment
=
Margin
```

必须明确比较口径：

- 预估毛利；
- 实际毛利；
- 已入账毛利；
- 是否包含周期返利；
- 汇率时间；
- 是否包含税费。

毛利不得作为 SELL PricingPlan 内隐式可变字段。

# 第八部分：安全、多租户与数据权属

# 53. 租户隔离

所有业务命令必须携带租户上下文。租户拥有的数据必须包含 `tenant_id`、`OwnershipScope` 或不可变的 `ownership_scope_snapshot`；GLOBAL 参考数据必须显式标记为 GLOBAL，不能以缺失 tenant 字段隐式表示全局。版本聚合即使可从父身份推导归属，也必须在持久化和事件中携带归属快照。

隔离要求：

- 数据库查询自动附加 tenant scope；
- 缓存 key 包含 tenant；
- 消息事件包含 tenant；
- 对象存储路径隔离；
- 搜索索引隔离；
- 日志避免输出完整敏感价格；
- 跨租户管理员操作必须单独审计。

---

# 54. 组织和数据范围

同一 tenant 内可按以下范围控制：

- organization；
- business unit；
- warehouse；
- customer portfolio；
- carrier account；
- pricing plan owner scope。

授权判断同时考虑：

```text
Principal
+ Role
+ Organization Scope
+ Resource Scope
+ Field Policy
+ Business State
```

---

# 55. 敏感数据分类

| 等级 | 数据 | 默认控制 |
|---|---|---|
| 高敏感 | BUY 价格、CarrierAccount、Margin、承运商合同 | 字段级权限、脱敏、访问审计 |
| 中敏感 | SELL 价格、客户折扣、账单差异 | 客户/组织范围隔离 |
| 一般业务 | 产品能力、公开公布价 | 租户内按角色访问 |
| 证据数据 | 发票、测量照片、争议附件 | 对象权限、时效签名、下载审计 |

---

# 56. 职责分离

必须执行：

```text
Pricing Editor ≠ Pricing Approver（高风险变更）
Contract Manager ≠ Finance Poster
Reconciliation Analyst ≠ Dispute Final Approver（超过阈值）
Sales Viewer 默认不可看 BUY Cost
Finance Reviewer 不可修改 PricingPlanVersion
Security Admin 不自动获得价格查看权限
```

例外必须通过时效性授权并审计。

---

# 57. 数据保留与删除

- 正式价格版本、Evaluation、Assessment、Financial 文档和账单按财务/合同要求长期保留；
- 客户主数据删除请求不应破坏财务和审计记录，可进行去标识化；
- 原始证据附件按保留策略归档；
- 不允许物理删除已被正式结果引用的版本；
- 草稿和失败导入可以按策略清理，但保留审计摘要。

# 第九部分：研发落地约束与验收

# 58. Repository 边界

每个聚合根一个 Repository 接口，典型：

```text

PricingPlanVersionRepository
RateTableVersionRepository
```

---

# 59. 应用层约束

应用服务负责：

- 身份认证后的命令接收；
- 加载聚合；
- 调用领域行为；
- 提交事务；
- 写 Outbox；
- 返回 DTO。

应用服务不得：

- 在 Controller 中实现计费公式；
- 绕过聚合直接更新状态字段；
- 直接修改 ACTIVE 版本；
- 把数据库行对象当领域对象；
- 在 Rating 热路径调用人工工作流。

---

# 60. 基础设施层约束

基础设施允许：

- PostgreSQL；
- Redis；
- 对象存储；
- 消息队列；
- Secret Manager；
- 搜索和分析存储。

但领域模型不得依赖具体产品名称。

大型 RateTable、CarrierInvoiceLine 和 ChargeLine 可以采用分区表或列式分析副本，但业务写入必须仍遵循聚合状态和版本约束。

---

# 61. 错误处理

## 61.1 业务错误

返回稳定错误码和结构化详情。

## 61.2 技术错误

- 不转换为错误价格；
- 不生成部分正式 Evaluation；
- 可重试错误与不可重试错误区分；
- 外部系统超时不改变领域事实；
- 技术重试使用同一幂等键。

## 61.3 人工待办

适用于：

- 价卡歧义；
- 未知承运商费用代码；
- 无法匹配账单行；
- 超过自动责任判断阈值；
- 高风险追溯调价。

---

# 62. 性能与模型约束

Rating 热路径：

- 不加载完整合同历史；
- 不扫描全部 RateTable；
- 不同步访问 ERP；
- 不调用非确定性外部服务；
- 使用已编译计划和索引；
- 解释轨迹结构化生成，不进行昂贵的运行时推理。

建议目标：

```text
单包裹 P95 < 50 ms
普通多包裹 Shipment P95 < 100 ms
历史回放一致率 100%
发布切换期间无混合版本
```

性能指标最终由专项技术设计和压测冻结。

---

# 63. 领域模型验收标准

## 63.1 业务验收

- UPS Ground 重量 × Zone 和附加费可表达；
- 国际专线首重续重可表达；
- 国家重量价可表达；
- 不同客户体积除数、部分计泡和舍入可表达；
- 多包裹独立和整票聚合可表达；

- Quote、Assessment 和 Financial 三层无混淆；
- 承运商复称和账单调整可闭环；
- 月度返利不污染实时计费。

## 63.2 模型验收

- 每个业务写入有明确聚合根；
- 每个聚合有不变量；
- 正式版本不可变；
- 跨聚合协作使用事件或应用编排；
- 所有关键事实有权威来源；
- 所有金额有币种；
- 所有重量尺寸有单位；
- 所有历史结果有版本清单；
- 所有财务修正采用冲销或调整；
- 多租户和成本权限明确。

## 63.3 与 V1.2 一致性验收

- 不引入采购到销售的隐式继承；
- 不把 Evaluation 当应收应付；
- 不把 Carrier Invoice billed weight 当物理实重；
- 不把 Scope、Basis、Method 混在一个枚举；
- 不让单票 Rating 依赖月累计状态；
- 不让 Pricing Governance 决定价格业务语义；
- 不让平台替代 ERP 总账；
- 不引入外部执行平台依赖。

# 附录 D：端到端领域示例

## D.1 场景

客户 A 从洛杉矶仓使用 UPS Ground 发送一个住宅包裹：

```text
实际重量：10 LB
尺寸：50 × 20 × 10 IN
目的邮编：90210
计算目的：QUOTE
业务时间：2026-08-03
```

合同规则：

```text
SELL PricingPlan: Customer-A-UPS-Sell-V4
GeometryProfile: UPS-GEO-V1
WeightProfile: divisor 250, MAX, 1 LB ceiling
AggregationProfile: PER_PACKAGE
FuelPolicy: official rate × 80%
Residential surcharge: enabled
AHS Dimension: longest side > 48 IN
AHS dimension minimum billed weight: 40 LB
```

## D.2 Facts & Classification

1. 创建 `RatingInputSnapshot`；
2. 选择 CUSTOMER_DECLARED MeasurementFact；
3. GeometryCalculator 排序尺寸：50、20、10 IN；
4. longest side > 48 IN，生成 AHS_DIMENSION 触发事实；
5. ZoneScheme 计算 Zone；
6. 地址分类为 RESIDENTIAL。

## D.3 Weight

```text
实际重量 = 10 LB
体积重 = 50 × 20 × 10 / 250 = 40 LB
条件最低重量 = 40 LB
计费重量 = MAX(10, 40, 40) = 40 LB
舍入后 = 40 LB
```

## D.4 Rating

1. WEIGHT_ZONE 查询基础价；
2. 命中 RESIDENTIAL；
3. 命中 AHS_DIMENSION；
4. Fuel basis 只包含正式声明的费用；
5. 执行金额舍入；
6. 生成独立 SELL RatingEvaluation。

Evaluation 保存：

- input snapshot；
- measurement selection；
- product/contract/pricing/profile/index versions；
- 每个费用行 basis、method 和 rule reference；
- 总额和解释。

## D.5 Quote

Quote Management 创建 OFFERED Quote：

```text
valid_until = 2026-08-04 23:59:59
price_lock_policy = REPRICE_ON_WAREHOUSE_SHIP
```

Quote 不形成应收。

## D.6 实际履约

仓库 DWS 测得 52 × 21 × 11 IN、11 LB。出库时按合同重算：

- 创建新 MeasurementFact；
- 创建新 RatingInputSnapshot；
- 生成新 CUSTOMER_BILLING Evaluation；
- 原 QuoteVersion 保留；
- Charge Assessment 根据差异和合同政策认定最终客户费用；
- FINALIZED 后形成应收 FinancialChargeDocument。

## D.7 承运商账单

UPS 账单给出 billed weight 45 LB：

- 创建 CarrierAssessmentFact；
- 不覆盖仓库 11 LB MeasurementFact；
- Reconciliation 比较 45 LB 与系统预期；
- 差异超过容差，创建 Case；
- 若承运商计费正确且合同允许补扣，创建 Supplemental Customer ChargeAssessment；
- 若承运商错误，创建 DisputeCase；
- Credit Note 到达后形成贷项认定和财务冲销。

该案例验证：

- 产品、事实、计算、报价、认定、财务和对账边界不混淆；
- 销售和采购价格可独立；
- 物理事实与承运商认定不混淆；
- 历史对象均不可覆盖。

# 附录 E：最终自洽审查

## E.1 价格语义审查

- `PricingPlan` 只表示价格方案，不表示客户合同；
- `RateTable` 是价格方案组件，不是方案本身；
- BUY 与 SELL 是独立价格域；
- COST_PLUS 和 TARGET_MARGIN 通过显式 Evaluation 引用；
- Contract 只绑定和覆盖，不拥有采购价格内容。

**结论：通过。**

## E.2 结果语义审查

- RatingEvaluation 是纯计算；
- Quote 是商业承诺；
- ChargeAssessment 是业务费用认定；
- FinancialChargeDocument 是财务子账或入账指令；
- Settlement 通过调整 Assessment 进入财务；
- Reconciliation 不能直接修改财务账。

**结论：通过。**

## E.3 事实语义审查

- RatingInputSnapshot 冻结上游输入；
- MeasurementFact 保存物理事实；
- CarrierAssessmentFact 保存承运商计费认定；
- ClassificationFact 保存版本化分类；
- 后到事实不覆盖历史计算引用。

**结论：通过。**

## E.4 费用语义审查

- Scope、Basis、Method 分离；
- package 与 shipment 通过 AggregationProfile 控制；
- 燃油、折扣、最低收费通过依赖图排序；
- 费用行保存规则、基数、查表条目和舍入轨迹。

**结论：通过。**

## E.5 时间语义审查

- 正式版本使用 valid time 和 system time；
- Quote 使用 priced_at 和 valid_until；
- Evaluation 冻结具体版本；
- 追溯调价通过新版本和调整处理；
- 历史对象不被当前版本重算覆盖。

**结论：通过。**

## E.6 聚合边界审查

- 每个写操作有唯一聚合根；
- 跨上下文使用 ID、VersionRef 和事件；
- 大型表和账单采用逻辑聚合；
- Process Manager 不拥有核心事实；
- Repository 不承担跨聚合查询。

**结论：通过。**

## E.7 安全审查

- 所有业务命令具有 tenant 上下文，聚合具有明确 OwnershipScope；
- BUY、SELL、Margin 字段权限分离；
- 价格录入和审批职责分离；
- 财务与定价权限分离；
- 承运商账号凭据外置。

**结论：通过。**

## E.8 V1.2 一致性结论

本领域模型没有改变 V1.2 已冻结的核心架构决策，而是将其转换为：

```text
12 个限界上下文
41 类主要聚合根/版本聚合（终审未新增聚合，仅精化状态与值对象语义）
明确的状态机
明确的不变量
明确的跨上下文流程
明确的领域事件和事务边界
```

未发现以下旧问题回归：

- 未引入任何外部执行平台作为核心依赖；
- 未恢复采购到销售的错误继承；
- 未将报价或 Evaluation 直接作为财务账；
- 未将承运商 billed weight 当物理测量；
- 未将单票计费与月累计结算混合；
- 未使用任意脚本作为主规则机制；
- 未让 Governance 或数据库结构反向决定价格业务语义。

## E.9 V1.0.1 终审专项结论

终审额外验证并修正：

- CalculationPurpose 枚举与 V1.2 完全一致；
- 物理事实选择不再混入承运商计费认定；
